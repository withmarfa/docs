# Pages

How pages are placed and wired into the site. `STYLE.md` at the repository root says how they are written, and the root `AGENTS.md` still applies.

This file sits above `content/docs/` on purpose: the docs collection publishes every `.md` and `.mdx` file inside it.

## Placing a page

- Each folder directly under `content/docs/` is a tab, in the order `content/docs/meta.json` gives: Start, Run, Catalog, Build, Reference. `(start)/` and `(reference)/` are folder groups, so their pages sit at the site root (`/files`, `/cli`), and `(start)/index.mdx`, the landing page, is served at `/` itself. `build/`, `run/` and `catalog/` keep their names in the URL, and so does `(reference)/api-reference/`. The Catalog sidebar has three labeled sections: Data (Items, Types, Edges), Events and access, and Integrations (Connectors). The Catalog tab's Types pages sit in a folder group, `catalog/(types)/`, which the sidebar shows as a closed folder named Types. Its own page is `types.mdx` (`pagesIndex` in its `meta.json`, so the folder opens on `/catalog/types`), and it holds Type rules, Display hints and Field kinds and two more folder groups, `(core)/` and `(system)/`, shown as closed folders, "Core types" and "System types". No group adds to an address: a type page stays at `/catalog/note`.
- A new page needs its file and an entry in its folder's `meta.json`. `content/docs/meta.json` orders the tabs. **Every tab opens on a page titled Overview**, listed first in its `meta.json` before any group: `index.mdx` in Start, Run, Catalog and Build, and `reference.mdx` (`/reference`) in Reference. Its description says what the tab covers, and its `headTitle` names it in browser tabs, such as "Run overview". Start then has the groups Get started (Quickstart, Connect your agent) and Concepts; a page that belongs in Build (code against an instance) or Run (an instance and its care, with no code) goes in that folder, under the group a reader would name.
- A slug in `(start)/` or `(reference)/` must not repeat a slug in either group. It must not be a name the Worker answers at the root (`api`, `assets`, `mcp`, `llms`, `llms-full`, `docs-map`, `version`) or a tab folder (`build`, `run`, `catalog`), or `docs`, which `marfa docs` strips as a prefix.
- The Catalog tab lists names and shapes and explains nothing. Each top-level type, core or system, has a page (`src/lib/catalog.test.ts` holds them to `src/generated/catalog/builtin-catalog.json`) that takes its title and description from the type and includes the type's generated file. A core type's page ends with one `## Example` item that the test checks; Marfa writes system items itself, so their pages have none. Add a type's page, in the folder of its family and in that folder's `meta.json`, when marfa ships a type, and leave explanation to Start, Run and Build. Include `catalog/edge-types.md`, `permissions.md` and `event-types.md` on Catalog pages only; every other page links to the Catalog page.
- The header tabs come from `SECTIONS` in `src/components/section-nav.tsx`, not from `meta.json`. A new tab, a renamed tab or a moved landing page needs both, and `src/lib/site-links.test.ts` fails until each pill's label matches its tab's `meta.json` title, in order, and opens on a page titled Overview. The Reference tab's Overview has a card for each destination. A new Reference page needs its entry in `(reference)/meta.json`, which the header reads, and a card there when it is a new kind of destination.
- The header holds no text links. The Changelog and the contract sit in the Reference tab's Resources group, so a new destination goes in a sidebar group, not in `links` in `src/lib/layout.shared.tsx`.
- The Reference tab's `meta.json` lifts the API pages into its own sidebar with `...api-reference`, and `src/lib/api-reference-tree.ts` finds the tab by that `meta.json` title. Renaming the title needs `REFERENCE_TITLE` changed there.
- `(reference)/api-reference/` holds only the hand-written overview and Errors pages. Every operation page is generated from `openapi.json`, into the folder `src/lib/source.ts` names.
- An operation page sits at `/api-reference/<group>/<operationId>`, where the group is its tag in lowercase with hyphens for spaces (`/api-reference/api-keys/createKey`). The sidebar and `docs-map.md` list the groups in the order of `tags` in `openapi.json` and each group's operations in that tag's `x-operation-order`; an operation missing from the list sorts last and fails `src/lib/api-reference-tree.test.ts`. A link to an operation page uses that address, and `src/lib/content-lint.test.ts` finds one that does not resolve.
- The API reference's overview draws every operation with `ApiMap`, by area. `src/lib/api-map-areas.json` places each tag of `openapi.json` in one area, and `src/lib/api-map.test.ts` fails when a sync brings a tag that no area holds: add it to the area a reader would look in.
- **A renamed or removed page gets no redirect.** Change every link to it: in pages, components, `src/` (`llms.txt`, the docs MCP server, the docs map), tests, and the other WithMarfa repositories that link to the docs. The content lint finds a page's broken link and `src/lib/site-links.test.ts` one in the site code. When a page's path or title changes, also check what the agent surfaces say about it, including the example path in the `docs_fetch` description in `src/lib/mcp/tools.ts`.

## Wiring a page

- Frontmatter holds a `title` and a `description`, and a `headTitle` where the title repeats another page's (`STYLE.md`, "Frontmatter"). A Catalog type page also holds `identifier`, the type's ID, which the page header and the Markdown copy show.
- A page uses what `src/components/mdx.tsx` registers without importing it. Import anything else from `fumadocs-ui/components/`.
- Show a generated file with `<include cwd>src/generated/<file>.md</include>`, and add `#<heading-id>` for one section, which ends at the next heading of any level. Never copy generated text into a page or show it through a component: the include keeps the Markdown copy and the docs tools in step with the HTML.
- `pnpm test` runs the content lint (`src/lib/content-lint.test.ts`) over every page and the text it includes, and a test that the CLI page is the one page that includes `src/generated/cli/`. Passing them is not the same as following `STYLE.md`.

## Code Review Rules

- **Page not wired.** Flag a page missing from its `meta.json`, a root slug that collides, or a tab change without a matching `SECTIONS` entry.
- **Generated text copied.** Flag a generated table, CLI section or install step written into a page instead of included.
- **Lost in the Markdown copy.** Flag a component a page relies on that `source.config.ts` leaves out of the copy (`STYLE.md`, "Components").
