# Pages

How pages are placed and wired into the site. `STYLE.md` at the repository root says how they are written, and the root `AGENTS.md` still applies.

This file sits above `content/docs/` on purpose: the docs collection publishes every `.md` and `.mdx` file inside it.

## Placing a page

- Each folder directly under `content/docs/` is a tab, in the order `content/docs/meta.json` gives: Home, Use, Run, Build, Catalog, Reference (`STYLE.md`, "Where a page goes", says what each holds). **A page's address starts with its tab's segment, and Home's segment is the root.** `use/`, `run/`, `build/`, `catalog/` and `reference/` keep their names in the URL (`/use/sync-a-folder`, `/reference/cli`, `/reference/api/items/listItems`). `(home)/` is a folder group, so its pages sit at the root: the landing page `(home)/index.mdx` at `/`, then `/quickstart`, `/connect-your-agent`, `/how-marfa-works`, `/glossary`, `/changelog` and `/get-help`. Home's sidebar has two groups, Get started and Resources, and the Glossary, Changelog and Get help are ordinary Home pages in it. `src/lib/addresses.test.ts` fails a page whose address does not follow its tab, so a new page goes in the folder of the tab it belongs to.
- A page whose title is too long for the sidebar can set `sidebar_label` in its frontmatter. The sidebar and the breadcrumb show it in place of the title, because both read the page tree and the reader has just followed the sidebar's names; the previous and next cards, the heading, search, `llms.txt`, the Markdown copy and the page metadata keep the full title (`src/lib/sidebar-label.ts`). Leave it out unless the title wraps.
- **No tab has a landing page.** Each tab's `meta.json` starts with its first real page or a `---Group---` separator, and the tab opens on the first page its sidebar lists. Don't add an index of cards for a tab or a group.
- A new page needs its file and an entry in its folder's `meta.json`, under the group a reader would name. Build lists its concept pages first, under Concepts, and each one is a `concept` page: give it `kind: concept` in its frontmatter, or an entry in `src/lib/page-limits.json`. A page named `fix-*` is a fix page.
- The Catalog is a tab of its own, the root folder `catalog/`, with the same addresses as before (`/catalog/note`). The Types pages sit in a folder group, `catalog/(types)/`, which the sidebar shows as a closed folder named Types. Its own page is `types.mdx` (`pagesIndex` in its `meta.json`, so the folder opens on `/catalog/types`), and it holds Type definition and Field kinds and two more folder groups, `(core)/` and `(system)/`, shown as closed folders, "Core types" and "System types". No group adds to an address: a type page stays at `/catalog/note`.
- A slug in `(home)/` must not be a name the Worker answers at the root (`api`, `assets`, `mcp`, `llms`, `llms-full`, `docs-map`, `version`), a tab folder (`use`, `run`, `build`, `catalog`, `reference`) or `docs`, which `marfa docs` strips as a prefix. The docs API also resolves a single name that is no path, such as `connect-your-agent` or `cli`, to the page whose address ends in it (`findPage` in `src/lib/source.ts`): the page nearest the root wins, and two at one depth find none. That keeps names that the install message and `marfa docs` print working; it is a lookup and the site has no redirect, so a link always uses the full address.
- The Catalog lists names and shapes and explains nothing. Each top-level type, core or system, has a page (`src/lib/catalog.test.ts` holds them to `src/generated/catalog/builtin-catalog.json`) that takes its title and description from the type and includes the type's generated file. A core type's page ends with one `## Example` item that the test checks; Marfa writes system items itself, so their pages have none. Add a type's page, in the folder of its family and in that folder's `meta.json`, when marfa ships a type, and leave explanation to Build. Include `catalog/edge-types.md`, `permissions.md` and `event-types.md` on Catalog pages only; every other page links to the Catalog page.
- The header tabs come from `SECTIONS` in `src/components/section-nav.tsx`, not from `meta.json`. Each pill's `href` is the first page of its tab's sidebar. A new tab, a renamed tab or a new first page needs both, and `src/lib/site-links.test.ts` fails until each pill's label matches its tab's `meta.json` title, in order, and opens on that first page. A page belongs to the tab whose segment its address starts with, and to Home when it starts with none, so a new tab needs its segment in `SECTIONS` too.
- The Reference tab's `meta.json` lifts the API pages into its own sidebar with `...api`, and `src/lib/api-reference-tree.ts` finds the tab by that `meta.json` title. Renaming the title needs `REFERENCE_TITLE` changed there.
- `reference/api/` holds only the hand-written overview page, and `reference/errors.mdx` is the Errors page, listed in the tab's `meta.json` before the operation groups. Every operation page is generated from `openapi.json`, into the folder `src/lib/source.ts` names.
- An operation page sits at `/reference/api/<group>/<operationId>`, where the group is its tag in lowercase with hyphens for spaces (`/reference/api/api-keys/createKey`). The sidebar and `docs-map.md` list the groups in the order of `tags` in `openapi.json` and each group's operations in that tag's `x-operation-order`; an operation missing from the list sorts last and fails `src/lib/api-reference-tree.test.ts`. A link to an operation page uses that address, and `src/lib/content-lint.test.ts` finds one that does not resolve.
- The API reference's overview draws every operation with `ApiMap`, by area. `src/lib/api-map-areas.json` places each tag of `openapi.json` in one area, and `src/lib/api-map.test.ts` fails when a sync brings a tag that no area holds: add it to the area a reader would look in.
- A connector page under `catalog/connectors/` is a generated header, included from `src/generated/connectors/<name>.md`, followed by the hand-written sections, and is keyed by the connector's `name`. Add a connector by running `scripts/sync-from-plugins.sh`, which writes the page's first version with a generated `description` and `job` line; write its sections after the include, and replace the generated `description` and `job` with your own. The folder's `meta.json` lists no `pages`: the sidebar orders the connectors by file name, and the sync never writes it. Say how many connectors there are nowhere: the content lint fails a number before "connector" and a list shows what exists.
- Icons mean something and appear nowhere else: a Catalog type's page heading and its row in a list of types show the type's `display_hints.icon`, and a connector shows its `sourceMark`. `remarkIcons` (`src/lib/remark-icons.ts`) draws them at build time from the pinned `@iconify-json/lucide` and `@iconify-json/simple-icons`, and refuses an ID the contract does not allow, so a page never calls an icon API. A table's "Mark" column of icon IDs, and a first-cell link to a type, get the icon on their own. A type or connector with no icon shows none. Never add an icon to a callout, a card or a heading.
- **A renamed or removed page gets no redirect.** Change every link to it: in pages, components, `src/` (`llms.txt`, the docs MCP server, the docs map), tests, and the other WithMarfa repositories that link to the docs. The content lint finds a page's broken link and `src/lib/site-links.test.ts` one in the site code. When a page's path or title changes, also check what the agent surfaces say about it, including the example path in the `docs_fetch` description in `src/lib/mcp/tools.ts`.

## Wiring a page

- Frontmatter holds a `title` (at most 12 words), a `description` (at most 40) and a `job` line (a page in `pending` may lack one until its rewrite), a `kind` where the folder does not decide it, and a `headTitle` where the title repeats another page's (`STYLE.md`, "Naming"). A Catalog type page also holds `identifier`, the type's ID, which the page header and the Markdown copy show.
- A page uses what `src/components/mdx.tsx` registers without importing it. Import anything else from `fumadocs-ui/components/`.
- Show a generated file with `<include cwd>src/generated/<file>.md</include>`, and add `#<heading-id>` for one section, which ends at the next heading of any level. Never copy generated text into a page or show it through a component: the include keeps the Markdown copy and the docs tools in step with the HTML.
- `pnpm test` runs the content lint (`src/lib/content-lint.test.ts`) over every page and the text it includes, and a test that the CLI page is the one page that includes `src/generated/cli/`. Passing them is not the same as following `STYLE.md`.

## Code Review Rules

- **Page not wired.** Flag a page missing from its `meta.json`, a root slug that collides, or a tab change without a matching `SECTIONS` entry.
- **Generated text copied.** Flag a generated table, CLI section or install step written into a page instead of included.
- **Lost in the Markdown copy.** Flag a component a page relies on that `source.config.ts` leaves out of the copy (`STYLE.md`, "Components").
