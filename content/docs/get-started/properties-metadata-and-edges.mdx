- **Properties**, here `title` and `body`, are inside the note. The note's type, `core.note`, defines them. [Update an item](/api-reference/items/updateItem) writes them, and each write raises the note's version by one.
- **Tags**, here `favorite`, are in the note's metadata record. You or an app choose them freely, with no schema. [Add tags to an item](/api-reference/metadata/addItemTags) writes them, and the note's version stays as it is.
- **Extensions**, here the `com.example.reader` namespace, are in the metadata record too. The app that writes a namespace decides what it holds. [Replace an extension namespace](/api-reference/extensions/replaceItemExtension) writes one, and the note's version stays as it is.
- **An `about` edge** joins the note to a book, a `core.media.book`. The edge type `about` defines it: any item can be about any other. [Create an edge](/api-reference/edges/createEdge) writes it. The edge has its own version, so the note's stays as it is.
- **A `parent-of` edge** joins the note to a child note. The edge type `parent-of` defines it: an item has one parent at most, and trashing the parent trashes its children. It also has its own version.

## Properties

Properties are an item's own content: named values such as a note's `title` and `body`.

The item's type defines them: each property's name and shape, and which ones are required, as [Items and types](/get-started/items-and-types) explains. A property the type doesn't declare is kept, unless strict mode is on for that type.

An update names the `version` it read, and the properties it sends are laid over the ones the item has. Each update raises the item's `version` by one, and Marfa keeps a snapshot of the properties as they were.

```http
PATCH /items/{id}
Content-Type: application/json

{ "version": 3, "properties": { "title": "Reading list" } }
```

The note comes back at `version` 4, with its `body` unchanged.

## Metadata

Every item has a metadata record beside it, which holds its tags and its extensions. Neither is a property. A write to either leaves the item's `version` as it is and moves its `updated_at`, and Marfa announces it as `metadata.changed`. Writing either needs write on the item's type.

### Tags

A tag is a free-form label, such as `favorite`. Tags are flat, with no hierarchy and no schema, so you or an app decide which to use. An item's tags are a set: a tag written twice is kept once. A search matches tags along with an item's text.

You can send `tags` when you [create an item](/api-reference/items/createItem), and change them later with the [Metadata](/api-reference/metadata/getItemMetadata) operations:

```http
POST /items/{id}/tags
Content-Type: application/json

{ "tags": ["favorite"] }
```

### Extensions

An extension is a JSON object stored on an item under a namespace. It holds what an app keeps about an item that something else wrote: a reading app can keep your place in an article that a connector brought in.

The app that writes a namespace decides what goes in it, and Marfa requires only a JSON object. Writing one namespace leaves the others alone, and `core`, `marfa` and `system` are reserved. A credential's permissions name the namespaces it can read and write, and it sees only the namespaces it can read. [Keys and permissions](/get-started/keys-and-permissions) explains permissions.

```http
PUT /items/{id}/extensions/com.example.reader
Content-Type: application/json

{ "position": 0.42 }
```

## Edges

An edge is a typed, directed relationship from a source item to a target item, such as a note `about` a book. It's a record of its own, with its own `id`, `properties` and `version`, so writing it leaves both items' versions as they are. Writing an edge needs write on its source item's type and on its edge type.

An edge starts at version 1, and each update raises it by one. You can also send `edges` when you create or update an item, and an update that carries only `edges` leaves the item's version as it is.

### Edge types

An edge's type defines it. Marfa ships ten edge types, such as `about`, `parent-of`, `references` and `in-folder`, and you can [register more](/api-reference/edge-types/registerEdgeType). An edge type sets these:

| What it sets | For example |
| --- | --- |
| Cardinality: how many edges of the type each end can hold | `parent-of` is `one-to-many`, so an item has one parent at most. |
| The item types each end can be | `in-folder` joins any item to a `system.folder`. |
| What trashing an item does across the edge: `cascade`, `orphan` or `block` | Trashing a parent trashes its children, and trashing a note leaves the book it's `about`. |
| The edge's own properties | An `in-thread` edge carries a `position`. |
| A reverse name: the edge's name read from its target | A `parent-of` edge reads as `child-of` from the child. |

A `block` edge refuses the trash of either item it joins.

## What moves the version

Only a write to an item's own fields moves its version: its properties, `type`, `tier`, `occurred_at` and `source_id`. Tag, extension and edge writes leave it alone, so they don't make another writer's pending update stale: a title changed in one app and a tag added in another both land. [Changes over time](/get-started/changes-over-time) covers versions, snapshots and conflicts.

The rules behind this page are in the [items](https://github.com/withmarfa/marfa/blob/main/conformance/spec/items.md) and [edges](https://github.com/withmarfa/marfa/blob/main/conformance/spec/edges.md) chapters of the contract.
