This page starts a trial instance on your own machine. To run one you keep, see [Deploy](/guides/deploy).

You need:

- Node.js 22.12 or later, [pnpm](https://pnpm.io/installation) and Git.
- The `marfa` command, installed as [The marfa command](/tools/marfa-command#install) describes. The browser route below doesn't need it, but the key step does.
- On Linux, the `acl` package, which the server uses to check who may reach its private socket.

## Start the server

Clone the repository, build it, and start the server:

```bash
git clone https://github.com/withmarfa/marfa.git
cd marfa
pnpm install
pnpm build
cd packages/server
export MARFA_AUTH_SECRET="$(openssl rand -hex 32)"
pnpm dev
```

The server listens on `http://localhost:8600`. It creates its data under `packages/server/data` the first time it starts, as [Where the data lives](#where-the-data-lives) describes.

A new instance has no owner, so the server prints a setup code in its log:

```text
Claim this Marfa at /setup with setup code: U3HCA-6SVZS-XA236-4SVTY-OHH5T-Q
```

The setup code lets one person claim the instance. It gives no access to the API. The server makes a new code each time it starts while the instance is unclaimed, and `marfa setup code` makes one on demand and ends the earlier code.

### What the server needs to start

A trial instance needs no setting. The server reads its settings when it starts, and if one is outside its rule it exits with status 1 and names every such setting. These are the ones to know:

<ReferenceList description={2}>

| Setting | Default | What it does |
| --- | --- | --- |
| `MARFA_AUTH_SECRET` | A random value for each start | Signs sign-in cookies and links. Use at least 32 characters. Set it, as above, so the apps you sign in keep working after a restart. |
| `API_KEY_SALT` | A built-in value | Hashes keys and access tokens. Changing it ends every key and token. |
| `MARFA_AUTH_BASE_URL` | `http://localhost:<PORT>` | The public URL of the instance, which is also the OAuth issuer. |
| `NODE_ENV` | `development` | Set to `production` and the server refuses to start without `MARFA_AUTH_SECRET`, `API_KEY_SALT` and `MARFA_AUTH_BASE_URL`, and refuses a short or predictable secret or salt. |
| `PORT` | `8600` | The port the server listens on. |

</ReferenceList>

Make a secret or salt with `openssl rand -hex 32`. [Settings](/guides/settings) lists every setting, and the rules are in the settings table of the [instance chapter](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#settings) of the contract.

## Claim the instance

Claiming makes you the owner. It happens once: after it, a second claim is refused with `409 owner_exists`. The commands from here on run in a second terminal, in `packages/server`, as the account that runs the server.

Choose one way.

### In the browser

1. Open a single-use link from the machine that runs Marfa:

   ```bash
   unset MARFA_API_URL MARFA_API_KEY
   marfa --socket "$(pwd -P)/data/control/marfa.sock" setup open
   ```

   `--socket` makes the command act with the machine's own authority through the instance's private socket. The command opens the link in your browser, and the link stops working after five minutes. Add `--no-browser` to print it instead.

2. In the browser, choose the owner's email and a password.

Without the command, open `http://localhost:8600/setup` and enter the setup code from the log first. Marfa allows ten wrong codes from one address in fifteen minutes and then answers `429 rate_limited`; a link from `marfa setup open` still works.

### In the terminal

```bash
unset MARFA_API_URL MARFA_API_KEY
marfa --socket "$(pwd -P)/data/control/marfa.sock" setup claim --email owner@example.com
```

The command asks for the password without echoing it. For a script, `setup claim --stdin` reads a JSON object with `email`, `password` and an optional `name` instead. Pass secrets by prompt or standard input, never as arguments.

The owner signs in to the browser at `http://localhost:8600/auth/sign-in`. If you lose the password, `marfa --socket <path> owner recover` sets a new one, and keys and signed-in apps keep working. [Keys and permissions](/get-started/keys-and-permissions) explains what the owner can do and what it can't.

## Make your first key

The owner manages the instance but reads and writes no items. For that, mint a key. With the socket, the owner can give a key anything:

```bash
marfa --socket "$(pwd -P)/data/control/marfa.sock" keys create \
  --label laptop --source laptop \
  --type-permission '*=write' --edge-permission '*=write' \
  --metadata-permission '*=write' --extension-permission '*=write' \
  --profile-permission '*=write'
```

The command prints the key, which begins `marfa_k1_`, once. Each key has its own `--source`, which Marfa stamps on the items the key writes, and no two keys share one.

This key reads and writes every type, edge type, extension namespace and profile field, and holds none of the twelve named permissions. Give a script or an app only what it needs: [Keys and permissions](/get-started/keys-and-permissions) explains each map, and [Create an API key](/api-reference/access/createKey) has every field. You can also make a key in the browser, signed in as the owner.

Keep the key where the `marfa` command finds it, and point the command at the instance. The command asks for the key and stores it in your keychain:

```bash
marfa --url http://localhost:8600 keys keep
```

Paste the key and press Return. The command checks the key against the server before it keeps it. Without a keychain, set `MARFA_API_URL` and `MARFA_API_KEY` instead. [The marfa command](/tools/marfa-command#choose-a-server-and-a-credential) explains the order the command looks in.

## Check that the instance answers

```bash
marfa status
```

```text
server http://localhost:8600
instance 01a12188-2c98-7829-ab4f-7e93cbbb16e5 (marfa dev)
health ok
credential from keychain
items {}
```

`status` shows what the instance says about itself, which [Describe the instance](/api-reference/instance/getInstance) answers without a credential, its health, the credential the command used, and how many items that credential reaches. The count stays empty until you write an item, as [Your first items](/get-started/first-items) does.

A request to `/health` needs no credential either. It answers `200` with the status of four components, `database`, `database_write`, `disk` and `blob_storage`, and `503` if any is down.

## Where the data lives

The instance is one SQLite file and a folder of blobs, so there is no database to install. The server reads these locations from its settings, and a relative path starts from the directory where the server runs:

| What | Setting | Default |
| --- | --- | --- |
| The database | `SQLITE_PATH` | `./data/marfa.db` |
| The blobs | `BLOB_PATH` | `./data/blobs` |
| The private socket | `MARFA_CONTROL_SOCKET` | `control/marfa.sock` beside the database |

A socket path must be absolute and at most 103 bytes. [Back up and restore](/guides/back-up-and-restore) covers copying an instance.

The rules behind this page are in the [instance claim](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance-claim.md) and [instance](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md) chapters of the contract.
