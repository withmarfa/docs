## A file is an item and a blob

A file comes in two parts. The **blob** is the bytes, stored once under the SHA-256 hash of their content. The **file** is an item whose type inherits from `core.file`, and its `blob_ref` names the blob by that hash. An item refers to a blob and never contains one.

[Upload a blob](/api-reference/blobs/uploadBlob) sends the bytes as the request body, under the media type they are:

```http
POST /blobs
Content-Type: image/jpeg

<the bytes of the photo>
```

Marfa answers the blob's `hash`, its `size_bytes` and the `mime_type` it serves the bytes under:

```json
{ "hash": "sha256:d71b77fe25721711f07e19c5f39e768e1356349c08b58260a42ed97eb996a01b", "mime_type": "image/jpeg", "size_bytes": 13 }
```

Then an item names the hash:

```http
POST /items
Content-Type: application/json

{ "type": "core.file.image", "properties": { "title": "Holiday photo", "blob_ref": "sha256:d71b77fe25721711f07e19c5f39e768e1356349c08b58260a42ed97eb996a01b", "mime_type": "image/jpeg" } }
```

The same bytes uploaded again answer the same hash and are stored once, so two files can share a blob. The first upload fixes the media type the bytes are served under. Marfa sets the file's `size_bytes` itself, from the bytes, and ignores any size a write sends.

## What keeps a blob

A hash anywhere in a string counts as a reference to the blob: a whole `blob_ref`, a `sha256:` link inside a Markdown body, the same link URL-encoded, or the 64 hexadecimal characters alone. A blob is kept as long as something names it. Select a piece to see what keeps the blob and who it lets read it.

<FileMap />

- **A file item**, or any other item, in any state, the bin included. It can lend the blob's read to a credential that may read the item's type.
- **An edge's properties.** They can lend the read to a credential that may read the edge's type and its source item's type.
- **An extension namespace.** It can lend the read to a working key that may read the namespace and the item's type.
- **An earlier version** in an item's history. It keeps the blob but lends no read.
- **A queued bulk action** whose `update_properties` patch names the hash, until the job ends. It lends no read.
- **The blob** is the bytes, with their size and the media type of their first upload.
- **The disk** beside the server holds every upload, on every instance.
- **An object store**, an S3-compatible bucket the instance is configured with, holds a copy of every blob once the `blob-replicate` housekeeping job has run.

## Who may read a blob

Knowing a hash isn't enough to read the bytes. A reference lends the blob's read only if whoever wrote it had uploaded the bytes or could already read them, so naming a hash you found somewhere gives you nothing. A reference keeps the standing it was written with: a later write that leaves the hash in place neither grants nor withdraws it.

A blob that nothing names can't be read yet, even by the credential that uploaded it, because the upload's answer already told it everything. A blob the credential may not read answers `404 blob_not_found`, exactly as an unknown hash does. The operator key reads every blob.

## Downloading

[Download a blob](/api-reference/blobs/downloadBlob) answers the bytes, unchanged, and takes a `Range` header for part of them. Marfa always sends a blob as an attachment and in a sandbox, so a browser never shows its bytes as a page of the instance, whatever its media type.

[Get a blob URL](/api-reference/blobs/getBlobUrl) answers a link that serves the bytes to a request with no credential, such as an image element in a page. A link lasts an hour unless you ask for another lifetime, up to seven days, and it keeps working for its whole lifetime even if the key that asked for it is revoked. Once an object store holds the blob, the link is the store's own, so the bytes don't pass through the instance.

## Where the copies live

A store is a place a blob's bytes live. Every instance has the disk store, a directory beside the server, and every upload lands there. Configure an object store with `S3_BUCKET` and the other `S3_` settings, and the instance attaches it as a second store.

Every store wants every blob. The `blob-replicate` housekeeping job copies each blob to every attached store that lacks it, straight after an upload and on its interval. The `blob-integrity` housekeeping job checks the copies: a copy it finds missing or altered is struck, and the next replication puts it back from a store that holds it. [List a blob's locations](/api-reference/blobs/listBlobLocations) shows which stores hold a blob and when each copy was last checked.

## When nothing names a blob

The `blob-orphans` housekeeping job finds blobs that nothing names. It reports each one first, and a later run purges it only once it has stood in the report longer than the grace, `MARFA_BLOB_CLEANUP_GRACE_MS` (1 day by default). An upload or a write that names the hash in between takes it off the report. [List orphaned blobs](/api-reference/blobs/listBlobOrphans) shows the report to the operator key.

Trashing a file keeps its blob, because an item in the bin still names it. Purging the file removes its history too, so once nothing else names the hash, the blob goes after the grace. [Housekeeping](/guides/housekeeping) covers the jobs, and [Handle files](/guides/handle-files) walks through uploading and downloading from an app.

The rules behind this page are in the [blobs](https://github.com/withmarfa/marfa/blob/main/conformance/spec/blobs.md) and [stores](https://github.com/withmarfa/marfa/blob/main/conformance/spec/stores.md) chapters of the contract.
