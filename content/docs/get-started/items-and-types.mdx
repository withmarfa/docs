## Items

An item is one record in Marfa, such as a note, a task, a photo or a message. Everything else hangs off items: tags, extensions and edges attach to one, as [Properties, metadata and edges](/get-started/properties-metadata-and-edges) explains.

Whatever its type, every item has the same fixed parts:

| Part | What it holds |
| --- | --- |
| `id` | The item's UUIDv7. Marfa mints one, or keeps the one a client sends. |
| `type` | What the item is, such as `core.note`. |
| `properties` | The item's content, as named values that its type checks. |
| `state` | Where the item is in its lifecycle: `active`, `archived` or `trashed`. A `system.*` item is `active` or `revoked`. |
| `tier` | Which layer the item sits in: `library` or `feed`. |
| `occurred_at` | When the thing the item records happened, in UTC. It defaults to when the item was created. |
| `version` | Starts at 1, and goes up by one each time the item's properties, type, tier, `occurred_at` or `source_id` change. |
| `source` and `source_id` | The source the item was written under, and the item's identifier at that source. Together they're the item's natural key. |

[Get an item](/api-reference/items/getItem) lists the rest, such as `created_at` and `schema_version`.

This request creates a note from a type and its properties:

```http
POST /items
Content-Type: application/json

{ "type": "core.note", "properties": { "title": "Reading list", "body": "Start with the essays." } }
```

Marfa fills in the rest: a new `id`, `state` `active`, `tier` `library`, `version` 1, and an `occurred_at` of when the note was created.

## Types

A type is the schema for an item's properties. It declares each property's name and shape, and which ones are required. Marfa checks every write of an item's properties against the item's type.

`core.note` requires `body`, so Marfa refuses this note with `400 invalid_properties` and names `body` in `details.errors`:

```http
POST /items
Content-Type: application/json

{ "type": "core.note", "properties": { "title": "Reading list" } }
```

A type identifier has two or more segments separated by dots, and at most 128 characters. Each segment starts with a lowercase letter and holds only lowercase letters, digits, hyphens and underscores. The first segment is the namespace, which says who adds types there:

| Namespace | Identifiers | Who adds types |
| --- | --- | --- |
| `core` | `core.note`, `core.file.image` | Marfa ships them. No credential can register, replace or delete one. |
| `system` | `system.connection`, `system.folder` | Marfa ships them. Their items are written only through their own operations, such as creating a folder. |
| `marfa` | None | Reserved for Marfa. No credential can register a type here. |
| `app` | `app.<app-name>.<type>`, exactly three segments | An app, for its own types. |
| `user` | `user.<type>`, such as `user.recipe` | You, for your own types. |
| A publisher | `<publisher>.<type>`, such as `acme.deal` | Anyone publishing types for others to use, such as a connector's types for the service it reads. |

Nothing ties an `app`, `user` or publisher namespace to one app or person: a credential can register any identifier there that its type map reaches. A publisher's first segment can't be a word Marfa reserves for its permissions, such as `items` or `keys`, and the [types chapter of the contract](https://github.com/withmarfa/marfa/blob/main/conformance/spec/types.md#typesid-reserved-scope-root) lists them all. To register a type of your own, follow [Define a type](/guides/define-a-type).

## Inheritance

A type can name another type as its `parent`. Its items then take every property the parent declares, the parent's required properties stay required, and the type adds properties of its own. A child can redeclare an inherited property with a new `description`, or make an optional one required, but it can't change the property's shape: Marfa refuses that with `400 inheritance_violation`. A type can have at most ten ancestors, and [Get a type](/api-reference/types/getType) answers a type with everything it inherits.

Files show how this works. `core.file` requires `blob_ref` and `mime_type`, and a file is any item whose type inherits from `core.file`, as [Files](/get-started/files) explains. `core.file.image` is a child of `core.file` that adds `width`, `height` and a location, and an app can register a child of its own under it.

A listing that names a type also returns the items of the types under it: each type whose identifier starts with the type's identifier and a dot, such as `core.file.image`, and each type whose chain of `parent` reaches it, such as an app's child type. This request lists every file, images included:

```http
GET /items?type=core.file
```

### Compatible types

A child can never give an inherited property another shape, so inherit only when every property of the parent means what it should for your type. When your type should be readable as another type without taking all of its properties, name the other type in `compatible_with` instead.

Marfa checks the claim when you save the type. Your type has to require every property the target requires, and each property it shares with the target has to be readable as the target's. A claim that doesn't hold is refused with `422 compatible_with_violation`. A compatible type inherits nothing, and a listing of the target leaves its items out.

- **`core.file`** is a `core` type: Marfa ships it, and no credential can register, replace or delete it. A file is an item whose type inherits from it.
- **`core.file.image`** is shipped and locked too. Its `parent` is `core.file`, so an image has every file property and adds its own.
- **`app.example.receipt`** is an example of an app's own type, with `core.file.image` as its `parent`. It inherits from `core.file` too, so a listing of `core.file` includes receipts. A credential whose type map reaches it can register and change it.
- **`core.note`** is shipped and locked, and requires `body`.
- **`user.recipe`** is an example of your own type. It names `core.note` in `compatible_with`, so it inherits nothing, has to require `body` as a note does, and is left out of a listing of `core.note`. A credential whose type map reaches it can register and change it.

## Feed and library

An item's tier says which layer it sits in:

- **`feed`** holds what arrives in volume and as it came, from connectors and capture, under the source's own type. It's transitory until it's promoted or archived.
- **`library`** holds what a person chose to keep, in a core type or a child of one.

A tier isn't a permission and isn't a lifecycle state. A new item takes the tier its write names, or else its credential's `default_tier`, or else `library`. `PATCH /items/{id}` with a `tier` moves an item. A listing returns both tiers unless it names one:

```http
GET /items?tier=feed
```

To promote a feed item is to make a library item from it: a copy in a core type, made by a person or an app, with a `derived-from` edge back to the feed item, which stays as it came. For that, the feed item's type has to be readable as a core type, through `parent` or `compatible_with`.

## Access by type

A credential's type map names the types it can read and the types it can write, so a type is also what access is granted to. Inheritance doesn't widen a type map: one that reaches `core.file` doesn't reach `core.file.image`, or an app's child of it, unless it names those types too. The types themselves are open to every credential, which can read the whole registry with [List types](/api-reference/types/listTypes). [Keys and permissions](/get-started/keys-and-permissions) explains credentials, their maps and their permissions.

The rules behind this page are in the [items](https://github.com/withmarfa/marfa/blob/main/conformance/spec/items.md) and [types](https://github.com/withmarfa/marfa/blob/main/conformance/spec/types.md) chapters of the contract.
