An app built on the [Swift package](/tools/swift-package) is a device, and so is the [`marfa` command](/tools/marfa-command). A device reads from a copy of part of an instance and writes through a queue, so it works without a connection. A folder is a device whose face is a directory.

## What a device keeps

A device keeps a working copy and a queue, and follows one instance. The instance is the truth: the copy is a copy, not a peer. Select a piece to see what it holds and which operations reach it.

<DeviceMap />

- **Instance.** A device reads its items with [List items](/api-reference/items/listItems) to hydrate, follows [Stream change events](/api-reference/event-stream/streamEvents) to catch up, and sends each queued write to the operation that makes it, such as [Update an item](/api-reference/items/updateItem).
- **Working copy.** A local replica of a **slice** of the instance: the types it names and the types under them, a tier (`library`, `feed` or both), and any edge types the device holds whole. Listings, searches and reads answer from the copy. A **pin** holds one item by ID whatever the slice says of it.
- **Queue.** Every write the device makes shows in the copy at once and waits in the queue until the instance answers it. The queue outlives the process that made it.
- **Directory.** A folder's files, on a Mac. [Folders](#folders) covers it.

## How the copy stays current

A copy is filled once and then kept current from the instance's event log.

- **Hydrate.** The device reads the log's head, then the item listing for each type in the slice, in the slice's tier and in every state, with each item's edges and tags. It then applies the events written while it read. Hydrating replaces the copy and keeps the queue and the pins.
- **Catch up.** The device opens the event stream at its cursor and takes each event until the stream says it has reached the head. It skips an event older than the item it holds, lets go of an item that has left the slice by type or tier, and adds one that has entered it. Every event, taken or skipped, moves the cursor past it.
- **Follow.** A device can hold the stream open and apply events as they arrive. A stream that drops opens again from the cursor after a wait that grows each time, up to 30 seconds, and a refusal no retry changes, such as a refused credential, ends it.

A copy **expires** when it can no longer be kept current from where it stands: the log has dropped the event after its cursor (the instance keeps events for its event log retention), the log ends behind the cursor because the instance was restored from an earlier point, another instance answers at the same address, or the read view the copy was certified under changed. An expired copy refuses reads and writes with `hydration_incomplete` until the next hydration replaces it. The queue survives. [Staying in step](/get-started/staying-in-step) explains the event stream and read views.

## Working offline

A copy that has hydrated answers every read with no connection. A device that has never hydrated reads what it holds and still queues writes.

- **A write is queued the moment it is made.** The queue gives it an idempotency key then, and keeps the same key on every retry, so a retry whose answer was lost doesn't write twice.
- **Writes go in order.** A drain sends the queue in the order the writes were made. A write to an item waits for the earlier unanswered writes to that item, and a write to an item the device just created waits for the create. A held write goes in the same drain once what it waits for is answered.
- **An unreachable instance counts for nothing.** A dropped connection, a timeout, a `5xx`, a `408`, a `425` or a `429` leaves the write unanswered and uncounted, and the drain ends there.
- **An update names a version.** A device refuses to queue an update that names no version, and sends each property an edit names with the whole value its caller gave it. It resolves no collision itself: two values for one field are the instance's to reconcile.

## What a verdict is

A **drain** sends the queue once. The instance's answer to each write gives it one of six verdicts, and no write has more than one.

| Verdict | When the write gets it | What the device does next |
| --- | --- | --- |
| `accepted` | The instance applied the write as sent. | Reads the item or edge again, holds what comes back, and never sends the write again. |
| `merged` | The instance applied the write over changes made since, field by field, and names the fields. | The same. |
| `conflicted` | The instance kept its own text and put the write's in a new conflicted copy, and names the copy. | The same. The copy reaches the working copy with the event stream, not with the verdict. |
| `refused` | The instance refused the write with an error that names the contract, such as `validation_error`. | Keeps the answer whole with the write and reads the item again. Sends the write again only if it is released. |
| `blocked` | Something outside the queue has to change first. | Keeps the write laid over the item and sends nothing for it. |
| `dead` | Five failures that count have been counted against it. | Stops sending it until it is released. |

Only three kinds of failure count against a write: a success whose body the device can't read, a `409 idempotency_key_in_flight`, and a failure of the device's own store. An unreachable instance never counts.

A `blocked` write carries one of five reasons.

| Reason | Cause | How it ends |
| --- | --- | --- |
| `credential_refused` | The instance refused the credential with `401`, or refused a write because the credential lacks a grant. | The next drain tries it again. |
| `key_spent` | The instance answered `422 idempotency_key_reused`. | An app releases it. |
| `ancestor_unavailable` | The instance no longer keeps the version the write was based on (`409 ancestor_unavailable`). | An app withdraws or releases it. |
| `conflict_unresolved` | The instance answered `409 version_conflict`. | An app withdraws or releases it. |
| `awaiting_dependency` | The write waits for a write it depends on. | The write it waits for is answered. An app shows this as waiting, not as a stop. |

Every update goes with `conflict=auto`, so a type that settles a collision does it in the write and the verdict is `merged` or `conflicted`. Only a collision that the type's merge policy can't settle reaches `conflict_unresolved`. [Write safely](/guides/write-safely) covers both.

An app acts on a stopped write in four ways:

- **Release** a `blocked` or `dead` write to send it again under a fresh idempotency key, with its failure count cleared. A `refused` write can't be released.
- **Withdraw** a write blocked `ancestor_unavailable` or `conflict_unresolved` to take it out of the queue and hold the item as the instance has it. Withdrawing needs the instance, and any write waiting on it is refused unsent.
- **Discard** a `refused` write to take it out of the queue. The copy already shows what the instance holds. Until then the write keeps the content it carried, so an app can offer it back to the person.
- **Clear** the answered writes. This removes the `accepted`, `merged` and `conflicted` ones and the `refused` ones that carried no content. Stopped writes and refused writes with content stay.

## Folders

A folder is a device whose face is a directory. It has the same working copy, the same queue and the same verdicts, so the rules above hold. What differs is that an item is a file on disk, and an edit made to either the item or the file reaches the other.

### The settings

A `system.folder` item on the instance holds a folder's settings, and every machine bound to it shares them. Each machine writes them out as `.marfa/folder.yaml` in the directory.

- `search` decides which items the folder holds: `types`, `tier`, `state`, `filter` and `beneath`. A search that names no types holds every type the credential reads except `system.*`, in the `library` tier, active and archived.
- `defaults` is what a new file takes where it leaves a blank: `type`, `tier`, `properties`, `tags` and `edges`.
- `include` and `ignore` are lists of gitignore patterns for the paths the folder takes and leaves alone.
- `first_placement` says which directory a new item of a type first appears in.
- `removal_threshold` says when a removal waits for confirmation.

Edit `.marfa/folder.yaml` and the device sends the change with [Update a folder](/api-reference/folders/updateFolder), so it reaches every machine bound to the folder. [Create a folder](/api-reference/folders/createFolder) makes the settings.

### Items as files

A pull writes each item the search holds as a file, and a push turns an edit to a file into a queued write. A note in a folder is a Markdown file:

```markdown
---
type: core.note
tier: library
title: Written offline
marfa_id: 01a1218d-5ddd-77c1-a788-96a01aee5e83
marfa_version: 2
---
Start with the essays.
```

- `type`, `tier`, `tags`, `state` and `occurred_at` are the item's own fields.
- `marfa_id` and `marfa_version` name the item and the version the file was written from.
- Every other line between the `---` fences is a property, such as `title`, and the text after them is the body.

A `.txt` file is all body. Any other file becomes a file item and a blob, and a file the body embeds travels with the file that shows it. A new file's name comes from the item's title, and its path from the item's `in-folder` edge to the folder.

### Edits in either place

An edit to a file is an ordinary queued write based on the `marfa_version` its file names, so the rules of [Changes over time](/get-started/changes-over-time) apply. A file saved from an older version merges, field by field, and a collision the type settles with a conflicted copy gives a second file in the folder. A change made on the instance reaches the file at the next pull, which edits the file in place and keeps the frontmatter's order, comments and quoting.

A new Markdown file becomes an item when the device sends its create, and the device then writes the accepted `marfa_id` into the file. A renamed file stays the same item, found by its `marfa_id` line or by the file's identity on disk. A deleted file trashes its item after a five-second grace, so a rename or a save that replaces the file isn't taken for a delete.

### What a folder won't do on its own

- **It confirms the first pass.** A new folder reads the directory and the copy and says how many files it will write, send and place beside a file already there. Nothing is written into the directory or sent until a person confirms.
- **It pauses a large removal.** Missing files, or files whose items left the folder, wait for confirmation when they exceed both `removal_threshold.files` and `removal_threshold.fraction` of the bound files, 10 and 0.25 by default. `marfa folders confirm` carries the removal out and `marfa folders restore` undoes it.
- **It keeps secrets out.** A name such as `.env`, `*.pem` or `*.key` is never admitted, and the folder's own `.marfa/` directory is never read as items.
- **It keeps one process on a folder.** While a watch holds the folder, other calls on it are refused, except a status read.

A folder runs on macOS, through `marfa folders` or the Swift package's `Folders`. The [`marfa` command](/tools/marfa-command) lists every folder command, and the [Swift package](/tools/swift-package) shows how to add and watch a folder.
