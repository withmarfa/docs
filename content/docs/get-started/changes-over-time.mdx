## What moves the version

Every item has a `version`, a whole number that starts at 1 when the item is created. Each write to the item's own fields raises it by one, and nothing else moves it:

| Write | Moves the version |
| --- | --- |
| Properties, even ones equal to what the item holds | Yes |
| `type`, `tier`, `occurred_at` or `source_id` | Yes |
| Tags, metadata and extensions | No |
| An update that carries only `edges` | No |
| A move to the type the item already has | No |
| Archiving, trashing or restoring the item | No |

The version counts changes to the item itself, so a write beside it never makes another writer's update stale: a title changed in one app and a tag added in another both land. A tag, metadata or extension write and a change of state still move the item's `updated_at`. An edge has a version of its own, as [Properties, metadata and edges](/get-started/properties-metadata-and-edges#edges) explains.

## Writing at the version you read

An update names the `version` it read, and Marfa refuses one that names none. Say you read a note at version 3 and change its body, while another app changes its title, so the note is now at version 4:

```http
PATCH /items/{id}
Content-Type: application/json

{ "version": 3, "properties": { "body": "Start with the essays, then the letters." } }
```

Marfa compares your change with what changed since version 3, using the snapshot it kept of the note at that version:

- **Nothing collides.** You changed the body and the other app changed the title, so Marfa lays your change over the note as it is now. The note comes back at version 5, with both changes.
- **A field collides.** If the other app changed the body too, Marfa refuses the write with `409 version_conflict`. The answer holds the note as it is now and as you read it, and names the fields that collide, so you can merge them and send the result with version 4.
- **No snapshot covers the version.** If Marfa no longer keeps version 3, or never issued it, it refuses with `409 ancestor_unavailable` and merges nothing. Read the item again and make the change again.

What counts as a collision has a few edge cases, such as two writers setting a field to the same value, and the [versions chapter of the contract](https://github.com/withmarfa/marfa/blob/main/conformance/spec/versions.md#a-stale-write-that-collides) lists them all.

You can also let the item's type settle a collision. With `?conflict=auto`, Marfa resolves each colliding field by the type's merge policy instead of refusing the write:

- **`last_writer_wins`** gives the field your value.
- **`keep_both_copies`** keeps the value the item holds, and writes yours to a conflicted copy: a new item of the same type, tagged `conflicted-copy`, with a `derived-from` edge to the original.

`core.note` keeps both copies of a `body` and takes the last writer's `title`, so neither writer's text is lost.

[Trash an item](/api-reference/items/deleteItem) and [Purge an item](/api-reference/items/purgeItem) can name a version too, and refuse a stale one rather than merge it. [Update an edge](/api-reference/edges/updateEdge) always names one, and an edge keeps no snapshots, so a stale edge update is refused. [Write safely](/guides/write-safely) shows how to handle each answer, and [Update an item](/api-reference/items/updateItem) has the full request.

## History

Each time an item's version moves, Marfa keeps a snapshot of the item as it stood at the version it left: its properties, `type`, `tier`, `occurred_at` and `source_id`. The snapshots are what a stale write is merged against. [List item versions](/api-reference/items/listItemVersions) reads them, oldest first, and an item still at version 1 has none.

Marfa doesn't keep every snapshot forever. The `version-thinning` housekeeping job thins them by the `version_policy` of the item's type: every snapshot from the last `recent_days`, then the latest of each day back to `daily_snapshot_days`, then the latest of each week back to `weekly_snapshot_days`, and none older, with at most `max_versions` in all. A field the type doesn't set comes from its parent type, then from the instance defaults: every snapshot for 30 days, one a day back to 90 days, one a week back to a year, and 500 at most. [Define a type](/guides/define-a-type) sets a policy, and [Housekeeping](/guides/housekeeping) covers the job.

A write that names a version whose snapshot was thinned is refused with `ancestor_unavailable`, so an app that holds an edit for a long time reads the item again before it sends it.

## Leaving and coming back

An item's `state` is where it sits in its lifecycle: `active`, `archived` or `trashed`, and an item in the bin is `trashed`. A `system.*` item, such as a folder, is `active` or `revoked` instead, and a revoke is final.

No move between states changes the item's version or its history, so the version you read before an item was trashed is still the one to send. Select a move to see which operation makes it and what the item keeps.

<ItemLifecycle />

- **Archive**: [Change an item's state](/api-reference/items/transitionItem) to `archived` sets the item aside. A listing leaves it out unless it names `archived` or `any`, and a read by its ID still returns it.
- **Unarchive**: [Change an item's state](/api-reference/items/transitionItem) to `active` brings it back into listings.
- **Trash**: [Trash an item](/api-reference/items/deleteItem) moves an active or archived item to the bin, with every item a cascading edge such as `parent-of` reaches from it. Until it's restored, a read or write of the item is refused, and only a listing that names `trashed` or `any` returns it.
- **Restore**: [Restore an item](/api-reference/items/restoreItem) brings it back to `active`, with every item its trash took and nothing that was in the bin before.
- **Purge**: [Purge an item](/api-reference/items/purgeItem) deletes an item in the bin for good, with its history and its edges. The `trash-purge` housekeeping job purges every item that has been in the bin longer than the trash retention in the instance's configuration. Marfa keeps a tombstone of the item's link and natural key, if it held them, so a connector that meets the item again at its source can tell it was purged.

[Apply a bulk action](/api-reference/bulk-actions/applyBulkAction) makes any of these moves for every item that matches a filter.

The rules behind this page are in the [versions](https://github.com/withmarfa/marfa/blob/main/conformance/spec/versions.md), [items](https://github.com/withmarfa/marfa/blob/main/conformance/spec/items.md) and [housekeeping](https://github.com/withmarfa/marfa/blob/main/conformance/spec/housekeeping.md) chapters of the contract.
