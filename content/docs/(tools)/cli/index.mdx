The CLI is the `marfa` program. It lets you do anything the API does from a terminal: every operation has a command, such as `marfa items list` for listing items, and `marfa operations` prints each operation beside the command that reaches it. This page shows how to install the CLI, connect it to an instance, and use its output in scripts. The [CLI reference](/cli-reference) lists every command.

The CLI is also a [device](/devices). `marfa device` keeps a working copy of a slice of an instance in a local store, with a queue of writes, and `marfa folders` keeps a slice as files in a directory, as [Sync a folder](/guides/sync-a-folder) shows. And `marfa docs` reads these docs in the terminal: `marfa docs search "working copy"` finds the pages that mention working copies.

## Install

Each release of Marfa carries the CLI for macOS with Apple silicon. On Linux, build it from source.

<Tabs items={["Download", "Build from source"]}>
<Tab value="Download">

Download `marfa-<version>-darwin-arm64.tar.gz` from the [latest release](https://github.com/withmarfa/marfa/releases/latest). The archive holds the `marfa` program and nothing else. Unpack it, and move `marfa` to a directory on your `PATH`:

```bash
tar -xzf ~/Downloads/marfa-*-darwin-arm64.tar.gz -C ~/Downloads
sudo mkdir -p /usr/local/bin
sudo mv ~/Downloads/marfa /usr/local/bin/
marfa --version
```

</Tab>
<Tab value="Build from source">

You need Git and a current Rust toolchain from [rustup](https://rustup.rs). Clone Marfa and install the CLI from the clone:

```bash
git clone https://github.com/withmarfa/marfa.git
cd marfa
cargo install --locked --path core/marfa-cli
marfa --version
```

Cargo puts `marfa` in `~/.cargo/bin`, which rustup adds to your `PATH`.

</Tab>
</Tabs>

The docs follow the `main` branch of Marfa, and a release can lag behind it, so the latest release may not have a command these pages use. If the CLI says a command doesn't exist, build it from source to get it.

## Connect to a server

A command that talks to an instance needs two things: the server's address and a credential. The CLI can keep both for you, so a bare command such as `marfa status` knows where to go. There are two ways to give it a credential.

Sign in as an app with `marfa login`. The CLI shows a code and opens a page on the server, where you sign in as the owner and approve what it asks for. It then keeps the app's token in the keychain:

```bash
marfa login --url https://marfa.example.com
```

```text
Open https://marfa.example.com/auth/device?user_code=V3Z5RBBC and enter the code V3Z5RBBC
Waiting for the approval...
```

The token holds only the scopes you approve. The CLI asks for everything an owner can grant except `instance.read`, `instance.maintain`, `connectors.manage`, `blobs.manage` and `keys.manage`, so the commands that need one of those need a key instead. `marfa logout` revokes the token and forgets it.

Or keep a key you already have with `marfa keys keep`. It reads the key from `MARFA_API_KEY`, or, if that isn't set, from standard input, so you can paste it and press Return. It checks the key with the server, then keeps it in the keychain:

```bash
marfa keys keep --url https://marfa.example.com
```

[Manage keys](/guides/manage-keys) shows how to make a key that reaches only what you need.

Either way, the server you sign in to or keep a key for becomes the current server, which a command uses when nothing names another. The keychain holds one credential for each server. For each command, the CLI takes the first server and the first credential that's set, in this order:

| What it needs | First | Then | Then |
| --- | --- | --- | --- |
| A server | `--url` | `MARFA_API_URL` | The current server |
| A credential | `--key` | `MARFA_API_KEY` | What the keychain holds for that server |

So `MARFA_API_URL` and `MARFA_API_KEY` override what the keychain holds, which suits a script. Prefer them to `--key`: other users of the machine can read a command line, and it stays in your shell history. On macOS, `MARFA_KEYCHAIN` names a keychain file to use instead of your own, for a run with nobody there to answer a prompt.

## Check what a command will use

`marfa whoami` asks the server a command would reach, and says which instance answered and where the credential came from:

```bash
marfa whoami
```

```text
server https://marfa.example.com
instance 01a12312-7e62-70f2-a656-1c9eef418991 (marfa dev)
a key from the keychain
```

When a command reaches the wrong instance, or is refused, start here.

## On the instance's own machine

On the machine that runs the instance, logged in as the account that runs the server, the CLI can act with the machine's own authority instead of a credential. Pass `--socket` with the path of the server's private socket, which is `control/marfa.sock` in the server's data directory:

```bash
marfa --socket /path/to/data/control/marfa.sock setup status
```

```json
{
  "claimed": true,
  "owner_id": "pBOgdR5hPFLKrgGqkgKcIsRXxFtBNS6o",
  "generation": null
}
```

That's how the owner claims a new instance and makes its first key, as in the [Quickstart](/quickstart). Some commands work only this way: `marfa setup status`, `marfa setup code`, `marfa setup open`, `marfa owner recover` and the `marfa sign-ins` commands. The sign-in commands list every live browser, app and key, rename an app or key, and end an individual sign-in. Ending an app leaves its minted keys working unless `--revoke-keys` is given. A command given `--socket` uses no keychain, and refuses to run while `MARFA_API_URL` or `MARFA_API_KEY` is set.

Every request goes through the socket, including a command whose answer streams, such as `marfa blobs download`. The socket carries no key, though, so an operation that needs one, such as reading the event stream with `marfa events` or exporting with `marfa export`, is refused `401`. The CLI then says so, and exits `5`: run that command without `--socket`, with a key. The rule is [`device/local-socket-needs-key`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/device.md#devicelocal-socket-needs-key).

## Use it in a script

`--json` prints the answer as JSON on standard output. When a command fails, it prints one JSON object on standard error instead, with the CLI's own error code, the server's status and code where the server refused, and the exit code:

```bash
marfa items get 01a12192-a000-76e3-b129-b55027e21dcb --json
```

```json
{"error":{"code":"not_found","message":"the server refused (404 item_not_found): Item 01a12192-a000-76e3-b129-b55027e21dcb not found","server":{"status":404,"code":"item_not_found","details":null},"retry_after_seconds":null},"exit":1}
```

The exit code says what to do next:

- `0`: the command did what it was asked.
- `1`: the request was refused. Trying again gives the same answer.
- `2`: the command line was wrong, or named no server.
- `3`: the server couldn't be reached or failed. Try again.
- `4`: the working copy or the queue refused, or the machine has no keychain.
- `5`: there's no credential, or the server refused it. Sign in again, or use another key.

The [CLI reference](/cli-reference) has every exit code and every error code, and `marfa <command> --help` prints the help of the build you have.
