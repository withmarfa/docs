title: Files

A file in Marfa comes in two parts. The bytes are a **blob**, stored once under a hash of their content. The file itself is an **item**, which names the blob by that hash and carries everything else: a title, a media type, the size of an image.

Keeping them apart stores the same bytes once however many items use them, and keeps an item small enough to sync to every device.

## A blob and the item that names it

To add a file, upload its bytes, then create an item that names the hash Marfa answers. [Upload a blob](/api-reference/blobs/uploadBlob) takes the bytes as the request body:

```http title="Request"
POST /blobs
Content-Type: image/jpeg

<the bytes of the photo>
```

Marfa answers `201` with the blob's hash, media type and size:

```json title="Response" status="201"
{ "hash": "sha256:d71b77fe25721711f07e19c5f39e768e1356349c08b58260a42ed97eb996a01b", "mime_type": "image/jpeg", "size_bytes": 2481934 }
```

A file item is an item whose type inherits from `core.file`, such as `core.file.image`. Its `blob_ref` is that hash:

```http title="Request"
POST /items
Content-Type: application/json

{ "type": "core.file.image", "properties": { "title": "Holiday photo", "blob_ref": "<the hash>", "mime_type": "image/jpeg" } }
```

The same bytes uploaded again answer the same hash and are stored once, so two items can share a blob. [Handle files](/guides/handle-files) walks through uploading, downloading and replacing a file.

## Who may read a blob

**Knowing a hash isn't enough** to read the bytes. A credential reads a blob through an item that names it: if you can read a file item, you can read its blob. A hash anywhere else in an item counts too, such as an image link inside a note's Markdown body.

A reference counts only if whoever wrote it had uploaded the bytes or could already read them, so naming a hash you found somewhere gives you nothing. A file item can't name such a hash at all: the write is refused with `404 blob_not_found`. Upload the bytes with the same credential first, as [Handle files](/guides/handle-files#point-an-item-at-the-bytes) shows.

A blob you may not read answers `404 blob_not_found`, as a missing one does ([Access](/access#what-a-refusal-reveals)), even one you uploaded, until an item names it.

[Download a blob](/api-reference/blobs/downloadBlob) answers the bytes. For a web page that shows an image without sending a credential, [Get a blob URL](/api-reference/blobs/getBlobUrl) answers a link that works for a limited time.

## Where the copies live

Every instance stores its blobs on the disk beside the server. Add an **S3-compatible object store**, and the instance keeps a second copy of every blob there, checks the copies regularly, and replaces one that's missing or damaged. [Deploy](/guides/deploy#an-object-store) covers adding a store.

The instance records each copy in its **copy record**. [List a blob's copies](/api-reference/blobs/listBlobCopies), or `marfa blobs copies <hash>`, answers the stores that hold a blob and when each copy was last found intact. [Delete one copy of a blob](/api-reference/blobs/deleteBlobCopy), or `marfa blobs delete-copy`, removes one store's copy where enough live copies remain, and needs the `blobs.manage` permission.

A blob stays as long as something names it, including an item in the bin or an earlier version of an item. Once nothing does, Marfa removes it after a grace period that [Settings](/guides/settings) sets.

The rules behind this page are in the [blobs](https://github.com/withmarfa/marfa/blob/main/conformance/spec/blobs.md) and [stores](https://github.com/withmarfa/marfa/blob/main/conformance/spec/stores.md) chapters of the contract.
