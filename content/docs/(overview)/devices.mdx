---
title: Devices
description: How an app keeps a copy of your data on a phone or a Mac, works without a connection, and sends its changes when it can.
---

An app on your phone shouldn't stop working on a train. A **device** is a program that keeps a **working copy** of part of an instance on the machine it runs on. It reads from that copy, and puts its writes in a **queue** that it sends when it can reach the server.

An app built on the [Swift SDK](/swift-sdk) is a device, and so is the [CLI](/cli)'s `marfa device`. A device syncs only with the instance, never another device, because the instance is the [source of truth](/how-marfa-works#the-instance).

## The working copy

A device chooses the **slice** it keeps: a list of types, a tier and the edge types it holds, such as every `core.note` and `core.task` in the library. `*` alone holds every type except `system.*`. A device can also **pin** an item to keep it whatever the slice says.

The device fills its copy once, by a **hydration** that reads every item in the slice, then keeps it current from the instance's [event stream](/events). Reads, [saved views](/build/read-a-view) included, need no connection.

**While the copy fills, the device answers from what has arrived**, marking a list or search `partial`. A saved view's items, any edge read or write, and a read or write of an item that hasn't arrived are refused `hydration_incomplete`. Other writes wait in the queue until the copy is whole.

**A fill that stops partway resumes where it stopped**, unless something such as the slice has changed.

### Files on the device

A device keeps the files it fetched within a **file budget**, removing the ones read longest ago and fetching them again when asked. The default is the larger of 2 GiB and a tenth of the volume, leaving a twentieth free, and never below 256 MiB.

**Attachments of items in the copy stay**, outside the budget. On Apple platforms, fetched files stay out of backups. `marfa device blobs` and the Swift SDK's [file calls](/swift-sdk#keep-files-on-the-device) set the budget and fetch attachments ahead of time.

## When the copy falls behind

A copy sometimes needs filling again, and its **queued writes wait** for the fill.

- **After a device was away longer than the instance keeps events**, its copy is `stale`. It answers reads by ID, lists and searches, marking the last two `stale`, until a hydration refills it in place.
- **When another instance answers at the address, or the credential's reach changed**, the copy has expired. It refuses reads and writes until a hydration, which empties it first. A hydration also empties a copy ahead of an instance restored from backup.

An app can ask for a fill **only in place**, as `marfa device hydrate --in-place-only` does. If it can't, the fill is refused `copy_expired` with a [reason](https://github.com/withmarfa/marfa/blob/main/conformance/spec/device.md#devicerefill-in-place-only) and changes nothing, so the app can ask the person.

## A write made offline

A write waits in the queue until the instance answers it. Sending the queue is a **drain**.

<Sequence title="A note edited on a train">

1. You edit a note offline, and see the change at once.
2. The write waits in the queue, with the version of the note it was based on.
3. A drain can't reach the server, so the write stays.
4. Back online, a drain sends the queued writes in order. The instance recognizes a retry, so it never applies a write twice.
5. The device gives each answered write a verdict, and the copy takes what the instance now holds.

</Sequence>

A device sends every update with `conflict=auto`, so the instance settles most collisions, as [Versions](/versions#when-two-apps-write-the-same-item) explains.

## Verdicts

Each write a drain settles gets one verdict:

| Verdict | What happened |
| --- | --- |
| `accepted` | The instance applied the write. |
| `merged` | The write collided with another change to the same field, and the type's merge rule settled it. |
| `conflicted` | The write collided, and the type's merge rule put its value in a conflicted copy. |
| `refused` | The instance refused the write, whose content is kept to offer back. |
| `blocked` | Something must change before the write can go. |
| `dead` | The write failed five times, not counting lost connections, timeouts, rate limits or server errors. |

Only `refused`, `blocked` and `dead` need an **app's attention**. A `blocked` write says why:

| Reason | What clears it |
| --- | --- |
| `credential_refused` | A credential with the access it needs |
| `key_spent` | A release |
| `ancestor_unavailable` | A withdrawal, or a release once the credential can read the write's base version |
| `conflict_unresolved` | A withdrawal |
| `failing_alone` | A release or a withdrawal |
| `instance_changed` | A release, to the new instance, or a withdrawal |
| `awaiting_dependency` | Nothing: the answer to the write it waits for |

A **release** sends the write again in the next drain, under a fresh idempotency key. A **withdrawal** takes it out of the queue and puts the copy back to what the instance holds. `marfa device release`, `marfa device withdraw` and the Swift SDK's [queue](/swift-sdk#send-writes-and-read-verdicts) do these.

## Folders

A working copy can also be **a folder**: each item is a file, such as a note in Markdown. [Sync a folder](/run/sync-a-folder) explains how.

The rules behind this page are in the [device](https://github.com/withmarfa/marfa/blob/main/conformance/spec/device.md), [queue and verdicts](https://github.com/withmarfa/marfa/blob/main/conformance/spec/queue-and-verdicts.md) and [folders](https://github.com/withmarfa/marfa/blob/main/conformance/spec/folders.md) chapters of the contract.
