title: Items and types
description: An item is one record, such as a note or a task, and its type says what the item holds. Everything else in Marfa builds on these two ideas.
---

Everything in an instance is an item: a note, a task, a bookmark, a photo. Every item has a type, and the type is a **promise**: every app that reads a `core.note` knows it will find a `body`, because Marfa refused any note without one.

Every item also has the same fixed fields, such as its `id`, `state` and `version`, which the Catalog's [Items](/catalog/items#fields-every-item-has) page lists.

## Timestamps

Every item carries three timestamps, all in UTC. **`occurred_at` is when the item happened**, and defaults to when the item was created. `created_at` is when Marfa created the item, and `updated_at` is when it last wrote it. A change to a tag or an extension moves `updated_at` too, but not `version`. A write can set `occurred_at`; Marfa sets the other two.

## What a type does

A type is the schema for an item's properties. It names each property, gives its shape, and says which ones are required. Marfa **checks every write** against it, so this note, which has no `body`, is refused with `400 invalid_properties`:

```http
POST /items
Content-Type: application/json

{ "type": "core.note", "properties": { "title": "Reading list" } }
```

Marfa ships types for what people keep most, such as notes, tasks, bookmarks and files. The [Catalog](/catalog) lists each with its fields. When none fits, register a type of your own, as [Define a type](/guides/define-a-type) shows.

A type's identifier is two or more lowercase segments separated by dots. The first segment, its namespace, says who adds types there:

| Namespace | Example | Who adds types |
| --- | --- | --- |
| `core` | `core.note` | Marfa. No one can change them. |
| `system` | `system.folder` | Marfa, for its own records. |
| `app` | `app.readinglist.entry` | An app, for its own types. Always three segments. |
| `user` | `user.recipe` | You, for your own types. |
| A publisher's name | `acme.deal` | Anyone publishing types for others, such as a connector. |

## Building on another type

A type can name a parent. It then has every property the parent has, and adds its own. `core.file.image` is a child of `core.file`: it has a file's `blob_ref` and `mime_type`, and adds `width` and `height`.

A listing of a type includes **every type beneath it**, so `GET /items?type=core.file` returns images and receipts too. Inherit only when every property of the parent fits your type, because a child can't reshape what it inherits ([Type rules](/catalog/your-own-types#parent-and-inheritance) has the details).

When your type should be readable as another type without taking on its properties, name the other type in `compatible_with` instead. Marfa checks that your type requires everything the other one does, and a listing of the other type leaves yours out.

## Where an item came from

Every item records its **source**, the program that created it, such as `laptop` or `todoist`: the creating key's own source, or one that key claims. It never changes. An item can also carry a `source_id`, its own ID at that source, such as a task's ID in Todoist. Together they identify one record, so a connector that reads the record again updates the item instead of making a second one. [Manage keys](/guides/manage-keys#let-keys-share-a-source) shows how keys share a source.

## Library and feed

Items sit in one of two tiers. The **library** holds what a person chose to keep. The **feed** holds what arrives in volume from elsewhere, as it came, such as the tasks a connector copies from Todoist. A listing returns both tiers unless it names one.

A feed item stays until someone acts on it, or until its type's feed window runs out and it moves to the trash. [Retention policy](/catalog/your-own-types#retention-policy) describes the window, and [Housekeeping](/guides/housekeeping) the job that applies it. To keep a feed item, an app makes a library item from it, in a core type, linked back to the original with a `derived-from` edge.

## An item's life

An item starts `active`. It can be archived, which sets it aside without deleting it, or moved to the bin, where its state is `trashed`. From the bin it can be restored, or purged for good.

- **Archived** items stay readable by their `id`, but listings leave them out unless asked.
- **Moving an item to the bin** also moves the items under it, such as a task's subtasks, and restoring it brings them back.
- **Purging** deletes an item and its history, for good. [Housekeeping](/guides/housekeeping#empty-the-bin) covers when the bin empties itself.

### Delete and purge

**Deleting an item moves it to the bin.** `DELETE /items/{id}` is a soft delete: the item and its history stay, and a restore brings it back. Only a purge, which works on an item already in the bin, deletes for good.

[Change an item's state](/api-reference/items/transitionItem) and [Purge an item](/api-reference/items/purgeItem) are the operations.
