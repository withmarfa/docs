title: Items and types
description: An item is one record, such as a note or a task, and its type says what the item holds. Everything else in Marfa builds on these two ideas.
---

Everything in an instance is an item: one note, one task, one bookmark, one photo. Every item has a type, and **the type is a promise**: every app that reads a `core.note` knows it will find a `body`, because Marfa refused any note without one.

Beside its content, every item carries the same fixed fields, such as its `id`, `state` and `version`. The Catalog's [Items](/catalog/items#fields-every-item-has) page lists them all.

## What a type does

A type is the schema for an item's properties. It names each property, gives its shape, and says which ones are required. **Marfa checks every write against it**, so a note without a `body` is refused with `400 invalid_properties`:

```http
POST /items
Content-Type: application/json

{ "type": "core.note", "properties": { "title": "Reading list" } }
```

Marfa ships types for what people keep most: notes, tasks, bookmarks, highlights, messages, events, people, places, media and files, and the [Catalog](/catalog) lists each with its fields. When none fits, register a type of your own, as [Define a type](/guides/define-a-type) shows.

A type's identifier is two or more lowercase segments separated by dots. The first segment, its namespace, says who adds types there:

| Namespace | Example | Who adds types |
| --- | --- | --- |
| `core` | `core.note` | Marfa. No one can change them. |
| `system` | `system.folder` | Marfa, for its own records. |
| `app` | `app.readinglist.entry` | An app, for its own types. Always three segments. |
| `user` | `user.recipe` | You, for your own types. |
| A publisher's name | `acme.deal` | Anyone publishing types for others, such as a connector for the service it reads. |

**A type is also what access is given to.** A key or an app names the types it can read and the types it can write, as [Access](/access) explains.

## Building on another type

A type can name a parent. It then has every property the parent has, and adds its own.

`core.file.image` is a child of `core.file`: it has a file's `blob_ref` and `mime_type`, and adds `width` and `height`. An app can go further, with a receipt that is an image plus a total.

<TypeInheritance />

**A listing of a type includes every type beneath it**, so `GET /items?type=core.file` returns images and receipts too. A child can add properties and make an inherited one required, but can't change an inherited property's shape or make it optional, so inherit only when every property of the parent fits your type. The Catalog's [Type rules](/catalog/your-own-types#parent-and-inheritance) page lists what a child can and can't do.

When your type should be readable as another type without taking on all of its properties, name the other type in `compatible_with` instead. Marfa checks that your type requires everything the other one does, in shapes it can read.

## Library and feed

Items sit in one of two tiers. **The library holds what a person chose to keep.** **The feed holds what arrives in volume from elsewhere**, such as the tasks a connector copies from Todoist, kept as it came.

A feed item stays in the feed until someone acts on it. To keep one, an app makes a library item from it, in a core type, linked back to the original with a `derived-from` edge. A listing returns both tiers unless it names one.

## An item's life

An item starts `active`. It can be archived, which sets it aside without deleting it, or moved to the bin, where its state is `trashed`. From the bin it can be restored, or purged for good.

<ItemLifecycle />

- **Archived** items stay readable by their `id`, but listings leave them out unless they ask for them.
- **Moving an item to the bin** also moves the items under it, such as a task's subtasks, and restoring it brings them back.
- **Purging** deletes an item and its history. Marfa also purges what has been in the bin longer than `TRASH_RETENTION_DAYS`, 60 days by default.

None of these moves changes an item's version, so an edit made before a move to the bin still lands after a restore. [Change an item's state](/api-reference/items/transitionItem) and [Purge an item](/api-reference/items/purgeItem) are the operations.

### Empty the bin

**Only an item in the bin can be purged, and purging is permanent.** A key needs the `items.purge` permission, and the private socket can't do it, because it carries no key. To empty the bin in one step, purge every item whose state is `trashed`:

```bash tab="CLI" tab-group="client"
marfa items bulk-action purge --state trashed --confirm PURGE
```

```http tab="HTTP"
POST /items/bulk-actions
Authorization: Bearer <a key holding items.purge>
Content-Type: application/json

{ "action": "purge", "confirm": "PURGE", "filter": { "state": "trashed" } }
```

Marfa answers that it queued the purge as a job:

```json
{
  "id": "01a150c0-71c7-7ea5-b5a4-68b6267b988a",
  "action": "purge",
  "status": "queued",
  "matched": 3,
  "processed": 0,
  "succeeded": 0,
  "errored": 0
}
```

`marfa items bulk-action job <id>` shows the job again, and its `status` is `completed` once the purge has finished. Add `--dry-run` first to list what the purge would take and change nothing. A bin of more than 10,000 items is refused with `400 bulk_cap_exceeded` unless you raise `--max-items`, which Marfa counts as 50,000 at most: purge what's left with a second run. To purge one item, run `marfa items purge <id>`. Left alone, the bin empties itself: the `trash-purge` [housekeeping job](/guides/housekeeping) purges each item once it has been there longer than `TRASH_RETENTION_DAYS`, which [Settings](/guides/settings#change-settings-while-it-runs) can change while the server runs.

The rules behind this page are in the [items](https://github.com/withmarfa/marfa/blob/main/conformance/spec/items.md) and [types](https://github.com/withmarfa/marfa/blob/main/conformance/spec/types.md) chapters of the contract.
