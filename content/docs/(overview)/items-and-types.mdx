Everything in an instance is an item: a note, a task, a bookmark, a photo. Every item has a type, and the type is a **promise**: every app that reads a `core.task` knows it will find a `title`, because Marfa refused any task without one.

Every item also has the same fixed fields, such as its `id`, `state` and `version`, which the Catalog's [Items](/catalog/items#fields-every-item-has) page lists.

## Timestamps

Every item carries three timestamps, all in UTC:

- **`occurred_at`** is when the item happened. It defaults to when the item was created, and a write can set it.
- **`created_at`** is when Marfa created the item.
- **`updated_at`** is when Marfa last wrote it. A change to a tag or an extension moves it too, but not `version`.

An item in the bin also carries `trashed_at`, when it went there, and a listing of the bin comes most recently binned first.

## What a type does

A type is the schema for an item's properties. It names each property, gives its shape, and says which ones are required. Marfa **checks every write** against it, so this task, which has no `title`, is refused with `400 invalid_properties`:

```http title="Request"
POST /items
Content-Type: application/json

{ "type": "core.task", "properties": { "description": "Call the dentist" } }
```

Marfa ships types for notes, tasks, bookmarks, files and more, which the Catalog's [Types](/catalog/types) page lists. When none fits, [define a type](/build/define-a-type) of your own.

A type's identifier is two or more lowercase segments separated by dots. The first segment, its namespace, says who adds types there:

| Namespace | Example | Who adds types |
| --- | --- | --- |
| `core` | `core.note` | Marfa. No one can change them. |
| `system` | `system.folder` | Marfa, for its own records. |
| `app` | `app.readinglist.entry` | An app, for its own types. Always three segments. |
| `user` | `user.recipe` | You, for your own types. |
| A publisher's name | `acme.deal` | Anyone publishing types for others, such as a connector. |

## Building on another type

A type can name a parent. It then has every property the parent has, and adds its own. `core.file.image` is a child of `core.file`: it has a file's `blob_ref` and `mime_type`, and adds `width` and `height`.

A listing of a type includes **every type beneath it**. Inherit only when every property of the parent fits your type, because a child can't reshape what it inherits ([Type rules](/catalog/type-rules#parent-and-inheritance) has the details).

When your type should be readable as another type without taking on its properties, name the other type in `compatible_with` instead. Marfa checks that your type requires everything the other one does.

A listing of `core.file` returns images and an app's receipt type, which sit beneath it. A listing of `core.note` leaves out `user.recipe`, which names `core.note` only in `compatible_with`.

## How a type is shown

A type also tells an app how to show its items, through three **display hints**: the field that names an item, the field that holds its text, and an icon.

- **The text is Markdown.** An app renders it, and a device reads the links in it to make [edges](/edges).
- **The icon is an ID** such as `lucide:calendar`, or `simple-icons:github` for a brand. The owner can choose another for any type, including the ones Marfa ships.

Each hint comes from the nearest type that sets it, so a child that sets only an icon keeps its parent's title and text. [Type rules](/catalog/type-rules#display-hints) has the details.

## Where an item came from

Every item records its **source**, the program that created it, such as `laptop` or `todoist`: the creating key's own source, or one that key claims. It never changes.

An item can also carry a `source_id`, its own ID at that source, such as a task's ID in Todoist. Together they identify one record, so a connector that reads the record again updates the item instead of making a second one. [Manage keys](/run/manage-keys#let-keys-share-a-source) shows how keys share a source.

## Library and feed

Items sit in one of two tiers. The **library** holds what a person chose to keep. The **feed** holds what arrives in volume from elsewhere, such as the tasks a connector copies from Todoist. A listing returns both tiers unless it names one.

A feed item stays until someone acts on it, or until its type's [feed window](/catalog/type-rules#retention-policy) runs out and [Housekeeping](/run/housekeeping) moves it to the bin. To keep one, [change its `tier`](/api-reference/items/updateItem) to `library`. It's the same item, not a copy.

## An item's life

An item starts `active`. It can be archived, which sets it aside, or moved to the bin, where its state is `trashed`. An archived item stays readable by its `id`, but listings leave it out unless asked.

### Delete and purge

**Deleting an item moves it to the bin**, the API's trash. `DELETE /items/{id}` is a soft delete: the item keeps its history, the items under it, such as a task's subtasks, go with it, and a restore brings them all back. **Purging** an item in the bin deletes it and its history, for good. [Housekeeping](/run/housekeeping#empty-the-bin) covers when the bin empties itself.

[Change an item's state](/api-reference/items/transitionItem) and [Purge an item](/api-reference/items/purgeItem) are the operations.
