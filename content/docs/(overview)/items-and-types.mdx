Everything in an instance is an item: one note, one task, one bookmark, one photo. Each item has a type, which declares the properties the item carries and which of them are required, so that every app reading a `core.note` knows what it will find. This page explains what every item has, how types are named and built on each other, and the stages an item moves through.

## What every item has

Whatever its type, every item has the same fixed fields beside its properties:

## What a type does

A type is the schema for an item's properties. It names each property, gives its shape, and says which are required, and Marfa checks every write against it. `core.note` requires a `body`, so a note without one is refused with `400 invalid_properties`, and the error names the missing property:

```http
POST /items
Content-Type: application/json

{ "type": "core.note", "properties": { "title": "Reading list" } }
```

Marfa ships types for the things people keep most: notes, tasks, bookmarks, highlights, messages, events, people, places, media and files. They're in the `core` namespace, such as `core.note` and `core.task`, and you can't change them. When none fits, register a type of your own: [Define a type](/guides/define-a-type) shows how.

A type's identifier is two or more lowercase segments separated by dots. The first segment, its namespace, says who adds types there:

| Namespace | Example | Who adds types |
| --- | --- | --- |
| `core` | `core.note` | Marfa. No one can change them. |
| `system` | `system.folder` | Marfa, for its own records, written only through their own operations. |
| `app` | `app.readinglist.entry` | An app, for its own types: always three segments. |
| `user` | `user.recipe` | You, for your own types. |
| A publisher's name | `acme.deal` | Anyone publishing types for others, such as a connector for the service it reads. |
| `marfa` | None | Reserved. No one can register a type here. |

A type is also what access is granted to: a key or an app names the types it can read and the types it can write. [Access](/access) explains how.

## Building on another type

A type can name another type as its parent. It then has every property the parent declares, keeps the parent's required properties required, and adds properties of its own. `core.file.image` is a child of `core.file`: it has a file's `blob_ref` and `mime_type`, and adds `width` and `height`. An app can register a child of its own, such as a receipt that is an image with a total.

<TypeInheritance />

A listing of a type returns the items of every type beneath it, so `GET /items?type=core.file` returns images and receipts too. A child can't change the shape of a property it inherits, so inherit only when every property of the parent means what it should for your type.

When your type should be readable as another type without taking all of its properties, name the other type in `compatible_with` instead. Marfa checks the claim when you register the type: your type must require everything the other requires, in shapes the other can read. A compatible type inherits nothing, and a listing of the other type leaves it out.

## Library and feed

An item sits in one of two tiers. The library holds what a person chose to keep. The feed holds what arrives in volume from elsewhere, such as a connector's records, kept as it came until someone keeps it or sets it aside.

A write names the tier, or the item lands in the tier its credential defaults to, which is the library unless the credential says otherwise. A listing returns both tiers unless it names one. To keep a feed item, an app makes a library item from it, in a core type, linked back to the original with a `derived-from` edge.

## An item's life

An item starts `active`. (A `system` item, such as a folder's settings, is `active` or `revoked` instead.) It can be archived, which sets it aside without deleting it, and trashed, which moves it to the bin. From the bin it can be restored, or purged for good.

<ItemLifecycle />

Archiving keeps an item readable: a listing leaves it out unless it asks for archived items, and a read by its `id` still returns it. Trashing takes along every item a cascading edge reaches, such as a task's subtasks under `parent-of`, and restoring brings back everything that trash took, and nothing that was in the bin before. None of these moves changes an item's version, so an edit made before a trash still lands after a restore.

Purging deletes an item and its history. It needs the `items.purge` permission, and Marfa also purges every item that has been in the bin longer than the instance's trash retention, 60 days by default. [Change an item's state](/api-reference/items/transitionItem), [Trash an item](/api-reference/items/deleteItem), [Restore an item](/api-reference/items/restoreItem) and [Purge an item](/api-reference/items/purgeItem) are the operations.

The rules behind this page are in the [items](https://github.com/withmarfa/marfa/blob/main/conformance/spec/items.md) and [types](https://github.com/withmarfa/marfa/blob/main/conformance/spec/types.md) chapters of the contract.
