title: Events and webhooks
description: How an app learns what changed in an instance, by reading the event stream or by receiving webhooks.

An app that shows your data needs to know when it changes, whichever app changed it. Marfa records every change as an event in one log, in the order the changes happened, and offers two ways to follow it: your app reads the event stream, or Marfa sends events to your service as webhooks. This page explains what an event is and when to use each.

<EventFlow />

## The event log

Every change to an item, an edge, or an item's tags and extensions adds an event to the log when it commits; a write that's refused adds none. An event says what changed, such as `item.updated` or `edge.created`, and carries the thing as it stands after the change. Each event has an ID, a number that rises with every event, so an app that remembers the last ID it handled, its cursor, knows exactly where it stopped.

You only ever see events about what your credential can read. An item event reaches you if you can read the item's type, and an extension's change shows only the namespaces you can read. If your credential is narrowed, you stop receiving what it can no longer read.

The log doesn't keep events forever: by default it keeps them for at least seven days.

## The event stream

The [event stream](/api-reference/event-stream/streamEvents) is a long-lived connection your app opens. Send your cursor in the `Last-Event-ID` header, and Marfa replays every event after it, tells you when you've caught up, and then sends each new event as it happens. Resume from a cursor after a break, even across a restart of the server, and you receive every later event exactly once.

If you've been away longer than the log keeps events, the stream can't fill the gap. It ends with `catchup_too_old`, and your app reads its data again from the start. [Keep a copy in sync](/guides/keep-in-sync) shows how to follow the stream and handle each way it ends.

The Swift package and the CLI follow the stream for you, and also handle the case where the credential's reach changes under them. You deal with the stream yourself only when you build your own copy of an instance's data.

## Webhooks

A webhook turns the stream around: instead of your app connecting to Marfa, Marfa connects to your service. You register a URL and the event types you want, and Marfa posts each new event there, signed with a secret so your service can check it came from your instance. If your service can't be reached, or answers that it failed or is busy (`5xx`, `408` or `429`), Marfa tries again, eight times in all over about five and a half hours, before giving up. Any other refusal ends the delivery at once.

A webhook has no cursor and no replay. It delivers the events written after you registered it, and nothing earlier. Use it when a service should react to changes as they happen, such as sending a message when a task is completed. Use the stream when an app needs to catch up after being away. [Receive webhooks](/guides/receive-webhooks) shows how to register one and check each delivery.
