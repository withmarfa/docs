title: Quickstart
description: Start Marfa on your own computer, claim it, make a key, and write and change your first note.
---

- **You'll start** Marfa on your computer, claim it as its owner, and write your first note.
- **You need** macOS or Linux, with Git, [Node.js](https://nodejs.org) 22.14 or later and [pnpm](https://pnpm.io/installation), and two terminal windows: one for the server, one for everything else.
- **You'll have** a Marfa instance running on your computer, with you as its owner and one note in it.

On Linux, also install [Rust](https://www.rust-lang.org/tools/install), to build the CLI, and the `acl` package, which the server uses to check who may reach its private socket. This instance is for trying Marfa. [Deploy](/guides/deploy) covers one you keep.

<Steps paged>
<Step>

### Start the server

Clone Marfa into a short path, such as your home directory, build it, and start the server:

```bash
# Get Marfa and build it
cd ~
git clone https://github.com/withmarfa/marfa.git
cd marfa
pnpm install
pnpm build

# Start the server, with a secret that signs sign-ins
cd packages/server
export MARFA_AUTH_SECRET="$(openssl rand -hex 32)"
pnpm dev
```

The server listens on `http://localhost:8600` and keeps its data in `packages/server/data`. A new instance has no owner yet, so the server logs a **setup code**, in a line that reads `Claim this Marfa at /setup with setup code: …`. Keep it for the next steps, and leave the server running.

</Step>
<Step>

### Install the CLI

The CLI is the `marfa` program. Open a second terminal and install it:

<Tabs items={["macOS", "Linux"]}>
<Tab value="macOS">

Download it and put it on your path:

<include cwd>src/generated/cli-download.md</include>

</Tab>
<Tab value="Linux">

Build it from the clone with Rust:

```bash
cd ~/marfa
cargo install --locked --path core/marfa-cli
marfa --version
```

</Tab>
</Tabs>

</Step>
<Step>

### Claim the instance

Claiming makes you the owner, once and for good: a second claim is refused.

<Tabs items={["In the terminal", "In the browser"]}>
<Tab value="In the terminal">

```bash
marfa setup claim --url http://localhost:8600 --email you@example.com
```

The CLI asks for a password for the owner, then for the setup code the server printed. Neither is shown as you type.

</Tab>
<Tab value="In the browser">

Open `http://localhost:8600/setup`, enter the setup code the server printed, and choose the owner's email and password. **Claiming signs you in**, and setup goes on from there to add a passkey, name the instance, connect something and read how it's backed up. Done opens [Home](/guides/sign-in-as-the-owner#start-from-home).

</Tab>
</Tabs>

</Step>
<Step>

### Make a key

**Programs that work with your data use a key**, the CLI included. The owner makes the first one from the instance's own computer, through the server's private socket. In the second terminal:

<Terminal>

```bash
# The private socket sits in the server's data folder
cd ~/marfa/packages/server
marfa --socket "$(pwd -P)/data/control/marfa.sock" keys create --label laptop --source laptop
```

```text
marfa_k1_…
key 01a15f24-3ade-75f0-8862-b72a2e8e85ab (laptop); the plaintext is shown once, keep it now
  All your data               Read and edit
  Links between items         Read and edit
  Definitions on your server  Read and edit
  Profile                     Read and edit
```

</Terminal>

The first line is the key, shown only this once. It can do everything the owner can grant, which suits a trial. Give an app or a script a narrower one, as [Manage keys](/guides/manage-keys) shows.

</Step>
<Step>

### Point the CLI at your instance

Give the CLI the instance's address and your key, and check that it connects:

<Terminal>

```bash
# Replace <the key> with the key from the last step
export MARFA_API_URL=http://localhost:8600
export MARFA_API_KEY=<the key>
marfa status
```

```text
server http://localhost:8600
instance 01a15f22-b976-70e5-93ec-589b0c434770 (Marfa dev)
health ok
credential from MARFA_API_KEY
items {}
```

</Terminal>

The instance has no items yet. Each command after this sends the key with its request.

</Step>
<Step>

### Write a note

A note is an item of the type `core.note`. Create one:

<Terminal>

```bash
marfa items create --type core.note --prop title="Reading list" --prop body="Start with the essays."
```

```text
01a15f25-9482-7c0b-8b3c-fc6b5cccff72  core.note  2026-10-21T15:47:40.802Z  Reading list
{
  "body": "Start with the essays.",
  "title": "Reading list"
}
```

</Terminal>

The CLI prints the note's `id`, which Marfa made, its type, when it was made and its title, then its properties. A new item starts at version 1. Add `--json` to see the whole item, as the [HTTP API](/api-reference/items/createItem) returns it; the [TypeScript SDK](/typescript-sdk#write-and-read-an-item) shows the same request from code. Copy the `id` for the next step.

</Step>
<Step>

### Change the note

**An update names the version it read**, so Marfa can tell whether someone else changed the note in between. Change the body of version 1:

<Terminal>

```bash
# Replace <id> with the note's id
marfa items update <id> --version 1 --prop body="Start with the essays, then the letters."
```

```text
01a15f25-9482-7c0b-8b3c-fc6b5cccff72  core.note  2026-10-21T15:47:40.802Z  Reading list
{
  "body": "Start with the essays, then the letters.",
  "title": "Reading list"
}
```

</Terminal>

The note is now at version 2, with the new body and its title unchanged. Send another change to the body, still naming version 1, and Marfa refuses it rather than overwrite the newer body:

<Terminal>

```bash
marfa items update <id> --version 1 --prop body="Start with the letters."
```

```text
marfa: the server refused (409 version_conflict): Version 1 is stale; current version is 2. Conflicting fields: body.
```

</Terminal>

[Versions](/versions) explains what an app does next.

</Step>
</Steps>
