Much of your data starts somewhere else: tasks in a task manager, stars on GitHub, articles in an RSS feed. A connector is a program that reads such a service, its vendor, and writes what it finds to your instance as items. It can also carry changes made in Marfa back to the vendor. This page explains how a connector fits in and what the instance keeps for it.

<ConnectorParts />

## A program you run

The server never runs a connector and never calls a vendor. A connector is an ordinary program that you run wherever suits you, on a schedule or all the time, and it reaches the instance through the same API as any app. That keeps the server small and your vendor credentials out of it.

A connector runs with a key made for it alone. The key's source labels everything the connector writes, and together with each record's ID at the vendor, it lets the connector find a record again and update it, rather than write it twice. Its type map usually reaches only the connector's own types. [Access](/access) explains keys and sources.

What a connector brings in belongs in the feed tier, which holds records as they arrived, until a person or an app keeps one in the library. A connector names `feed` on each write, or its key sets `feed` as its default tier; otherwise its records land in the library. [Items and types](/items-and-types#library-and-feed) explains the tiers.

## What the instance keeps for a connector

A connector can stop, restart or move to another machine without losing its place, because the instance keeps what it needs:

- A registration, which names the connector, and shows when it last sent a heartbeat and how its recent runs went. A run is one pass of its work, reported as succeeded or failed.
- A state document: a JSON object the connector resumes from, such as the vendor's sync token or a cursor into its changes.
- Agreements: one record per item of what the connector and the vendor last agreed about it. A connector that carries changes back compares an item with its agreement to tell a change a person made in Marfa from one it made itself.
- A hold, which lets one process at a time write the state document and agreements, so two copies of a connector started by mistake don't write over each other. A process that crashes loses its hold after a few minutes.

The state document and agreements belong to the key's source, not to one key. If you replace a connector's key with a new one under the same source, the connector picks up where the old one stopped.

## Webhooks from the vendor

Many vendors post a webhook when something changes, so a connector can act at once instead of at its next scheduled read. The instance can give a connector an endpoint, a private address the vendor posts to without a credential. The instance stores each delivery as it arrived, and the connector reads them, checks each came from the vendor, and marks them handled. The instance holds no vendor secret, so the checking is the connector's job. [Receive vendor webhooks](/guides/connector-webhooks) shows how.
