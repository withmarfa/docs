Your instance holds everything about you, so **nothing reads or writes your data without a credential, and a credential reaches only what it was given**. A notes app can be allowed to read and write notes and nothing else, the way an app built for Apple's HealthKit asks for each kind of health data it needs.

## Who can act

Three kinds of caller act on an instance. The owner manages it, and hands access down to keys and apps:

| Caller | How it acts | What it reaches |
| --- | --- | --- |
| The owner | Signs in to the instance in a browser | Managing the instance: keys, apps, settings, maintenance. No items. |
| A key | Sent with each request, as `Authorization: Bearer marfa_k1_…` | What it was made with |
| An app | Signs in through OAuth, and sends its access token, `marfa_at_…` | What the owner approved |

**The owner manages the instance but reads and writes no items**, so even the owner works with data through a key. No key or app ever gets the owner's authority, whatever it holds. [Authenticate](/guides/authenticate) shows how the owner signs in, with a password or a passkey.

The computer the instance runs on has an authority of its own. The CLI uses it through a private socket, which only the account running the server can reach, to claim a new instance, make the first key and recover the owner's password.

## What a credential reaches

A key or an app's token is limited in two ways. **Its maps say which data it reads and writes**, and **its permissions say which other operations it may use**.

There are five maps. Each names things at a level, `read` or `write`, and anything a map doesn't name is out of reach:

| Map | What it names | Example |
| --- | --- | --- |
| Type | Item types, by identifier or pattern | `"core.*": "write"` |
| Edge | Edge types | `"about": "read"` |
| Extension | Extension namespaces | `"com.example.reader": "write"` |
| Metadata | Whether it may register types and edge types | `"types": "write"` |
| Profile | The owner's name, email and avatar | `"email": "read"` |

The type map matters most. **An item of a type the credential can't read answers `404 item_not_found`**, exactly as an item that doesn't exist does, so a refusal never tells a credential what it can't see. An item it can read but not write is refused with `403 type_not_permitted`.

## Permissions

A permission opens a group of operations, such as reading the audit log or making keys. It opens no items: a key with every permission and no maps reads nothing.

## Sources

Every key has a source of its own, chosen when it's made, such as `laptop` or `todoist`. **Marfa stamps the source on each item the key creates**, so you can always tell which writer an item came from. With the item's `source_id`, the source also identifies the item at that writer, which is how a connector finds a record again and updates it instead of making a second one.

## How a key or an app gets access

**You make a key** as the owner, or with a key that holds the `keys.mint` permission, and say what it holds. A key made by another key can hold only what its maker holds, and a key can be set to expire. [Manage keys](/guides/manage-keys) shows how to make, narrow and revoke keys.

**An app is never given a key.** It registers itself with the instance and sends the owner to approve it, as when you sign in to an app with your Google account. The owner sees each scope the app asks for, such as `core.note:read`, and the app's token holds only what the owner leaves ticked. The approval stands until the owner revokes it, or until the app goes unused for a year. [Authenticate](/guides/authenticate) shows an app's side of it.

The rules behind this page are in the [keys and sign-in](https://github.com/withmarfa/marfa/blob/main/conformance/spec/keys-and-oauth.md), [authentication](https://github.com/withmarfa/marfa/blob/main/conformance/spec/authentication.md) and [instance claim](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance-claim.md) chapters of the contract.
