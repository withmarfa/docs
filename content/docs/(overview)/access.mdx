Your instance holds everything about you, so **each credential reaches only what it was given**. A notes app can be allowed to read and write notes and nothing else, the way an app built for Apple's HealthKit asks for each kind of health data it needs.

## Who can act

Three kinds of caller act on an instance. The owner manages it, and hands access down to keys and apps:

| Caller | How it acts | What it reaches |
| --- | --- | --- |
| The owner | Signs in to the instance in a browser | Managing the instance, reading item counts, and exporting data. |
| A key | Sent with each request, as `Authorization: Bearer marfa_k1_…` | What it was made with |
| An app | Signs in through OAuth, and sends its access token, `marfa_at_…` | What the owner approved |

**The owner can read item counts and export data through a browser session**, without making a key or signing in again within the last five minutes. These reads still apply the instance's source filtering. Other item operations need a key or an app token. If a request sends a credential alongside the owner's browser session, that credential alone decides its access. No key or app ever gets the owner's authority, whatever it holds. [Authenticate](/guides/authenticate) shows how the owner signs in, with a password or a passkey.

The computer the instance runs on has an authority of its own. The CLI uses it through a private socket, which only the account running the server can reach, to claim a new instance, make the first key and recover the owner's password.

## What a credential reaches

A key or an app's token is limited in two ways. **Its maps say which data it reads and writes**, and **its permissions say which other operations it may use**.

There are five maps. Each names things at a level, `read` or `write`, which also covers reading. Email takes only `read`. Anything a map doesn't name is out of reach:

| Map | What it names | Example |
| --- | --- | --- |
| Type | Item types, by identifier or pattern | `"core.*": "write"` |
| Edge | Edge types | `"about": "read"` |
| Extension | Extension namespaces | `"com.example.reader": "write"` |
| Metadata | Whether it may register types and edge types | `"types": "write"` |
| Profile | The owner's name, email and avatar | `"email": "read"` |

**Profile write access changes only the owner's name and avatar.** The email used to sign in stays under the owner's control. An app asks for profile write access explicitly, and the approval screen identifies what it can change. [Authenticate](/guides/authenticate#change-profile-fields-with-a-credential) shows how to use it.

The type map matters most, and only it takes a third level, `none`, which shuts out a type its wildcard covers. **An item of a type the credential can't read answers `404 item_not_found`**, exactly as an item that doesn't exist does, so a refusal never tells a credential what it can't see. An item it can read but not write is refused with `403 type_not_permitted`.

## Permissions

A permission opens a group of operations, such as reading the audit log or making keys. It opens no items: a key with every permission and no type map reads nothing, and every item operation is refused with `403 type_not_permitted`.

The Catalog's [Permissions](/catalog/permissions) page lists every permission, and the levels a key's type, edge and profile maps take.

## Sources

Every key has a source of its own, chosen when it's made, such as `laptop` or `todoist`. **Marfa stamps the source on each item the key creates**, so you can always tell which writer an item came from. With the item's `source_id`, the source also identifies the item at that writer, which is how a connector finds a record again and updates it instead of making a second one.

## How a key or an app gets access

**You make a key** as the owner, or with a key that holds the `keys.mint` permission, and say what it holds. A key made by another key can hold only the permissions and maps its maker holds, and a key can be set to expire. **The maker's `enforcement_override` isn't carried over**: unless the new key names one, it follows the instance's levers ([Settings](/guides/settings) describes them), so it can list items that its maker's levers hide. [Manage keys](/guides/manage-keys) shows how to make, narrow and revoke keys.

**An app is never given a key.** It registers itself with the instance and sends the owner to approve it, as when you sign in to an app with your Google account. The owner chooses what to allow for each item type the app asks for, such as `core.note:read`, at the level No access, Read only or Read and edit, and the app's token holds only what the owner chooses. An app that asks for all data can be given chosen types instead. A browser that signed in more than five minutes ago can approve reading only; write access and permissions need a recent sign-in, which the page asks the owner to confirm. The approval stands until the owner revokes it, or until the app goes unused for a year. [Authenticate](/guides/authenticate) shows an app's side of it.
