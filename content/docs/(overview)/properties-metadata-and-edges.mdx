title: Properties, metadata and edges
description: An item's data lives in four places, properties, tags, extensions and edges, and each suits a different kind of information.
---

An item's data doesn't all live inside it. Its properties do: they're the content its type defines, such as a note's title and body. Beside the item sits its metadata record, which holds tags and extensions. And edges join the item to other items. The four differ in who decides their shape, in who can read them, and in whether writing them changes the item's version, so knowing which to use saves an app from fighting the model.

<ItemAnatomy />

| | What it holds | Who decides its shape | Moves the item's version |
| --- | --- | --- | --- |
| Properties | The item's own content, such as `title` and `body` | The item's type | Yes |
| Tags | Free-form labels, such as `favorite` | No one: a tag is a word | No |
| Extensions | An app's own data about the item, under a namespace | The app that writes the namespace | No |
| Edges | A typed link to another item, such as `about` | The edge type | No: an edge has its own version |

## Which to use

- Use a property when the information is part of what the item is, and every app reading the type should understand it: a task's due date, a bookmark's URL.
- Use a tag when a person groups or marks items in their own way: `favorite`, `to-read`, `work`.
- Use an extension when your app keeps something about an item that only it needs, especially on an item another app wrote: your place in an article a connector brought in.
- Use an edge when the information is a relationship to another item: a note about a book, a subtask under its task.

## Properties

Properties are an item's content, and its type declares them, as [Items and types](/items-and-types) explains. An update names the version it read and sends only the properties it changes; Marfa lays them over the ones the item has:

```http
PATCH /items/{id}
Content-Type: application/json

{ "version": 3, "properties": { "title": "Reading list" } }
```

The item comes back at version 4, with its other properties as they were. Because properties are what the version counts, two apps changing the same property at the same time can't silently overwrite each other. [Versions](/versions) explains how Marfa settles that.

## Tags and extensions

Every item has a metadata record beside it, which holds its tags and its extensions. Writing either leaves the item's version alone, so a tag added on one device never makes another device's edit stale. Writing either still needs write access to the item's type.

A tag is a label with no schema and no hierarchy. An item's tags are a set, so a tag added twice is kept once, and a search matches tags along with an item's text. Send `tags` when you [create an item](/api-reference/items/createItem), or add them later:

```http
POST /items/{id}/tags
Content-Type: application/json

{ "tags": ["favorite"] }
```

An extension is a JSON object stored on an item under a namespace, such as `com.example.reader`. Whoever writes a namespace decides what goes in it, and writing one namespace leaves the others alone. A key reads and writes only the namespaces its extension map names, so one app's extension stays out of another app's way:

```http
PUT /items/{id}/extensions/com.example.reader
Content-Type: application/json

{ "position": 0.42 }
```

Apps that sign in with OAuth reach no extensions: only a key's extension map grants them. [Access](/access) explains keys and their maps.

## Edges

An edge is a typed, directed link from one item to another: a note `about` a book, a task the `parent-of` a subtask. It's a record of its own, with its own `id`, properties and version, so writing it leaves both items' versions as they are.

```http
POST /edges
Content-Type: application/json

{ "source_id": "<note id>", "target_id": "<book id>", "edge_type": "about" }
```

The edge type sets the rules. It says how many edges of the type each item can hold (an item has at most one parent), which item types each end can be, what trashing an item does across the edge, and what the edge reads as from the other end (`parent-of` reads as `child-of` from the child). Trashing a parent trashes its children, for example, while trashing a note leaves the book it was about. Marfa ships ten edge types, and you can [register more](/api-reference/edge-types/registerEdgeType).
