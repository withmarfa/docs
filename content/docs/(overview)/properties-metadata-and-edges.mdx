---
title: Properties, metadata and edges
description: An item's data lives in four places, properties, tags, extensions and edges, and each suits a different kind of information.
---

The four places differ in who decides their shape and in whether a write to them moves the item's [version](/versions). Choosing the right one keeps an app from fighting the model:

| Kind | Holds | Shape set by | Moves the item's version |
| --- | --- | --- | --- |
| Properties | The item's content, such as `title` and `body` | The item's type | Yes |
| Tags | Labels, such as `favorite` | Nothing: a tag is a word | No |
| Extensions | An app's own data, under a namespace | The app that writes it | No |
| Edges | Links to other items, such as `about` | The edge type | No: each edge has its own version |

Tags and extensions together make up the item's **metadata record**, the `metadata` object on every item. In this sense metadata means data about one item, not the metadata map that [Access](/access) describes.

## Properties

Use a property when the information is part of what the item is, and every app reading the type should understand it: a task's due date, a bookmark's URL. The item's type declares its properties, as [Items and types](/items-and-types) explains.

An update sends only the properties it changes, and names the version it read:

```http
PATCH /items/{id}
Content-Type: application/json

{ "version": 3, "properties": { "title": "Reading list" } }
```

The item comes back at version 4, with its other properties as they were.

## Tags

Use a tag when a person groups or marks items in their own way: `favorite`, `to-read`, `work`. A tag is a label with no schema and no hierarchy. An item's tags are a set, and a search matches them along with the item's text.

```http
POST /items/{id}/tags
Content-Type: application/json

{ "tags": ["favorite"] }
```

[Add tags to an item](/api-reference/metadata/addItemTags) lists the few tags Marfa refuses, such as an empty one.

## Extensions

Use an extension when your app keeps something about an item that only it needs, especially on an item another app wrote: your place in an article a connector brought in.

An extension is a JSON object stored on an item under a namespace, such as `com.example.reader`. Whoever writes a namespace decides what goes in it, and one app's extension **stays out of another's way**: a key reads and writes only the namespaces its [extension map](/access#what-a-credential-reaches) names.

```http
PUT /items/{id}/extensions/com.example.reader
Content-Type: application/json

{ "position": 0.42 }
```

Writing a tag or an extension still needs write access to the item's type.

## Edges

Use an edge when the information is a relationship to another item: a note about a book, a subtask under its task. An edge is a typed, directed link from one item, its source, to another, its target. It's a record of its own, with its own `id`, properties and version.

```http
POST /edges
Content-Type: application/json

{ "source_id": "<note id>", "target_id": "<book id>", "edge_type": "about" }
```

The **edge type** sets the rules: the properties its edges hold, how many edges each item can hold (a task has at most one parent), which types each end can be, and what moving an item to the bin does across the edge. Read from the other end, an edge has a reverse name: `parent-of` reads as `child-of` from the child. You can [register edge types](/api-reference/edge-types/registerEdgeType) of your own.

Each of Marfa's edge types either **cascades** or **orphans** when an item goes to the bin:

- **A cascading edge** takes its target into the bin with its source, at every depth, and never the other way. `parent-of` is the one shipped edge type that cascades.
- **An orphaning edge** leaves the other end active, and the edge stays. Every other shipped edge type orphans.
