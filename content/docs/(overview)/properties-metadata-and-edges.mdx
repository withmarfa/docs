---
title: Properties, metadata and edges
description: An item's data lives in four places, properties, tags, extensions and edges, and each suits a different kind of information.
---

The four places differ in who decides their shape and in whether a write to them moves the item's [version](/versions). Choosing the right one keeps an app from fighting the model:

| Kind | Holds | Shape set by | Moves the item's version |
| --- | --- | --- | --- |
| Properties | The item's content, such as `title` and `body` | The item's type | Yes |
| Tags | Labels, such as `favorite` | Nothing: a tag is a word | No |
| Extensions | An app's own data, under a namespace | The app that writes it | No |
| Edges | Links to other items, such as `about` | The edge type | No: each edge has its own version |

Tags and extensions together make up the item's **metadata record**, the `metadata` object Marfa answers beside the item. In this sense metadata means data about one item, not the metadata map that [Access](/access) describes.

## Properties

Use a property when the information is part of what the item is, and every app reading the type should understand it: a task's due date, a bookmark's URL. The item's type declares its properties, as [Items and types](/items-and-types) explains.

An update sends only the properties it changes, and names the version it read:

```http title="Request"
PATCH /items/{id}
Content-Type: application/json

{ "version": 3, "properties": { "title": "Reading list" } }
```

The item comes back at version 4, with its other properties as they were.

## Tags

Use a tag when a person groups or marks items in their own way: `favorite`, `to-read`, `work`. A tag is a label with no schema and no hierarchy. An item's tags are a set, and a search matches them along with the item's text.

```http title="Request"
POST /items/{id}/tags
Content-Type: application/json

{ "tags": ["favorite"] }
```

An item holds at most 100 tags, each up to 128 characters, and [Add tags](/api-reference/metadata/addItemTags) refuses a request past either limit with `400 validation_error`.

## Extensions

Use an extension when your app keeps something about an item that only it needs, especially on an item another app wrote: your place in an article a connector brought in.

An extension is a JSON object stored on an item under a namespace, such as `com.example.reader`. Whoever writes a namespace decides what goes in it, and one app's extension **stays out of another's way**: a key reads and writes only the namespaces its [extension map](/access#what-a-credential-reaches) names.

```http title="Request"
PUT /items/{id}/extensions/com.example.reader
Content-Type: application/json

{ "position": 0.42 }
```

Writing a tag or an extension still needs write access to the item's type.

## Edges

Use an edge when the information is a relationship to another item. An edge is a typed, directed link from one item, its source, to another, its target. It's a record of its own, with its own `id`, properties and version.

```http title="Request"
POST /edges
Content-Type: application/json

{ "source_id": "<note id>", "target_id": "<book id>", "edge_type": "about" }
```

The **edge type** sets the rules: the properties its edges hold, which types each end can be, how many edges an item can hold, and what moving an item to the bin does across the edge. Marfa ships nine edge types. The Catalog's [Edges](/catalog/edges) page has each one's labels and limits, and you can [register your own](/api-reference/edge-types/registerEdgeType).

### Where an item sits

These place an item in a structure: under a parent, in a collection, thread or folder, or with another item.

| Edge type | Use it when | Example |
| --- | --- | --- |
| `parent-of` | An item is part of another. The source is the parent, and an item has at most one. | A task `parent-of` its subtasks |
| `in-collection` | You gather items into a container, in order. | A recipe in a collection of dinners |
| `in-thread` | Messages make one conversation, in order. A message is in at most one thread. | An email in its thread |
| `attached-to` | A file belongs with another item. The source is the file. | A receipt photo attached to an expense |
| `in-folder` | A [synced folder](/run/sync-a-folder) writes it for you, with the file's `path`. | A note in your `Notes` folder |

### How two items relate

These edges link two items that each stand on their own.

| Edge type | Use it when | Example |
| --- | --- | --- |
| `about` | One item is on the subject of another. | A note about a book |
| `references` | One item points at another, such as a link. | A note that links to another note |
| `derived-from` | An item was made from another, and both stay valid. | A summary written from an article |
| `supersedes` | A new item replaces an old one. | This year's lease superseding last year's |

### Moving an item to the bin

**Only `parent-of` cascades**: moving a parent to the bin takes its children with it, at every depth, and never the other way. Every other edge type orphans: the other item stays active, and so does the edge. In the figure, a note has a child note and is `about` a book.
