Every credential — an API key or an OAuth grant — carries one permission set: five permission maps plus the eleven [space permissions](/api-reference/authentication#space-permissions). Reads and writes are enforced against the maps, and **nothing bypasses them**. There is no rank: a credential reaches exactly what its set says and no more.

Two things follow that used not to.

**The reserved namespaces are the operator key's, and for `system.*` they are nobody's.** Writing to `system.*` or `marfa.*` is gated on the credential's `is_operator` flag. For `marfa.*` the operator key passes; for `system.*` nothing does, because the permission-map check runs beside the namespace gate and the operator key holds empty maps. Everything that writes a `system.*` row in the product does so through the storage layer rather than through a credential.

**An API key and a signed-in app are measured the same way.** An app gets exactly what the person granted it at consent, never the person's full access, and a key gets exactly what its maps and permission list say. The default consent grant projects to concrete map entries, one per granted core and integration type (`type_permissions: { "core.note": "write" }` and so on) rather than to a wildcard.

## The four maps

```json
{
  "type_permissions":      { "<type_pattern>": "read" | "write" | "none" },
  "extension_permissions": { "<namespace_pattern>": "read" | "write" },
  "edge_permissions":      { "<edge_type_pattern>": "read" | "write" },
  "metadata_permissions":  { "<sub_resource>": "read" | "write" },
  "profile_permissions":   { "<row>": "read" | "write" }
}
```

### Type permissions

The `type_permissions` map controls read and write access to item types. Patterns support `*` wildcard and `parent.*` subtree matching.

```json
{
  "core.note": "write",
  "core.bookmark.*": "read",
  "my-app.session": "write",
  "*": "none"
}
```

Resolution: most specific pattern wins. `core.bookmark.*` beats `*`; `core.bookmark.readwise` beats `core.bookmark.*`.

A subtree pattern covers the parent type as well as its descendants. `core.bookmark.*` matches `core.bookmark` itself, not only `core.bookmark.readwise` and its siblings. This is what the consent screen has always shown when it expands a subtree scope, and the permission check now agrees with it.

**A permission pattern matches on the identifier, not on declared parentage.** `core.bookmark.*` covers `core.bookmark` and every type whose identifier sits under `core.bookmark.`. A type registered as `acme.annotated_bookmark` with `parent: "core.bookmark"` is **not** covered: reaching it takes a pattern that names it, such as `acme.*`.

This differs from the `?type=` read filter, which does resolve declared parentage — see [Cross-discoverability](/guides/schema/authoring-types#cross-discoverability-and-the-inheritance-choice). The split is deliberate. A permission map is ranked by longest-prefix precedence, and there is no defensible way to rank a match on the name against a match through a declared parent. Resolving grants both ways made a map of `{"user.*": "none", "core.bookmark.*": "read"}` ambiguous for a type named under `user` that declares `core.bookmark` as its parent, and the two sides disagreed: a listing returned the row while fetching it by id returned `403`.

A grant is written against names, so names are what it means. The consequence to expect: a credential scoped to a subtree sees fewer rows than one holding the whole namespace for the same `?type=` query, because the query resolves parentage and the credential's grant does not.

It follows that a subtree pattern set to `none` also denies the parent. Given:

```json
{ "*": "write", "core.secret.*": "none" }
```

`core.secret` itself is denied, along with everything beneath it.

If you want the parent and the subtree to differ, name the parent explicitly. The more specific pattern wins:

```json
{ "core.secret.*": "none", "core.secret": "read" }
```

Reads inherit down the type chain — `read core.media` returns `core.media.*` items (book, article, film, etc.). Writes don't — writing to an inheriting type requires permission on the specific type. This prevents cross-app write-through on inheriting types.

A bare identifier means different things on the two sides of the gate, and the difference is deliberate. In a permission map, `core.note` grants that type alone: widening it to the subtree would hand a deliberately narrow credential everything beneath the type. In the `?type=` read filter, `core.note` has always selected the subtree, so `?type=core.note` returns `core.note.private` too. Write `core.note.*` when you mean the subtree in a grant.

<Callout type="info">
Declaring a parent now places your type in that parent's subtree for reads and for permissions, not only for field inheritance. Choose the parent deliberately: a credential granted `core.bookmark.*` reaches your type, and a query for `core.bookmark` returns it.
</Callout>

<Callout type="warn">
Subtree matching used to exclude the parent type, so `core.bookmark.*` granted access to `core.bookmark.readwise` but not to `core.bookmark`. That was inconsistent with what the consent screen described, and the two now agree.

The change applies to credentials and access tokens that already exist, with no re-consent, so review any grant where a subtree pattern and its parent type were meant to differ. It moves in both directions: a subtree `read` now also grants the parent, and a subtree `none` now also denies it.
</Callout>

### Extension permissions

The `extension_permissions` map controls which extension namespaces the credential can read or write. Extensions are **not** returned by default — a namespace must be explicitly permitted.

```json
{
  "my-app.*": "write",
  "readwise-reader.reading_progress": "read"
}
```

A credential with `extension_permissions: {}` cannot read or write any extension.

### Edge permissions

The `edge_permissions` map controls which edge types the credential can create, update, or delete.

```json
{
  "about": "write",
  "parent-of": "write",
  "in-thread": "read",
  "*": "none"
}
```

New credentials default to `edge_permissions: {}` — edge access is opt-in; apps must declare each edge type they need.

One path does not follow that default, and it is the one a person mints for themselves. The self-serve console at `/auth/keys` offers no edge picker, so it mirrors the level chosen for content onto a `*` entry: picking write on any content type mints a key carrying `edge_permissions: { "*": "write" }`. That is what lets a key you mint for your own space seed, migrate, or restore it, including relation types registered after the key was made. The dual-gate rule below still bounds it, so a key scoped to notes builds edges only out of notes. `POST /keys` and OAuth grants mirror nothing: each carries exactly the edge permissions it was given.

### Metadata permissions

The `metadata_permissions` map controls registration of new schema — the mutations that don't fit the type, extension, or edge axes.

```json
{
  "types": "write",
  "edge_types": "write"
}
```

Keys are sub-resource names. Two are enforced: `types` gates `POST /types`, and `edge_types` gates `POST /edge-types`. New credentials default to `metadata_permissions: {}`.

Note what this implies: registering a custom item type is a permission and nothing else. Any credential holding `metadata_permissions: { types: "write" }` can register one, and the registration is scoped to its own space.

OAuth tokens project the `metadata.<sub>:<verb>` scope into this map on the synthetic credential — a token granted `metadata.types:write` carries `metadata_permissions: { types: "write" }`. The bare `metadata:<verb>` scope projects a `*` wildcard across the sub-resources, so it covers both registration surfaces. It does not govern tags: tag reads and writes are gated on the parent item's own type. Nothing bypasses it — the map is the whole of what a credential reaches, and the operator key holds none.

## Your profile

Your name, email address and avatar are a category of their own, and it is **levelled**: read is a level rather than a free baseline, so a token holding nothing here may not read a name or an email address either.

```json
"profile_permissions": { "avatar": "write" }
```

Keys are row names — `name`, `email`, `avatar` — with the levelled parent keyed on `*`. A token granted `profile:read` carries `profile_permissions: { "*": "read" }` and reaches the whole category, **including rows added to it later**. A token granted `profile.avatar:write` reaches that row and no other.

Access in this category never follows from access in another. A grant over your content says nothing about your profile, and the content category's parent scope does not reach it.

The default-on profile bundle carries `profile:read` beside the OIDC literals, so an app granted the defaults reads the category. `profile:write` is in no bundle: an app that wants to change a profile asks for it by name, and the consent screen shows it pre-ticked beside the app's other write access.

Nothing bypasses the map. The gate is built on what a caller holds, not on which endpoint it chose or what rank it once carried.

### Where this overlaps the OIDC literals, and where it does not

`/oauth/userinfo` answers three claims — name, picture and email — and the OIDC `profile` and `email` literals authorise them. Those same three facts are in this category, so **the read at that endpoint is the union**: a caller sees a claim if it holds the OIDC literal *or* the corresponding profile scope. Neither door is a way around the other.

The direct profile routes are wider than those three claims: they answer your username, bio, timezone and timestamps as well. An OIDC literal does not authorise that wider object, so those routes require the category's own scope.

## Scopes that project into no map

Not every scope becomes a permission-map entry. The OIDC literals (`openid`, `profile`, `email`, `offline_access`) govern identity claims and refresh-token issuance, and the [space permissions](/api-reference/authentication#space-permissions) name administrative surfaces rather than resources. Neither reaches `type_permissions`, `edge_permissions`, `metadata_permissions` or `profile_permissions`, so a token holding one is exactly as wide on the data plane as a token holding none.

That is a property of the projection rather than an omission from it: the parser classifies every scope by family, and only the three resource families are projected. A grant the parser does not recognize at all projects nothing either, which is why a scope literal retired by a grammar change stops granting rather than starting to mean something else.

## The dual-gate rule

**Edge writes require permission on both the source item's type AND the edge type.**

Creating an `about` edge from a `core.note` to a `core.entity.person` needs:

- `type_permissions`: write on `core.note` (the source item).
- `edge_permissions`: write on `about`.

The two gates fail with different codes, so a client can tell them apart: a missing type write returns `403 type_not_permitted`, a missing edge write returns `403 edge_permission_denied`.

Nothing bypasses either.

The rationale: an edge is a mutation of the source item's graph view. Without type write, the app can't mutate the item; adding an edge would be a back-door around that. Without edge write on the type, the app can't create that kind of relationship — even if it owns the item.

### Every route that accepts inline edges applies it

`POST /items`, `POST /items/bulk` and the natural-key upsert branch of `POST /items` all take an `edges` payload, and all three run the same gate. There is no bulk exemption: a credential refused an edge on the single-item route is refused the same edge in a batch.

Bulk reports it in its own envelope. In atomic mode a refused edge aborts the batch with `400 bulk_atomic_rollback` carrying `edge_permission_denied` in the details, the same shape it already gives an unauthorized item type.

### An empty target list is a delete, and is gated as one

Inline edges are replace-all per edge type: the listed types have their existing edges removed and the given targets written in their place. So `{"edges": {"about": []}}` clears every `about` edge on the item.

That makes an empty list a delete instruction rather than a no-op, and it needs `edge_permissions[about]: write` exactly as a create would. Writing an empty list for an edge type you cannot write is refused, and the existing edges survive.

## Default tier on credentials

Credentials carry a `default_tier` field — `library` or `feed` — that stamps the tier on items written by the credential when the client omits one. Clients can override per-write. There is no read-side tier-gate on the credential; tier filtering is a query concern (`GET /items?tier=feed`), not a permission boundary.

## Patterns and practice

- **A single app typically needs ~3–5 types and one extension namespace.** A notes app might have `type: write` on `core.note`, `metadata: write`, `edge.about: write`, `edge.parent-of: write`, and `extension.notes-app.*: write`.
- **Publishing destinations tend to be narrower than capture apps.** A read-later service mostly writes `core.bookmark.*` and `core.highlight`; it needs edge write on `references`.
- **Start tight.** It's easier to add scopes than to audit what is in use later.

## Revocation effect

Revoking a credential returns `401 unauthorized` on the next request. In-flight long-lived connections (SSE) terminate on the next heartbeat failure — there's no active push. The audit trail captures the revocation event.

### Revoking an app's grant

Revoking an OAuth grant is wider than revoking a credential, because a grant can still be producing credentials at the moment you revoke it. It invalidates all four things a grant can leave behind:

- Every access token issued under it.
- Every refresh token, so no further rotation is possible.
- The consent record, so the next authorization attempt has to ask again.
- **Any authorization code still outstanding**, including one already redirected to the app but not yet exchanged.

That last one matters more than the code's ten-minute lifetime suggests. The lifetime bounds when a code can be redeemed, not what redeeming it yields: an exchange that includes `offline_access` returns a refresh token that rotates indefinitely. Without it, revoking an app mid-flow would leave it holding a credential chain that outlives the revocation, while the account's own security page reported the app as gone.

An exchange presenting a code whose grant has been revoked returns `400 invalid_grant`.
