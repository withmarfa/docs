Every error response follows the same shape:

```json
{
  "error": {
    "code": "validation_error",
    "message": "Required property 'body' is missing",
    "details": { "field": "body" }
  }
}
```

| Field | Notes |
|---|---|
| `code` | Machine-readable. Stable. Use this to branch in code. |
| `message` | Human-readable. Don't branch on this — wording may change. |
| `details` | Optional structured context (the conflicting field, the constraint that failed, etc.). Shape varies by code. |

The HTTP status reflects the error class but the `code` is the authoritative identifier — two codes can share the same status.

This shape is what every client gets, including for a path that matches no route at all: an unknown URL returns `404` with `code: "not_found"` in the envelope above, rather than a bare status with no body.

## Browsers get a page, clients get JSON

The one exception to "every error response follows the same shape" is a request that explicitly asks for HTML. A browser navigating to a Marfa URL that errors — a mistyped address, a link that has moved, an expired session — receives a rendered page instead of a JSON body, because a person reading raw JSON in a viewport learns nothing and can do nothing.

The negotiation is deliberately narrow, so that nothing an API client sends can trigger it:

| `Accept` header | Response |
|---|---|
| absent | JSON |
| `*/*` — what fetch, curl and most SDKs send | JSON |
| `application/json` | JSON |
| `text/html, application/json` | HTML |
| `text/html,application/xhtml+xml,…` — what browsers send | HTML |

A client must name `text/html` **and** rank it above `application/json` to receive a page. If you are writing an integration, you do not need to do anything: the default headers of every HTTP library resolve to JSON, and the status code and `X-Error-Code` header are identical on both branches.

<Callout type="info">
  The HTML page carries no value taken from the request — not the path, not the query, not the error message. Error pages are reachable by anyone on any URL, so every value from the request is attacker-chosen; the page's copy is fixed and keyed only on the status class. The machine-readable detail stays in the JSON branch and in `X-Error-Code`.
</Callout>

## Error codes

Every endpoint's response shapes — including the set of error codes it returns — are declared in the API reference tab. The list here is the cross-cutting catalog: stable `code` strings that clients branch on, grouped by HTTP status.

<Accordions type="single">
  <Accordion title="400 — validation and constraint failures">
    `validation_error`, `missing_required_field`, `invalid_type`, `invalid_id`, `invalid_transition`, `invalid_request`, `invalid_grant`, `invalid_client`, `invalid_scope`, `token_reuse_detected`, `inheritance_violation`, `edge_constraint_violation`, `edge_cycle`, `invalid_properties`, `invalid_schema`.

    Highlights:
    - `invalid_transition` — a lifecycle transition isn't allowed (e.g. `trashed` → `archived`). See [Lifecycle](/guides/core-model/lifecycle).
    - `edge_constraint_violation` — cardinality, type constraint, or duplicate. See [Edges](/guides/core-model/edges).
    - `token_reuse_detected` — OAuth refresh token reused after its successor issued. Both tokens now invalid; restart the authorization flow.
  </Accordion>
  <Accordion title="401 — authentication">
    `unauthorized` (missing or invalid bearer token), `expired_token` (OAuth access token expired — refresh it).
  </Accordion>
  <Accordion title="403 — permissions">
    `forbidden`, `type_not_permitted`, `edge_permission_denied`, `core_type_immutable`.

    An edge mutation is dual-gated on the source item's type and on the edge type, and the two gates report separately: a missing type write returns `type_not_permitted`, a missing edge-type write returns `edge_permission_denied`. See [Permissions](/api-reference/permissions).

    `DELETE /items/{id}/purge` answers `type_not_permitted` when the item is in a reserved namespace this credential may not write. Purging is trash-then-purge, so the refusal you would otherwise meet is that the item is not trashed — which is true, and describes an ordering mistake you did not make: the trash step was refused for the namespace, and the item never became trashable. The purge door names that reason directly rather than sending you back to a step that will refuse you again.
  </Accordion>
  <Accordion title="404 — not found">
    `not_found`, `item_not_found`, `blob_not_found`, `type_not_found`, `edge_not_found`, `edge_type_not_found`, `webhook_not_found`.

    `item_not_found` also fires when an item exists but isn't visible to this credential — don't leak existence.
  </Accordion>
  <Accordion title="409 — conflicts">
    `conflict`, `version_conflict`, `duplicate_source`, `type_mismatch`, `provenance_collision`, `type_already_exists`, `type_in_use`, `idempotency_key_in_flight`.

    A `conflict` on `POST /items` or `POST /edges` means the `id` in the body is held by a row you cannot see — one in another space. An `id` naming a row of your own that the create would have produced anyway is not a conflict: it is a repeat, and answers `200` with `acknowledged: true`. On `POST /edges` an id you hold that names a *different* edge is still a conflict, since the id and the endpoints disagree about which row you mean. `version_conflict` is the one with an enriched payload — see [below](#version-conflict). `duplicate_source` fires inside `POST /items/bulk` with `mode: create_only` as a per-item outcome reason, when `(source, source_id)` already exists and the caller asked not to update. The single-item `POST /items` path treats a duplicate `(source, source_id)` as an upsert: it short-circuits to update and returns `200`, provided the `type` in the body is the resolved item's own. `type_mismatch` is what you get when it is not, and it is worth knowing why it exists: the natural key resolves the row without consulting `type` at all, so a body naming a different one used to be merged in silently and the item kept its original type. A write never re-types the row it lands on, on any door. See [Items — relationships, lists, and writes](/guides/core-model/items#relationships-lists-and-writes).

    `provenance_collision` is the one an integration author is most likely to meet. An item's provenance is stamped from the integration and the space rather than from the individual connection, so that reinstalling adopts the items already there instead of duplicating them — which means **two connections of one integration share a single `(source, source_id)` namespace**. If both write the same upstream identifier, the second is refused with this code rather than overwriting the first, and the response names the connection that owns the row.

    **Do not retry it.** It cannot succeed while the owning connection stays installed. The fix belongs in the handler: scope `source_id` to the upstream source the record came from — the account, the calendar, the feed — so two connections stop competing for one key. See [How integrations work — what names a synced item](/guides/connections/how-integrations-work#what-names-a-synced-item).

    **A row whose recorded writer has been uninstalled is adopted rather than refused**, which is what keeps reinstall working and what stops a corpus becoming unreachable when the connection that wrote it goes away.

    **Destroying is gated the same way as writing.** An integration acting through its own runtime credential may only trash, archive, restore or delete rows it wrote: `DELETE /items/{id}`, `POST /items/{id}/transition`, `POST /items/{id}/restore` and the bulk route's `transition` action all answer `provenance_collision` when the row's writer is a sibling connection that is still installed. There is no remedy to apply here — unlike the refused write above, the answer is that this is not your row — so the connection that owns it is the one that can remove it.

    The bulk route **narrows rather than refusing**: rows written by a live sibling drop out of the match set and the rest of the action proceeds, because one unreachable row must not fail an action over thousands.

    **A person acting through their own credential is unaffected.** This narrows what an integration may do to rows it did not write, and nothing about what you can do in your own space.

    `idempotency_key_in_flight` belongs to the `Idempotency-Key` header on the item and edge write doors, and it is a true conflict: the key was not available, because an attempt carrying it is still being served or contention kept it changing hands. Nothing was written either way, so retry it. See [Sync contract — a write can be retried safely](/sdks/sync-contract#a-write-can-be-retried-safely).
  </Accordion>
  <Accordion title="413, 422 and 429">
    `blob_too_large` — exceeds the configured upload size limit. `rate_limited` — see [Rate limits](/api-reference/rate-limits).

    The two idempotency codes here are `422` rather than `409` for the same reason: neither is a conflict, so a client branching on `409` to mean somebody else got there first must not catch them.

    `idempotency_result_not_retained` — the first attempt's response was too large to keep, so it cannot be replayed. Nothing got there first and no second write happened; `details.original_status` reports the status the first attempt returned.

    `idempotency_key_reused` — an `Idempotency-Key` was sent with a request that differs from the one it was first used for. The comparison covers the method, the path, the query, the body and the credential. The request is refused because of what the caller sent rather than because of what the server holds. Mint a fresh key per logical write. See [Sync contract — a write can be retried safely](/sdks/sync-contract#a-write-can-be-retried-safely).
  </Accordion>
</Accordions>

## Version conflict

<Callout type="warn">
  `version_conflict` is the one error whose payload carries enough context to auto-resolve. Clients should branch on `err.code === "version_conflict"` before falling through to a generic error handler.
</Callout>

A `PATCH /items/{id}` whose `version` is stale returns `409 version_conflict` with an enriched payload — the server's `current` state, the `ancestor` the client was working from, the list of `conflicting_fields`, and the type's resolved `merge_policy`. Three resolution strategies are picked client-side: `auto` applies the merge policy per field, `manual` surfaces the three-way context to the app, `callback` delegates to a per-call resolver.

See [Conflicts](/guides/schema/conflicts) for the full payload shape, the keep-both semantics, the per-core-type defaults, and the resolution flow. Edges don't conflict per-field — they're atomic; constraint violations (e.g. a second `in-thread` where only one is allowed) are hard errors. Metadata conflicts (tags, tier, state) auto-merge server-side.

## Handling errors

```typescript
try {
  await client.items.update(id, { body: "..." }, { expectedVersion: 3 });
} catch (err) {
  if (err.code === "version_conflict") {
    // retry with err.current.version
  } else if (err.code === "rate_limited") {
    // back off
  } else {
    throw err;
  }
}
```

Branch on `err.code`, not on HTTP status or error message.
