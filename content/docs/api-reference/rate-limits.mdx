---
title: Rate limits
description: Per-credential request caps, the per-space ceiling, response headers, and how clients should back off.
---

Requests are bounded by three limits that stack: a fixed per-credential window per path group, an aggregate window across all of one credential's requests, and a per-space ceiling above both. The server returns rate-limit headers on every response so clients can pace themselves without blind retry loops.

## Per-credential window

- **Keyed by credential** — the API key id (or the caller's forwarded IP for unauthenticated bootstrap requests) identifies the bucket. Two keys on the same space get separate buckets.
- **Path-scoped** — sensitive paths (`/keys` and the `/auth/*` surfaces) each carry their own cap and their own window, keyed by the matched path prefix; every other path keys by its first path component (`/items`, `/edges`, ...), so hitting `/items` heavily doesn't crowd out `/edges` calls.
- **Read-friendly** — `GET` requests get double the default limit. Write endpoints enforce the base limit.
- **Fixed windows** — a window's reset time is stamped on its first request and does not slide; a cap of N admits exactly N requests, and the whole budget refreshes when the window lapses.

When the window is exceeded, the server returns `429 rate_limited`. Subsequent requests in the same window continue to fail until the window resets.

## Aggregate window

One credential's requests are also counted across every path group together, capped at a multiple of the default limit (`RATE_LIMIT_AGGREGATE_MULTIPLIER`, default 4). A caller spreading load across many endpoints meets this cap before any single path group's cap. It answers with the same `429 rate_limited` shape.

## Per-space ceiling

On top of the per-credential window, a space's whole fleet of credentials shares one ceiling. The per-credential window stops a single noisy key; the space ceiling stops many keys on the same space from collectively overwhelming the instance. A request that passes its credential window can still hit `429 rate_limited` if the space aggregate is over the ceiling.

The ceiling resolves in this order:

- **Per-space override** — `space_quotas.rate_per_minute_limit` for the space, when set, wins.
- **Instance default** — otherwise `MARFA_DEFAULT_QUOTA_RATE_PER_MINUTE`, the per-minute fallback applied to every space.
- **No ceiling** — if neither is set, only the per-credential window applies.

The ceiling is skipped entirely for credentials with no space — single-space self-hosts and platform-admin keys are bounded by the per-credential window alone.

## Headers

Every response (including `429`) carries:

| Header | Meaning |
|---|---|
| `X-RateLimit-Limit` | The effective per-credential limit for this request's path. |
| `X-RateLimit-Remaining` | Requests remaining in the current per-credential window. |
| `X-RateLimit-Reset` | Unix timestamp when the window resets. |
| `Retry-After` | On `429` only. Seconds to wait before retrying. |

The `X-RateLimit-*` headers report the per-credential window, the cap most callers meet first. A `429` from the space ceiling still carries `Retry-After`. Clients that read `X-RateLimit-Remaining` on every response can throttle proactively against their own window without ever hitting `429`.

## Configuration

Rate limiting is on by default. The tuning variables:

- **`RATE_LIMIT_ENABLED`** — set to `false` to disable entirely. Useful for trusted internal deployments behind their own rate-limiting proxy; otherwise leave it on.
- **`RATE_LIMIT_REQUESTS`** — requests per window, per credential, per path group. Path-specific overrides (tighter caps on `/keys` and the `/auth/*` surfaces) apply regardless.
- **`RATE_LIMIT_WINDOW_MS`** — window length in milliseconds, default one minute. Shared by all three limits.
- **`RATE_LIMIT_AGGREGATE_MULTIPLIER`** — the aggregate window's cap as a multiple of `RATE_LIMIT_REQUESTS`; `0` disables the aggregate window.
- **`MARFA_DEFAULT_QUOTA_RATE_PER_MINUTE`** — the per-space ceiling applied to every space that has no `space_quotas` override. Leave unset for no instance-wide space ceiling.

See [Configuration](/self-hosting/run/configuration) for defaults and the full variable set.

## Client strategy

- **Branch on the error code, not HTTP status.** `err.code === "rate_limited"` is the stable signal; treat other 429s as generic.
- **Respect `Retry-After`.** It's a server-computed delay to the next window edge — retrying earlier just wastes another request.
- **Batch where possible.** `POST /items/bulk` costs one request for many items; looping `POST /items` burns the window fast.
- **Paginate with cursors, not parallel scans.** Sequential cursor pagination is cheaper than concurrent offset walks and avoids hammering the window.
- **Never retry a rejected credential.** On `/auth/oauth2/token`, `invalid_grant` means the grant is gone. Retrying cannot change that answer, and a client that keeps asking saturates the tighter cap on that path within seconds. Restart the authorize flow instead.
- **Coalesce token refreshes.** Concurrent requests that each notice an expired token must share one exchange, not start several. Rotation invalidates the previous refresh token, so parallel refreshes make the losers replay a superseded one, which reads as reuse and revokes the session.

SDKs can retry `429` automatically with exponential backoff + jitter bounded by `Retry-After`. The Swift SDK's `retryPolicy` and the TypeScript SDK's built-in retry middleware both honor the header.
