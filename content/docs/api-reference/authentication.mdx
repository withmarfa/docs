Every API request carries a bearer token. Marfa accepts two token types, both sent in the `Authorization` header:

```http
Authorization: Bearer <token>
```

The token prefix indicates its kind:

| Prefix | Kind |
|---|---|
| `marfa_k1_...` | API key |
| `marfa_at_...` | OAuth access token |
| `marfa_rt_...` | OAuth refresh token (used only at the refresh endpoint) |

## API keys

Bearer tokens, suitable for development, automation, server-to-server calls, and app-to-Marfa in self-hosted deployments.

### Creating keys

Call `POST /keys` with the label, role, and the four permission maps (types, extensions, edges, metadata). The response contains the plaintext key **once** — the server never shows it again. Store it securely. Rotating means revoking the old key and creating a new one.

<Accordions type="single">
  <Accordion title="Example request and response">
    ```json
    POST /keys
    {
      "label": "my-app",
      "role": "member",
      "source": "My App",
      "default_tier": "library",
      "type_permissions": { "core.note": "write", "core.bookmark": "read" },
      "extension_permissions": { "my-app.*": "write" },
      "edge_permissions": { "parent-of": "write", "about": "write" },
      "metadata_permissions": { "types": "write" }
    }
    ```

    ```json
    {
      "id": "019d...",
      "key": "marfa_k1_abc...",
      "label": "my-app",
      "role": "member",
      "source": "My App",
      "default_tier": "library",
      ...
    }
    ```
  </Accordion>
</Accordions>

### Key fields

Full request and response shapes live in the API reference. A few fields carry rules worth calling out:

- **`role`** — `instance_admin` bypasses every permission check. `space_admin` is admin-shaped within its own space: an API key with this role bypasses the data-plane permission maps for its space and manages that space's keys (reserved `system.*` / `marfa.*` writes still require a platform credential). `member` is scoped by the permission maps with no key-management rights. The role bypass applies to API keys only — OAuth access tokens are always held to their granted scopes regardless of role (see [Scopes](#scopes)). A caller may not mint a key above its own role; see [Role ceiling](#role-ceiling).
- **`source`** — stamped onto every item written by this key. Unique per space; clients can't override.
- **`default_tier`** — stamps onto items when the client omits the field. Clients can override per item. See [Tier](/guides/core-model/tier).
- **`type_permissions`**, **`extension_permissions`**, **`edge_permissions`**, **`metadata_permissions`** — see [Permissions](/api-reference/permissions) for resolution rules and the dual-gate.

### Role ceiling

The roles are ordered: `instance_admin` > `space_admin` > `member`. Both of the admin-shaped roles name what they govern, which is the point of the top one's name: read beside `space_admin`, a bare `admin` looks like the smaller of the two when it is the larger. A caller may mint a key at its own role or below, never above. A `space_admin` asking for `role: "instance_admin"` gets `403 forbidden`; so does a request for any role the caller does not itself hold. The refusal is explicit rather than a silent downgrade, so a client never walks away holding a credential weaker than the one it asked for without knowing.

This bounds what a credential can turn into. Minting is not an escalation path: the strongest key a request can produce is a copy of the one that authorized it.

Two further axes are constrained separately and are not covered by the ordering:

- **`is_platform`** — only a caller that is already a platform credential can set it. Requested by anyone else, it is coerced to `false`.
- **Space** — inherited from the caller, never chosen by the request body. See [Space binding](#space-binding).

Bootstrap is the one exemption: on a fresh server there is no credential to compare against, so the seed key is minted as `instance_admin`.

### Platform admin and space-bound admin

`instance_admin` describes the role, not automatically the reach. Platform authority — the `/admin/*` space surface, cross-space quota writes, instance metrics — requires a credential that is **not bound to a space**. A key can legitimately carry `role: "instance_admin"` and still be confined to one space: `POST /admin/spaces/{id}/keys` mints exactly that, and its authority stops at that space's boundary. Such a key is admin-shaped inside its own space and is refused, with `403 forbidden`, on the cross-space surfaces.

Read `instance_admin` as "bypasses the permission maps" and space binding as "and here is how far that reaches".

### Space binding

A key minted through `POST /keys` always lands in the caller's own space. A `space_id` in the request body is rejected with `400 validation_error` rather than ignored, so a request aiming a key at one space can never quietly produce a key scoped to another.

One combination is therefore impossible. A platform-admin key has no space of its own, so it cannot mint `role: "space_admin"`: the new key would inherit no space either, and a space admin with no space is bounded by nothing. That request returns `400 validation_error`. To issue a credential for a specific space, use `POST /admin/spaces/{id}/keys`, which is platform-admin only, takes the space from the path, and never mints a platform credential. In the TypeScript SDK that is `client.admin.keys.create(spaceId, input)`.

`member` is unaffected. Minted by a caller with no space it produces a platform-tier key, which is usually what a platform operator wants. Any mint that lands without a space carries `platform_tier: true` on its `key.create` audit row, so those credentials can be found later.

### Bootstrap

On a fresh server with no keys, the first `POST /keys` succeeds without auth (bootstrap mode) and mints an admin key. Once any key exists, bootstrap mode disables — further key creation requires an admin or space_admin token.

If all keys are later revoked, bootstrap mode does not re-enable automatically. To recover, delete the `bootstrapped: true` row from the `settings` table directly, which re-opens the bootstrap window.

### Managing keys

List, retrieve, update, and revoke via the Keys endpoints. Key management is restricted to admin and space_admin roles; a space_admin manages only keys within its own space. `member` keys cannot manage other keys.

### Revocation

`DELETE /keys/{id}` revokes immediately. Revoked tokens return `401 unauthorized` on the next request.

## OAuth 2.1

Authorization Code flow with PKCE. The "Sign in with Marfa" flow for third-party apps.

The OAuth-protocol surface is owned by the `@better-auth/oauth-provider` plugin mounted on Marfa's Better Auth instance. Endpoints land under `/auth/oauth2/*`; discovery and JWKS are published at the well-known URLs the specs form for this server's path-aware issuer (see [Endpoint surface](#endpoint-surface)). The consent screen and grants management remain Marfa-owned and sit on top of the plugin's tables.

### High-level flow

<Steps>

<Step>

### Client registration

An app registers as an OAuth client. Two paths: dynamic registration via `POST /auth/oauth2/register` (RFC 7591, open — `allowUnauthenticatedClientRegistration: true`), or admin-side via `POST /auth/clients`. Public clients (native apps, SPAs) use PKCE without a client secret; confidential clients (server apps) receive a `client_secret`.

</Step>

<Step>

### Authorization request

The app redirects the user to `GET /auth/authorize` with `client_id`, `redirect_uri`, `scope`, `state`, `code_challenge`, and `code_challenge_method=S256`. If the user has no active session, the server redirects to `/auth/sign-in` (a server-rendered HTML form) preserving the original authorize URL as a return target. After sign-in, the user lands on the consent screen, which groups the requested access into a few plain-language [permission bundles](/guides/identity/permission-bundles) — unless they have already granted this app these scopes, in which case the server approves silently and sends them straight back to the app (see [Consent persistence](#consent-persistence)).

</Step>

<Step>

### Consent

The user approves (or modifies) the scope. The consent form POSTs to `/auth/authorize/decision`, which forwards to the plugin's `/auth/oauth2/consent` and redirects back to `redirect_uri` with an authorization code.

</Step>

<Step>

### Token exchange

The app exchanges the code at `POST /auth/oauth2/token` with the `code_verifier`. Response: access token, scope granted, and a refresh token when `offline_access` is among the granted scopes.

</Step>

<Step>

### Use the access token

The app calls the API with `Authorization: Bearer marfa_at_...`. Access tokens are short-lived (default 1 hour).

</Step>

<Step>

### Refresh

Before the access token expires, the app calls `POST /auth/oauth2/token` with `grant_type=refresh_token` to get a new pair. Refresh token rotation: the old refresh token is invalidated.

</Step>

</Steps>

### The resource parameter

Token requests may carry the RFC 8707 `resource` parameter naming the endpoint the token will be used against — MCP clients send it on every authorization and token request. The server accepts its own canonical URIs (the API origin and its `/mcp` endpoint), refuses any other value with `invalid_target`, and always mints the same opaque access token: every accepted audience is this server, so the issuer boundary already provides what audience restriction would. An unauthenticated request to a protected discovery-aware surface such as [the MCP endpoint](/sdks/mcp) is answered with a 401 whose `WWW-Authenticate` header names the Protected Resource Metadata document, which is where a client's authorization discovery starts.

### Scopes

The grammar has six shapes. Four are verb-on-resource and mirror the permission maps; two carry no verb, because what they name is not a level of access to a resource.

| Scope | Meaning |
|---|---|
| `<type>:read` | Read items of this type (pattern matches subtypes). |
| `<type>:write` | Create / update items of this type. |
| `edge.<type>:read` | Read edges of this type. |
| `edge.<type>:write` | Create / delete edges of this type (dual-gated with type write). |
| `metadata:read` | Read tags. |
| `metadata:write` | Write tags. |
| `metadata.<sub>:read` | Read a specific metadata sub-resource. |
| `metadata.<sub>:write` | Write a specific metadata sub-resource: `metadata.types:write` gates `POST /types`; `metadata.edge_types:write` gates `POST /edge-types`. |
| `content:read` | Read every type in the content category — everything whose family is not `system`, including types added later. |
| `content:write` | Write the same set, except that `marfa.*` types stay read-only. See [The content category](#the-content-category). |
| `capability.<surface>` | Authority over one administrative surface. No verb; see [Capability scopes](#capability-scopes). |
| `profile:read` | Read the whole of your profile, including rows added to it later. |
| `profile:write` | Read and update the same. |
| `profile.<row>:read` | Read one row: `name`, `email` or `avatar`. |
| `profile.<row>:write` | Read and update one row. |
| `openid`, `profile`, `email`, `offline_access` | The standard OIDC literals. No verb, and no reach into a space's data: they govern identity claims and refresh-token issuance. |

`profile` appears in that table twice and the two are different scopes. The
OIDC literal is the bare word and carries no verb; the profile category's
literals always carry one, so the parser tells them apart on the colon. They
are not unrelated, though — see [Your profile](/api-reference/permissions#your-profile)
for where they overlap and where they do not.

Wildcards are allowed on type scopes: `core.bookmark.*:read` covers bookmark and all its subtypes; `user.*:write` covers every runtime type in the `user.*` namespace; `*:read` covers everything. A wildcard is how an app reaches a space's runtime `user.*` types, which are never enumerated individually in the static scope allowlist.

Wildcards stop there. The edge grammar takes them (`edge.*:read`, `edge.user.*:write`), the metadata grammar does not, and the two verb-less shapes are closed sets of exact literals.

`content` is a reserved root and a closed pair: `content:read` and `content:write` are the only two literals under it, and no type may be registered there.

#### The content category

`content:read` and `content:write` name the category rather than its members. **A type registered after the grant was made is covered**, which is what makes them different from naming every type individually.

That difference is the point, and both behaviours are intended:

- **A grant holding `content:read` is not asked again when a release ships a new type.** It already covers it.
- **A grant naming individual types is asked**, because it named things rather than a category, and a type nobody approved is not one of them.

For the same reason a standing grant that lists every type today **does not** count as holding the category — coverage is membership, not enumeration — so an app moving to the category asks once.

**What the category excludes.** Everything whose family is `system`: stored credentials, devices, webhooks, connections, and the other records that describe a space rather than living in it. That set is read from the family recorded against each type rather than inferred from its name, so a type that is renamed, retired or restored is classified the same way throughout.

**One asymmetry worth knowing.** `content:write` grants read rather than write over `marfa.*` types. Those are platform-shipped integration types, and writes to them are refused to any credential that is not the platform's own — so a grant claiming to write them would describe access the server will not give, which is the one thing a consent screen must never do.

**A named type still wins over the category.** A scope naming a row sits above or below the category's default for that row, so requesting `content:read` alongside `system.connection:read` grants the category plus that one system type. Naming something has always granted it, and the category does not take that away.

OAuth access tokens are enforced against exactly the scopes granted at consent. The `space_admin` role bypass that applies to API keys does not apply to OAuth tokens — the signed-in user's role is the ceiling on what an app can be granted, not a pass-through of the user's own access. An app granted only `*:read` can read but not write, even when the user is a space admin.

Extension namespaces are not part of the OAuth scope grammar — extension reads and writes are governed by the credential's `extension_permissions` map (see [Permissions](/api-reference/permissions)). OAuth tokens carry no extension permissions: the map on an OAuth-derived credential is always empty, so the extension surface is reachable only with an API key.

The consent screen groups the requested scopes into [permission bundles](/guides/identity/permission-bundles); expanding a group reveals a per-type toggle for each scope it covers.

### Capability scopes

The type, edge, and metadata scopes all name a resource and a level of access to it. A space's administrative surfaces are not resources in that sense: registering an outbound webhook, installing a connection, minting a key, emptying the trash for good. A capability scope names one of those surfaces.

| Scope | What it covers |
|---|---|
| `capability.webhooks` | Outbound webhook subscriptions: what fires, and where the events are delivered. |
| `capability.connections` | Installing, configuring, and removing connections to upstream services, and deciding what each one can reach. Covers a connection's data mapping, its inbound receipt endpoints, and the leased tokens it issues. |
| `capability.upstream_access` | Calling a connected service directly through the proxy, spending that connection's live credential. |
| `capability.schema` | Changing and removing item and relation type definitions that already exist. Registering a new one is a different grant, below. |
| `capability.space_usage` | Reading the space's quotas and how much of each is used. |
| `capability.space_settings` | The space's configuration and its schema-enforcement settings. |
| `capability.audit_read` | Reading the space's audit log. |
| `capability.item_purge` | Permanently deleting an item, past the trash. |
| `capability.keys` | Creating, listing, and revoking the space's own API keys. |
| `capability.credentials` | Registering and removing the upstream client secrets and API tokens that connections are installed against. |
| `capability.app_grants` | Listing and revoking the other apps the space has authorized. |

Several of those boundaries are decisions rather than groupings, and each is where an obvious grouping would have handed a holder more than the name implies.

- **Using a connected account is not managing connections.** The proxy spends a connection's live upstream token, so `capability.upstream_access` reaches the person's actual account at the third-party service. Installing and removing connections does not.
- **Grant administration is not key management.** The two sit beside each other, and folding them together would let an app trusted to rotate a key enumerate and revoke every other app the space has authorized.
- **Credentials are not connections.** Registering the client secrets and tokens a connection is installed against is its own authority. Leased tokens are not here: one carries no reach beyond the connection that minted it.
- **Schema change is not schema registration.** Registering a type is already governed by `metadata.types:write` and `metadata.edge_types:write`. `capability.schema` covers only what that grammar does not, so the two never describe the same act.
- **Usage is not settings.** An app doing ordinary work may want to know how much room is left. That should not require the power to rewrite the space's enforcement policy, which is also what decides how long the audit trail survives.
- **Outbound and inbound webhooks are different things.** `capability.webhooks` covers the subscriptions that send a space's events out. A connection's inbound receipt endpoints belong to that connection.

Two rules govern the literal, and both are enforced rather than conventional.

**The set is closed.** Those eleven are the whole of it. A literal under the `capability.` root that is not one of them is not a scope at all: it fails to parse, and it is refused wherever a scope is validated. The root is reserved alongside `core`, `system`, `app`, `user`, and `marfa` (see [Namespaces](/guides/schema/namespaces)), so no type can ever be registered under it and a capability literal can never collide with a type identifier.

**A capability carries no verb.** `capability.webhooks:read` is not a narrower form of `capability.webhooks`; it is invalid. The read/write axis describes how far into a resource a grant reaches, and an administrative surface has no such axis: an app either holds the authority to manage a space's webhooks or it does not. Where a surface does divide, the division is in the name, which is why `capability.audit_read` is one capability and there is no writing counterpart.

Capability scopes reach none of the three permission maps. A granted capability projects into `type_permissions`, `edge_permissions`, and `metadata_permissions` exactly as much as an OIDC literal does, which is not at all, so holding one widens nothing on the data plane.

<Callout type="warn">
No route consults a capability scope. The grammar recognizes these literals and the reserved root protects them, but the administrative surfaces above are gated on the caller's role, exactly as they were: a `space_admin` OAuth token reaches them without holding any capability, and holding one grants nothing a role does not already carry. Do not read a capability scope as a fence.
</Callout>

Because no bundle offers them and the scope allowlist does not enumerate them, an authorization request naming a capability is refused with `invalid_scope`.

**That first clause is enforced rather than incidental**, which matters if you run your own instance. A capability literal named in `MARFA_PERMISSION_BUNDLES` is dropped when the allowlist is assembled and a warning is logged naming it, so a configured bundle cannot publish one. The bundle's other scopes are unaffected — the drop is per scope, not per bundle.

### Partial grants

Users can approve a subset of requested scopes. The returned `scope` parameter in the token response lists what was actually granted. Apps must handle receiving less than they asked for.

### Consent persistence

Consent is remembered per client. When a signed-in user reaches the authorization flow for an app they have already approved, and the standing grant reaches everything the request asks for, the server approves silently with no consent screen and redirects straight back to `redirect_uri` with a fresh authorization code. Signing out and back in does not re-prompt.

**Reach, not set membership**, and the difference decides both directions:

- **A broader grant covers a narrower request.** A standing grant of `core.*:read` covers a later request naming `core.note:read`, so an app that starts asking for one type by name does not send the user back through consent for access they already gave. Breadth is the wildcard and only the wildcard: a grant on `core.media` does not reach `core.media.book`, because `core.media` names one type. `core.media.*` names that type and everything under it.
- **Asking for less is not automatically covered.** A grant can pair a broad scope with a narrower one at a lower level — `*:write` alongside `core.*:read` means "write anything, but only read what is under `core`". Dropping `core.*:read` from a later request leaves a strictly smaller scope list that asks for **more**: the narrower scope was what held the broader one down, and without it the token could write `core.note`. That renders the consent screen.
- **A capability scope and an OIDC literal are reached by naming them exactly.** No wildcard covers either, and one never covers another.

Re-consent happens when it should:

- **Scope widening.** A request for anything the standing grant does not reach renders the consent screen with a diff — new permissions are listed separately from those already allowed.
- **`prompt=consent`.** An app that wants an explicit re-approval passes the OIDC `prompt=consent` parameter; the consent screen always renders.
- **Revocation.** Revoking a grant (via the grants surface below) deletes the stored consent, so the next authorization request renders the consent screen again.

`prompt=none` behaves per OIDC: with a covering grant the server issues a code silently; without one it redirects back to the app's registered `redirect_uri` with `error=consent_required`, never rendering UI.

**Request a stable scope set.** The cheapest way to never meet a re-prompt is to ask for the same thing every time. An app that computes its request from the server's advertised bundles will find the set moves whenever the platform registers a type, and each move is a scope the standing grant has not seen. Deciding the set at release time, and re-authorizing deliberately when a release changes it, is what keeps a returning user out of the consent screen.

### Authorization requests expire

An authorization request is signed when it first reaches `GET /auth/authorize` and is valid for ten minutes. Past that, both the consent screen and the decision endpoint render a page telling the user the request expired and to start again from the app.

Ten minutes covers the user's whole authentication journey, not just the consent click, and that journey is often longer than it looks. A user who has to sign up, wait for a verification email and come back, or who signs in by magic link, can exceed it comfortably. Apps should treat a user returning without a code as ordinary rather than exceptional, and offer a plain way to retry.

The expired page deliberately renders no detail from the request. On that path every value in the query is unverified, so echoing any of it would turn a real Marfa origin into somewhere an attacker can put chosen text.

A silent re-authorization leaves the grant untouched (the granted scope set and grant timestamps stay as the user approved them) and is recorded in the audit trail as `auth.grant.reused`, distinct from first consent.

### Refresh token rotation

Each refresh invalidates the prior refresh token and issues a new one. Reusing an invalidated refresh token returns `400 token_reuse_detected` and signals that the token pair has been compromised — both access and refresh tokens are invalidated. The app must restart the authorization flow.

### Device Authorization Grant

For headless and CLI contexts where the Authorization Code flow's browser-redirect can't run, the platform implements RFC 8628 Device Authorization Grant.

<Steps>

<Step>

### Initiate

The CLI calls `POST /auth/device` with `client_id` and `scope`. Response carries `device_code`, a short human-readable `user_code`, the `verification_uri` to open in a browser, the `verification_uri_complete` form with the user code embedded as a query parameter (so the form pre-fills), and the `interval` between polls.

</Step>

<Step>

### Display and poll

The CLI prints the URL and code; the user opens the URL on any browser-capable device, signs in if needed, enters or confirms the code, and approves. Meanwhile the CLI polls `POST /auth/device/token` at the declared interval. Visiting `GET /auth/device?user_code=XXX-XXXX` short-circuits straight to the consent screen.

</Step>

<Step>

### Token issuance

Once the user approves, the next poll returns the same token response as the Authorization Code flow, gated the same way: an access token always, a refresh token when `offline_access` is among the granted scopes, and an `id_token` when `openid` is.

</Step>

</Steps>

While the user has not yet approved, polls return `400 authorization_pending`. Polling faster than the declared interval returns `400 slow_down` and bumps the interval up. Past the device-code expiry, polls return `400 expired_token`.

A device approval merges into the app's [standing grant](#consent-persistence) rather than replacing it, so a CLI asking for one type by name never shrinks a grant the user made in a browser. The device screen confirms a scope list rather than offering the [per-scope toggles](/guides/identity/permission-bundles#per-type-control) the consent screen carries, so a narrower request there reflects what that client asked for rather than a permission the user elected to give up. The consent screen, where the tick to withhold does exist, still narrows the grant and revokes the app's live tokens. The token the CLI receives is issued for what the device asked for, bounded by what the grant reaches, never for the merged set.

A device approval leaves the same stored consent a browser approval does. A later authorization request from the same app in a browser is therefore covered by it, and skips the consent screen when the standing grant reaches what it asks for; revoking the grant removes both.

### Sign-in and sign-up surfaces

The platform serves server-rendered HTML at `/auth/sign-in` and (when sign-up is enabled) `/auth/sign-up`. These are the surfaces the consent flow redirects unauthenticated users to. They also stand alone for direct sign-in to the platform's own console. Programmatic signup against a hosted Marfa instance hits `POST /auth/sign-up/email` — see [Hosted mode](/self-hosting/run/hosted-mode).

The sign-in page offers email and password, a passwordless magic link, and passkeys. When the operator configures federated identity providers, the page also renders one button per provider; choosing one posts to `/auth/sign-in/provider/<id>`, which hands off to the upstream provider's authorize flow and signs the user in on return. Provider availability is operator-configured, so the buttons appear only on instances that wire at least one provider.

### Email verification

When the operator wires a real email backend, every new sign-up must confirm its address before a session lands. Sign-up succeeds without a session cookie, and the platform sends a verification email carrying a single-use link back to `/auth/verify-email`. Clicking it confirms the account and signs the user in; the token expires an hour after issue. A user who lets it lapse requests a fresh one from the verify-email page, which posts to `/auth/verify-email/resend`. Instances without an email backend skip verification and sign new accounts in directly.

### Password reset

A signed-out user who has forgotten their password starts at `/auth/forgot-password`, submits their email, and receives a single-use reset link valid for one hour. The link opens `/auth/reset-password`, where they choose a new password; a successful reset signs out every other session. The forgot-password response is identical whether or not an account exists for the address, so the flow never reveals which emails are registered.

### OIDC identity tokens

When `openid` is among the granted scopes, the token endpoint returns an `id_token` alongside the access and refresh tokens. The id token is a signed JWT carrying:

- Required claims: `iss`, `sub`, `aud`, `exp`, `iat`
- With `profile` scope: `name`, `preferred_username`, `picture`
- With `email` scope: `email`, `email_verified`

Verify signatures against the platform's JWKS at `/auth/jwks`, which the discovery doc advertises as its `jwks_uri`. Algorithms supported are advertised in the OIDC discovery doc at `/.well-known/oauth-authorization-server/auth` under `id_token_signing_alg_values_supported` (today: `RS256`).

For most clients the userinfo endpoint at `/auth/oauth2/userinfo` is the simpler way to fetch claim data — it returns the same shape over a request rather than as a JWT. Use the id token when verifying identity statelessly without a server round-trip; use userinfo when you have a bearer in hand and want the current claim values.

### Token revocation

`POST /auth/oauth2/revoke` implements RFC 7009. Pass the access or refresh token as `token` in a form-encoded body, with the app's `client_id`. The server returns `200` regardless of whether the token was valid, per the spec, to avoid leaking token-existence information.

What is revoked depends on which token you present:

- **An access token** is invalidated on its own. The refresh token, the stored consent and the app's entry on the user's security page all stand: this is a sign-out, and the app can obtain a new access token without asking the user again.
- **A refresh token** ends the grant it belongs to. Every access and refresh token issued under that grant is invalidated, the stored consent is removed, the app disappears from the user's security page, and an `auth.grant.revoked` audit row is written with `source: client`. The next authorization request renders the consent screen again. The grant is per app and user, so this reaches every device the user signed the app in on. A refresh token presented with a `client_id` other than the one it was issued to revokes nothing. A refresh token that has already been rotated away answers `400 invalid_request`, since the server treats a stale token as a replay and invalidates the whole family, and the grant ends in that case too.

```bash
curl -X POST https://marfa.example.com/auth/oauth2/revoke \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d 'token=marfa_at_...'
```

Revoke the access token on sign-out and the refresh token when the user disconnects the app, so server-side state matches the user's intent. The endpoint is advertised in the OIDC discovery doc as `revocation_endpoint`.

### Signing out invalidates the tokens issued under that session

RP-initiated logout at `/auth/oauth2/end-session` ends the browser session **and** invalidates the access and refresh tokens issued under it. The next request carrying one of those bearers returns `401 unauthorized`, whatever its remaining lifetime says.

Three consequences worth designing around:

- **A stored bearer stops working the moment the user signs out**, not when it expires. An app holding one should treat a `401` after sign-out as expected rather than as an error to retry.
- **Refresh tokens carrying `offline_access` are deliberately exempt.** That scope exists so a client can keep working while the user is away, and ending a browser session is not a statement about background access. A client that wants sign-out to stop its background work too should revoke explicitly, at the endpoint above.
- **Only tokens tied to that session are reached.** Device-flow tokens carry no session, so signing out of a browser does not touch a token minted on another device. Revoke those explicitly, or revoke the whole grant.

Calling `POST /auth/oauth2/revoke` on sign-out remains worth doing: it is explicit, it covers the `offline_access` and device-flow cases this does not, and it works for clients that never had a browser session at all.

### Token introspection

`POST /auth/oauth2/introspect` implements RFC 7662. Form-encoded body with `token` and (for confidential clients) `client_id` + `client_secret`. The server returns `{ active: boolean, scope?, client_id?, exp?, ... }` — `active: false` is the not-valid response, never an error.

### Grant lifecycle audit

The auth audit-row catalog carries three grant-lifecycle entries:

- `auth.grant.created` — emitted on consent acceptance (both code-flow via `/auth/authorize/decision` and device-flow via `/auth/device/consent`). `details.source` distinguishes the surface; `details.created` distinguishes first-consent from re-consent.
- `auth.grant.reused` — emitted on silent re-authorization (see [Consent persistence](#consent-persistence)): the prior grant already covered the request, so no consent screen rendered and the grant record was not modified.
- `auth.grant.revoked` — emitted on `DELETE /auth/grants/:id`, the form-friendly `POST /auth/grants/:id/revoke`, and when an app revokes its refresh token at `POST /auth/oauth2/revoke`; that last row carries `details.source: client`.

All three rows carry the verified `client_id`, `user_id`, and grant item id without trusting form fields: the route handlers read them from the signed request or the grant record, and the client-revoke row resolves them from the token's own record.

### Grants management

`/auth/grants` exposes the user's current OAuth grants — one row per `system.connection` of `kind: app`. Listing, inspecting, and revoking grants happens through this surface. Revoking a grant invalidates the associated tokens immediately. See [Connections](/guides/connections/connections) for the underlying type.

**A revoke that cannot invalidate the tokens fails rather than reporting success.** The token invalidation runs before the grant record is updated, so a failure leaves the grant reading active, which is the truth: the tokens still work. The alternative — marking it revoked and moving on — produces a security page describing access the user no longer has while that access carries on working, which is the worse of the two outcomes by some distance. `DELETE /auth/grants/:id` surfaces this as a 5xx; the form-friendly route redirects with `?notice=grant_revoke_failed`. Either way the correct response is to retry, not to assume it worked.

### Integration OAuth bootstrap

Distinct from the user-facing OAuth flow above: the platform also runs an OAuth callback at `/oauth/callback` for integrations that need to establish OAuth tokens against an external service (Google Calendar, GitHub, and so on). The callback verifies a server-signed state, exchanges the upstream code for tokens, and stores them encrypted for the integration's later use through the OAuth proxy. End users see a normal upstream OAuth flow; the platform handles the bootstrap on the integration's behalf. See [Integrations](/guides/connections/integrations) for the wider context.

**Registering the callback.** One URI covers every provider a deployment connects: your public base URL followed by `/oauth/callback`. Register that exact string on each upstream service's OAuth app. `POST /connections/:id/oauth/start` returns it as `redirect_uri` alongside the authorize URL, so it can be copied rather than assembled — a mismatch is the most common way this flow fails, and the provider reports it as a generic error with nothing on the Marfa side to explain it. Providers are told apart by the signed `state`, not by the path.

The bootstrap flow is hardened with two platform-side controls:

- **PKCE on the upstream authorize call.** The platform generates a code verifier per attempt, persists it inside the AES-GCM-signed state envelope, and sends `code_challenge` + `code_challenge_method=S256` on the authorize redirect. The verifier is replayed at token exchange. Integrations don't manage PKCE themselves — it's enforced by the platform regardless of what the upstream service expects, defending against authorization-code injection.
- **A redirect URI the caller cannot choose.** The bootstrap sends its own callback, `<MARFA_AUTH_BASE_URL>/oauth/callback`, and ignores anything a request says about where to come back to. Only one value could ever be correct, since a provider honors a redirect only against the URI registered on its own OAuth app, so accepting one from the caller bought nothing and risked handing an authorization code to whoever supplied it.

## Choosing between API keys and OAuth

- **API keys** for: your own apps against your own space, server-to-server calls, scripts, CI, MCP servers and CLIs connecting to a known space.
- **OAuth** for: third-party apps where the user wants explicit consent per type, revocable without rotating an API key, and a flow that terminates at a login experience.

Both produce the same server behavior — permissions enforce identically regardless of credential kind.
