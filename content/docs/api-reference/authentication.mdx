Every API request carries a bearer token. Marfa accepts two token types, both sent in the `Authorization` header:

```http
Authorization: Bearer <token>
```

The token prefix indicates its kind:

| Prefix | Kind |
|---|---|
| `marfa_k1_...` | API key |
| `marfa_at_...` | OAuth access token |
| `marfa_rt_...` | OAuth refresh token (used only at the refresh endpoint) |

## API keys

Bearer tokens, suitable for development, automation, server-to-server calls, and app-to-Marfa in self-hosted deployments.

### Creating keys

Call `POST /keys` with the label, role, and the four permission maps (types, extensions, edges, metadata). The response contains the plaintext key **once** — the server never shows it again. Store it securely. Rotating means revoking the old key and creating a new one.

    ```json
    POST /keys
    {
      "label": "my-app",
      "role": "member",
      "source": "My App",
      "default_tier": "library",
      "type_permissions": { "core.note": "write", "core.bookmark": "read" },
      "extension_permissions": { "my-app.*": "write" },
      "edge_permissions": { "parent-of": "write", "about": "write" },
      "metadata_permissions": { "types": "write" }

    ```

    {
      "id": "019d...",
      "key": "marfa_k1_abc...",

### Key fields

Full request and response shapes live in the API reference. A few fields carry rules worth calling out:

- **`role`** — `admin` bypasses every permission check. `space_admin` is admin-shaped within its own space: an API key with this role bypasses the data-plane permission maps for its space and manages that space's keys (reserved `system.*` / `marfa.*` writes still require a platform credential). `member` is scoped by the permission maps with no key-management rights. The role bypass applies to API keys only — OAuth access tokens are always held to their granted scopes regardless of role (see [Scopes](#scopes)). A caller may not mint a key above its own role; see [Role ceiling](#role-ceiling).
- **`source`** — stamped onto every item written by this key. Unique per space; clients can't override.
- **`default_tier`** — stamps onto items when the client omits the field. Clients can override per item. See [Tier](/guides/core-model/tier).
- **`type_permissions`**, **`extension_permissions`**, **`edge_permissions`**, **`metadata_permissions`** — see [Permissions](/api-reference/permissions) for resolution rules and the dual-gate.

### Role ceiling

The roles are ordered: `admin` > `space_admin` > `member`. A caller may mint a key at its own role or below, never above. A `space_admin` asking for `role: "admin"` gets `403 forbidden`; so does a request for any role the caller does not itself hold. The refusal is explicit rather than a silent downgrade, so a client never walks away holding a credential weaker than the one it asked for without knowing.

This bounds what a credential can turn into. Minting is not an escalation path: the strongest key a request can produce is a copy of the one that authorized it.

Two further axes are constrained separately and are not covered by the ordering:

- **`is_platform`** — only a caller that is already a platform credential can set it. Requested by anyone else, it is coerced to `false`.
- **Space** — inherited from the caller, never chosen by the request body. See [Space binding](#space-binding).

Bootstrap is the one exemption: on a fresh server there is no credential to compare against, so the seed key is minted as `admin`.

### Platform admin and space-bound admin

`admin` describes the role, not automatically the reach. Platform authority — the `/admin/*` space surface, cross-space quota writes, instance metrics — requires a credential that is **not bound to a space**. A key can legitimately carry `role: "admin"` and still be confined to one space: `POST /admin/spaces/{id}/keys` mints exactly that, and its authority stops at that space's boundary. Such a key is admin-shaped inside its own space and is refused, with `403 forbidden`, on the cross-space surfaces.

Read `admin` as "bypasses the permission maps" and space binding as "and here is how far that reaches".

### Space binding

A key minted through `POST /keys` always lands in the caller's own space. A `space_id` in the request body is rejected with `400 validation_error` rather than ignored, so a request aiming a key at one space can never quietly produce a key scoped to another.

One combination is therefore impossible. A platform-admin key has no space of its own, so it cannot mint `role: "space_admin"`: the new key would inherit no space either, and a space admin with no space is bounded by nothing. That request returns `400 validation_error`. To issue a credential for a specific space, use `POST /admin/spaces/{id}/keys`, which is platform-admin only, takes the space from the path, and never mints a platform credential. In the TypeScript SDK that is `client.admin.keys.create(spaceId, input)`.

`member` is unaffected. Minted by a caller with no space it produces a platform-tier key, which is usually what a platform operator wants. Any mint that lands without a space carries `platform_tier: true` on its `key.create` audit row, so those credentials can be found later.

### Bootstrap

On a fresh server with no keys, the first `POST /keys` succeeds without auth (bootstrap mode) and mints an admin key. Once any key exists, bootstrap mode disables — further key creation requires an admin or space_admin token.

If all keys are later revoked, bootstrap mode does not re-enable automatically. To recover, delete the `bootstrapped: true` row from the `settings` table directly, which re-opens the bootstrap window.

### Managing keys

List, retrieve, update, and revoke via the Keys endpoints. Key management is restricted to admin and space_admin roles; a space_admin manages only keys within its own space. `member` keys cannot manage other keys.

### Revocation

`DELETE /keys/{id}` revokes immediately. Revoked tokens return `401 unauthorized` on the next request.

## OAuth 2.1

Authorization Code flow with PKCE. The "Sign in with Marfa" flow for third-party apps.

The OAuth-protocol surface is owned by the `@better-auth/oauth-provider` plugin mounted on Marfa's Better Auth instance. Endpoints land under `/auth/oauth2/*`; discovery + JWKS are re-published at the standard well-known paths. The consent screen and grants management remain Marfa-owned and sit on top of the plugin's tables.

### High-level flow

<Steps>

<Step>

### Client registration

An app registers as an OAuth client. Two paths: dynamic registration via `POST /auth/oauth2/register` (RFC 7591, open — `allowUnauthenticatedClientRegistration: true`), or admin-side via `POST /auth/clients`. Public clients (native apps, SPAs) use PKCE without a client secret; confidential clients (server apps) receive a `client_secret`.

</Step>

<Step>

### Authorization request

The app redirects the user to `GET /auth/authorize` with `client_id`, `redirect_uri`, `scope`, `state`, `code_challenge`, and `code_challenge_method=S256`. If the user has no active session, the server redirects to `/auth/sign-in` (a server-rendered HTML form) preserving the original authorize URL as a return target. After sign-in, the user lands on the consent screen, which groups the requested access into a few plain-language [permission bundles](/guides/identity/permission-bundles) — unless they have already granted this app these scopes, in which case the server approves silently and sends them straight back to the app (see [Consent persistence](#consent-persistence)).

</Step>

<Step>

### Consent

The user approves (or modifies) the scope. The consent form POSTs to `/auth/authorize/decision`, which forwards to the plugin's `/auth/oauth2/consent` and redirects back to `redirect_uri` with an authorization code.

</Step>

<Step>

### Token exchange

The app exchanges the code at `POST /auth/oauth2/token` with the `code_verifier`. Response: access token, refresh token, scope granted.

</Step>

<Step>

### Use the access token

The app calls the API with `Authorization: Bearer marfa_at_...`. Access tokens are short-lived (default 1 hour).

</Step>

<Step>

### Refresh

Before the access token expires, the app calls `POST /auth/oauth2/token` with `grant_type=refresh_token` to get a new pair. Refresh token rotation: the old refresh token is invalidated.

</Step>

</Steps>

### Endpoint surface

| Endpoint | Spec / purpose |
| --- | --- |
| `POST /auth/oauth2/authorize` + `POST /auth/oauth2/consent` | Authorization Code + PKCE S256. |
| `POST /auth/oauth2/token` | `authorization_code`, `refresh_token`, `client_credentials`. Refresh rotation built in. A `client_credentials` request that names no scope, for a client registered without scopes, is granted nothing — the grant has no user to review it, so a machine client states what it needs explicitly. |
| `POST /auth/oauth2/userinfo` | OIDC userinfo. |
| `POST /auth/oauth2/revoke` | RFC 7009 token revocation. |
| `POST /auth/oauth2/introspect` | RFC 7662 token introspection. |
| `POST /auth/oauth2/register` | RFC 7591 Dynamic Client Registration. Open to unauthenticated callers. A registration omitting `scope` defaults to the bundle expansion, not the full allowlist; wider scopes are requested explicitly. |
| `GET /auth/jwks` | JWKS for `id_token` signature verification. |
| `GET /.well-known/oauth-authorization-server` | RFC 8414 authorization-server metadata. |
| `GET /.well-known/openid-configuration` | OIDC discovery. |
| `GET /auth/authorize` + `POST /auth/authorize/decision` | Marfa-owned consent screen + decision handler (forwards to the plugin's `/auth/oauth2/consent`). |
| `/auth/device*` | Marfa-owned device-flow state machine; tokens land in the plugin's tables on issuance. |
| `/auth/grants*`, `/auth/sessions*`, `/auth/security` | Marfa-owned user-facing grants + session management. |

### Scopes

Scopes use a verb-on-resource grammar that mirrors the permission maps:

| Scope | Meaning |
|---|---|
| `<type>:read` | Read items of this type (pattern matches subtypes). |
| `<type>:write` | Create / update items of this type. |
| `edge.<type>:read` | Read edges of this type. |
| `edge.<type>:write` | Create / delete edges of this type (dual-gated with type write). |
| `metadata:read` | Read tags. |
| `metadata:write` | Write tags. |
| `metadata.<sub>:write` | Write a specific metadata sub-resource: `metadata.types:write` gates `POST /types`; `metadata.edge_types:write` gates `POST /edge-types`. |

Wildcards are allowed on type scopes: `core.bookmark.*:read` covers bookmark and all its subtypes; `user.*:write` covers every runtime type in the `user.*` namespace; `*:read` covers everything. A wildcard is how an app reaches a space's runtime `user.*` types, which are never enumerated individually in the static scope allowlist.

OAuth access tokens are enforced against exactly the scopes granted at consent. The `space_admin` role bypass that applies to API keys does not apply to OAuth tokens — the signed-in user's role is the ceiling on what an app can be granted, not a pass-through of the user's own access. An app granted only `*:read` can read but not write, even when the user is a space admin.

Extension namespaces are not part of the OAuth scope grammar — extension reads and writes are governed by the credential's `extension_permissions` map (see [Permissions](/api-reference/permissions)). OAuth tokens carry no extension permissions: the map on an OAuth-derived credential is always empty, so the extension surface is reachable only with an API key.

The consent screen groups the requested scopes into [permission bundles](/guides/identity/permission-bundles); expanding a group reveals a per-type toggle for each scope it covers.

### Partial grants

Users can approve a subset of requested scopes. The returned `scope` parameter in the token response lists what was actually granted. Apps must handle receiving less than they asked for.

### Consent persistence

Consent is remembered per client and scope set. When a signed-in user reaches the authorization flow for an app they have already approved, and the requested scopes are covered by the prior grant (equal or narrower), the server approves silently with no consent screen and redirects straight back to `redirect_uri` with a fresh authorization code. Signing out and back in does not re-prompt.

Re-consent happens when it should:

- **Scope widening.** A request for any scope the user has not already granted renders the consent screen with a diff — new permissions are listed separately from those already allowed.
- **`prompt=consent`.** An app that wants an explicit re-approval passes the OIDC `prompt=consent` parameter; the consent screen always renders.
- **Revocation.** Revoking a grant (via the grants surface below) deletes the stored consent, so the next authorization request renders the consent screen again.

`prompt=none` behaves per OIDC: with a covering grant the server issues a code silently; without one it redirects back to the app's registered `redirect_uri` with `error=consent_required`, never rendering UI.

### Authorization requests expire

An authorization request is signed when it first reaches `GET /auth/authorize` and is valid for ten minutes. Past that, both the consent screen and the decision endpoint render a page telling the user the request expired and to start again from the app.

Ten minutes covers the user's whole authentication journey, not just the consent click, and that journey is often longer than it looks. A user who has to sign up, wait for a verification email and come back, or who signs in by magic link, can exceed it comfortably. Apps should treat a user returning without a code as ordinary rather than exceptional, and offer a plain way to retry.

The expired page deliberately renders no detail from the request. On that path every value in the query is unverified, so echoing any of it would turn a real Marfa origin into somewhere an attacker can put chosen text.

A silent re-authorization leaves the grant untouched (the granted scope set and grant timestamps stay as the user approved them) and is recorded in the audit trail as `auth.grant.reused`, distinct from first consent.

### Refresh token rotation

Each refresh invalidates the prior refresh token and issues a new one. Reusing an invalidated refresh token returns `400 token_reuse_detected` and signals that the token pair has been compromised — both access and refresh tokens are invalidated. The app must restart the authorization flow.

### Device Authorization Grant

For headless and CLI contexts where the Authorization Code flow's browser-redirect can't run, the platform implements RFC 8628 Device Authorization Grant.

<Steps>

<Step>

### Initiate

The CLI calls `POST /auth/device` with `client_id` and `scope`. Response carries `device_code`, a short human-readable `user_code`, the `verification_uri` to open in a browser, the `verification_uri_complete` form with the user code embedded as a query parameter (so the form pre-fills), and the `interval` between polls.

</Step>

<Step>

### Display and poll

The CLI prints the URL and code; the user opens the URL on any browser-capable device, signs in if needed, enters or confirms the code, and approves. Meanwhile the CLI polls `POST /auth/device/token` at the declared interval. Visiting `GET /auth/device?user_code=XXX-XXXX` short-circuits straight to the consent screen.

</Step>

<Step>

### Token issuance

Once the user approves, the next poll returns the same access + refresh token pair as the Authorization Code flow. When `openid` is among the granted scopes, an `id_token` is also returned.

</Step>

</Steps>

While the user has not yet approved, polls return `400 authorization_pending`. Polling faster than the declared interval returns `400 slow_down` and bumps the interval up. Past the device-code expiry, polls return `400 expired_token`.

### Sign-in and sign-up surfaces

The platform serves server-rendered HTML at `/auth/sign-in` and (when sign-up is enabled) `/auth/sign-up`. These are the surfaces the consent flow redirects unauthenticated users to. They also stand alone for direct sign-in to the platform's own console. Programmatic signup against a hosted Marfa instance hits `POST /auth/sign-up/email` — see [Hosted mode](/self-hosting/run/hosted-mode).

The sign-in page offers email and password, a passwordless magic link, and passkeys. When the operator configures federated identity providers, the page also renders one button per provider; choosing one posts to `/auth/sign-in/provider/<id>`, which hands off to the upstream provider's authorize flow and signs the user in on return. Provider availability is operator-configured, so the buttons appear only on instances that wire at least one provider.

### Email verification

When the operator wires a real email backend, every new sign-up must confirm its address before a session lands. Sign-up succeeds without a session cookie, and the platform sends a verification email carrying a single-use link back to `/auth/verify-email`. Clicking it confirms the account and signs the user in; the token expires an hour after issue. A user who lets it lapse requests a fresh one from the verify-email page, which posts to `/auth/verify-email/resend`. Instances without an email backend skip verification and sign new accounts in directly.

### Password reset

A signed-out user who has forgotten their password starts at `/auth/forgot-password`, submits their email, and receives a single-use reset link valid for one hour. The link opens `/auth/reset-password`, where they choose a new password; a successful reset signs out every other session. The forgot-password response is identical whether or not an account exists for the address, so the flow never reveals which emails are registered.

### OIDC identity tokens

When `openid` is among the granted scopes, the token endpoint returns an `id_token` alongside the access and refresh tokens. The id token is a signed JWT carrying:

- Required claims: `iss`, `sub`, `aud`, `exp`, `iat`
- With `profile` scope: `name`, `preferred_username`, `picture`
- With `email` scope: `email`, `email_verified`

Verify signatures against the platform's JWKS at `/auth/jwks`, which the discovery doc advertises as its `jwks_uri`. Algorithms supported are advertised in the OIDC discovery doc at `/.well-known/oauth-authorization-server` under `id_token_signing_alg_values_supported` (today: `RS256`).

For most clients the userinfo endpoint at `/auth/oauth2/userinfo` is the simpler way to fetch claim data — it returns the same shape over a request rather than as a JWT. Use the id token when verifying identity statelessly without a server round-trip; use userinfo when you have a bearer in hand and want the current claim values.

### Token revocation

`POST /auth/oauth2/revoke` implements RFC 7009. Pass the access or refresh token as `token` in a form-encoded body. The server invalidates the token (and, for refresh tokens, the entire grant) and returns `200` regardless of whether the token was valid — per the spec, to avoid leaking token-existence information.

```bash
curl -X POST https://marfa.example.com/auth/oauth2/revoke \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d 'token=marfa_at_...'
```

Apps should call this on sign-out to ensure server-side state matches the user's intent. The endpoint is advertised in the OIDC discovery doc as `revocation_endpoint`.

### Token introspection

`POST /auth/oauth2/introspect` implements RFC 7662. Form-encoded body with `token` and (for confidential clients) `client_id` + `client_secret`. The server returns `{ active: boolean, scope?, client_id?, exp?, ... }` — `active: false` is the not-valid response, never an error.

### Grant lifecycle audit

The auth audit-row catalog carries three grant-lifecycle entries:

- `auth.grant.created` — emitted on consent acceptance (both code-flow via `/auth/authorize/decision` and device-flow via `/auth/device/consent`). `details.source` distinguishes the surface; `details.created` distinguishes first-consent from re-consent.
- `auth.grant.reused` — emitted on silent re-authorization (see [Consent persistence](#consent-persistence)): the prior grant already covered the request, so no consent screen rendered and the grant record was not modified.
- `auth.grant.revoked` — emitted on `DELETE /auth/grants/:id` and the form-friendly `POST /auth/grants/:id/revoke`.

All three rows are written by Marfa route handlers, not by the plugin, so they carry the verified `client_id`, `user_id`, and grant item id without trusting form fields.

### Grants management

`/auth/grants` exposes the user's current OAuth grants — one row per `system.connection` of `kind: app`. Listing, inspecting, and revoking grants happens through this surface. Revoking a grant invalidates the associated tokens immediately. See [Connections](/guides/connections/connections) for the underlying type.

**A revoke that cannot invalidate the tokens fails rather than reporting success.** The token invalidation runs before the grant record is updated, so a failure leaves the grant reading active, which is the truth: the tokens still work. The alternative — marking it revoked and moving on — produces a security page describing access the user no longer has while that access carries on working, which is the worse of the two outcomes by some distance. `DELETE /auth/grants/:id` surfaces this as a 5xx; the form-friendly route redirects with `?notice=grant_revoke_failed`. Either way the correct response is to retry, not to assume it worked.

### Connector OAuth bootstrap

Distinct from the user-facing OAuth flow above: the platform also runs an OAuth callback at `/oauth/callback/:provider` for Integration connectors that need to establish OAuth tokens against an external service (Google Calendar, GitHub, etc.). The callback verifies a server-signed state, exchanges the upstream code for tokens, and stores them encrypted for the connector's later use through the OAuth proxy. End users see a normal upstream OAuth flow; the platform handles the bootstrap on the connector's behalf. See [Integrations](/guides/connections/integrations) for the wider context.

The bootstrap flow is hardened with two platform-side controls:

- **PKCE on the upstream authorize call.** The platform generates a code verifier per attempt, persists it inside the AES-GCM-signed state envelope, and sends `code_challenge` + `code_challenge_method=S256` on the authorize redirect. The verifier is replayed at token exchange. Connectors don't manage PKCE themselves — it's enforced by the platform regardless of what the upstream service expects, defending against authorization-code injection.
- **Redirect allow-list.** `MARFA_OAUTH_REDIRECT_ALLOWLIST` (comma-separated) lists the canonical `redirect_uri` values the bootstrap will accept. Requests whose `redirect_uri` doesn't match (after scheme + host + path normalization) are rejected at `/oauth/start` with `400`. Required in production; misconfigured deployments fail loudly rather than accept arbitrary redirects.

## Choosing between API keys and OAuth

- **API keys** for: your own apps against your own space, server-to-server calls, scripts, CI, MCP servers and CLIs connecting to a known space.
- **OAuth** for: third-party apps where the user wants explicit consent per type, revocable without rotating an API key, and a flow that terminates at a login experience.

Both produce the same server behavior — permissions enforce identically regardless of credential kind.
