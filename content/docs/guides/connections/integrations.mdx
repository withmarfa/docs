An Integration is a publishable, installable description of how Marfa talks to an external service or runs a space-internal automation. It carries everything a space needs to stand up a working `integration`-kind Connection: the trigger declarations, the OAuth or webhook authentication shape (where applicable), the runtime requirements, the bidirectional handling rules, and the permissions the integration needs against the space's items.

Integrations are persisted as `system.integration` items — one item per (`name`, `version`) pair. A space installs one specific version into a Connection; later versions are sibling items, not edits.

## The manifest contract

The manifest is the canonical description. The platform validates it on registration and on every install. Required fields:

| Field | Meaning |
|---|---|
| `name` | Handle-and-name identifier — `acme/calendar-sync`. See [Naming an integration](#naming-an-integration). |
| `version` | Semver. Used to dedupe (`name` + `version` is the registration key). |
| `publisher` | Human-readable publisher name shown to users at install time. |
| `description` | One-line summary shown to users at install time. |
| `manifest_schema_version` | Semver of the manifest contract itself, currently `2.x`. The server refuses a manifest whose major it does not support. |
| `direction` | `read`, `write`, or `both` — the data flow this integration implements. |
| `target_types` | Item types the integration reads or writes. It sets the credential's reach; it does not filter which events an `item-event` handler receives. Every entry must resolve to a registered type, or a type the manifest itself declares in `type_schemas`; registration refuses a manifest naming a type that exists nowhere. |
| `triggers` | Array of discriminated `{ type, config? }` objects. `type` is one of `schedule`, `webhook`, `item-event`, `manual`. Schedule triggers carry `config: { cron }`; the others have no config payload today. `manual` declares that a person may ask for a run through [`POST /connections/{id}/run`](#running-on-demand), and it reaches the same handler the schedule trigger does. |
| `bidirectional_handling` | The four positions: `echo_ttl_seconds`, `lag_window_seconds`, `tombstone_mapping` (`state-trashed | prompt-user | ignore`), `partial_write_mode` (`all-or-nothing | accept-partial`). Required even when `direction !== "both"`; defaults absorb the read-only case. |
| `oauth_requirements` | Per-capability map — `proxy` (route through Marfa's OAuth proxy) or `leased` (issue a short-TTL bearer for the integration's own use). |
| `token_requirements` | Per-capability map for integrations authenticated by a static upstream API token (rather than OAuth). Each entry declares `required`; the install pipeline gates on a matching `kind: api_token` credential being supplied as `credential_ref`. |
| `webhook_verification` | Discriminated on `method`: `hmac-sha256`, `slack`, `stripe`, `github`, `google-channel`, or `cloudflare-email`. The platform's adapter for each method lives in [@withmarfa/webhooks](https://www.npmjs.com/package/@withmarfa/webhooks) and is consumed by the server's webhook receipt route. |
| `permissions` (optional) | Per-axis grant — `extension` and `edge` maps. The install pipeline translates these onto the runtime credential. |

| `configuration_schema` (optional) | The connection configuration contract: every key the integration reads from the Connection's `configuration`, each with a type, a description, and optionally a required flag, a closed value set, `from_target_types` to derive the set from `target_types`, or `from_write_families` to derive it from the declared write families. Supplied configuration is validated against it at install and on every configuration write; an undeclared key is refused. The contract binds both ways: a declared key must be read by the integration's own code, and the in-tree test suite enforces that, so a key that stops being read is removed rather than left promising something on the configure screen that setting it will not do. An integration that omits the field accepts no configuration. |
| `write_families` (optional) | Named sets of target types chosen together. Each family maps the author's role vocabulary to the type each role writes (`{ show, episode }`, or just `item` for a single-type integration), with a description the configure surface shows and a declared default. The platform validates coherence centrally: every family member must appear in `target_types`, and every `target_types` entry must belong to a family. A connection selects one family with a `from_write_families` configuration key; an integration with one family needs no chooser. |
| `type_schemas` (optional) | Type schemas the integration brings with it, registered at catalog registration. Same shape and same validator as a type registered through the API. Each one must sit inside the publisher's own handle, so `readwise/reader` may declare `readwise.document` and nothing else; a reserved root is refused outright, because the platform's own vocabulary is seeded rather than registered. |
| `supports_user_mappings` (optional) | Whether the integration's handlers consult the per-connection [user mapping](#user-defined-mappings) on their write path. The mapping surface refuses connections whose integration does not declare it, so a stored mapping can never be silently ignored. |

Full schema and each field's accepted values live in the `IntegrationManifestSchema` Zod schema in `@withmarfa/shared` — published as a JSON Schema artifact alongside the SDK.

## Naming an integration

**Dots name data; the slash names an installable.** A type identifier is dotted all the way down and never carries a slash — `core.note`, `readwise.document`. An integration is the one thing a person installs, so it takes the character that says so: `<handle>/<name>`, as in `readwise/reader` or `acme/calendar-sync`.

The handle is the publisher's, under the same rules as any Marfa handle: lowercase letters, digits and single hyphens, three to thirty-two characters. The name after the slash follows the identifier rules types use, so a publisher with a family of integrations can carry a sub-namespace (`acme/calendar.events`).

Two things this grammar buys. An integration can never be mistaken for a type at a glance, which was the practical problem: a name like `readwise.reader` reads as a type identifier and is not one. And the name stays a single stable string for the catalog to key on, so a published identifier means one thing everywhere it appears.

Whether a publisher may *claim* a given handle is a separate question, answered at registration against the account that holds it, not by the shape of the string. The first-party set lives under `marfa/`.

The slash is required. Names shipped before this grammar used the dot form (`readwise.reader`), which parsed alongside the new spelling for one release while installed connections were migrated; it is no longer accepted.

The manifest identifier is the only name the platform reads. An integration ships as an npm package, and nothing in the runtime keys off that package's name: the identifier comes out of the manifest, so a package called anything at all registers under the name its manifest declares. Name the package whatever suits you.

Add the `marfa-integration` keyword to it so an npm search finds it. That is a recommendation rather than a rule, and nothing refuses a package without it.

## Types that travel with an integration

An integration can ship the types it writes. Declaring them in `type_schemas` registers them when the catalog entry is registered, so an integration is installable on an instance that has never heard of its types.

Two limits are worth knowing before relying on it.

**A publisher may only declare inside its own handle.** The handle is the part of the manifest name before the slash. This is the same ownership rule that governs registering a type directly, applied at the other door: without it a package could register into another publisher's namespace by putting the type in its manifest instead of a request body.

**A schema reaches a connection only when that connection resolves the manifest carrying it.** A connection resolves the manifest frozen on its catalog row at install time, so types shipped with a new version of an integration do not reach a connection installed against an older one.

## Write families

An integration's author ships one or more write families: coherent sets of target types with the author's own mapping code behind them. The podcasts integration is the shape in full — a `podcast` family keeping everything a feed carries, and a `core` family writing the shared media types, each pairing a show type with an episode type that travel together. A connection picks one family at configure time; the chooser's options derive from the declaration, so they cannot drift from what the credential may write.

Families exist because a flat `target_types` list cannot say which types belong together. An integration writing a container and its members offered four individual choices where only two coherent pairs existed. The family declaration carries that structure, and the platform validates it rather than each integration hand-rolling the same test.

## User-defined mappings

Shipped families are defaults, not limits. A connection can carry the user's own mapping: conditions on the incoming record choose the target type, and fields are assigned onto that type's schema. The mapping targets whatever type the user names — their own registered types included; core types hold no special place.

```json
PUT /connections/{id}/mapping
{
  "version": 1,
  "rules": [
    {
      "when": { "path": "kind", "op": "equals", "value": "episode" },
      "target_type": "user.podcast_log",
      "assign": {
        "title": { "path": "episode.title" },
        "url": { "path": "enclosure.url" },
        "listened": { "const": false }
      }
    }
  ],
  "otherwise": "family"
}
```

- **Conditions** are a closed operator set over dot-paths into the upstream-faithful record: `equals`, `not_equals`, `exists`, `missing`, `contains`, composable with `all`. First matching rule wins. There is no templating language — rule branching covers conditional values, and computed values are deliberately out.
- **Assignments** map a target field to a source path or a scalar literal. The literal exists so a required target field the source cannot supply can be satisfied.
- **`otherwise`** decides unmatched records: fall through to the selected write family (the default), or `skip`. Deliberate skips surface as one summary activity row per run.
- **Validation is wholesale at PUT**, against the connection's space registry: target types must resolve (reserved namespaces refused), every assigned field must exist on its target, and required target fields must be covered. Each refusal names the field. A record that fails its target type's validation at write time surfaces as a per-item activity row — never a silent drop.
- Only integrations declaring `supports_user_mappings` accept a mapping; the surface refuses the rest so configuration cannot silently do nothing.

## Where an integration runs

**There is one runtime.** An integration's handler code runs inside the Marfa server process, on the in-process runtime described in [Runtime substrates](/guides/connections/runtime-substrates). Hosted Marfa and a self-hosted deployment run the same image, so an integration behaves identically on both, and where the deployment lives is not something a manifest declares.

Where the code runs is the same everywhere. Who may publish is not: because handler code runs inside Marfa's own process, a hosted deployment installs only what Marfa publishes and stands behind, while the trust decision on a deployment you operate is yours. The position and the reason behind it are on the [marketplace page](/guides/connections/marketplace).

<Callout type="info">
  **Upgrading an existing deployment.** A manifest already registered in your catalog keeps the fields it was registered with, and a Connection resolves that stored copy every time it runs. So a field the contract drops is tolerated on a stored manifest and ignored, rather than refused: refusing it would fail manifest resolution, and a Connection whose manifest will not resolve loses its permissions rather than logging a warning. The tolerance is a named list of retired keys and nothing wider, so a genuine typo in a manifest still fails validation.
</Callout>

The manifest declares nothing about this, and used to. `runtime_compatibility` listed the substrates an integration supported, from a time when the in-process runtime sat beside a separate Workers one. That substrate was retired, which left a required field whose only remaining value meant "runs on the Marfa runtime", which is true of every integration. It was removed rather than renamed, because a rename would have preserved a distinction that had stopped existing. The runtime loads an integration that ships a handler entry.

Code that runs on *your* machine rather than Marfa's is a client, not an integration, and is not covered by this field. The file-sync agent is the example.

## Install flow

The install pipeline is the same wherever the deployment runs. The user installs an Integration through the console; the server then:

<Steps>

<Step>

### Validates the manifest

The Zod schema check, plus type-identifier and scope-grammar validation. Any configuration supplied at install is judged against the manifest's declared contract — an undeclared key, a wrong type, or a missing required key refuses the install. Rejected manifests never produce a Connection.

</Step>

<Step>

### Renders the consent screen

Mirrors the `/auth/authorize` consent precedent — shows the user the scopes the integration wants and the manifest's declared OAuth requirements. The user approves, modifies, or cancels.

</Step>

<Step>

### Persists the credential

The credential shape follows the integration's authentication model. For OAuth-backed integrations, the user supplies the OAuth provider config (client_id, client_secret); the server encrypts the secret and creates a `kind: oauth_token` `system.credential`. For token-authenticated integrations (manifests declaring `token_requirements`), the user supplies an upstream API token; the server encrypts the bearer and creates a `kind: api_token` credential carrying the upstream base URL and the `auth_scheme` it expects (`Bearer`, `Token`, or `Basic`). Both shapes are referenced by the Connection via `credential_ref` and resolved by the proxy at request time.

</Step>

<Step>

### Mints a runtime credential

A short-TTL API key scoped to the manifest's declared permissions and bound to the connection_id. It carries a hard expiry and the runtime refreshes it transparently as the integration runs — see [Runtime credential lifecycle](#runtime-credential-lifecycle).

</Step>

<Step>

### Creates the Connection

A `system.connection` item with `kind: integration`, `integration_ref` pointing at the manifest, `credential_ref` pointing at the persisted credential, and the manifest-derived `configuration`, `direction`, and `triggers` fields. The pipeline stamps `runtime_status: healthy` to seed the operational state.

</Step>

<Step>

### Bootstraps OAuth (when applicable)

For integrations whose manifest declares `oauth_requirements`, the consent flow continues into an OAuth Authorization Code dance against the upstream service. Tokens land in encrypted storage; the proxy reads them at request time.

</Step>

</Steps>

The result: a Connection ready to receive triggers and emit `system.activity` rows.

## The mirror rule [#the-mirror-rule]

An item an integration writes is its copy of an external record — a mirror, and the mirror stays faithful. Nothing else writes to it: not another integration, not an app, not a platform admin. A write to an integration-owned item by anyone but the owning integration is refused with `403 integration_owned`, naming the promotion path.

The owning integration re-syncs its mirror with faithful-mirror semantics: fields update per field, and a field the upstream cleared is cleared here too — an explicit null deletes the key rather than reading as "leave unset".

To make an integration's copy your own, promote it: `POST /items/{id}/promote` mints a new item you own with the mirror's content, joined back by a `derived-from` edge. The mirror keeps re-syncing; your copy is never touched by a re-sync. Lifecycle transitions, tags, and tier changes stay ordinary user gestures on a mirror — they do not edit the copy, so the rule does not apply to them.

The two drift from there, which is the point of the join. `GET /items/{id}/reconcile` reports the drift field by field against every mirror the item is joined to: each property is `same`, `diverged`, `only_yours`, or `only_mirror`, with the values on both sides. The read decides nothing and writes nothing — taking a field from the mirror is an ordinary `PATCH` on your own item, so which side wins stays yours to choose, one field at a time.

## Running a connection on demand [#running-on-demand]

An integration that declares the `manual` trigger can be run without waiting for its next scheduled tick:

```bash
curl -X POST https://api.marfa.so/connections/<connection-id>/run \
  -H "Authorization: Bearer $MARFA_API_KEY"
```

Space-admin only, like pause and uninstall, and the console offers it as **Run now** on the connection's page. The run is queued exactly as a cron tick is, so it takes the same per-connection lock and cannot overlap a run already in flight. A manual run reaches the integration's scheduled handler, which is why an integration needs no extra code to support it: declaring the trigger is the whole opt-in.

Four refusals, each naming what to do about it:

- **The manifest declares no `manual` trigger.** The declaration is the contract; without it, nothing runs.
- **The connection is paused.** Pause means stopped, and a queued run would be discarded at dispatch. Resume first.
- **The deployment does not run that integration.** An integration whose code runs on your own machine is started by that program, not by Marfa. `marfa/sync` is the standing case: it is a client, and its daemon drives it.
- **The running build and the stored manifest disagree** about whether manual runs are accepted. Moving the connection to the newer version resolves it, which is what the section below is about.

## Shipping a new version [#shipping-a-new-version]

A Connection resolves the manifest it was installed against, frozen on the catalog entry at install time. That freeze is deliberate: what an integration is allowed to do should not change under someone who already installed it because an unrelated catalog edit landed. It also means **shipping a new version of your integration does not reach anybody's Connection on its own.**

Registration keys on `(name, version)`. A new version registers as a sibling entry beside the old one, and existing Connections keep pointing at the entry they were installed against until they are deliberately moved.

Two consequences worth knowing before you publish.

**A manifest change needs a version bump, every time.** Because registration keys on `(name, version)`, a manifest whose content changes while its version stands still cannot be registered anywhere the old version already exists: it collides with the entry it was meant to replace. The change ships in your code and never reaches the catalog, with nothing reporting it. If you add a capability flag, a target type, or a trigger, move the version in the same change.

**A version bump with nothing behind it is also wrong.** It registers a second catalog entry identical to the first, which is one more manifest for a Connection to be stranded on and no new capability for anyone.

### Moving a Connection to a newer version

**A Connection that reaches nothing new moves on its own.** A background pass compares each live Connection against the newest registered version of its own Integration and applies the move where it widens nothing, writing an activity row naming the version change. That is not a decision anybody needs to make: the Connection is resolving a manifest its own deployment already ships, and holding it back protects nobody while leaving the drift number permanently above zero.

`GET /connections/{id}/upgrade` reports whether a newer version is registered and exactly what it would newly be allowed to do. `POST` to the same path performs the move, for a Connection the pass has simply not reached yet. It does not override the two things the pass declines: a widening move needs the approval route below, and one that would strand a mapping is refused everywhere.

An upgrade keeps the Connection's cursor state, so an integration resumes where it left off rather than re-pulling the upstream corpus. It re-validates the stored configuration against the new manifest and refuses the whole move if the settings no longer satisfy it, rather than leaving a Connection bound to a manifest its own configuration contradicts. It revokes the Connection's runtime credentials, so the next one minted projects its permissions from the manifest the Connection now resolves.

**A stored user mapping holds a Connection back**, even when the move widens nothing. A version that stops declaring support for mappings would strand one the space had already set: the rules would keep being applied and nothing could edit them again. Every route refuses the move with `409`, and the background pass leaves such a Connection alone rather than attempting it. Clear the mapping first if you want the Connection to move; clearing still works, it is only editing that the newer version takes away. This is not a consent question, because agreeing to it would not bring the mapping back.

**Widening needs consent.** The upgrade compares what the two manifests grant, not their version numbers: target types, extension and edge permissions, credential requirements, and configuration fields that become required. A version that takes the same or less proceeds. A version that reaches further is refused with `403`, naming exactly what is new. One that would also strand a mapping is refused with `409` for that instead, since no amount of agreeing brings a mapping back. This is why adding a target type to a shipped Integration is a bigger change than it looks: everyone who installed it has to agree to the new one.

**Approving one is a separate route.** `GET /connections/upgrades/pending` lists the Connections in your space held back this way, each with the version it would move to and the sentences describing what that move would newly allow. `POST /connections/{id}/upgrade/approve` performs it, and the body names the version being approved:

```json
{ "to_version": "2.0.0" }
```

Naming the version is what keeps an approval attached to what was read. If a further version registers between the list and the approval, the request is refused with `409` and names the candidate it found instead, rather than carrying the decision onto a widening nobody saw. Approving a move that turns out to need no approval is refused the same way, because the ordinary upgrade route already handles those and the background pass will take them without being asked.

Both routes need space-admin authority, which a platform credential also carries.

A Connection that would *both* widen and strand a mapping appears on neither list: it is not a decision anybody can make, so it is counted as blocked rather than offered for approval. `GET /connections/{id}/upgrade` on that Connection still reports what it would change, and the refusal names the mapping. The plain `POST /connections/{id}/upgrade` cannot approve anything: consent is not readable from its request body, so a caller cannot approve on its own behalf.

<Callout type="warn">
  **There is no screen for this yet.** The routes above are the whole surface today, so approving a widening upgrade means calling the API. A Connection left unapproved stays on the version it installed and keeps working.
</Callout>

**Triggers are not part of that comparison, deliberately.** A trigger changes when an Integration runs, not what it can reach, so adding one is not a widening and moves on its own. Reach is target types, the permission maps and the credential requirements.

This is also the difference between an upgrade and a reinstall. Uninstalling and reinstalling picks up the newest catalog entry, but it creates a new Connection with no cursor state and re-pulls everything the integration can see.

## Uninstall and reinstall [#uninstall-and-reinstall]

Item provenance keys on the integration and the space, not the Connection, so removing an integration and installing it again lands on the items already there: the first re-sync resolves each upstream record by its natural key and updates the existing row rather than storing a second copy. Uninstall itself never touches items — what an integration synced stays in the space, attributed to the integration, whether or not a Connection currently exists for it.

## OAuth proxy and leased tokens

Integrations don't hold OAuth tokens directly. The platform offers two patterns, declared per-capability in `oauth_requirements`:

- **`proxy`** — the integration calls a Marfa endpoint with its runtime credential; Marfa injects the upstream OAuth bearer and forwards the request. Tokens never leave the platform.
- **`leased`** — the integration requests a short-TTL bearer for direct calls (used when the proxy can't carry the request shape: multipart uploads, streaming, non-HTTP protocols).

Both routes audit every call. Refresh-on-401 with refresh-token rotation is handled centrally; replay detection trips the Connection into `runtime_status: reauth_required` and surfaces an `action_required` activity row.

## Token-authenticated integrations

Not every upstream uses OAuth. An integration targeting an API authenticated by a long-lived bearer token declares `token_requirements` in its manifest; the install pipeline gates on a `kind: api_token` credential supplied as `credential_ref`. The credential carries the encrypted bearer, the upstream base URL, and the `auth_scheme` to stamp on the request header (`Bearer`, `Token`, or `Basic` — the wire format some services demand instead of `Bearer`).

The proxy stamps the configured `auth_scheme` on the upstream call uniformly with the OAuth path. From the integration's perspective the call shape is identical — it issues a request against the runtime credential and the platform substitutes the upstream auth. The substantive difference is the absence of a refresh dance: static tokens don't expire and have no refresh primitive. A 401 from the upstream surfaces as `action_required` and trips the Connection into `runtime_status: reauth_required` — the user updates the token to recover.

A single `kind: api_token` credential can be shared across Connections that target the same upstream base. When an integration's upstream lives on a different host than the credential's default, the Connection sets `properties.configuration.upstream_base_url_override` and the proxy consults it before falling back to the credential's URL. This lets a family of related integrations share one credential row across distinct upstream hosts.

## Removing a credential

`DELETE /credentials/{id}` removes a credential and the secret it holds. Space admins may remove credentials in their own space.

The delete is hard rather than soft: the encrypted secret is gone, not left behind on a row marked inactive. A credential holds something a person pasted in from another service, so leaving it recoverable would defeat the point of removing it.

Removal refuses with `credential_in_use` while any Connection that is not revoked still references the credential, and the response names those Connections. Uninstall them first — and uninstalling the last one removes the credential on its own, so this route is for a credential no Connection ever used, or one whose Connections were revoked before uninstall did this. Refusing is deliberate: taking a working integration down as a side effect of tidying up a credential is the more surprising of the two behaviours.

Credential removal has its own route rather than going through `POST /items/{id}/transition`. Items carry the universal `active | archived | trashed` lifecycle, while `system.*` types carry a bounded `active | revoked` one, and the transition endpoint validates against the universal set — so the states a system type actually uses are not reachable through it.

Uninstalling a Connection removes the upstream credential it was installed with, unless another Connection that is not revoked still references it — several Connections may share one row, and the four Google integrations do.

Three different things are called a credential here, and uninstall reports each separately for that reason. The **runtime credential** is Marfa's own, minted per dispatch and revoked routinely, so an uninstall often finds none left to revoke. The **cached upstream OAuth tokens** are the proxy's working copy, and a token-authenticated Connection never has any. The **upstream credential** is the secret a person pasted in, and nothing in the platform can recreate it. The response's `upstream_credential` field distinguishes `purged`, `retained` (naming the Connections still using it), `already_gone`, and `none`.

Removing the stored credential does not invalidate the token at the far end. A token you want dead everywhere is revoked at the service that issued it.

## Runtime credential lifecycle

A runtime credential is a machine credential, not a human one. The runtime obtains a fresh one for each dispatch, so no integration needs to hold one for long. The rules below keep that fleet bounded and keep each credential answerable for exactly one Connection.

**Scoped to the manifest.** The server derives a credential's reach from the Connection's persisted manifest at every mint. Each `target_types` entry receives write access because `direction` describes flow relative to the upstream service: a read Integration pulls from upstream and writes the result into Marfa. The manifest's `permissions.extension` and `permissions.edge` maps supply the other declared grants. Two substrate rules complete the projection: write access to `system.activity` for status reporting, and write access to the credential's own `connection.runtime` extension. Reading configuration is a per-item exception limited to the credential's own Connection, not a space-wide `system.connection` grant. If the manifest cannot be resolved, the credential keeps only the substrate grants and never receives wildcard reach.

**Scoped to its own rows, not just its own types.** Write access to `system.activity` is a substrate grant every runtime credential holds, because reporting progress is what it is for. A type grant alone would therefore let any integration reach every other integration's activity in the same space, so a second check runs on the row itself: a credential may only write activity attributed to its own Connection.

That applies to every surface reaching an item, not only the ones that write `properties`. Changing a row's lifecycle state, restoring it, tagging it, rewriting its metadata, or writing an extension namespace onto it all answer to the same rule. It is one check shared by those surfaces rather than a rule each of them remembers, because the surfaces that forgot it were found one at a time.

**Scoped to a space.** A credential inherits the Connection's space, never the broker's. On a multi-space deployment the server refuses to mint for a Connection that belongs to no space at all: a credential with no space is not a narrow credential but a platform one, and it would read every space's items. The refusal covers every path that mints, installation included, so an install that names no space fails and rolls itself back rather than leaving a Connection behind. A Connection installed before that check existed stays installed and cannot dispatch until it is moved into a space. Either way the trade is the intended one: a Connection that refuses to run is recoverable, and one quietly reading other spaces' data is not.

**Bound to its Integration.** Every mint names the Integration the runtime authenticated as, and the server checks that name against the manifest persisted on the Connection at install time. An integration that somehow reaches the broker holding another Integration's Connection ID (Connection IDs are not secrets; they appear in operator surfaces and in logs) is refused. The check runs against state the runtime cannot edit, which is why it lives on the server rather than in the runtime that made the claim.

**Bounded lifetime.** Every runtime credential carries an expiry stamped at mint. A request bearing a credential past its expiry is refused with `401 unauthorized`, exactly as a revoked credential would be. Human-minted API keys are unaffected: they carry no expiry and never expire on their own.

**Superseded on mint.** Minting a fresh credential for a Connection retires every earlier credential it has, expired or not. Retiring only the expired ones left the fleet bounded by the TTL alone, so a Connection dispatching faster than its credentials expire accumulated live credentials it had no use for. Revoking the unexpired ones is safe because dispatches for one Connection are serialized: when a mint runs, no other dispatch for that Connection is in flight, so no sibling credential is in use.

**Reaped in the background.** A Connection that stops dispatching stops superseding its own credentials, so a background job is the backstop. Each tick it revokes credentials past their expiry, retires credentials that carry no expiry once they age past the mint TTL plus a grace window, and hard-deletes revoked runtime-credential rows more than seven days old. Cadence is `MARFA_RUNTIME_CREDENTIAL_REAPER_INTERVAL_MS` (hourly by default; `0` disables). Only runtime credentials are touched — human-minted keys are never revoked or deleted by the reaper.

**Serialized against uninstall.** Every path that mints, installation included, takes the same per-Connection lock as uninstall, and re-reads the Connection's state while holding it. Without that, an uninstall could revoke every credential a Connection had at the moment a mint was midway through issuing another, leaving a live credential behind a revocation that was supposed to end it.

<Callout type="info">
Upgrading an instance that ran before credential expiry existed? Its accumulated runtime credentials carry no expiry, so the reaper's first passes retire them by age. Integrations are unaffected: the next dispatch mints a fresh credential. Human-minted keys are untouched.
</Callout>

### What a rotation does not change

Credentials rotate constantly; two things deliberately do not move with them.

**Item provenance.** Items an integration writes are stamped with a `source` derived from the Connection, not from the credential that happened to be live. That matters because natural-key identity is the `(source, source_id)` pair: an integration re-syncing an upstream record looks it up by that pair, and a `source` that changed on every credential refresh would make the lookup miss and store a second copy. Provenance is fixed for the Connection's lifetime, so re-syncing the same upstream record always updates the same item however many credentials have come and gone.

**Activity attribution.** An integration writes `system.activity` rows to report progress and ask for attention, and every operator surface groups those rows by `connection_id`. A runtime credential may only write activity for its own Connection: it cannot create a row attributed to a sibling, edit a sibling's row, or re-point one of its own rows at a sibling afterwards. Without that rule, one integration could raise an `action_required` prompt against an integration that is working perfectly, and nothing about the row would say where it came from.

## Reactive runs and cycle detection

Integrations that declare `triggers: item-event` receive every item event in their space. The platform routes events through a per-Connection queue with backpressure; cycle metadata (originating connection, hop count) flows on every event so an integration that writes back into Marfa cannot infinite-loop. The default ceiling is five steps, and a space can change it: see [the event hop budget](/self-hosting/run/configuration#the-event-hop-budget).

Three gates run before an event reaches a subscriber, and no others:

- The item must not be a `system.*` row. Activity, connection lifecycle, credentials and the integration catalog are the platform's own bookkeeping. Reporting progress writes a `system.activity` row, which is itself an item event, so without this gate two reactive integrations in one space answer each other's log lines and walk the hop counter to its budget without either writing anything a handler wanted.
- The event must belong to the subscriber's space.
- The event must not be one the subscriber's own writes produced.

`target_types` is a permissions declaration, not a subscription filter, so a handler still receives events for domain types it never named and has to check `event.item.type` itself before acting.

## Inbound webhooks

When an integration declares `triggers: webhook`, the platform exposes a public receipt endpoint per subscription, verifies the signature using the adapter named in `webhook_verification.method`, deduplicates on the sender's delivery id, and enqueues for the per-Integration Worker. See [Inbound webhooks](/guides/realtime/inbound-webhooks) for the full surface — the verification adapters, dedup semantics, the per-Connection DLQ, and the manual replay endpoint.

## Versioning and upgrades

Manifests are versioned by semver. A patch or minor bump produces a new sibling `system.integration` item, and a live Connection follows it on its own where the new version reaches nothing further. A version that widens what the Integration can reach waits, as above.

The runtime credential's permissions are projected from the persisted manifest at mint time. A consenting reader sees exactly what each version requires.

## Choosing what an integration writes

Most integrations write one shape. Some let a Connection choose, because two honest answers exist and only the person installing it knows which they want.

`marfa/podcasts` is the clearest case. It polls podcast RSS feeds and can write either family:

- **Its own types** (the default) — `withmarfa.podcast.show` and `withmarfa.podcast.episode`, which keep everything a feed carries: the enclosure's MIME type and claimed size, the duration exactly as written as well as normalized, explicitness, categories, episode type.
- **The core types** — `core.media.series` and `core.media.episode`, which every app that understands core media can already read, and which cannot hold the fields above.

The choice is a configuration key on the Connection, so two Connections to the same integration can answer differently.

```json
POST /connections/install
{
  "integration_id": "<id>",
  "configuration": {
    "feed_urls": ["https://feeds.example.com/a-show"],
    "write_family": "core"
  }
}
```

Fidelity is the default everywhere this appears. An integration type round-trips what the upstream considers authoritative, and a field dropped on the way in cannot be recovered later; a reader that wants core shapes can be added at any time, but a re-import cannot un-lose a value. Pick core when another app has to read the data without knowing the vendor, and accept the loss knowingly.

Episodes join their show through the `in-collection` edge in both families, with the episode as the source. Containment is structural rather than part of a type name, so the same edge works whichever family the Connection writes.

## A minimal example — the RSS Watcher

The simplest integration possible is a schedule-driven reader against a public source. `marfa/rss-watcher` ships in-tree and polls an Atom 1.0 or RSS 2.0 feed on a cron, creating a `core.bookmark` per new entry. No OAuth, no token, no webhook — just the manifest declaring its shape and a handler that runs once per tick.

```ts
export const RSS_WATCHER_MANIFEST: IntegrationManifest = {
  name: "marfa/rss-watcher",
  version: "0.1.0",
  manifest_schema_version: "2.0.0",
  publisher: "marfa",
  description:
    "Polls an Atom 1.0 or RSS 2.0 feed on a schedule and creates a core.bookmark per new entry.",
  direction: "read",
  target_types: ["core.bookmark"],
  triggers: [{ type: "schedule", config: { cron: "0 * * * *" } }],
  bidirectional_handling: {
    echo_ttl_seconds: 60,
    lag_window_seconds: 60,
    tombstone_mapping: "ignore",
    partial_write_mode: "accept-partial",
  },
  oauth_requirements: {},
  webhook_verification: { method: "hmac-sha256" },
  permissions: {
    extension: { "connection.runtime": "write" },
    edge: {},
  },
};
```

Three details worth calling out:

- **`oauth_requirements: {}`** — the integration authenticates against the upstream by virtue of the feed being public. No OAuth provider, no token credential required at install. `token_requirements` is similarly omitted.
- **`webhook_verification`** — required by the schema for shape-uniformity, but the value is informational for an integration that doesn't carry a `webhook` trigger.
- **`bidirectional_handling`** — required for every integration, even read-only ones. The defaults absorb the read-only case; tombstone mapping is `ignore` because there's nothing to retract.

Installing from the integration's own install page renders the declared configuration as form fields, so a required key with no default (this integration's `feed_url`) is collected there; the JSON install route accepts the same keys in its `configuration` body. Either way the install refuses a submission that does not satisfy the contract, naming the key.

The handler is a single `registerScheduleHandler` call against `@withmarfa/runtime-sdk`, fetching the feed, diffing against the connection's cursor, and emitting `CreateItemInput` per new entry. The same `dist/local.js` entry runs on both [runtime substrates](/guides/connections/runtime-substrates); the integration author writes the handler once.

Use this shape as a starting point — every other in-tree integration layers more onto the same skeleton (OAuth proxy for the Google family, token credentials for Todoist / Readwise / Raindrop, an `item-event` trigger for bidirectional sync, a `webhook` trigger for push-driven sources).

Most of those write a **integration type** rather than a core one, so the upstream payload round-trips without being flattened on the way in. The set that ships, and the trade against writing the core type instead, is on [Types](/guides/core-model/types#integration-types).
