title: Marketplace
description: The catalog of installable integrations, and how publishing works.

The marketplace is the catalog of integrations a space can browse and install. Every listing is a registered integration: one `system.integration` item per (`name`, `version`) pair, carrying the manifest that declares what the integration does, what it needs, and what it may touch.

Three deployment shapes coexist:

- **Pure-local users** never touch the catalog. Their schemas stay private.
- **Self-hosted users** run whatever their own deployment ships, which is their decision rather than Marfa's.
- **Hosted users** install from the catalog surface in the console.

## Two kinds of installable thing

The clean axis is declarative schemas versus active integrations.

- **Types — declarative.** A type is a schema: no runtime, no credentials. A space registers its own types at runtime via `POST /types`, and a type is portable by construction — inspect the JSON, copy it, register it in another space or on another deployment. There is no publishing step between spaces: sharing a type today means sharing its definition. See [Authoring types](/guides/schema/authoring-types).
- **Integrations — active.** Running code, so installing one is heavier:
  - **A runtime to host the code.** There is one, and the server is it; see [Integration runtime](/guides/connections/runtime-substrates).
  - **A scoped permission set declared in the manifest.** Which item types it writes, which extension namespaces it touches, which edge types it traverses, which upstream credentials it needs. Shown at install; the runtime credential is projected from the manifest, so an integration can never reach more than it declared.

For the manifest contract, see [Integrations](/guides/connections/integrations).

## Publisher identity

Publisher identity is the Marfa handle — see [Handles and publishers](/guides/identity/handles-and-publishers). Publishing under a handle means owning it: registering a type in a publisher namespace requires the caller's account to hold that handle, and `marfa` is the platform's own handle.

## Versioning

Semver: patch and minor are additive, major is breaking. Each (`name`, `version`) pair persists as a sibling `system.integration` item, and published entries are frozen: a correction ships as a new version, never an edit to an existing one. A space installs against one of those rows.

**A version is frozen once registered.** Registering a (`name`, `version`) the catalog already holds never replaces it, and the route answers a publisher with a `409`. So a manifest whose declarations change while its version stands still cannot reach an installed Connection: the catalog keeps answering with the entry it collided with. The runtime reads a few fields, such as trigger schedules, from the built code rather than the catalog row, so those do move on a redeploy; everything a Connection is granted comes from the frozen row.

**In-tree integrations carry a second guard.** A committed lock records what each one declares and at which version, and a test in the ordinary suite fails on both a declaration change that does not move the version and a version that moves with no declaration change. It hashes the manifest's canonical form, so reformatting a file is not a change. It covers every integration Marfa ships and the manifests the server itself carries, each guarded where its source lives; a third-party publisher does not pass through it.

**What the version number is not.** Nothing ties it to what the manifest grants. The platform does compare two manifests, on their declared reach rather than their numbers, and it does that at upgrade rather than at registration: a version taking the same or less applies on its own, and one reaching further is refused.

That refusal holds until a space admin lifts it, one Connection at a time, through [the approval route](/guides/connections/integrations#moving-a-connection-to-a-newer-version). Nothing does it in bulk and nothing does it automatically. So a patch bump that widens a permission set registers cleanly and then stops every Connection moving until somebody reads what it would newly allow and says yes, while a major bump that narrows applies to all of them without anyone being asked.

Version to say what you did. Consumers read the number, and the platform will not correct you. See [Moving a Connection to a newer version](/guides/connections/integrations#moving-a-connection-to-a-newer-version) for what the comparison covers and what else can hold an upgrade back.

## Who can publish, and where the code runs

Integration code runs inside Marfa's own process, in a worker thread beside every credential the deployment holds. That one fact decides publishing, and it decides it differently for each deployment shape. [How integrations work](/guides/connections/how-integrations-work) covers the delivery side: what a deployment has to carry before any of this applies.

**Hosted Marfa installs only what Marfa publishes.** The catalog on a hosted deployment is the set Marfa wrote and stands behind. Opening it to anyone's code would mean isolating every integration from the process it runs in: a materially heavier runtime, and a trade not taken.

**On a deployment you operate, the trust decision is yours.** The process is yours, every integration in it holds your deployment's credentials, and Marfa's judgment about what belongs in a hosted catalog does not bind it. The posture is the one you already accept installing an npm package into an application you run. See [Integration runtime](/guides/connections/runtime-substrates).

**To push data into hosted Marfa from your own program, use the API.** It is open to every account, needs no publishing step, and runs on your own infrastructure rather than Marfa's, which makes it a client rather than an integration. See [Building a client](/sdks/building-a-client).

The catalog carries no trust tiers, verified-publisher badges, ratings or install counts. Outside it entirely: themes and view extensions, since apps own their UI; a billing layer; and federation between registries.
