title: Marketplace
description: The catalog of installable integrations, and how publishing works.

The marketplace is the catalog of integrations a space can browse and install. Every listing is a registered integration: one `system.integration` item per (`name`, `version`) pair, carrying the manifest that declares what the integration does, what it needs, and what it may touch.

Three deployment shapes coexist:

- **Pure-local users** never touch the catalog. Their schemas stay private.
- **Self-hosted users** install the integrations Marfa publishes, plus any other package the operator chooses to add.
- **Hosted users** install from the catalog surface in the console.

## Two kinds of installable thing

The clean axis is declarative schemas versus active integrations.

- **Types — declarative.** A type is a schema: no runtime, no credentials. A space registers its own types at runtime via `POST /types`, and a type is portable by construction — inspect the JSON, copy it, register it in another space or on another deployment. There is no publishing step between spaces: sharing a type today means sharing its definition. See [Authoring types](/guides/schema/authoring-types).
- **Integrations — active.** Running code, so installing one is heavier:
  - **A runtime to host the code.** There is one, and the server is it; see [Integration runtime](/guides/connections/runtime-substrates).
  - **A scoped permission set declared in the manifest.** Which item types it writes, which extension namespaces it touches, which edge types it traverses, which upstream credentials it needs. Shown at install; the runtime credential is projected from the manifest, so an integration can never reach more than it declared.

For the manifest contract, see [Integrations](/guides/connections/integrations).

## Publisher identity

Publisher identity is the Marfa handle — see [Handles and publishers](/guides/identity/handles-and-publishers). Publishing under a handle means owning it: registering a type in a publisher namespace requires the caller's account to hold that handle, and `marfa` is the platform's own handle.

## Versioning

Semver, server-enforced. Patch and minor changes are additive; a major change is a new artifact. Each (`name`, `version`) pair persists as a sibling `system.integration` item, and published entries are frozen — a correction ships as a new version, never an edit to an existing one. Spaces pin a version at install time. The server-side diff at registration enforces correct bumps; see [Authoring types — the version field](/guides/schema/authoring-types#the-version-field-and-the-diff-rail).

## Who can publish, and where the code runs

Integration code runs inside Marfa's own process, in a worker thread beside every credential the deployment holds. That one fact decides publishing, and it decides it differently for each deployment shape.

**Hosted Marfa installs only what Marfa publishes.** The catalog on a hosted deployment is the set Marfa wrote and stands behind. Opening it to anyone's code would mean isolating every integration from the process it runs in: a materially heavier runtime, and a trade not taken.

**A self-hosted deployment installs anything.** The operator adds whichever packages they choose and carries the risk knowingly, the same posture as installing an npm package in any application they run. See [Integration runtime](/guides/connections/runtime-substrates).

**To push data into hosted Marfa from your own program, use the API.** It is open to every account, needs no publishing step, and runs on your own infrastructure rather than Marfa's, which makes it a client rather than an integration. See [Building a client](/sdks/building-a-client).

The catalog carries no trust tiers, verified-publisher badges, ratings or install counts. Outside it entirely: themes and view extensions, since apps own their UI; a billing layer; and federation between registries.
