## What makes something an integration

**An integration is whatever ships a manifest and installs as a Connection.** The upstream can be a vendor's API, an open protocol, Marfa's own infrastructure, or nothing outside your space at all. None of that changes what the thing is; it changes only what it talks to.

The other kind of Connection is an OAuth grant to an app, which carries no manifest at all. That is the line the model actually draws. See [Connections](/guides/connections/connections).

**Where the code runs is a separate question, and the manifest answers it.** `runs_on` takes one of two values.

| `runs_on` | Where the code runs | Example |
|---|---|---|
| `server` (the default) | The Marfa deployment's own runtime, which dispatches it | A calendar sync. Marfa holds the upstream grant and makes the calls. |
| `client` | A machine the deployment does not have, so the program that owns it starts every run | Marfa's own file-sync tool. It watches a filesystem, so it can only run on the machine holding the files. |

Anything reaching a device is `client` for the same reason. A phone's reminders or its messages can be read only from the phone, so the program reading them runs on the phone. Declaring `server` would not make it dispatchable — the field records a fact about the code, and a manifest that misstates it produces a Connection that never runs.

**A `client` integration is an integration in every other respect.** It carries a manifest, holds credentials, reports activity, and appears in the catalog exactly as any other does, because those are useful whoever runs the code. The single thing it does not get is dispatch: [running a connection on demand](/guides/connections/integrations#running-on-demand) reads `runs_on` before anything else and refuses, naming where the code runs. [Building a client](/sdks/building-a-client) covers writing one.

## Integration code is not sandboxed

There is one runtime and it is the Marfa server. Handlers run in worker threads inside the server process, pooled per integration, with Postgres underneath for scheduling and state.

**The isolation is against faults, not against the integration.** A worker thread stops a crashing handler taking the server down and caps the memory it can hold. It does not stop the code doing anything the process can do, and the process holds every credential the deployment has.

That one fact decides the rest of this page: who may publish, what a hosted deployment installs, and why adding an integration is a deployment action rather than a click. The mechanics of scheduling, queuing, per-connection locking, and credential minting are on [Integration runtime](/guides/connections/runtime-substrates).

## The manifest and the code are separate deliveries

Registering a manifest and putting code on a deployment are two acts, and only one of them is an API call.

- **The manifest** is the catalog entry. `POST /integrations` registers one `system.integration` item per name-and-version pair, describing what the integration writes, what triggers it, and what authority it needs. See [the manifest contract](/guides/connections/integrations#the-manifest-contract).
- **The code** is a built entry in the directory the runtime loads from. Nothing puts it there over the network.

A manifest whose code is absent registers, installs, and produces a Connection holding credentials, configuration, and observability. It dispatches nothing. That is a supported shape rather than a broken one: it is what a `runs_on: client` integration looks like from the server's side, where the code is somewhere the deployment cannot reach.

## How the runtime finds an integration

The runtime reads its integrations directory at boot, two levels deep: one directory per publisher, each holding one directory per integration. A candidate is therefore a publisher and a name together, and two publishers can ship the same name without collision. Names beginning with a dot or an underscore are skipped as tooling and scaffolding, at either level. A candidate with no built entry, or one whose manifest fails validation, is skipped and the reason logged. The runtime itself keeps no list of what to expect: a candidate is whatever is actually staged in the directory, not an entry it looked up. A deployment's own build can declare and enforce a fixed installed set separately, which is a different check on a different surface: see [Which deployments carry which integrations](#which-deployments-carry-which-integrations).

**The identifier comes out of the manifest**: a publisher handle and a name joined by a slash, as in `readwise/reader`. That is the string the catalog keys on and the only name the platform reads. The two directory levels mirror it, so a directory states which integration it holds rather than merely being named after it. The manifest is still what names one; the directory only decides where the runtime looks. See [Naming an integration](/guides/connections/integrations#naming-an-integration).

<Callout type="warn">
  **Integrations load at boot, so adding one is a deployment action.** There is no
  hot reload and nothing watches the directory: place the built output, restart the
  server, and the boot reconcile registers what it found. The reconcile adds
  name-and-version pairs the catalog does not already hold, and never rewrites one
  it does.
</Callout>

**No command installs an integration into a deployment.** `marfa connections install` is a different operation: it connects and configures an integration the deployment already carries, creating the Connection; the runtime mints credentials per dispatch. It delivers no code, and nothing else does either.

## Which deployments carry which integrations

| Deployment | What it carries |
|---|---|
| Hosted Marfa | The set the server image was built to install. |
| Container self-host | The same set, from the same build. |
| Self-host from a source checkout | Whatever the checkout's integrations directory holds. |

**The image declares its own integration set and is held to it.** The build stages exactly the integrations the server declares it installs, and a verification step inside the image fails the build unless exactly those arrived, each in the shape it was declared in and each one importable. Installing nothing is a legitimate shape, and the declaration has to say so in as many words rather than being left empty.

A container self-host therefore assembles nothing to get the shipped set. `MARFA_INTEGRATIONS_ROOT` already points at the directory the image populated; set it yourself when the server runs outside a source tree, or to point it somewhere else. `MARFA_INTEGRATION_WORKER_THREADS` sizes the pool. Both are in [Configuration](/self-hosting/run/configuration#integration-runtime), and the [Docker Compose quickstart](/self-hosting/run/docker-compose) covers the stack.

The runtime needs Postgres. On SQLite it stays off, though the catalog still reconciles, so such a deployment lists what it could install and runs none of it.

## What an integration writes is yours to redefine

An integration ships one or more write families: coherent sets of types its own code knows how to fill. A Connection picks one at configure time. Beyond that, a Connection can carry the user's own mapping, where conditions on the incoming record choose the target type and fields are assigned onto it, including onto types the user registered themselves.

The manifest sets the ceiling on what an integration may touch; the mapping decides what it does touch. See [write families](/guides/connections/integrations#write-families) and [user-defined mappings](/guides/connections/integrations#user-defined-mappings).

## What names a synced item

An item mirrored from upstream is identified by `(source, source_id)`. **`source` is stamped by the platform** from the integration and the space — never from the individual connection. That is deliberate: it means uninstalling and reinstalling lands on the items already there rather than forking the corpus.

**`source_id` is the handler's**, and the consequence of the rule above is the thing to design for: **two connections of one integration in one space share a single `source_id` namespace.** Somebody connecting two accounts of the same service gets two connections, and if both write a bare upstream id, the second collides with the first.

**Scope `source_id` unless the upstream documents that its identifier is globally unique.** Take the scope from upstream data — the account, the calendar, the mailbox, the feed — rather than from the connection's configuration, and compose it per record:

```ts
// The account this record belongs to, read once from upstream and kept on
// the cursor, then composed into every key the handler writes.
source_id: `note:${accountId}:${note.id}`
```

Three properties make that work, and each fails differently if dropped.

**Read the scope from upstream, not from configuration.** A connection id changes on every reinstall, so keying on one re-imports the whole corpus as duplicates. Configuration a person edits has the same problem in slower motion.

**Compute it once and read it from stored state.** Re-deriving it per tick invites two derivations to disagree.

**Land every write path on the same rung.** Taking identity from upstream is necessary and not sufficient. Where a handler falls back — a guid, else an enclosure URL, else a digest — two passes over the same record can land on different rungs and produce two keys for one thing. That is not hypothetical: a feed drain and a directory backfill did exactly this, agreed on the rule, disagreed on the rung, and turned 57 recordings into 171.

**Over-scoping is the safe direction.** Two connections pointed at one account keeping separate copies is untidy and visible. Under-scoping overwrites silently, and the platform cannot always catch it for you: a write that resolves a row a *live* sibling connection wrote is refused with `provenance_collision`, but a row whose writer has been uninstalled is adopted, and that is what keeps reinstall working.

**Some records genuinely need no scope.** An identifier the upstream guarantees platform-wide is already unique, and scoping one can be actively wrong — an email delivered to two of your addresses is one email, and giving it two keys makes it two.

## Hosted runs a curated set, and that is the trade

Because handler code runs inside Marfa's process beside every credential, a hosted deployment installs only what Marfa publishes. Opening that catalog to arbitrary code means isolating every integration from the process it runs in, which is a materially heavier runtime. The trade is not taken.

**On a deployment you operate, the decision is yours.** The process is yours and so are the credentials in it, so Marfa's judgment about what belongs in a hosted catalog does not bind it. The posture is the one you already accept installing a dependency into an application you run.

Neither position limits reaching Marfa with your own program. The API is open to every account and needs no publishing step, and code you run on your own infrastructure needs no publishing step either — it installs as a `runs_on: client` integration, or as nothing at all. [Marketplace](/guides/connections/marketplace) has the catalog side of this.

## Writing your own

You can, by two routes with different standing.

**Reaching hosted users means being merged into the integrations repository.** What merges is what hosted Marfa ships, reviewed like any other change. That repository is not public, so getting an integration into it is a conversation with Marfa rather than a pull request you can open.

**Your own copy on a deployment you operate** needs nobody's agreement, because the runtime only reads a directory: build it, place it, restart. It is also listed by nobody and vouched for by nobody, so it is an escape hatch rather than a distribution path.
