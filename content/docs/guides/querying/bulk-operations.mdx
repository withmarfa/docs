Three endpoints move data and mutate many items at once, each shaped around where the target set comes from.

<Callout type="warn">
  All `/items/bulk*` and `/edges/bulk` endpoints are admin-only. The server stamps `source` from the credential, so bulk writes cannot forge provenance and only platform admins can mass-mutate across sources. Third-party integrations writing many items should use `POST /items` with `source_id` per item: the server upserts on `(source, source_id)`, so re-posts merge in place without needing a bulk endpoint. See [Items — relationships, lists, and writes](/guides/core-model/items#relationships-lists-and-writes).
</Callout>

| Endpoint | Shape | Use when |
|---|---|---|
| `POST /items/bulk` | List-in, items | The caller holds the payload: an importer, a reconciler, a replay of an external source. |
| `POST /items/bulk-actions` | Filter-in, items | The target set is defined by a filter, such as "archive everything tagged wip" or "purge every trashed item older than 90 days". |
| `POST /edges/bulk` | List-in, edges | Edges whose source and target exist already: replies, attachment links, a reply tree assembled after its items land. |

A fourth endpoint, `POST /admin/restore-archive`, ingests a tar.gz produced by [`GET /export?format=archive`](/guides/querying/export). It sits under Admin because it is a space-restore operation, not an item-level write.

<Callout type="info">
  Every bulk endpoint writes **one aggregate audit entry per call**, and every bulk write reaches the event log and the change stream unconditionally. That record is what a client rebuilding its state reads, so a write kept out of it is one that client can never learn about.

  `enable_fanout` defaults to `false` and governs the outbound work only: per-item and per-edge webhook delivery, and the integration reactions a bulk import would otherwise trigger. Bulk calls should not flood subscribers with deliveries; they are in the record either way.
</Callout>

## Inline edges on items.bulk vs standalone edges.bulk

Both ways of writing edges alongside items exist. Pick based on whether source and target live in the same batch.

| Situation | Endpoint |
| --- | --- |
| Edge source and target both in the same bulk-items payload | Inline `edges` block on `/items/bulk` |
| Edge source or target was created in an earlier batch (or already existed) | Separate `/edges/bulk` pass after items land |
| Mode-transition migration at space scale (Local → Marfa, iCloud → Marfa) | `/items/bulk` first, then `/edges/bulk` — cross-batch edges can't ride inline |

## Bulk items

`POST /items/bulk`. Admin-only. Up to 5000 items per call.

### Modes

- **`upsert`** (default) — match existing rows by `(source, source_id)` and update in place. Properties merge shallow-ly, last-writer-wins per key. Tags replace if provided. Edges union-merge if provided. Unprovided fields leave the existing row alone.
- **`create_only`** — matching rows surface as `skipped`, not updated. Only new `(source, source_id)` pairs get written. A row matched by an `id` you supplied is `skipped` with reason `duplicate_id`, which is this door's form of the acknowledgement the single-item route gives: the create already happened, so the entry reports what is there rather than failing. The match ignores state, so a repeat landing on a row you have since trashed is skipped too, rather than colliding and rolling an atomic batch back.

### Atomic flag

`atomic: true` (default) wraps the batch in one transaction — any failure rolls back every write in the call. `atomic: false` runs per-item, returning per-item outcomes and continuing past errors.

<Callout type="warn">
  `source` is server-stamped from the credential. Any caller-supplied `source` is silently overwritten — bulk writes cannot forge provenance.
</Callout>

### Outcomes

Every response carries per-item `results`:

```json
{
  "counts": { "created": 42, "updated": 3, "skipped": 1, "errored": 0 },
  "results": [
    { "index": 0, "outcome": "created", "id": "itm_abc" },
    { "index": 1, "outcome": "updated", "id": "itm_def" },
    { "index": 2, "outcome": "skipped", "reason": "duplicate_source" },
    { "index": 3, "outcome": "errored",
      "error": { "code": "invalid_type", "message": "..." } }
  ]
}
```

### Inline edges

Each item may carry an `edges` block: a map from `edge_type` to target-item ids. Edges are created in the same transaction as the item, with **replace-all** semantics per edge type — any edge type listed wipes existing outbound edges of that type before the new set is created. Unmentioned edge types are untouched.

This path only works when source and target both land in the same call. For cross-batch edges — the target exists already, or lands in a separate bulk call — use `/edges/bulk`.

Inline edges are announced with the item, after the batch commits, so a batch that rolls back announces nothing at all. They follow the batch's own `enable_fanout` for webhook delivery, and reach the stream either way.

## Bulk edges

`POST /edges/bulk`. Admin-only. Up to 5000 edges per call.

Sibling to `/items/bulk` for the graph half of space migrations. Items created in an earlier bulk call exist on the server; a second pass through `/edges/bulk` wires them together without having to hold source and target in the same payload.

### Modes

- **`upsert`** (default) — match existing rows by `(source_id, target_id, edge_type)` and replace `properties` in place. Non-matching rows are created.
- **`create_only`** — matching rows surface as `skipped` with reason `"duplicate_edge"`. Useful for replayable migrations where the same edge set may be pushed twice. This door matches on the `(source, target, type)` triple rather than on a supplied `id`, which is its own contract and differs from the single-edge route: there a repeated `id` naming the same edge is acknowledged.

### Validation

Every edge runs the same rules as `POST /edges`: edge type registered, source and target exist and belong to the caller's space, source and target type constraints satisfied, cardinality respected, no cycle on `parent-of` or `supersedes`. Violations surface per-edge in `atomic: false` mode or abort the batch in `atomic: true` mode.

<Callout type="warn">
  **An unrecognized field inside `filter` is refused with a `400`, not ignored.** This matters more here than on a read: the filter *is* the match set, so a field the server dropped would leave `{}` behind and apply the action to every item in the space. A filter still carrying the old `since` or `until` names is refused specifically, with the replacement named.
</Callout>

### Events

Every newly-created edge publishes `edge.created`, and every upsert that replaced an existing edge's properties publishes `edge.updated`. A subscriber cannot tell a bulk edit from one made through `PATCH /edges/{id}`, so both routes emit the same event; `skipped` and `errored` outcomes wrote nothing and emit nothing. `enable_fanout: true` delivers each as a webhook as well.

## Bulk actions

`POST /items/bulk-actions`. Applies one action to every item matching a filter. Six actions, discriminated on `action`.

| `action` | Params | Auth | Confirm |
| --- | --- | --- | --- |
| `transition` | `state: "active" \| "archived" \| "trashed"` | write-access per matched type | — |
| `purge` | — | **admin-only** (hard 403) | `"confirm": "PURGE"` |
| `update_tags` | `add?`, `remove?` (at least one non-empty) | write-access per matched type | — |
| `update_tier` | `tier: "library" \| "feed"` | write-access per matched type | — |
| `update_properties` | `patch: object` (shallow-merged into properties, and validated against each row's type) | write-access per matched type | — |
| `update_timestamp` | `timestamp: ISO 8601` | write-access per matched type | — |

Non-admin callers see their match set narrowed to types they hold `write` on — consistent with `GET /items`. `purge` is the exception and returns 403 for non-admin regardless of filter.

### Filter grammar

The `filter` field takes the [`GET /items`](/guides/querying/search-and-query) grammar, narrowed in one place: `tier` accepts `library` and `feed`, not the read's `all`. `state` accepts every lifecycle value — `active`, `archived`, `trashed` and `revoked` — but not the read's `any` catch-all. The narrowing is enforced: a value outside it is refused with a `400` rather than ignored, which matters more here than on a read, because the filter *is* the match set and a value the server dropped would leave a wider one behind.

**Selecting a revoked row and moving one into `revoked` are different questions, and only the second is refused.** The filter takes `revoked` because the reserved `system.*` lifecycle is exactly `active` and `revoked`, so a filter offering three states could not select a reserved row at all. A `transition`'s own target state is the narrower set — `active`, `archived`, `trashed` — because `revoked` is terminal and a bulk action may not move a row into it.

### Reserved rows are matched only by a platform credential naming them

**A filter that names no type never matches a `system.*` row**, as [`GET /items`](/guides/querying/search-and-query) never returns one without being asked. The opt-in is narrower than the read's, in two ways.

**It is a concrete reserved type**, not a pattern. This door validates `filter.type` as an identifier rather than as a pattern, so `system.*` is a `400` rather than a widening and each reserved type is named on its own:

```json
{ "type": "system.device", "state": "revoked" }
```

**And the credential has to be a platform one.** This is the difference that matters, because this door has no per-row permission check: the filter it derives from a credential is the whole of what stands between the caller and the rows the action rewrites. On a single-item write door the platform-credential gate refuses a reserved-namespace write regardless; here there is no such gate to reach, so the widening is what carries it.

There is deliberately no `include` token beside the type filter. Widening a read answers a bigger question; widening an action acts on more rows.

**Both ways of reaching a reserved row without asking are closed by the same rule**, because it narrows the type rather than the state. Omitting `state` applies the default mask, which drops only trashed rows and so would otherwise keep revoked ones; and the free-text `filter` string recognizes `state` with no value allowlist, so it compiles straight through to the query. Neither reaches a reserved row now, and `dry_run` therefore no longer enumerates one.

**The match set is what the caller may write, not what it may read.** The filter this door derives admits the types the credential holds `write` on; a type it holds only `read` on is visible to `GET /items` and absent from the match set, the same answer `PATCH /items/{id}` gives on that row. A credential that bypasses the permission maps, such as a space admin, is unaffected.

**A space's source filter narrows this door too**, resolved per row from the row's own type, exactly as on the three read doors. It is a narrowing lever, so a filter that names no type and one that reaches through the free-text grammar both meet it: a match set can no longer include a row a read hides.

```json
{
  "type": "core.note",
  "state": "active",
  "source": "raindrop",
  "tier": "library",
  "tags": ["scratch"],
  "timestamp_after": "2025-01-01T00:00:00Z",
  "timestamp_before": "2026-01-01T00:00:00Z",
  "filter": "edge[about] eq \"itm_xyz\""
}
```

### Events

Every action publishes what it wrote, after its chunk commits: a `transition` an `item.state_changed` per item it moved, a `purge` an `edge.deleted` per edge its removal cascaded and an `item.purged` per row it removed, a tag change a `metadata.changed`, and a tier, properties or timestamp change an `item.updated`.

`enable_fanout` defaults to `false`, like every other bulk endpoint, and decides only whether each of those is also delivered as a webhook.

A purge announces its rows as well as its cascade, on this door and on `DELETE /items/{id}/purge`. The trash transition that has to precede a purge already announced the item, but `item.deleted` says recoverable, so a client that acted on it holds a trashed row nothing would ever correct: the row is absent afterwards rather than changed, and no later event can describe it. The cascade is announced per edge because an edge pointing *at* a purged item lives on an item that is not being purged, so nothing else tells its holder the relationship is gone. Edges first, then the rows they hung off.

### Safety rails

- **`dry_run: true`** returns matched ids and count without writing. Synchronous, returns 200.
- **`update_properties` is judged per row.** The patch is validated against each matched row's own type, on the properties the write would leave rather than on the patch alone — so a patch that removes a required field is refused even though it names no invalid value. A row the type refuses is reported in `errors` under `invalid_properties` and the rest of the action proceeds, which is how this door reports every other per-row refusal.
- **`max_items`** caps the match set (default 10000, hard ceiling 50000). Going over returns `400 bulk_cap_exceeded`.
- **`confirm: "PURGE"`** is required on the purge action. Missing it returns `400 bulk_confirmation_required`.
- **`Idempotency-Key`** header (optional) — retrying a `POST` with the same key returns the original job, not a duplicate. Scoped per space.

### Async behavior

Non-dry-run calls return **202 Accepted** with a job envelope. The server queues the work and an in-process worker runs it through to a terminal status. Poll `GET /items/bulk-actions/jobs/{id}` until `status` is `completed`, `failed`, or `cancelled`. SDKs (TypeScript, Swift) hide the polling — `client.items.bulkAction(input)` resolves with the same `BulkActionResult` shape regardless of size.

```json
// 202 response shape
{
  "id": "0192a5be-2c5f-7d8b-9a23-4f5e6c1a2b3c",
  "action": "purge",
  "status": "queued",
  "matched": 1234,
  "processed": 0,
  "succeeded": 0,
  "errored": 0
}
```

Pickup is prompt: enqueueing wakes the worker rather than leaving the job for its next poll, so a job starts within a poll cadence of being accepted rather than waiting out an idle interval.

Cancel mid-flight via `DELETE /items/bulk-actions/jobs/{id}`. The worker observes the flag between chunks (typically within seconds) and stops; partial progress (`processed` / `succeeded` / `errored`) is preserved on the row.

Job rows live for 7 days after they reach a terminal state, then a sweep deletes them. Polling a long-gone job id returns `404 bulk_job_not_found`.

### Who can read or cancel a job

A job id alone is not enough. Both `GET` and `DELETE /items/bulk-actions/jobs/{id}` check the calling credential against the job:

- **The credential that created the job** always reaches it. This is the ordinary case, and it is narrower than the space: two credentials inside the same space do not see each other's jobs.
- **A space admin** reaches every job in its own space, and nothing outside it.
- **A platform credential**, meaning an admin credential with no space binding, reaches any job on the instance.

The two refusals differ deliberately:

- **Across a space boundary**, the job reads as `404 bulk_job_not_found`, exactly as an id that never existed would. A credential in one space cannot use this endpoint to discover which job ids exist in another.
- **Inside your own space**, a credential asking for a sibling credential's job gets `403`. The job's existence is not a secret from you; only its contents are.

Cancellation follows the same rule, so a refused `DELETE` leaves the job untouched and still cancellable by someone who is allowed to.

### Wiping a scratch space

```bash
# Preview first — dry-run stays synchronous (200 with the result inline)
curl -X POST "$MARFA_API_URL/items/bulk-actions" \
  -H "Authorization: Bearer $MARFA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "action": "purge", "filter": {}, "dry_run": true, "confirm": "PURGE" }'

# Real thing — returns 202 with a job id
JOB=$(curl -s -X POST "$MARFA_API_URL/items/bulk-actions" \
  -H "Authorization: Bearer $MARFA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{ "action": "purge", "filter": {}, "confirm": "PURGE" }' | jq -r .id)

# Poll until terminal
while true; do
  STATE=$(curl -s "$MARFA_API_URL/items/bulk-actions/jobs/$JOB" \
    -H "Authorization: Bearer $MARFA_API_KEY" | jq -r .status)
  case $STATE in
    completed|failed|cancelled) echo "Final: $STATE"; break ;;
    *) sleep 1 ;;
  esac
done
```

## Archive restore

`POST /admin/restore-archive` accepts a tar.gz produced by `GET /export?format=archive`. The body is `application/gzip`; the response is JSON counts: `imported`, `duplicates`, `edges_imported`, `edges_skipped`, `blobs_imported`, and the four registration counts described below.

Restore reproduces the archive's content, not just its items:

- **Custom type and edge-type registrations restore first**, before anything that needs them, so a space whose items use types it registered itself round-trips into an empty space. A registration the target already holds identically is skipped and counted in `custom_types_skipped` / `custom_edge_types_skipped`; the rest are counted in `custom_types_registered` / `custom_edge_types_registered`.
- **Item ids are preserved**, so the archive's edges resolve after restore. A collision — the same id, or the same `(source, source_id)` natural key, already present in the restore space — counts as a duplicate and leaves the existing row untouched.
- **Where each type came from is carried and replayed.** A `{custom_type}` line's `provenance` records whether the type was registered by the person or published by a connected integration, and the restore writes what it says rather than defaulting. That distinction decides what an application can be granted over the type: a person's own namespace is offered for reading and writing, an integration's is offered read-only, because its rows mirror an upstream record and a third-party write would fork them.
- **Tags and extensions** restore with their items.
- **Edges** restore in a second pass, after every item the archive carries exists. An edge whose endpoints do not both resolve in the restore space is skipped and counted in `edges_skipped`, so a partial or hand-edited archive cannot plant a reference to an item that is not there. Re-restoring the same archive is idempotent: existing edges count as skipped.
- **Version history and row timestamps are re-stamped**, not carried. The restore is content-faithful, not history-faithful.
- **What the restore wrote is announced**, once its transaction has committed: an `item.created` for every item it imported, then an `edge.created` for every edge. Items go first, so a subscriber is never handed an edge naming a row it has not been told about. A duplicate or a skipped edge wrote nothing and so announces nothing. These announcements reach subscribers and the event log; they do not drive installed connections outward, because a restore can carry thousands of items and replaying all of them into an external system is not what restoring a backup should mean. See [Realtime](/guides/realtime/realtime).

An archive restores into the space it was exported from: the manifest's `space_id` must match the restore target, so moving a space between instances is export on one, restore on the other, under the same space. Cross-space copies are deliberately refused.

Three claims in an archive are checked rather than believed, because an archive is a file and a file can be handed to you by anyone. A type claiming to be platform-shipped is refused with `403`, as is one claiming a family the platform reserves for types it ships. A type claiming to be the person's own under a publisher namespace is accepted, but recorded as unrecorded rather than as theirs unless the space holds that publisher handle, which is the same rule [`POST /types`](/guides/core-model/types) applies to registering there directly.

An archive taken before archives carried provenance has none to replay. Its types restore and stay usable, recorded as unrecorded: their namespace is offered for reading rather than for writing, since nothing in the archive says whose they were.

A restore refuses outright, with nothing written, when the archive redefines a type the target space already registers differently. The response is `409` and its `details.conflicting_ids` names every clashing identifier, so the fix is one decision rather than a per-type hunt: rename in the archive, or delete the target's registration and restore again. An archive claiming a reserved namespace (`core.*`, `system.*`, `marfa.*`) or redefining a core edge type is refused the same way, whatever credential is restoring it.

```bash
# Export and restore in one pipe, against the same space
curl -s "$MARFA_API_URL/export?format=archive" \
  -H "Authorization: Bearer $MARFA_API_KEY" \
  -o snapshot.tar.gz

curl -X POST "$MARFA_API_URL/admin/restore-archive" \
  -H "Authorization: Bearer $MARFA_API_KEY" \
  -H "Content-Type: application/gzip" \
  --data-binary @snapshot.tar.gz
```

Blobs are content-addressed and register idempotently. Space migration between Marfa instances is export-then-restore.
