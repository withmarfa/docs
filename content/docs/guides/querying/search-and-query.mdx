A single query surface covers two capabilities: a filter language that narrows a list of items by field, property, tag, or edge, and full-text search that finds items by keyword across their content. Both use the same `filter` parameter grammar and return paginated item lists.

## Listing items

`GET /items` accepts type / state / tag / tier / edge / backref / filter narrowing plus pagination. A few characteristic examples:

```
GET /items
GET /items?type=core.note&state=active
GET /items?tier=library&tags=to-read
GET /items?edge[parent-of]=<parent-id>
GET /items?filter=properties.author eq "George Orwell"
```

The full parameter list and response shape are in the API reference. A few semantics worth knowing:

- **`type`** — matches subtypes via inheritance. `type=core.media` returns `core.media.book`, `core.media.article`, etc. It resolves both halves of the subtree: types named under the parent, and types that declare it as their `parent` while living elsewhere in the namespace. `core.media` and `core.media.*` are two spellings of the same thing. The bare `*` is rejected — everything is the request with no `type` at all.
- **`since`** and **`until`** — operate on the item's effective time (`timestamp`, falling back to `created_at`), not `updated_at`.
- **`include`** — off by default to keep list responses lean. See [Including extras](#including-extras) below.
- **`tier`** — `library`, `feed`, or omitted (returns both slices).
- **`sort`** — a system column (`created_at`, `updated_at`, `timestamp`) or a property field via `properties.<field>`, paired with `direction` (`asc` / `desc`). A property sort orders on the extracted value: numeric fields compare numerically (so `2` precedes `10`), datetimes and strings lexically, and items missing the field sort last in either direction. Enum fields such as `status` or `priority` are not sortable this way; their order is meaning-bearing rather than lexical, so sort those client-side.

<Callout type="info">
  Cursors are stable within the cursor's lifetime (24h typical) — concurrent writes don't shift pages already returned. Paginate by passing `cursor` back as a query parameter.
</Callout>

## Including extras

`GET /items` returns the minimum item shape by default — no edges, no metadata, no extensions. The `?include=` parameter is the escape hatch: name what you need and the server batches it inline. A naive "fetch the extras per item" loop is an N+1 trap; `?include=` collapses it to one request.

Currently supported values (comma-separated):

- `?include=edges` — hydrates outbound edges per item, grouped by edge type. Same shape as single-item responses.
- `?include=metadata` — wraps each entry as `{ item, metadata }` so tags travel inline.
- `?include=extensions` — hydrates extension namespaces per item, filtered by caller permissions (same rule as `GET /items/:id/extensions`).

Combinations work. `?include=edges,extensions` is the typical "rendering a rich list view" shape: one request, everything the UI needs, no per-item follow-ups.

The TypeScript SDK exposes typed helpers — `client.items.listWithMetadata`, `client.items.listWithExtensions` — that call these under the hood. Prefer them over assembling raw query strings.

### Reading one item with its neighborhood

`GET /items/:id` always returns the item's `metadata` layer and its **outbound** edges hydrated inline. For a detail view that also needs the rest of the item's 1-hop neighborhood — inbound edges, the items on the far end of those edges, version history — `?include=` widens the single read instead of forcing a per-section fan-out:

- `?include=backrefs` — **inbound** edges (where this item is the target), grouped by edge type, the same block shape as the outbound `edges` (per-type cap with `has_more` + `next_cursor` to paginate via `GET /items/:id/backrefs?edge_type=X&cursor=...`).
- `?include=neighbors` — the **far-end items** of the item's edges: outbound targets, plus inbound sources when `backrefs` is also requested. Each neighbor arrives as `{ item, metadata }` and is **permission-filtered** — a neighbor the caller cannot read (other space, type not permitted) is silently omitted, never leaked, exactly like [bulk-get](/guides/querying/bulk-operations). The combined neighbor set is **bounded per read**, and the response carries a `neighbors_truncated` boolean alongside `neighbors`: when `true`, the bound was hit and more neighbors exist than were hydrated. This is the **only** completeness signal for that case — the per-type edge-block `has_more` does *not* cover it, because several edge types can each sit below their own cap while their combined set overflows. Treat every neighbor-derived view as incomplete when `neighbors_truncated` is set, and page the per-type edge/backref endpoints for the full set.
- `?include=versions` — the item's version snapshots, newest-first (same shape as `GET /items/:id/versions`).

```
GET /items/<id>?include=backrefs,neighbors
```

One bundled read replaces the open-a-detail pattern of "fetch the item, then its metadata, then a request per relationship section". Tokens compose, and the blocks are absent unless requested so the lean read stays lean.

The TypeScript SDK exposes this as `client.items.getDetail(id, { include: ["backrefs", "neighbors", "versions"] })`, returning a typed `ItemDetail`. Prefer it over the bare `client.items.get(id)` (which keeps only the item) whenever you're rendering a detail surface.

## Full-text search

`GET /search` accepts `q` plus the same filter parameters as `/items`:

```
GET /search?q=orwell
GET /search?q=orwell&type=core.bookmark&state=active
GET /search?q=orwell&tier=library
GET /search?q=orwell&tags=fiction,classic
```

Index scope: all textual properties of the item (body, title, description, etc.) plus tags. Ranking by relevance, with recency boost configurable per space. `q` narrows by text match, filter parameters narrow further.

The filter parameters mean exactly what they mean on `/items`, `type` included: it resolves the subtree rather than matching one identifier, so narrowing a search and narrowing a listing the same way returns the same set. `GET /export` reads it the same way too.

`tags` accepts a comma-separated list with AND semantics — items must have every listed tag.

<Callout type="info">
  Result ordering is stable; the absolute `score` value isn't guaranteed across index rebuilds. Rely on order, not magnitude.
</Callout>

## Filter language

The `filter` parameter accepts expressions over system fields, properties, and metadata.

### Grammar

```
expression := condition (AND condition)* | condition (OR condition)*
condition  := field operator value | field operator | edge-clause

field      := "properties." name | "metadata." name | <system-field>
operator   := eq | neq | gt | gte | lt | lte | contains | starts_with | exists | not_exists
value      := number | string | boolean | null

edge-clause := "edge[" edge_type "]" ("eq" target_id | "exists")
             | "backref[" edge_type "]" ("eq" source_id | "exists")
```

System fields recognized: `id`, `type`, `state`, `source`, `source_id`, `timestamp`, `created_at`, `updated_at`, `tier`, `device`, `version`.

`source_id` is the identifier the writing client stored the item under. For a file-sync client that is the path relative to the watched folder, which makes a folder a prefix query rather than a container:

```
source_id starts_with "Notes/"
```

### Examples

```
properties.author eq "George Orwell"
state eq "active" AND properties.language eq "en"
tags contains "to-read" AND tier eq "library"
edge[references] exists
edge[authored-by] eq "person-id"
backref[parent-of] eq "child-id"
properties.word_count gt 1000 AND tags contains "longread"
```

### Operators

| Operator | Applies to | Meaning |
|---|---|---|
| `eq`, `neq` | strings, numbers, booleans, null | Equality. Case-sensitive. |
| `gt`, `gte`, `lt`, `lte` | numbers, datetimes | Range. |
| `contains` | arrays (e.g. `tags`), strings | Membership for arrays; case-insensitive substring match for strings. |
| `starts_with` | strings | Prefix match. Case-insensitive. |
| `exists`, `not_exists` | any | Field presence (with value ≠ null). |

`starts_with` and string `contains` match case-insensitively on every
deployment: `source_id starts_with "notes/"` finds items stored under
`Notes/`. One engine limitation is worth knowing: on SQLite the
case-insensitivity covers ASCII letters only, so a path containing
non-ASCII capitals (say `Ärenden/`) matches case-sensitively there,
while Postgres folds the full character set. That is a property of the
storage engine, not a choice, and it affects only self-hosted SQLite
deployments with non-ASCII names.

### Combining conditions

Conditions join with `AND` or `OR`. You can't mix `AND` and `OR` within a single expression — use one or the other. For complex logic, break into multiple queries or chain via a client-side join.

### Edge shorthand

`edge[X]=Y` as a query parameter is equivalent to `filter=edge[X] eq "Y"`. Both return items that have an outbound edge of type `X` targeting `Y`. Use the shorthand when only one edge clause is needed.

`backref[X]=Y` is the inbound equivalent.

## Quoting and escaping

String values in the filter language use double quotes: `"George Orwell"`. Double quotes inside a string are escaped with a backslash.

The `filter` query parameter value must be URL-encoded in the request line.

## Paginating search results

Search results use `limit` and `offset` pagination rather than cursors:

```
GET /search?q=orwell&limit=50&offset=50
```

Offset pagination is stable for the lifetime of a given query.
