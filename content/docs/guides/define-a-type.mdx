---
title: Define a type
description: Register a type for your own items, check what Marfa stored, and change or delete it later.
---

A type declares the properties its items hold. [Items and types](/get-started/items-and-types) explains what a type is, how identifiers and namespaces work, and when to inherit from another type rather than name it in `compatible_with`. This guide registers a type for receipt photos, `app.example.receipt`, as a child of `core.file.image`.

## Choose an identifier

Pick the namespace for who the type is for: `user.<type>` for your own, `app.<app-name>.<type>` for an app's own, or `<publisher>.<type>` for types others will use. You can't register a type under `core`, `system` or `marfa`.

These conventions aren't enforced, but they match the types Marfa ships:

- Name the type with a singular noun: `user.recipe`, not `user.recipes`.
- Use `snake_case` for words within a segment and for property names, as in `blob_ref` and `mime_type`.
- Keep the time the thing happened in the item's own `occurred_at`, not in a property, as `core.highlight` does.

## Declare the properties

`fields` holds one entry for each property, by name. Each entry needs a `type`, and can refine it:

| Attribute | What it does |
| --- | --- |
| `type` | `string`, `number`, `integer`, `boolean`, `url`, `email`, `datetime`, `date`, `enum`, `array`, `object` or `thumbnail`. |
| `required` | `true` if every item of the type has to hold the property. |
| `description` | What the property holds. |
| `enum_values` | The values an `enum` allows. An `enum` needs it. |
| `items_type` | The type of each element of an `array`. An `array` needs it. |
| `format` | A refinement of a `string`, such as `url` or `bcp47`. |
| `maxLength` | The longest value a `string` or `enum` allows. A string without one holds at most 100,000 UTF-16 code units. |
| `maxItems` | The most elements an `array` allows. |
| `searchable` | `false` keeps the property out of full-text search. |

[Register a type](/api-reference/types/registerType) has the full shape, including `display_hints`, `merge_policy`, `version_policy` and `link_field`.

A property can't share a name with a field every item has. Marfa refuses these names with `400 property_shadows_field`: `id`, `type`, `state`, `tier`, `properties`, `created_at`, `updated_at`, `occurred_at`, `source`, `source_id`, `version`, `schema_version`, `capture_latitude`, `capture_longitude`, `trashed_by_cascade` and `trashed_with`.

## Register the type

Send the type to `POST /types`:

```http
POST /types
Content-Type: application/json

{
  "id": "app.example.receipt",
  "parent": "core.file.image",
  "fields": {
    "merchant": { "type": "string", "required": true, "description": "Where the purchase was made" },
    "total": { "type": "number" },
    "currency": { "type": "string", "maxLength": 3 }
  }
}
```

Marfa answers `201` with the type as it stored it. Because the request names no `label`, the label is `Receipt`, made from the identifier's last segment. Because it names no `version`, the version is 0. The version is yours to keep: Marfa stores the number each write names and never changes it.

An identifier under `core`, `system` or `marfa` answers `403 forbidden`. If the identifier is already registered, Marfa answers `409 type_already_exists`. A parent that isn't registered, or a chain of more than ten ancestors, answers `400 validation_error`.

## Check the type

Read the type back:

```http
GET /types/app.example.receipt
```

The answer holds the type's own properties and every property it inherits, so `blob_ref` and `mime_type` from `core.file` and `width` and `height` from `core.file.image` sit beside `merchant`. An item of the type has to hold every required property along the chain: `blob_ref`, `mime_type` and `merchant`.

## Change the type

`PUT /types/{id}` replaces the whole type, so send everything you want to keep. This request adds an optional `category` and raises the version to 1:

```http
PUT /types/app.example.receipt
Content-Type: application/json

{
  "parent": "core.file.image",
  "version": 1,
  "fields": {
    "merchant": { "type": "string", "required": true, "description": "Where the purchase was made" },
    "total": { "type": "number" },
    "currency": { "type": "string", "maxLength": 3 },
    "category": { "type": "enum", "enum_values": ["travel", "meals", "supplies"] }
  }
}
```

What a replacement does to the items you already have:

- **A property you add** leaves stored items as they are. An item meets a new required property at its next write of properties.
- **A property you leave out** is removed from the type, but items keep their values for it, and a later write isn't refused for them.
- **A `version` you leave out** goes back to 0, so name the version on every replacement.

## Delete the type

`DELETE /types/{id}` removes a type that no item holds and no other type names as its `parent`. Marfa refuses the rest:

| Answer | When |
| --- | --- |
| `409 type_has_subtypes` | Another type names this one as its `parent`, with `force=true` or without. `details.subtype_ids` names each one. |
| `409 type_in_use` | An item of the type exists, in any state, the trash included. |

`DELETE /types/{id}?force=true` deletes a type that items still hold, and keeps the items. Until the type is registered again, Marfa refuses a write that sets such an item's properties, tier, time or natural key with `unknown_type`. Its tags, extensions and state can still change.

## Permissions each action needs

Every action needs a credential whose type map grants write on the type's identifier. Each also needs one more grant, from its metadata map or its permissions:

| Action | Also needs |
| --- | --- |
| Register a type | `metadata.types:write`. Naming a `parent` that Marfa doesn't ship also takes write on the parent. |
| Add optional properties that no item holds a value under, or change the label, the description, a property's description, the display hints or the version | `metadata.types:write` or `schema.write`. |
| Any other replacement, such as removing a property, making one required or changing the `parent` | `schema.write`. |
| Delete a type | `schema.write`. |

When a replacement needs `schema.write` and the credential doesn't hold it, Marfa answers `403 forbidden` with `details.required_scope` set to `schema.write` and `details.changes` listing each part of the replacement that needs it. Split those parts off, or send the replacement with a credential that holds `schema.write`. [Keys and permissions](/get-started/keys-and-permissions) explains how maps and permissions are given to a key.

The rules behind this guide are in the [types chapter of the contract](https://github.com/withmarfa/marfa/blob/main/conformance/spec/types.md).
