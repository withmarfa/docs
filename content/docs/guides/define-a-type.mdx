---
title: Define a type
description: Register a type for items no shipped type fits, then change it as your app grows, or delete it.
---

When none of the types Marfa ships fits what your app keeps, you register a type of your own, and Marfa checks the properties you declare on every item of it. The examples register a type for receipt photos, `app.example.receipt`, built on the shipped `core.file.image`, then change it and delete it. [Items and types](/items-and-types) explains what a type is and when to build on another. The TypeScript examples use a client made as [the TypeScript SDK](/typescript-sdk) shows.

<Steps>
<Step>

### Choose an identifier

The identifier's namespace says who the type is for. Use `app.<app name>.<type>` for your app's own types, `user.<type>` for types you keep for yourself, and a name of your own, such as `acme.deal`, for types you publish for others. The Catalog's [Type rules](/catalog/your-own-types#identifier) page lists what an identifier must meet, including the roots Marfa keeps.

**Name a type with a singular noun**, `user.recipe` and not `user.recipes`, and write words within a segment and in property names in `snake_case`, as the shipped types do with `blob_ref` and `mime_type`.

</Step>
<Step>

### Declare the properties

`fields` holds one entry for each property, by name. Each entry needs a `type`, and can refine it:

<ReferenceList description={2}>

| Field | Type | Description | Default |
| --- | --- | --- | --- |
| `type` | `string` | One of the [field kinds](/catalog/field-kinds). |  |
| `required` | `boolean` | Whether every item of the type must hold the property. | `false` |
| `description` | `string` | What the property holds. |  |
| `enum_values` | `string[]` | The values an enum allows. An enum needs it. |  |
| `items_type` | `string` | The type of each element of an array. An array needs it, and a write is refused if an element isn't a value of that type. |  |
| `maxLength` | `integer` | The longest value a string or enum allows. |  |
| `searchable` | `boolean` | Set to false to keep the property out of search. | `true` |

</ReferenceList>

**A property can't share a name with a field every item has**, such as `source` or `version`. The Catalog lists the [reserved field names](/catalog/your-own-types#reserved-field-names). Keep the time the thing happened in the item's own `occurred_at` rather than a property. [Register a type](/api-reference/types/registerType) lists everything a type can declare, such as its label, display hints, merge policy, version policy and retention policy.

**A property you don't declare is kept by default.** Marfa checks the declared properties, and accepts an item that carries others and serves them back. To refuse an undeclared property, name the type in the instance's strict mode: a write that carries one is then refused `400 invalid_properties`, with `details.code` set to `unknown_property`. Strict mode holds for exactly the types it names, not the types that inherit from them. [What the enforcement levers do](/guides/settings#what-the-enforcement-levers-do) shows how to turn it on.

</Step>
<Step>

### Register the type

Put the definition in a file. This one makes receipts a child of `core.file.image`, so each receipt is an image with a merchant and a total:

```json title="receipt.json"
{
  "id": "app.example.receipt",
  "parent": "core.file.image",
  "fields": {
    "merchant": { "type": "string", "required": true, "description": "Where the purchase was made" },
    "total": { "type": "number" },
    "currency": { "type": "string", "maxLength": 3 }
  }
}
```

To start from a scaffold instead of a blank file, `marfa types scaffold` prints a definition from the identifier and the fields you name. It needs no server, working copy or key, and sends nothing:

```bash
marfa types scaffold app.example.receipt --parent core.file.image \
  --field merchant:string --field total:number --field currency:string \
  --required merchant > receipt.json
```

```json
{
  "id": "app.example.receipt",
  "parent": "core.file.image",
  "fields": {
    "merchant": { "type": "string", "required": true },
    "total": { "type": "number" },
    "currency": { "type": "string" }
  }
}
```

A field is `NAME:TYPE`, an enum is `NAME:enum:one,two` and an array is `NAME:array:TYPE`. The command refuses an identifier or a field whose form registration would refuse, and says why. What it prints registers unchanged, where your key may register that identifier. It can't set a field's `description` or `maxLength`, so edit the file to add them.

Then register it:

```bash tab="CLI" tab-group="client"
marfa types register --file receipt.json
```

```http tab="HTTP"
POST /types
Authorization: Bearer <key>
Content-Type: application/json

{
  "id": "app.example.receipt",
  "parent": "core.file.image",
  "fields": {
    "merchant": { "type": "string", "required": true, "description": "Where the purchase was made" },
    "total": { "type": "number" },
    "currency": { "type": "string", "maxLength": 3 }
  }
}
```

```ts tab="TypeScript"
const { data, error } = await marfa.POST("/types", {
  body: {
    id: "app.example.receipt",
    parent: "core.file.image",
    fields: {
      merchant: { type: "string", required: true, description: "Where the purchase was made" },
      total: { type: "number" },
      currency: { type: "string", maxLength: 3 },
    },
  },
});
```

Marfa answers `201` with the type as it stored it. It made the label `Receipt` from the identifier, and set the type's `version` to 0. **That version is yours to keep**: Marfa stores the number you send and never changes it.

```json
{
  "type": {
    "id": "app.example.receipt",
    "label": "Receipt",
    "version": 0,
    "fields": {
      "merchant": { "type": "string", "description": "Where the purchase was made", "required": true },
      "total": { "type": "number" },
      "currency": { "type": "string", "maxLength": 3 }
    },
    "parent": "core.file.image"
  }
}
```

An identifier someone already registered answers `409 type_already_exists`.

</Step>
<Step>

### Check what Marfa stored

Read the type back:

```bash tab="CLI" tab-group="client"
marfa types get app.example.receipt
```

```http tab="HTTP"
GET /types/app.example.receipt
Authorization: Bearer <key>
```

```ts tab="TypeScript"
const { data } = await marfa.GET("/types/{id}", {
  params: { path: { id: "app.example.receipt" } },
});
```

The answer holds every property a receipt has: its own, and those it inherits from `core.file` and `core.file.image`, such as `blob_ref`, `mime_type`, `width` and `height`. **An item of the type must hold every required property along the chain**, so a receipt needs a `blob_ref`, a `mime_type` and a `merchant`. One without a `merchant` is refused with `400 invalid_properties`, naming it.

</Step>
</Steps>

## Compare a definition without registering it

[Normalize a type](/api-reference/types/normalizeType) validates a candidate and makes its declared defaults explicit, **without changing the registry or adding an audit entry**. Any authenticated credential can use it, even without type or metadata write grants. Use it before deciding whether a connector needs to register or replace its type.

For the `receipt.json` definition above:

```bash tab="CLI" tab-group="client"
marfa types normalize --file receipt.json
```

```http tab="HTTP"
POST /types/normalize
Authorization: Bearer <key>
Content-Type: application/json

{
  "id": "app.example.receipt",
  "parent": "core.file.image",
  "fields": {
    "merchant": { "type": "string", "required": true, "description": "Where the purchase was made" },
    "total": { "type": "number" },
    "currency": { "type": "string", "maxLength": 3 }
  }
}
```

```ts tab="TypeScript"
const { data, error } = await marfa.POST("/types/normalize", {
  body: {
    id: "app.example.receipt",
    parent: "core.file.image",
    fields: {
      merchant: { type: "string", required: true, description: "Where the purchase was made" },
      total: { type: "number" },
      currency: { type: "string", maxLength: 3 },
    },
  },
});
if (error) throw new Error(error.error.message);
```

The answer's `type` is your canonical declared definition. `registered_type` is the registered declared definition, and `resolved_type` adds its inherited fields and resolved policies. Both registered forms are `null` if the identifier is not registered.

**Compare declared forms to detect a definition change**: a resolved form includes ancestor fields your candidate never declared.

**Unknown schema keys are refused rather than ignored**, including inside field definitions and policies. [Type rules](/catalog/your-own-types#fields) lists the keys a field definition takes. Normalization validates the candidate against the same schema and parent-chain rules as registration.

## Make it readable as another type

A child takes every property of its parent. When your type should instead be readable as another type without taking its properties, **name that type in `compatible_with`**.

A connector's type does this, for example, so that a person can keep one of its feed items as a library item of a core type. A recipe can be read as a note if it requires a `body`, as a note does:

```json title="recipe.json"
{
  "id": "user.recipe",
  "compatible_with": ["core.note"],
  "fields": {
    "title": { "type": "string" },
    "body": { "type": "string", "required": true },
    "servings": { "type": "integer" }
  }
}
```

Marfa checks the claim when you register or replace the type, by the rule in [Type rules](/catalog/your-own-types#parent-and-inheritance).

A claim that doesn't hold is refused with `422 compatible_with_violation`, naming the property and what it should be. **A compatible type inherits nothing**, and a listing of `core.note` leaves recipes out.

**Marfa keeps the claim true afterward.** Marfa refuses a replacement or deletion of a type that you registered if it would break another type's claim, such as a change to a target's properties that leaves `user.recipe` unreadable as it. A platform type such as `core.note` can't be replaced or deleted at all. [Change the type](#change-the-type) and [Delete the type](#delete-the-type) cover the refusals.

## Change the type

`PUT /types/{id}` **replaces the whole definition**, so send everything you want to keep. This adds an optional `category` and sets the type's `version` to 1:

```json title="receipt.json"
{
  "parent": "core.file.image",
  "version": 1,
  "fields": {
    "merchant": { "type": "string", "required": true, "description": "Where the purchase was made" },
    "total": { "type": "number" },
    "currency": { "type": "string", "maxLength": 3 },
    "category": { "type": "enum", "enum_values": ["travel", "meals", "supplies"] }
  }
}
```

```bash tab="CLI" tab-group="client"
marfa types replace app.example.receipt --file receipt.json
```

```http tab="HTTP"
PUT /types/app.example.receipt
Authorization: Bearer <key>
Content-Type: application/json

{
  "parent": "core.file.image",
  "version": 1,
  "fields": {
    "merchant": { "type": "string", "required": true, "description": "Where the purchase was made" },
    "total": { "type": "number" },
    "currency": { "type": "string", "maxLength": 3 },
    "category": { "type": "enum", "enum_values": ["travel", "meals", "supplies"] }
  }
}
```

```ts tab="TypeScript"
await marfa.PUT("/types/{id}", {
  params: { path: { id: "app.example.receipt" } },
  body: {
    parent: "core.file.image",
    version: 1,
    fields: {
      merchant: { type: "string", required: true, description: "Where the purchase was made" },
      total: { type: "number" },
      currency: { type: "string", maxLength: 3 },
      category: { type: "enum", enum_values: ["travel", "meals", "supplies"] },
    },
  },
});
```

**A replacement changes no item you already hold.** An item meets a property you made required the next time its properties are written. A property you leave out is gone from the type, but items keep their values for it, and a later write isn't refused for them.

**Name the `version` on every replacement:** one that leaves it out sets it back to 0.

**A replacement can't break another type's `compatible_with` claim.** If a change would leave a type that names this one unable to keep its claim, such as by removing a property the claimant relies on, Marfa refuses it with `422 compatible_with_violation`. `details.dependent_type_ids` lists the claimants. Change or remove their claims first.

## Delete the type

`DELETE /types/{id}` removes a type **that no item holds and no other type names as its parent or in `compatible_with`**:

```bash tab="CLI" tab-group="client"
marfa types delete app.example.receipt
```

```http tab="HTTP"
DELETE /types/app.example.receipt
Authorization: Bearer <key>
```

```ts tab="TypeScript"
await marfa.DELETE("/types/{id}", {
  params: { path: { id: "app.example.receipt" } },
});
```

Marfa refuses to delete a type that another type names as its parent, with `409 type_has_subtypes`, and one that items still hold, in any state and the bin included, with `409 type_in_use`. A type that other types name in `compatible_with` is refused with `422 compatible_with_violation`, and `details.dependent_type_ids` lists them. Remove their claims first.

<Callout type="warn">
`force=true` (the CLI's `--force`) deletes a type that items still hold. It doesn't override a subtype or a `compatible_with` claim. The items stay, but until the type is registered again, Marfa refuses any write to their properties, tier or time, so they can't be edited. You can still tag, archive or move them to the bin.
</Callout>

## What your key needs

Registering, replacing and deleting a type each need a key whose type map **grants write on the type's identifier**. Each also needs a grant or a permission of its own:

- **Registering** needs `types` at `write` in the key's metadata map, written `metadata.types:write`. Naming a parent or a `compatible_with` target that Marfa doesn't ship also needs write on it.
- **Replacing** needs `metadata.types:write` when it only adds optional properties no item holds a value under, or changes the label, a description, the display hints or the version. Any other change, such as removing a property or making one required, needs the `schema.write` permission. A replacement that adds a parent or a `compatible_with` target Marfa doesn't ship also needs write on that target, and one that keeps a parent or target the type already names doesn't, so a connector can update its type after its permissions narrow. Marfa answers `403 type_not_permitted` when the key's type map lacks that write, and `details.grant` names the target.
- **Deleting** needs `schema.write`.

When a replacement needs `schema.write` and the key doesn't hold it, Marfa answers `403 forbidden`, and `details.changes` lists each part of the replacement that needs it:

```json
{
  "error": {
    "code": "forbidden",
    "message": "Changing fields.currency, fields.total requires schema.write. …",
    "details": { "required_scope": "schema.write", "changes": ["fields.currency", "fields.total"] }
  }
}
```

Split those parts off, or send the replacement with a key that holds `schema.write`. [Manage keys](/guides/manage-keys) shows how to give a key its maps and permissions.

The rules behind this guide are in the [types](https://github.com/withmarfa/marfa/blob/main/conformance/spec/types.md) chapter of the contract.
