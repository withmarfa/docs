---
title: Sync a folder
description: Keep a directory on your Mac and a set of items in step, so each note is a Markdown file you can edit in any app.
---

A folder lets you work on your items in the tools you already use. A file you add becomes an item, and a change on either side reaches the other. If you stop following the folder, the files stay behind as plain files.

A folder is a [device](/devices) whose working copy is a directory. **Its settings live on the instance** as a `system.folder` item, so every computer that follows the folder shares them, and each keeps its own copy and queue of writes. [Folder safeguards](/guides/folder-safeguards) says when a folder removes a file or an item.

The steps use the CLI's `marfa folders` commands. [A Mac app](#use-a-folder-from-a-mac-app) does the same with the Swift SDK.

<Steps paged>
<Step>

### Make a key for the folder

The folder needs a key that reaches what it holds. Make one as the owner, on the instance's machine. This key suits a folder of notes and files:

```bash
marfa --socket /srv/marfa/data/control/marfa.sock keys create \
  --label "Notes folder" --source notes-folder \
  --type-permission system.folder=write \
  --type-permission core.note=write \
  --type-permission 'core.file.*=write' \
  --edge-permission in-folder=write
```

- **`system.folder`:** write creates the settings, and read lets `folders add` bind a directory to them.
- **The types the folder holds:** write on each type the search admits, here `core.note`. `core.file.*` covers `core.file` and every type under it.
- **`in-folder`:** write on this edge, which records where each file sits.

`folders add` is refused without read on `system.folder`, naming `system.folder:read`, and without write on `in-folder`, naming `edge.in-folder:write`. [Manage keys](/guides/manage-keys) explains each flag.

</Step>
<Step>

### Create the folder's settings

The settings say which items the folder holds, through a search, and what a new file becomes. This folder holds every note:

<Terminal>

```bash
marfa folders create --title Notes --search '{"types":["core.note"]}'
```

```text
01a1232d-949d-758c-b244-70057174b96a  system.folder  2026-10-10T00:19:12.157Z  Notes
```

</Terminal>

**Keep the ID** in the first column: the next step binds a directory to it.

</Step>
<Step>

### Add the directory

Bind a directory to the folder. It can be empty or hold files already, and the CLI makes it if it isn't there:

<Terminal>

```bash
marfa folders add Notes --folder 01a1232d-949d-758c-b244-70057174b96a
```

```text
/Users/sam/Notes follows the folder 01a1232d-949d-758c-b244-70057174b96a
the first sync will write and send nothing until you confirm it: 2 file(s) to write into the directory, 1 to send to the server
`marfa folders confirm Notes` lets it go; `marfa folders remove Notes` drops the folder and leaves the files
```

</Terminal>

**Nothing is written into the directory or sent to the instance until you confirm the first sync.** Here the instance holds two notes and the directory held one file, `Ideas.md`. At a terminal the command asks first; in a script, pass `--yes` to confirm at once.

Where an item's file would land on a file the folder will send, one of the two gets a number added to its name, and **neither is written over**. If the existing file is held back, the plan counts the item as `left`, not as written beside it; that file stays for you to fix. A directory inside a folder you already added, or around one, is refused.

Keep the directory out of iCloud Drive, other cloud-synced folders and network storage: two programs syncing the same files can overwrite each other's changes. `marfa folders add` warns and goes on.

</Step>
<Step>

### Confirm the first sync

Check the plan first. **The search decides every item the folder takes in.** A search that names only a type holds every active and archived item of that type in the library tier, and the first sync writes all of them to disk. With no `types`, it holds every type the key reads except `system.*`. To narrow it, use `filter`, `tier`, `state` or `beneath`, as [list, filter and search](/guides/list-filter-search) describes.

Then confirm, and sync once:

```bash
marfa folders confirm Notes
marfa folders push Notes
```

`marfa folders push` sends what changed in the directory, catches up with the instance, and writes out what changed there. To sync without running it by hand, [keep folders running](/guides/keep-folders-running).

</Step>
</Steps>

The directory now holds a file for each note, and `Ideas.md` is an item:

## How items appear as files

A note is a Markdown file named after its title, or after its ID if it has none. Here's `Reading list.md`:

```markdown title="Notes/Reading list.md"
---
type: core.note
tier: library
title: Reading list
marfa_id: 01a1232d-947e-7399-86e1-97648a87c232
marfa_version: 1
---
Start with the essays, then the letters.
```

The lines between the `---` fences are the frontmatter. The text after them is the body.

- **`type`:** the item’s type when the value is a Marfa type identifier. A value that is not a type identifier belongs to the item’s `type` property instead and survives writing the file back.
- **`tier`, `tags`, `state` and `occurred_at`:** the item’s own fields.
- **A line named after an edge type,** such as `references`: an edge.
- **Every other line:** a property.
- **`marfa_id` and `marfa_version`:** the item and the version the file was written from. Leave them to Marfa.

A new Markdown file needs no frontmatter. It takes its type and tier from the folder's `defaults` or its search, and its title from `defaults` or, without one, its file name. Once the instance creates the item, Marfa writes the frontmatter and `marfa_id` into the file. A `.txt` file is all body. Any other file the search admits, such as a photo, becomes a file item with its bytes uploaded as a blob, as [Handle files](/guides/handle-files) describes.

## Edit on either side

Edit a file and sync, and the edit reaches its item:

<Terminal>

```bash
marfa folders push Notes
```

```text
0 created, 1 updated, 0 renamed, 2 unchanged, 0 missing, 0 deleted, 0 skipped
the server answered 1 write(s)
1 file(s) written
```

</Terminal>

An edit is a write based on the `marfa_version` the file names. If another app changed the same note meanwhile, the instance settles the two as [Versions](/versions) explains: changes to different fields merge, and a collision the type can't merge leaves a conflicted copy, which appears as a second file.

A note's file name and its title stay in step. Rename the file and the new name, without its extension, becomes the title. Change the title anywhere else and the next sync renames the file, numbering the name if another file has it. The folder leaves a name alone when it can't tell whether you chose it.

## Change a folder's settings

Each computer writes the folder's settings out as `.marfa/folder.yaml`:

```yaml title="Notes/.marfa/folder.yaml"
# This folder's settings, the system.folder it follows. An edit here is
# sent through the folder operations by `folders push`, or while watching.
folder: 01a1232d-949d-758c-b244-70057174b96a
version: 1
title: Notes
search:
  types:
    - core.note
```

Edit the file and the next sync sends your change to the instance through [Update a folder](/api-reference/folders/updateFolder), so **it reaches every computer that follows the folder**. `marfa folders change` changes the settings without the file. `folder` and `version` are Marfa's to write. [Folder](/catalog/folder) lists every other setting.

This edit leaves a `drafts` directory alone and tags every new note:

```yaml title="Notes/.marfa/folder.yaml"
ignore:
  - drafts/
defaults:
  tags:
    - from-folder
```

## Replace a folder's key

A new key with the same `--source` is refused `409 conflict` while the old key is live. [Revoke the old key](/guides/manage-keys#revoke-a-key), run the `keys create` command from the first step again, then run `marfa keys keep` so the folder reads the new key from the keychain.

Then run `marfa folders push Notes`. If the key's read view changed, the push rebuilds the working copy once and sends the waiting writes in the same run, keeping earlier verdicts. If the view changes again during that run, the push stops and keeps the remaining writes queued. Try again once the key's access is settled.

## Stop following a folder

To stop following a folder on one computer, run `marfa folders remove Notes`. It is refused while writes wait, apart from a first sync still waiting for confirmation. The folder's own state goes, and **the files stay where they are, as plain files**.

## Use a folder from a Mac app

The Swift SDK's `Folders` shares the Mac's list of folders with `marfa folders`. This creates the folder, binds a directory and confirms the first sync, with `serverURL`, `key` and `storeURL` as in [Open a working copy](/swift-sdk#open-a-working-copy). Until the first sync is confirmed, `sync(_:)` returns `.awaitingConfirmation` with the plan:

```swift
import Marfa

let server = Server(url: serverURL, key: key)
let copy = try await WorkingCopy.open(store: storeURL, server: server)
let folder = try await copy.createFolder(
    FolderSettings(title: "Notes", search: FolderSearch(types: ["core.note"])))

let folders = Folders(server: server)
let directory = URL(filePath: "/Users/sam/Notes")
_ = try await folders.add(directory, following: folder.id)
_ = try await folders.sync(directory)               // .awaitingConfirmation(plan)
_ = try await folders.confirmFirstSync(in: directory)
_ = try await folders.sync(directory)
```

[Folders on a Mac](/swift-sdk#folders-on-a-mac) lists every call, including `changeFolder(_:_:baseVersion:)`. A client without the SDK calls [Create a folder](/api-reference/folders/createFolder) and the other folder operations.

The rules behind this guide are in the [folders](https://github.com/withmarfa/marfa/blob/main/conformance/spec/folders.md) and [device](https://github.com/withmarfa/marfa/blob/main/conformance/spec/device.md) chapters of the contract.
