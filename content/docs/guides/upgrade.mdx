---
title: Upgrade
description: Move an instance to a new build of Marfa by exporting your data, starting the new build on empty storage, and restoring the archive.
---

Before Marfa's first release, nothing upgrades a database in place. A new build may lay out its database differently, and it refuses to start on a database another build wrote rather than risk changing it. So you move to a new build the way you move to a new machine: export your data with the build that holds it, start the new build on empty storage, and restore the archive there. This guide takes you through that, and through what to do if the new build can't read your archive.

## What a new build does with your database

When the server starts, it checks the database before it changes anything. If a table, an index or a trigger differs from the build's own, or the database holds something the build retired, it refuses: it leaves the file as it found it, opens no port, and exits with status `78`. The error in its log names what it found and the file's path, and says what to do:

```text
RefusedDatabaseError: The type registry in /srv/marfa/data/marfa.db is still held in custom_types, which this build does not read. Nothing is upgraded in place. To carry what this file holds into this build, export it with the build that wrote it (`GET /export?format=archive`), start this build on a fresh file, and restore the archive there (`POST /restore`). Until the first public release an archive is read only by the build that wrote it, so that restore can refuse it; the file stays readable by the build that wrote it either way.
```

A build's version doesn't tell you whether its database differs, so treat every new build as one that might refuse. Starting the old build again on the same file brings the instance back. In the container, a refused database doesn't stop the container: it stays up and unhealthy with the reason in its log, so a restart policy can't loop on it.

## Move to a new build

Keep the old build, and its data, until the last step.

<Steps>
<Step>

### Export with the running build

Follow [Export an archive](/guides/back-up-and-restore#export-an-archive). Stop your apps first, so the archive holds every write, and check that the file unpacks.

</Step>
<Step>

### Start the new build on empty storage

Give the new build a new database file and an empty blob folder. In a container, that's a new volume. If you use a bucket, give the new instance a new bucket too: on an empty volume, the container restores the database from its bucket, and that is the old build's database, which the new build refuses.

</Step>
<Step>

### Claim the new instance

Claim it as you did the first, with `marfa --socket <path> setup open`. The new instance has an `instance_id` of its own.

</Step>
<Step>

### Restore the archive

Restore it as the owner, through the private socket of the new instance:

```bash
marfa --socket /srv/marfa/data/control/marfa.sock restore marfa-archive.tar.gz
```

[Restore an archive](/guides/back-up-and-restore#restore-an-archive) explains the answer.

</Step>
<Step>

### Recreate what an archive doesn't hold

Make your keys again, register your webhooks again, and set the configuration again: an archive carries none of them. Sign your apps in again too. Restored app connections are revoked historical records, and their items carry `restored:` sources rather than the sources of the apps you reconnect. [Manage keys](/guides/manage-keys) and [Settings](/guides/settings) cover them.

</Step>
<Step>

### Check, then retire the old build

`GET /` answers the build that's running, as `version`. Remove the old build and its data only when the new instance holds what you expect.

</Step>
</Steps>

## If the new build refuses the archive

Before the first release, only the build that wrote an archive is sure to read it. If the new build refuses yours, it can't read it. A refused restore writes nothing, so the new instance is unchanged and the old build still holds your data: keep running the old build until a build can read the archive.

On Railway, template updates are opt-in, and a rollback changes the deployment, not the database. The [Railway guide](https://github.com/withmarfa/marfa/blob/main/deploy/railway.md#update-the-server) applies the same steps.

The rules behind this page are in the [upgrading](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#upgrading) section of the instance chapter and the [restore](https://github.com/withmarfa/marfa/blob/main/conformance/spec/search-and-filters.md#restore) section of the search and filters chapter of the contract.
