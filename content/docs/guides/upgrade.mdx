---
title: Upgrade
description: Check a new build against your database while keeping a way back to the build that wrote it.
---

A build **never upgrades a database in place**. It refuses a database whose schema differs from its own or that holds retired tables or settings. If a new build refuses your database, keep the previous build and its data. An archive from it may be refused by a different build, so check a restore on separate storage before deciding to switch.

[`marfa server upgrade`](/guides/install#change-upgrade-or-remove-it) moves a server that `marfa server install` set up to a release, and does not move data. When the [changelog](/changelog) says a release changes the database's shape, follow the steps below instead.

## What a new build does with your database

When the server starts, it checks the database before it changes anything. If a table, an index or a trigger differs from the build's own, or the database holds something the build retired, it refuses: **it leaves the file as it found it**, opens no port, and exits with status `78`. The error in its log names what it found and the file's path, then says what to do, which is the steps below:

```text
RefusedDatabaseError: The type registry in /srv/marfa/data/marfa.db is still held in custom_types, which this build does not read. Nothing is upgraded in place. …
```

A build's version doesn't tell you whether its database differs, so **treat every new build as one that might refuse**. Starting the old build again on the same file brings the instance back. In the container, a refused database doesn't stop the container: it stays up and unhealthy with the reason in its log, so a restart policy can't loop on it.

## Move data to a different schema

Use these steps to test a move when the new build refuses your database. A build that accepts the existing schema can keep using the same storage. **Keep the old build, its data and its export until the new build has accepted and verified the restore.** An archive is guaranteed only for the build that wrote it.

<Steps>
<Step>

### Export with the running build

Follow [Export an archive](/guides/export-and-restore#export-an-archive). **Stop your apps first**, so the archive holds every write, and check that the file unpacks.

Note which build this is. `GET /` answers its `release` beside `version`, which is the commit, and `marfa status` shows both. **The image of that release, `ghcr.io/withmarfa/marfa-server:<release>`, stays available under that tag**, so you can start the old build again at any time, even on a machine that has pulled a newer one. A build made from a clone has no `release`, so note its `version` and keep that clone.

</Step>
<Step>

### Start the new build on empty storage

Give the new build a new database file and an empty blob folder. In a container, that's a new volume, and the new container can run beside the old one on **its own volume and its own port**, such as `-p 127.0.0.1:8601:8600`.

If you use a bucket, **give the new instance an `S3_PREFIX` of its own**, such as `v2/blobs`, or a new bucket. On an empty volume, the container restores the database it finds under its prefix, and under the old instance's prefix that is the old database. If that database has the incompatible schema, the new build refuses it again. An instance keeps its blobs and its database replica under its prefix, so a new prefix on the same bucket leaves the old instance's replica as it is.

</Step>
<Step>

### Claim the new instance

Claim it as you did the first, with `marfa --socket /srv/marfa/data/control/marfa.sock setup open`. The new instance has an `instance_id` of its own.

</Step>
<Step>

### Restore the archive

Try the restore as the owner, through the private socket of the new instance. **The new build may refuse an archive from the old build**, even when that archive is valid:

```bash
marfa --socket /srv/marfa/data/control/marfa.sock restore marfa-archive.tar.gz
```

[Restore an archive](/guides/export-and-restore#restore-an-archive) explains the answer.

</Step>
<Step>

### Recreate what an archive doesn't hold

Make your keys again, register your webhooks again, and set the configuration again: **an archive carries none of them**. Sign your apps in again too. Restored app connections are revoked historical records, and their items carry `restored:` sources rather than the sources of the apps you reconnect. [Manage keys](/guides/manage-keys) and [Settings](/guides/settings) cover them.

</Step>
<Step>

### Check, then retire the old build

`GET /` answers the build that's running, as `release` and `version`. Remove the old build and its data **only when the new instance holds what you expect**.

</Step>
</Steps>

## If the new build refuses the archive

Only the build that wrote an archive is sure to read it. If the new build refuses yours, it cannot read it. Do not treat the archive as a migration path until the target build has accepted it and you have checked its contents. A refused restore writes nothing, so the new instance is unchanged and the old build still holds your data: **keep running the old build until a build can read the archive**.

On Railway, [update the server](https://github.com/withmarfa/marfa/blob/main/deploy/railway.md#update-the-server) applies these steps: template updates are opt-in, and a rollback changes the deployment, not the database.

The rules behind this page are in the [upgrading](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#upgrading) section of the instance chapter and the [restore](https://github.com/withmarfa/marfa/blob/main/conformance/spec/search-and-filters.md#restore) section of the search and filters chapter of the contract.
