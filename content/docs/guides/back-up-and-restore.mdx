---
title: Back up and restore
description: Copy an instance's data directory and secrets so you can bring it back after a failed disk or a lost machine.
---

Keep a copy of your instance somewhere the instance isn't. A copy of the data directory brings the same instance back with everything in it: items, keys, configuration and sign-ins. To carry your data into another instance instead, [export an archive](/guides/export-and-restore). A different build may refuse the archive; [Upgrade](/guides/upgrade) explains how to test it before switching.

## What to copy

Copy two things:

- **The data directory.** It holds the database, the `marfa.db-wal` log beside it and the blob folder, as [Deploy](/guides/deploy#the-data-directory) shows. In the container, it's the volume at `/data`.
- **The two secrets**, `API_KEY_SALT` and `MARFA_AUTH_SECRET`. They aren't in the data directory. Without the original `API_KEY_SALT`, a restored instance holds every key and **accepts none**. Without `MARFA_AUTH_SECRET`, every signed-in session ends.

## Copy the directory safely

How you copy the directory decides whether the copy restores. Each of these keeps every write the instance acknowledged before the copy began:

- **A snapshot** of the volume or the filesystem, such as Time Machine on an APFS volume or a host's disk snapshot. SQLite recovers from it as it does from a crash.
- **A stopped server.** Stop it, copy the directory including the log if one is there, and start it again.
- **A held read transaction.** Copy the files one after another while the server runs, with a read transaction open on the database for the whole copy: the database file, then the log, then the blob folder.

A copy with no read transaction can leave **a database that won't open, or has lost writes**. With the `sqlite3` program on the instance's machine, the held transaction looks like this:

```bash
sqlite3 /srv/marfa/data/marfa.db "BEGIN; SELECT count(*) FROM sqlite_master;" \
  ".shell cp /srv/marfa/data/marfa.db /srv/marfa/data/marfa.db-wal /backup/" \
  ".shell cp -R /srv/marfa/data/blobs /backup/" \
  "COMMIT;"
```

## Restore the copy

Stop the server, put the copied files where `SQLITE_PATH` and `BLOB_PATH` name, and leave out `marfa.db-shm`. Start the server with the same two secrets. `GET /health` answers `200` when it's back, and your keys work as before. If the instance uses a bucket, read [With a bucket](#with-a-bucket) first.

## With a bucket

When `S3_BUCKET` is set, **the container copies for you**. It streams each committed database write to the bucket within a second, keeps a day of hourly snapshots, and the `blob-replicate` housekeeping job copies each blob; a blob whose store hasn't answered is skipped and copied on a later run. A new volume started with the same bucket, prefix and secrets restores the database as it starts and brings the blobs back as replication runs.

Everything the instance keeps in the bucket is under its `S3_PREFIX`, so **give each instance on a shared bucket its own prefix**. [Settings](/guides/settings#every-environment-setting) says what a prefix may hold.

**A copy older than the bucket needs a prefix of its own.** Started under the bucket's current prefix, it becomes the bucket's newest copy of the database. The [deployment guide](https://github.com/withmarfa/marfa/blob/main/deploy/README.md#restore-a-backup-that-is-older-than-the-bucket) gives those steps, and the steps for [restoring by hand](https://github.com/withmarfa/marfa/blob/main/deploy/README.md#restoring-by-hand) or to a point in time.

The rules behind this page are in the [backing up](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#backing-up) section of the instance chapter of the contract, with the [held reader](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#instancecopy-under-reader) rule.
