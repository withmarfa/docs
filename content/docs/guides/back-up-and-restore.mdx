---
title: Back up and restore
description: Copy an instance's data directory and secrets so you can bring it back after a failed disk or a lost machine.
---

Keep a copy of your instance somewhere the instance isn't. A copy of the data directory brings the same instance back with everything in it: items, keys, configuration and sign-ins. To carry your data into another instance instead, [export an archive](/guides/export-and-restore). A different build may refuse the archive; [Upgrade](/guides/upgrade) explains how to test it before switching.

## What to copy

Copy two things:

- **The data directory.** It holds the database, the `marfa.db-wal` log beside it and the blob folder, as [Deploy](/guides/deploy#the-data-directory) shows. In the container, it's the volume at `/data`, which with a bucket also holds the hidden `.marfa.db-litestream` folder and `marfa.db-replica` file. The blob folder holds a hidden `.marfa-store` file that names its store. Copy all of them.
- **The two secrets**, `API_KEY_SALT` and `MARFA_AUTH_SECRET`. They aren't in the data directory. Without the original `API_KEY_SALT`, a restored instance holds every key and **accepts none**. Without `MARFA_AUTH_SECRET`, every signed-in session ends.

## Copy the directory safely

How you copy the directory decides whether the copy restores. Each of these keeps every write the instance acknowledged before the copy began:

- **A snapshot** of the volume or the filesystem, such as Time Machine on an APFS volume or a host's disk snapshot. SQLite recovers from it as it does from a crash.
- **A stopped server.** Stop it, copy the directory including the log if one is there, and start it again.
- **A held read transaction.** Copy the files one after another while the server runs, with a read transaction open on the database for the whole copy: the database file, then the log, then the blob folder.

A copy with no read transaction can leave **a database that won't open, or has lost writes**. With the `sqlite3` program on the instance's machine, the held transaction looks like this:

```bash
sqlite3 /srv/marfa/data/marfa.db "BEGIN; SELECT count(*) FROM sqlite_master;" \
  ".shell cp /srv/marfa/data/marfa.db /srv/marfa/data/marfa.db-wal /backup/" \
  ".shell cp -R /srv/marfa/data/blobs /backup/" \
  "COMMIT;"
```

## Restore the copy

Stop the server and delete the `marfa.db-wal` and `marfa.db-shm` files in the data directory, because SQLite applies a log it finds beside a database file, even one from another copy. Put the copied files where `SQLITE_PATH` and `BLOB_PATH` name, and leave out `marfa.db-shm`. Start the server with the same two secrets. `GET /health` answers `200` when it's back, and your keys work as before. If the instance uses a bucket, read [With a bucket](#with-a-bucket) first.

**Put the blob folder back whole, with its `.marfa-store` file.** With no bucket, the server refuses to start when that folder or file is missing and the database records saved files in the store kept there, because a drive may not have mounted. It stops with status `1`, names the folder in its log and creates nothing. Mount or restore the folder and start again. To start with an empty folder on purpose, point `BLOB_PATH` at another folder, and the store kept at the old one is detached. With a bucket, the server starts on an empty folder instead, and the `blob-replicate` job fills it. The rule is [`stores/missing-folder-refused`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/stores.md#storesmissing-folder-refused).

## With a bucket

When `S3_BUCKET` is set, **the container copies for you**. It streams each committed database write to the bucket within a second, keeps a day of hourly snapshots, and the `blob-replicate` housekeeping job copies each blob; a blob whose store hasn't answered is skipped and copied on a later run. A new volume started with the same bucket, prefix and secrets restores the database as it starts and brings the blobs back as replication runs.

Everything the instance keeps in the bucket is under its `S3_PREFIX`, so **give each instance on a shared bucket its own prefix**. [Settings](/guides/settings#every-environment-setting) says what a prefix may hold.

**The container refuses to replicate a database that may be older than the bucket's copy.** Replicating it would make it the bucket's newest copy, and the writes made since would stay only in history that expires. When the volume already holds a database, the container compares it with the bucket's replica before it starts the server. If the database may be older, it exits with status `1`, names the reason in its log, and leaves the bucket unchanged. A copy restored without its `.marfa.db-litestream` folder, a database that lost writes since it last replicated, and a point-in-time restore onto the same prefix all count. If the bucket can't be listed, the container can't compare and exits the same way, so a restart tries again.

A fresh volume restores the bucket's newest state, and the `.marfa.db-litestream` folder appears about a second later. If the container stops before then, the next start refuses the database. Delete `marfa.db`, `marfa.db-wal` and `marfa.db-shm`, and the next start restores it again.

When the container refuses a database, choose one of these:

| You want | Do this |
| --- | --- |
| To run the older copy and keep the bucket's newer history | Start it under a new `S3_PREFIX`. The old prefix is left as it was. |
| To run the bucket's newest state | Delete `marfa.db`, `marfa.db-wal` and `marfa.db-shm` from the data directory. The next start restores the database from the bucket. |
| To make this database the bucket's newest state | Set `MARFA_REPLACE_NEWER_REPLICA` to `true` for one start, then unset it. The writes the bucket held after the database stay only in history that expires. |

The same override starts an instance whose bucket can't be reached. The [deployment guide](https://github.com/withmarfa/marfa/blob/main/deploy/README.md#restore-a-backup-that-is-older-than-the-bucket) gives each step, and the steps for [restoring by hand](https://github.com/withmarfa/marfa/blob/main/deploy/README.md#restoring-by-hand) or to a point in time. The rule is [`instance/replica-not-older`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#instancereplica-not-older).

The rules behind this page are in the [backing up](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#backing-up) section of the instance chapter of the contract, with the [held reader](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#instancecopy-under-reader) rule.
