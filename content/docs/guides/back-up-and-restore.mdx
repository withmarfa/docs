---
title: Back up and restore
description: Export your data to an archive, restore it into an instance, and copy the machine so you can bring the same instance back.
---

Two kinds of copy do two jobs:

- **A copy of the machine's data** brings the same instance back: its items, keys, configuration and sign-ins.
- **An export archive** carries your items, edges, types and blobs into an instance. Before Marfa's first release, only the build that wrote an archive is sure to read it, so an archive moves data between instances and builds ([Upgrade](/guides/upgrade)) and is not a backup that outlasts a build.

## Export an archive

[Export items and edges](/api-reference/export-and-restore/exportData) with `format=archive` answers a `.tar.gz` file. It holds what the credential can read: items with their tags, extensions and version history, the edges between them, the type registrations, and the blobs they name.

The credential decides what the archive holds, and a permission such as `blobs.manage` adds no content. To keep everything, use a key that reads every type, edge type and extension namespace:

```bash
marfa --socket /data/control/marfa.sock keys create --label backup --source backup \
  --type-permission '*=read' --edge-permission '*=read' --extension-permission '*=read'
```

Run the command on the instance's machine, under the server's account. [Create a key](/api-reference/access/createKey) shows the key once, so copy it then. Then export:

```http
GET /export?format=archive&state=any
Authorization: Bearer <credential>
```

Or with the `marfa` command, with the key in `MARFA_API_KEY`:

```bash
marfa export --format archive --state any --output marfa-archive.tar.gz
```

Without `state`, the archive leaves out the bin. `state=any` includes it. The `type`, `source`, `occurred_after` and `occurred_before` filters make a partial archive.

Know these four things before you export a large instance:

- **The first byte comes late.** The server reads the whole selection first, and keeps what it reads in a `tmp` folder inside the blob folder. Leave room for about as much as the archive's text takes uncompressed. The server removes the files when the response ends.
- **It is not one instant.** An item created after the export began is not carried, and an edge made while the export read the items may or may not be. Stop your clients first if the archive must hold every write.
- **A failed export looks like a short file.** If the server fails partway, it ends the connection early, and the file does not unpack. Check it with `tar -tzf marfa-archive.tar.gz`.
- **Each accepted export is audited** as an `export.run` entry. See [The audit log](/guides/audit-log).

## Restore an archive

[Restore from an archive](/api-reference/export-and-restore/restoreArchive) takes the file as its body. Only the owner may restore: signed in to the browser with the password in the last five minutes, or a command run through the instance's private socket. A key answers `403 forbidden`, even one holding all twelve permissions.

```bash
marfa --socket /data/control/marfa.sock restore marfa-archive.tar.gz
```

The target can be a new instance or the one the archive came from. The answer counts what happened. Restoring the same archive a second time into the same instance answers:

```json
{
  "imported": 0,
  "duplicates": 412,
  "edges_imported": 0,
  "edges_skipped": 96,
  "edges_skipped_reasons": { "already_present": 96 },
  "blobs_imported": 31,
  "types_registered": 0,
  "types_skipped": 3,
  "edge_types_registered": 0,
  "edge_types_skipped": 0
}
```

A restore writes in one transaction. One that is refused, fails, or is interrupted leaves no rows, types or edges behind, so you can run it again. A blob's bytes are written before the transaction opens. If the process stops, the `blob-replicate` and `blob-integrity` [housekeeping jobs](/guides/housekeeping) remove the bytes no row names.

While it runs, `GET /health` reports `database_write` as `degraded`, and a request that writes waits for the restore. After the busy budget, 5 seconds by default (`SQLITE_BUSY_BUDGET_MS`), it answers `503 write_contention`. Let the restore answer before you connect clients. When it commits, the restored items appear on the event stream.

### What a restore keeps and skips

**Kept as the archive has them:**

- The IDs, versions, `created_at` and `updated_at` of items and edges, and the state, tier and `source` of items.
- Tags and extensions.
- Every earlier version of an item, exactly, even where the type's current shape would refuse it.
- Edges, in both directions.
- Blobs, with their bytes checked against their hashes.
- Type and edge type registrations.

**Skipped and counted, not refused:**

- An item whose ID, natural key or link the instance already holds, counted in `duplicates`. The existing item, its tags, extensions and history stay as they are.
- An edge the instance already holds, one with a missing endpoint, or a malformed one, counted in `edges_skipped_reasons` under `already_present`, `endpoint_missing` or `malformed`.
- A type or edge type the instance already registers identically, counted in `types_skipped` or `edge_types_skipped`.
- A blob entry whose bytes do not hash to its name, left out and not counted in `blobs_imported`.

**Never in an archive:** keys, webhooks, configuration, tombstones, and the audit log. Trashed items are in an archive only if the export named `state=any`.

Replaying a backup never overwrites work made since: a duplicate keeps the instance's copy. A restore refuses the whole archive, and writes nothing, in these cases:

- **The archive was written by another build.** Its `manifest.json` names a `version` other than 0, and the answer is `400 validation_error`. See [`search-and-filters/restore-version`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/search-and-filters.md#search-and-filtersrestore-version).
- **A type or edge type differs.** The archive registers one the instance holds differently, or carries a core edge type: `409 conflict`, with `details.conflicting_ids` naming each.
- **A row cannot be valid.** It has a state its type cannot be in, a `source` starting with `oauth:`, a bad version, tier or date, or malformed history: `400 validation_error` naming the row. A row that sets a property no type declares, where `strict_mode` names its type, answers `400 invalid_properties`.
- **It does not unpack.** The body is empty, is not a gzip-compressed tar, or has an entry twice, or a line over 64 MiB: `400 validation_error`.

[Errors](/api-reference/errors) lists every code.

## Copy the machine

A restore of the machine's data brings back everything an archive leaves out. Copy two things:

- **The data directory.** The database file (`SQLITE_PATH`), the log beside it named `marfa.db-wal`, and the blob folder (`BLOB_PATH`). In the container image, this is the volume at `/data`.
- **The two secrets**, `API_KEY_SALT` and `MARFA_AUTH_SECRET`, from wherever you keep them. They are not in the data directory. A restore without the salt holds every key and accepts none.

How you copy decides whether the copy restores. Each of these restores to an instance with every write it had acknowledged before the copy began:

| How | Why it works |
| --- | --- |
| A snapshot of the volume or filesystem, such as Time Machine on an APFS volume or a host's disk snapshot. | It is an image of the directory at one instant, which SQLite recovers from as it does from a crash. |
| Stop the instance, copy the directory, start it. | A stop moves every write into the database file. Copy `marfa.db-wal` too when it exists. |
| Copy the files one after another while the instance runs, holding a read transaction on the database for the whole copy. | The log is not restarted while a reader holds it. Copy the database file, then the log, then the blob folder. |

Copying the files one after another with no reader held does not restore. A checkpoint between reading the file and reading the log leaves a database that either does not open or has lost writes. With the `sqlite3` command on the same machine, hold the transaction like this:

```bash
sqlite3 /data/marfa.db "BEGIN; SELECT count(*) FROM sqlite_master;" ".shell cp /data/marfa.db /data/marfa.db-wal /backup/" ".shell cp -R /data/blobs /backup/" "COMMIT;"
```

To restore, stop the instance, put the copied files where `SQLITE_PATH` and `BLOB_PATH` name (leave out any `marfa.db-shm`), and start it with the same two secrets. Read `GET /health` to confirm. The rules are in the [instance chapter](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#instancecopy-under-reader).

### With a bucket

The container recipe copies for you when `S3_BUCKET` is set. Litestream streams each committed database write to the bucket within a second and keeps a day of hourly snapshots. The `blob-replicate` housekeeping job copies each blob there. A new volume with the same bucket and secrets restores the database at start and brings the blobs back as replication runs.

The database reaches the bucket before a blob does, so a restore to a moment between the two can name a blob the bucket does not hold yet. The [deployment guide](https://github.com/withmarfa/marfa/blob/main/deploy/README.md#restoring-by-hand) has the commands to restore to the latest state or to a point in time.
