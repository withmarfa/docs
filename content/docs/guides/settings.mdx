An instance has two places for settings. The **environment** is read once, when the server starts, and covers everything from where the database lives to how often each housekeeping job runs. The **configuration** at `/config` changes while the server runs: it holds the instance's display name, three enforcement levers and the retentions you're most likely to adjust.

[Deploy](/guides/deploy#what-the-server-needs) shows the environment for an instance you keep.

## Set an environment setting

Set the setting as an environment variable of the server process, then start the server. To change one, restart the server:

```bash
export TRASH_RETENTION_DAYS=30
node dist/index.js
```

In the container, change its environment file and create the container again with `docker run`, because **a restart keeps the environment the container was created with**. A blank value counts as unset.

If any setting is outside its allowed values, the server opens no port and creates no file. It exits with status `1` and names every wrong setting at once, with the value it was given:

```text
The server cannot start; fix these settings:
  PORT must be a whole number, from 0 to 65535 (got "99999")
  MARFA_AUTH_SECRET must be at least 32 characters; generate one with `openssl rand -hex 32`
  TRASH_RETENTION_DAYS must be a whole number, from 0 to 36500 (got "forever")
```

A setting that holds a secret, or an address that can carry one such as `S3_ENDPOINT`, is named but never printed ([`instance/settings-refused-secret-hidden`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#instancesettings-refused-secret-hidden)).

## The settings to check first

Most settings have defaults that suit any instance. Check these before you keep one:

| Setting | Check it when | Read more |
| --- | --- | --- |
| `NODE_ENV` | Always. `production` refuses a start without `API_KEY_SALT`, `MARFA_AUTH_SECRET` and `MARFA_AUTH_BASE_URL`. | [Deploy](/guides/deploy#what-the-server-needs) |
| `SQLITE_PATH`, `BLOB_PATH` | Always. They say where your data lives. | [Back up and restore](/guides/back-up-and-restore) |
| `TRUSTED_PROXY_CIDRS`, `TRUSTED_PROXY_HEADER` | A proxy or tunnel sits in front of the server. | [Deploy](/guides/deploy#the-address) |
| `S3_PREFIX` | Instances share a bucket. Each needs its own. | [Deploy](/guides/deploy#an-object-store) |
| `MARFA_WEBHOOK_ALLOW_PRIVATE_ADDRESSES` | A webhook receiver is on a Tailscale or home network. | [Receive webhooks](/guides/receive-webhooks#receive-deliveries-on-a-private-network) |
| `OTEL_RESOURCE_ATTRIBUTES`, `OTEL_SERVICE_NAME` | You run more than one instance and send telemetry. | [Send telemetry](/guides/telemetry#tell-instances-apart) |
| `CORS_ORIGINS` | A web page on another origin calls the API. | [Connect a web page](/guides/connect-a-web-page) |
| `PORT`, `MARFA_LISTEN_HOST` | The default port `8600` or address doesn't suit. `0` lets the operating system assign a port. | |

## Every environment setting

The list comes from the server's own definition of its settings. It includes the intervals and retention windows of the [housekeeping jobs](/guides/housekeeping).

The `MARFA_TEST_` settings are for the conformance harness, the suite that holds a server to the contract. **Never set them on an instance that holds real data.** The server refuses `MARFA_TEST_HOOKS` when `NODE_ENV` is `production`, which the container sets ([`instance/test-hooks-production-refused`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#instancetest-hooks-production-refused)). [Housekeeping](/guides/housekeeping#try-feed-expiry-with-a-moved-clock) shows one use on a test server.

The owner can read the same settings in a browser, with each one's current value, on the All settings page at `/auth/owner/settings`. A setting that holds a secret shows only whether it is set, on that page and in Home's search ([`authentication/console-settings-no-secret`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/authentication.md#authenticationconsole-settings-no-secret)).

## Change settings while it runs

The configuration at `/config` takes effect at once, with no restart. A credential needs the `config.manage` permission to read, replace or update it. The owner needs no key through the private socket, and can change the name and the five retentions in a browser, on the General page at `/auth/owner/general`.

A field you haven't set is left out of the answer:

<ReferenceList description={2}>

| Field | Type | Description |
| --- | --- | --- |
| `name` | `string` | The instance's display name. Defaults to `Marfa`. |
| `enforcement` | `object` | The three [enforcement levers](#what-the-enforcement-levers-do): `strict_mode`, `source_allowlist` and `source_filter`. |
| `trash_retention_days` | `integer` | Days an item stays in the bin before Marfa purges it. Overrides `TRASH_RETENTION_DAYS`. |
| `audit_retention_days` | `integer` | Days Marfa keeps audit log entries and the history of outbound webhook deliveries. Overrides `AUDIT_RETENTION_DAYS`. |
| `event_log_retention_hours` | `integer` | Hours Marfa keeps events for a stream to replay. Overrides `MARFA_EVENT_LOG_RETENTION_HOURS`. |
| `inbound_handled_retention_days` | `integer` | Days Marfa keeps an inbound webhook delivery a connector has marked handled. Overrides `MARFA_INBOUND_HANDLED_RETENTION_DAYS`. |
| `inbound_pending_retention_days` | `integer` | Days Marfa keeps an inbound webhook delivery no connector has handled. Overrides `MARFA_INBOUND_PENDING_RETENTION_DAYS`. |

</ReferenceList>

A retention you leave unset takes the environment setting's value, and **a retention of `0` keeps those records with no age limit**. The ranges are in [`housekeeping/retention-days-range`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/housekeeping.md#housekeepingretention-days-range) and [`housekeeping/retention-hours-range`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/housekeeping.md#housekeepingretention-hours-range).

A name change takes effect on the next request and keeps the same instance ID. Marfa trims the name, and refuses an empty one or one over 200 Unicode code points ([`instance/config-name-invalid`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#instanceconfig-name-invalid)).

### Read the configuration

```bash tab="CLI" tab-group="client"
marfa config get
```

```http tab="HTTP"
GET /config
Authorization: Bearer <key>
```

An instance that has set nothing answers its `instance_id` alone:

```json
{
  "instance_id": "01a12311-6155-71e2-aec5-7c532fdb4d3d"
}
```

### Replace the configuration

**A replace sets the whole configuration: a field you leave out goes back to its default.** Read the configuration first, change what you need, and send all of it back. This names the instance Library, keeps the bin for 30 days and makes `core.note` refuse a property it doesn't declare:

```bash tab="CLI" tab-group="client"
marfa config replace --body '{"name": "Library", "enforcement": {"strict_mode": {"types": ["core.note"]}}, "trash_retention_days": 30}'
```

```http tab="HTTP"
PUT /config
Authorization: Bearer <key>
Content-Type: application/json

{
  "name": "Library",
  "enforcement": { "strict_mode": { "types": ["core.note"] } },
  "trash_retention_days": 30
}
```

The answer is the configuration as it now stands. `--file config.json` reads the body from a file, and `--file -` from standard input. **Sending `{}` clears every field.**

The server refuses a body with a field it doesn't know, an invalid name or a retention out of range, and keeps the configuration as it was. [Replace the configuration](/api-reference/instance/replaceConfig) has every refusal.

### Update the configuration

**An update changes only the settings it names.** A setting in the body is replaced, a setting set to `null` is removed so that its default applies, and every other setting stays as it was. Two callers who each change one setting don't undo each other, as they can with a replace. This keeps the bin for 30 days and puts the name back to `Marfa`:

```bash tab="CLI" tab-group="client"
marfa config update --body '{"trash_retention_days": 30, "name": null}'
```

```http tab="HTTP"
PATCH /config
Authorization: Bearer <key>
Content-Type: application/json

{
  "trash_retention_days": 30,
  "name": null
}
```

The answer is the whole configuration as it now stands. `enforcement` is one setting, so an update that names it replaces all three levers: include every lever you want on, and `null` removes them all. [Update the configuration](/api-reference/instance/updateConfig) has every refusal, and [`instance/config-patch-merges`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#instanceconfig-patch-merges) holds the rule.

The server records each accepted replace or update in the [audit log](/guides/audit-log) as `config.update`.

## What the enforcement levers do

A lever holds chosen types to a stricter rule. Each names `types`, and `source_allowlist` and `source_filter` also name `sources`.

| Lever | What it does | What the caller meets |
| --- | --- | --- |
| `strict_mode` | Refuses a write that names a property neither the item's type nor an ancestor declares. Without it, Marfa keeps an undeclared property and serves it back. | `400 invalid_properties`, with `details.code` set to `unknown_property`. |
| `source_allowlist` | Lets only the listed sources create items of a type. Use it when one app should own a type, such as a notes app that alone writes notes. | `403 forbidden`, with `details.type`, `details.source` and `details.allowed`. |
| `source_filter` | Leaves out of every read that returns a set, such as listings, searches, counts and exports, an item of a type whose source isn't listed. Event streams and webhook deliveries leave it out too. | Nothing: the item isn't there. |

`strict_mode` and `source_allowlist` hold for exactly the types they list, **not the types that inherit from them**, so list each type you mean. `source_filter` also covers the types under a listed type.

**Reading an item by its ID isn't filtered.** An item with no source counts as one whose source is `unknown`. The edge cases are in the contract: [`types/strict-mode`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/types.md#typesstrict-mode), [`types/source-allowlist`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/types.md#typessource-allowlist), [`types/source-filter`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/types.md#typessource-filter), and for the filter on streams [`events/source-filter-item`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/events.md#eventssource-filter-item) and [`events/source-filter-copy`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/events.md#eventssource-filter-copy).

A key can carry levers of its own in `enforcement_override`. A lever it names replaces the instance's for that key, looser or stricter. This key lists only the notes the notes app wrote:

```bash
marfa keys create --enforcement-override '{"source_filter": {"types": ["core.note"], "sources": ["notes-app"]}}'
```

Setting a key's levers needs `config.manage`, or the owner's own authority ([`keys-and-oauth`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/keys-and-oauth.md#a-keys-own-levers)). [Manage keys](/guides/manage-keys) covers minting a key.

The rules behind this page are in the [instance](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#settings) chapter, the [enforcement levers](https://github.com/withmarfa/marfa/blob/main/conformance/spec/types.md#enforcement-levers) in the types chapter, and the [retention](https://github.com/withmarfa/marfa/blob/main/conformance/spec/housekeeping.md#retention) rules in the housekeeping chapter of the contract.
