title: Settings

An instance has two kinds of settings. Environment settings are read once, when the server starts, and cover everything from where the database lives to how often each housekeeping job runs. The configuration at `/config` changes while the server runs: it holds the instance's display name, three enforcement levers, which hold chosen types to stricter rules, and the retentions you're most likely to adjust.

## Set an environment setting

Set the setting as an environment variable of the server process, then start the server, or restart it to change a setting:

```bash
export TRASH_RETENTION_DAYS=30
node dist/index.js
```

In the container, change its environment file and create the container again with `docker run`, because **a restart keeps the environment the container was created with**. A blank value counts as unset.

If any setting is outside its allowed values, the server opens no port and creates no file. It exits with status `1` and **names every wrong setting at once**, with the value it was given, so you can fix them all before you start again:

```text
The server cannot start; fix these settings:
  PORT must be a whole number, from 0 to 65535 (got "99999")
  MARFA_AUTH_SECRET must be at least 32 characters; generate one with `openssl rand -hex 32`
  TRASH_RETENTION_DAYS must be a whole number, from 0 to 36500 (got "forever")
```

A setting that holds a secret is named, and its value is never printed.

## The settings to check first

Most settings have defaults that suit any instance. Check these before you keep one:

- `NODE_ENV=production` makes the server refuse to start without `API_KEY_SALT`, `MARFA_AUTH_SECRET` and `MARFA_AUTH_BASE_URL`. Outside production, it falls back to a built-in salt and a new secret at each start, which signs every browser out at each restart.
- `SQLITE_PATH` and `BLOB_PATH` say where your data lives. [Back up and restore](/guides/back-up-and-restore) covers protecting it.
- `TRUSTED_PROXY_CIDRS` or `TRUSTED_PROXY_HEADER` tells the server which client address to believe behind a proxy or tunnel. [Deploy](/guides/deploy#the-address) explains when you need one.
- `CORS_ORIGINS` names the browser origins whose pages may call the API.
- `PORT` selects the public listener's port; `0` asks the operating system to assign one. `MARFA_LISTEN_HOST` selects its bind address. Leave it unset to use the runtime's unspecified address.

[Deploy](/guides/deploy#what-the-server-needs) shows a complete set for an instance you keep.

## Change settings while it runs

The configuration at `/config` **takes effect at once, with no restart**. Reading or replacing it needs the `config.manage` permission; the owner, signed in or through the private socket, needs no key. It holds these fields, and a field you haven't set is left out of the answer:

<ReferenceList description={2}>

| Field | Type | Description |
| --- | --- | --- |
| `name` | `string` | The instance's display name. Defaults to `Marfa`. |
| `enforcement.strict_mode` | `{ types }` | The types that refuse a property their type doesn't declare. |
| `enforcement.source_allowlist` | `{ types, sources }` | The types that take new items only from the listed sources. |
| `enforcement.source_filter` | `{ types, sources }` | The types whose listings, searches, exports, event streams and webhook deliveries show only items from the listed sources. |
| `trash_retention_days` | `integer` | Days an item stays in the bin before Marfa purges it. Overrides `TRASH_RETENTION_DAYS`. |
| `audit_retention_days` | `integer` | Days Marfa keeps audit log entries and the history of outbound webhook deliveries. Overrides `AUDIT_RETENTION_DAYS`. |
| `event_log_retention_hours` | `integer` | Hours Marfa keeps events for a stream to replay. Overrides `MARFA_EVENT_LOG_RETENTION_HOURS`. |
| `inbound_handled_retention_days` | `integer` | Days Marfa keeps an inbound webhook delivery a connector has marked handled. Overrides `MARFA_INBOUND_HANDLED_RETENTION_DAYS`. |
| `inbound_pending_retention_days` | `integer` | Days Marfa keeps an inbound webhook delivery no connector has handled. Overrides `MARFA_INBOUND_PENDING_RETENTION_DAYS`. |

</ReferenceList>

**A retention of `0` keeps those records with no age limit.** A retention you leave unset takes the environment setting's value.

The display name identifies the instance to apps and on its existing pages. **A name change keeps the same instance ID** and takes effect on subsequent requests. Marfa trims whitespace from each end and accepts up to 200 Unicode code points, with no control or bidirectional formatting characters. Leaving `name` out of a replacement restores `Marfa`.

### Read the configuration

```bash tab="CLI" tab-group="client"
marfa config get
```

```http tab="HTTP"
GET /config
Authorization: Bearer <key>
```

An instance that has set nothing answers its `instance_id` alone:

```json
{
  "instance_id": "01a12311-6155-71e2-aec5-7c532fdb4d3d"
}
```

### Replace the configuration

**A replace sets the whole configuration: a field you leave out goes back to its default.** Read the configuration first, change what you need, and send all of it back. This names the instance Library, keeps the bin for 30 days and makes `core.note` refuse a property it doesn't declare:

```bash tab="CLI" tab-group="client"
marfa config replace --body '{"name": "Library", "enforcement": {"strict_mode": {"types": ["core.note"]}}, "trash_retention_days": 30}'
```

```http tab="HTTP"
PUT /config
Authorization: Bearer <key>
Content-Type: application/json

{
  "name": "Library",
  "enforcement": { "strict_mode": { "types": ["core.note"] } },
  "trash_retention_days": 30
}
```

The answer is the configuration as it now stands. `marfa config replace --file config.json` reads the body from a file, and `--file -` from standard input. **Sending `{}` clears every field.**

The server refuses a body with a field it doesn't know, an invalid name or a retention out of range, and keeps the configuration as it was. Each accepted replace is recorded in the [audit log](/guides/audit-log) as `config.update`. [Replace the configuration](/api-reference/instance/replaceConfig) has every refusal.

## What the enforcement levers do

Each lever names types. `strict_mode` and `source_allowlist` hold for exactly those types, **not the types that inherit from them**, so list each type you mean.

`strict_mode` refuses a write that names a property neither the item's type nor an ancestor declares. Without it, Marfa keeps an undeclared property and serves it back. With `core.note` listed, a note with a `colour` property is refused `400 invalid_properties`, with `details.code` set to `unknown_property`.

`source_allowlist` lets only the listed sources create items of a type. Use it when one app should own a type, such as a notes app that alone writes notes. Any other key that creates a note is refused `403 forbidden`, with the type, its source and the allowed sources in `details`.

`source_filter` hides the items of a type, and of the types under it, whose source isn't listed, from every read that returns a set: listings, searches, counts and exports. It narrows the event stream too, live and on a replay from a cursor, and the deliveries of a webhook subscription: neither carries an event for a hidden item, and neither carries an edge event when the filter hides the edge's source item. A delivery already waiting is settled unsent once the filter comes to hide its item. An edge counts toward a `backref` term of a filter only if the filter shows its source item. An item with no source is judged as one whose source is `unknown`. **Reading an item by its ID isn't filtered.** A copy stream, which a device uses to keep its working copy, still sends such an item, marked `listed: false`, so the device holds every row it may read.

A key can carry levers of its own in `enforcement_override`, which **replace the instance's for that key, looser or stricter**. A key minted with `--enforcement-override '{"source_filter": {"types": ["core.note"], "sources": ["notes-app"]}}'` lists only the notes the notes app wrote. Setting a key's levers needs `config.manage`, or the owner's own authority.

## Move the clock for a test

`MARFA_TEST_HOOKS` and `MARFA_TEST_CLOCK_OFFSET_MS` are for the conformance harness, the suite that holds a server to the contract, and **never for an instance that holds real data**. `MARFA_TEST_HOOKS=true` serves a clock route and a fault route at `/_control/test` on the private socket only, and the server refuses it when `NODE_ENV` is `production`, which the container sets. `MARFA_TEST_CLOCK_OFFSET_MS` starts the clock that far ahead of the system clock, and needs `MARFA_TEST_HOOKS`.

`GET /_control/test/clock` answers the `offset_ms` and the server's `now`. `POST /_control/test/clock` with `{ "advance_ms": 172800000 }` moves the clock forward by that many milliseconds. It never moves back, and everything that reads the time moves with it. [Housekeeping](/guides/housekeeping#try-feed-expiry-with-a-moved-clock) tries feed expiry this way.
