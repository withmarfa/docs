---
title: Housekeeping
description: See the work an instance does on itself, read what each housekeeping job last did, and run one now.
---

An instance looks after itself on a schedule: it purges the bin, thins old versions, moves expired feed items to the bin, clears old log entries, sends webhook deliveries, and copies and checks blobs. Each piece of that work is a housekeeping job. Reading what each job last did shows whether the instance is keeping up, and running one applies a new retention without waiting for its schedule.

Listing needs the `instance.read` permission, and running needs `instance.maintain`. The owner needs neither, through the private socket or signed in. The **Health** page, at `/auth/owner/health`, lists every job with when it last ran and its error if it failed, and **Run now** runs one.

## List the housekeeping jobs

```bash tab="CLI" tab-group="client"
marfa housekeeping list --json
```

```http tab="HTTP"
GET /housekeeping
Authorization: Bearer <key>
```

The answer is one page with every job the instance runs, as `data`. Each entry gives its schedule, whether it is running now, and what its last run did. This is the entry for `audit-cleanup`:

```json
{
  "name": "audit-cleanup",
  "interval_ms": 86400000,
  "next_run_at": "2026-10-22T15:45:40.513Z",
  "running_since": null,
  "last_started_at": "2026-10-21T15:45:40.438Z",
  "last_finished_at": "2026-10-21T15:45:40.513Z",
  "last_outcome": "ok",
  "last_error": null,
  "last_result": {
    "deleted": 0,
    "deliveries": 0
  }
}
```

## Read what a job did

- `running_since` is the time the current run started, or `null` when nothing is running.
- `last_outcome` is `null` until a run finishes, then `ok` or `error`, with the reason in `last_error`.
- `last_result` holds counts of the job's own: `deleted` for a cleanup, `copied` and `remaining` for `blob-replicate`, `pruned` for `version-thinning`.

A job whose `last_outcome` stays `error`, or whose `next_run_at` is long past, is **the place to look when an instance falls behind**. A run that hangs is recorded as an `error` once its deadline passes, and the job can run again. [List housekeeping jobs](/api-reference/instance/listHousekeeping) has every field.

### Feed expiry

`feed-expiry` acts only on a type with a `feed_days` window in its [retention policy](/catalog/your-own-types#retention-policy), set on the type or taken from a parent. Once more than that many days have passed since an active feed item arrived, the job moves it to the bin, as a delete does. A type with no window keeps its items, and so does the job for **library items, archived items and items brought back from the bin**. A moved item can be restored until the bin's retention ends, and then `trash-purge` deletes it. The interval is `FEED_EXPIRY_INTERVAL_MS`.

Each run reports `moved` and `held` in `last_result`. `moved` includes items a cascade took with them. `held` counts expired items the job left alone because:

- Deleting one would also delete an item that hasn't expired, isn't a feed item or was brought back from the bin.
- An edge with `cascade_on_delete` set to `block` refuses the delete.
- The delete failed.

### Switch a job off

**Jobs controlled by live configuration stay listed when switched off.** You can still run one on demand; it answers `200` without doing the disabled work. This includes `enrichment-sweep` when `enrichment_enabled` is false and `grant-inactivity-retirement` when its retention is `0`. Enabling either in [configuration](/guides/settings#change-settings-while-it-runs) starts its work without a restart. A retention of `0` likewise keeps a cleanup job registered but stops age-based expiry.

`heartbeat` is registered when a receiver is configured at startup. Its live `heartbeat_enabled` switch controls whether a run sends a ping. **A machine-only setting can prevent a job from being registered at all**, as `MARFA_BLOB_CLEANUP_INTERVAL_MS=0` does for `blob-orphans`. Such a job is absent from the listing and a run request for it answers `404 housekeeping_job_not_found`. Check the listing for the jobs this instance has.

## Run a housekeeping job now

Name the job as the listing shows it:

```bash tab="CLI" tab-group="client"
marfa housekeeping run trash-purge
```

```http tab="HTTP"
POST /housekeeping/trash-purge/run
Authorization: Bearer <key>
```

**The server runs it before it answers**, so the request waits until the run finishes. The answer is the run:

```json
{
  "name": "trash-purge",
  "started_at": "2026-10-21T15:45:49.651Z",
  "finished_at": "2026-10-21T15:45:49.653Z",
  "outcome": "ok",
  "result": {
    "deleted": 0
  },
  "error": null
}
```

**A run that fails still answers `200`**, with `outcome` set to `error` and the reason in `error`. The listing then shows this run as the last one, and a run on demand never makes the next scheduled run later.

The server refuses `409 housekeeping_job_running` while a run of the same housekeeping job is already in progress, so try again when it finishes. A name it has not registered is refused `404 housekeeping_job_not_found`. [Run a housekeeping job](/api-reference/instance/runHousekeeping) lists every answer.

## Empty the bin

An item stays in the bin until it is purged. Left alone, `trash-purge` purges each item once it has been in the bin longer than `TRASH_RETENTION_DAYS`, which is 60 days unless you change it. `trash_retention_days` in the [configuration](/guides/settings#change-settings-while-it-runs) overrides that while the server runs, and a retention of `0` keeps every item. A run removes a limited number of items, and while items past the retention remain after a run that removed some, the job runs again at once.

<Callout type="warn">A purge deletes items and their history for good. To see what it would take first, add `--dry-run` to the CLI command, or `"dry_run": true` to the HTTP body. A dry run changes nothing.</Callout>

To empty the trash through the private socket, use the owner's summary operation. **Each call attempts up to 200 selected items** and returns the committed purge count, per-item failures and a cursor for the next batch. Send `--cursor` or the HTTP `cursor` query parameter with the returned value until `next_cursor` is `null`. If a write outcome is unknown, read the trash again before retrying. The owner can also empty it from a recent browser session.

```bash tab="CLI" tab-group="client"
marfa --socket /path/to/data/control/marfa.sock items trash empty --confirm PURGE
```

```http tab="HTTP"
POST /trash/empty
Cookie: <recent owner session>
```

Continue a batch with `POST /trash/empty?cursor=<next_cursor>`. The response reports `purged`, per-item `failures` and `next_cursor`.

A key holding `items.purge` can instead queue a bulk action for every item whose state is `trashed`. This dry run counts what a purge would take:

<Terminal>

```bash
marfa items bulk-action purge --state trashed --confirm PURGE --dry-run
```

```json
{
  "action": "purge",
  "matched": 0,
  "succeeded": 0,
  "errored": 0,
  "dry_run": true,
  "ids": []
}
```

</Terminal>

Without `--dry-run`, Marfa queues the purge as a job and answers with its `id`, `status` (`queued`) and the `matched` count. The HTTP request is:

```http
POST /items/bulk-actions
Authorization: Bearer <a key holding items.purge>
Content-Type: application/json

{ "action": "purge", "confirm": "PURGE", "filter": { "state": "trashed" } }
```

`marfa items bulk-action job <id>` shows the job again, and its `status` is `completed` once the purge has finished. A bin of more than 10,000 items is refused `400 bulk_cap_exceeded` unless you raise `--max-items`, which Marfa caps at 50,000: purge what's left with a second run. To purge one item, run `marfa items purge <id>`.

## Try feed expiry with a moved clock

A test server can move its clock forward, so you can watch `feed-expiry` act without waiting a day. Start it with `MARFA_TEST_HOOKS=true`, and **never** on an instance that holds real data: the server refuses it when `NODE_ENV` is `production`, which the container sets.

The hooks sit at `/_control/test` on the private socket only, so run these steps on the instance's machine. `GET /_control/test/clock` answers `offset_ms` and the server's `now`. `POST /_control/test/clock` with `{ "advance_ms": 172800000 }` moves the clock forward by that many milliseconds, never back, and everything that reads the time moves with it. `MARFA_TEST_CLOCK_OFFSET_MS` starts the clock that far ahead and needs `MARFA_TEST_HOOKS`.

**Two authorities are in play**: a key runs `marfa types register`, `marfa items create` and the content listing below, while the private socket reaches the clock and owner summary operations. It does not authorize ordinary item content reads or writes.

<Steps>
<Step>

### Put an expiring item in the feed

With a key in `MARFA_API_KEY`, register a type whose feed items expire after one day, and create one item in the feed:

```bash
marfa types register --body '{"id":"user.headline","fields":{"title":{"type":"string","required":true}},"retention_policy":{"feed_days":1}}'
marfa items create --type user.headline --prop title="Today" --tier feed
```

</Step>
<Step>

### Move the clock two days forward

Through the socket:

```bash
curl --unix-socket /srv/marfa/data/control/marfa.sock \
  -X POST http://localhost/_control/test/clock \
  -H 'Content-Type: application/json' -d '{"advance_ms": 172800000}'
```

</Step>
<Step>

### Run the job and read the bin

Run `feed-expiry` now. `moved` is `1` when the job found the item:

<Terminal>

```bash
marfa housekeeping run feed-expiry
```

```json
{
  "name": "feed-expiry",
  "started_at": "2026-10-23T15:45:53.273Z",
  "finished_at": "2026-10-23T15:45:53.282Z",
  "outcome": "ok",
  "result": {
    "moved": 1,
    "held": 0,
    "types": 1,
    "unresolvable": 0
  },
  "error": null
}
```

</Terminal>

Then list the bin, which now holds the item:

```bash
marfa items list --state trashed --type user.headline
```

</Step>
</Steps>

The rules behind this page are in the [housekeeping](https://github.com/withmarfa/marfa/blob/main/conformance/spec/housekeeping.md) chapter of the contract, and the test hooks in the [instance](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md) chapter.
