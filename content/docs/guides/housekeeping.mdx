---
title: Housekeeping
description: See the work an instance does on itself, read what each housekeeping job last did, and run one now.
---

An instance looks after itself on a schedule: it purges the trash, thins old versions, clears old log entries, sends webhook deliveries, and copies and checks blobs. Each piece of that work is a housekeeping job, and one scheduler runs them all from one table. Reading what each job last did is how you check that an instance is keeping up, and running one yourself applies a new retention without waiting for its schedule.

Listing needs the `instance.read` permission, and running needs `instance.maintain`; neither reads or writes any item. The owner needs no key for either, through the private socket or signed in to the instance's Manage Marfa pages.

## List the housekeeping jobs

```bash tab="CLI" tab-group="client"
marfa housekeeping list --json
```

```http tab="HTTP"
GET /housekeeping
Authorization: Bearer <key>
```

The answer holds every housekeeping job the instance runs, in one page. Each entry gives its schedule, whether it's running now, and what its last run did:

```json
{
  "data": [
    {
      "name": "audit-cleanup",
      "interval_ms": 86400000,
      "next_run_at": "2026-10-10T23:48:29.141Z",
      "running_since": null,
      "last_started_at": "2026-10-09T23:48:29.138Z",
      "last_finished_at": "2026-10-09T23:48:29.141Z",
      "last_outcome": "ok",
      "last_error": null,
      "last_result": { "deleted": 0, "deliveries": 0 }
    }
  ],
  "next_cursor": null
}
```

The answer has an entry for every housekeeping job; this shows one.

## Read what a housekeeping job did

`running_since` holds the time the current run started, and is `null` when nothing is running. `last_outcome` is `null` until a run finishes, then `ok` or `error`, with the reason in `last_error`. `last_result` holds what the run reported, in counts of its own: `deleted` for a cleanup, `copied` and `remaining` for `blob-replicate`, `pruned` for `version-thinning`.

A housekeeping job whose `last_outcome` stays `error`, or whose `next_run_at` is long past, is the place to look when an instance falls behind. Every run has a deadline, so a run that hangs is recorded as an `error` once the deadline passes, and the housekeeping job is free to run again. [List housekeeping jobs](/api-reference/instance/listHousekeeping) has every field.

## The housekeeping jobs

An interval not marked fixed is a default, which an environment setting changes; [Settings](/guides/settings#every-environment-setting) names the setting for each, such as `TRASH_PURGE_INTERVAL_MS` for `trash-purge`.

<ReferenceList>

| Housekeeping job | What it does | Runs every |
| --- | --- | --- |
| `audit-cleanup` | Deletes audit log entries, and the record of outbound webhook deliveries, older than the audit retention. | 1 day |
| `auth-session-cleanup` | Deletes expired sign-in sessions. | 1 hour |
| `blob-integrity` | Checks that each store still holds its copies of blobs intact. A missing or altered copy is struck, and `blob-replicate` puts it back. | 1 hour |
| `blob-orphans` | Finds blobs that nothing refers to, and deletes each one on a later run, after `MARFA_BLOB_CLEANUP_GRACE_MS` (default 1 day). | 1 day |
| `blob-replicate` | Copies blobs to each store that its policy says should hold them. | 1 minute, and after each upload |
| `bulk-action-gc` | Deletes finished bulk actions older than `MARFA_BULK_ACTION_JOB_RETENTION_MS` (default 7 days). | 1 hour |
| `dcr-client-cleanup` | Deletes apps that registered themselves for sign-in more than `MARFA_DCR_CLIENT_RETENTION_DAYS` ago (default 30) and hold no access. | 1 day |
| `enrichment-sweep` | Reads the bytes of file items, and writes an image's `width` and `height` and a file's `extracted_text` onto the item. | 30 seconds |
| `event-log-cleanup` | Deletes events, and the stored answers to requests sent with an `Idempotency-Key`, older than the event log retention. | 1 hour |
| `grant-inactivity-retirement` | Disconnects an app you signed in to once it goes unused for `MARFA_GRANT_INACTIVITY_DAYS` (default 365). | 1 day (fixed) |
| `heartbeat` | Sends a `GET` request to `MARFA_HEARTBEAT_URL`, so a monitor somewhere else can tell the instance is up. | 1 minute |
| `inbound-delivery-cleanup` | Deletes inbound webhook deliveries past their retention: handled ones after 7 days and unhandled ones after 30, by default. | 1 minute |
| `rate-limit-cleanup` | Deletes expired rate-limit windows. | 1 hour |
| `revoked-grant-purge` | Deletes the record of a disconnected app after `MARFA_REVOKED_GRANT_RETENTION_DAYS` (default 90). | 1 hour (fixed) |
| `revoked-key-reap` | Deletes a revoked key 30 days after it was revoked. | 1 hour (fixed) |
| `trash-purge` | Purges items that have been in the trash longer than the trash retention. | 1 day |
| `version-thinning` | Removes old version snapshots that the version policy of each item's type no longer keeps. | 1 hour |
| `webhook-poll` | Sends outbound webhook deliveries that are due, and retries the ones that failed. | 30 seconds (fixed), and when deliveries are queued |
| `webhook-schedule` | Reads new events from the event log, and queues a delivery for each webhook that subscribes to them. | 1 second (fixed) |

</ReferenceList>

A setting can switch a housekeeping job off, and one that's off isn't listed. `heartbeat` is off until `MARFA_HEARTBEAT_URL` names a receiver, so a new instance doesn't list it. `enrichment-sweep` is off when `MARFA_ENRICHMENT_ENABLED` is `false`. `blob-orphans`, `bulk-action-gc`, `dcr-client-cleanup`, `grant-inactivity-retirement` and `revoked-grant-purge` are off when the interval or retention that drives them is `0`.

The retentions that `audit-cleanup`, `trash-purge`, `event-log-cleanup` and `inbound-delivery-cleanup` read can also be changed while the server runs, in the [configuration](/guides/settings#change-settings-while-it-runs).

## Run a housekeeping job now

Name the housekeeping job as the listing shows it:

```bash tab="CLI" tab-group="client"
marfa housekeeping run trash-purge
```

```http tab="HTTP"
POST /housekeeping/trash-purge/run
Authorization: Bearer <key>
```

The server runs it before it answers, so the request waits until the run finishes. The answer is the run:

```json
{
  "name": "trash-purge",
  "started_at": "2026-10-09T23:50:54.872Z",
  "finished_at": "2026-10-09T23:50:54.872Z",
  "outcome": "ok",
  "result": { "deleted": 0 },
  "error": null
}
```

A run that fails still answers `200`, with `outcome` set to `error` and the reason in `error`. The listing then shows this run as the last one, and a run on demand never makes the next scheduled run later.

The server refuses `409 housekeeping_job_running` while a run of the same housekeeping job is already in progress, so try again when it finishes. One that's switched off, or a name it doesn't run, is refused `404 housekeeping_job_not_found`. [Run a housekeeping job](/api-reference/instance/runHousekeeping) lists every answer.

The rules behind this page are in the [housekeeping chapter](https://github.com/withmarfa/marfa/blob/main/conformance/spec/housekeeping.md) of the contract.
