title: Housekeeping
description: See the work an instance does on itself, read what each housekeeping job last did, and run one now.
---

An instance looks after itself on a schedule: it purges the bin, thins old versions, moves expired feed items to the bin, clears old log entries, sends webhook deliveries, and copies and checks blobs. Each piece of that work is a housekeeping job, and one scheduler runs them all from one table. Reading what each job last did is how you check that an instance is keeping up, and running one yourself applies a new retention without waiting for its schedule.

**Listing needs the `instance.read` permission, and running needs `instance.maintain`.** These permissions apply to housekeeping operations. Item routes use their own permissions. The owner needs no key for either, through the private socket or signed in to the Health page, at `/auth/owner/health`, which lists every job with when it last ran and its error if it failed, and runs one with Run now.

## List the housekeeping jobs

```bash tab="CLI" tab-group="client"
marfa housekeeping list --json
```

```http tab="HTTP"
GET /housekeeping
Authorization: Bearer <key>
```

The answer holds every housekeeping job the instance runs, in one page. Each entry gives its schedule, whether it's running now, and what its last run did:

```json
{
  "data": [
    {
      "name": "audit-cleanup",
      "interval_ms": 86400000,
      "next_run_at": "2026-10-10T23:48:29.141Z",
      "running_since": null,
      "last_started_at": "2026-10-09T23:48:29.138Z",
      "last_finished_at": "2026-10-09T23:48:29.141Z",
      "last_outcome": "ok",
      "last_error": null,
      "last_result": { "deleted": 0, "deliveries": 0 }
    }
  ],
  "next_cursor": null
}
```

The answer has an entry for every housekeeping job; this shows one.

## Read what a housekeeping job did

`running_since` holds the time the current run started, and is `null` when nothing is running. `last_outcome` is `null` until a run finishes, then `ok` or `error`, with the reason in `last_error`. `last_result` holds what the run reported, in counts of its own: `deleted` for a cleanup, `copied` and `remaining` for `blob-replicate`, `pruned` for `version-thinning`.

A housekeeping job whose `last_outcome` stays `error`, or whose `next_run_at` is long past, is **the place to look when an instance falls behind**. Every run has a deadline, so a run that hangs is recorded as an `error` once the deadline passes, and the housekeeping job is free to run again. [List housekeeping jobs](/api-reference/instance/listHousekeeping) has every field.

## The housekeeping jobs

**The listing shows each registered job's schedule.** [Settings](/guides/settings#every-environment-setting) lists the environment settings that change configurable intervals and retention windows.

<include cwd>src/generated/housekeeping.md</include>

`feed-expiry` acts only on a type that has a `feed_days` window in its [retention policy](/catalog/your-own-types#retention-policy), set on the type or taken from a parent. It moves an active feed item to the bin, as a delete does, once more than that many days have passed since the item arrived. **Library items, archived items and items brought back from the bin are kept**, and a type with no window keeps its items. A moved item can be restored until the bin's retention ends, and `trash-purge` then deletes it for good. Each run reports `moved` and `held` in `last_result`; `moved` includes items a cascade took with them. `held` counts expired items it left alone because deleting them would also delete an item that hasn't expired, isn't a feed item or was brought back from the bin, because an edge with `cascade_on_delete` set to `block` refuses the delete, or because the delete failed. [Settings](/guides/settings#every-environment-setting) names `FEED_EXPIRY_INTERVAL_MS`.

A setting can switch a housekeeping job off, and **one that's off isn't listed**.

`heartbeat` is off until `MARFA_HEARTBEAT_URL` names a receiver, so a new instance doesn't list it. `enrichment-sweep` is off when `MARFA_ENRICHMENT_ENABLED` is `false`. `blob-orphans`, `bulk-action-gc`, `dcr-client-cleanup`, `grant-inactivity-retirement` and `revoked-grant-purge` are off when the interval or retention that drives them is `0`.

The retentions that `audit-cleanup`, `trash-purge`, `event-log-cleanup` and `inbound-delivery-cleanup` read can also be changed while the server runs, in the [configuration](/guides/settings#change-settings-while-it-runs).

## Run a housekeeping job now

Name the housekeeping job as the listing shows it:

```bash tab="CLI" tab-group="client"
marfa housekeeping run trash-purge
```

```http tab="HTTP"
POST /housekeeping/trash-purge/run
Authorization: Bearer <key>
```

**The server runs it before it answers**, so the request waits until the run finishes. The answer is the run:

```json
{
  "name": "trash-purge",
  "started_at": "2026-10-09T23:50:54.872Z",
  "finished_at": "2026-10-09T23:50:54.872Z",
  "outcome": "ok",
  "result": { "deleted": 0 },
  "error": null
}
```

**A run that fails still answers `200`**, with `outcome` set to `error` and the reason in `error`. The listing then shows this run as the last one, and a run on demand never makes the next scheduled run later.

The server refuses `409 housekeeping_job_running` while a run of the same housekeeping job is already in progress, so try again when it finishes. One that's switched off, or a name it doesn't run, is refused `404 housekeeping_job_not_found`. [Run a housekeeping job](/api-reference/instance/runHousekeeping) lists every answer.

## Empty the bin

**An item stays in the bin until it is purged, and a purge is permanent.** Left alone, the `trash-purge` job purges each item once it has been in the bin longer than `TRASH_RETENTION_DAYS`, which is 60 days unless you change it. `trash_retention_days` in the [configuration](/guides/settings#change-settings-while-it-runs) overrides that while the server runs, and a retention of `0` keeps every item. A run removes a limited number of items, and while items past the retention remain after a run that removed some, the job runs again at once rather than waiting for its interval.

To empty the bin now, purge every item whose state is `trashed`. A key needs the `items.purge` permission, and **the private socket can't do it**, because it carries no key:

```bash tab="CLI" tab-group="client"
marfa items bulk-action purge --state trashed --confirm PURGE
```

```http tab="HTTP"
POST /items/bulk-actions
Authorization: Bearer <a key holding items.purge>
Content-Type: application/json

{ "action": "purge", "confirm": "PURGE", "filter": { "state": "trashed" } }
```

Marfa answers that it queued the purge as a job:

```json
{
  "id": "01a150c0-71c7-7ea5-b5a4-68b6267b988a",
  "action": "purge",
  "status": "queued",
  "matched": 3,
  "processed": 0,
  "succeeded": 0,
  "errored": 0
}
```

`marfa items bulk-action job <id>` shows the job again, and its `status` is `completed` once the purge has finished. Add `--dry-run` first to list what the purge would take and change nothing. A bin of more than 10,000 items is refused with `400 bulk_cap_exceeded` unless you raise `--max-items`, which Marfa counts as 50,000 at most: purge what's left with a second run. To purge one item, run `marfa items purge <id>`.

## Try feed expiry with a moved clock

On a test server started with `MARFA_TEST_HOOKS=true`, [Settings](/guides/settings#move-the-clock-for-a-test) explains how to move the clock, and you can watch `feed-expiry` act without waiting a day. **Two credentials are in play**: a key runs the `marfa types register` and `marfa items create` commands, because the private socket refuses item operations, and the socket alone reaches the clock.

<Steps>
<Step>

With a key in `MARFA_API_KEY`, register a type whose feed items expire after one day, and put one in the feed:

```bash
marfa types register --body '{"id":"user.headline","fields":{"title":{"type":"string","required":true}},"retention_policy":{"feed_days":1}}'
marfa items create --type user.headline --prop title="Today" --tier feed
```

</Step>
<Step>

Move the clock two days forward, through the socket:

```bash
curl --unix-socket /srv/marfa/data/control/marfa.sock \
  -X POST http://localhost/_control/test/clock \
  -H 'Content-Type: application/json' -d '{"advance_ms": 172800000}'
```

</Step>
<Step>

Run the job, in place of waiting for its next turn, and read the item from the bin:

```bash
marfa housekeeping run feed-expiry
marfa items list --state trashed --type user.headline
```

```json
{
  "name": "feed-expiry",
  "started_at": "2026-10-22T20:42:52.014Z",
  "finished_at": "2026-10-22T20:42:52.016Z",
  "outcome": "ok",
  "result": {
    "moved": 1,
    "held": 0,
    "types": 1,
    "unresolvable": 0
  },
  "error": null
}
```

</Step>
</Steps>
