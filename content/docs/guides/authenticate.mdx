title: Authenticate
description: Send a key with data requests, or connect an app with OAuth so the owner approves its access.

A program has two ways into Marfa. A script sends a key, which begins `marfa_k1_`. An app connects with OAuth and receives an access token, which begins `marfa_at_`. **No program ever needs the owner's password.** [Access](/access) explains what a credential can hold.

## Send a key

Send the key in the `Authorization` header as a bearer token. [Get the current key](/api-reference/access/getCurrentKey) checks one by answering what it holds.

```bash tab="CLI" tab-group="client"
export MARFA_API_URL=http://localhost:8600
export MARFA_API_KEY=<key>
marfa keys current
```

```http tab="HTTP"
GET /keys/current
Authorization: Bearer <key>
```

```ts tab="TypeScript"
import { createClient } from "@withmarfa/client";

const marfa = createClient({
  baseUrl: "http://localhost:8600",
  credential: process.env.MARFA_API_KEY ?? "",
});

const { data } = await marfa.GET("/keys/current");
```

The CLI reads the key from `--key`, then `MARFA_API_KEY`, then the keychain, as [the CLI](/cli) explains. [The Swift SDK](/swift-sdk) takes it in the `Server` you open a working copy with. A missing, unknown, expired or revoked credential answers `401 unauthorized`.

## Connect an app with OAuth

The app registers, sends the owner to approve it, and receives an access token for the scopes the owner approved. These steps use the authorization code grant. A web page follows them with a few more constraints, which [Connect a web page](/guides/connect-a-web-page) covers. An app with no browser uses [the device grant](#connect-a-command-line-app). The instance's discovery document, at `/.well-known/oauth-authorization-server/auth`, lists every endpoint and the `scopes_supported`.

<Steps>
<Step>

### Register the app

Registration takes no credential:

```http
POST /auth/oauth2/register
Content-Type: application/json

{
  "client_name": "Reading app",
  "redirect_uris": ["https://reader.example.com/callback"],
  "token_endpoint_auth_method": "none",
  "grant_types": ["authorization_code", "refresh_token"],
  "scope": "core.note:read core.note:write offline_access"
}
```

Marfa answers `201` with the `client_id`. With `"token_endpoint_auth_method": "none"` the app proves itself with PKCE alone. Leave it out, and the answer also holds a `client_secret` to send with each token request. Redirect addresses must use `https`, unless you also set `"application_type": "native"`, which allows an `http` loopback address such as `http://127.0.0.1:9000/callback`. [Register an OAuth client](/api-reference/access/registerOAuthClient) lists every field.

</Step>
<Step>

### Send the owner to approve

Marfa accepts only PKCE with `S256`. Make a random verifier and keep it for the next step:

```bash
verifier=$(openssl rand -hex 32)
challenge=$(printf %s "$verifier" | openssl dgst -sha256 -binary | openssl base64 -A | tr '+/' '-_' | tr -d '=')
```

Open the authorization endpoint in the owner's browser, with the challenge and a `state` of your own:

```http
GET /auth/oauth2/authorize?response_type=code&client_id=<client_id>&redirect_uri=https%3A%2F%2Freader.example.com%2Fcallback&scope=core.note%3Aread%20core.note%3Awrite%20offline_access&code_challenge=<challenge>&code_challenge_method=S256&state=<state>
```

The owner signs in if needed and [chooses what to allow](#what-the-owner-chooses). Marfa then redirects the browser to your address with `code`, `state` and `iss`. **Check that `state` is the one you sent.** If the owner declines, the redirect carries `error=access_denied` and no code.

</Step>
<Step>

### Exchange the code for tokens

Send the code and the verifier to the token endpoint as a form:

```http
POST /auth/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=authorization_code&code=<code>&redirect_uri=https%3A%2F%2Freader.example.com%2Fcallback&client_id=<client_id>&code_verifier=<verifier>
```

```json
{
  "access_token": "marfa_at_…",
  "expires_in": 3600,
  "expires_at": 1791593756,
  "token_type": "Bearer",
  "refresh_token": "marfa_rt_…",
  "scope": "core.note:read core.note:write offline_access"
}
```

A code works once. `scope` lists what the owner approved, which **can be less than you asked for**. Send the access token exactly as you would a key.

</Step>
<Step>

### Keep the token fresh

Before the access token expires, exchange the refresh token for a new pair:

```http
POST /auth/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=refresh_token&refresh_token=marfa_rt_…&client_id=<client_id>
```

The app gets a refresh token only if it asked for `offline_access` and the owner approved it. **Each exchange ends the refresh token you sent**, so store the new one first. Sending a used refresh token answers `400 invalid_grant` and ends the whole chain, because Marfa can't tell which holder is the app. The app then signs in again.

</Step>
</Steps>

## Connect a command-line app

An app with no browser uses the device grant: it shows the owner a short code, and the owner approves it on another device. `marfa login` signs in this way.

<Steps>
<Step>

### Register for the device grant

Register as a native app with no redirect addresses. Keep `refresh_token` in `grant_types` if the app will ask for `offline_access`, or Marfa refuses the scope.

```http
POST /auth/oauth2/register
Content-Type: application/json

{
  "client_name": "Reading CLI",
  "application_type": "native",
  "token_endpoint_auth_method": "none",
  "grant_types": ["urn:ietf:params:oauth:grant-type:device_code", "refresh_token"]
}
```

</Step>
<Step>

### Ask for a device code

Name the scopes the app needs. A request with no `scope` answers `400 invalid_scope`.

```http
POST /auth/device/code
Content-Type: application/x-www-form-urlencoded

client_id=<client_id>&scope=core.note%3Aread%20offline_access
```

```json
{
  "device_code": "…",
  "user_code": "LFMCH9Q4",
  "verification_uri": "http://localhost:8600/auth/device",
  "verification_uri_complete": "http://localhost:8600/auth/device?user_code=LFMCH9Q4",
  "expires_in": 600,
  "interval": 5
}
```

Show the owner the `user_code` and `verification_uri`, or open `verification_uri_complete` for them. They sign in and choose what to allow, under [the same recent sign-in rule](#when-approval-needs-a-recent-sign-in) as the browser flow.

</Step>
<Step>

### Poll for the token

Ask for the token, **waiting `interval` seconds between requests**:

```http
POST /auth/oauth2/token
Content-Type: application/x-www-form-urlencoded

grant_type=urn%3Aietf%3Aparams%3Aoauth%3Agrant-type%3Adevice_code&device_code=<device_code>&client_id=<client_id>
```

Until the owner decides, Marfa answers `400 authorization_pending`, or `400 slow_down` if you ask too soon. Approval answers `200` with the same token response as the code exchange. `400 access_denied` means the owner declined, and `400 expired_token` means the code lapsed: start again.

</Step>
</Steps>

## What the owner chooses

The Approve access screen and the device approval page offer a choice for what the app asks, and nothing more.

- **Your data:** one control for each item type, from No access to Read only or Read and edit, up to the highest level the app asked for.
- **More control over Marfa:** each [permission](/catalog/permissions) starts turned off. `instance.maintain`, `schema.write` and `items.purge` are marked because they can't be undone.
- **Already allowed:** what the app held before it asked again. Approving never lowers it.

An app that asks for all data with `*:read` or `*:write` can be given chosen types instead, such as `core.note:read`. A form can only narrow the request. If the owner turns off everything beyond `openid` and `offline_access` that the app doesn't already hold, approving is declining: the app gets `access_denied` and keeps what it held. The rules are `keys-and-oauth/approval-*` and `keys-and-oauth/consent-nothing-denies` in [the contract](https://github.com/withmarfa/marfa/blob/main/conformance/spec/keys-and-oauth.md).

## When approval needs a recent sign-in

**Approving a write, or a permission the app doesn't already hold, needs a sign-in from the last five minutes.** Turning on only reading never does. If the owner's sign-in is older, the page asks them to [confirm it's them](/guides/sign-in-as-the-owner#confirm-its-you) as they press Approve. A program that sends an approval without a recent sign-in gets `403 forbidden` and no code.

The app does nothing differently: it waits for the redirect, or keeps polling and gets `authorization_pending`. The rules are `keys-and-oauth/consent-recent-needed` and `keys-and-oauth/consent-older-reads` in [the contract](https://github.com/withmarfa/marfa/blob/main/conformance/spec/keys-and-oauth.md#keys-and-oauthconsent-recent-needed).

## Revoke access

An app disconnects itself by revoking its refresh token, which ends its tokens and the owner's approval:

```http
POST /auth/oauth2/revoke
Content-Type: application/x-www-form-urlencoded

token=marfa_rt_…&token_type_hint=refresh_token&client_id=<client_id>
```

Marfa answers `200`, even for a token it doesn't hold. The owner can also disconnect an app on the Connected apps page, and can revoke the keys the app made at the same time. A credential holding `grants.manage` lists apps with `GET /auth/grants` and ends one with `DELETE /auth/grants/{id}`.

**Disconnecting from a browser needs a sign-in from the last five minutes.** A request without a page is refused `403 forbidden` and leaves the app working. `grants.manage` and the private local command are not affected by when the owner last signed in.

The `/auth/oauth2/` and `/auth/device/` endpoints **answer errors in OAuth's own shape**, such as `{ "error": "invalid_grant" }`, not in the [error envelope](/api-reference/errors).

## What a refusal looks like

**Branch on `error.code`, never on the message:**

- `401 unauthorized`: no credential, or one that is unknown, expired or revoked. An app whose access token expired exchanges its refresh token.
- `403 forbidden`: the credential lacks a permission, and `details.required_scope` names it.
- `403 type_not_permitted`: the credential can't read or write the type at the level needed, and `details.grant` names the type and level.
- `404 item_not_found`: the item doesn't exist, or it's of a type the credential can't read. The two answers are identical.

A refusal never tells a credential what it can't see.

## Change profile fields with a credential

A key or app with write access to each field it sends uses [Update the profile](/api-reference/access/updateProfile) to change the owner's name or avatar. This example needs `"name": "write"` in a key's `profile_permissions`, or the app scope `profile.name:write`:

```bash tab="CLI" tab-group="client"
marfa profile update --name "Reader"
```

```http tab="HTTP"
PATCH /profile
Authorization: Bearer <credential>
Content-Type: application/json

{ "name": "Reader" }
```

If any submitted field lacks write access or is invalid, none of them changes. **Profile write cannot change email**, even through a wildcard. [Permissions](/catalog/permissions#access-to-profile-fields) lists the fields and levels.
