---
title: Permission bundles
description: How the consent screen groups scopes into a few plain-language permissions.
---

When an app asks to sign in, the consent screen does not show the raw OAuth scope list. It groups the requested scopes into a small set of named permission bundles, each rendered as one checkbox in plain language. The issued token still carries the underlying scopes; the bundles are a presentation and request convenience over the [scope grammar](/api-reference/authentication#scopes).

## The default bundles

A hosted instance ships four bundles, all granted by default:

| Bundle | What granting it allows |
| --- | --- |
| Read your stuff | Read your items, tags, files, and the relationships between them. |
| Write your stuff | Create and change your data, and let the app set up the data types it needs. |
| Your profile | See and update your name and account details. |
| Connected services | See the outside services connected to your space. |

Read and write cover your content namespaces and deliberately exclude `system.*` security internals (credentials, devices, webhooks); Connected services is the only default bundle that grants read on `system.connection` / `system.integration`. The exact scope set each bundle expands to is advertised on the discovery document under `marfa_permission_bundles`.

## Generous by default, customisable

Every default bundle is pre-ticked, so the common path is a single approve. A Customise control reveals the underlying scope patterns for anyone who wants to grant less. Unticking a bundle drops its scopes from the grant; [partial grants](/api-reference/authentication#partial-grants) are honoured end to end.

## Enforcement

The bundles are a grouping over real scopes, so they genuinely bind. An OAuth access token is enforced against exactly the scopes granted at consent, regardless of the signed-in user's role — the role is the ceiling on what an app can be granted, not a pass-through of the user's own access. Unticking Write at consent blocks the app from writing, even for a tenant admin. See [Permissions](/api-reference/permissions) for how granted scopes project into the permission maps.

The generous default expands to wildcard scopes (`user.*:write`, and the content namespaces), which is how an app reaches a tenant's runtime `user.*` types — those never appear individually in the static scope allowlist.

## Self-hosting

The bundle set is configuration. Override it with the `MARFA_PERMISSION_BUNDLES` environment variable (a JSON array of bundles); an absent or malformed value falls back to the built-in defaults. The full `*:read` / `*:write` scopes remain available through the consent screen's Customise control for clients that genuinely need them.
