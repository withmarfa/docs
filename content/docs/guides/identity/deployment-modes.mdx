Marfa has one SDK surface and two client modes. Apps use the same call sites in either; what changes is where a read is answered from and what the deployment can enforce.

<Callout type="info">
  **Mode versus client.** Sync agents, importers, CLIs and similar automation
  tools are **apps with credentials**. Each runs against whichever mode its host
  chose, and the word _sync_ in a client's name says nothing about the mode it
  runs in.
</Callout>

## Remote

**The SDK and a Marfa server. Every call crosses the network.**

The canonical mode, and the one most features target: multi-space, multi-app, realtime over SSE, durable storage, server-stamped non-forgeable provenance, OAuth grants, an audit trail, metrics.

<Callout type="warn">
  Run one server process per database. The event bus lives in the process, so a
  second process against the same database silently stops delivering realtime
  events and stops firing installed integrations. Read [Running more than one
  process](#running-more-than-one-process) before adding a second instance.
</Callout>

A remote client holds nothing, so it reads nothing without a network. That is the trade: everything the server enforces applies, and nothing is available when the server is not.

Reach for it when the data matters across apps, devices and time, and the app can assume connectivity — a CLI, an MCP server, a scheduled job, a web app.

## Local

**The SDK and a durable on-device store, with a server if one is configured.**

The store is the app's read path. Items, edges, metadata and extensions are persisted locally, so a read is a local query and a write is applied before it leaves the device. Whether that store reconciles with anything is a separate question, and it has three answers.

| Configuration | What reconciles the store | Where the guarantees come from |
| --- | --- | --- |
| A Marfa server | The SDK's own queue and change stream | The server: non-forgeable `source`, field-level conflict resolution, OAuth, audit, realtime |
| An external sync layer, such as CloudKit or a file-sync tool | That tool, replicating the store's file across devices | That tool: a space maps to its account, and conflicts resolve by its rules, not Marfa's |
| Nothing | Nothing. The store is private to the app and the device | The SDK alone, best-effort |

The SDK surface is identical across all three, and moving between them is a change to the client configuration rather than to the call sites. The TypeScript kit's local engine covers the first row only: it reconciles with a Marfa server, and it needs a filesystem, so it runs under Node.js, Bun, Deno or an Electron main process rather than in a browser.

### What a local store cannot do on its own

- **Provenance is best-effort without a server.** `source` is stamped by whichever SDK writes it, and there is nothing to validate it. With a Marfa server configured it is credential-stamped and non-forgeable.
- **Conflict resolution belongs to whatever reconciles the store.** With a Marfa server that is the server's field-level machinery. With an external sync layer it is that tool's, typically last-writer-wins over a whole record. With nothing configured there is a single writer and the question does not arise.
- **The server-only surfaces stay server-only.** SSE `/events`, OAuth grants, webhook delivery, the audit trail and admin metrics all need a Marfa server, whichever mode the client runs in.

A client that keeps a durable store and reconciles it with a server is holding state the server has not seen. The rules that keep the two from drifting are the [sync contract](/sdks/sync-contract).

## What is the same in both

- The **SDK surface**. `client.items.create`, `client.edges.create` and the rest are identical.
- The **data shape**. Items, edges, metadata, extensions and attachments have the same structure.
- The **type system**. Core and custom types register the same way, and inheritance works the same way.
- The **edge model**. Dual-gate write semantics apply where permissions are present, and are trust-based where they are not.

## What differs

| Feature | Remote | Local, with a Marfa server | Local, without one |
|---|---|---|---|
| `source` non-forgeable | Yes (credential-stamped) | Yes (credential-stamped on replay) | No (SDK best-effort) |
| SSE `/events` | Yes | Yes | No |
| OAuth grants | Yes | Yes | No |
| Webhook delivery | Yes | Yes | No |
| Audit trail | Yes | Yes | No |
| Admin metrics | Yes | Yes | No |
| Rate limiting | Yes | Yes | N/A |
| Conflict resolution | Field-level optimistic concurrency | The same, applied on replay | Single writer, or the external tool's semantics |
| Retention and storage tiering | Tier-aware, server-enforced | The same | App-coordinated |
| Reads without a network | No | Yes | Yes |

## Which SDK offers which

| SDK | Remote | Local |
|---|---|---|
| [Swift SDK](/sdks/swift) | Yes | Yes, backed by SwiftData — with a server or without one |
| [TypeScript SDK](/sdks/typescript) | Yes | Yes, backed by SQLite — the [local engine](/sdks/local-engine), reconciling with a Marfa server |

## Running a server: scaling and operational limits

<Callout type="warn">
  Run one server process per database. The event bus is in-process, so a second
  process against the same database silently stops delivering realtime events
  and stops firing reactive integrations. See [Running more than one
  process](#running-more-than-one-process) below.
</Callout>

Cross-instance coordination is handled through Postgres — no Redis, no separate worker tier. Some subsystems are genuinely cluster-safe; the event bus is not, and the difference decides how far a deployment can scale horizontally today.

Cluster-safe:

- **Webhook delivery.** Publishing writes a row to a durable outbox table, and the delivery poller claims rows with `SELECT … FOR UPDATE SKIP LOCKED`, so a given delivery is picked up by exactly one instance no matter which instance produced it. Failed instances release claims automatically after a short TTL. This is the one event path that survives a multi-process deployment intact.
- **Background jobs.** Trash purge, version thinning, audit cleanup, event-log cleanup, rate-limit cleanup, auth-session cleanup, account-deletion purge, and bulk-action GC each run under a named Postgres advisory lock, so only one instance performs work on each tick. Other instances skip the tick cleanly.
- **API-key `last_used_at`.** The conditional UPDATE debounces writes at the database layer, so writes collapse to at most one per hour per key regardless of how many instances are handling requests.

Per-instance, and therefore approximate under a load balancer:

- **Rate limits.** Counters live in the database (`rate_limit_windows`), so instances sharing one database share one budget: a caller limited to `RATE_LIMIT_REQUESTS` gets that many requests per window collectively, however many instances answer. Only the per-space ceiling lookup is cached in-process (60 seconds), so a changed space cap takes up to a minute to propagate on every instance.

### Running more than one process

The server publishes change events on an in-process emitter. Writes are recorded durably in the `event_log` table, but nothing reads that table as a bus: no `LISTEN`/`NOTIFY`, no Redis, no polling consumer. A process only ever sees the events it published itself.

Two consequences, both silent — no error, no warning, no failed health check:

- **Realtime events go missing.** An SSE client attached to instance A never sees a write made on instance B. Sticky sessions do not fix this. Stickiness pins the *reader* to one instance; the problem is which instance the *writer* happened to land on. A healthy long-lived connection never reconnects, so it never triggers the `Last-Event-ID` replay that would otherwise fill the gap from `event_log`.
- **Reactive integrations stop firing for most writes.** The bridge that fans events out to installed integrations runs under a Postgres advisory lock so exactly one instance drains it. That instance drains its own in-process emitter, so with N instances roughly (N − 1) / N of all events reach no integration at all. The same lock covers the subscription-registry cache, so a connection installed or paused on another instance is not seen either.

Until the bus has a cross-process transport, a server deployment scales vertically. One process per database, restarted gracefully, is the supported shape. If you need more request throughput than one process delivers and can accept the constraints, the safe partial pattern is to keep exactly one process publishing writes and serving `/events`, and use webhooks rather than SSE for anything a second process would need to observe.

## Choosing

- **Remote when the app can assume a network.** Nothing to migrate, nothing to reconcile, and every guarantee the server enforces.
- **Local when a read has to be answered with no network**, or has to be answered in a frame. Point it at a server for the full guarantees, or at nothing for a private single-app store.
- **Local with an external sync layer** when you specifically want cross-device sync without running a Marfa server, and that tool's conflict semantics meet the bar.

Switching later is a change to the client configuration. The type system, the edge model and the data shape do not change.
