Marfa has one SDK surface and three deployment modes. Apps use the same client code regardless of mode; only the transport and enforcement guarantees change.

<Callout type="info">
  **Mode versus client.** Sync agents, importers, CLIs, and similar automation tools are **apps with credentials**, not a deployment mode and not a server feature. Each runs against whichever mode its host chose. The word _sync_ in "server-synced" describes data movement between a client and the server — it is independent of any particular client, including clients that happen to carry _sync_ in their name.
</Callout>

## Local-only

**SDK + local SQLite store. No server.**

The SDK talks to an on-device store rather than a remote API. Items, edges, metadata, extensions — all persisted locally. Suitable for:

- Single-app, single-device setups. A journal app that doesn't need cross-app data.
- Multi-app setups sharing a local store via OS mechanisms (iOS App Groups, macOS shared containers).
- Apps that want to start local and optionally graduate to server-synced later.

### Trade-offs

- **No conflict resolution.** Single writer per store, or app-coordinated. The server's version-conflict machinery doesn't apply.
- **No cross-app provenance enforcement.** Apps trust the local SDK. `source` is stamped best-effort by whichever SDK writes; there's no server to validate it.
- **No sync.** Data stays on-device. Reconciling across devices needs an external mechanism.

### When to use

Prototypes, offline-first apps, privacy-first apps, apps that run disconnected for extended periods. Apps that later move to server-synced without changing their code.

## Server-synced

**SDK + the Marfa server.**

The canonical mode. Multi-space, multi-app, real-time via SSE, durable storage, server-stamped non-forgeable provenance, OAuth grants, audit trail, metrics.

<Callout type="warn">
  Run one server process per database. The event bus lives in the process, so a
  second process against the same database silently stops delivering realtime
  events and stops firing installed integrations. Read [Running more than one
  process](#running-more-than-one-process) before adding a second instance.
</Callout>

All the mode-specific features called out across these docs (server-stamped `source`, SSE `/events`, OAuth flow, webhook delivery, admin metrics) apply only here.

### Trade-offs

- **Requires connectivity.** Without a network, apps can't read or write unless they run their own local cache on top.
- **Introduces a server to operate.** Self-hosted or managed by someone — someone is running Postgres and keeping it healthy.

### When to use

The platform-thesis mode. Any time data matters across apps, devices, and time.

## Third-party-synced

**SDK + local SQLite + an external sync layer.**

The SDK reads and writes locally, same as in local-only mode. An external sync engine (CloudKit, a custom WebDAV bridge, a file-sync system) replicates the SQLite store across devices.

### Trade-offs

- **No Marfa server.** No OAuth, no SSE, no server-enforced provenance. Whatever the third-party tool provides is what you get.
- **Conflict resolution is the third-party tool's.** Apps inherit CloudKit's last-writer-wins-per-zone semantics, for example.
- **Provenance is best-effort.** Same as local-only — no server to enforce `source`.
- **Space boundaries map to the third-party account.** One iCloud account = one space. A user with personal and work iCloud accounts runs them as separate Marfa spaces.

### When to use

Apps that want cross-device sync without standing up a Marfa server. Consumer iOS/macOS apps that lean on CloudKit for free sync. Privacy-first setups where data never leaves the user's own cloud account.

## What's the same across modes

- The **SDK surface.** `client.items.create`, `client.edges.create`, etc. are identical.
- The **data shape.** Items, edges, metadata, extensions, attachments all have the same structure.
- The **type system.** Core types and custom types register the same way. Inheritance works the same way.
- The **edge model.** Dual-gate write semantics apply when permissions are present; otherwise trust-based (local-only, third-party-synced).

## What's mode-specific

| Feature | Local-only | Server-synced | Third-party-synced |
|---|---|---|---|
| `source` non-forgeable | No (SDK best-effort) | Yes (credential-stamped) | No (SDK best-effort) |
| SSE `/events` | No | Yes | No |
| OAuth grants | No | Yes | No |
| Webhook delivery | No | Yes | No |
| Audit trail | No | Yes | No |
| Admin metrics | No | Yes | No |
| Rate limiting | N/A | Yes | N/A |
| Conflict resolution | app-coordinated | field-level optimistic concurrency | third-party tool's semantics |
| Retention / storage tiering | app-coordinated | tier-aware, server-enforced | per the third-party tool |
| Works offline | Yes (always local) | No (unless local cache layered) | Yes (sync on reconnect) |

## Server-synced: scaling and operational limits

<Callout type="warn">
  Run one server process per database. The event bus is in-process, so a second
  process against the same database silently stops delivering realtime events
  and stops firing reactive integrations. See [Running more than one
  process](#running-more-than-one-process) below.
</Callout>

Cross-instance coordination is handled through Postgres — no Redis, no separate worker tier. Some subsystems are genuinely cluster-safe; the event bus is not, and the difference decides how far a deployment can scale horizontally today.

Cluster-safe:

- **Webhook delivery.** Publishing writes a row to a durable outbox table, and the delivery poller claims rows with `SELECT … FOR UPDATE SKIP LOCKED`, so a given delivery is picked up by exactly one instance no matter which instance produced it. Failed instances release claims automatically after a short TTL. This is the one event path that survives a multi-process deployment intact.
- **Background jobs.** Trash purge, version thinning, audit cleanup, event-log cleanup, rate-limit cleanup, auth-session cleanup, account-deletion purge, and bulk-action GC each run under a named Postgres advisory lock, so only one instance performs work on each tick. Other instances skip the tick cleanly.
- **API-key `last_used_at`.** The conditional UPDATE debounces writes at the database layer, so writes collapse to at most one per hour per key regardless of how many instances are handling requests.

Per-instance, and therefore approximate under a load balancer:

- **Rate limits.** Counters live in the database (`rate_limit_windows`), so instances sharing one database share one budget: a caller limited to `RATE_LIMIT_REQUESTS` gets that many requests per window collectively, however many instances answer. Only the per-space ceiling lookup is cached in-process (60 seconds), so a changed space cap takes up to a minute to propagate on every instance.

### Running more than one process

The server publishes change events on an in-process emitter. Writes are recorded durably in the `event_log` table, but nothing reads that table as a bus: no `LISTEN`/`NOTIFY`, no Redis, no polling consumer. A process only ever sees the events it published itself.

Two consequences, both silent — no error, no warning, no failed health check:

- **Realtime events go missing.** An SSE client attached to instance A never sees a write made on instance B. Sticky sessions do not fix this. Stickiness pins the *reader* to one instance; the problem is which instance the *writer* happened to land on. A healthy long-lived connection never reconnects, so it never triggers the `Last-Event-ID` replay that would otherwise fill the gap from `event_log`.
- **Reactive integrations stop firing for most writes.** The bridge that fans events out to installed integrations runs under a Postgres advisory lock so exactly one instance drains it. That instance drains its own in-process emitter, so with N instances roughly (N − 1) / N of all events reach no integration at all. The same lock covers the subscription-registry cache, so a connection installed or paused on another instance is not seen either.

Until the bus has a cross-process transport, a server-synced deployment scales vertically. One process per database, restarted gracefully, is the supported shape. If you need more request throughput than one process delivers and can accept the constraints, the safe partial pattern is to keep exactly one process publishing writes and serving `/events`, and use webhooks rather than SSE for anything a second process would need to observe.

## Choosing

- **Build against server-synced by default.** It's the mode with the most guarantees and the one most features target.
- **Add local-only as an option** if your app has a meaningful offline story or a "free tier" that doesn't need a server. Same SDK call sites; different client config.
- **Use third-party-synced** when you specifically want to avoid running a server and your platform's sync layer meets the bar.

Switching modes later is mostly a config change in the SDK. The type system, edge model, and data shape don't change.
