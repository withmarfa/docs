`system.*` is a small reserved namespace for operational items. Only the platform defines these types; spaces and apps cannot register new ones.

## The set

Every `system.*` type is registered, and every one is listable as an item.

| Type                    | Represents                                                                                                                                                                                                                                                                                                | Surfaces in console as                                                           |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `system.device`         | A connected device. Carries name, kind, last-active timestamp.                                                                                                                                                                                                                                            | A Devices list. Revocable.                                                       |
| `system.credential`     | A platform credential — discriminated on `kind`: `api_key` (a Marfa client credential), `oauth_token` (encrypted OAuth provider config for an Integration), or `api_token` (encrypted bearer for an Integration whose upstream is API-key-authenticated, not OAuth). Carries permissions, last-used time. | A Credentials list. Revocable.                                                   |
| `system.webhook`        | A webhook subscription. Carries URL, filters, delivery history.                                                                                                                                                                                                                                           | A Webhooks list. Editable.                                                       |
| `system.app`            | A registered app identity. Required for `app.<app-name>.<type>` to mean anything.                                                                                                                                                                                                                         | An Apps list.                                                                    |
| `system.connection`     | An approved relationship between this space and an external authority. Two kinds: `app`, `integration`. See [Connections](/guides/connections/connections).                                                                                                                                               | A Connections list. Revocable.                                                   |
| `system.integration`    | A published manifest describing how an integration talks to an external service. One item per (name, version) pair. See [Integrations](/guides/connections/integrations).                                                                                                                                 | An Integrations list — typically the marketplace surface.                        |
| `system.activity`       | Operator-visible state — sync progress, errors, reauthorization prompts. Severity-tagged. See [Activity](/guides/connections/activity).                                                                                                                                                                   | An Activity feed; the `action_required` slice surfaces as a Repairs-style inbox. |
| `system.account_holder` | The graph handle for the person who owns a space, so edges such as `authored-by` can name them. One item per space, created at sign-up. Carries no fields — the profile endpoints stay the source of truth, and the item id is exposed on the profile wire shape as `account_holder_item_id`.             | Not listed — referenced by edges.                                                |

The user's account profile is **not** in this set. There is no `system.profile` type and no profile item: the profile is served directly from `GET /profile/me` and the OIDC userinfo endpoint, with no row in the items table and nothing to list or transition. See [Profile](/guides/identity/profile).

## Listing system items

Every `system.*` type is listed through the items route, and that is the general answer. Two kinds carry a route of their own as well: `GET /integrations` returns registered integrations shaped for a catalog — see [Marketplace](/guides/connections/marketplace) — and `GET /webhooks` returns outbound webhook subscriptions with their secrets redacted. There is no `GET /connections`; that root path exists for install, uninstall and proxy operations on the kind rather than for listing.

To enumerate any of them through the items route:

```
GET /items?type=system.connection
GET /items?include=system
GET /items?type=system.integration
GET /items?type=system.webhook
GET /items?type=system.device
```

Standard items semantics apply — pagination, filters, edge / metadata hydration, audit. The same applies to single-item GET, PATCH, and `transition`. See [Search and query](/guides/querying/search-and-query) for the filter grammar.

The `include=system` parameter is for the case the list above mostly does not show: a query that does **not** name a `system.*` type. A listing or a search with no system type in its filter omits `system.*` rows, and the token is what opts them back in. A query already filtering on a specific `system.*` type has opted in by doing so, so only the second example above needs the token. See the next section.

## Items with reduced operability

`system.*` items are items, so they share the standard item plumbing — they're listable, addressable, audit-logged. The web console can render lists for them through ordinary item views without bespoke pages.

But they are not user content, and several universal operations don't apply:

- **Excluded from list and search defaults.** `GET /items` and `GET /search` skip `system.*` rows unless the caller opts in — with `?include=system`, or by filtering on a specific `system.*` type.
- **No tier dimension.** `system.*` items don't carry the `tier` field. Setting it on write returns `400 validation_error` naming the `tier` field.
- **Bounded lifecycle.** `system.*` items use only `active` and `revoked` — not the universal three-state (`active` / `archived` / `trashed`). The `transition` endpoint enforces this.
- **No runtime registration.** `system.*` types are platform-shipped and seeded into the instance rather than registered; `POST /types` refuses the namespace for every credential, platform included, with `403 forbidden`.

This is a recurring pattern — "item with reduced operability" — and any future `system.*` types will follow the same shape.

## Why items, not bespoke pages

Treating these as items rather than special-cased records means the web console gets device, credential, webhook, and app management for free through the same surfaces it uses for everything else. Listings, filters, audit logs, search, permissions — all work uniformly.

The trade-off is that some universal operations have to be carved out (tier, archive). The carve-outs are small. The reuse is large.

## Permissions

`system.*` permissions are scoped per type: a credential can hold `read system.device` without `read system.credential`. The console uses this to expose, say, a Devices list to a user-level credential while keeping credential management admin-only.

A non-platform credential can never write to `system.*`. The reserved-root check at `POST /items` rejects ordinary clients.

## Naming pattern

The single segment after `system.` is a singular operational noun. New `system.*` types — when added — follow the same shape.
