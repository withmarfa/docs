Registering a type is a structured operation. The platform has correctness rails to keep registrations honest at scale — useful to any author, whether writing TypeScript directly, building visually in the console, or working through Claude Code or another AI assistant.

## The inherit-vs-sibling rubric

The most common authoring decision: should this be a sibling type (its own shape, optionally `compatible_with`) or a child of an existing type?

**Inherit only if every ancestor field is semantically required for your type. Otherwise sibling.**

Why this rule, in this direction:

- A bad inheritance choice is hard to recover from. A child can sharpen an inherited field's description or tighten it to required, but it cannot change what the field is. If you decide later that your type's `body` should mean something different from `core.note.body`, you cannot fix it without re-publishing under a different identifier.
- Sibling is recoverable. You can always add inheritance later if the semantic alignment becomes real. You cannot remove inheritance later without breaking consumers.
- AI-assisted authoring tends toward over-inheritance — it's the kind of structure a model recognizes and reaches for. Defaulting to sibling counter-balances that.

If the rubric tells you sibling, declare `compatible_with` if your shape is a structural superset. The platform verifies the claim at registration — see [Namespaces](/guides/schema/namespaces#declaring-compatibility).

## Cross-discoverability and the inheritance choice

The rubric above is about correctness. A second consideration sometimes pulls in the other direction: discoverability by generic readers.

Children appear in parent-type queries automatically — `?type=core.bookmark` returns both `core.bookmark` items and items of any type that inherits from it. Generic readers — feed apps, search interfaces, AI assistants browsing across a whole space — find your items without knowing your type exists.

This holds on every read surface that takes `?type=`: `GET /items`, `GET /search` and `GET /export` resolve the parameter identically. `core.bookmark` and `core.bookmark.*` are two spellings of the same subtree, and both are accepted everywhere.

This holds whatever you name your type. `acme.annotated_bookmark` with `parent: "core.bookmark"` is returned by a query for `core.bookmark`, exactly like `core.bookmark.readwise` is. Naming your type under the parent's namespace is a readability choice, not a requirement for discovery.

Permissions work the other way, and the difference matters when you pick an identifier: a `core.bookmark.*` grant does **not** reach a type named outside that namespace, whatever it declares as its parent. A credential reaches `acme.annotated_bookmark` through a pattern that names it. See [Type permissions](/api-reference/permissions#type-permissions).

Siblings with `compatible_with` do not appear in parent-type queries. The declaration is a trustworthy claim that consumers *can* read your items via the parent shape, but they have to know your type identifier and query for it directly.

If your items should be discoverable by readers expecting the parent shape, prefer inheritance even when the correctness rubric leans sibling. If the shape genuinely diverges and inheritance would force you to redefine ancestor fields, stay sibling and accept that generic readers find your items only when they enumerate known compatible types.

## When a subtype earns its place

Whether you're inheriting or just nesting names, a subtype is justified only when:

1. **Convergent shape across instances of the kind.** Multiple instances of the subtype share fields that the parent doesn't carry.
2. **Queryable or renderable separately by consumer apps.** A consumer can do something different with the subtype than with the parent — different UI, different filter, different processing.
3. **Differentiating fields aren't already on the parent.** If everything that distinguishes the subtype is already in the parent, the subtype is just a label.

A worked counter-example: there is no `core.file.document`. PDFs, Word docs, plain text, EPUBs — they don't share fields beyond what `core.file` already carries (`blob_ref`, `mime_type`). A generic file viewer reads them all the same way through `mime_type`. There's no consensus shape to add. So `core.file` stops at `image`, `audio`, `video` — each of which carries additional fields (`width`, `height`, `duration`).

Apply the same test to your own subtypes. If you can't fill in all three points, prefer a flat sibling.

## The version field and the diff rail

A type's `version` is a positive integer, not a semver string. It defaults to `1`, and `POST /types` rejects a non-integer (or a value below 1) with `400 invalid_schema` on the `version` field. The integer counts schema revisions; it isn't a `major.minor.patch` triple.

The diff rail is the load-bearing check on top of that integer. When you submit a new version of an existing type, the server computes the structural diff against the prior version and classifies it. The class decides whether the integer must increase:

| Diff class | What changed | Version requirement |
|---|---|---|
| No-op | Structurally identical | Rejected — nothing to register |
| Descriptive | Label, description, field descriptions, or display hints only | Same integer accepted, or higher |
| Additive | A new optional field, a raised size cap, a search-flag change, or a new compatibility claim | Must increase |
| Breaking | Field removed, shape changed, required flipped either way, a lowered size cap, a parent change, or a withdrawn compatibility claim | Must increase |

The diff reads every attribute a field carries, not just its type. A `maxLength` quietly halved rejects writes that used to succeed, so it is breaking; a `maxLength` raised accepts strictly more, so it is additive. Adding or removing a cap altogether is breaking, because the value it falls back to is an instance default the schema can't see. Flipping `required` is breaking in both directions — tightening rejects existing rows, loosening breaks every reader compiled against the guarantee.

A descriptive-only change may keep the same integer so a docs tweak doesn't force consumers to re-pin; everything else must bump.

The integer collapses the additive and breaking cases into one rule — both require the number to go up — while the diff class still surfaces in the error so you know which fields drove it. A bump that doesn't satisfy the rule returns `422 version_bump_mismatch` with the offending fields listed.

Without this rail, version bumps drift over time. Convention alone (style guides, CLAUDE.md notes) helps but is advisory; only the registration-time check enforces. The platform stays honest by construction because every author hits the same gate.

A registration request carries the integer directly:

```json
POST /types
{
  "id": "carla.meal_plan",
  "description": "A weekly meal plan.",
  "version": 1,
  "fields": {
    "week_of": { "type": "string", "required": true },
    "title": { "type": "string", "required": true }
  }
}
```

All of the above governs types: an integer, a diff, and a check at registration. Integrations carry a version of their own, a semver string rather than an integer, and the [marketplace](/guides/connections/marketplace) page describes it.

## Field attributes

A field declaration is `type` plus whatever refinements apply. Everything below is optional and everything below is carried through to the registry, so `GET /types/{id}` returns what you wrote.

| Attribute | Applies to | What it does |
|---|---|---|
| `description` | any | One line of prose. Surfaced in the type catalog and to authoring tools. |
| `required` | any | A write missing the field is rejected `400 validation_error`. May also be declared as a top-level `required: ["title"]` array; the two are equivalent. |
| `enum_values` | `enum` | The closed set of accepted values. Required on an `enum` field. |
| `items_type` | `array` | Names the element type. Required on an `array` field. |
| `maxLength` | `string`, `enum` | Caps one field's length, independently of the request-body limit. Defaults to 100,000 characters. |
| `maxItems` | `array` | Caps element count. Defaults to 10,000. |
| `searchable` | `string` | `false` keeps the field out of full-text search. Use it for opaque ids, secrets, and anything that would only ever be noise in results. |
| `format` | `string` | `bcp47` or `iso3166` — annotates what the string contains. |

The field types are `string`, `integer`, `number`, `boolean`, `url`, `email`, `date`, `datetime`, `enum`, `array`, and `object`.

`url`, `email`, `date` and `datetime` may also be written as a `string` with a matching `format`, which normalizes to the field type: `{ "type": "string", "format": "url" }` and `{ "type": "url" }` register the same field. `bcp47` and `iso3166` have no equivalent field type, so they stay as `format`.

## The SDK helper

`defineType()` is the SDK helper for authoring in TypeScript. It is a no-op at runtime — it returns its argument unchanged — but at compile time it constrains the input to a structurally-valid type schema, so field-shape mistakes surface in the editor rather than at registration. It carries the same `version` integer as the wire shape, defaulting to `1`. Pair it with `client.types.register()` to send the registration.

```typescript
import { defineType } from '@withmarfa/sdk';

export const mealPlan = defineType({
  id: 'carla.meal_plan',
  description: 'A weekly meal plan.',
  version: 1,
  fields: {
    week_of: { type: 'string', required: true },
    title: { type: 'string', required: true },
  },
});

await client.types.register(mealPlan);
```

The schema passed to `defineType()` is the same shape `POST /types` accepts — the integer `version`, the `fields` map, and an optional `parent` — so the curl body and the SDK call register the same type. The register call surfaces the server's error shape directly when the registration is rejected.

One file per type, predictable layout. AI-assisted authoring works well when there's a consistent shape to follow — `defineType()` is that shape.

## Generated TypeScript registry

Codegen emits a single human-readable file (or small set) listing every type's name, fields, parent, and one-line description. The first place an author looks when extending an existing type, and the source of truth that consumer apps import from.

The generated registry is the artifact `defineType()` calls feed; it's also the artifact community-published types add to when consumers install them.

## Reserved field names

A handful of field names are reserved across every type, regardless of who authored it. They live as top-level columns on the item wire shape and carry platform-wide meaning — the capturing device, the user-meaningful timestamp, the natural-key identifier, and so on. A custom type cannot redeclare them as properties; registration is rejected `400 property_shadows_field`.

| Field | Meaning |
|---|---|
| `device` | Capturing host label (`"MacBook Pro"`, `"iphone-aic-15"`) — see [Provenance](/guides/core-model/provenance). |
| `source_id` | Upstream system's stable identifier — the natural-key half of `(source, source_id)`. |
| `timestamp` | User-meaningful time for the item (e.g. when a photo was taken). |
| `capture_latitude`, `capture_longitude` | Where the device was at item creation. |
| `version`, `schema_version` | Server-managed integers (mutation count, type-schema version). |
| `tier`, `state` | Curation axis (`library` / `feed`) and lifecycle axis (`active` / `archived` / `trashed`). |
| `source` | Credential-stamped origin — non-forgeable in server-synced mode. |
| `id`, `type`, `space_id`, `properties`, `created_at`, `updated_at` | Structural keys on the wire shape. |

If your type carries a concept that overlaps semantically with one of these (e.g. an audio input device for a voice-capture type), set the first-class field directly when it matches and pick a more specific property name when it doesn't (`input_device`, `audio_input`, etc.). The rule prevents two values coexisting under the same key with nothing telling downstream consumers which is authoritative.

## Error shapes

Quality of error responses is part of the authoring surface. Specific over generic.

| Code | When | Detail |
|---|---|---|
| `400 inheritance_violation` | Child changes an inherited field's shape, or loosens one the ancestor requires. | Names the attribute that conflicts and the ancestor that declared it. |
| `400 property_shadows_field` | A property name shadows a first-class Item field. | Lists every colliding `fields.<name>`. |
| `422 compatible_with_violation` | A `compatible_with` claim doesn't hold. | Names each missing or mismatched field, and the target that requires it. |
| `422 version_bump_mismatch` | Diff class doesn't match the submitted version bump. | Lists the fields that drove the actual diff class. |
| `403 forbidden` | Any credential tries to register a reserved-root type (`core.*`, `system.*`, `marfa.*`) — the platform's own vocabulary is seeded, not registered. Also a publisher-tier registration under a handle the caller's account does not hold. | Names the reserved namespace, or the handle the registration would need. |
| `400 handle_reserved` | Reserved word or reserved-root collision in a `<publisher>.<type>` registration. | Names the rule that failed. |

A registration that fails any of these returns the structured error and writes nothing. Refining the schema and resubmitting is the workflow.

## Why server-side enforcement matters

Convention helps; enforcement holds the line. Across enough authors over enough time, the rubric drifts and version bumps slip — unless the server is the gate. Documenting the rules here is the human-readable half; the server-side checks are the load-bearing half.
