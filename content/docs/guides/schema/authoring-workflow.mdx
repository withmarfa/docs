A type schema is JSON. Nothing stops you writing one in an editor and POSTing it, and for a second field on an existing type that is the right amount of ceremony. For a new type the loop below is shorter, because it starts from something that already validates.

## The loop

<Steps>

<Step>

### Scaffold

```bash
marfa types scaffold carla.meal_plan --output carla.meal_plan.json
```

The command runs offline — no server, no credential. It emits a schema carrying one field per supported attribute, with each field's description explaining what its attribute does, so the vocabulary is in front of you rather than in another tab.

Pass `--minimal` for a couple of starter fields instead. Pass `--parent <type>` to inherit; fields the parent already declares are left out, since a child that restates one is rejected rather than helped.

</Step>

<Step>

### Edit

Rename the fields to what your type is about and delete the ones you don't need. The scaffold is a menu, not a starting shape — a good type is usually five fields, not twelve.

Two decisions worth making deliberately here:

- **`required`.** Only for fields without which the item is meaningless. Required-ness is the hardest thing to change later: tightening it rejects items that already exist, so both directions are a breaking diff.
- **`compatible_with`.** Declare it only if every field your target requires is present under the same name, and any of its optional fields you also declare are shaped so a reader of the target could not mis-parse them. The server checks, and a claim that doesn't hold is rejected — the rules are on [Namespaces](/guides/schema/namespaces#declaring-compatibility).
- **`roles`.** A closed set of structural roles your type declares about itself, so an edge can constrain on what a type is *for* rather than on its name. `container` is the only one today: declare `roles: ["container"]` and your type becomes a valid target for `in-collection`, which is how a publisher's own container holds a publisher's own members with no core change. Roles are inherited, so a subtype of a container needs none of its own. Adding one widens the type; removing one is breaking, because every edge constraining on it stops accepting the type.

</Step>

<Step>

### Validate

```bash
marfa types scaffold carla.meal_plan | marfa types register
```

There is no separate validate step, and that is the point: the scaffold runs the same validator the server applies at registration, so a schema that came out of `scaffold` is one `register` accepts. If you edited it into something invalid, `register` says exactly which field and what to do.

</Step>

<Step>

### Register

```bash
marfa types register --file carla.meal_plan.json
marfa types describe carla.meal_plan
```

`describe` reads the schema back as the registry stored it. Worth doing once: it shows you the normalized form, which is what every consumer of `GET /types` sees.

</Step>

</Steps>

## A worked example

A meal-planning app's type, after editing the scaffold down:

```json
POST /types
{
  "id": "carla.meal_plan",
  "label": "Meal Plan",
  "description": "A week of planned meals, with the shopping list it implies.",
  "version": 0,
  "compatible_with": ["core.task"],
  "fields": {
    "title": { "type": "string", "description": "What this week's plan is called." },
    "week_of": { "type": "date", "description": "Monday of the week the plan covers." },
    "status": {
      "type": "enum",
      "description": "Where the plan is in its life.",
      "enum_values": ["draft", "shopping", "cooking", "done"]
    },
    "shopping_list": {
      "type": "array",
      "description": "Ingredients still to buy.",
      "items_type": "string",
      "maxItems": 200
    },
    "notes": {
      "type": "string",
      "description": "Free-form notes on the week.",
      "maxLength": 20000
    },
    "grocery_order_ref": {
      "type": "string",
      "description": "Opaque id from the grocery service. Never useful in search results.",
      "searchable": false
    }
  },
  "required": ["title"],
  "display_hints": { "title_field": "title", "body_field": "notes" },
  "merge_policy": {
    "fields": { "notes": "keep_both_copies" },
    "default": "last_writer_wins"
  }
}
```

Reading it back:

- `compatible_with: ["core.task"]` holds because `core.task` requires `title` and this type declares `title` as a string. A task-aware reader can pick up a meal plan and find what it expects.
- `searchable: false` on `grocery_order_ref` keeps an opaque id out of full-text results, where it could only ever be noise.
- `maxItems` and `maxLength` bound one field each, independently of the request-body limit.
- `merge_policy` sends `notes` down the keep-both-copies path, so a concurrent edit spawns a sibling item rather than dropping a write.

## One validator, both paths

The types Marfa ships are authored as JSON files in the platform repository; yours arrive over `POST /types`. Both are checked by the same code, so a schema that is legal one way is legal the other, verbatim — including required-ness declared as a top-level array, `format` normalization, and every optional field attribute.

That matters mostly when you learn from an example. Copying a shipped type's JSON and editing it gets you a valid submission, because there is nothing the in-tree files can express that a registration cannot.

<Callout type="info">
  Every rejection names the path that failed, what was expected there, what arrived, and what to do about it. If you get one that doesn't, that's a bug worth reporting — the error surface is part of the authoring surface.
</Callout>
