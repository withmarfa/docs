Every type identifier sits in one of six namespace tiers. The first segment of the identifier — the **root** — tells a reader (or parser) the shape at first glance.

## The tiers

| Namespace | Segments | Purpose |
|---|---|---|
| `core.*` | Two or more | Platform-shipped, immutable, narrow. Reference types and universal content kinds. |
| `system.*` | Two | Platform-internal operational types. Devices, credentials, webhooks, app identities. |
| `marfa.*` | Two or more | The platform's own first-party types — captured email and the podcast pair ship here. Reserved so it cannot be claimed as a handle. |
| `app.<app-name>.<type>` | Exactly three | App-published types. Available in any space that uses the app. |
| `user.<type>` | Two or more | Unpublished personal types. Space-scoped; never published to the registry. |
| `<publisher>.<type>` | Two or more | Publisher-namespaced types. Installable from the registry. |

A tier is a naming grammar, not a statement of origin. It tells you the shape of an identifier and which rules govern registering it, and nothing about who authored the type: `readwise.book` ships with the platform, a person's own `nadia.meal_plan` does not, and both sit in the publisher tier.

## Reserved roots

The roots `core`, `system`, `app`, `user`, `marfa`, and `space` are reserved. They cannot be claimed as publisher handles.

`core.*`, `system.*`, and `marfa.*` types cannot be registered at runtime by any credential. The platform's own vocabulary is seeded into the instance rather than registered, and `POST /types` rejects a reserved-root claim whoever makes it.

Seeded means the build carries the schemas and writes them into the instance at boot, and the stored row is what resolves at runtime rather than the compiled set. The seed reapplies on every start, so a direct database edit to a shipped type is lost at the next restart. A custom type edited the same way is not.

`space` is the one reserved root that names no tier, and it holds no types at all. It is reserved so that the OAuth [space permissions](/api-reference/authentication#space-permissions), which are literals of the form `space.<surface>`, can never be confused with a type identifier. Nothing can be registered beneath it, which is what makes a grant under that root unambiguous.

The roots are the whole of what a handle claim is refused for. No structural word is reserved beyond them, because a handle is a namespace claim rather than a URL path — no Marfa route is served at `/<handle>` — so a word like `admin` or `settings` collides with nothing. What reservation covers is the type grammar's own first segments, which is narrower than every first segment that carries meaning: the [scope grammar](/api-reference/authentication#scopes) reads `metadata.<sub>` and `edge.<type>` literals, and `metadata` and `edge` are both claimable handles. `PUT /auth/me/handle` rejects a reserved root with `400 handle_reserved`.

## App vs publisher

`app.` separates app trust from publisher trust. An app publishes under `app.<app-name>.*`, registered through a `system.app` identity; a community publisher publishes under `<handle>.*`, registered through a claimed handle. Two distinct trust contexts, two distinct namespaces, and the reserved-root rule disambiguates them: any first segment that isn't a reserved root is a publisher handle.

Publishing under a handle means owning it. On hosted deployments, registering a publisher-tier type requires the caller's account to hold the handle in the first segment: a credential whose account holds a different handle, or none, is refused with `403 forbidden` naming the namespace and the handle it would need. The operator key is exempt, which is how the platform's own vendor-shaped types exist under roots like `google.*`. Self-hosted deployments in keys mode have no user accounts and therefore no handle system; the ownership rule does not apply there, and the deployment's operator registers publisher-tier types freely.

The `app.` tier is pinned at exactly three segments so the app name always occupies a known position. Publisher types are not pinned — `<publisher>.<type>` is the common shape, but a publisher may nest further, which is how the platform's own integration types are named (`google.calendar.event`, `google.tasks.task`). Treat two segments as the convention rather than the rule.

## Worked examples

| Identifier | Tier | Reading |
|---|---|---|
| `core.note` | `core` | A platform-shipped type. |
| `core.entity.person` | `core` | A platform-shipped subtype of `core.entity`. |
| `system.device` | `system` | A platform-internal operational type. |
| `app.fieldbook.daily_note` | `app` | A type published by the registered Fieldbook app. |
| `user.recipe` | `user` | A personal type, scoped to one space. |
| `nadia.meal_plan` | `<publisher>` | A type published by the publisher with handle `nadia`. |
| `google.calendar.event` | `<publisher>` | A platform-shipped integration type, nested under a publisher root. See [Types](/guides/core-model/types#what-ships-in-the-registry). |
| `marfa.captured_email` | `marfa` | A first-party integration type under the reserved platform root. |

## Sibling vs child

A custom type can be a **sibling** of another type (its own shape, optionally declaring `compatible_with`) or a **child** that inherits.

Both are first-class. The default is sibling. Inheritance is a stronger commitment — a child may sharpen an inherited field's description or tighten it to required, but it cannot change what the field is, so a bad inheritance choice is hard to recover from. Sibling is recoverable; you can always add inheritance later.

The rubric: inherit only if every ancestor field is semantically required for your type. Otherwise sibling, optionally `compatible_with`. The full rubric lives on [Authoring types](/guides/schema/authoring-types).

User types are flat by convention but can extend via inheritance where it earns its place. The same applies to publisher and app types — flat is the default; nest when the structural relationship is real.

### Declaring compatibility

A sibling type declares `compatible_with` to assert that its shape is a structural superset of one or more other types, so a reader that understands the target can read this type without knowing it exists.

```json
POST /types
{
  "id": "carla.meal_plan",
  "version": 0,
  "compatible_with": ["core.task"],
  "fields": {
    "title": { "type": "string", "required": true },
    "week_of": { "type": "date" }
  }
}
```

It is an array of type identifiers — a type may be compatible with several targets at once. Field names are not remapped: compatibility means a reader can pick up your item and find the fields where it expects them, which a rename would defeat.

Two rules apply, because the reader does two different things:

- **Every field the target requires must be present here, required, and shaped compatibly.** A reader expects those on every item.
- **Every field the target merely declares must, if you declare the same name, be shaped compatibly.** A reader reads an optional field whenever it is present, so a same-named field of a different shape is a mis-parse rather than a harmless extra. Omitting the field entirely is fine.

#### What counts as shaped compatibly

The question is whether a value valid under your field could be handed to a reader of the target's field without a mis-parse. So a narrower type stands in for the wider one whose values contain it, and never the reverse:

| Your field | Reads as | Why |
|---|---|---|
| `url`, `email`, `datetime`, `date` | `string` | each holds a string |
| `enum` | `string` | an enum only ever holds one of a fixed set of strings |
| `integer` | `number` | every integer is a number |

An `enum` may also narrow an `enum` target to a subset of its values. `items_type` on an array, and the value set of an enum against an enum, otherwise have to match.

`format` is the one attribute that does not fail on absence. Only the annotation formats `bcp47` and `iso3166` survive registration as `format`, and neither is checked against field values, so a plain `string` and an annotated one admit the same values. Omitting the target's annotation is accepted; declaring a different one is rejected.

The check reaches field declarations only. Two `object` fields, or two arrays of them, compare as compatible whatever they contain, because a field declaration has no vocabulary for nested shape. A claim involving a structured `object` field carries no machine-checked guarantee about what is inside it.

The platform verifies every claim at registration. A claim that does not hold is rejected with `422 compatible_with_violation` naming the field, what was expected, what arrived, and the concrete next step. The same check runs at build time over the types Marfa itself ships.

`compatible_with` is server-checked, not a free-text tag, which is what makes it worth relying on. Declare it only when the claim holds — a false claim is worse than none, because it invites a reader to parse fields that aren't there.

#### Reading the declaration

The declaration rides the type resource itself: every read of a type — the list, the single-type lookup, and the schema returned on registration — carries `compatible_with`, and the field is part of the published API specification, so generated clients see it without special handling. A client that renders items generically resolves the relationship at runtime: fetch the type, read `compatible_with`, and treat the item as the target when its own type is unknown.

Compatibility is a read-as promise, not query membership. A query for the target type returns the target and its descendants only; items of a compatible sibling appear under their own type identifier, and a reader that wants them has to ask for them by name. Discoverability through the target's queries is what [inheritance](#inheritance) provides.

### Inheritance

Single-parent. Additive. A child adds fields, and may re-state an inherited field only to sharpen its `description` or tighten it to required. Changing an inherited field's type, format, element type, enum values, search flag or size caps — or loosening one the ancestor requires — is rejected with `400 inheritance_violation`.

The line sits there because a reshaped field leaves two incompatible readings of one property name on items a parent-typed reader expects to understand, while a sharper description resolves unambiguously in the child's favor.

```
core.bookmark         (parent)
└── nadia.reader_document   (child — inherits everything, adds new fields)
```

Reads inherit down: `GET /items?type=core.bookmark` returns both parents and children. Writes require the exact type — a credential with `write core.bookmark` cannot update a `nadia.reader_document` without that scope.

## Identifiers

Type identifiers use dots only. No forward slashes. Segments are lowercase and start with a letter; the validator also accepts digits, underscores, and hyphens after that, with a 128-character ceiling on the whole identifier.

The slash is not merely unused here, it is spoken for: **dots name data, and the slash names an installable**. An integration is identified as `<namespace>/<name>` — `readwise/reader` — so nothing that names a type can be mistaken for something you install, and nothing you install can be mistaken for a type. See [Naming an integration](/guides/connections/integrations#naming-an-integration).

Within what the validator accepts, snake_case is the convention for multi-word components: `demo.web_gallery`, not `demo/web-gallery` or `demo.WebGallery`. Edge type names are the deliberate exception and use kebab-case (`parent-of`, `in-thread`), so a reader can tell an edge name from a type identifier at a glance.
