---
title: Export and restore an archive
description: Export your items, edges, types and files to an archive, and restore it into the same instance or another, such as a new build.
---

An archive carries your content to another instance: items with their tags, extensions and earlier versions, edges, the types and edge types you registered, and file bytes. It leaves the instance's own setup behind, so it holds no keys, webhooks, configuration or audit log. It can move your data to a new build when you [upgrade](/guides/upgrade), but **test the restore on fresh storage first**: a different build may refuse the archive.

An archive isn't a long-term backup, because only the build that wrote it is sure to read it. To recover an instance from a failed disk, [back up the data directory](/guides/back-up-and-restore) instead.

## Export an archive

An archive holds what its caller can read. The owner can export everything from a browser, without a key, on the **Export and restore** page at `/auth/owner/export`: choose everything or one type in **What to export**, then select **Export**. That page always leaves out the trash. To export from a script, follow these steps.

<Steps>
<Step>

### Make an export key

On the instance's machine, under the account that runs the server, make a key that reads every type, edge type and extension:

```bash
marfa --socket /srv/marfa/data/control/marfa.sock keys create --label backup --source backup \
  --type-permission '*=read' --edge-permission '*=read' --extension-permission '*=read' \
  --permission blobs.manage
```

The CLI shows the key once. Set it as `MARFA_API_KEY` wherever you export from. Without `blobs.manage`, the archive leaves out the bytes of files that only an earlier version of an item names, lists them under `missing_blobs` and makes `marfa export` exit with code 1 ([below](#when-an-archive-lacks-a-files-bytes)).

</Step>
<Step>

### Export

`state=any` includes the trash, which an export leaves out otherwise:

```bash tab="CLI" tab-group="client"
marfa export --format archive --state any --output marfa-archive.tar.gz
```

```http tab="HTTP"
GET /export?format=archive&state=any
Authorization: Bearer <key>
```

The CLI writes to a hidden file beside the path and renames it over the path only when the export ended whole and lacks no files, so the file at the path is always the last whole archive the command wrote. Any other ending leaves the path as it was and exits with a nonzero [exit code](/cli#exit-codes).

</Step>
<Step>

### Check the file

An archive holds four files, plus one file for each blob it carries:

<Terminal>

```bash
tar -tzf marfa-archive.tar.gz
```

```text
manifest.json
items.ndjson
edges.ndjson
types.ndjson
blobs/sha256:f1062b81e1771fa1b881c035d40485418ecb4c74fa1b427c1155506a26382c46
```

</Terminal>

An export that was cut short doesn't unpack.

</Step>
</Steps>

## Leave out the files

An archive without file bytes is much smaller. Add `files=false` to the request, or turn off **Include files** on the **Export and restore** page. The CLI has no option for it.

```http
GET /export?format=archive&files=false
Authorization: Bearer <key>
```

The manifest then names every file under `missing_blobs`, and a restore reports in `blobs_missing` each one the target doesn't hold.

## When an archive lacks a file's bytes

An export leaves out a blob its items name in two cases: no store holds a whole copy of it, as after a disk lost the file, or the key that exports may not read it. A key without `blobs.manage` may not read the bytes of a file that only an earlier version of an item names.

Either way, the export names the blob under `missing_blobs` in the manifest. One missing file costs the archive that file, not everything else. Over HTTP the answer is still `200`. The CLI keeps the archive as `<path>.incomplete`, leaves the file at the path as it was, and exits with code 1 and `blobs_missing`.

The manifest's blob fields show what the archive lacks:

<Terminal>

```bash
tar -xzOf marfa-archive.tar.gz.incomplete manifest.json | jq '{blob_count, blobs, missing_blobs}'
```

```json
{
  "blob_count": 0,
  "blobs": {},
  "missing_blobs": {
    "sha256:f1062b81e1771fa1b881c035d40485418ecb4c74fa1b427c1155506a26382c46": {
      "mime_type": "image/png",
      "size_bytes": 73
    }
  }
}
```

</Terminal>

`mime_type` and `size_bytes` are `null` when the instance has no record of the bytes, as after a restore that lacked them, and for every blob the key may not read, because the archive says no more about such a blob than the blob operations do. An empty `missing_blobs` means the archive holds every blob its items name.

**A blob the key may not read needs no upload.** Export again with a key that holds `blobs.manage`, or as the owner in a browser, and the archive carries the bytes. **A blob that no store holds stays named in every later export** until you upload its bytes again:

```bash
marfa blobs upload <file>
```

A store that fails is not a lost file. Unless another store holds the blob whole, the export is refused with `503 blob_store_unavailable` before it begins, so try again once the store answers.

## What an export checks

- **It isn't taken at one instant.** An item created while it runs may not be in it, so stop your apps first if the archive must hold every write.
- **It ends when its credential does.** If the key or app that started it is revoked, expires, is disconnected or loses access to what is left to send, the response ends with an error and the file doesn't unpack. Export again.
- **It's checked against a restore.** Before it sends a byte, Marfa checks that the archive restores into an empty instance of the same build, and reads the selection again if a row fails. A row that fails twice refuses the export with `409 export_rows_unrestorable` and is named in `details.row`: correct the row or its type, then export again. If writes changed the row between the reads, the answer is `503 export_unrestorable`: export again once the writes stop.
- **It needs room.** The server builds the archive in the blob folder first, so leave that disk room for about the archive's uncompressed text. An export that would take the disk below `MARFA_DISK_RESERVE_BYTES` is refused `507 insufficient_storage`.
- **A source filter hides items.** A [source filter](/guides/settings#what-the-enforcement-levers-do) on the instance or the key leaves items out of an export, the owner's too.

[Export items and edges](/api-reference/export-and-restore/exportData) lists every answer.

## Restore an archive

A restore adds what the instance lacks and replaces nothing. An item the instance already holds is counted in `duplicates` and left as it is, so replaying an archive never overwrites work done since. The target can be a new instance or the one the archive came from.

Only the owner can restore: through the private socket, with `MARFA_API_URL` and `MARFA_API_KEY` unset in that shell, or signed in to the instance within the five minutes before the restore starts. A key is refused `403 forbidden`, whatever it holds. In a browser, on the **Export and restore** page, select **Choose file...**, choose the archive, then select **Restore**. An older sign-in is asked to confirm in a **Confirm it's you** dialog first.

The answer counts what the restore did. Through the socket, into a fresh instance:

<Terminal>

```bash
marfa --socket /srv/marfa/data/control/marfa.sock restore marfa-archive.tar.gz
```

```json
{
  "imported": 6,
  "duplicates": 0,
  "edges_imported": 1,
  "edges_skipped": 0,
  "edges_skipped_reasons": {},
  "blobs_imported": 1,
  "blobs_missing": [],
  "types_registered": 0,
  "types_skipped": 0,
  "edge_types_registered": 0,
  "edge_types_skipped": 0
}
```

</Terminal>

The same archive restored again answers `"imported": 0`, `"duplicates": 6` and `"edges_skipped_reasons": { "already_present": 1 }`. Check two fields:

- **`blobs_missing`** lists the blobs the archive names but carries no bytes for, and no store of the instance holds. The restore still writes the items but no record for those blobs, so their files have no bytes until you [upload them again](#when-an-archive-lacks-a-files-bytes). The CLI then exits with code 1 and `blobs_missing`.
- **`edges_skipped_reasons`** counts why edges were skipped, such as `already_present` or `endpoint_missing`. An edge to an item in the trash is restored.

A restore writes in one transaction. If it's refused, fails or is interrupted, it leaves nothing behind, so you can run it again. Other writes wait while it runs, so let it answer before you start your apps.

A restore refuses the whole archive when the file isn't a valid archive, lacks one of its four files, names another format version, or conflicts with what the instance registers. [Restore from an archive](/api-reference/export-and-restore/restoreArchive) lists each refusal. If a newer build refuses your archive, [keep running the old build](/guides/upgrade#if-the-new-build-refuses-the-archive).

## What a restore leaves for you

- **Keys, webhooks and configuration.** Make keys, register webhooks and set the configuration again.
- **Connected apps.** A restored `system.connection` item has `status: revoked`: it records past access rather than reconnecting the app, so sign the app in again. An item an app wrote gets `restored:` in front of its source, so a later sign-in can't overwrite it.
- **Rows as archived.** A restore takes an item exactly as archived, even when its type is no longer registered or has changed its fields. An item of a `core` or `system` type that the build ships is still held to its shape.

The rules behind this page are in the [export](https://github.com/withmarfa/marfa/blob/main/conformance/spec/search-and-filters.md#export) and [restore](https://github.com/withmarfa/marfa/blob/main/conformance/spec/search-and-filters.md#restore) sections of the search and filters chapter of the contract, with [`search-and-filters/archive-missing-unreadable`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/search-and-filters.md#search-and-filtersarchive-missing-unreadable) for a blob the key may not read.
