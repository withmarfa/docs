title: Audit log
description: Find out who changed what on an instance, and when, by reading and filtering its audit log.
---

The log shows which key created an item, who made a key, when the configuration changed, and who exported your data. Marfa writes every entry itself, and nothing can write one for it.

## What the log records

Marfa records **writes, sign-ins and exports, and never reads**. That covers:

- Writes to items, edges, tags, extensions, types and blobs.
- Making, changing and revoking keys.
- App consents and tokens, and the owner's password sign-ins, failed ones included.
- Configuration changes, webhooks and connector registrations.
- Every export and restore.

The list isn't closed, so read the log to see the actions your instance records.

Some writes leave no entry: a refused write, a dry run of a bulk action, a request to run a housekeeping job, and the routine traffic of connectors (heartbeats, holds and state writes).

Three rules make the log dependable:

- **A write that answers success is already in the log**, and if Marfa can't record the entry, it rolls the write back.
- **An export is recorded before its file starts**, so an export that fails partway still has its entry.
- **An entry never holds a secret**: no key, password, authorization code or cookie.

Each entry holds these fields:

| Field | Type | Description |
| --- | --- | --- |
| `id` | `string` | The entry's identifier. |
| `created_at` | `string` | When Marfa recorded the entry, in UTC. |
| `actor` | `object \| null` | The recorded sign-in kind, ID and readable name; Marfa for server work, or null when the actor is unknown. |
| `key_id` | `string \| null` | The acting credential's ID, or null when no credential is recorded. |
| `action` | `string` | What happened, such as `item.create` or `export.run`. |
| `resource_type` | `string` | The kind of thing acted on, such as `item`, `key` or `config`. |
| `resource_id` | `string \| null` | The ID of the thing acted on, or null where there is none. |
| `client_ip` | `string \| null` | The address the request came from, or null where there is none. |
| `details` | `object` | More about the action, depending on action. |

**Use `actor` to identify who acted.** For authenticated actions, its `kind`, `id` and `name` are captured at the time, so a later rename or removal does not change the entry. Server work has actor `{ "kind": "server", "id": "server", "name": "Marfa" }`. Older entries without a captured actor, and actions before authentication, have `actor: null`; do not infer a person from their `key_id`. Behind a proxy or a tunnel, `client_ip` is the proxy's address unless the server is told which address to believe, as [Deploy](/guides/deploy#the-address) explains.

## Read the log

**Reading the log needs the `audit.read` permission**, which opens the log and no item. The owner needs no key, through the private socket or signed in.

Entries come newest first. This lists the latest item creation:

<Terminal>

```bash
marfa audit --action item.create --limit 1 --json
```

```json
{
  "data": [
    {
      "id": "01a16970-ceb8-7dc2-9619-9b8d17b41c1b",

        "type": "core.task"

  ],
```

Over HTTP, send `GET /audit?action=item.create&limit=1` with `Authorization: Bearer <key>`. Without `--json`, the CLI prints one line for each entry: its ID, action and time.

The owner can also read the log **in a browser**. The **Activity** page, at `/auth/owner/activity`, lists the entries newest first and filters them by kind, time and text.

## Filter it

Seven filters narrow the log, and you can combine them:

- `action` keeps the entries with this action.
- `resource_type` keeps the entries about this kind of thing.
- `resource_id` keeps the entries about the thing with this ID.
- `created_after` and `created_before` keep the entries recorded between two times, not counting an entry at either time itself.
- `kind` keeps the entries of one kind, listed below. Any other value is refused `400 validation_error`.
- `q` keeps the entries that match the words of its text. [List audit log entries](/api-reference/instance/listAuditLog) says how it matches.

Each entry is of exactly one `kind`:

| `kind` | What it holds |
| --- | --- |
| `access` | Sign-ins, keys, folders and the owner's profile. |
| `data` | Items, edges, types, files and restores. |
| `settings` | The configuration, webhooks and connectors. |
| `housekeeping` | What Marfa does on its own. |

To see what happened to one item, filter by its ID:

<Terminal>

```bash
marfa audit --resource-type item --resource-id 01a16970-ceb9-7a31-a880-857c997d17b5
```

```text
01a16970-d8e8-737d-ad96-c22f54612c26  item.purge   2026-10-23T15:46:05.674Z
01a16970-d8dd-7b06-867f-2e4b79d1e81a  item.delete  2026-10-23T15:46:05.662Z
01a16970-ceb8-7dc2-9619-9b8d17b41c1b  item.create  2026-10-23T15:46:03.066Z
```

</Terminal>

The HTTP request is `GET /audit?resource_type=item&resource_id=<id>`.

`marfa audit` takes all seven filters. Use `--kind` for `kind` and `--query` for `q`. [The audit kinds](https://github.com/withmarfa/marfa/blob/main/conformance/spec/events.md#eventsaudit-kind) and [the search](https://github.com/withmarfa/marfa/blob/main/conformance/spec/events.md#eventsaudit-search) hold the rules.

**There is no filter for `key_id`**, so to see what one key did, read the entries and compare their `key_id`. Use `actor` for the readable identity where it was recorded.

A page holds 50 entries unless `limit` asks for up to 200. When more match, the answer carries a `next_cursor`: send it back as `cursor` (or `--cursor`) for the next page, and stop when it's `null`. **Marfa refuses a query key it doesn't know** with `400 validation_error`, so a misspelled filter never reads as one that matched everything.

## How long entries are kept

Marfa keeps entries for **90 days** by default. The `audit-cleanup` [housekeeping job](/guides/housekeeping) runs once a day and deletes older ones, along with the history of outbound webhook deliveries past the same age.

`AUDIT_RETENTION_DAYS` sets the retention when the server starts, and `audit_retention_days` in the [configuration](/guides/settings#change-settings-while-it-runs) changes it while the server runs. At `0`, no entry expires.

The rules behind this page are in [the audit log](https://github.com/withmarfa/marfa/blob/main/conformance/spec/events.md#the-audit-log) section of the events chapter of the contract, including the [kinds](https://github.com/withmarfa/marfa/blob/main/conformance/spec/events.md#eventsaudit-kind) and the [text search](https://github.com/withmarfa/marfa/blob/main/conformance/spec/events.md#eventsaudit-search).
