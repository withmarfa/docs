title: Audit log
description: Find out who changed what on an instance, and when, by reading and filtering its audit log.
---

The audit log answers who changed what on your instance, and when: which key created an item, who made a key, when the configuration changed, and who exported your data. Marfa writes every entry itself, and nothing can write one for it.

## What the log records

**Marfa records writes, sign-ins and exports, and never reads.** That covers writes to items, edges, tags, extensions, types and blobs; making, changing and revoking keys; app consents and tokens, and the owner's password sign-ins, failed ones included; configuration changes, webhooks and connector registrations; and every export and restore. The list isn't closed, so read the log to see the actions your instance records.

Some writes leave no entry: a write that Marfa refuses, a dry run of a bulk action, a request to run a housekeeping job, and the routine traffic of connectors, such as their heartbeats, holds and state writes.

Three rules make the log dependable:

- **A write that answers success is already in the log**, and if Marfa can't record the entry, it rolls the write back.
- **An export is recorded before its file starts**, so an export that fails partway still has its entry.
- **An entry never holds a secret**: no key, password, authorization code or cookie.

Each entry holds these fields:

| Field | Type | Description |
| --- | --- | --- |
| `id` | `string` | The entry's identifier. |
| `created_at` | `string` | When Marfa recorded the entry, in UTC. |
| `key_id` | `string \| null` | Who acted: the ID of a key or an app's token, or null for a write of Marfa's own, such as a housekeeping job. |
| `action` | `string` | What happened, such as `item.create` or `export.run`. |
| `resource_type` | `string` | The kind of thing acted on, such as `item`, `key` or `config`. |
| `resource_id` | `string \| null` | The ID of the thing acted on, or null where there is none. |
| `client_ip` | `string \| null` | The address the request came from, or null where there is none. |
| `details` | `object` | More about the action, depending on action. |

When the owner acts, `key_id` names the owner's authority rather than a key: `local:process` through the private socket, or `owner:` and the browser session when signed in. Behind a proxy or a tunnel, `client_ip` is the proxy's address unless the server is told which address to believe, as [Deploy](/guides/deploy#the-address) explains.

## Read the log

**Reading the log needs the `audit.read` permission**, which opens the log and no item. The owner needs no key, through the private socket or signed in.

Entries come newest first. This lists the most recent exports since the start of October:

```bash tab="CLI" tab-group="client"
marfa audit --action export.run --created-after 2026-10-01T00:00:00Z --limit 20 --json
```

```http tab="HTTP"
GET /audit?action=export.run&created_after=2026-10-01T00:00:00Z&limit=20
Authorization: Bearer <key>
```

```json
{
  "data": [
    {
      "id": "01a12312-fb3b-7053-b8d7-cbe616d22d71",
      "created_at": "2026-10-09T23:50:08.955Z",
      "key_id": "01a12312-ef3c-7fc2-977f-3d4b0b77407d",
      "action": "export.run",
      "resource_type": "export",
      "resource_id": null,
      "client_ip": "::1",
      "details": { "format": "archive" }
    }
  ],
  "next_cursor": null
}
```

Without `--json`, the CLI prints one line for each entry: its ID, action and time.

## Filter it

Five filters narrow the log, and you can combine them:

- `action` keeps the entries with this action.
- `resource_type` keeps the entries about this kind of thing.
- `resource_id` keeps the entries about the thing with this ID.
- `created_after` and `created_before` keep the entries recorded between two times, not counting an entry at either time itself.

To see what happened to one item, filter by its ID:

```bash tab="CLI" tab-group="client"
marfa audit --resource-type item --resource-id 01a12312-d8f1-7766-8f94-278746e3ca32
```

```http tab="HTTP"
GET /audit?resource_type=item&resource_id=01a12312-d8f1-7766-8f94-278746e3ca32
Authorization: Bearer <key>
```

```text
01a12312-d918-7987-9bb3-ec6d81e74a38  item.update  2026-10-09T23:50:00.218Z
01a12312-d8f0-7301-94a8-558a479db26c  item.create  2026-10-09T23:50:00.178Z
```

**There is no filter for `key_id`**, so to see what one key did, read the entries and compare their `key_id`.

A page holds 50 entries unless `limit` asks for up to 200. When more match, the answer carries a `next_cursor`: send it back as `cursor` (or `--cursor`) for the next page, and stop when it's `null`. **Marfa refuses a query key it doesn't know** with `400 validation_error`, so a misspelled filter never reads as one that matched everything.

## How long entries are kept

**Marfa keeps entries for 90 days by default.** The `audit-cleanup` [housekeeping job](/guides/housekeeping) runs once a day and deletes older ones, along with the history of outbound webhook deliveries past the same age.

`AUDIT_RETENTION_DAYS` sets the retention when the server starts, and `audit_retention_days` in the [configuration](/guides/settings#change-settings-while-it-runs) changes it while the server runs. At `0`, no entry expires.

The rules behind this page are in [the audit log](https://github.com/withmarfa/marfa/blob/main/conformance/spec/events.md#the-audit-log) section of the events chapter of the contract.
