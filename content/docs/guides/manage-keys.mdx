---
title: Manage keys
description: Give each app or script a key that reaches only what it needs, make it expire, narrow or revoke it, and recover the owner's password.
---

A script or service you run yourself uses a key, which reaches only what it was made with. An app can instead sign in with OAuth, as [Authenticate](/guides/authenticate) shows. A notes app needs notes and nothing else; a script that runs for a week needs a key that stops working after a week. [Access](/access) explains the maps and permissions a key holds.

Two kinds of caller can make keys: the owner, through the instance's private socket or signed in to the instance's Manage Marfa pages in a browser, and a key or an app's token that holds the `keys.mint` permission. The CLI examples use the socket, so run them on the instance's machine, under the account that runs the server.

## Make a key for an app or a script

Name the key's label, its source, and what it reaches. This key, for a notes app, reads and writes notes and nothing else:

```bash tab="CLI" tab-group="client"
marfa --socket /srv/marfa/data/control/marfa.sock keys create \
  --label "Notes app" --source notes-app --type-permission core.note=write
```

```http tab="HTTP"
POST /keys
Authorization: Bearer <a key holding keys.mint>
Content-Type: application/json

{
  "label": "Notes app",
  "source": "notes-app",
  "type_permissions": { "core.note": "write" }
}
```

Marfa answers the key's plaintext, which begins `marfa_k1_`, once. No later answer shows it, so **copy it to the app now**.

```text
marfa_k1_614e182634b2e78eb69e0a3cda8806b739be5a4917c5765a5420dfe766c63947
key 01a12311-8b01-7c3c-879e-3ff7346ce72f (Notes app); the plaintext is shown once, keep it now
```

The source, here `notes-app`, is stamped on every item the key creates, so you can always tell which app wrote what. **Each key in use has a source of its own**, and a source another key already has is refused `409 conflict`. With this key, creating a note works, and creating a bookmark is refused `403 type_not_permitted`.

Each map and permission has a flag of its own: `--edge-permission`, `--extension-permission`, `--metadata-permission`, `--profile-permission` and `--permission`, each repeatable. `--claim` is explained below. [Create an API key](/api-reference/access/createKey) has every field.

## Let keys share a source

A key writes under its own source and the sources it **claims**. Keys that stand for one thing, such as a laptop and a phone, can claim one source and update each other's items. Name the claims when you make the key:

```bash tab="CLI" tab-group="client"
marfa --socket /srv/marfa/data/control/marfa.sock keys create \
  --label "Laptop" --source laptop --claim notes-sync --type-permission core.note=write
```

```http tab="HTTP"
POST /keys
Authorization: Bearer <a key holding keys.mint>
Content-Type: application/json

{
  "label": "Laptop",
  "source": "laptop",
  "sources": ["notes-sync"],
  "type_permissions": { "core.note": "write" }
}
```

**A write names its source in the item's `source` field**, `--source` in `marfa items create`. Leave it out and the item takes the key's own source. Another source is refused `403 forbidden`, naming it in `details.source`. Many keys can claim a source, but a key's own source stays its alone.

The owner can grant any source except one beginning with `oauth:` or `restored:`; a key holding `keys.mint` only its own and the ones it claims. Naming claims names what the key holds, so `--claim` alone leaves no permission and no map. `marfa keys update --claim` replaces the claims and `--no-claims` removes them; items already under a lost claim stay editable.

## What a key holds

What a new key holds depends on what the request names.

If the request names no permission, map or [claimed source](#let-keys-share-a-source), **the key takes everything its maker could give**. A key the owner makes this way holds every [permission](/catalog/permissions) and wildcard `write` in all five maps, which suits your own laptop and nothing else. **Profile write changes only name and avatar; email stays read-only.** A key made this way by another key inherits only that key's effective access.

If the request names any of them, the key holds exactly what it names in each part it names, and **nothing in each part it leaves out**. The notes app's key above named one map, so it holds that map and no permission at all. A key made with only `--permission audit.read` reads the audit log and no item.

**A key can hand on only what it holds.** A key asking for a permission or map entry it lacks is refused `403 forbidden`, with the first one it lacks in `details.required_scope`.

## Make a key expire

A key can stop working at a set time. Give it a duration from now, or a time:

```bash tab="CLI" tab-group="client"
marfa --socket /srv/marfa/data/control/marfa.sock keys create \
  --label "Import script" --source import --type-permission core.note=write --expires-in 7d
```

```http tab="HTTP"
POST /keys
Authorization: Bearer <a key holding keys.mint>
Content-Type: application/json

{
  "label": "Import script",
  "source": "import",
  "type_permissions": { "core.note": "write" },
  "expires_at": "2026-10-17T12:00:00Z"
}
```

`--expires-in` takes a whole number and a unit, `s`, `m`, `h`, `d` or `w`, measured on your machine's clock. `--expires-at` takes a time such as `2026-10-17T12:00:00Z`.

**Once the time passes, the key is gone.** Every request with it is refused `401 unauthorized`, it leaves the key list, and changing or revoking it answers `404 api_key_not_found`. Its source is free for a new key.

**A key that expires passes its expiry on.** A key it makes expires when it does, unless the request names an earlier time, and asking for a later expiry, or none, is refused:

```text
marfa: the server refused (403 forbidden): This credential expires at 2026-10-09T23:49:43.000Z, so it cannot give a key a later expiry or none. {"expires_at":"2026-10-09T23:49:43.000Z"}
```

A key that expires can't lengthen any key's life, its own included, and a key holding `keys.manage` can only bring an expiry forward. The owner can clear an expiry, and so can a key holding `keys.mint` with no expiry of its own, for a key within its reach, with `marfa keys update <id> --no-expiry`, or `"expires_at": null` in an update.

## Read what a key holds

**Any key can read itself**, so a program can check it holds what it should and no more:

```bash tab="CLI" tab-group="client"
marfa keys current
```

```http tab="HTTP"
GET /keys/current
Authorization: Bearer <key>
```

```json
{
  "id": "01a12311-8b01-7c3c-879e-3ff7346ce72f",
  "label": "Notes app",
  "source": "notes-app",
  "sources": [],
  "permissions": [],
  "type_permissions": { "core.note": "write" },
  "extension_permissions": {},
  "edge_permissions": {},
  "metadata_permissions": {},
  "profile_permissions": {},
  "expires_at": null
}
```

The answer has more fields than this. To find another key's ID, `marfa keys list` lists the keys you can reach: every key for the owner or a key holding `keys.manage`, and the keys within its own reach for a key holding `keys.mint`.

## Narrow a key

Change a key in place by its ID. A map or the permissions you name replace what the key held in that part, and **the parts you leave out stay as they were**. This makes the notes app's key read-only, and has it expire in 30 days:

```bash tab="CLI" tab-group="client"
marfa --socket /srv/marfa/data/control/marfa.sock keys update 01a12311-8b01-7c3c-879e-3ff7346ce72f \
  --type-permission core.note=read --expires-in 30d
```

```http tab="HTTP"
PATCH /keys/01a12311-8b01-7c3c-879e-3ff7346ce72f
Authorization: Bearer <a key holding keys.mint>
Content-Type: application/json

{
  "type_permissions": { "core.note": "read" },
  "expires_at": "2026-11-08T12:00:00Z"
}
```

`--no-type-permissions` and its siblings empty one map, and `--no-permissions` empties everything, so a key made too wide is narrowed without changing the app that holds it. **A key's source never changes.** Sources and claimed sources beginning with `oauth:` or `restored:` are reserved and refused, so choose a source outside those prefixes.

A key holding `keys.mint` changes only the keys that hold nothing it doesn't. A key holding `keys.manage` reaches every key, but can only take access away.

## Revoke a key

**Revoking ends a key at once**: the next request it sends is refused `401 unauthorized`.

```bash tab="CLI" tab-group="client"
marfa --socket /srv/marfa/data/control/marfa.sock keys revoke 01a12311-8b01-7c3c-879e-3ff7346ce72f
```

```http tab="HTTP"
DELETE /keys/01a12311-8b01-7c3c-879e-3ff7346ce72f
Authorization: Bearer <a key holding keys.mint>
```

**Revoking a key from a browser needs a sign-in within the last five minutes.** A browser that signed in earlier is refused `403 forbidden` and leaves the key working. The private socket and a key that holds `keys.mint` or `keys.manage` are not affected by when the owner last signed in.

Revoke a key you think has leaked, then make a new one for the app.

## Recover the owner's password

If you lose the owner's password, set a new one through the private socket, on the instance's machine:

```bash
marfa --socket /srv/marfa/data/control/marfa.sock owner recover
```

The CLI asks for the new password without showing it; for a script, `--stdin` reads `{"password": "…"}` instead. **Recovery signs out every browser.** Keys and the apps you signed in keep working, and the owner keeps the same email.

Recovery also lifts a password lock: **ten password attempts from one address in 15 minutes** answer `429` with `Retry-After`, and a passkey still works. Behind a proxy every client shares one address unless `TRUSTED_PROXY_CIDRS` or `TRUSTED_PROXY_HEADER` is set, as [Deploy](/guides/deploy#the-address) explains.

In the container, run the command inside it, with `docker exec -it marfa marfa --socket /data/control/marfa.sock owner recover`.

The socket answers only while the server runs. If the server can't start in full, such as when its port is taken, **start it with `MARFA_CONTROL_ONLY=true`**: it then opens the socket alone, with no public port, for as long as you need to recover.

The rules behind this page are in the [keys and sign-in](https://github.com/withmarfa/marfa/blob/main/conformance/spec/keys-and-oauth.md) and [instance claim](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance-claim.md#direct-ownership-and-recovery) chapters of the contract.
