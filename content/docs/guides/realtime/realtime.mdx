Marfa emits live events on a per-space Server-Sent Events stream. Clients that need to reflect changes in real time subscribe to `GET /events`.

## Connecting

```http
GET /events HTTP/1.1
Host: marfa.example.com
Authorization: Bearer <token>
Accept: text/event-stream
```

The connection stays open. The server streams events as they occur, each on its own SSE record:

```
id: 4521
event: item.created
data: {"type":"item.created","item":{"id":"019d...","type":"core.note","properties":{ ... }}}

id: 4522
event: edge.created
data: {"type":"edge.created","edge":{"id":"...","edge_type":"about","source_id":"...","target_id":"..."}}

: ping
```

Each `data` payload is a JSON envelope: `{ type, item }` for item events (the full item under `item`, plus `metadata` when metadata changed) and `{ type, edge }` for edge events. The `id` is an integer — persist the **most recent one you received** and send it back as `Last-Event-ID` to resume after a drop. It is not strictly increasing: an event whose transaction commits after a reconnect's replay has already passed its id is delivered when it arrives, so a lower id can follow a higher one on the same connection. Store the last id you received rather than the highest you have seen — storing the highest would skip the event that arrived late — and apply each payload by item id, which is idempotent either way.

Comments (lines starting with `:`) are heartbeats. The server sends one every ~30 seconds. Treat an idle stream longer than 60s as disconnected and reconnect.

## Event types

Item events are filtered by the subscriber's permissions: the server won't stream an event for an item whose type the credential can't read, and every payload carrying a metadata row — `metadata.changed`, and `item.created`, `item.updated`, `item.restored` and `item.state_changed` alike — carries only the extension namespaces the credential's `extension_permissions` admit — the same narrowing a REST read of that metadata applies, on the live stream and on a `Last-Event-ID` replay alike. Admin and space-admin API keys bypass it, as they bypass the same map on a read. An OAuth access token does not, whatever role it projects: it is minted with no extension permissions at all, so it receives no namespace on the stream, exactly as it would read none over REST.

Edge events reach every authenticated subscriber in the space, as edge reads do. `GET /edges` and the per-item edge listings gate on authentication and space rather than on `edge_permissions`, which govern writes, so the stream is exactly as wide as a read of the same edges. Do not rely on `edge_permissions` to keep an edge off a subscriber; it does not narrow reads and does not narrow the stream.

    Edge events come from every route that writes an edge, not only from `/edges`. An item created with an inline `edges` payload, an item updated with one, a promotion's link back to its mirror, a purge cascading the edges on both sides of the item, an archive restore, and a connection uninstall all publish. A subscriber cannot tell which route wrote an edge, so none of them is quieter than the others. The bulk doors (`POST /items/bulk`, `POST /edges/bulk` and `POST /items/bulk-actions`) are no exception either: every bulk write reaches the stream, and `enable_fanout` governs only whether webhooks and integration reactions fire, never whether the event happens.

    **A delete and a purge are not the same news.** `item.deleted` says the row was trashed and can come back, so a store that keeps trash keeps it. `item.purged` says the row is gone for good, and nothing later will correct a copy of it, because the row is absent rather than changed. Both carry the item as it last stood, since there is nothing left to read once a purge has been published. Match on the type rather than on the state the payload carries: an ordinary item is purged out of `trashed`, but a `system.*` row soft-deletes to `revoked`, so reading the state would keep every purged one forever.

    **Every door that removes a row announces it.** `DELETE /items/{id}/purge`, the `purge` action on `POST /items/bulk-actions`, and the credential teardown that a connection uninstall runs all publish `item.purged`, and each announces the `edge.deleted` events its cascade produced first, then the row they hung off. That ordering mirrors a create in reverse, where an edge arrives behind the item it belongs to.

    **The sweeps are the exception, and deliberately so.** Trash retention, the activity sweep and the revoked-grant sweep remove rows on a cutoff measured in days, against an event log kept for hours, so a row they remove fell out of the replay window long before it was touched and no cursor survives that could carry the event. Deleting an account or a space is silent for the same reason plus one of its own: the credentials that would have read the stream go with it. Those removals are the prune's business instead. A cursor too old to resume is answered with `catchup_too_old`, and the re-import behind it drops whatever the server no longer returns. An absence a sweep leaves is a decision; an absence a purge leaves would be a defect.

## Filtering

Clients can narrow the stream to a single item type:

```
GET /events?type=core.note
```

The filter applies on the server, and it covers the type's subtypes as well, so unwanted events never leave the stream.

<Callout type="warn">
  `type` is the only filter the endpoint reads. Unrecognized query parameters
  are ignored rather than rejected, so a request that appears to filter on an
  event name or an edge type opens a stream carrying everything. Filter the rest
  client-side on the `type` field of each payload.
</Callout>

## Reconnecting after a drop

On reconnect, the client sends the `Last-Event-ID` header with the last event id it received:

```http
GET /events HTTP/1.1
Last-Event-ID: 4521
```

The server replays events that occurred after that id from its event log, then transitions to live streaming. This is gapless for events within the log's retention window (default 7 days).

The browser `EventSource` API handles `Last-Event-ID` automatically, but it cannot set an `Authorization` header, so it cannot authenticate against this endpoint on its own. Use the TypeScript SDK's `client.events.subscribe`, which streams the response through `fetch` and keeps the credential in the header, or implement the same shape yourself. Clients that do roll their own should persist the most recent event id and re-send it on reconnect.

<Callout type="info">
  `client.events.subscribe` handles resume, reconnection with backoff, and the
  stale-cursor case below. See [Optimistic updates](/guides/realtime/optimistic-updates).
</Callout>

## When the event log is stale

If `Last-Event-ID` is older than the event log retention window, the server replies with a terminal event indicating the gap. The `data` payload carries the oldest id the log can still replay (`min_retained_id`) and the id the client asked to resume from (`requested`):

```
event: catchup_too_old
data: {"type":"catchup_too_old","min_retained_id":"...","requested":"..."}
```

Clients should recover by falling back to an incremental sweep, then reconnect to live streaming:

```
GET /items?updated_after=<last_applied_updated_at>&state=any&limit=...
GET /edges?updated_after=<last_applied_updated_at>&limit=...
```

Both parameters are load-bearing. `updated_after` reads `updated_at`, so the sweep returns everything written during the gap — including a change that touched only tags or an extension. `state=any` widens the listing past its default, which excludes trashed items: without it a row that reached the bin during the gap is simply absent from the sweep, and a client cannot tell that from a row that never existed.

The sweep is inclusive at the bound, because `updated_at` is a millisecond timestamp and a bulk write ties many rows on one instant. Passing the last value you applied therefore re-delivers the rows sharing it; deduplicate by id. A strict bound would drop them instead, which is the failure this inclusivity exists to avoid.

Deletes are surfaced this way as long as the row is still present as trashed. A row purged during the gap is gone from the sweep as well, and the `item.purged` that named it is out of reach too: this path is only reached once the cursor has aged past the event log, which is the same window that event lived in. So a client reconciling after an outage that long prunes anything it holds that the sweep did not return, rather than relying on an event it can no longer be served. Inside the replay window the event is the mechanism and no prune is needed.

## Catch-up strategy

A typical sync engine follows this pattern:

<Steps>

<Step>

### First connection

Connect to `GET /events` without `Last-Event-ID`. Persist the most recent id received.

</Step>

<Step>

### Live streaming

Apply events as they arrive, and persist `Last-Event-ID` **after** the event has been applied, not when it arrives. Persisting on receipt means a failure between the two loses the event: the cursor has moved past work that never happened, and nothing replays it. Persisting after makes delivery at-least-once, so handlers need to be idempotent — item events already are, since each carries the whole item.

</Step>

<Step>

### Reconnect on disconnect

Send persisted `Last-Event-ID`. Server replays from that point.

</Step>

<Step>

### Handle the stale-cursor signal

When the server emits a terminal `catchup_too_old` event, fall back to the incremental sweep above — `GET /items?updated_after=<last_applied_updated_at>&state=any`, then the same over `GET /edges` — with pagination. Reconnect live after catch-up completes.

</Step>

</Steps>

## Keepalive

The server sends `:ping` comment frames every ~30 seconds. Clients should close the connection and reconnect if no event (including pings) arrives for > 60 seconds — the connection is likely dead even if the TCP socket is open.

## Scale

The event bus is in-process. A subscriber only receives events published by the server process it is connected to, so on a deployment running more than one process against the same database an SSE client misses every write that landed on another process.

Sticky sessions do not solve this. Stickiness pins a client to one process; the gap is which process handled the *write*. Use [webhooks](/guides/realtime/webhooks) instead when a consumer has to see every event regardless of topology — delivery goes through a durable outbox table claimed with `SELECT … FOR UPDATE SKIP LOCKED`, so it is the one event path that is safe across processes. See [Running more than one process](/guides/identity/deployment-modes#running-more-than-one-process) for the full picture.

## SSE vs webhooks

| Use case | Use |
|---|---|
| Live UI that updates as data changes | SSE |
| Long-running server ingesting events | SSE (or webhooks with a local queue) |
| Triggering workflows in external systems | Webhooks |
| Integrating with services that expect HTTP POST | Webhooks |

Both fire on the same event surface — an item creation produces both an SSE event and a webhook delivery. Use whichever matches your consumer.
