Marfa emits live events on a per-space Server-Sent Events stream. Clients that need to reflect changes in real time subscribe to `GET /events`.

## Connecting

```http
GET /events HTTP/1.1
Host: marfa.example.com
Authorization: Bearer <token>
Accept: text/event-stream
```

The connection stays open. The server streams events as they occur, each on its own SSE record:

```
id: 4521
event: item.created
data: {"type":"item.created","item":{"id":"019d...","type":"core.note","properties":{ ... }}}

id: 4522
event: edge.created
data: {"type":"edge.created","edge":{"id":"...","edge_type":"about","source_id":"...","target_id":"..."}}

: ping
```

Each `data` payload is a JSON envelope: `{ type, item }` for item events (the full item under `item`, plus `metadata` when metadata changed) and `{ type, edge }` for edge events. The `id` is an integer — persist the **most recent one you received** and send it back as `Last-Event-ID` to resume after a drop. It is not strictly increasing: an event whose transaction commits after a reconnect's replay has already passed its id is delivered when it arrives, so a lower id can follow a higher one on the same connection. Store the last id you received rather than the highest you have seen — storing the highest would skip the event that arrived late — and apply each payload by item id, which is idempotent either way.

Comments (lines starting with `:`) are heartbeats. The server sends one every ~30 seconds. Treat an idle stream longer than 60s as disconnected and reconnect.

## The stream says where it is

A stream announces the log position it opened at:

```
event: stream_cursor
data: {"type":"stream_cursor","cursor":"4521"}
```

It does not wait for anything to happen, which is the point. A client that subscribes and then reads a snapshot — the order that keeps a write landing between the two from falling in the gap — otherwise holds nothing to resume from until an event happens to arrive. On a quiet space it can finish a full read, be interrupted, and come back with no way to ask what it missed and no way to know that it missed anything. The announcement is what it comes back to: a resume point from the first moment of the connection, instead of from whenever a write happens to land.

**The frame carries no `id:` field, deliberately.** A resuming client is sent it too, before its backlog, and SSE clients treat `id:` as the cursor to resume from next time. One here would move a reconnecting client's cursor to the head of the log before a single replayed event had been applied, discarding exactly the backlog the reconnect existed to fetch. Read the value from `data.cursor` instead, and adopt it only when you have no cursor of your own.

**Adopting it is a starting position, not a promise that nothing precedes it.** The announced value is the highest id visible when the stream opened. On Postgres an id is taken when a row is written and the row becomes visible when its transaction commits, so a write already in flight can commit below a cursor you have just adopted. If that write's live frame went out before you subscribed, it reaches you on neither path: a replay returns only ids above the cursor. Adopt the cursor anyway when you hold nothing, since you have received no event it could put you behind. Once events are arriving, the rule above takes over, and it is the one that matters here too: store the last id you received rather than the highest you have seen. A client that cannot tolerate the remaining gap reconciles on `updated_after` as well, the same sweep the stale-cursor path below describes.

**The frame can also be absent.** Reading the head is bounded, so a stream opened while the database is not answering carries no cursor rather than holding its events back. That leaves the client where it would have been without the frame at all, which is a state it already has to handle. Treat the cursor as the first frame delivered rather than as one that is guaranteed, and never block hydration on its arrival.

**A cursor is a position in the log, not in the filter.** The filters below select a subset of the log rather than reordering it, so a cursor taken under one filter is safe to replay under another: the set of rows changes, the sequence does not. The announced value is the log's head rather than the newest row your filter admits, which is what makes that true. A head computed with your filter applied would sit below rows the log already held, so replaying from it under a wider filter would walk back over them.

## Event types

Item events are filtered by the subscriber's permissions: the server won't stream an event for an item whose type the credential can't read, and every payload carrying a metadata row — `metadata.changed`, and `item.created`, `item.updated`, `item.restored` and `item.state_changed` alike — carries only the extension namespaces the credential's `extension_permissions` admit — the same narrowing a REST read of that metadata applies, on the live stream and on a `Last-Event-ID` replay alike. Admin and space-admin API keys bypass it, as they bypass the same map on a read. An OAuth access token does not, whatever role it projects: it is minted with no extension permissions at all, so it receives no namespace on the stream, exactly as it would read none over REST.

Edge events reach every authenticated subscriber in the space, as edge reads do. `GET /edges` and the per-item edge listings gate on authentication and space rather than on `edge_permissions`, which govern writes, so the stream is exactly as wide as a read of the same edges. Do not rely on `edge_permissions` to keep an edge off a subscriber; it does not narrow reads and does not narrow the stream.

A `type` filter does not narrow them either. An edge carries no item type, so the parameter has nothing to say about one, and a client watching two types needs to hear about the edges joining them — that is the half nothing else can reconstruct, since an edge has no row to re-read and leaves no tombstone when it goes. Use `edges=none` if your subscriber only ever looks at items.

    Edge events come from every route that writes an edge, not only from `/edges`. An item created with an inline `edges` payload, an item updated with one, a promotion's link back to its mirror, a purge cascading the edges on both sides of the item, an archive restore, and a connection uninstall all publish. A promotion announces the copy it minted first and its link back to the mirror second, so the edge's `source_id` names an item the subscriber has already been told about; every door that writes an item and an edge together orders them that way. A subscriber cannot tell which route wrote an edge, so none of them is quieter than the others. The bulk doors (`POST /items/bulk`, `POST /edges/bulk` and `POST /items/bulk-actions`) are no exception either: every bulk write reaches the stream, and `enable_fanout` governs only whether webhooks and integration reactions fire, never whether the event happens.

    **An archive restore announces both halves.** It publishes `item.created` for each item it wrote and `edge.created` for each edge, after its transaction commits and with every item ahead of the edges, so an edge never reaches a subscriber naming an endpoint it has not been told about. The items arrive as creates. `item.restored` is a different event and belongs to `POST /items/{id}/restore`, one item coming back out of the [trash](/guides/core-model/lifecycle).

    **A delete and a purge are not the same news.** `item.deleted` says the row was trashed and can come back, so a store that keeps trash keeps it. `item.purged` says the row is gone for good, and nothing later will correct a copy of it, because the row is absent rather than changed. Both carry the item as it last stood, since there is nothing left to read once a purge has been published. Match on the type rather than on the state the payload carries: an ordinary item is purged out of `trashed`, but a `system.*` row soft-deletes to `revoked`, so reading the state would keep every purged one forever.

    **Every door that removes a row announces it.** `DELETE /items/{id}/purge`, the `purge` action on `POST /items/bulk-actions`, and the credential teardown that a connection uninstall runs all publish `item.purged`, and each announces the `edge.deleted` events its cascade produced first, then the row they hung off. That ordering mirrors a create in reverse, where an edge arrives behind the item it belongs to.

    **The sweeps are the exception, and deliberately so.** Trash retention, the activity sweep and the revoked-grant sweep remove rows on a cutoff measured in days, against an event log kept for hours, so a row they remove fell out of the replay window long before it was touched and no cursor survives that could carry the event. Deleting an account or a space is silent for the same reason plus one of its own: the credentials that would have read the stream go with it. Those removals are the prune's business instead. A cursor too old to resume is answered with `catchup_too_old`, and the re-import behind it drops whatever the server no longer returns. An absence a sweep leaves is a decision; an absence a purge leaves would be a defect.

## Filtering

Two parameters narrow the stream, both applied on the server so unwanted events never leave it.

`type` takes one item type or several, comma-separated, up to ten:

```
GET /events?type=core.note
GET /events?type=core.note,core.media
```

Each entry covers its subtree, resolved exactly as the same parameter on `/items`, `/search` and `/export`. That is two things at once: everything under the name, so `core.media` delivers `core.media.song`, and everything that *declares* `core.media` as its parent, so a type your space registered under a name of its own answers too. The explicit `core.media.*` spelling means the same as the bare one. The rule is the same live and on a `Last-Event-ID` replay.

An entry the parameter cannot honor is refused with `400` rather than accepted and then matched against nothing:

```
GET /events?type=*                 400 — to receive everything, omit the parameter
GET /events?type=core              400 — not a type identifier
GET /events?type=a,b,c,...         400 — more than ten entries
```

The global `*` is refused rather than read as "everything" for the reason it is refused on the listing surfaces: everything is the request with no `type` at all, and a filter matching every type would slip past the per-type levers keyed off this parameter. The refusals matter because the alternative is a `200` carrying an empty stream, which a client cannot tell apart from a space where nothing is happening.

`edges` decides whether edge lifecycle events reach the stream. It is `all` by default, including under a `type` filter for the reason above, and `none` opts out:

```
GET /events?type=core.note&edges=none
```

A value outside `all` and `none` is refused with `400` rather than ignored, because an ignored one would open a stream carrying everything while the caller believed it had opted out.

<Callout type="warn">
  Those are the only two filters the endpoint reads, and only their values are
  checked. An unrecognized parameter *name* is still ignored rather than
  rejected, so a request that appears to filter on an event name opens a stream
  carrying everything. Filter the rest client-side on the `type` field of each
  payload.
</Callout>

## Which space an event reaches

An event is addressed to the space the row it describes belongs to, and your subscription receives the events for yours. An event carrying a different space is one you never see, live or on replay.

For an ordinary credential that is not a distinction worth making: your credential is bound to one space, every row you can read is in it, and every event about those rows arrives. It matters for a **platform admin**, whose credential has no space of its own. A write it makes to another account's rows is announced to *that* account's space, not to the admin's absence of one — so the owner's clients are told, which is the point. An unscoped subscription still receives everything.

This is worth knowing when you are the one writing: an admin tool that purges or retags rows across spaces is not the only thing that has to learn about it, and the owner learning about it is what keeps their open clients honest. A purge in particular leaves nothing behind for a later read to correct — the row is absent rather than changed, so the event is the only notice there will ever be.

## Reconnecting after a drop

On reconnect, the client sends the `Last-Event-ID` header with the last event id it received:

```http
GET /events HTTP/1.1
Last-Event-ID: 4521
```

The server replays events that occurred after that id from its event log, then transitions to live streaming. This is gapless for events within the log's retention window (default 7 days).

The browser `EventSource` API handles `Last-Event-ID` automatically, but it cannot set an `Authorization` header, so it cannot authenticate against this endpoint on its own. Use the TypeScript SDK's `client.events.subscribe`, which streams the response through `fetch` and keeps the credential in the header, or implement the same shape yourself. Clients that do roll their own should persist the most recent event id and re-send it on reconnect.

<Callout type="info">
  `client.events.subscribe` handles resume, reconnection with backoff, and the
  stale-cursor case below. See [Optimistic updates](/guides/realtime/optimistic-updates).
</Callout>

## When the event log is stale

If `Last-Event-ID` is older than the event log retention window, the server replies with a terminal event indicating the gap. The `data` payload carries the oldest id the log can still replay (`min_retained_id`) and the id the client asked to resume from (`requested`):

```
event: catchup_too_old
data: {"type":"catchup_too_old","min_retained_id":"...","requested":"..."}
```

Clients should recover by falling back to an incremental sweep, then reconnect to live streaming:

```
GET /items?updated_after=<last_applied_updated_at>&state=any&limit=...
GET /edges?updated_after=<last_applied_updated_at>&limit=...
```

Both parameters are load-bearing. `updated_after` reads `updated_at`, so the sweep returns everything written during the gap — including a change that touched only tags or an extension. `state=any` widens the listing past its default, which excludes trashed items: without it a row that reached the bin during the gap is simply absent from the sweep, and a client cannot tell that from a row that never existed.

The sweep is inclusive at the bound, because `updated_at` is a millisecond timestamp and a bulk write ties many rows on one instant. Passing the last value you applied therefore re-delivers the rows sharing it; deduplicate by id. A strict bound would drop them instead, which is the failure this inclusivity exists to avoid.

Deletes are surfaced this way as long as the row is still present as trashed. A row purged during the gap is gone from the sweep as well, and the `item.purged` that named it is out of reach too: this path is only reached once the cursor has aged past the event log, which is the same window that event lived in. So a client reconciling after an outage that long prunes anything it holds that the sweep did not return, rather than relying on an event it can no longer be served. Inside the replay window the event is the mechanism and no prune is needed.

## When the stream stops delivering

A stream that cannot deliver what it opened with says so and closes, rather than staying open in a state you cannot observe:

```
event: stream_incomplete
data: {"type":"stream_incomplete","reason":"replay_failed","cursor":"4530"}
```

`reason` says what happened. `replay_failed` is a catch-up that could not finish, `backlog_overflow` a connection that took long enough to open that the events it would have received outgrew what the server holds for it meanwhile, and `live_delivery_failed` and `edge_delivery_failed` a subscription that failed on the server — the last of those being the one that used to leave a connection carrying items and no relationships, looking healthy the whole time.

Only traffic this subscription would actually receive counts toward that buffer: a stream that passed `edges=none` is never charged for edge events, and a credential is never charged for a type it cannot read. So narrowing a subscription can only make `backlog_overflow` less likely, never more.

The TypeScript SDK surfaces this as `onStreamIncomplete` and reconnects on its own; nothing is required of the caller, so the callback is optional and its absence is not escalated to `onError`.

**Recover by reconnecting with the cursor you already hold.** Nothing after the gap is ever sent, so the last `id:` you received is still the last event you hold, and everything past it is still in the log: resuming from it replays exactly what you missed. The frame carries no `id:` of its own for that reason, and `cursor` repeats the position for a client that is not tracking one. A client that reconnects with backoff, which is what `client.events.subscribe` does, therefore recovers on its own.

<Callout type="info">
  This is the opposite of `catchup_too_old` above, which says the log can no
  longer serve your cursor at all and you have to re-read state. Here the
  cursor is good and reconnecting is the whole recovery, so do not re-import
  on a `stream_incomplete`.
</Callout>

A repeating `stream_incomplete` is worth reporting rather than looping on: `replay_failed` can be a transient database failure, and `backlog_overflow` means the events this subscription wants were arriving faster than the connection could open, which more reconnects will not fix on their own — narrowing `type` or setting `edges=none` will, if there is a narrower view you can work from.

## Catch-up strategy

A typical sync engine follows this pattern:

<Steps>

<Step>

### First connection

Connect to `GET /events` without `Last-Event-ID` and persist the `stream_cursor` frame's `cursor`. It arrives before anything else, so the store has somewhere to resume from before the first write, which on a quiet space may be days away or never. Adopt it only on a store that holds no cursor, with the caveat stated above. After that, persist the most recent id received, not the highest.

</Step>

<Step>

### Live streaming

Apply events as they arrive, and persist `Last-Event-ID` **after** the event has been applied, not when it arrives. Persisting on receipt means a failure between the two loses the event: the cursor has moved past work that never happened, and nothing replays it. Persisting after makes delivery at-least-once, so handlers need to be idempotent — item events already are, since each carries the whole item.

</Step>

<Step>

### Reconnect on disconnect

Send persisted `Last-Event-ID`. Server replays from that point.

</Step>

<Step>

### Handle the stale-cursor signal

When the server emits a terminal `catchup_too_old` event, fall back to the incremental sweep above — `GET /items?updated_after=<last_applied_updated_at>&state=any`, then the same over `GET /edges` — with pagination. Reconnect live after catch-up completes.

</Step>

</Steps>

## Keepalive

The server sends `:ping` comment frames every ~30 seconds. Clients should close the connection and reconnect if no event (including pings) arrives for > 60 seconds — the connection is likely dead even if the TCP socket is open.

## Scale

The event bus is in-process. A subscriber only receives events published by the server process it is connected to, so on a deployment running more than one process against the same database an SSE client misses every write that landed on another process.

Sticky sessions do not solve this. Stickiness pins a client to one process; the gap is which process handled the *write*. Use [webhooks](/guides/realtime/webhooks) instead when a consumer has to see every event regardless of topology — delivery goes through a durable outbox table claimed with `SELECT … FOR UPDATE SKIP LOCKED`, so it is the one event path that is safe across processes. See [Running more than one process](/guides/identity/deployment-modes#running-more-than-one-process) for the full picture.

## SSE vs webhooks

| Use case | Use |
|---|---|
| Live UI that updates as data changes | SSE |
| Long-running server ingesting events | SSE (or webhooks with a local queue) |
| Triggering workflows in external systems | Webhooks |
| Integrating with services that expect HTTP POST | Webhooks |

Both fire on the same event surface — an item creation produces both an SSE event and a webhook delivery. Use whichever matches your consumer.
