Relationships between items are **first-class typed edges**, not embedded references. An edge has a source item, a target item, an edge type, and an optional `properties` object. Edges are stored separately from items and queryable from both ends.

## Edge shape

Beyond the source, target, type, and optional `properties` already named, the server stamps each edge with its own `id`, the `space_id`, and `created_at` / `updated_at` timestamps. The full wire shape is in the [API reference](/api-reference).

Edges sit in the same space as their source and target items. Cross-space edges don't exist.

## Querying edges

Edges are queryable from either direction, filtered by type.

```
GET /items/{id}/edges                  # outbound edges (this item as source)
GET /items/{id}/edges?edge_type=about  # filter by type
GET /items/{id}/backrefs               # inbound edges (this item as target)
GET /items/{id}/backrefs?edge_type=in-thread
```

The query language shorthand filters items by edge membership:

```
GET /items?edge[references]=<doc-id>    # items that reference this doc
GET /items?backref[parent-of]=<parent-id>  # items that have this parent
```

### Listing edges by type

For taxonomy-style traversals — "every reply", "every annotation", "every parent-of edge" — list edges globally across the space:

```
GET /edges?edge_type=in-thread         # all in-thread edges
GET /edges?edge_type=parent-of,about   # multiple types (comma-separated, max 10)
```

Cursor + limit pagination, identical to the per-item edge listings. Space-scoped.

This replaces the walk-every-item N+1 pattern that clients otherwise have to write to count or display all edges of a type. SDKs expose it as `client.edges.list({ edge_type })`.

## Core edge types

Nine types ship in the core set. Each has documented constraints.

| Type | Semantics | Cardinality |
|---|---|---|
| `about` | Source is about the target. Topical link. | many-to-many |
| `parent-of` | Source is the parent of the target. Each target has at most one parent. Hierarchy: folders, projects, trees. | one-to-many |
| `in-collection` | Source is a member of the container represented by the target. Carries a `position` property. An item belongs to any number of containers. Target must be a `user.collection`, a `core.media.series` or a `core.media.album`. | many-to-many |
| `in-thread` | Source is a member of the thread represented by the target. Carries a `position` property. Source is in at most one thread. | many-to-one |
| `attached-to` | Source is an attachment (a file or media item) belonging to the target. | many-to-many |
| `references` | Source explicitly references the target. Covers wikilink-style mentions and the highlight-on-a-passage case. | many-to-many |
| `authored-by` | Source was authored by the target (a `core.entity.person`, or the account holder's own `system.account_holder` item). | many-to-many |
| `derived-from` | Source was produced from the target. Both items remain valid in parallel. | many-to-many |
| `supersedes` | Source replaces target as the current version. Linear chains only. | one-to-one |

Cardinalities are enforced at edge-creation time. Creating a second `parent-of` edge with the same target (child), or a second `in-thread` edge with the same source (member), is rejected with `400 edge_constraint_violation`.

## Pointing an edge at yourself

The person who owns a space has an item of their own, `system.account_holder`, created when the space is provisioned. It exists to be addressable: an edge names items at both ends, so without a row there is nothing to put at the end of an `authored-by`.

Its id is on the profile response as `account_holder_item_id`, so a client reads it rather than deriving it:

```bash
curl https://api.marfa.so/profile/me -H "Authorization: Bearer $MARFA_API_KEY"
```

Then use it like any other target:

```bash
curl -X POST https://api.marfa.so/edges \
  -H "Authorization: Bearer $MARFA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"source_id":"<note-id>","target_id":"<account-holder-item-id>","edge_type":"authored-by"}'
```

The item carries no profile fields. `GET /profile/me` remains the source of truth for username, display name and avatar, so the item is a handle for the graph rather than a second copy of your identity that could drift from the first. It is a reserved `system.*` type, so ordinary credentials cannot create, modify or delete it, and it is removed with its edges when the account is deleted.

Use it instead of creating a `core.entity.person` for yourself. A person item representing the account holder duplicates identity into the graph and links back to nothing.

## Derived-from versus supersedes

Both `derived-from` and `supersedes` point backward from a new item to an older one. They mean different things.

- **`derived-from`** — "this came from that; both are still valid." Multiple derivations from the same source coexist. Use for AI-generated alternatives, transformations, parallel takes.
- **`supersedes`** — "this replaces that as the current version." Linear chain, no branching. Cycles are rejected at edge-creation time. Use when one version is meant to take over from another.

Both can coexist on the same item. An AI-cleaned version of a note can be `derived-from` AND `supersedes` the original — it was produced from it and replaces it.

## Cleanup, derivation, and replacement patterns

When one item produces another — an AI cleanup pass, a transcoder, a translator, a refinement — the choice of edge depends on the relationship being modeled. Four core edges apply, each capturing a different aspect:

| Edge | Means | Use when |
|---|---|---|
| `derived-from` | B was produced from A; both remain valid in parallel. | AI alternatives, transformations, or parallel takes that should coexist. |
| `supersedes` | B replaces A as the current version; linear chain. | Cleanup or refinement where the new version is meant to take over from the old. |
| `in-thread` | B is a member of the thread represented by A; carries `position`. | An ordered iteration history of cleanup passes you want to keep navigable. |
| `parent-of` | B is grouped under A as a child. | Cleanup that produces grouped children under a host item. |

These aren't mutually exclusive. An AI-cleaned version of a transcript can be `derived-from` the raw (provenance), `supersedes` the raw (replaces as current), AND `in-thread` a series of cleanup attempts (iteration history). The combination expresses what the integration is modeling.

`supersedes` carries the cleanest semantic for replacement — the predecessor still exists (Marfa doesn't delete A) but B is the "current" version. Use it when versions chain linearly with clear succession.

## Cascade on delete

Each edge type declares a `cascade_on_delete` behavior:

| Behavior | Meaning |
|---|---|
| `cascade` | Deleting the source or target cascades: connected items are also deleted. |
| `orphan` | Deleting one endpoint leaves the other in place; the edge is removed. |
| `block` | Deleting an endpoint with existing edges is rejected. |

`parent-of` cascades by default (deleting a parent deletes children). Other core edge types default to `orphan`.

## Threads are implicit

<Callout type="info">
  There is no `core.thread` type. A thread is whatever item is the target of a bunch of `in-thread` edges — its type gives the thread its semantics.
</Callout>

Example target types:

- A chain of reply notes: `core.note` items `in-thread` to an opener `core.note`.
- An ordered reading queue: `core.bookmark` items `in-thread` to an app-registered `app.reading_list`.
- A timeline of a trip: various types `in-thread` to a `core.event` (the trip).

The `in-thread` edge is many-to-one on the source side: each item can be in at most one thread. Ordering uses the edge's `position` property. Query a thread:

```
GET /items?edge[in-thread]=<target-id>&sort=edge.position
```

## Grouping

Four grouping primitives, each with a narrow purpose.

- **Tags** — flat labels for cross-cutting classification. See [Metadata](/guides/core-model/metadata).
- **Threads** — ordered sequences via `in-thread` edges. Single membership per source.
- **`parent-of` hierarchy** — tree structure. Source is parent, target is child. One parent per child, and deleting the parent deletes the children. Use it for natural hierarchy: folders, projects, outlines.
- **Collections** — sets via `in-collection` edges. An item belongs to as many collections as you like, and deleting a collection leaves its members alone.

### Collections

`in-collection` is the membership relation, and it accepts three kinds of container: a `user.collection`, a `core.media.series` or a `core.media.album`. The media containers ship with the core set. A plain collection does not: it is a user-space concept, so a space registers `user.collection` (or a subtype of it) itself and the edge is already waiting.

```bash
# Register the type once per space.
curl -X POST https://api.marfa.so/types \
  -H "Authorization: Bearer $MARFA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "id": "user.collection",
    "name": "Collection",
    "description": "A named set of items.",
    "version": 1,
    "fields": {
      "name": { "type": "string", "required": true, "description": "Display name." }
    }
  }'

# Create a collection, then put an item in it.
curl -X POST https://api.marfa.so/edges \
  -H "Authorization: Bearer $MARFA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "source_id": "<item-id>",
    "target_id": "<collection-id>",
    "edge_type": "in-collection",
    "properties": { "position": 1 }
  }'
```

Members can also be attached inline when the item is created, through the `edges` payload on `POST /items`.

Read a collection's members with a backref query, and an item's collections with a forward one:

```
GET /items?backref[in-collection]=<collection-id>&sort=edge.position
GET /items/<item-id>/edges?edge_type=in-collection
```

Containers do not nest. Anything the edge accepts as a target is refused as a source: putting a `user.collection`, a `core.media.series` or a `core.media.album` inside another container is rejected with `400 edge_constraint_violation` and `details.constraint: "nesting"`, subtypes included. So a series cannot sit inside a collection of shows, and an album cannot sit inside a series. Hierarchy is what `parent-of` is for, and an item that had both would have two competing answers to where it sits. Nest the collections under `parent-of` if you want a tree of them, and keep membership flat.

### Folders vs tags vs edges

Each grouping primitive answers a different question:

- **Folders** — where the bytes live. The [sync agent](/sdks/sync) stores each file's root-relative path as `source_id`, so a folder query is a `source_id starts_with "..."` filter. Good at what filesystems are good at: familiar mental model for organizing files on disk, cheap prefix queries.
- **Tags** — flat cross-cutting labels that travel with the item regardless of where the file moves on disk. Use when grouping needs to be portable across folder reorganizations.
- **Edges** — typed, directional relationships between items the query layer can traverse. Use when grouping needs first-class data treatment — "all notes about Project X" (an `about` edge), "every reply in this thread" (an `in-thread` edge), "every member of this collection" (an `in-collection` edge).

Tags and edges are independent of where files sit in the folder tree.

## Custom edge types

Apps register their own edge types when the core set doesn't fit:

```json
POST /edge-types
{
  "id": "app.shops-for",
  "cardinality": "many-to-one",
  "source_type_constraints": ["app.shopping_list_item"],
  "target_type_constraints": ["*"],
  "cascade_on_delete": "orphan",
  "property_schema": {
    "quantity": { "type": "integer" }
  }
}
```

Admin only. Core edge names are reserved and collide with `409 conflict`. Custom edge types don't inherit. See the API reference for the full schema.

## Atomic item + edges write

A single `POST /items` call creates the item and its edges in one transaction:

```json
POST /items
{
  "type": "core.highlight",
  "properties": { "text": "...", "locator_type": "offset", "start_location": 2341, "end_location": 2367 },
  "edges": {
    "references": ["<document-id>"]
  }
}
```

Either the whole write succeeds or nothing is persisted.

## Permissions

Edge writes are **dual-gated**: the caller needs both write permission on the source item's type AND write permission on the edge type. Admin keys bypass both. The gate applies wherever an `edges` payload is accepted, `POST /items/bulk` included, and it applies to an empty target list too, because inline edges replace rather than append and an empty list therefore clears them. See [Permissions](/api-reference/permissions).

## Reading across edges

The filter language doesn't do graph traversal — an edge clause narrows the item list by edge membership, but it doesn't return the connected items. Reading an item's edge targets is a two-step flow: fetch the item (which hydrates edges inline), then fetch the targets by id.

This is a real trade-off. Polymorphic references where one item points at some other typed item — a shopping-list entry that references a book, a wine bottle, or a gadget — carry the ceremony of that second call. In exchange, edges are queryable from both ends, constrained per type, and space-scoped alongside items.

Clients that need a single round-trip batch-fetch targets after the first response and join client-side.
