Every item carries a `source` system field that records which app or credential wrote it. Combined with `source_id`, it forms the natural key behind the [idempotent upsert behavior](/guides/core-model/items#relationships-lists-and-writes) and supports audit trails and cross-app data inspection.

## The natural key is scoped to the space

`(source, source_id)` is unique **within a space**, not across the instance. Two spaces syncing the same integration against the same upstream record hold two independent items: they are two people's copies of the same calendar entry, not one shared row, and each space's re-sync resolves to its own.

A deployment with no space concept — a single-space self-host, or a platform-level credential — is deduped against its own bucket on the same terms.

## Re-syncing an item the user deleted

If the natural key resolves an item that has been moved to trash, the write is **accepted and nothing is written**. The response is a `200` carrying `acknowledged: true` alongside the item as it stands.

The deletion is the user's decision. Reviving the item silently would overturn it, and refusing the write would wedge the integration: the item stays in trash, so every later sync would fail identically and never recover. Acknowledging lets the sync continue past it.

Restoring the item from trash resumes ordinary upsert behavior on the next sync — the acknowledgement is a hold, not a tombstone.

## The source field

The `source` field is the human-readable display name of the app or credential that wrote the item.

- Examples: `"Readwise Reader"`, `"Marfa Web Console"`, `"Marfa Sync (Claude)"`.
- **With a Marfa server**, stamped from the credential server-side. **Not forgeable.** A client cannot choose a different `source`; whatever it sends is ignored. That holds for a remote client and for a local one, whose queued writes are stamped when they replay.
- **With no server**, stamped by the SDK from app identity. Best-effort; there is nothing to enforce it.

Registered at credential creation time. Uniqueness enforced per space (and globally for published apps), so two apps can't claim the same `source` in the same space.

## Other client-supplied fields

A few fields are client-supplied and preserved as written but **not validated or authenticated**:

- **`device`** — optional human-readable device label (`"iphone-aic-15"`, `"MacBook Pro"`). A label, not an identifier — two clients sending the same label claim the same device.
- **`capture_latitude`, `capture_longitude`** — where the device was at item creation. Distinct from any subject coordinates in properties.
- **`timestamp`** — the user-meaningful time for the item (e.g. when a photo was taken).

<Callout type="warn">
  These are hints, not assertions. A malicious or buggy client can send any value. Downstream consumers that need trustworthy values should treat them as untrusted input.
</Callout>

Custom-type schemas cannot redeclare any of these as properties — they live as first-class wire fields on every item. Registration is rejected `400 property_shadows_field`. See [Reserved field names](/guides/schema/authoring-types#reserved-field-names) for the full list and the rationale.

## Field enforcement summary

| Field | Enforcement |
|---|---|
| `id`, `created_at`, `updated_at`, `version`, `schema_version`, `space_id` | Server-managed. Always set server-side. |
| `source` | Credential-stamped wherever a Marfa server is configured. Non-forgeable. SDK-stamped best-effort without one. |
| `timestamp`, `device`, `capture_latitude`, `capture_longitude` | Client-supplied, preserved as written, not validated. |
| Everything in `properties` | Client-supplied, type-validated. The schema validates shape; it doesn't attest to truth. |
