Types are schemas. Every item has a `type`, and its `properties` are validated against that type's schema on write.

## What ships in the registry

Every space starts with the same globally-registered type set. None of it is editable through the API, and a `POST /types` for one of these identifiers returns `409 type_already_exists`. It comes in three groups, and the distinction matters when you are choosing a namespace for your own types.

| Group | Count | Namespace | What it is |
|---|---|---|---|
| Core | 22 | `core.*` | The disciplined cross-app vocabulary. Notes, tasks, events, entities, media, files. |
| Integration | 13 | Vendor roots such as `google.*`, `readwise.*` | Shapes for data the platform's own integrations import from named third-party services. |
| System | 8 | `system.*` | Platform-internal operational records. See [System types](/guides/schema/system-types). |

Core is the part that carries the design discipline described below. **Integration types do not, and are not meant to.** They exist so an integration that pulls from a specific service can land its data losslessly, in the service's own shape, without either flattening it into a core type or asking every self-hoster to register the same schemas by hand. `google.youtube.playlist` is not a claim that playlists are a universal life-noun; it is a claim that if you sync YouTube, this is the shape you get.

Two consequences worth knowing before you name a type:

- **Those vendor roots are occupied.** `readwise.book`, `todoist.task`, `google.drive.file` and the rest already exist globally, so you cannot register them, and a publisher who claims one of the unreserved handles inherits a namespace the platform is already writing into.
- **Some integration types declare `compatible_with` against a core type**, which is how a reader that only understands core still gets something useful. It is a per-type claim, not a blanket one, so check the individual type rather than assuming.

Query the live set rather than trusting a count in prose: `GET /types` returns everything registered in the calling space, core, integration, system, and your own.

## Custom types are the default path

`core.*` is small and narrow on purpose. Most apps register their own types — inheritance from `core.*` is optional, not expected.

A type earns core-set inclusion only by passing four tests:

1. **Life-noun.** Names something a person would describe as a thing in their life, not infrastructure or app state.
2. **Stable shape.** Canonical fields don't change with context.
3. **Cross-app meaning.** Multiple unrelated apps want to read each other's writes in the raw form, without translation.
4. **Stewardship.** The core maintainers are willing and able to own the schema long-term.

Most candidates fail. That's the feature — the core is the lingua franca precisely because it's disciplined. The same rule applies recursively to subtypes (see [Why core file subtypes stop where they do](#why-core-file-subtypes-stop-where-they-do)).

Tool-specific things are not core. Memories, summaries, embeddings, AI-specific artifacts — none have broad shape consensus across producers, so they become custom types: `claude.memory`, `chatgpt.memory`, `cursor.memory`. Different shapes are honest.

The shipped integration types are that same rule applied by the platform to its own integrations, not an exception to it. They are deliberately outside the core catalog for exactly the reason a tool-specific type of yours would be.

For the namespace grammar — reserved roots, app vs publisher, identifier rules — see [Namespaces](/guides/schema/namespaces). For the inherit-vs-sibling decision and the registration-time correctness rails, see [Authoring types](/guides/schema/authoring-types).

### Why core file subtypes stop where they do

`core.file` has three subtypes: `image`, `audio`, `video`. There is no `core.file.document`.

`core.file.image` carries `width` and `height`; image viewers rely on those. `core.file.audio` and `core.file.video` carry `duration` (plus dimensions for video). `core.file.document` doesn't earn a subtype — PDFs, Word docs, Markdown, plain text, EPUBs don't share fields beyond what `core.file` already carries (`blob_ref`, `mime_type`); a generic file viewer reads them all the same way.

For the full rubric behind the boundary, see [Authoring types — when a subtype earns its place](/guides/schema/authoring-types#when-a-subtype-earns-its-place).

## What ships in the registry

`GET /types` returns 43 types before a space registers anything of its own. They come from three families, and the distinction is worth knowing because it changes how much weight a type carries:

| Family | Count | What it is |
|---|---|---|
| Core | 22 | The shared vocabulary. Life-nouns that passed the four tests above. |
| Integration | 13 | One vendor's payload shape, so an integration has somewhere faithful to write. |
| System | 8 | Platform-internal records — see [System types](/guides/schema/system-types). |

All three resolve the same way and none can be modified or deleted through the API. Only the core set is the lingua franca; an integration type is `google.calendar.event`-shaped because Google's API is, not because anyone converged on it.

## The core catalog

22 types across four families. Required fields only — full schemas in the API reference.

<Accordions type="single">
  <Accordion title="Standalone (6)">
    | Type | Purpose | Required |
    |---|---|---|
    | `core.note` | User-authored text | `body` |
    | `core.bookmark` | Saved external content | — |
    | `core.task` | Something to be done | `title` |
    | `core.event` | Something that happens at a time | `title` |
    | `core.highlight` | User engagement with content | `text` |
    | `core.message` | Cross-platform message | `body`, `from` |

    `core.highlight` carries its highlighted parent via a `references` edge, not an embedded reference. `core.message` is a light cross-platform handle — threading reuses the existing `in-thread` and `parent-of` edges; tool-specific richness (reactions, read receipts, channel ids) lives in app namespaces, not core. `core.note` and the optional bodies on `core.bookmark` and `core.task` are markdown.
  </Accordion>
  <Accordion title="Entity (3)">
    | Type | Purpose | Required |
    |---|---|---|
    | `core.entity` | Things with identity | `name` |
    | `core.entity.person` | People | `name` (inherited) |
    | `core.entity.place` | Locations | `name` (inherited) |

    `core.entity.person` adds `given_name`, `family_name`, pronouns, organization, job title, birthday. `core.entity.place` adds address components plus latitude / longitude / altitude / timezone.
  </Accordion>
  <Accordion title="Media (8)">
    | Type | Purpose | Required |
    |---|---|---|
    | `core.media` | Content the user engages with | `title` |
    | `core.media.book` | Books | `title` (inherited) |
    | `core.media.article` | Articles | `title` (inherited), `body` |
    | `core.media.film` | Films | `title` (inherited) |
    | `core.media.song` | Songs | `title` (inherited) |
    | `core.media.album` | Albums | `title` (inherited) |
    | `core.media.series` | Any ongoing container: a TV show, a podcast, a serial | `title` (inherited) |
    | `core.media.episode` | Any member of a series, whatever its medium | `title` (inherited) |

    All subtypes inherit the shared media fields (`title`, `description`, `author`, `url`, `publisher`, `published_at`, `image_url`, `language`, `body`, `notes`) and add their own (`isbn`, `duration`, `section`, `track_number`, etc.). `core.media.article` is the one subtype that promotes an inherited optional to required: an article without a `body` is rejected.

    Containment is structural, never part of a type name: a type says what a thing is, an edge says what it belongs to, and a property says how it varies. An episode joins its series — and a song joins its album — through the `in-collection` edge, so a crossover special can sit in two series and deleting a series leaves its episodes in place. Both `series` and `episode` carry a `medium` property (`tv`, `podcast`, `radio`, `video`, `mixed`), so a video podcast is an episode with `medium: video`, not a new type.
  </Accordion>
  <Accordion title="File (4)">
    | Type | Purpose | Required |
    |---|---|---|
    | `core.file` | Binary content | `blob_ref`, `mime_type` |
    | `core.file.image` | Images | `blob_ref`, `mime_type`, `width`, `height` |
    | `core.file.audio` | Audio | `blob_ref`, `mime_type`, `duration` |
    | `core.file.video` | Video | `blob_ref`, `mime_type`, `width`, `height`, `duration` |

    `blob_ref` is a SHA-256 content hash — see [Items — Attachments](/guides/core-model/items#attachments) for the blob upload flow.
  </Accordion>
</Accordions>

<Callout type="info">
  `core.message` is intentionally light — `body` + `from` + optional `to`. Tool-specific richness (reactions, read receipts, channel ids, attachment vocabularies) varies too much per producer; apps and publishers register their own message types in their own namespaces (e.g. `slack.message`, `apple.imessage`) when they need it.

  There is no `core.collection`: a space registers `user.collection` itself and connects members with the core `in-collection` edge, which is already constrained to that type. See [Collections](/guides/core-model/edges#collections).

  There is no `core.thread` — threads are implicit, defined by `in-thread` edges. See [Edges](/guides/core-model/edges#threads-are-implicit).
</Callout>

## Integration types

Thirteen types ship shaped after a specific upstream service, so an integration can write what the vendor actually returns instead of flattening it into a core type on the way in. They live in the publisher tier, under the vendor's own namespace.

<Accordions type="single">
  <Accordion title="The integration set (13)">
    | Type | Upstream |
    |---|---|
    | `google.calendar.event` | Google Calendar events |
    | `google.contacts.contact` | Google People contacts |
    | `google.drive.file` | Google Drive files |
    | `google.tasks.task` | Google Tasks |
    | `google.youtube.video` | YouTube videos |
    | `google.youtube.playlist` | YouTube playlists |
    | `google.youtube.channel` | YouTube channels |
    | `raindrop.raindrop` | Raindrop bookmarks |
    | `raindrop.collection` | Raindrop collections |
    | `readwise.book` | Readwise sources |
    | `readwise.highlight` | Readwise highlights |
    | `todoist.task` | Todoist items |
    | `withmarfa.captured_email` | Email captured through the inbox integration |

    Four of them declare `compatible_with` against a core type — `google.calendar.event`, `google.tasks.task`, `google.youtube.video` and `raindrop.raindrop` — so a reader that only understands `core.event` or `core.bookmark` can read them without knowing the vendor shape. The rest do not, because the claim would not hold: each keeps a field where the vendor puts it rather than where the core type expects it, and moving it would orphan the property on every item already captured. See [Namespaces](/guides/schema/namespaces#declaring-compatibility).
  </Accordion>
</Accordions>

Several integrations can be configured to write the core type instead when cross-app interop matters more than upstream fidelity. That is the trade: the integration type round-trips everything the vendor considers authoritative; the core type is the one every other app already reads.

<Callout type="info">
  Integration types are ordinary types under a publisher namespace. Nothing stops a space from ignoring them entirely, and a deployment that connects none of these services never sees an item of one.
</Callout>

## Registering a custom type

Register a custom type at runtime:

```json
POST /types
{
  "id": "nadia.reader_document",
  "version": 1,
  "parent": "core.bookmark",
  "fields": {
    "location": { "type": "enum", "enum_values": ["inbox", "later", "shortlist", "archive", "feed"] },
    "word_count": { "type": "integer" },
    "reading_time": { "type": "integer" },
    "html_content": { "type": "string" },
    "parsed_at": { "type": "datetime" }
  }
}
```

Registering is governed by the `types` entry in [metadata permissions](/api-reference/permissions#metadata-permissions), not by a role, so a `member` credential granted it can register. Updating and deleting a type need space-admin. `core.*` and `system.*` are platform-only, and the shipped core, integration, and system types cannot be modified or deleted through the API at all. A registration lands in the caller's own space and is invisible to every other space.

See [Authoring types](/guides/schema/authoring-types) for the inheritance rubric, the SDK helper (`defineType()`), and the server-side correctness rails.

## Field types

Type field definitions support `string`, `integer`, `number`, `boolean`, `array`, `object`, `enum`, and the four semantic string types `url`, `email`, `date`, `datetime`.

Required fields are declared with `required: true` on the field definition, or as a top-level `required: ["title"]` array — the two are equivalent. Missing required fields return `400 validation_error`.

For the optional per-field refinements — `enum_values`, `items_type`, `maxLength`, `maxItems`, `searchable`, `format` — see [Authoring types — field attributes](/guides/schema/authoring-types#field-attributes).

## Type-specific time fields

Every item carries `timestamp` — the primary user-meaningful time for the item. Type-specific time properties appear only when a type carries more than one meaningful time.

- **`core.task`** adds `due_at`, `completed_at`, optional `starts_at` — three distinct moments, none reducible to `timestamp`.
- **`core.event`** adds `starts_at` and `ends_at`, plus `timezone` and `end_timezone` for the wall clock each end keeps, and `all_day` for an event that occupies whole days instead. See [Recurring events](/guides/querying/recurring-events#whole-days).
- **`core.media.*`** adds `published_at` — the content's publication date, distinct from when the user engaged with it.

When a type has one meaningful user-time, that time is `timestamp` and the type adds no extra field. A highlight's "when-highlighted" is `timestamp`; there is no separate `highlighted_at`.

## Display hints

Types may declare an optional `display_hints` block:

```json
"display_hints": {
  "title_field": "title",
  "body_field": "body"
}
```

This points generic readers (catalog views, search UIs, item previews) at the canonical title and body fields. Hints are inherited from the nearest ancestor when a subtype omits them.

## Merge policy

Concurrent-edit resolution per field is declared via `merge_policy` on the type. The full treatment — declaration grammar, inheritance, keep-both semantics, per-core-type defaults, the 409 envelope — lives on [Conflicts](/guides/schema/conflicts).
