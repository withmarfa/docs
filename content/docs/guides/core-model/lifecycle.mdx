Every item has `state`, one of three values:

| State | Meaning |
|---|---|
| `active` | The item is live and part of the user's data. Default for new items. |
| `archived` | Kept for reference; excluded from the default active view. Still searchable. |
| `trashed` | Soft-deleted. Excluded from search. Hard-deleted once it has been in the trash longer than the retention window. See [Trash retention](#trash-retention). |

Lifecycle is **universal** for user content — the same three states apply to every `core.*`, `app.*`, `user.*`, and `<publisher>.*` type. Types don't declare their own states or transitions.

[`system.*` items](/guides/schema/system-types) are the exception. Their lifecycle is bounded to `active` and `revoked`, a different shape because they're operational records rather than user content. The universal three-state model doesn't apply, and the bound is enforced rather than conventional: a `system.*` item cannot be archived or trashed by any route.

## Transitions

| From | To |
|---|---|
| `active` | `archived`, `trashed` |
| `archived` | `active`, `trashed` |
| `trashed` | `active` (restore) |

For `system.*` items the graph is `active` to `revoked`, and `revoked` is terminal.

Invalid transitions return `400 invalid_transition`. You cannot go directly from `trashed` to `archived` — restore to `active` first.

## API

Transitions happen through four routes:

```
POST /items/{id}/transition  # any → any (subject to the graph below)
POST /items/{id}/restore     # archived → active, or trashed → active
DELETE /items/{id}           # soft delete: → trashed, or → revoked for system.*
DELETE /items/{id}/purge     # hard delete; admin scope; irreversible
```

`POST /items/{id}/transition` is the universal entry point — pass the target state in the body:

```
POST /items/{id}/transition
{ "state": "archived" }
```

The dedicated `restore` and `delete` routes are sugar for the common cases. Transitions are logged in the audit trail.

`DELETE /items/{id}` soft-deletes into whichever state the item's own lifecycle uses for it: `trashed` for user content, `revoked` for a `system.*` item, which has no `trashed`. Purge follows the same rule and accepts an item in that state. Deleting something already soft-deleted is a no-op, not an error.

## Triage vs lifecycle

Triage workflows — a read-later app's Inbox / Later / Shortlist, a clipboard's pinned vs. unpinned — are **app concerns**, not core state. Apps model triage in their own type's properties (e.g. `location: "shortlist"` on a custom bookmark type) or in extensions.

Lifecycle and triage are separate axes. An item can be triaged to "Shortlist" (app concept) while its `state` is `active` (core concept).

## Trash retention

A trashed item is hard-deleted once it has been in the trash longer than the retention window. An instance sets that window with `TRASH_RETENTION_DAYS` and a space overrides it with `trash_retention_days`; both are described in [Configuration](/self-hosting/run/configuration).

The clock starts when the item is trashed and runs from there. Editing it while it sits in the trash does not restart it, and neither does a tag or extension write. Restoring it stops the clock, and trashing it again starts a fresh window rather than resuming the first.

Only `trashed` is swept. A `system.*` item soft-deletes to `revoked`, which no retention job removes.

## Hard deletion

<Callout type="warn">
  `DELETE /items/{id}/purge` is **irreversible**. Admin-scoped, logged, no soft-delete safety net. The normal `DELETE` is soft: user content transitions to `trashed` and auto-purges after the retention window, while a `system.*` item transitions to `revoked` and stays until purged.
</Callout>

Purge removes:

- The item row.
- All edges with this item as source or target.
- The metadata row.
- All extensions scoped to this item.
- Attachment references (blobs themselves are content-addressed and may be retained if referenced by other items).
