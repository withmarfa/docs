---
title: Build a connector
description: Make a working connector from the kit's template, run it against a stand-in service, and watch it follow changes and report a failure.
---

In this tutorial you build a connector for a small reading list service. It reads the list, writes each entry to your instance as an item, and sets aside an entry the service drops. The connector is a few short files, because the connector kit registers it, writes only what changed, and reports each run for you.

You need the instance from the [Quickstart](/quickstart), running at `http://localhost:8600`, and the Quickstart terminal, where you set `MARFA_API_URL` and `MARFA_API_KEY`. The key you made there can make other keys, which the connector needs. You also need Git, [Node.js](https://nodejs.org) 22.13 or later and [pnpm](https://pnpm.io/installation) 11.

<Steps paged>
<Step>

### Get the kit

The [marfa-connectors](https://github.com/withmarfa/marfa-connectors) repository holds the connector kit, `@withmarfa/connector`, a template to start from, and the connectors Marfa ships. It has no releases, so build it from its `main` branch:

```bash
git clone https://github.com/withmarfa/marfa-connectors.git
cd marfa-connectors
pnpm install --frozen-lockfile
pnpm build
```

</Step>
<Step>

### Save a reading list

A connector reads a vendor: the service that holds the records. Here the vendor is a stand-in that serves a list from a file, so you can change the list and watch the connector follow.

Make a folder outside the checkout, such as `reading-list`, and save the list in it:

```json title="reading-list/entries.json"
[
  {
    "id": "1",
    "title": "The Pragmatic Programmer",
    "url": "https://example.com/pragmatic",
    "author": "Hunt and Thomas",
    "added": "2026-09-01T09:00:00Z"
  },
  {
    "id": "2",
    "title": "A Philosophy of Software Design",
    "url": "https://example.com/philosophy",
    "author": "Ousterhout",
    "added": "2026-09-03T18:30:00Z"
  }
]
```

</Step>
<Step>

### Serve the reading list

Save the stand-in service beside the list. It answers `GET /entries` with an account name and the entries, and only for the token `demo-token`:

```js title="reading-list/vendor.mjs"
import { createServer } from "node:http";
import { readFile } from "node:fs/promises";

createServer(async (request, response) => {
  if (request.headers.authorization !== "Bearer demo-token") {
    response.writeHead(401).end();
  } else if (request.url === "/entries") {
    const entries = JSON.parse(await readFile("entries.json", "utf8"));
    response.writeHead(200, { "Content-Type": "application/json" });
    response.end(JSON.stringify({ account: "demo", entries }));
  } else {
    response.writeHead(404).end();
  }
}).listen(4100, "127.0.0.1", () => {
  console.log("The reading list is at http://127.0.0.1:4100");
});
```

In a new terminal, start it from the `reading-list` folder, and leave it running:

<Terminal>

```bash
node vendor.mjs
```

```text
The reading list is at http://127.0.0.1:4100
```

</Terminal>

Go back to the Quickstart terminal, in the `marfa-connectors` checkout, for the rest.

</Step>
<Step>

### Copy the template

Make a folder for the connector, and copy the template's package and build settings into it:

```bash
mkdir -p connectors/readlist/src
cp template/connector/package.json template/connector/tsconfig.json connectors/readlist/
```

In `connectors/readlist/package.json`, change `"name": "example"` to `"name": "readlist"`. Then add the folder to the `references` list in the root `tsconfig.json`, so that the build includes it:

```json title="tsconfig.json"
    { "path": "connectors/readlist" },
```

</Step>
<Step>

### Describe the type

A connector writes items of a type of its own. Save its definition beside the connector's source:

```json title="connectors/readlist/src/readlist.entry.json"
{
  "id": "readlist.entry",
  "label": "Reading List Entry",
  "description": "An entry from the reading list service.",
  "parent": "core.bookmark",
  "fields": {
    "entry_id": {
      "type": "string",
      "required": true,
      "description": "The entry's ID in the reading list service."
    }
  },
  "display_hints": { "title_field": "title" }
}
```

Its parent is `core.bookmark`, so an entry already has a `title`, a `url` and an `author`. The type adds only the entry's ID in the service. [Define a type](/guides/define-a-type) explains each part.

</Step>
<Step>

### Read the service

Keep the vendor's side in a file of its own. This function asks the service for its entries, and fails if the service refuses:

```ts title="connectors/readlist/src/readlist.ts"
export interface ListedEntry {
  id: string;
  title: string;
  url?: string;
  author?: string;
  added: string;
}

export async function readList(
  address: string,
  token: string,
  signal: AbortSignal,
): Promise<{ account: string; entries: ListedEntry[] }> {
  const response = await fetch(`${address.replace(/\/+$/, "")}/entries`, {
    headers: { Authorization: `Bearer ${token}` },
    signal: AbortSignal.any([signal, AbortSignal.timeout(30_000)]),
  });
  if (!response.ok) {
    throw new Error(`the reading list answered ${String(response.status)}`);
  }
  return (await response.json()) as { account: string; entries: ListedEntry[] };
}
```

The `signal` comes from the kit, so stopping the connector ends a request in flight.

</Step>
<Step>

### Declare the connector

Save the connector's definition. The next two steps fill in `run`:

```ts title="connectors/readlist/src/main.ts"
import {
  defineConnector,
  main,
  type TypeDefinition,
} from "@withmarfa/connector";
import readlistEntry from "./readlist.entry.json" with { type: "json" };
import { readList } from "./readlist.js";

const connector = defineConnector({
  name: "readlist",
  description: "Entries from a reading list service.",
  source: "readlist",
  types: [
    {
      type: readlistEntry as TypeDefinition,
      fields: ["entry_id", "title", "url", "author"],
    },
  ],
  env: { READLIST_URL: "required", READLIST_TOKEN: "secret" },
  async run({ env, signal, upsert, held, archive }) {
  },
});

await main(connector);
```

`source` is the label on every item the connector writes. `types` names its type and the fields the service holds, and **the kit registers the type on the first start** and checks it on every start after. A missing `required` or `secret` setting stops the connector before it starts, and **a `secret` never appears in a log line**.

</Step>
<Step>

### Write each entry

Inside `run`, read the list and hand every entry to `upsert`:

```ts title="connectors/readlist/src/main.ts"
    const { account, entries } = await readList(
      env.READLIST_URL,
      env.READLIST_TOKEN,
      signal,
    );
    const key = (id: string): string => `${account}:${id}`;

    await upsert(
      readlistEntry.id,
      entries.map((entry) => ({
        source_id: key(entry.id),
        properties: {
          entry_id: entry.id,
          title: entry.title,
          url: entry.url,
          author: entry.author,
        },
        occurred_at: entry.added,
      })),
    );
```

Each entry's `source_id` is its ID in the service, after the account, so two accounts never share an item. The kit compares each entry with the item already written under that `source_id`, and **writes only what changed**.

</Step>
<Step>

### Set aside what the service dropped

At the end of `run`, archive each item whose entry the service no longer lists:

```ts title="connectors/readlist/src/main.ts"
    const listed = new Set(entries.map((entry) => key(entry.id)));
    const gone = (await held(readlistEntry.id))
      .map((row) => row.source_id)
      .filter((id): id is string => id !== undefined && !listed.has(id));
    await archive(readlistEntry.id, gone);
```

`held` answers the items the connector wrote. Reading a missing entry as deleted is safe here because **this service lists every entry it has**; [Pull and push](/guides/connector-pull-and-push#set-aside-what-the-vendor-deleted) covers a vendor that doesn't.

Install, which links the new folder into the workspace, and build:

```bash
pnpm install
pnpm build
```

</Step>
<Step>

### Make the connector's key

A connector runs on a key of its own, which reaches only what the connector needs. Make it with your key from the Quickstart:

<Terminal>

```bash
marfa keys create --label readlist --source readlist \
  --type-permission readlist.entry=write \
  --metadata-permission types=write --default-tier feed
```

```text
marfa_k1_0f3f249028434bdd1d81827b44aa0c993f9d15ea8f9830bc411b5443fede637c
key 01a15f19-6c20-7c68-a0b3-40bd8a431442 (readlist); the plaintext is shown once, keep it now
  readlist.entry     Read and edit
  Custom data types  Read and edit
```

</Terminal>

<Callout type="warn">Copy the key now. Marfa shows it only once.</Callout>

The key writes the connector's one type and can register it, and its source matches the connector's `source`. **The connector refuses a key that reaches further**, such as your own. [Manage keys](/guides/manage-keys) explains each flag.

</Step>
<Step>

### Run it

Run the connector once, with its key and the service's address and token. **Set them on the command alone**, so they don't replace the key your CLI uses:

<Terminal>

```bash
MARFA_API_URL=http://localhost:8600 \
MARFA_API_KEY=<the connector's key> \
READLIST_URL=http://127.0.0.1:4100 \
READLIST_TOKEN=demo-token \
node connectors/readlist/dist/main.js --once
```

```text
2026-10-21T15:34:24.326Z info registered as 01a15f19-6d25-7806-8fd1-226237a916c5
2026-10-21T15:34:24.404Z info run succeeded: created 2, updated 0, archived 0, unchanged 0, skipped 0
```

</Terminal>

The connector registered with your instance, wrote both entries, reported the run and exited. [Run a connector](/guides/run-a-connector) covers running one on a schedule, and what each exit code means.

</Step>

### Run it again

Run the connector with the same command. Its report counts one entry of each kind:

<Terminal>

```bash
MARFA_API_URL=http://localhost:8600 \
MARFA_API_KEY=<the connector's key> \
READLIST_URL=http://127.0.0.1:4100 \
READLIST_TOKEN=demo-token \
```

```text

2026-10-21T15:34:24.883Z info run succeeded: created 1, updated 1, archived 1, unchanged 0, skipped 0
```

List the items in every state, to see the archived one too:

```bash
marfa items list --type readlist.entry --state any
```

The retitled entry kept its ID and moved to version 2. The new entry is a new item, and the dropped one is **archived, not deleted**, so it keeps its history. Run the connector once more without changing the list, and its report counts every entry `unchanged`.

<Step>

### See a run fail

Run the connector with a token the service refuses. The service answers `401`, and the run fails:

<Terminal>

```bash
MARFA_API_URL=http://localhost:8600 \
MARFA_API_KEY=<the connector's key> \
READLIST_URL=http://127.0.0.1:4100 \
READLIST_TOKEN=wrong-token \
node connectors/readlist/dist/main.js --once
```

```text
2026-10-21T15:34:25.323Z info registered as 01a15f19-6d25-7806-8fd1-226237a916c5
2026-10-21T15:34:25.355Z error run failed: the reading list answered 401; created 0, updated 0, archived 0, unchanged 0, skipped 0
```

</Terminal>

The instance keeps the failure on the connector's registration, with its error:

<Terminal>

```bash
marfa connectors list
```

```text
01a15f19-6d25-7806-8fd1-226237a916c5  readlist  readlist  failed  2026-10-21T15:34:25.355Z  the reading list answered 401
```

</Terminal>

**Nothing it wrote before is lost**, and the next run with the right token reads the whole list again.

</Step>

## Next steps

You have a connector that reads a vendor, keeps your instance in step with it, and reports each run. Stop the reading list service with Control-C when you're done.

This connector only reads. Edit an entry's title in Marfa, and the next run puts the service's title back, with a warning that names the field. To carry changes back to the vendor, or to act on its webhooks, go on to the connector guides:
