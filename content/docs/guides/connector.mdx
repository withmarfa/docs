---
title: Build a connector
description: Make a working connector from the kit's template, run it against a stand-in service, and watch it follow changes and report a failure.
---

In this tutorial you build a connector for a small reading list service. The connector reads the list, writes each entry to your instance as an item, and sets aside an entry the service drops. You run it, look at what it wrote, change the list and run it again, and then see what a failed run looks like. The connector is one short file, because the connector kit registers it, compares what it read with what it wrote before, and reports each run for you.

You need the instance from the [Quickstart](/quickstart), running at `http://localhost:8600`, with the CLI pointed at it through `MARFA_API_URL` and `MARFA_API_KEY`. The key you made there can make other keys, which the connector needs. You also need Git, [Node.js](https://nodejs.org) 22.13 or later and [pnpm](https://pnpm.io/installation) 11.

<Steps>
<Step>

### Get the kit and the template

The [marfa-connectors](https://github.com/withmarfa/marfa-connectors) repository holds the connector kit, `@withmarfa/connector`, a template to start from, and the connectors Marfa ships. The repository has no releases, so these steps build from its `main` branch, and its own tests run against a Marfa server that v0.0.9 and every later release contains. Clone it and build it:

```bash
git clone https://github.com/withmarfa/marfa-connectors.git
cd marfa-connectors
pnpm install --frozen-lockfile
pnpm build
```

</Step>
<Step>

### Start a reading list to read

A connector reads a vendor: the service that holds the records. Here the vendor is a stand-in, a small server that serves a list from a file, so you can change the list and watch the connector follow.

Make a folder outside the checkout, such as `reading-list`, and save the list in it:

```json title="entries.json"
[
  {
    "id": "1",
    "title": "The Pragmatic Programmer",
    "url": "https://example.com/pragmatic",
    "author": "Hunt and Thomas",
    "added": "2026-09-01T09:00:00Z"
  },
  {
    "id": "2",
    "title": "A Philosophy of Software Design",
    "url": "https://example.com/philosophy",
    "author": "Ousterhout",
    "added": "2026-09-03T18:30:00Z"
  }
]
```

Save the service beside it:

```js title="vendor.mjs"
import { createServer } from "node:http";
import { readFile } from "node:fs/promises";

createServer(async (request, response) => {
  if (request.headers.authorization !== "Bearer demo-token") {
    response.writeHead(401).end();
    return;
  }
  if (request.method === "GET" && request.url === "/entries") {
    const entries = JSON.parse(await readFile("entries.json", "utf8"));
    response.writeHead(200, { "Content-Type": "application/json" });
    response.end(JSON.stringify({ account: "demo", entries }));
    return;
  }
  response.writeHead(404).end();
}).listen(4100, "127.0.0.1", () => {
  console.log("The reading list is at http://127.0.0.1:4100");
});
```

Start it from that folder, and leave it running:

```bash
node vendor.mjs
```

```text
The reading list is at http://127.0.0.1:4100
```

The service answers `GET /entries` with its account name and its entries, and only for the token `demo-token`. Open another terminal in the `marfa-connectors` checkout for the rest.

</Step>
<Step>

### Copy the template

Make a folder for the connector, and copy the template's package and build settings into it:

```bash
mkdir -p connectors/readlist/src
cp template/connector/package.json template/connector/tsconfig.json connectors/readlist/
```

In `connectors/readlist/package.json`, change `"name": "example"` to `"name": "readlist"`. Then add the folder to the `references` list in the root `tsconfig.json`, so that the build includes it:

```json title="tsconfig.json"
    { "path": "connectors/readlist" },
```

</Step>
<Step>

### Describe the type

A connector writes items of a type of its own. Save this definition beside the connector's source:

```json title="connectors/readlist/src/readlist.entry.json"
{
  "id": "readlist.entry",
  "label": "Reading List Entry",
  "description": "An entry from the reading list service.",
  "parent": "core.bookmark",
  "fields": {
    "entry_id": {
      "type": "string",
      "required": true,
      "description": "The entry's ID in the reading list service."
    }
  },
  "display_hints": { "title_field": "title" }
}
```

The type's parent is `core.bookmark`, so an entry already has a `title`, a `url` and an `author`. The type adds only what a bookmark lacks: the entry's ID in the service. [Define a type](/guides/define-a-type) explains type definitions.

</Step>
<Step>

### Write the connector

Save the connector itself:

```ts title="connectors/readlist/src/main.ts"
import {
  defineConnector,
  main,
  type Entry,
  type TypeDefinition,
} from "@withmarfa/connector";
import readlistEntry from "./readlist.entry.json" with { type: "json" };

interface VendorEntry {
  id: string;
  title: string;
  url?: string;
  author?: string;
  added: string;
}

const connector = defineConnector({
  name: "readlist",
  description: "Entries from a reading list service.",
  source: "readlist",
  types: [
    {
      type: readlistEntry as TypeDefinition,
      fields: ["entry_id", "title", "url", "author"],
    },
  ],
  env: {
    READLIST_URL: "required",
    READLIST_TOKEN: "secret",
  },
  async run({ env, signal, upsert, archive, held }) {
    const base = env.READLIST_URL.replace(/\/+$/, "");
    const response = await fetch(`${base}/entries`, {
      headers: { Authorization: `Bearer ${env.READLIST_TOKEN}` },
      signal: AbortSignal.any([signal, AbortSignal.timeout(30_000)]),
    });
    if (!response.ok) {
      throw new Error(`the reading list answered ${String(response.status)}`);
    }
    const { account, entries } = (await response.json()) as {
      account: string;
      entries: VendorEntry[];
    };

    // The account goes inside the source ID, so two accounts under one
    // source never share a row.
    const key = (entry: VendorEntry): string => `${account}:${entry.id}`;

    await upsert(
      readlistEntry.id,
      entries.map((entry): Entry => ({
        source_id: key(entry),
        properties: {
          entry_id: entry.id,
          title: entry.title,
          url: entry.url,
          author: entry.author,
        },
        occurred_at: entry.added,
      })),
    );

    // This service lists every entry it has, so a row it no longer lists
    // was deleted there.
    const listed = new Set(entries.map(key));
    const gone = (await held(readlistEntry.id))
      .map((row) => row.source_id)
      .filter((id): id is string => id !== undefined && !listed.has(id));
    await archive(readlistEntry.id, gone);
  },
});

await main(connector);
```

The definition says what the connector is. `name` and `description` register it with your instance, and `source` is the label on every item it writes. `types` names the type it writes and, in `fields`, the properties the service holds: the kit registers the type on the first start and checks it on every start after.

`env` names the settings the connector reads from its environment. A missing `required` or `secret` setting stops the connector before it starts, and **a `secret` never appears in a log line or a report**.

`run` is one pass of the connector's work. It reads the service, passing the kit's `signal` so that a stop ends the request, beside a time limit of its own.

It hands every entry to `upsert`, keyed by a `source_id` that puts the account before the service's own ID. The kit compares each entry with the item already written under that key, and **writes only what changed**.

Last, `run` asks `held` for the items the connector holds, and archives each one the service no longer lists. **That's safe because this service lists every entry it has.** A vendor whose listing leaves some records out has to be asked about each missing one before it's archived, as [Pull and push](/guides/connector-pull-and-push) explains.

</Step>

### Build it

Install, which links the new folder into the workspace, and build:

```bash
pnpm install
pnpm build
```

</Step>
<Step>

### Make the connector's key

A connector runs with a key of its own, which reaches only what the connector needs. Make it with the CLI, which uses your key from the Quickstart:

```bash
marfa keys create --label readlist --source readlist --type-permission readlist.entry=write --metadata-permission types=write --default-tier feed
```

`--source readlist` matches the connector's `source`. `--type-permission` gives the key write on the connector's one type and on nothing else, and `--metadata-permission types=write` lets the connector register that type. `--default-tier feed` sends any write under the key that names no tier to the feed rather than the library.

[Manage keys](/guides/manage-keys) explains each part of a key.

The CLI prints the key, which begins `marfa_k1_`, **once**. Keep it for the next step. **The connector refuses to run on a key that reaches further than it needs**, such as your own.

</Step>
<Step>

### Run it

Run the connector once, with its own key and the service's address and token. **Set them on the command alone**, so they don't replace the key your CLI uses:

```bash
MARFA_API_URL=http://localhost:8600 \
MARFA_API_KEY=<the connector's key> \
READLIST_URL=http://127.0.0.1:4100 \
READLIST_TOKEN=demo-token \
node connectors/readlist/dist/main.js --once
```

The connector registers with your instance, reads the list, writes what it found, reports the run and exits:

```text
2026-10-09T23:49:45.389Z info registered as 01a12312-9f1c-7f9f-9178-ea715f343015
2026-10-09T23:49:45.435Z info run succeeded: created 2, updated 0, archived 0, unchanged 0, skipped 0
```

`--once` runs one pass. The connector exits with `0` for a run that succeeded, `1` for a run that failed, and `2` for a setting that's missing or malformed.

</Step>
<Step>

### See what it wrote

With your own key, list the items of the connector's type:

```bash
marfa items list --type readlist.entry
```

```text
01a12312-9f50-7c69-b82f-6240a285e7a0  readlist.entry  2026-09-03T18:30:00.000Z  A Philosophy of Software Design
01a12312-9f4c-7e1f-b73e-a18c655d5296  readlist.entry  2026-09-01T09:00:00.000Z  The Pragmatic Programmer
```

Read one of them in full:

```bash
marfa items get 01a12312-9f4c-7e1f-b73e-a18c655d5296 --json
```

```json
{
  "item": {
    "id": "01a12312-9f4c-7e1f-b73e-a18c655d5296",
    "type": "readlist.entry",
    "state": "active",
    "tier": "feed",
    "properties": {
      "url": "https://example.com/pragmatic",
      "title": "The Pragmatic Programmer",
      "author": "Hunt and Thomas",
      "entry_id": "1"
    },
    "occurred_at": "2026-09-01T09:00:00.000Z",
    "version": 1,
    "source": "readlist",
    "source_id": "demo:1"
  }
}
```

The answer has more fields than this. The item is in the feed tier, where what a connector brings in waits until a person or an app keeps it in the library.

Its `source` and `source_id` are its natural key: **the next run finds the item by them and updates it**, rather than writing a second copy. `occurred_at` is when the entry was added to the list, not when the connector read it.

The connector's registration shows how its runs went:

```bash
marfa connectors list
```

```text
01a12312-9f1c-7f9f-9178-ea715f343015  readlist  readlist  succeeded  2026-10-09T23:49:45.435Z  created 2, updated 0, archived 0, unchanged 0, skipped 0
```

`marfa connectors runs <connector-id>` lists its last runs, newest first.

</Step>
<Step>

### Change the list and run again

Edit `entries.json` in the `reading-list` folder: retitle entry 1, delete entry 2, and add entry 3.

```json title="entries.json"
[
  {
    "id": "1",
    "title": "The Pragmatic Programmer, 20th anniversary edition",
    "url": "https://example.com/pragmatic",
    "author": "Hunt and Thomas",
    "added": "2026-09-01T09:00:00Z"
  },
  {
    "id": "3",
    "title": "Designing Data-Intensive Applications",
    "url": "https://example.com/ddia",
    "author": "Kleppmann",
    "added": "2026-10-02T07:15:00Z"
  }
]
```

Run the connector with the same command as before. Its report says what changed:

```text
2026-10-09T23:50:04.768Z info run succeeded: created 1, updated 1, archived 1, unchanged 0, skipped 0
```

List the items in every state, to see the archived one too:

```bash
marfa items list --type readlist.entry --state any
```

```text
01a12312-ead4-72f8-a68e-2f996039e3bb  readlist.entry  2026-10-02T07:15:00.000Z  Designing Data-Intensive Applications
01a12312-9f50-7c69-b82f-6240a285e7a0  readlist.entry  2026-09-03T18:30:00.000Z  A Philosophy of Software Design                     [archived]
01a12312-9f4c-7e1f-b73e-a18c655d5296  readlist.entry  2026-09-01T09:00:00.000Z  The Pragmatic Programmer, 20th anniversary edition
```

The retitled entry was updated in place: it keeps its ID and moves to version 2. The new entry is a new item, and the entry the service dropped is **archived, not deleted**, so its history stays. Run the connector a third time without changing the list, and every entry is `unchanged`: the connector writes nothing, and no item's version moves.

**The service is the source of truth for the fields the connector writes.** Change an entry's title in Marfa, and the next run puts it back and logs a warning that names the field.

</Step>
<Step>

### See a run fail

Run the connector with a token the service refuses, `READLIST_TOKEN=wrong-token`. The service answers `401`, and the run fails:

```text
2026-10-09T23:50:10.200Z error run failed: the reading list answered 401; created 0, updated 0, archived 0, unchanged 0, skipped 0
```

The connector exits with `1`, and `marfa connectors list` shows the run as `failed`, with its error:

```text
01a12312-9f1c-7f9f-9178-ea715f343015  readlist  readlist  failed  2026-10-09T23:50:10.200Z  the reading list answered 401
```

**Nothing it wrote before is lost**, and the next run with the right token reads the whole list again. Leave the token out altogether and the connector doesn't start: it names the missing setting and exits with `2`.

</Step>
</Steps>

## Next steps

You have a connector that reads a vendor, keeps your instance in step with it, and reports each run. Stop the reading list service with Control-C when you're done. To run a connector on a schedule, run it with `--every 15m` as a long-lived process, or run `--once` from launchd, cron or a container; `template/README.md` in the checkout covers each.
