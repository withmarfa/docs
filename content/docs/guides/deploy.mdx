---
title: Deploy
description: Run Marfa somewhere it stays up, with storage that survives a restart, two secrets and an address.
---

An instance is one server process on one SQLite file. To deploy it, give that process storage that outlives it, two secrets, and an address you can reach. [Run an instance](/get-started/run-an-instance) starts a server to try. This guide is for one you leave running.

## Where it can run

| Where | How |
| --- | --- |
| A computer you own that stays on | Run the server under a supervisor that restarts it. |
| A container on a host you run | Build the image from `deploy/Dockerfile` in the [Marfa repository](https://github.com/withmarfa/marfa) and mount one volume at `/data`. |
| Railway | Deploy the [Marfa template](https://railway.com/new/template/5z9-Ja). It creates the server, a volume, and a private bucket for backups, and generates the two secrets. [Create a personal Marfa instance on Railway](https://github.com/withmarfa/marfa/blob/main/deploy/railway.md) has the steps, including claiming the instance. Railway bills the service and its storage to you. |

Run one server for each database, so keep a host at one replica. The server also runs its own [housekeeping jobs](/guides/housekeeping) and backup work in the background, so turn off any host feature that stops an idle service, such as Railway's Serverless mode.

## What the server needs

| Need | Setting | What to know |
| --- | --- | --- |
| A place for the database | `SQLITE_PATH` | One file, `./data/marfa.db` by default. A log named `marfa.db-wal` sits beside it and holds writes not yet moved into the file. |
| A place for blobs | `BLOB_PATH` | A folder, `./data/blobs` by default. Every upload lands here. |
| Two secrets | `API_KEY_SALT` and `MARFA_AUTH_SECRET` | Required in production. |
| The address clients use | `MARFA_AUTH_BASE_URL` | Required in production. |
| A port | `PORT` | `8600` by default. |

Put the database and the blob folder on storage that survives a restart: a volume in a container, or a directory on a disk you keep. [Back up and restore](/guides/back-up-and-restore) covers copying it. [Settings](/guides/settings) covers every other setting.

### The secrets

Generate each secret once and keep a copy outside the data directory, because neither is stored in it:

```bash
openssl rand -hex 32
```

- `API_KEY_SALT` hashes keys and app tokens. The database holds only the hashes, so a server started with another salt refuses every existing key and token with `401 unauthorized`. Starting again with the original salt accepts them again.
- `MARFA_AUTH_SECRET` signs sign-in cookies and credential-free blob links, among other things. It must be at least 32 characters. Starting with another value ends every signed-in session.

Set `NODE_ENV=production`. The server then refuses to start without both secrets and `MARFA_AUTH_BASE_URL`, and refuses a weak secret. Outside production an unset salt falls back to a built-in one, which is no protection on an address anyone can reach. The container image sets `NODE_ENV=production`.

### The address

`MARFA_AUTH_BASE_URL` is the public URL clients reach the server at, such as `https://marfa.example.com`. The server uses it as the OAuth issuer, the cookie domain, and the origin of the links it makes. The owner can claim the instance and sign in only at an `https` address, or on a loopback host such as `localhost`.

[Where it runs](/get-started#where-it-runs) lists the ways to get an address: Tailscale (suggested) or a Cloudflare Tunnel. When a proxy or tunnel sits in front of the server, set `TRUSTED_PROXY_CIDRS` to the proxy's address ranges, or `TRUSTED_PROXY_HEADER` to a header the platform's edge overwrites with the client address. Without either, the server ignores `X-Forwarded-For`.

### An object store

Add an S3-compatible bucket with `S3_BUCKET` and the other `S3_` settings, and the server keeps a second copy of every blob there. The `blob-replicate` housekeeping job makes the copies. With the container recipe, the bucket also receives the database, so an instance can be rebuilt from the bucket alone.

Put the bucket on a different site from the instance. A link the bucket signs serves a blob from the bucket's own host, without the protections the instance adds to its own downloads, so a bucket under the instance's domain could let an uploaded HTML file run as a page of the instance.

## Run it in a container

Build the image from the repository root, then start it with one volume at `/data` and the settings in an environment file:

```bash
docker build -f deploy/Dockerfile --build-arg VERSION_SHA=$(git rev-parse HEAD) -t marfa-server .
docker run --name marfa -d --restart unless-stopped -p 8600:8600 -v marfa-data:/data --env-file <your-env-file> marfa-server
```

The environment file holds `API_KEY_SALT`, `MARFA_AUTH_SECRET`, `MARFA_AUTH_BASE_URL` and the `S3_` settings. Keep it out of any repository.

Without `S3_BUCKET`, the container runs the server alone and says so in its log. That is a trial, because nothing is streamed off the machine.

The image includes the `marfa` command. To claim the new instance, open a single-use setup link from inside the container, then follow [Run an instance](/get-started/run-an-instance):

```bash
docker exec marfa marfa --socket /data/control/marfa.sock setup open --no-browser
```

## Keep it running

Whatever supervises the server, three facts decide how to configure it:

- **Health.** `GET /health` answers without a credential. It answers `503` when the database, a write, the disk, or blob storage is `down`, and `200` otherwise, `degraded` included. The container image checks it every 30 seconds.
- **Stopping.** `SIGTERM` or `SIGINT` stops the server. It ends open event streams with a `stream_incomplete` frame whose `reason` is `server_stopping`, finishes the requests and housekeeping runs in flight, and exits `0` within eight seconds. A runtime that allows ten seconds before it kills the process leaves room for that.
- **Exit statuses.** Status `78` means the database was written by another build: the server changed nothing and starting it again meets the same refusal, so do not restart on `78`. [Upgrade](/guides/upgrade) says what to do. Status `1` is any other failed start, such as a setting outside its rules or a port in use. The container does not exit on `78`. It stays up and unhealthy with the reason in its log, so a restart policy cannot loop on it.

Without a container, build the server with `pnpm --filter "@withmarfa/server..." build` in a clone of the repository, then run `node dist/index.js` from `packages/server` with the settings in its environment. The container recipe is the tested route.

The server creates a private socket at `control/marfa.sock` beside the database, unless `MARFA_CONTROL_SOCKET` names another path. A command run on the machine, under the server's account, reaches the instance through it with direct authority. [The marfa command](/tools/marfa-command) explains `--socket`.

The rules behind this page are in the [instance chapter of the contract](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md). The container recipe is documented in the [deployment guide](https://github.com/withmarfa/marfa/blob/main/deploy/README.md).
