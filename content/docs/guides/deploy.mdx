The Quickstart runs an instance to try. **An instance you keep needs more**: storage that outlives the process, two secrets kept somewhere safe, and an address your devices can reach.

An instance is one server process and one SQLite database, so there's no database server to set up. Run one server for each database: **keep a host at one replica**.

## Where it can run

| Where | How | Good for |
| --- | --- | --- |
| A computer you own | Run the server under a supervisor that restarts it, as in [Run it without a container](#run-it-without-a-container). | A Mac or a home server that stays on. |
| A container | Build the image from `deploy/Dockerfile` in the [Marfa repository](https://github.com/withmarfa/marfa) and give it one volume, as in [Run it in a container](#run-it-in-a-container). | A server you already run. |
| Railway | Deploy the [Marfa template](https://railway.com/new/template/5z9-Ja). It creates the server, a volume and a private bucket for backups, generates the two secrets, and sets the address. | The quickest way to an instance on the internet. Railway bills the service and its storage to you. |

[Create a personal Marfa instance on Railway](https://github.com/withmarfa/marfa/blob/main/deploy/railway.md) has the Railway steps, including claiming the instance.

The server runs its own [housekeeping jobs](/guides/housekeeping) and backup work in the background, so **turn off any host feature that stops an idle service**, such as Railway's Serverless mode.

## What the server needs

The server reads its settings from its environment when it starts. An instance you keep needs these seven:

| Setting | What it's for |
| --- | --- |
| `NODE_ENV` | `production` makes the server refuse to start without the two secrets and the address. |
| `PORT` | The port the server listens on. |
| `SQLITE_PATH` | Where the database file lives. |
| `BLOB_PATH` | Where file contents live. |
| `API_KEY_SALT` | A secret that keys and app tokens are hashed with. |
| `MARFA_AUTH_SECRET` | A secret that signs sign-in cookies and the links the server makes. |
| `MARFA_AUTH_BASE_URL` | The address clients reach the instance at. |

Here they are as an environment file:

```bash title="marfa.env"
NODE_ENV=production
PORT=8600
SQLITE_PATH=/srv/marfa/data/marfa.db
BLOB_PATH=/srv/marfa/data/blobs
API_KEY_SALT=<a secret>
MARFA_AUTH_SECRET=<another secret>
MARFA_AUTH_BASE_URL=https://marfa.example.com
```

With `NODE_ENV=production`, the server refuses to start without the two secrets and the address, and refuses a weak secret. **Outside production it falls back to defaults that suit only a trial.** [Settings](/guides/settings) covers every other setting.

### The data directory

The database and the blobs are the whole of your data. **Put them on storage that survives a restart**: a volume in a container, or a directory on a disk you keep. With the paths above, the directory looks like this once the server has started:

<Files>
  <Folder name="data" defaultOpen>
    <File name="marfa.db" />
    <File name="marfa.db-wal" />
    <File name="marfa.db-shm" />
    <Folder name="blobs" />
    <Folder name="control" defaultOpen>
      <File name="marfa.sock" />
    </Folder>
  </Folder>
</Files>

`marfa.db` is the database. `marfa.db-wal` is SQLite's log of writes not yet moved into the file, and **belongs with it in every copy**; `marfa.db-shm` is an index SQLite rebuilds, which no copy needs. Every upload lands in `blobs/`.

[Back up and restore](/guides/back-up-and-restore) covers copying the directory safely.

### The private socket

`control/marfa.sock` is the instance's private socket. A command run on the same machine, under the account that runs the server, reaches the instance through it with the owner's own authority, and **needs no key**:

```bash
marfa --socket /srv/marfa/data/control/marfa.sock setup open
```

That is how you claim the instance, make the first key and [recover the owner's password](/guides/manage-keys#recover-the-owners-password). **The CLI refuses `--socket` while `MARFA_API_URL` or `MARFA_API_KEY` is set**, so unset them first.

The socket's folder must belong to the server's account and be readable by no one else. **On Linux, install the `acl` package**: the server uses it to check who can reach the socket. `MARFA_CONTROL_SOCKET` moves the socket to another absolute path.

### The secrets

Generate each secret once:

```bash
openssl rand -hex 32
```

**Keep a copy of both secrets outside the data directory, because neither is stored in it.** `API_KEY_SALT` hashes keys and app tokens, and the database holds only the hashes: a server started with another salt refuses every existing key and token with `401 unauthorized`, until it starts again with the original. `MARFA_AUTH_SECRET` signs sign-in cookies and the links the server makes; starting with another value signs out every browser.

### The address

`MARFA_AUTH_BASE_URL` is the URL your devices reach the instance at. The server uses it as the OAuth issuer and in every link it makes. The owner can claim the instance and sign in **only when it is `https`, or `http` on `localhost`, `127.0.0.1` or `[::1]`**.

You reach an instance in one of three ways:

- **On your local network**, anything on the same network reaches the machine directly.
- **Over Tailscale**, which these docs suggest, your phones and computers reach it from anywhere, over a private network of your own.
- **Through a Cloudflare Tunnel**, it has a public address on a domain you own, without opening a port on your network.

When a proxy or tunnel sits in front of the server, **tell the server which client address to believe**: `TRUSTED_PROXY_CIDRS` names the proxy's address ranges, or `TRUSTED_PROXY_HEADER` names a header the platform's edge overwrites with the client's address. Without either, the server ignores `X-Forwarded-For`, and every request seems to come from the proxy.

### An object store

Name an S3-compatible bucket with `S3_BUCKET` and the other `S3_` settings, and the server keeps a second copy of every blob there. In the container, the bucket also receives the database, so the instance can be rebuilt from the bucket alone.

**Put the bucket on a different site from the instance.** A link the bucket signs serves a blob from the bucket's own host, without the protections the instance adds to its own downloads, so a bucket under the instance's domain could let an uploaded HTML file run as a page of the instance.

## Run it in a container

<Steps>
<Step>

### Build the image

From a clone of the repository:

```bash
docker build -f deploy/Dockerfile --build-arg VERSION_SHA=$(git rev-parse HEAD) -t marfa-server .
```

</Step>
<Step>

### Start it

Put `API_KEY_SALT`, `MARFA_AUTH_SECRET`, `MARFA_AUTH_BASE_URL` and the `S3_` settings in `marfa.env`, kept out of any repository. **Leave out `NODE_ENV`, `PORT` and the paths**: the image sets them, with the database, the blobs and the socket under `/data`. Then start the container with one volume there:

```bash
docker run --name marfa -d --restart unless-stopped -p 8600:8600 \
  -v marfa-data:/data --env-file marfa.env marfa-server
```

Without `S3_BUCKET`, the container runs the server alone and says so in its log: that's a trial, because nothing leaves the machine.

</Step>
<Step>

### Claim the instance

The image includes the CLI. Ask it for a single-use setup link, and open the link in your browser to choose the owner's email and password:

```bash
docker exec marfa marfa --socket /data/control/marfa.sock setup open --no-browser
```

The CLI prints the link as `url`, at the address `MARFA_AUTH_BASE_URL` names. **It works once, for five minutes.**

</Step>
</Steps>

## Run it without a container

In a clone of the repository, build the server:

```bash
pnpm install --frozen-lockfile
pnpm --filter "@withmarfa/server..." build
```

Then start it from `packages/server`, with the settings in its environment:

```bash
cd packages/server
node dist/index.js
```

Claim it with `marfa --socket <path> setup open`, as the account that runs the server. **The container is the tested route**; this suits a computer you own, under a supervisor such as launchd or systemd.

## Keep it running

`GET /health` answers without a credential. It answers `503` when the database, a write, the disk or blob storage is down, and `200` otherwise, a degraded component included. **Point your supervisor or monitor at it**; the container checks it every 30 seconds.

`SIGTERM` or `SIGINT` stops the server within eight seconds, so **give it ten before a runtime kills the process**.

When the server can't start, its exit status tells your supervisor whether to try again:

- `1` is a failed start that a restart may mend, such as a port in use. A setting outside its rules is reported this way too, with every wrong setting named in the log.
- `78` means the database was written by another build. The server changed nothing, and starting it again meets the same refusal, so **don't restart on `78`**: [Upgrade](/guides/upgrade) says what to do. The container doesn't exit on `78`; it stays up and unhealthy with the reason in its log, so a restart policy can't loop on it.

A server that crashes can leave its socket file behind. On restart, the server replaces a socket that refuses connections. If another listener accepts connections there, the new start refuses and preserves it: check which process is running rather than removing its socket.

The rules behind this page are in the [instance chapter](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md) of the contract, and the container recipe is described in the [deployment guide](https://github.com/withmarfa/marfa/blob/main/deploy/README.md).
