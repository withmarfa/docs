When Marfa refuses a request, it says why in a form a program can act on: a stable code, a message for people, and details that name what went wrong. Branch on the code, never the message. Each operation's page lists the codes that operation can return, and a tool on the [Marfa MCP server](/reference/marfa-mcp-server#tool-errors) answers the same codes.

## The shape of a refusal

A refusal is a JSON body holding one `error` object. Here a key that may read `core.note` but not write it tries to create a note. A key with no grant on the type gets `No access to type "core.note"` instead, so branch on the code:

```http title="Response"
HTTP/1.1 403 Forbidden
Content-Type: application/json
X-Error-Code: type_not_permitted
X-Request-ID: 01a1f14d-e3b6-7626-aab1-d8ee63685943

{ "error": { "code": "type_not_permitted", "message": "Write access to type \"core.note\" denied", "details": { "grant": { "kind": "type", "name": "core.note", "level": "write" } } } }
```

- **`code`:** one of the codes below, and the value to branch on.
- **`message`:** a sentence for people. It can change.
- **`details`:** an object whose members depend on the refusal, when there is one.
- **`X-Error-Code`:** the code again, so a client or a proxy can read it without parsing the body.
- **`X-Request-ID`:** on every answer. Quote it when you [ask for help](/get-help). Send your own of 1 to 128 letters, digits, underscores and hyphens and Marfa answers with it, except under `/inbound/`.

A few answers differ from this shape:

- A `HEAD` request gets the status and headers with no body.
- `409 version_conflict` and `409 ancestor_unavailable` also carry the item as it is now, in `current` beside `error`, as [Update an item](/reference/api/items/updateItem) shows.
- A page under `/auth/` refuses in plain text or as an HTML page, and an OAuth endpoint under `/oauth/` refuses in the shape its RFC sets ([`errors/envelope`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/errors.md#errorsenvelope)).
- A request whose `Accept` names `text/html` before `application/json` gets an HTML page of the refusal's status, still with `X-Error-Code` ([`errors/html-page`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/errors.md#errorshtml-page)).

## What a refusal tells you

- **A missing grant:** a `403` that a grant could lift names it in `details.grant`, with its `kind` (`type`, `edge_type` or `extension`), its `name`, and the `level` the operation needed, `read` or `write`. That's what the key lacks: [Manage keys](/use/manage-keys#narrow-a-key) says who can give it. A `403` that no grant could lift, such as a write to a `system.*` type through the item operations, names none.
- **Data the credential can't read:** never described. An item of a type the credential can't read answers `404 item_not_found`, exactly as an item that doesn't exist does. A credential learns its reach from [Get an overview](/reference/api/instance/getOverview), and a key from [Get the current API key](/reference/api/api-keys/getCurrentKey). [Access](/build/access) explains why.
- **An item in the bin:** a read or a change answers `404 item_not_found` with `"details": { "trashed": true }` when the credential may read the item's type. Read it with `state=trashed`, or restore it before you change it.
- **An edge rule:** `400 edge_constraint_violation` names the rule in `details.constraint`, such as `duplicate` for a second edge of the type between the same two items, or `cardinality` for a second edge at an end that holds one. A writer that sends an edge again after an uncertain answer can treat `duplicate` as success. A working copy gives the same code before it queues the write ([Write edges in a working copy](/build/write-in-a-working-copy#write-items-and-edges)).

## Retrying

These codes mean the same request can succeed later:

- `write_contention` (`503`): the write waited the five seconds that `details.budget_ms` names for the store's lock, or a restore is running (`details.reason` is `restore_running`, with a `Retry-After`). Send it again unchanged. A write behind a bulk page that keeps writing waits for the page instead, so allow for a long page in its timeout.
- `version_conflict` (`409`): the item changed since the version the write named. Merge your change into the item in `current`, then send it again naming that item's version.
- `idempotency_key_in_flight` (`409`): the first request with this `Idempotency-Key` hasn't answered yet. Send it again with the same key.
- `rate_limited` (`429`): past a limit for the current window. Wait the seconds that `Retry-After` and `details.retry_after_seconds` name.
- `housekeeping_job_running` (`409`): the job is in the middle of a run. Run it again once that run ends.
- `stream_capacity_exhausted` (`503`): the instance is serving as many live event streams as it allows. Open the stream again later.
- `blob_store_unavailable` (`503`): a blob store failed or didn't answer in time. Nothing was written.
- `too_many_connections` (`503`): the instance, or your address, holds as many open connections as it allows.
- `inbound_unavailable` (`503`): an inbound endpoint can't take a delivery now. The sender sends it again after `Retry-After`.
- `insufficient_storage` (`507`): the volume has no room. Send it again once the volume has room, after reading what it changed if `details.write_outcome` is `unknown`.

With `Idempotency-Key`, a retried write is safe: Marfa answers a repeat with the first answer and doesn't write again. Without one, read what the first request changed before you send a write again.

`500 internal_error` is a fault in the server, and the answer says nothing of what failed. Read what the request changed before you retry, and quote its `X-Request-ID` when you [ask for help](/get-help).
