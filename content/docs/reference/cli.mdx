The CLI is the `marfa` program. **Every operation in the API has a command,** such as `marfa items list`, except [Authorize an app](/reference/api/apps/authorizeApp), which an app opens in a person's browser: `marfa login` signs in with a device code instead. **`marfa operations` lists each operation** in the [API reference](/reference/api) beside its command, without a request. [Work from the command line](/use/command-line) shows the everyday commands. **`marfa <command> --help` is the reference for each command,** with every option, for the version you have. This page covers what every command shares.

The CLI also does work the API doesn't: `marfa server` ([Install Marfa](/run/install)), `marfa folders` ([Sync a folder](/use/sync-a-folder)), `marfa device` ([Write in a working copy](/build/write-in-a-working-copy)), `marfa types scaffold` ([Define a type](/build/define-a-type)) and `marfa docs` ([Docs MCP server](/reference/docs-mcp-server)).

## Install

On macOS with Apple silicon, or Linux on x86_64 or arm64, the install script picks the archive for your machine, checks it against the release's checksum file, and puts `marfa` and `marfa-server` side by side in `~/.local/bin`:

```bash
curl -fsSL https://raw.githubusercontent.com/withmarfa/marfa/main/scripts/install.sh | sh
marfa --version
```

- **When that folder isn't on your `PATH`, the script prints the `export PATH=` line to add** to your shell's startup file. Until you add it and open a new shell, `marfa` isn't found.
- `MARFA_VERSION` installs another release, and `MARFA_INSTALL_DIR` another folder. Intel Macs aren't supported.
- Homebrew installs the same two programs: `brew install withmarfa/tap/marfa`.

### Update the CLI

On a computer that runs no server, run the script again, or `brew upgrade marfa`. **On the server's own machine, leave the server's programs as they are:** once they're replaced the server refuses to start until [`marfa server upgrade`](/run/upgrade) moves it. Install the newer CLI into a folder of its own, off your `PATH`, and run it by its path:

```bash
curl -fsSL https://raw.githubusercontent.com/withmarfa/marfa/main/scripts/install.sh | MARFA_INSTALL_DIR=~/marfa-cli sh
~/marfa-cli/marfa status
```

The macOS programs are also signed with a Developer ID and notarized by Apple.

## Connect to a server

A command that talks to an instance takes the server's address and a credential from the first of these given:

1. **`--profile`:** a [profile](#name-a-server-with-a-profile). Refused beside `--url` or `--key`, and it reads none of `MARFA_API_URL`, `MARFA_API_KEY` and `MARFA_PROFILE`.
2. **`--url` or `--key`,** with no `MARFA_PROFILE` read beside either.
3. **`MARFA_PROFILE`,** a profile for a whole shell. Refused beside a `MARFA_API_URL` or `MARFA_API_KEY` that isn't empty, so a key exported for one server never reaches another.
4. **No profile:** the variables, then the keychain:

| What it needs | First | Then | Then |
| --- | --- | --- | --- |
| A server | `--url` | `MARFA_API_URL`, when not empty | The current server: the last you signed in to or kept a key for |
| A credential | `--key` | `MARFA_API_KEY` | What the keychain holds for that server |

**A key from `--key` or `MARFA_API_KEY` needs its server named,** so it is never sent to the current server by mistake. A key or token sent over plain `http` to another machine gets a warning on standard error, which `--allow-http` or `MARFA_ALLOW_HTTP=1` drops.

### Name a server with a profile

A profile is a section of a file you write by hand, `profiles.toml`, that names a server and where its key comes from. It isn't the owner's profile, which `marfa profile` changes. **A profile's key goes only to its own server.** The file is `~/Library/Application Support/Marfa/profiles.toml` on macOS, and `$XDG_CONFIG_HOME/marfa/profiles.toml`, or `~/.config/marfa/profiles.toml`, elsewhere:

```toml title="profiles.toml"
[demo]
url = "http://localhost:8600"

[example]
url = "https://marfa.example.com"
key_command = ["op", "read", "op://Private/Marfa/key"]
```

Pick one with `--profile example`, or for a shell with `export MARFA_PROFILE=demo`.

- **Without `key_command`, the key is the keychain's** for that server: `marfa login --profile demo` signs in to it, and `marfa keys keep --profile demo` keeps a key for it.
- **With `key_command`, the CLI runs it and reads the key from what it prints:** a program and its arguments, run with no shell and no standard input, at most once in a run, printing the key alone on one line within 60 seconds and exiting 0. It can't use the terminal. `login` without `--print-token`, `logout`, `keys keep` and `keys forget` refuse such a profile.
- **The CLI refuses a file others can change,** naming the `chmod` or `chown` that fixes it, and a field it doesn't know.
- **`--socket`, `marfa server` and `marfa types scaffold` refuse `--profile`.**

### Keep a credential in the keychain

The keychain holds one credential for each server, and only what these commands put there. A locked, missing or unreadable keychain ends a command with exit code 4, `no_keychain`. [Manage keys](/use/manage-keys) shows how to make a key to keep.

| Command | What it does |
| --- | --- |
| `marfa login` | Signs in as an app with a [device code](/build/connect-an-app#connect-with-the-device-flow) you approve on the server's page, and keeps the app's token. Refused while a key is kept for that server. |
| `marfa logout` | Revokes the token and forgets it. |
| `marfa keys keep` | Checks a key you already have with the server, then keeps it. |
| `marfa keys forget` | Forgets a kept key, without revoking it. |

**Without the keychain,** for a script, a CI job or an agent, pass `--no-keychain` or set `MARFA_NO_KEYCHAIN=1`: the CLI reads and writes nothing there, and a command that names no server is refused. Every command needs a profile with a `key_command`, or a server and key from `--url` or `MARFA_API_URL` and `--key` or `MARFA_API_KEY`. `login --print-token` prints the token set, and `logout` revokes the token passed as the key.

**On macOS, `MARFA_KEYCHAIN` names a keychain file** for a run with nobody to answer a prompt. It must exist: make one with `security create-keychain -p '' <path>`. The folder watch reads each folder's credential from the keychain: where nobody signs in to unlock it, give it [a key file](/use/manage-keys#a-key-for-a-folder-watch).

### Use the private socket

On the instance's own machine, as the account that runs the server, `--socket <path>` acts with the machine's own authority instead of a credential, through [the private socket](/run/run-on-a-server#the-private-socket). **Every owner task works through it,** such as `marfa setup status`, `marfa keys list` and `marfa config get`, and claiming the instance and recovering the owner's password need it.

- **The socket carries no key,** so item properties, edges, tags, search, counts, events, exports and `marfa overview` are refused `401 unauthorized`, with exit code 5.
- **It can't be combined with a profile, a server or a key:** unset `MARFA_API_URL`, `MARFA_API_KEY` and `MARFA_PROFILE` first.
- Commands that use no server or keep a credential refuse it, such as `login`, `server`, `device`, `docs`, `types scaffold` and every `folders` command except `folders inventory`.

## Check which server a command reaches

Before a command first sends a request that can change data, the CLI prints `marfa: writing to <server>` on standard error, with `(profile <name>)` after it where a profile named the server. **A read prints nothing,** and neither does signing in. `marfa whoami` asks the server a command would reach, and prints the server, the instance with its name and release, and the credential and where it came from:

<Terminal>

```bash
marfa whoami
```

```text
server https://marfa.example.com
instance 01a1f11d-c2f1-7630-9670-c83bbe952280 (Marfa 0.0.89)
a key named laptop from MARFA_API_KEY
```

</Terminal>

Under an app's token, `whoami` also lists what the owner approved, and `marfa keys list` and `keys current` print a key's access the same way. `marfa overview` shows what the credential can reach, and needs no type access.

## Output

- **`--json` prints the answer as JSON.** A list prints `{"data": [...], "next_cursor": ...}`, and a command for a paged operation takes `--limit`, `--cursor` and `--all`.
- **Bold and color are for a person only:** none on a stream that isn't a terminal, with `NO_COLOR` set, with `TERM` of `dumb`, or under `--json`.
