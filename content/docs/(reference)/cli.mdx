The CLI is the `marfa` program. **Every operation in the API has a command**, such as `marfa items list`, and most AI agents work with Marfa through it. It also does work the API doesn't:

- `marfa device` keeps a [working copy](/devices) of part of an instance, as [Write in a working copy](/build/write-in-a-working-copy) shows.
- `marfa server` installs, upgrades and removes a server in Docker on this machine, as [Install with the CLI](/run/install) shows.
- `marfa folders` keeps part of an instance as files in a directory, as [Sync a folder](/run/sync-a-folder) shows.
- `marfa types scaffold` prints a starting definition for a type without a server, as [Define a type](/build/define-a-type) shows.
- `marfa docs` searches these docs from the terminal, as [Docs for agents](/docs-for-agents) shows.

## Install

Each release of Marfa carries the CLI as four archives, for macOS on Apple silicon and Intel and for Linux on x86_64 and aarch64, and one checksum file, `marfa-<version>-checksums.txt`, that lists all four.

<Tabs items={["macOS", "Linux"]}>
<Tab value="macOS">

Install it with Homebrew:

```bash
brew install withmarfa/tap/marfa
marfa --version
```

Or download the release for Apple silicon in the terminal:

<include cwd>src/generated/cli-download.md</include>

An Intel Mac uses the archive that ends in `darwin-x86_64.tar.gz` instead.

</Tab>
<Tab value="Linux">

Download the archive for your machine from the [release](https://github.com/withmarfa/marfa/releases/latest). It ends in `linux-x86_64.tar.gz` or `linux-aarch64.tar.gz` and holds one file, `marfa`. Check it against the checksum file, then put `marfa` on your `PATH`:

```bash
sha256sum --check --ignore-missing marfa-*-checksums.txt
tar -xz -f marfa-*-linux-x86_64.tar.gz
sudo mv marfa /usr/local/bin/
marfa --version
```

To build it from source, install Git and a current Rust toolchain from [rustup](https://rustup.rs), then:

```bash
git clone https://github.com/withmarfa/marfa.git
cd marfa
cargo install --locked --path core/marfa-cli
marfa --version
```

Cargo puts `marfa` in `~/.cargo/bin`, which rustup adds to your `PATH`. A clone follows `main`, which can be ahead of the release these docs describe.

</Tab>
</Tabs>

On either system, the install script picks the archive for your machine, checks it against the checksum file, and puts `marfa` in `~/.local/bin`. Set `MARFA_VERSION` to install a release other than the latest, and `MARFA_INSTALL_DIR` to install somewhere else:

```bash
curl -fsSL https://raw.githubusercontent.com/withmarfa/marfa/main/scripts/install.sh | sh
```

**When that folder isn't on your `PATH`, the script prints the `export PATH=` line to add** to your shell's startup file. Until you add it and open a new shell, `marfa` isn't found, such as on a Linux system whose profile leaves `~/.local/bin` out.

With Docker installed, [`marfa server install`](/run/install) sets up a server on the same machine.

## Connect to a server

A command that talks to an instance needs the server's address and a credential. The CLI takes both from the first of these that is given:

1. **`--profile`**: a [profile](#name-a-server-with-a-profile), which holds a server and where its key comes from. It's refused beside `--url` or `--key`, and it reads none of `MARFA_API_URL`, `MARFA_API_KEY` and `MARFA_PROFILE`.
2. **`--url` or `--key`**: as in the table below, and the CLI reads no `MARFA_PROFILE` beside either.
3. **`MARFA_PROFILE`**: a profile for a whole shell. It's refused beside a `MARFA_API_URL` or `MARFA_API_KEY` that isn't empty, so a key exported for one server never reaches another.
4. **No profile**: the variables and the keychain, in this order:

| What it needs | First | Then | Then |
| --- | --- | --- | --- |
| A server | `--url` | `MARFA_API_URL`, when it isn't empty | The current server: the one you last signed in to or kept a key for |
| A credential | `--key` | `MARFA_API_KEY` | What the keychain holds for that server |

**A key from `--key` or `MARFA_API_KEY` needs its server named** with `--url` or `MARFA_API_URL`. Without one, the command ends with exit code 2 and the key is never sent to the current server. Prefer the variable to `--key`: a command line is readable by other users of the machine and stays in your shell history.

### Name a server with a profile

A profile is a section of a file you write by hand, `profiles.toml`, that names a server and where its key comes from, as the contract's [profile rules](https://github.com/withmarfa/marfa/blob/main/conformance/spec/device.md#profiles) state. It isn't the owner's profile, which `marfa profile update` changes. **A profile's key goes only to its own server.** The file is `~/Library/Application Support/Marfa/profiles.toml` on macOS, and `$XDG_CONFIG_HOME/marfa/profiles.toml`, or `~/.config/marfa/profiles.toml` where that isn't set, elsewhere. Name each profile for the instance it reaches:

```toml title="profiles.toml"
[demo]
url = "http://localhost:8600"

[example]
url = "https://marfa.example.com"
key_command = ["op", "read", "op://Private/Marfa/key"]
```

Pick one for a command with `--profile`, or for a whole shell with `MARFA_PROFILE`:

```bash
marfa --profile example items list
export MARFA_PROFILE=demo
```

- **Without `key_command`, the key is the keychain's** credential for that server. `marfa login --profile demo` signs in to it, and `marfa keys keep --profile demo` keeps a key for it, read from standard input.
- **With `key_command`, the CLI runs it and reads the key from what it prints.** It's a program and its arguments, run without a shell and with no standard input, when a request first needs the key and at most once in a run. It must print the key alone on one line, finish within 60 seconds and exit with 0. It can't use the terminal, so a program that asks for a password must ask some other way, as a password manager's own window does. `login` without `--print-token`, `logout`, `keys keep` and `keys forget` refuse such a profile, because it never reads the keychain.
- **The CLI refuses a file that others can change**: one that belongs to another user, or that its group or others can write, or whose folder they can write. Whoever can change the file can name a program the CLI runs as you. The refusal names the `chmod` or `chown` that fixes it. It refuses a field it doesn't know too, so a misspelled `key_command` can't leave a profile on the keychain unseen.
- **`--socket`, `marfa server` and `marfa types scaffold` refuse `--profile`**, since none of them uses a server's address and key. `--socket` refuses `MARFA_PROFILE` too.

### Keep a credential in the keychain

The keychain holds one credential for each server, and only what these commands put there:

| Command | What it does |
| --- | --- |
| `marfa login` | Signs in as an app with the [device grant](/build/authenticate#connect-a-command-line-app): you approve what it may reach on a page on the server, and it keeps the app's token. It refuses while a key is kept for that server. |
| `marfa logout` | Revokes the token and forgets it. |
| `marfa keys keep` | Checks a key you already have with the server, then keeps it. It sends the key, so a key from `MARFA_API_KEY` needs the server named. |
| `marfa keys forget` | Forgets a kept key, without revoking it. |

```bash
marfa login --url https://marfa.example.com
```

[Manage keys](/run/manage-keys) shows how to make a key to keep. A script takes its key from a secrets manager instead, as the next section shows.

### Run without the keychain

For a script, a CI job or an agent, pass `--no-keychain` or set `MARFA_NO_KEYCHAIN` to `1`, `true`, `yes` or `on`. **The CLI then reads nothing from the keychain and writes nothing to it**, so it can't raise a system prompt, and a command that names no server is refused instead of reaching the current one. Every command needs a profile with a `key_command`, or `--url` or `MARFA_API_URL` and the credential from `--key` or `MARFA_API_KEY`. A profile without a `key_command` is refused with `no_credential`.

A command that keeps or removes a credential refuses: `marfa keys keep`, `keys forget`, `logout`, and `login` without `--print-token`. `marfa login --print-token` prints the token set instead of keeping it.

Run the CLI under a secrets manager to give it the key. With 1Password, `MARFA_API_KEY` holds a secret reference, which `op run` replaces with the key:

```bash
export MARFA_API_URL=https://marfa.example.com
export MARFA_API_KEY="op://Private/Marfa/key"
MARFA_NO_KEYCHAIN=1 op run -- marfa items list
```

`MARFA_NO_KEYCHAIN=1 infisical run -- marfa items list` does the same with Infisical, from a secret named `MARFA_API_KEY`.

### Check which server a write reaches

Before a command first sends a request that can change data, the CLI prints `marfa: writing to <server>` on standard error as one plain line, with `(profile <name>)` after it where a profile named the server. A run with writes to two servers prints it once for each. **A read prints nothing**, and neither does signing in. The line is printed with `--json` too, and standard output is unchanged.

### Use another keychain file

On macOS, `MARFA_KEYCHAIN` names a keychain file to use instead of your own, for a run with nobody there to answer a prompt. **The file must already exist**: `marfa login`, `logout`, `keys keep` and `keys forget` refuse a missing one with exit code 4 and `no keychain file is there`, and other commands find nothing kept in it. Make one with `security create-keychain -p '' <path>`. On other systems the CLI refuses the variable with exit code 4.

`marfa folders watch` with no directory, and the login agent `marfa folders autostart` sets up, read each folder's credential from the keychain. The login agent starts outside your shell, so it never sees the variables or options above and reads your own keychain.

For a machine where nobody signs in to unlock the keychain, give the watch a key file instead: `marfa folders watch --key-file <file>`, or `marfa folders autostart on --key-file <file>` for the login agent. [Use a key file instead of the keychain](/run/sync-from-login#use-a-key-file-instead-of-the-keychain) covers both.

### Use the private socket

On the instance's own machine, as the account that runs the server, `--socket <path>` acts with the machine's own authority instead of a credential, through [the private socket](/run/deploy#the-private-socket). These commands need it:

| Command | What it does |
| --- | --- |
| `marfa setup status`, `setup code`, `setup open` | Check and claim the instance. |
| `marfa owner recover`, `owner update`, `owner passkeys`, `sign-ins` | Recover the password and manage the owner's profile, passkeys and sign-ins ([Sign in as the owner](/run/sign-in-as-the-owner)). |
| `marfa items summaries`, `items trash`, `folders inventory` | List item summaries, manage the bin and list the instance's folders. |

- **The socket carries no key**, so the server refuses item properties, edges, tags, search, counts, events and exports through it with `401 unauthorized`, and the CLI exits with `5`. Attachments, bulk job status and removing an unused registered type work through it.
- **It can't be combined with a profile, a server or a key**, from an option or the environment, so unset `MARFA_API_URL`, `MARFA_API_KEY` and `MARFA_PROFILE` first.
- `marfa login`, `logout`, `keys keep`, `keys forget`, `server`, `device`, `docs`, `types scaffold` and every `folders` command except `folders inventory` refuse it.

## Color and piped output

The CLI draws bold and color only for a person: when the stream is a terminal, `NO_COLOR` is unset or empty, `TERM` isn't `dumb`, and the command wasn't given `--json`. **A stream that is piped or redirected, or a command given `--json`, gets no escape characters from the CLI.** Each stream is judged alone, so a refusal on a piped standard error stays plain while the answer on a terminal is drawn. A drawn word keeps its text: color never says what the words don't.

## Find a command

`marfa --help` lists the commands, and `marfa <command> --help` shows what a command does and every option it takes, for the version you have. `marfa operations` lists each operation in the [API reference](/api-reference) beside the command that reaches it:

<Terminal>

```bash
marfa operations
```

```text
getInstance                      marfa status
getInstanceMetrics               marfa metrics
createItem                       marfa items create
listItems                        marfa items list
getItemStats                     marfa items stats
getItem                          marfa items get
```

</Terminal>

## Check what a command will use

**When a command reaches the wrong instance or is refused, start with `marfa whoami`.** It asks the server a command would reach, and prints the server, the instance with its name, release and build commit, and where the credential came from:

<Terminal>

```bash
marfa whoami
```

```text
server https://marfa.example.com
instance 01a15f23-b450-79e7-90ac-978f5ec4b38b (Marfa 0.0.20, build 03dd2018d3621d73465b9ea1d1fbb38c1ea756af)
a key from MARFA_API_KEY
```

</Terminal>

With a profile, the first line ends with `(profile example)`, and the credential line says the credential came from `the profile's key_command` or `the keychain`.

The instance name defaults to Marfa, which [Settings](/run/settings#change-settings-while-it-runs) changes; a server built from a clone shows only the commit. Under an app's token, `marfa whoami` also lists what the owner approved, in the words of the approval page: each type as No access, Read only or Read and edit, and each permission by its title. `marfa keys list`, `current`, `create` and `update` print a key's access the same way, and `--json` prints it structured.

## See what a credential can reach

`marfa overview` shows what the instance holds that the credential can reach: types with item counts, edge types, top tags, views and folders, and what the credential may do. Each list is capped. **It needs no type access**, so run it first with a new key. The private socket can't read it. [Get an overview](/api-reference/instance/getOverview) is the operation.

## Move several items to the bin

`marfa items delete` takes up to 20 item IDs and moves them to the bin, **all of them or none**. Each takes the items under it, such as a task's subtasks, and every comment or attachment whose hosts all go to the bin. Run it with `--dry-run` to see what it would move and a digest, then send the digest, so nothing moves if that has changed:

```bash
marfa items delete <id> <id> --dry-run
marfa items delete <id> <id> --digest <digest>
```

A changed plan is refused with `409 trash_plan_changed`. `marfa items restore <id>` brings an item back. [Preview trashing items](/api-reference/items/previewItemTrash) and [Trash items](/api-reference/items/trashItems) are the operations.
