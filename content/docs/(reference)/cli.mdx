The CLI is the `marfa` program, Marfa's command-line tool. **Everything the API does has a command**, such as `marfa items list` for listing items, so anything you can build, you can also do from a terminal. It's also how most AI agents work with Marfa.

The CLI does more than send requests. `marfa device` keeps a [working copy](/devices) of part of an instance, `marfa folders` keeps part of it as files in a directory and can keep them in step from login, `marfa types scaffold` prints a starting definition for a type without a server, and `marfa docs` searches these docs from the terminal.

Each release of Marfa carries the CLI for macOS on Apple silicon. On Linux, build it from source.

You need Git and a current Rust toolchain from [rustup](https://rustup.rs). Clone Marfa and install the CLI from the clone:

```bash
git clone https://github.com/withmarfa/marfa.git
cd marfa
cargo install --locked --path core/marfa-cli
marfa --version
```

Cargo puts `marfa` in `~/.cargo/bin`, which rustup adds to your `PATH`.

These docs follow Marfa's `main` branch, which can be ahead of the latest release. If the CLI says a command doesn't exist, build it from source to get it.

## Connect to a server

A command that talks to an instance needs the server's address and a credential. **The CLI can keep both for you**, so a bare command such as `marfa status` knows where to go. There are two ways to give it a credential.

**Sign in as an app** with `marfa login`. The CLI shows a code and opens a page on the server, where you sign in as the owner and approve what it asks for. The CLI asks for more than reading, so the page asks you to sign in again if you signed in more than five minutes ago and haven't approved the CLI for those scopes before. It then keeps the app's token in the keychain:

```bash
marfa login --url https://marfa.example.com
```

```text
Open https://marfa.example.com/auth/device?user_code=V3Z5RBBC and enter the code V3Z5RBBC
Waiting for the approval...
```

The token holds only the scopes you approve. The CLI asks for everything an owner can grant except `instance.read`, `instance.maintain`, `connectors.manage`, `blobs.manage` and `keys.manage`, so the commands that need one of those need a key instead. `marfa logout` revokes the token and forgets it.

Or **keep a key** you already have with `marfa keys keep`. It reads the key from `MARFA_API_KEY`, or, if that isn't set, from standard input, so you can paste it and press Return. It checks the key with the server, then keeps it in the keychain.

```bash
marfa keys keep --url https://marfa.example.com
```

**Any valid key is kept**, including one that holds only permissions such as `keys.mint`, `instance.read` or `audit.read` and reaches no type. A key the server doesn't accept, because it's revoked, expired or unknown, is kept nowhere and ends the command with exit code 5. An app's access token isn't a key: the command keeps nothing and exits 1, because the token ends within the hour and `marfa login` keeps a sign-in that renews it.

[Manage keys](/guides/manage-keys) shows how to make a key that reaches only what you need.

Either way, the server you sign in to or keep a key for becomes the current server, which a command uses when nothing names another. The keychain holds one credential for each server. For each command, the CLI takes the first server and the first credential that's set, in this order:

| What it needs | First | Then | Then |
| --- | --- | --- | --- |
| A server | `--url` | `MARFA_API_URL` | The current server |
| A credential | `--key` | `MARFA_API_KEY` | What the keychain holds for that server |

So `MARFA_API_URL` and `MARFA_API_KEY` override what the keychain holds, which suits a script. Prefer them to `--key`: other users of the machine can read a command line, and it stays in your shell history. On macOS, `MARFA_KEYCHAIN` names a keychain file to use instead of your own, for a run with nobody there to answer a prompt. **The file must already exist.** The CLI doesn't create it, and a missing file ends the command with exit code 4 and `no keychain file is there`. Make an empty one with `security`, then keep the key in it:

```bash
security create-keychain -p '' "$HOME/marfa.keychain-db"
export MARFA_KEYCHAIN="$HOME/marfa.keychain-db"
MARFA_API_KEY=<the key> marfa keys keep --url https://marfa.example.com
```

On other systems the CLI refuses the variable. A watch that runs without you reads the keychain too: `marfa folders watch` with no directory, and the login agent `marfa folders autostart` sets up, take each folder's credential from it. Run `marfa keys keep` or `marfa login` for the instance first. The login agent starts outside your shell, so it doesn't see `MARFA_KEYCHAIN` and reads your own keychain. [Keep folders running](/guides/keep-folders-running) covers the watch.

## Find a command

**The CLI explains its own commands.** `marfa --help` lists them, and `marfa <command> --help` shows what a command does and every option it takes, for the version you have:

```bash
marfa items --help
marfa items list --help
```

To find the command for an operation in the [API reference](/api-reference), `marfa operations` lists each operation beside the command that reaches it:

```bash
marfa operations
```

```text
getInstance                      marfa status
getServerMetrics                 marfa metrics
createItem                       marfa items create
listItems                        marfa items list
```

## Check what a command will use

`marfa whoami` asks the server a command would reach, and says which instance answered and where the credential came from:

```bash
marfa whoami
```

```text
server https://marfa.example.com
instance 01a12312-7e62-70f2-a656-1c9eef418991 (Marfa 0.0.14, build 37eff92)
a key from the keychain
```

The instance name comes from its live configuration and defaults to Marfa. [Settings](/guides/settings#change-settings-while-it-runs) shows how to change it. After the name comes the **release** the server was built as, then the commit it was built from. `marfa status` names them the same way. A server built from a clone shows only the commit, because it has no release.

When a command reaches the wrong instance, or is refused, start here.

## On the instance's own machine

On the computer that runs the instance, logged in as the account that runs the server, the CLI can act with the machine's own authority instead of a credential. Pass `--socket` with the path of the server's private socket, which is `control/marfa.sock` in the server's data directory:

```bash
marfa --socket /path/to/data/control/marfa.sock setup status
```

```json
{
  "claimed": true,
  "owner_id": "pBOgdR5hPFLKrgGqkgKcIsRXxFtBNS6o",
  "generation": null
}
```

That's how the owner makes the first key, as in the [Quickstart](/quickstart), and recovers a lost password. A few commands work only this way: `marfa setup status`, `marfa setup code`, `marfa setup open`, `marfa owner recover`, `marfa owner update`, the `marfa owner passkeys` commands, and the `marfa sign-ins` commands.

`marfa owner passkeys add` opens the ordinary owner sign-in page in a browser, where you sign in yourself with the password or a passkey, and then reach the passkey page. Use `--no-browser` to print the sign-in URL instead. The command does not sign you in or make a setup credential. [Authenticate](/guides/authenticate#sign-in-as-the-owner) covers passkey management.

`marfa --socket <path> owner update --email owner@example.com --name "Reader"` changes the owner's sign-in address and display name. `marfa profile update --name "Reader"` uses a key or app token with profile write access instead; it can change name and avatar, never email. [Authenticate](/guides/authenticate#change-the-owners-email-or-name) explains both operations.

**The socket carries no key.** A command given `--socket` refuses to run while `MARFA_API_URL` or `MARFA_API_KEY` is set, and an operation that needs a key, such as `marfa events` or `marfa export`, is refused. Run those without `--socket`, with a key.

## Use it in a script

`--json` prints the answer as JSON on standard output. When a command fails, it prints one JSON object on standard error instead, with the CLI's own error code, the server's status and code where the server refused, and the exit code:

```bash
marfa items get 01a12192-a000-76e3-b129-b55027e21dcb --json
```

```json
{"error":{"code":"not_found","message":"the server refused (404 item_not_found): Item 01a12192-a000-76e3-b129-b55027e21dcb not found","server":{"status":404,"code":"item_not_found","details":null},"retry_after_seconds":null},"exit":1}
```
