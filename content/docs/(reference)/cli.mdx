The CLI is the `marfa` program. **Every operation in the API has a command**, such as `marfa items list`, and most AI agents work with Marfa through it. It also does work the API doesn't:

- `marfa device` keeps a [working copy](/devices) of part of an instance.
- `marfa server` installs, upgrades and removes a server in Docker on this machine, as [Install with the CLI](/guides/install) shows.
- `marfa folders` keeps part of an instance as files in a directory, as [Sync a folder](/guides/sync-a-folder) shows.
- `marfa types scaffold` prints a starting definition for a type without a server, as [Define a type](/guides/define-a-type) shows.
- `marfa docs` searches these docs from the terminal, as [Docs as Markdown](/docs-as-markdown) shows.

## Install

Each release of Marfa carries the CLI as four archives, for macOS on Apple silicon and Intel and for Linux on x86_64 and aarch64, and one checksum file, `marfa-<version>-checksums.txt`, that lists all four.

<Tabs items={["macOS", "Linux"]}>
<Tab value="macOS">

Install it with Homebrew:

```bash
brew install withmarfa/tap/marfa
marfa --version
```

Or download the release for Apple silicon in the terminal:

<include cwd>src/generated/cli-download.md</include>

An Intel Mac uses the archive that ends in `darwin-x86_64.tar.gz` instead.

</Tab>
<Tab value="Linux">

Download the archive for your machine from the [release](https://github.com/withmarfa/marfa/releases/latest). It ends in `linux-x86_64.tar.gz` or `linux-aarch64.tar.gz` and holds one file, `marfa`. Check it against the checksum file, then put `marfa` on your `PATH`:

```bash
sha256sum --check --ignore-missing marfa-*-checksums.txt
tar -xz -f marfa-*-linux-x86_64.tar.gz
sudo mv marfa /usr/local/bin/
marfa --version
```

To build it from source instead, you need Git and a current Rust toolchain from [rustup](https://rustup.rs). Clone Marfa and install the CLI from the clone:

```bash
git clone https://github.com/withmarfa/marfa.git
cd marfa
cargo install --locked --path core/marfa-cli
marfa --version
```

Cargo puts `marfa` in `~/.cargo/bin`, which rustup adds to your `PATH`. A clone follows `main`, which can be ahead of the release these docs describe.

</Tab>
</Tabs>

On either system, the install script picks the archive for your machine, checks it against the checksum file, and puts `marfa` in `~/.local/bin`. Set `MARFA_VERSION` to install a release other than the latest, and `MARFA_INSTALL_DIR` to install somewhere else:

```bash
curl -fsSL https://raw.githubusercontent.com/withmarfa/marfa/main/scripts/install.sh | sh
```

With Docker installed, [`marfa server install`](/guides/install) sets up a server on the same machine.

## Connect to a server

A command that talks to an instance needs the server's address and a credential. For each, the CLI takes the first one that's set:

| What it needs | First | Then | Then |
| --- | --- | --- | --- |
| A server | `--url` | `MARFA_API_URL`, when it isn't empty | The current server: the one you last signed in to or kept a key for |
| A credential | `--key` | `MARFA_API_KEY` | What the keychain holds for that server |

**A key from `--key` or `MARFA_API_KEY` needs its server named** with `--url` or `MARFA_API_URL`. Without one, the command ends with exit code 2 and the key is never sent to the current server. Prefer the variable to `--key`: a command line is readable by other users of the machine and stays in your shell history.

### Keep a credential in the keychain

The keychain holds one credential for each server, and only what these commands put there:

| Command | What it does |
| --- | --- |
| `marfa login` | Signs in as an app with the [device grant](/guides/authenticate#connect-a-command-line-app): you approve what it may reach on a page on the server, and it keeps the app's token. It refuses while a key is kept for that server. |
| `marfa logout` | Revokes the token and forgets it. |
| `marfa keys keep` | Checks a key you already have with the server, then keeps it. It sends the key, so a key from `MARFA_API_KEY` needs the server named. |
| `marfa keys forget` | Forgets a kept key, without revoking it. |

```bash
marfa login --url https://marfa.example.com
```

[Manage keys](/guides/manage-keys#give-a-key-to-a-script-or-agent) covers `marfa keys keep`, and how to give a script a key from a secrets manager.

### Run without the keychain

For a script, a CI job or an agent, pass `--no-keychain` or set `MARFA_NO_KEYCHAIN` to `1`, `true`, `yes` or `on`. **The CLI then reads nothing from the keychain and writes nothing to it**, so it can't raise a system prompt. Every command needs `--url` or `MARFA_API_URL`, and the credential from `--key` or `MARFA_API_KEY`.

A command that keeps or removes a credential refuses: `marfa keys keep`, `keys forget`, `logout`, and `login` without `--print-token`. `marfa login --print-token` prints the token set instead of keeping it.

### Use another keychain file

On macOS, `MARFA_KEYCHAIN` names a keychain file to use instead of your own, for a run with nobody there to answer a prompt. **The file must already exist**: `marfa login`, `logout`, `keys keep` and `keys forget` refuse a missing one with exit code 4 and `no keychain file is there`, and other commands find nothing kept in it. Make one with `security create-keychain -p '' <path>`. On other systems the CLI refuses the variable with exit code 4.

`marfa folders watch` with no directory, and the login agent `marfa folders autostart` sets up, read each folder's credential from the keychain. The login agent starts outside your shell, so it never sees the variables or options above and reads your own keychain. [Keep folders running](/guides/keep-folders-running) covers it.

## Find a command

`marfa --help` lists the commands, and `marfa <command> --help` shows what a command does and every option it takes, for the version you have. `marfa operations` lists each operation in the [API reference](/api-reference) beside the command that reaches it:

<Terminal>

```bash
marfa operations
```

```text
getInstance                      marfa status
getInstanceMetrics               marfa metrics
createItem                       marfa items create
listItems                        marfa items list
getItemStats                     marfa items stats
getItem                          marfa items get
```

</Terminal>

## Check what a command will use

**When a command reaches the wrong instance or is refused, start with `marfa whoami`.** It asks the server a command would reach, and prints the server, the instance with its name, release and build commit, and where the credential came from:

<Terminal>

```bash
marfa whoami
```

```text
server https://marfa.example.com
instance 01a15f23-b450-79e7-90ac-978f5ec4b38b (Marfa 0.0.20, build 03dd2018d3621d73465b9ea1d1fbb38c1ea756af)
a key from MARFA_API_KEY
```

</Terminal>

The instance name defaults to Marfa, and [Settings](/guides/settings#change-settings-while-it-runs) changes it. A server built from a clone shows only the commit. Under an app's token, `marfa whoami` also lists what the owner approved, in the words of the approval page: each type as No access, Read only or Read and edit, and each permission by its title. `marfa keys list`, `current`, `create` and `update` print a key's access the same way, and `--json` prints it structured.

## Use the private socket

On the computer that runs the instance, logged in as the account that runs the server, the CLI can act with the machine's own authority instead of a credential. Pass `--socket` with the server's private socket, `control/marfa.sock` in its data directory:

<Terminal>

```bash
marfa --socket /path/to/data/control/marfa.sock setup status
```

```json
{
  "claimed": true,
  "owner_id": "mPfnOasjLXnMRG6AG6qclGUhdhBetUn6",
  "generation": null
}
```

</Terminal>

That's how the owner makes the first key in the [Quickstart](/quickstart). These commands work only through the socket:

| Command | What it does | Guide |
| --- | --- | --- |
| `marfa setup status`, `setup code`, `setup open` | Check whether the instance is claimed, replace the setup code, and open the browser handoff. | [Quickstart](/quickstart) |
| `marfa owner recover` | Set a new owner password. | [Sign in as the owner](/guides/sign-in-as-the-owner#recover-the-owners-password) |
| `marfa owner update` | Change the owner's email and name, upload the owner's picture from a file with `--avatar`, or remove it with `--clear-avatar`. | [Sign in as the owner](/guides/sign-in-as-the-owner#change-the-owners-profile) |
| `marfa owner passkeys` | Add, list, rename and remove passkeys. | [Sign in as the owner](/guides/sign-in-as-the-owner#manage-passkeys-and-sign-ins) |
| `marfa items summaries` | List item summaries without opening item content. | [Access](/access#who-can-act) |
| `marfa items trash` | List, move, restore and purge items in the trash. | [Housekeeping](/guides/housekeeping#empty-the-bin) |
| `marfa sign-ins` | List, rename and end the sign-ins that can reach the server. | [Sign in as the owner](/guides/sign-in-as-the-owner#manage-passkeys-and-sign-ins) |

`marfa owner picture` writes the owner's picture to the file named by `--output`, or its bytes to standard output, and a key that may read the profile's `avatar` can run it too. A key or an app with profile write access changes the name and the picture with `marfa profile update`, which takes `--name`, `--avatar <file>` and `--clear-avatar`. [Sign in as the owner](/guides/sign-in-as-the-owner#change-the-owners-profile) shows both.

**The socket carries no key.** `--socket` can't be combined with `--url`, `--key`, `MARFA_API_URL` or `MARFA_API_KEY`. An operation that needs a key, such as `marfa events` or `marfa export`, ends with exit code 5, so run it with a key instead. `marfa login`, `logout`, `device`, `docs`, `types scaffold` and local folder commands refuse `--socket`. `marfa folders inventory` is the exception: it reads the owner’s reported folder copies through the socket.
