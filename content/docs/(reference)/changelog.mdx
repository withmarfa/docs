---

Each release of Marfa ships the server and its container image, the CLI for macOS on Apple silicon and Intel and for Linux on x86_64 and aarch64 with a checksum file, a Homebrew formula for the CLI, and the TypeScript SDK on npm. This page lists every release, newest first, with what changed and a link to the full list on GitHub. The Swift SDK's own releases are listed after Marfa's.

**A new build updates the database an earlier build wrote, in place,** after it copies the database to a file beside it, which it keeps until you remove it. Going back to an earlier build means starting it on that copy. [Upgrade](/run/upgrade) shows each step.

## v0.0.45

Released October 28, 2026. [v0.0.45 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.45)

This release fixes the watch of every folder after an upgrade to v0.0.44. The server's database and the API keep the shapes they had in v0.0.44, so an instance needs no export to upgrade.

For folders (upgrade the CLI, or the core embedded in your app, to get these):

- **A watch of every folder takes up a folder whose working copy lacks a table this build adds.** In v0.0.44, `marfa folders watch` with no directory, which the login agent runs, reported every folder that an earlier build had set up as not watched, and tried again without end. It now opens such a folder as its writer, which adds the table, and watches it. A command that only reads a folder still refuses it.
- **A folder held by another process is refused before its working copy is opened.** A watch that finds another process holding a folder changes nothing in that folder's working copy, and reports the folder as held.

## v0.0.44

Released October 28, 2026. [v0.0.44 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.44)

This release reduces the folder watch's work and changes the macOS login agent. **Run `marfa folders autostart on` again** after you upgrade the CLI. The server's database and the API keep the shapes they had in v0.0.43, so an instance needs no export to upgrade.

For folders (upgrade the CLI, or the core embedded in your app, to get these):

- **The macOS login agent no longer sets `ProcessType` to `Background`.** That class starved the watch when every core was busy. The agent sets `Nice` to 10 and `LowPriorityIO` to true instead, which lowers its CPU and I/O priority without that class. An agent written by v0.0.43 keeps the old setting until `marfa folders autostart on` replaces it, and `marfa folders autostart status` says so. Run `on` again with the same options, such as `--key-file`. See [Sync from login](/run/keep-folders-running#sync-from-login).
- **A running watch skips files already in step** when no change affects them. Affected files include the changed item's file, files showing linked items, and files whose links need disambiguating after a name changes. It still renders every file when the working copy's generation or the folder's settings change, more than 4,096 items changed, or a type changed. See [What the watch does while it runs](/run/keep-folders-running#what-the-watch-does-while-it-runs).
- **A watch renders every file once an hour** to check its choice of files. It warns only about files it rewrites that the choice would have skipped. The warning contains `warning: the hourly check rewrote` followed by the file's path.
- **A quiet pass that does the full check reuses the folder's status.** A full pass that finds the folder as the last one left it no longer works out the status again.

## v0.0.43

Released October 28, 2026. [v0.0.43 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.43)

The server's database and the API keep the shapes they had in v0.0.42, so an instance needs no export to upgrade.

For folders (upgrade the CLI, or the core embedded in your app, to get these):

- **A watch can reuse its last pull** when nothing changes and no work remains. Such a pass renders no file, where it rendered every file before.
- **The login agent runs at a lower priority.** `marfa folders autostart on` writes the Linux unit with `Nice=10`, `IOSchedulingClass=best-effort` and `IOSchedulingPriority=7`, and the macOS agent with `ProcessType` set to `Background`, which v0.0.44 replaces. An agent from an earlier build keeps its old settings until `on` replaces it.
- **On Apple platforms a watch runs at utility quality of service.** The thread that calls the watch and the threads it starts give way to foreground work, in the CLI and in an app that embeds the core.
- **`marfa folders autostart status` says when the agent is from an earlier build.** It reports that the agent differs from the one `on` writes now, and that running `on` again with the same options replaces it. `--json` reports it as `outdated`. See [Keep folders running](/run/keep-folders-running#sync-from-login).

## v0.0.42

Released October 27, 2026. [v0.0.42 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.42)

**This release updates a database in place, so an instance on v0.0.38 to v0.0.40 needs no export to upgrade.** Start v0.0.42 on the data directory of one of those builds and the server copies the database, then adds the `type_icons` table that v0.0.41 introduced. A database v0.0.41 wrote already has that shape, so v0.0.42 records its schema version in the file and takes no copy. The API and the working copy keep the shapes they had in v0.0.41. [Upgrade](/run/upgrade) covers the update and the way back.

For running an instance:

- **The server copies the database before it changes it, and keeps the copy.** The copy sits beside the database as `marfa.db.backup-schema-<from>-to-<to>-<time>`, and nothing removes it. The update is one transaction, and the server commits it only if every table it kept holds as many rows as before and the result has the build's own shape. A server stopped partway leaves the database as it was and updates it again at the next start. The log line that says the database was updated carries `schema_from`, `schema_to` and `backup_path`.
- **A build refuses a database it cannot update, and changes nothing in it.** That covers a database a newer build wrote, one whose shape matches no earlier build's schema, a failed update and a disk with less than twice the database's size free. The server opens no port and exits with status `78`. For a shape no build knows, the log says to export with the build that wrote the file and restore into this one, which [Export and restore](/run/export-and-restore) covers.
- **To go back, start the earlier build on the copy, not on the updated database.** Delete `marfa.db-wal` and `marfa.db-shm` first, because SQLite applies a log it finds beside a database file. Writes made after the upgrade aren't in the copy, and with a bucket the copy needs a new `S3_PREFIX`. See [Go back to the earlier build](/run/upgrade#go-back-to-the-earlier-build).
- **`marfa server upgrade` says where the copy is.** It still refuses a release older than the one installed, because an older build doesn't know what a newer one changed. See [Change, upgrade or remove it](/run/install#change-upgrade-or-remove-it).
- **Two test settings are new, `MARFA_TEST_MIGRATION_FAULT` and `MARFA_TEST_FREE_DISK_BYTES`.** Both need `MARFA_TEST_HOOKS`, are for the conformance harness, and have no use on an instance that holds real data. See [Settings](/run/settings).

For folders (upgrade the CLI, or the core embedded in your app, to get these):

- **A file moved to another folder on the same Mac keeps its item and every edit.** The receiving folder binds the moved file to the item, whether or not its query holds the item, and delivers the edits made to the file before the move and after it. Two moves still make a new item in the receiving folder: a Markdown note moved before its `marfa_id` line was written, after which the first folder trashes nothing, and an item the server won't show to the receiving folder. See [Folder safeguards](/run/folder-safeguards#what-removes-a-file-or-an-item).
- **A sweep trashes every file it found missing together.** Files deleted at once are all trashed, whichever the sweep reaches first and whether they link one another. A link line shows the note it names by title, and a note trashed earlier in the same sweep no longer reads as a change made elsewhere. The sweep decides each deletion on everything it read of the item, its version, tags and edges, and queues it only while the working copy still holds exactly that.

## v0.0.41

Released October 27, 2026. [v0.0.41 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.41)

**This release changes the database's shape, so v0.0.41 refuses an existing v0.0.40 database without changing it.** A new `type_icons` table holds the icons the owner chooses for types. v0.0.41 migrates nothing, so to move an instance that holds data, export it with v0.0.40 and restore the archive into a fresh v0.0.41 instance. An archive carries the owner's type icons. The working copy keeps the shape it had in v0.0.40, and v0.0.42 and later builds update a v0.0.40 database in place instead.

For apps and the API:

- **The owner chooses a type's icon.** `PUT /types/{id}/icon` sets it and `DELETE /types/{id}/icon` clears it, as [`setTypeIcon`](/api-reference/types/setTypeIcon) and [`clearTypeIcon`](/api-reference/types/clearTypeIcon). It works on any registered type, a core type or a connector's among them, without replacing the definition. A replacement keeps the choice, and `GET /types/{id}`, `GET /types` and the answer to `PUT /types/{id}` show it as `display_hints.icon` in place of the author's. The owner's session, a local process, and a key with `schema.write` and write on the type may set it; a key without those is refused `403` with `forbidden` or `type_not_permitted`. A type nothing registered answers `404 type_not_found`, and deleting a type discards its icon. Each change is audited as `type.icon.set` or `type.icon.clear`. See [The owner's icon](/catalog/your-own-types#the-owners-icon).
- **An icon is a Lucide name.** `display_hints.icon` takes the kebab-case name of an icon in Lucide 1.61.0, the one release Marfa pins, and every operation that takes a type definition refuses any other name `400 invalid_schema`, naming `display_hints.icon`. Every type Marfa ships has an icon. See [Display hints](/catalog/your-own-types#display-hints).
- **Each display hint comes from the nearest type that sets it.** Before, a type that set any of `title_field`, `body_field` and `icon` lost all of its parent's. Now `GET /types/{id}` answers each hint on its own, so a subtype that sets only some hints may show a different title or body than before. A hint a type doesn't set, written back as the `GET` answered it, isn't stored, and `GET /types` lists the hints each type declares itself. The text in `body_field` is Markdown, which the server stores as sent. See [Change a type](/build/change-a-type).
- **An archive carries the owner's type icons.** `types.ndjson` holds one `type_icon` line for each, and the manifest counts them in `type_icon_count`. A restore sets an icon only for a type that has none from the owner, and answers `type_icons_added`, `type_icons_skipped` and `type_icons_skipped_reasons`, with the reasons `already_set` and `unknown_icon`. See [Restore an archive](/run/export-and-restore#restore-an-archive).
- **Web Page, `core.file.webpage`, holds an HTML page as a file.** It inherits `core.file` and uses the `globe` icon. The enrichment sweep writes the text a person would read in the page, without markup, script or style, as its `extracted_text`, so search finds a page by its words. It stops at the first limit a page passes, which is 8 MiB of source, 512 open elements at one point or `MARFA_ENRICHMENT_MAX_TEXT_CHARS` of text, and keeps the text before it. See [File](/catalog/file).
- **`marfa types set-icon <id> <icon>` and `marfa types clear-icon <id>` set and clear the owner's icon.**

For devices and folders:

- **A device types a file as a Web Page where its MIME type is `text/html` or `application/xhtml+xml`.** `marfa items add` and `marfa items attach` do so when given no `--type`, and a folder does for a nonempty file at an `.html`, `.htm` or `.xhtml` name.
- **A working copy holds each type's icon, the owner's choice included, and reads each hint from the nearest type that sets it.** A catalog that differs from an interrupted hydration's only in an icon is adopted without restarting the hydration.

## v0.0.40

Released October 27, 2026. [v0.0.40 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.40)

The server's database, the API and the working copy keep the shapes they had in v0.0.39, so an instance needs no export to upgrade.

For folders:

- **`marfa folders add` warns when git tracks the directory.** A directory is tracked when it is in a git work tree and that work tree's index holds a file in it. The warning is one line on standard error that begins `marfa: warning: ` and names git and the directory, and the command adds the folder all the same. A directory git ignores, one outside every work tree, and a machine where git can't be run get no warning. See [Add the directory](/run/sync-a-folder#add-the-directory).

For devices and the API:

- **The contract states that a search finds a file by its extracted text.** The server matches a query against the text the enrichment sweep wrote on a file item that isn't in the bin, and a working copy matches the same text once it holds it. Until a file has `extracted_text`, a search finds it by its other properties and tags alone.

## v0.0.39

Released October 26, 2026. [v0.0.39 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.39)

The server's database, the API and the working copy keep the shapes they had in v0.0.38, so an instance needs no export to upgrade.

For apps and the API:

- **Collection, `core.collection`, gathers items of any type.** It requires a `title` and takes a `description`, which is its `body_field`. It declares the `container` role, so items join it through `in-collection` edges and it can hold any item except another container. Every other shipped container is a kind of media. See [Collection](/catalog/collection).

## v0.0.38

Released October 25, 2026. [v0.0.38 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.38)

The server's database, the API and the working copy keep the shapes they had in v0.0.37, so an instance needs no export to upgrade.

For devices and apps:

- **An app can remove its working copy.** The core's Node and Swift bindings gain `removeStore`, which takes the number of writes the server hasn't taken that the person agreed to lose. It removes the copy, whichever build made it, only when the copy holds exactly that number, and otherwise refuses with the new error code `unsent_differs`, which carries the copy's own count. It refuses `reading_handle` while another process writes the copy, and `invalid` for a folder's copy. See [Devices](/devices#the-working-copy).

## v0.0.37

Released October 25, 2026. [v0.0.37 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.37)

**Upgrade the CLI if v0.0.36 refused a folder with `wrong_schema`.** v0.0.36 changed the shape of the working copy, so it refused every folder store an earlier CLI made, and no command could replace one. The server's database and the API keep the shapes they had in v0.0.36.

For folders:

- **A folder replaces a store another build made.** Its next push, pull, scan or watch, including `marfa folders watch` with no directory, replaces the store when the old one names the folder and holds no write still to be sent and no answer the folder has yet to record, and says so on standard error. The new store keeps the folder's record of which file is which item, which files went missing, which writes and placements the server refused and which notes were purged, along with the folder's first sync and the server it was filled from, and is filled again from the server. The replacement changes no file and asks for no new first sync, and the command then sends what changed in the folder while the store was refused. While writes wait, the command leaves the store and the files as they are and names the count, so you can push them with the earlier CLI first. A write the server gave up on, or a refused write the folder doesn't keep against a file, such as the deletion of a file, also keeps the store, and a push leaves it, so remove the folder with the earlier CLI and add it again; a file whose deletion the server never took then comes back. See [Troubleshooting](/run/troubleshooting#staying-in-step).

For working copies, **a copy that replaces one refused with `wrong_schema` keeps the file budget the old copy recorded**, whether a byte count or every file. If the old copy records no budget that can be read, the replacement still happens, with the default budget.

## v0.0.36

Released October 25, 2026. [v0.0.36 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.36)

**Send the writes a working copy holds before you upgrade the CLI or the core embedded in your app.** The working copy gains two columns, so v0.0.36 refuses a copy an earlier build made with `wrong_schema` and says how many writes it holds that the server hasn't taken. Run `marfa device drain` with the earlier build first; [Troubleshooting](/run/troubleshooting#staying-in-step) says what to do with a refused copy. The server's database and the API keep the shapes they had in v0.0.35, so an instance needs no export to upgrade.

For devices and apps:

- **A working copy writes and queries every item field the API takes.** A create takes `state`, a capture location and `edges`, and an edit sets or clears the item's own time. A list narrows by `source` and by when an item last changed, and sorts by a property; a search narrows by tier and by the item's own time. In the CLI, these are new flags on `marfa device items create`, `marfa device items update`, `marfa device items list` and `marfa device search`. In the Node and Swift bindings, a sort's `field` names any sort field, including a property, and its `field` and `direction` are each optional. See [Write and read items in a working copy](/cli#write-and-read-items-in-a-working-copy).
- **A hydration replaces a declared `app.*` type the instance holds in another definition**, if the credential may change it. The hydration report lists the types it replaced in `replaced_types`, and each one the instance refused, with the server's code and message, in `unreplaced_types`. A type outside `app.*`, such as one under `user.*`, is never replaced. See [Declare an app type](/swift-sdk#declare-an-app-type).

## v0.0.35

Released October 24, 2026. [v0.0.35 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.35)

**Change anything that sends view layouts before you upgrade.** A view is a `title`, a `query`, an optional `sort` and an optional `group`. A request that sends `layouts` is refused `400 validation_error`, and a view saved with `layouts` drops them the next time it is changed. In the CLI, `marfa views create` and `marfa views change` take `--sort` and `--group` in place of `--layouts`, `marfa device items list --layout` and `marfa device views groups --layout` are gone, and so is a group's `sum`. The server's database and the working copy keep the shapes they had in v0.0.34, so an instance needs no export to upgrade. See [Save a list as a view](/build/save-a-view).

For apps and the API:

- **A view clears its grouping with `group: null`.** Send it on `PATCH /views/{id}`, or run `marfa views change <id> --version <n> --group null`. A view's `filter` takes an `edge` term, a `backref` term and a `source` term, and a working copy answers a `backref` condition where it holds that edge type whole. See [Read a view offline](/build/read-a-view).
- **Notes, articles and messages no longer require a `body`.** A note can be only a title, and a message only a file. An existing instance stops requiring it the next time it starts, with no migration. See [Items and types](/items-and-types).
- **Every edge type names both of its ends.** `label` names the source end and the optional `reverse_label` names the target end. Without a `reverse_label`, the label names both ends; without a `label`, Marfa makes one from the ID. See [Edges](/catalog/edges).
- **Move every item of a type to another type in one step.** `POST /types/{id}/move`, or `marfa types move <from> <to>`, queues a bulk-action job that moves the items, the trash included. Once none is left, it changes the folders, views and webhooks that name the old type. `DELETE /types/{id}` now refuses while a folder, view or webhook names the type, and lists them in `details.settings`. See [Move items to another type](/build/move-items-to-another-type).

For folders:

- **A folder writes every attached file beside its document**, whether or not the body embeds it, and lists the files no embed places under the document's `has-attachment` line. A file follows its document to another directory, and leaves with it. A second folder on the same Mac that holds the file keeps its own copy, and a folder pull no longer deletes and rewrites it on every pass. See [Files attached to a note](/run/folder-files#files-attached-to-a-note).

## v0.0.33

Released October 24, 2026. [v0.0.33 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.33)

**Upgrade the server to repair folders that still hold `search`.** A folder made in v0.0.29 or earlier can keep that setting on the instance, where changing the local YAML alone cannot remove it. Read its version with `marfa items get <id>`, then run `marfa folders change <id> --version <n> --file settings.json`, naming the intended `query` in the JSON file and leaving out `search`. The accepted change removes the stored `search`; it does not translate it. The server's database, the HTTP API and the working copy keep the shapes they had in v0.0.32, so an instance needs no export to upgrade. See [Change a folder's settings](/run/sync-a-folder#change-a-folders-settings).

For folders:

- **An accepted settings change removes stored settings the folder type no longer declares.** Each setting you send replaces its value whole, and omitted declared settings stay, whether you use flags, `--file` or `--body`. The version rules still apply: changes to different settings can merge, and a collision is refused without removing anything. The old `search` key remains refused in a request, with no alias for `query`. See [Update a folder](/api-reference/folders/updateFolder).

## v0.0.32

Released October 24, 2026. [v0.0.32 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.32)

**Upgrade the CLI or the core embedded in your app to keep using a copy whose cursor aged out.** The server's database, the HTTP API and the working copy keep the shapes they had in v0.0.31, so an instance needs no export to upgrade and a working copy keeps its queue. The CLI and the core's Node and Swift bindings add `stale` to hydration and read completeness, and the hydration report adds `in_place`; apps must handle the added state.

For devices and apps:

- **An aged-out copy keeps answering reads while it fills again.** After `catchup_too_old`, status reports `stale`, item lists and searches mark their answers `stale`, and reads by ID return held rows. Run `marfa device hydrate` with the same instance, reach and slice to refill in place. It updates rows as pages arrive and, only after the fill and replay finish, removes rows and edges it did not bring back, keeping pinned rows and those needed by waiting writes. An interrupted refill removes nothing and can resume. A changed instance, reach or slice, or a server restored behind the held cursor, requires a clearing fill. See [The working copy](/devices#the-working-copy).
- **Queue creates and edits while a copy fills.** A first fill or a stale copy takes new items, files and writes to rows it holds, keeping each write's base version when a later page brings a newer row. A drain sends them once the copy is whole. Writes to unheld rows and direct edge writes are refused with `hydration_incomplete`; body links wait until the server answers the body write. See [The working copy](/devices#the-working-copy).
- **Operations that need a whole copy still wait.** A folder pull, a view's items, search or groups, and edge reads refuse a partial or stale copy with `hydration_incomplete`. A stale copy's drain and catch-up return `copy_expired` with `catchup_too_old` until its refill finishes. A follow waits for a refill already under way, but refuses a stale copy whose refill has not started. See [Troubleshooting](/run/troubleshooting#staying-in-step).

## v0.0.31

Released October 24, 2026. [v0.0.31 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.31)

**Upgrade the CLI or the core embedded in your app to get these device changes.** The server's database and the HTTP API keep the shapes they had in v0.0.30, so an instance needs no export to upgrade. The working copy adds a table for attachments: the new build's writer adds it when it opens a v0.0.30 copy, without replacing the copy or its queue. Open the copy once with that writer before opening it read-only with the new build.

For devices and apps:

- **Read saved views offline.** `marfa device views` lists held views, reads their settings and returns a layout's groups, counts and sums. `marfa device items list` and `marfa device search` take `--view` to select a saved view; their old `--folder` option is removed, with no alias. Item lists follow the layout's sort, and date groups use the device's time zone unless you name one. A query the copy cannot answer whole is refused with a reason. The core's Node and Swift bindings expose the same reads. See [Read a view offline](/build/read-a-view).
- **Create, change and delete views through the core's Node and Swift bindings.** `createView`, `changeView` and `deleteView` send the write to the server at once and never queue it, so they need a connection. A change names the version it starts from and keeps the server's merge and conflict rules. An accepted create or change refreshes the held view when its read-back succeeds; a failed read-back leaves the write accepted, and a later catch-up can refresh the copy. An accepted delete removes the held view. Retry with the same idempotency key when an answer is lost. See [Views written through a copy](https://github.com/withmarfa/marfa/blob/main/conformance/spec/device.md#views-written-through-a-copy).
- **An interrupted hydration resumes from the page it reached, including an every-type slice.** The next hydration of the same slice reads the pages left, then applies events since the fill began. It starts again when the instance, reach, slice or catalog changed, the event log cannot supply the needed history, or the server refuses the saved page cursor. The report gives `resumed`, the `restarted` reason, `pages` read in this call and `pages_total` across the fill. See [The working copy](/devices#the-working-copy).
- **Keep attachments of held items offline.** Files attached to items the copy holds stay outside the file budget, including partial downloads, and a trim leaves them in place while a hydration is unfinished. After hydration and each catch-up, call `marfa device blobs fetch-kept`, or `fetchKept` in the core's Node or Swift binding, to fetch missing attachments smallest first. This fetch is explicit: watching or following does not run it. Status reports held attachments and why others are missing. When a file stops being an attachment, its bytes return to the ordinary cache. See [The working copy](/devices#the-working-copy).

## v0.0.30

Released October 24, 2026. [v0.0.30 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.30)

**A folder's `search` setting is now `query`, and the old key is refused.** Change scripts that say `search` to use `query`, and use the query option in place of the old search option. A folder made before this release can still hold `search` on the instance: editing `.marfa/folder.yaml` alone cannot repair it, and v0.0.30's folder changes leave the old setting stored. Upgrade the server to v0.0.33 or later and follow [Change a folder's settings](/run/sync-a-folder#change-a-folders-settings). The API changes the folder setting's shape and adds view operations. The server's database keeps the schema it had in v0.0.29, so an instance needs no export to upgrade. The working copy changes shape: send its waiting writes with the earlier build before upgrading, then follow [Troubleshooting](/run/troubleshooting#staying-in-step) if it is refused with `wrong_schema`.

For folders:

- **A query can hold both tiers.** Set `query.tier` to `all` to write matching library and feed items as files. A new file without an explicit tier uses `defaults.tier`, or `library` when no default is set. Narrowing the query's tier keeps files whose items leave it as unmatched unless another folder takes them; it never deletes or trashes those items. `marfa folders create` and `marfa folders change` take `--query`. See [Sync a folder](/run/sync-a-folder).

- **Save a list and its layouts as a view.** A `system.view` item holds a title, a query and layouts shared by apps. For running an instance:

- **A type can say how long its feed items stay.** The `feed-expiry` housekeeping job, hourly unless `FEED_EXPIRY_INTERVAL_MS` says otherwise, moves feed items past that window to the trash, counting from when each arrived, which a refresh by natural key doesn't reset. [Housekeeping](/run/housekeeping) covers the job and [Type rules](/catalog/your-own-types#retention-policy) the policy.
- **Feed expiry leaves some items alone.** It skips library and archived items and items brought back from the trash, and holds back an item whose delete would delete one that hasn't expired, or one an edge with `cascade_on_delete: block` protects.

- **A copy stream still sends a hidden item**, marked `listed: false`, so a device's working copy keeps it.
- **The source filter judges an item with no source as `unknown`**, as every read already shows it.
- **Two settings let a test harness control the server.** `MARFA_TEST_HOOKS` and `MARFA_TEST_CLOCK_OFFSET_MS` move the server's clock and set faults through the private socket. **Leave them off on any instance that holds data.**
- **The server refuses to start with test hooks in production.** It refuses when `NODE_ENV` is `production`, as the container image sets, and `MARFA_TEST_HOOKS` is on, and when `MARFA_TEST_CLOCK_OFFSET_MS` is above 0 while hooks are off.

Released October 18, 2026. [v0.0.10 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.10)

For the CLI:

- **Any number of listeners can share one watch of a working copy.** `Core::watch` in the core, `core.watch(onChange, onEnd)` in the Node module and `Core.watch` in the Swift binding hold one event stream, and tell each listener, in order, the changes made after it joined.

- **A watch of a working copy with no server is refused `no_server`**, unless the copy is opened to read.

- **The Swift binding hands over JSON values, not text.** Properties, queued bodies and answers arrive as `JsonValue`, or `JsonObject` for a set of properties.
- **The Swift binding keeps an unreadable row in a read.** A list, search or edge read returns it with empty properties and `unreadableProperties` saying why; a write to it still fails, and a hydration replaces it. The Swift SDK took these changes in [Swift SDK v0.0.18](#swift-sdk-v0018).

Released October 25, 2026. [v0.0.34 on GitHub](https://github.com/withmarfa/marfa-swift/releases/tag/v0.0.34)

- **`WorkingCopy.remove(store:unsent:)` is new, with `MarfaError.unsentDiffers`.** An app removes a store, whichever build made it, once the person agrees to lose the unsent writes it holds. The call removes the store only when its count of unsent writes equals `unsent`, and otherwise throws `unsentDiffers` with the store's own count. An exhaustive `switch` over `MarfaError` needs the case. [Remove a copy](/swift-sdk#remove-a-copy) explains it.
- **`replaceRefused(store:server:fileBudget:)` keeps the old store's file budget when `fileBudget` is `nil`.** [Replace a refused copy](/swift-sdk#replace-a-refused-copy) says what else it keeps.

### Swift SDK v0.0.33

Released October 25, 2026. [v0.0.33 on GitHub](https://github.com/withmarfa/marfa-swift/releases/tag/v0.0.33)

- **Builds against Marfa v0.0.36.** Releases v0.0.25 to v0.0.32 carried the core of the Marfa releases of those days and have no notes of their own.
- **A `Draft` takes every field a create takes.** `state`, `captureLatitude` with `captureLongitude`, and `edges` go in the one write that creates the item. An `Edit` can set or clear the item's own time with `occurredAt` and `clearOccurredAt`.
- **`ListFilters` and `SearchFilters` narrow by more, and `Sort` names a field.** `source`, `updatedAfter`, `updatedBefore`, `occurredAfter` and `occurredBefore` are new on `ListFilters`, `SearchFilters` takes `tier` and the occurred range, and a `Sort` can name `.createdAt`, `.updatedAt`, `.occurredAt` or `.property(name:)`.
- **`HydrateReport.replacedTypes` and `unreplacedTypes` are new.** A hydration now replaces a declared `app.*` type that the instance holds in another definition, and `unreplacedTypes` lists, with the server's code and message, each one the instance refused. [Declare an app type](/swift-sdk#declare-an-app-type) explains it.
- **`WorkingCopy.fake(items:itemTypes:)` answers these writes and sorts**, and throws `FakeCopyError.unsupported(call:)` for a call it can't match exactly. [Test against a fake copy](/swift-sdk#test-against-a-fake-copy) lists what it answers.

### Swift SDK v0.0.23

Released October 20, 2026. [v0.0.23 on GitHub](https://github.com/withmarfa/marfa-swift/releases/tag/v0.0.23)

- **Builds against Marfa v0.0.18.**
- **`BlockedReason.failingAlone` is new.** A write set aside for failing alone is blocked with it, so an exhaustive `switch` over `BlockedReason` needs the case. [Devices](/devices#verdicts) explains the reason.
- **`QueuedWrite.lastFailure` and `environmentalStreak` are new.** `lastFailure` holds the status and the start of the text body of the last failure that wasn't an answer to the write, and `environmentalStreak` counts the drains in a row that met such a failure.
- **`Queue.withdraw(_:)` also takes a write blocked `failingAlone`**, and returns `false` instead of throwing `invalid` when the copy moved while it read the row from the server.
- **`WorkingCopy.open(store:server:)` throws `MarfaError.store` when it can't write the store's lock file.**

### Swift SDK v0.0.20

### Swift SDK v0.0.18

Released October 18, 2026. [v0.0.18 on GitHub](https://github.com/withmarfa/marfa-swift/releases/tag/v0.0.18)

- **Builds against Marfa v0.0.10.**
- **Properties, bodies and answers are JSON values, not text.** `Edit(properties:replaceProperties:baseVersion:)` replaces `Edit(.merge(_:))` and `Edit(.replace(_:))`, `declareTypes(_:)` takes `[JSONObject]`, and `QueuedWrite.answer` is a `JSONValue?`; the release on GitHub lists every change.
- **`Item.unreadableProperties` and `Edge.unreadableProperties` are new.** A row whose stored properties can't be read comes back with empty `properties` instead of failing the whole read.
- **A value the core can't hold is refused `invalid` before it's queued:** a number that isn't finite, a key that repeats in one object, or nesting deeper than the server reads.
- **`LiveQuery` is new.** It reads from the working copy and reads again when the copy changes, so a SwiftUI view stays current with no refresh code. [Swift SDK](/swift-sdk) covers it.
- **A held `changes()` stream drains after a drain left a write undelivered**, the next time the server is reached, and tells `.queueDrained`.
- **A follow that ends on the server's own answer after an outage tells `.serverReachable` before `.stopped`.**
