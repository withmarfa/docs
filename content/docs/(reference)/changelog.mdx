---
title: Changelog
description: What each release of Marfa changed for someone running an instance or building on it.
---

Each release of Marfa ships the server and its container image, the CLI for macOS on Apple silicon, and the TypeScript SDK on npm. Below is what each one changed that you'd notice when you run an instance or build on it, newest first, with a link to the full list on GitHub.

Marfa **doesn't upgrade a database in place**. A build refuses a database whose schema differs from its own or that holds retired tables or settings, and leaves the file unchanged. If the build refuses your database, [Upgrade](/guides/upgrade) covers exporting with the old build and restoring into fresh storage. A version change alone does not cause a refusal.

## v0.0.19

Released October 21, 2026. [v0.0.19 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.19)

For running an instance:

- **The owner has General and Health pages.** General, at `/auth/owner/general`, shows the instance's name and the five retentions that change while the server runs, and saves only the ones you changed. Health, at `/auth/owner/health`, shows whether the database, saving changes, disk and file storage are working, and the object store when one is attached. It lists every housekeeping job with when it last ran, its error if it failed, and Run now. [Change settings while it runs](/guides/settings#change-settings-while-it-runs) and [Housekeeping](/guides/housekeeping) cover them.
- **The owner has Connected apps and Browsers pages.** Connected apps, at `/auth/owner/apps`, lists the apps you approved, what each can reach, and the keys it made. Disconnecting an app ends its sign-in at once, and its keys keep working unless you also revoke them there. Browsers, at `/auth/owner/browsers`, lists where you are signed in, and signs out one other browser or all of them. Disconnecting an app and signing out another browser need a sign-in within the last five minutes, and the page asks you to confirm it's you if yours is older. [Revoke access](/guides/authenticate#revoke-access) covers apps, and [Manage passkeys and sign-ins](/guides/sign-in-as-the-owner#manage-passkeys-and-sign-ins) covers browsers.
- **The owner has Activity and All settings pages.** Activity, at `/auth/owner/activity`, lists the [audit log](/guides/audit-log) newest first and filters it by kind, time and text. All settings, at `/auth/owner/settings`, lists every environment setting by group with its variable, whether it can change while the server runs, and its value now. A setting that holds a secret shows only whether it is set.
- **Eight more settings count as secrets.** `S3_ENDPOINT`, `S3_ACCESS_KEY_ID`, `ERROR_WEBHOOK_URL`, `MARFA_HEARTBEAT_URL`, `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` and `MARFA_POSTHOG_HOST` can carry a credential in an address, so no page shows their value and a startup message that names one no longer prints it. `MARFA_AUTH_BASE_URL` stays readable and the server now refuses one that has a user name, password or query string. [Authentication](https://github.com/withmarfa/marfa/blob/main/conformance/spec/authentication.md#authenticationconsole-settings-no-secret) holds the rule.
- **The owner has Export and restore and Connectors pages, and the Manage and Restore pages are gone.** Export and restore, at `/auth/owner/export`, downloads an archive of everything or of one type and the types under it, with or without file bytes, and restores one. Connectors, at `/auth/owner/connectors`, lists each connector as Failing, Problems, Not heard from for over a day, or Running, shows its recent runs, and clears its saved state or removes it after you confirm. `/auth/owner/manage` and `/auth/owner/restore` no longer exist, and nothing redirects from them to the new pages. [Export an archive](/guides/export-and-restore#export-an-archive) and [Restore an archive](/guides/export-and-restore#restore-an-archive) cover them.

For apps and devices:

- **`PATCH /config` changes only the settings it names.** A setting in the body is replaced, a setting set to `null` is removed so its default applies, and every other setting stays. `enforcement` is one setting, so a patch that names it replaces all three levers. It takes the same fields and refusals as `PUT /config`. `marfa config update` sends it, with `--body` or `--file`. [Update the configuration](/guides/settings#update-the-configuration) covers it.
- **`GET /audit` filters by `kind` and `q`.** `kind` is one of `access`, `data`, `settings` and `housekeeping`, and each entry is of exactly one kind. `q` keeps the entries that hold every word you give, in any order, ignoring ASCII case. Any other `kind` is refused `400 validation_error`. `marfa audit` doesn't take either yet. [Filter it](/guides/audit-log#filter-it) covers them.
- **`GET /export?format=archive&files=false` leaves out file bytes.** The archive carries no file, and its manifest names each file it would have carried under `missing_blobs`. A restore of it reports those files in `blobs_missing` when the instance doesn't hold them. `marfa export` has no option for it yet. [Leave out the files](/guides/export-and-restore#leave-out-the-files) covers it.

## v0.0.18

Released October 20, 2026. [v0.0.18 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.18)

For running an instance:

- **The owner has a Home page at `/`.** A browser signed in as the owner sees the instance's name and address, what needs attention, a search for pages, and Sign out. A browser that isn't signed in gets a page that says the instance is running, with a Sign in link. An owner page under `/auth/owner/` sends a browser with no session to the sign-in page and returns it to the page it asked for, and an unclaimed instance sends it to `/setup`. A program that requests `/` still gets the description of the instance. [Start from Home](/guides/sign-in-as-the-owner#start-from-home) covers it.
- **The owner manages API keys in the browser.** The API keys pages list the keys, create one, and edit or revoke one. A key's access starts off, and the secret shows once and is removed when the owner leaves the page. A save is refused if the key changed after the page opened. [Use the API keys page](/guides/manage-keys#use-the-api-keys-page) covers it.
- **The owner has Profile and Password and passkeys pages.** Adding, renaming or removing a passkey asks the owner to confirm it's them when the sign-in is more than five minutes old. Changing the password asks for the current password instead. A passkey name that is empty or too long is refused `400 validation_error` when the passkey is verified. [Manage passkeys and sign-ins](/guides/sign-in-as-the-owner#manage-passkeys-and-sign-ins) covers it.
- **A folder that a different directory replaces stays listed.** A folder registry entry records the directory's identity. When another directory takes the folder's place, the entry stays, and the watch resumes when the directory the folder was admitted at returns. Marfa removes an entry when the directory at its path holds no folder state and isn't known to differ from the one admitted. [Folder safeguards](/guides/folder-safeguards#a-missing-or-unreadable-directory) covers it.
- **Sign out stays beside the title on a phone.** On Home, the Sign out button no longer drops under the title and address.
- **Destructive actions sit in their own card, and Save appears only after a change.** Revoking a key and removing a passkey are in a bordered card of their own. A key's page shows Save and Discard, with a count of the changes, only once something has changed.
- **The server needs Node.js 22.14 or later.** The container image runs Node.js 24. [Deploy](/guides/deploy) covers it.

For apps and devices:

- **The owner chooses what an app gets.** The approval screen lists each type with No access, Read only or Read and edit, then the owner's profile and the powers over Marfa that are off until the owner turns them on. Three powers that can't be undone are marked. Access the app already holds shows as Already allowed. A request for all data also shows Choose types, and if the owner picks types the token names them instead of all data. If the request asks for access that the app doesn't already hold and the owner turns all of it off, the app gets `access_denied` and keeps what it held. A request for nothing but `openid` and `offline_access` offers nothing to turn off, so the owner can approve it. [What the owner chooses](/guides/authenticate#what-the-owner-chooses) covers it.
- **A device code is easier to type.** The device page shows a code as `XXXX-XXXX`, accepts it in any case with or without the hyphen, and a code ends after 10 minutes.
- **Approving or revoking asks to confirm in a dialog, not a redirect.** `POST /auth/confirm` takes the owner's password or a passkey and replaces the session, so the browser carries on at the same page. A password counts against the attempt windows: a wrong one answers `401 unauthorized`, and once the windows are spent the answer is `429 rate_limited` with `Retry-After`. A refused confirmation keeps the session. A program that calls a route that needs a recent sign-in gets `403 forbidden` with "Sign in again to perform this operation". `POST /auth/confirm` answers `401` to a request with no live owner session or with a key. A browser may end its own sign-in at any time. [When approval needs a recent sign-in](/guides/authenticate#when-approval-needs-a-recent-sign-in) covers it.
- **`narrow_only` keeps a key from gaining access.** `PATCH /keys/{id}` with `narrow_only: true` refuses a change that adds access, and the API keys pages send it. `POST /keys` answers `Cache-Control: no-store`, so the secret isn't cached. [Narrow a key](/guides/manage-keys#narrow-a-key) covers it.
- **Marfa keeps a whole number exact, or refuses it.** A `number` or `integer` value that Marfa can't serve back with the same digits, such as `1500000000000000001`, is refused `400 invalid_properties`, and `details.errors` names the field. A `url` value is trimmed and judged as the WHATWG URL Standard does. For a special scheme such as `http`, a host with a non-ASCII character must be valid IDNA, and a host with a forbidden code point is refused. [Field kinds](/catalog/field-kinds) covers it.
- **A tag of `.` or `..` is refused** with `400 validation_error`, as an empty, blank or over-long tag is. A restore still accepts what an archive holds.
- **Narrowing a webhook cancels the deliveries it no longer selects.** Pending deliveries that the narrowed subscription doesn't select end `canceled`. Changing the `url` or setting `active: false` cancels all of them, and widening revives none. [Change what a webhook sends](/guides/receive-webhooks#change-what-a-webhook-sends) covers it.
- **The CLI prints access in the words the approval page uses.** `marfa login`, `whoami`, and `keys list`, `current`, `create` and `update` print No access, Read only and Read and edit for each type, and name powers by their titles. `--json` is unchanged. [CLI](/cli#check-what-a-command-will-use) covers it.
- **A write that fails alone is set aside.** A device marks a queued write `blocked` with the reason `failing_alone` when it keeps failing in the words of an outage, over some minutes, while the server still answers other writes. It tests the write first by sending another write that doesn't depend on it, and sets the write aside only if it fails in the same way when sent once more. Its dependents wait as `awaiting_dependency`. `marfa device queue` prints the last answer the write met after `last answer:`. [Devices](/devices#verdicts) covers it, and [`queue-and-verdicts/stuck-write-suspect`](https://github.com/withmarfa/marfa/blob/main/conformance/spec/queue-and-verdicts.md#queue-and-verdictsstuck-write-suspect) has the exact rule.
- **A file item keeps its bytes at a document name.** A file already bound to a file item, at a name ending `.md`, `.markdown` or `.txt`, is sent as bytes whatever they hold, with no frontmatter read. If it is empty it waits, and the rest of the scan goes on. A file at such a name that isn't bound to a file item is still read as a document. A `marfa_id` over 256 bytes is no id.
- **`--no-keychain` keeps the CLI off the keychain.** `--no-keychain` or `MARFA_NO_KEYCHAIN=1` makes every command treat the keychain as absent, and `marfa login --print-token` no longer reads or writes it. A command that sends a key from `--key` or `MARFA_API_KEY` and has no server named is refused `no_server`. [CLI](/cli#run-without-the-keychain) covers it.
- **The approval rows of two types with the same label are told apart.** When two item types share a label, such as `core.task` and `aic.ticket.task`, each shows its identifier under the label, and the type search matches the identifier.
- **A lock file the CLI can't write is refused with a message.** When the lock file opens read-only, the CLI stops with `<file> cannot be opened for writing, so it cannot be locked: check that it is writable`.
- **A repeat of a write whose first answer was large is refused, not run again.** Marfa keeps only the status of a first answer over 1,048,576 bytes, so a repeat under the same `Idempotency-Key` answers `422 idempotency_result_not_retained` with `details.original_status`, and writes nothing. A device counts a `2xx` status there as accepted, except for a create that names no `id`, which it refuses. [Write safely](/guides/write-safely#retry-with-an-idempotency-key) covers it.
- **A waiting edge edit or delete stays in view through a catch-up.** When a catch-up brings an item into a device's copy along with its edges, the device lays its own waiting writes over those edges, as hydration does, instead of showing the server's version until the server answers.

## v0.0.17

Released October 20, 2026. [v0.0.17 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.17)

For running an instance:

- **A blob folder that has gone is no longer read as an empty one.** When the disk store's folder or its `.marfa-store` marker is missing, as when its drive is unmounted while the server runs, `GET /health` answers `blob_storage` as `down` with status `503`. The `blob-integrity` job strikes none of that store's copies, counts the store in `unreachable` in its result, and still checks the stores it can reach. A blob read answers `503 blob_store_unavailable` rather than `404 blob_not_found` when a store that holds a copy can't answer and no other store returns the bytes. A restore that finds the disk store's marker missing, or naming another store, when it places a blob answers the same and writes nothing. Replication doesn't end its run on such a store, and the `enrichment-sweep` job doesn't count the attempt against the file. [Deploy](/guides/deploy#keep-it-running) covers the health check.
- **The bin purge keeps going through a backlog.** `trash-purge` removes a limited number of items in a run. While items past the retention remain after a run that removed some, the job runs again at once instead of waiting for its next interval, so an instance that bins more items in an interval than a run removes no longer falls behind. [Housekeeping](/guides/housekeeping#empty-the-bin) covers the job.
- **A restore keeps an item or an edge as the archive holds it.** An item whose type the instance no longer registers, such as after a forced delete, or that lacks a field its type later required, is restored with the properties and `schema_version` the archive holds. A restore also keeps an edge whose edge type was force-deleted, and no longer judges an end that is an item of a force-deleted type against the edge type's constraints. Such an edge is still skipped for the other reasons, such as a missing end. An export no longer refuses these with `409 export_rows_unrestorable`, so an instance that holds them can be exported again. An item of a `core` or `system` type that the build ships is still held to its shape. [Export and restore an archive](/guides/export-and-restore#restore-an-archive) covers it.
- **A restore refuses an archive that lacks one of its four files.** An archive without `manifest.json`, `items.ndjson`, `edges.ndjson` or `types.ndjson` is refused `400 validation_error`, naming each missing entry in the message and in `details.entries`. Before, it answered `200` with counts of zero.
- **A restore or an upload is no longer cut off while its bytes arrive.** An admitted upload has no total time limit. `MARFA_UPLOAD_IDLE_TIMEOUT_MS`, 60000 milliseconds unless set, ends one that receives no bytes for that long with `408 request_timeout`, and a restore then writes nothing and an upload stores no blob. The owner's recent sign-in is judged when a restore starts, so a restore that starts within five minutes of the sign-in isn't refused for finishing later. A session that signed in more than five minutes before the restore starts is refused `403 forbidden` without waiting for the body to finish arriving, and one that ends during the upload is answered `401 unauthorized`. [Settings](/guides/settings#every-environment-setting) lists the setting.
- **`marfa export --output` keeps the last whole archive.** When the new archive lacks blobs, the CLI doesn't replace the file at the path. It keeps the archive beside it as `<path>.incomplete`, replacing only an earlier file of that name, and exits `1` with `blobs_missing`. The message says whether the path still holds an earlier file. If the CLI can't write that name, it keeps the archive in a hidden file beside the path and names the file. [Export and restore an archive](/guides/export-and-restore#when-an-archive-lacks-a-files-bytes) covers it.
- **Claiming in a browser signs the owner in, and setup is six steps.** A claim that carries the instance's own `Origin` leaves the browser signed in, as a sign-in does, and that counts as a sign-in within the last five minutes, so adding a passkey needs no second prompt. A claim that sends no `Origin`, such as a script's, and a claim that is refused set no session. If the sign-in that follows a claim fails, the owner stays claimed and signs in at the page that follows. Setup runs as six steps: the setup code, the owner's details, a passkey, a name for the instance, connecting, and backups. [Quickstart](/quickstart#claim-the-instance) covers claiming.
- **The sign-in page says how long a lockout lasts.** When password sign-in or a device code lookup is refused for too many attempts, the page states the wait in whole minutes, rounded up, and the sign-in page says that a passkey still signs in. The wait runs to the time another attempt is allowed, the latest end among the limits that are spent. The sign-in page also links to a Forgot password page at `/auth/forgot-password`, which gives the command that recovers the owner on the instance's machine. [Troubleshooting](/guides/troubleshooting) covers it.

For apps and devices:

- **An export ends with an error when its credential ends.** If the key or signed-in app that started `GET /export` is revoked, expires or is disconnected while the response is open, the response ends with an error instead of ending cleanly, in both formats and while an archive sends a blob. The same happens if the credential is narrowed so that it no longer reads something the export has still to send. A narrowing that takes away nothing the export has still to send changes nothing. An archive export whose key is revoked while it reads the selection, before the response begins, gets `401 unauthorized`. [Export and restore an archive](/guides/export-and-restore#what-an-export-checks) covers it.

## v0.0.16

Released October 19, 2026. [v0.0.16 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.16)

For running an instance:

- **An archive export is checked against a restore before it is sent.** Before it sends a byte, Marfa checks the whole archive the way a restore into an empty instance does, so an archive it sends restores into an empty instance of the same build without skipping an item or an edge, even when writes landed between its pages. If a row fails the check, Marfa reads the selection once more. A row that fails both times and didn't change answers `409 export_rows_unrestorable`, and `details.row` names it. A row or type that changed, or a second read that refused a different row, answers `503 export_unrestorable`, so export again. An export's temporary files count against `MARFA_DISK_RESERVE_BYTES`. [Export and restore an archive](/guides/export-and-restore#what-an-export-checks) covers it.
- **Marfa refuses text that is not well-formed UTF-16.** A request body that holds a string or a property name with a lone surrogate, such as an emoji cut in the middle, is refused `400 validation_error`, and `details.errors[].path` names the text by its JSON pointer. A restore refuses an archive that holds such text, and names the row. Text that the server extracts from a file is cut at `MARFA_ENRICHMENT_MAX_TEXT_CHARS` UTF-16 code units, never through a character. The body checks, this one and the limit of 64 nested levels, now apply whatever `Content-Type` a request states, except on `POST /blobs`, `POST /restore` and inbound webhooks. [Troubleshooting](/guides/troubleshooting) covers the refusal.

For apps and devices:

- **Approving an app for more than reading needs a recent sign-in.** On the approval screen and the device approval screen, a browser that signed in more than five minutes ago can approve reading only. To approve write access, or a permission the app wasn't approved for before, Marfa asks the owner to sign in again and returns them to the screen. Revoking a key or disconnecting an app from a browser needs a recent sign-in too. A key, an app token and the private local command are not affected. [Authenticate](/guides/authenticate#when-approval-needs-a-recent-sign-in) covers it.
- **A write is judged by the key as it stands when it commits.** If a key is narrowed or revoked while one of its item writes waits its turn, the write is refused where before it went through with the old grants: `403 type_not_permitted`, `404 item_not_found` when the key can no longer read the type, or `401 unauthorized`. This covers creating, updating, deleting, restoring, transitioning and purging an item, and bulk writes, where an atomic page is refused and a best-effort entry is `errored`, naming the same code.
- **A device keeps its working copy when the server sends an answer it cannot read.** A hydration, catch-up or follow whose answer or event isn't JSON ends with `decoding`, and the copy and its place in the event stream are kept, where before the copy expired and asked for a hydration that failed the same way. A stream cut in the middle of an event is an interruption: a catch-up ends `stream_incomplete`, and a follow opens the stream again from its place.

## v0.0.15

Released October 19, 2026. [v0.0.15 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.15)

For running an instance:

- **A restore keeps the edges of items in the bin.** An archive made with `--state any` carries them, and a restore used to skip them as `item_not_found`. `edges_skipped_reasons` now names only `already_present`, `endpoint_missing`, `malformed`, or the error code `POST /edges` would answer for that edge. [Export and restore an archive](/guides/export-and-restore#restore-an-archive) covers it.
- **A backup restores when its types refer to each other.** Types that name each other in `compatible_with`, and a type whose display hints, links or merge fields name fields it inherits, restore in any order. Marfa also refuses a change to a type that would break another type's `compatible_with` claim, so an archive Marfa wrote stays restorable.
- **A first request with a key no longer fails with 503 during a long restore or bulk job.** A read with a key that was new to the process, or the first after a restart, waited behind the job and could answer `503 write_contention`. Marfa now records a key's last use in the background, so `last_used_at` can lag behind, or stay `null` after a busy moment.
- **A bulk job ends when the key that started it is revoked.** It ends `failed` and writes nothing more, where it used to stay `in_progress`. A text-extraction run or a webhook scheduling run started by hand no longer fails for the same reason.

For apps and devices:

- **A read answers from the data it checked.** When an item changed type during a read, the read could return metadata, such as a private tag, to a key that could no longer read the item. The same applied to the link between an occurrence and its series. A read now checks permission against the data it returns.
- **Replacing or deleting a type that another type depends on can be refused.** A replacement that breaks another type's `compatible_with` claim, and a deletion of a type that other types name in `compatible_with`, are refused with `422 compatible_with_violation`, and `details.dependent_type_ids` names the dependents. `force=true` does not bypass it. [Define a type](/guides/define-a-type#change-the-type) covers it.
- **Adding a parent or a compatibility target needs write permission on it.** Keeping one the type already has does not, so a connector can still update its type after its permissions narrow. [Define a type](/guides/define-a-type#what-your-key-needs) covers it.

## v0.0.14

Released October 19, 2026. [v0.0.14 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.14)

**Before you update, if your container keeps its database in a bucket:** the replica moves from `db` at the bucket's root to `<S3_PREFIX>/db`. On its next start, an existing deployment streams its database to the new path and takes a full snapshot there at once. The old `db/` objects are no longer read or pruned, and you can delete them once the new replica exists. **Every instance on a shared bucket now needs its own `S3_PREFIX`.** Before this release, instances on one bucket shared one replica, and a new volume of one could start on another's database. [Back up and restore](/guides/back-up-and-restore#with-a-bucket) and [Deploy](/guides/deploy#an-object-store) explain the prefix.

For running an instance:

- **Each release publishes the server image** to `ghcr.io/withmarfa/marfa-server`, for `linux/amd64` and `linux/arm64`, tagged with the release and `latest`. [Deploy](/guides/deploy#run-it-in-a-container) pulls it, and [Upgrade](/guides/upgrade) names the old build by its tag. `GET /` answers the `release` of such a build beside `version`, and `marfa status` and `marfa whoami` show both. A build made from a clone has no `release`. The container's port is published on the loopback address only, because Docker publishes a bare port on every interface.
- **A proxy on the same machine as the container needs `TRUSTED_PROXY_CIDRS`** set to the container network's range. Without it, every caller shares one address, and sign-in lockouts, which count attempts for each address, apply to everyone together. [Deploy](/guides/deploy#the-address) explains it.
- **A webhook to a private address is refused when you register it.** A `url` whose host is a private address, or a name that resolves to one, such as a Tailscale name, is refused `400 validation_error` that names `MARFA_WEBHOOK_ALLOW_PRIVATE_ADDRESSES`, and so is a change of `url` to one. A delivery refused for its address is `dead_letter` at once and not retried, so redeliver it after you allow private addresses. An outbound webhook reaches only global IPv6 addresses, and other IPv6 blocks are refused. [Receive webhooks](/guides/receive-webhooks#receive-deliveries-on-a-private-network) covers it.
- **Telemetry names the instance.** Every log record, span and reported exception carries `service.instance.id`, the `instance_id` that `GET /` answers. `OTEL_RESOURCE_ATTRIBUTES` marks an instance, such as `deployment.environment=staging` for a test one, for the server and the CLI, and `OTEL_SERVICE_NAME` wins over a `service.name` in it. The bare-metal start in [Deploy](/guides/deploy#run-it-without-a-container) loads the telemetry preload. [Send telemetry](/guides/telemetry#tell-instances-apart) covers it.
- **A backup names the files it lacks.** An archive leaves out a blob that no store holds whole and names it under `missing_blobs` in its manifest. `marfa export` then exits `1` with `blobs_missing`, a restore answers `blobs_missing`, and `marfa restore` exits `1` when it lists any. A cut `marfa export --output` leaves the path as it was and exits `3`. A blob store that fails answers `503 blob_store_unavailable`. [Export and restore an archive](/guides/export-and-restore#when-an-archive-lacks-a-files-bytes) covers it.
- **Headers a Tailscale proxy adds, those named `Tailscale-`, are not stored** with a connector's inbound delivery. [Receive vendor webhooks](/guides/connector-webhooks) covers it.

For apps and devices:

- **A file item names only bytes its writer uploaded or can already read.** Any other write of `blob_ref` is refused `404 blob_not_found`, where it was taken and left a file that nobody could download. Upload with the same credential first. The refusal isn't kept against an `Idempotency-Key`, and a working copy uploads again under its current key when the key changed. [Handle files](/guides/handle-files#point-an-item-at-the-bytes) covers it.
- **`marfa folders push` says whether it finished.** It exits `3` when a write is left unsent or the catch-up fails, and `5` when the credential is refused. Under a rate limit it doesn't wait: it reports the writes as not delivered, names the wait and exits `3`, and a watch waits on its own. The report counts files with an unanswered write as waiting. `marfa folders restore` lists the files it couldn't write back. A file moved to another folder and saved again as UTF-16 stays the same item, and a file that isn't text no longer holds up deletes in other folders. [Folder safeguards](/guides/folder-safeguards#know-whether-a-push-finished) covers it.

Released October 18, 2026. [v0.0.11 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.11)

For running an instance:

- A type can say how long its feed items stay, and a new `feed-expiry` housekeeping job moves the ones that have outlived it to the trash. It runs every hour by default; `FEED_EXPIRY_INTERVAL_MS` changes that. The job counts from when an item arrived, so refreshing an item by its natural key doesn't restart the count. It leaves library items, archived items and items you brought back from the trash alone, and it holds back an item whose delete would also delete an item that hasn't expired or that an edge with `cascade_on_delete` set to `block` protects. A moved item can be restored until the trash retention ends. Each move is announced as `item.deleted` and audited as `items.feed_expired`. A stream of events, live and on a replay from a cursor, and the deliveries of a webhook subscription leave out an item whose source the filter hides, and an edge whose source item it hides. A delivery already waiting is settled unsent once the filter comes to hide its item. A copy stream, which a device keeps its working copy from, still sends such an item, marked `listed: false`. [Settings](/guides/settings#what-the-enforcement-levers-do) covers the filter.
- An item with no source is judged by the source filter as an item whose source is `unknown`, as every read already shows it.
- `MARFA_TEST_HOOKS` and `MARFA_TEST_CLOCK_OFFSET_MS` are new settings for testing the server, which let a test harness move the server's clock and set faults through the private socket. **Leave them off on any instance that holds data.** The server refuses to start when `NODE_ENV` is `production`, which the container image sets, and `MARFA_TEST_HOOKS` is on, and when `MARFA_TEST_CLOCK_OFFSET_MS` is above 0 while hooks are off.

- A type definition can carry `retention_policy`, an object with one key, `feed_days`: a whole number from 1 to 36500, or `null` to keep feed items although a parent type sets a window. A type that names none takes its parent's. `GET /types/{id}` shows the window after inheritance, and `GET /types` shows the one the type declares.
- **An array property now has each element checked against its `items_type`**, for items and for edges. A write that leaves an element of the wrong kind is refused `400 invalid_properties`, and `details.errors` names the property and the element's position, as `names.1`. Some writes that were accepted before are now refused. The check also covers `links` (strings) and `attachments` (objects), the two arrays every type has. It judges the properties the item would hold after the write, so an item that already stores a wrong element refuses a write that carries `properties` or changes its type and leaves that array in place, until the write corrects it. The refusal names the element, and the item stays as it was. An `items_type` that isn't a field kind leaves the elements unchecked.

- A `backref` term of a filter counts an edge only if the key's source filter shows the edge's source item, as a listing of edges does.
- The description of `core.entity` now says it covers any named entity: a person, a company, a band, a team, a charity, a brand, a school or a place. It said non-person entities before.

For the CLI:

- `marfa` checks array elements in the writes it queues, and flags a folder file that names an edge no file writes, such as a line for an `in-folder` edge. `marfa` lists an edge type that no file writes as written at no end.

## v0.0.10

Released October 18, 2026. [v0.0.10 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.10)

For the CLI:

- `marfa device watch` holds a working copy's watch open and prints a line for each change, as an app's listener is told them. With `--reader`, it holds no event stream and prints a line for each save another process makes instead. It ends with the error if the watch fails, and `--for <SECONDS>` stops it after that long. Without `--reader`, it drains the queue once each time the server is reachable again after it was lost, and once at its first stream after a drain left a write undelivered.
- `marfa device changes` checks the store for a save by another process every 250 milliseconds, not every 100.

For apps and devices:

- An app can watch a working copy once and share the watch among any number of listeners. `Core::watch` in the core, `core.watch(onChange, onEnd)` in the Node module and `Core.watch` in the Swift binding hold one event stream for all of them, and tell each listener the changes made after it joined, in order. One listener that is slow to return delays the others but makes them lose no change. A watch of a store opened to read tells `store.saved`, with the data version, after another process saves, and a watch that fails tells each listener `watch.failed` once. A working copy with no server that isn't opened to read is refused `no_server`.
- A hydration or catch-up takes the stream from a running watch and gives it back, so an app no longer stops its listeners around either. One called from inside a listener's change handler is refused `invalid`, because it would wait on its own thread.
- A listener is told `server.unreachable` once for each loss of the server and `server.reachable` once for each return, and a listener that joins during an outage is told about it first. Any request that reaches the server ends an outage: the stream ending on the server's own answer, a hydration or catch-up that succeeded, or a drain that answered a write.
- A drain that left a write undelivered is finished by the first stream a watch has afterward, even after the app restarts. Before, only an outage that the same stream saw earned a drain. A working copy where an app only holds writes, with the server never lost, still drains nothing by itself.
- A link in a body written on another device keeps naming its item after that item is renamed, and after another item takes the old title. Before, a working copy recorded which item each link named only for bodies it wrote itself, so after a rename such a link read as `pending`, and a later write could answer it with the item that took the title. The copy now records it just before a name changes, and before a hydration replaces what it holds. A body and edge that reach the copy only after the rename, and a rename made before this release, leave no record, so the link is read by the names the copy holds.
- A link that another device takes out of a body and puts back is read afresh, by the titles the copy holds then, not by the item the link named before it was taken out.
- A write whose JSON body nests more than 64 levels, counting the outermost object as the first, is refused `invalid` when it is queued, as the server would refuse it, and nothing is queued. This holds in the CLI, the Node module and the Swift binding. Before, a body only a little too deep was queued and left for the server to refuse.
- A list or search filtered on properties no longer fails as a whole because one row's stored text isn't JSON. That row matches no property condition, `not_exists` included, so a filtered list leaves it out. A folder placement whose stored text isn't JSON no longer fails the lookup of an item that a body link names by its path.
- A read that refuses a row whose stored properties can't be read, as the CLI and the Node module do, also refuses a row whose stored properties aren't an object, instead of showing them as empty. An edit to an edge with unreadable properties is refused, and a hydration replaces the edge from the server.
- The Swift binding hands properties, queued bodies and answers to an app as JSON values (`JsonValue`, and `JsonObject` for a set of properties) in place of JSON text, so the app doesn't parse text again. A queued write's `answer` arrives parsed.
- The Swift binding keeps a row whose stored properties can't be read in a list, a search or an edge read, with empty properties and `unreadableProperties` saying why, in place of failing the whole read. A write to that item still fails, and a hydration replaces it from the server. The Swift SDK adopts the Swift binding's changes in its own release.

For the CLI, `marfa items add` adds a file as an item of its own, and the first run of a new instance is a series of `marfa` commands. Under `--json`, a usage error is a JSON refusal like any other.

## v0.0.2

Released September 27, 2026. [v0.0.2 on GitHub](https://github.com/withmarfa/marfa/releases/tag/v0.0.2)

- A key can read its own grants, with `GET /keys/current` or `marfa keys current`.
- The event stream sends `stream_live` once it has replayed what you missed, so a reader can tell it has caught up.
- `marfa keys update --no-permissions` takes every permission and map from a key, so a key made too wide can be emptied without making a new one.
- The TypeScript SDK refuses a credential with characters a bearer token can't hold, without repeating the credential in the error, and sends a body of bytes as the bytes.
