---
title: Swift SDK
description: Give an iOS or macOS app a working copy of your instance that reads offline, queues its writes and keeps itself current.
---

The Swift SDK is how an app on iPhone, iPad or Mac works with an instance. **An app built on it is a [device](/devices)**: it keeps a working copy of the data it needs, reads from that copy with or without a connection, and queues its writes until it can send them. It's the Swift package `Marfa`, which embeds Marfa's core, the engine every native client shares, so your app gets the same working copy and queue as the [CLI](/cli).

The sections below cover the main tasks. [Build an app with Swift](/guides/swift-app) puts them together into a working app.

## Add the package

The SDK supports iOS 27 and macOS 27, and builds with Xcode 27 on a Mac with Apple silicon. In Xcode, choose File > Add Package Dependencies, enter `https://github.com/withmarfa/marfa-swift`, and add the `Marfa` product to your app's target. In a `Package.swift`, add the package and the product:

```swift title="Package.swift"
.package(url: "https://github.com/withmarfa/marfa-swift", exact: "<latest release>"),
```

```swift title="Package.swift"
.product(name: "Marfa", package: "marfa-swift"),
```

Replace `<latest release>` with the version of the [latest release](https://github.com/withmarfa/marfa-swift/releases/latest). Every release adds 0.0.1 to the version, whatever it changes, so pin one version and move to the next on purpose.

Each release carries the core already built, so your app needs no Rust toolchain. The core is built for Apple silicon only, so in your app target's build settings, set Excluded Architectures for Any iOS Simulator SDK to `x86_64`. Without it, some simulator builds fail to link.

## Open a working copy

A working copy keeps its data in a SQLite file, which it makes the first time you open it. Give it a URL for that file, and the server's URL with a credential, a key or an app's access token:

```swift
import Marfa

let copy = try await WorkingCopy.open(store: storeURL, server: Server(url: serverURL, key: key))
```

Opening reads nothing from the instance. When the address changes, the copy remains usable offline and checks the instance identity anonymously before sending credentials or data, as the `wrong_server` entry in [Troubleshooting](/guides/troubleshooting) explains. The copy holds the credential in memory and never writes it to its store, so keep it in the keychain between launches. `Keychain.system` does that:

```swift
try Keychain.system.save(key: key, service: "com.example.readinglist", account: serverURL.absoluteString)
let saved = try Keychain.system.key(service: "com.example.readinglist", account: serverURL.absoluteString)
```

When the credential changes, give the open copy the new one with `useKey(_:)`. [Manage keys](/guides/manage-keys) shows how to make a key that reaches only the types your app needs.

For a command-line tool, `try Server.fromEnvironment()` reads `MARFA_API_URL` and `MARFA_API_KEY`. It returns `nil` when both are absent or empty, and throws when only one is set or the URL is invalid. Close a copy when its owner finishes with it:

```swift
await copy.close()
```

## Declare an app type

An app can bring its own types, under its own namespace, such as `app.readinglist.entry`. Declare them when you open the copy, each as a type definition, a `JSONObject`:

```swift
try await copy.declareTypes([
    ["id": "app.readinglist.entry", "fields": ["title": ["type": "string", "required": true]]]
])
```

`declareTypes(_:)` replaces the app's whole set, so pass every type on each call. Until the copy first hydrates, it checks a queued create against these declarations and the types Marfa ships, so an app can work offline from its first launch. When it hydrates, it registers each declared type the instance doesn't have yet, if the credential may register types, and lists them in the report's `registeredTypes`. [Define a type](/guides/define-a-type) explains what a type definition holds.

## Read and edit items

A new copy is empty. `hydrate(types:tier:)` chooses the slice the copy keeps, the types it names in the library, the feed or both (`.all`), and fills the copy with it. Reads then come from the copy:

```swift
_ = try await copy.hydrate(types: ["core.note"], tier: .library)

for note in try await copy.items.list(ListFilters(type: "core.note")) {
    print(note.title ?? "Untitled")
}
```

An item's `title` and `body` read the properties its type uses for a title and a body, whatever they're called, so prefer them to reading `properties`. A row whose stored properties can't be read stays in a list or a search with empty `properties` and `unreadableProperties` saying why, so check `unreadableProperties` before you write back from `properties`.

To make an item, pass a `Draft`. To change one, pass an `Edit` with the version you read, so the instance can tell whether someone else changed the item in between:

```swift
let created = try await copy.items.create(
    Draft(type: "core.note", properties: ["title": "Reading list", "body": "Start with the essays."]))

guard let id = created.itemId, let note = try await copy.items.get(id) else { return }
_ = try await copy.items.update(id, Edit(properties: ["title": "Books to read"], baseVersion: note.version))
```

Each write shows in the copy at once, with or without a connection, and waits in the queue. An edit changes the properties it names and keeps the rest. With `replaceProperties: true`, its properties become the item's whole set, so that's how you remove a property.

## Read the bin

`copy.items.bin(type:after:limit:)` reads **the server's bin online**, independently of the copy's slice, and adds none of its items to the copy. Follow `nextCursor` even when a page is short or empty:

```swift
var cursor: String?
repeat {
    let page = try await copy.items.bin(type: "core.note", after: cursor)
    for item in page.items {
        print(item.id, item.title ?? "Untitled")
    }
    cursor = page.nextCursor
} while cursor != nil
```

`copy.items.restore(_:)` queues a restore by ID, including an item the copy doesn't hold. `copy.items.purge(_:version:)` permanently destroys an item through an online request. The bin isn't cached, so an offline read throws `MarfaError.network`.

## Move an edge

An `EdgeEdit` changes properties, moves one end of an edge, or does both in one write. For a `parent-of` edge, move the source to give the child a different parent:

```swift
_ = try await copy.edges.update(
    edge.id, EdgeEdit(baseVersion: edge.version, move: .source(destination.id)))
```

Use `.target(id)` to move a target where the edge type permits it. A move is refused when the end that stays can hold multiple edges, or when it would make the edge point to itself. An edit that names no properties and moves no end to a different item returns `nil`. A successful source move expires the copy's read view, so handle `MarfaError.copyExpired` by hydrating again; a target move doesn't expire it. The queue keeps writes behind the move.

## Read body links and embeds

`copy.items.links(in:)` reads resolved links and file embeds **from the copy**, in body order. Each `BodyName.target` is an item ID or a reason it hasn't resolved: pending, missing, ambiguous or refused.

```swift
let names = try await copy.items.links(in: note.id)
for name in names.links + names.embeds {
    print(name.text, name.target)
}
```

`copy.items.embedText(of:in:)` returns `![[title]]` for a file attached to an item, and refuses a file whose title can't identify it alone. [Files](/files) explains attachments and embeds.

## Keep the copy in step

Your app decides when the copy first talks to the instance. Four moments matter:

- On first launch, or when `status().hydration` is anything but `.complete`, call `hydrate(types:tier:)`. It replaces what the copy holds and keeps the queue.
- When the app starts or comes to the front, call `catchUp()` to apply what changed while it was away, then `queue.drain()` to send what it queued.
- While a screen shows data, hold a `changes()` stream, which follows the instance's events as they happen. **The stream also sends the writes queued while the server was away**, once each time the server is back, and once after a drain left a write undelivered.
- After each write, call `queue.drain()`. A drain that can't reach the server leaves the writes queued.

The stream also tells your app when the server goes away and comes back, and when following it needs the app's help:

```swift
for await change in copy.changes() {
    switch change.origin {
    case .serverUnreachable(let error):
        showOffline(error)
    case .serverReachable:
        showOnline()
    case .queueDrained(let report):
        showSent(report)
    case .queueNotDrained(let error):
        showNotSent(error)
    case .stopped(.copyExpired):
        _ = try? await copy.hydrate(types: ["core.note"], tier: .library)
    case .stopped(.unauthorized), .stopped(.signedOut):
        askForANewCredential()
    default:
        refresh(change.itemId)
    }
}
```

On `.serverReachable`, show the app as online and start nothing: the stream drains the queue itself, and tells how it ended. It drains once each time the server is back. It also drains once at its next contact with the server after any drain, yours or its own, left a write undelivered. That contact comes when the follow next starts, for example after a catch-up, a hydration or a new stream, and if the server was never lost, no `.serverReachable` comes with it. `.queueDrained` carries the drain's `DrainReport`, and each write the drain answered is told first as `.answered`, as for a drain your app starts. `.queueNotDrained` carries the `MarfaError` that stopped it. The answers it had recorded stay recorded and the rest stay queued. Call `queue.drain()` when your app can send sooner.

`.copyExpired` means the copy can't be kept current from where it stands, and has to hydrate again. Its queue survives. Its `reason` is an open string, so keep a default when you switch over it. Two reasons are common: the device was away longer than the instance keeps events, and the server at the copy's address is now another instance (`instance_changed`), in which case the writes stay queued under their keys and go to the instance now there once you hydrate.

A drain returns the instance's verdict on each write it sent. Answered writes stay in the queue, with their verdicts, until you call `queue.forgetAnswered()`:

```swift
let report = try await copy.queue.drain()
for answer in report.verdicts {
    print(answer.kind, answer.verdict.map { "\($0)" } ?? "no answer")
}
_ = try await copy.queue.forgetAnswered()
```

```text
createItem accepted
updateItem accepted
```

A refused write that carried content stays even then, so your app can offer the content back, until you call `queue.discard(_:)`. [Devices](/devices#verdicts) explains each verdict.

## Keep a view current

A `LiveQuery` reads from the working copy and reads again whenever the copy changes, so a SwiftUI view that reads its `value` stays current with no refresh code. Create one on the main actor, in the model that owns the copy, and give it a `Reading`:

```swift
@MainActor @Observable
final class Library {
    let notes: LiveQuery<[Item]>

    init(copy: WorkingCopy) {
        notes = LiveQuery(copy, reading: .list(ListFilters(type: "core.note")))
    }
}
```

A view reads `library.notes.value`, and `Item` is `Identifiable`, so `List(library.notes.value)` works. Assigning `reading` reads again at once, so a search field can switch the same query to `.search(text)`. A query reads its copy for life, so a view for another copy needs another query.

| Reading | Value | Reads |
| --- | --- | --- |
| `.list(_:sort:)` | `[Item]` | `items.list`. `ListFilters.limit` and `offset` bound the result. |
| `.search(_:filters:limit:)` | `[Item]` | `search`, best match first. |
| `.item(_:)` | `Item?` | `items.get`, `nil` while the copy doesn't hold the item or it's in the bin. |
| `.queue` | `[QueuedWrite]` | `queue.all()`. |
| `Reading(placeholder:_:)` | Any `Sendable` and `Equatable` type | Any other read, in a closure that only reads. |

The query reads again after each change the copy tells that can alter a read, including a write your app makes offline. It makes no read for `.serverUnreachable`, `.serverReachable` or `.stopped`. A burst of changes causes the read in flight and at most one more.

A query shows its state in four properties:

- **`value`** is what the last successful read answered, and the reading's placeholder before one.
- **`isLoading`** is true from creation to the end of the first read, and during every later read.
- **`error`** is why the last read failed, and `nil` after a read succeeds. `value` keeps the rows of the last successful read.
- **`following`** is `.live`, `.stopped(error)` or `.ended(error)`. `.stopped` means the copy's follow of the server failed, and local writes still refresh the query. It returns to `.live` on a server event, or on a hydration or a catch-up that tells a change. `.ended` means the stream finished, with the error the core ended it on, or `nil` when the copy is closed.

`refresh()` reads now and returns after a read that began after the call, so it fits `.refreshable`. The query never asks for a new stream by itself, but on an `.ended` query `refresh()` asks the copy for one. Releasing the query ends its stream.

## Conflicted copies

When two devices change the same text, such as a note's body, the instance keeps one version on the item and puts the other in a conflicted copy: a new item tagged `conflicted-copy`, linked to the original, so neither text is lost. The drain's verdict for the write is `.conflicted(siblingId:fields:)`, and the conflicted copy reaches the working copy with the next catch-up. Find the copies of an item, or the original of a copy, like this:

```swift
for conflicted in try await copy.items.conflictedCopies(of: note.id) {
    print("Also edited elsewhere:", conflicted.body ?? "")
}
if let original = try await copy.items.original(ofConflictedCopy: item.id) {
    showBeside(original)
}
```

`original(ofConflictedCopy:)` returns an ID, because the working copy might not hold the original. To settle on one text, edit the original and delete the conflicted copy.

## Folders on a Mac

On macOS, `Folders` keeps a directory of files in step with a folder's settings on the instance, as `marfa folders` does. Both use the same list of folders on the Mac, so a folder your app adds shows in `marfa folders list`, and the other way around. Nothing is written into the directory or sent until the first sync is confirmed:

```swift
let folder = try await copy.createFolder(
    FolderSettings(title: "Notes", search: FolderSearch(types: ["core.note"])))

let folders = Folders(server: Server(url: serverURL, key: key))
let added = try await folders.add(notesDirectory, following: folder.id)
if let storage = added.storage {
    showWarning(storage.warning)
}

if case .awaitingConfirmation(let plan) = try await folders.sync(notesDirectory) {
    print("Writes \(plan.write) files here and sends \(plan.send) to the server.")
    _ = try await folders.confirmFirstSync(in: notesDirectory)
    _ = try await folders.sync(notesDirectory)
}
```

A directory in iCloud Drive, in a cloud service's synced location or on a network file system is added all the same, but a second program may sync the same files, or changes made from another computer may not be noticed. `add(_:following:)` returns the cause as `storage`, and the `.watching` event of a watch carries it too. A `StorageCause` is `iCloudDrive`, `cloudService`, `cloudSynced` (iCloud Drive or another cloud service, which macOS doesn't tell apart) or `networkFileSystem(kind:)`. Its `warning` is a plain sentence that names the cause: show it once for each folder.

Call `sync(_:)` to sync once. `watch(_:)` throws `MarfaError.firstSyncWaiting` until the first sync is confirmed. To keep the folders in the shared registry current, list them and start a watch for each confirmed folder:

```swift
for listed in try await folders.list() {
    guard try await folders.status(of: listed.directory).firstSync == nil else { continue }
    let watch = try await folders.watch(listed.directory)
    Task {
        do {
            for try await event in watch {
                print(event)
            }
        } catch {
            print(error)
        }
        await watch.stop()
    }
}
```

Keep the watches in your model and call `await watch.stop()` when their owner finishes. `folders.remove(_:)` leaves the directory's files intact and cancels a waiting first sync. After first sync is confirmed, it refuses removal while writes are unsent, so sync those before removing the folder.

One process works a folder at a time. When a call such as `sync(_:)` or `confirmFirstSync(in:)`, or a command like `marfa folders confirm`, asks for a folder your watch holds, the watch lets it go and tells `.handedOver`, then takes it back and tells `.takenBack`. No pass runs in between, so don't show the folder as in step. `.heldElsewhere` says another process holds a folder that no call asked for, and `.removed` and `.unlisted` say the call took the folder off the Mac, so the watch ends without an error. A call that isn't let the folder within 10 seconds throws `MarfaError.readingHandle`. A sandboxed app has its own home directory, and so its own list of folders. [Sync a folder](/guides/sync-a-folder) explains what a folder does with each file.

The full API is in the [marfa-swift repository](https://github.com/withmarfa/marfa-swift), and the rules a device follows are in the [device](https://github.com/withmarfa/marfa/blob/main/conformance/spec/device.md) and [queue and verdicts](https://github.com/withmarfa/marfa/blob/main/conformance/spec/queue-and-verdicts.md) chapters of the contract.
