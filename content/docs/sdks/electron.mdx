## What it is

`@withmarfa/sdk/electron` runs the [local engine](/sdks/local-engine) in an Electron main process and publishes it to a sandboxed renderer. The main process owns the store and is the only thing that does. The renderer has no Node, reaches the engine through a preload bridge, and calls a closed set of methods over one IPC channel.

That is the design rather than a hardening pass over it. A renderer with Node could open the store itself and become a second writer over one file, which is what the engine's [writer lock](/sdks/local-engine#one-writer-per-store) exists to refuse.

It ships as code rather than as a page of instructions because an Electron integration is only correct as a whole. Channel names, argument shapes and `webPreferences` all have to agree across a process boundary, and a written recipe is a copy that drifts separately in every application that followed it. **Here a disagreement is a type error in the application that made it.**

<Callout type="info">
  Everything the engine itself does is on the [local engine](/sdks/local-engine)
  page: the three layers, the queue and its failure classes, hydration, the
  fail-safe. This page is only the hosting.
</Callout>

## Three entry points

| Subpath | Context | What it holds |
| --- | --- | --- |
| `@withmarfa/sdk/electron` | Main process | The host, the store-path helpers, the protocol, and the packaging check |
| `@withmarfa/sdk/electron/preload` | Preload | `exposeLocalBridge`, and the bridge builder behind it |
| `@withmarfa/sdk/electron/renderer` | Renderer | The channel names, the bridge type, and `refusalNameOf` |

**The split is not tree-shaking.** A sandboxed preload has no filesystem `require`: Electron resolves `electron` and a handful of builtins and nothing off disk, so a preload has to be bundled into one file. A combined entry point would pull the store, and `@libsql/client` with it, into a context that could not load a native addon even if a bundler managed to inline it.

The renderer entry exists because a page can load neither of the other two. The main-process entry imports the store; the preload entry imports `electron`, which is not a module a browser bundle has. Everything in the renderer entry is a type, a constant, or a pure function over a string.

## Install

```bash
pnpm add @withmarfa/sdk @libsql/client drizzle-orm
```

`electron` is an optional peer dependency, so a consumer that is not building a desktop application never installs it. It is also what the main-process entry is typed against: `serve` takes Electron's own `IpcMain` and `WebContents` rather than narrowed stand-ins, because a stand-in that has fallen out of step with the thing it stands for is the version that compiles while the application does not.

Desktop packaging needs more than this. See [Packaging a desktop artifact](#packaging-a-desktop-artifact).

## The main process

```ts
import { fileURLToPath } from 'node:url';
import { app, BrowserWindow, ipcMain } from 'electron';
import { MarfaClient } from '@withmarfa/sdk';
import {
  openElectronLocalStore,
  sandboxedWebPreferences,
} from '@withmarfa/sdk/electron';
import { SINGLE_ACCOUNT, SINGLE_SPACE } from '@withmarfa/sdk/local';

const url = 'https://marfa.example.com';

await app.whenReady();

const host = await openElectronLocalStore({
  userData: app.getPath('userData'),
  identity: { origin: url, spaceId: SINGLE_SPACE, accountId: SINGLE_ACCOUNT },
  client: new MarfaClient({ url, apiKey: process.env.MARFA_API_KEY! }),
  onRecovery: (recovery) => reportToTheUser(recovery),
});

host.serve({
  ipcMain,
  // Read per event, so a window opened later is told and a window closed
  // earlier is not looked for.
  renderers: () => BrowserWindow.getAllWindows().map((w) => w.webContents),
});

const main = new BrowserWindow({
  webPreferences: sandboxedWebPreferences(
    fileURLToPath(new URL('./preload.cjs', import.meta.url)),
  ),
});
await main.loadFile(fileURLToPath(new URL('../app/index.html', import.meta.url)));

await host.engine.start();

app.on('window-all-closed', () => {
  // Releases the writer lock and gives the IPC channel back, so the next
  // launch is a writer.
  host.close();
  app.quit();
});
```

`openElectronLocalStore` makes the store's directory, opens the store, migrates it, and builds the engine over it.

| Option | What it is |
| --- | --- |
| `userData` | `app.getPath('userData')`, under which every store lives. |
| `identity` | The `origin`, `spaceId` and `accountId` this store belongs to. All three are required, and `SINGLE_SPACE` and `SINGLE_ACCOUNT` stand in on a server with no spaces or a credential naming no account. |
| `client` | A `MarfaClient` for the same origin. The engine takes one whether or not there is a server to reach. |
| `retryCeiling` | Transient attempts a mutation gets before it parks. |
| `initialRetryMs` | First reconnect backoff, in milliseconds. |
| `connectTimeoutMs` | How long `start` waits for the stream's opening announcement. |
| `onRecovery` | Called when a store had to be set aside and rebuilt. Worth wiring: the sidecar it names is the only copy of writes that never left. |

The engine makes no request until it is started or drained, so an application that opens a store and does neither runs with no server to reach at all.

| On the host | What it is |
| --- | --- |
| `engine`, `store` | The [engine and store](/sdks/local-engine) themselves, for the main process's own reads and writes. |
| `path` | Where the store's database file is. |
| `writer` | False when another engine already holds the store and this handle can only read. |
| `serve(options)` | Answer a renderer's calls and push it events. Returns the function that stops both. |
| `close()` | Stop serving, stop the engine, close the store. Idempotent. |

- **`renderers` is a function, read at the moment each event is sent.** Windows open and close over the life of a host, so a list captured at `serve` time is stale by the second window. Each renderer is sent to separately, because Electron throws on a destroyed `webContents` and one window closed between the read and the send must not stop the others being told.
- **`close` gives the channel back.** Electron refuses a second `handle` on one channel, so a host that leaves its handler behind makes the next host over that `ipcMain` throw, whether that is a teardown and rebuild or a second account signing in.
- **`sandboxedWebPreferences` sets three flags from one place**, and every one of them is load-bearing and silent when it is wrong. With `sandbox` off the renderer gets a Node environment it has no use for; with `contextIsolation` off the page's own scripts share a context with the preload; with `nodeIntegration` on the page can open the store directly. It is checked against Electron's own `WebPreferences`, so a renamed or removed flag fails the build rather than being ignored at runtime, which is what Electron does with a `webPreferences` key it does not recognize.

### Two locks, and they are not the same lock

Both are called a lock and both are about only one of something, which is why they get conflated. They answer different questions and an application can want both.

- **Electron's single-instance lock decides whether a second copy of the application starts.** Without it, opening the app twice gives two processes, and the second finds the store held and opens it read-only: an app that looks identical to the first and silently cannot save.
- **The engine's writer lock decides which handle over one store file may advance its cursor.** It still refuses a second writer when one process opens the same store twice, and it still permits two stores in one process, which is what a second signed-in account is.

Holding the first does not give you the second. `host.writer` and `engine.status().writer` report the second one.

## Where the store goes

A store lives at `<userData>/marfa-local/<origin-slug>-<digest>/store.db`, where the digest is the first sixteen hex characters of a SHA-256 over the origin, the space and the account.

- **The separator between the three fields is load-bearing, and dropping it fails silently.** They are joined by a NUL before hashing. Concatenated instead, a space of `bc` with an account of `d` and a space of `b` with an account of `cd` produce one digest, one directory and one store for two accounts, and the engine's identity check, which exists to catch exactly this, would never see a mismatch to refuse. An identity carrying a NUL in any of the three is refused rather than escaped, because such an identity is wrong wherever it came from.
- **A directory per store, not a bare file.** SQLite writes `-wal` and `-shm` siblings, the writer lock is a lockfile beside them, and a store the [fail-safe](/sdks/local-engine#the-fail-safe) had to set aside leaves the old database and a recovery sidecar behind. One directory makes removing an account's store a single safe operation rather than a pattern match over a shared folder.
- **The slug is decoration and the digest is identity.** The slug is the origin's host, lowercased and hyphenated, so a person opening the folder can tell which server a store belongs to rather than reading a row of bare digests.
- **Everything sits under one parent.** An application that also keeps window bounds, caches and its own preferences in `userData` can clear every store without knowing how many there are or what they are called.

`localStorePath` and `localStoreDirectory` are exported for an application that needs the location without opening the store.

## The preload

```ts
import { exposeLocalBridge } from '@withmarfa/sdk/electron/preload';

exposeLocalBridge();
```

That is the whole preload for most applications. It puts the bridge on `window.marfaLocal`, and `contextBridge` is what makes the renderer's copy a set of proxies rather than the object itself, so the page's own scripts cannot reach past the published methods into the preload's context.

**Bundling it is the application's job**, and two constraints on that bundle are not preferences.

- **One self-contained file.** A sandboxed preload's `require` resolves `electron` and a few builtins and nothing off disk, so a preload that imports this package by name loads only once a bundler has inlined it.
- **CommonJS output.** Electron loads an ES-module preload only when the renderer is not sandboxed, which is the setting this whole arrangement exists to keep on.

`createLocalBridge(ipcRenderer)` builds the same object without the `contextBridge` call, for an application that wants the engine under a different global or merged into an API of its own.

## The renderer

```ts
import { refusalNameOf } from '@withmarfa/sdk/electron/renderer';
import type { MarfaLocalBridge } from '@withmarfa/sdk/electron/renderer';

declare global {
  interface Window {
    marfaLocal: MarfaLocalBridge;
  }
}

const marfa = window.marfaLocal;

const notes = await marfa.listItems({ type: 'core.note' });
const status = await marfa.status();

const off = marfa.on((event) => {
  if (event.type === 'drain.finished') refreshList();
});
```

`MarfaLocalBridge` publishes `start`, `stop`, `drain` and `status`; the reads `getItem`, `listItems`, `getEdge`, `listEdges` and `getMetadata`; the writes `createItem`, `updateItem`, `deleteItem`, `createEdge`, `updateEdge` and `deleteEdge`; and `listDeadLetters`. Each one behaves as its counterpart on the engine or the store does.

- **The method set is closed, and it is derived from the type rather than kept beside it.** The main process's handler table is keyed by a `LocalMethod` computed from `MarfaLocalBridge`, so a method added to the contract and not handled fails to compile rather than failing on a user's machine, and a handler for a method the contract does not name is a type error in the other direction. A method the host never published is refused, not reached.
- **Everything is a promise**, including the two the engine answers synchronously. A process boundary makes them all round trips and a type saying otherwise would be a lie.
- **`on` is not one of the methods**, because it takes a function and a function cannot cross the boundary as an argument. The listener stays in the renderer and the preload relays to it. It returns the function that stops listening.
- **Arguments are checked, coarsely and deliberately.** The store refuses a write it cannot make and says why, so a full schema per method would restate the engine's validation somewhere it could disagree with it. What is caught here is the shape that would otherwise fail somewhere unrecognizable, such as an id that is not a string reaching a query builder.

## A refusal loses its class on the way across

**`error.name` does not survive the trip and cannot be made to.** Electron does not hand the renderer the preload's Error. It serializes what it can and rebuilds one in the renderer's realm, and custom properties are not part of that: `error.name = 'ReadOnlyStoreError'` on an instance is a custom own property, shadowing the prototype's `name` rather than replacing it, so the renderer reads `'Error'`. A subclass fares no better, because the prototype does not cross either.

`message` does survive, so that is where the class travels. The bridge writes `<Name>: <message>` and `refusalNameOf` reads it back.

```ts
try {
  await marfa.createItem({ type: 'core.note', properties: { title } });
} catch (error) {
  // `error.name` is 'Error' here, whatever the store threw.
  if (refusalNameOf(error) === 'ReadOnlyStoreError') {
    showBanner('Another window holds this store, so nothing here can be saved.');
  }
}
```

**An application that branches on `error.name` will silently never match.** It compiles, it runs, and the branch is dead: the read-only banner never appears, and every refusal reads as an ordinary failure.

`refusalNameOf` returns three things.

- **The class name**, for a refusal that carries one: `ReadOnlyStoreError` from a write on a handle another engine holds the store against, and the host's own `UnknownMethodError` and `BadArgumentError`, along with anything else the store or engine raises.
- **`PLAIN_REFUSAL`, which is `'Error'`**, for an ordinary failure. One is not dressed up, because prefixing every message with a word that says nothing helps nobody. The engine's own messages are prefixed `@withmarfa/sdk/local:`, and that prefix is not a bare identifier, so it is never mistaken for a class.
- **`undefined`** for something that is not an Error at all.

The main process resolves an answer rather than rejecting, which is what makes any of this possible: a rejection out of `ipcMain.handle` reaches the renderer as a string with Electron's own prefix wrapped round it, and the class is gone before the bridge sees it.

## An event loses what it cannot clone

`sync.error` carries the value that was thrown, and that field does not cross. Everything on the event channel goes through the structured clone algorithm, the field is whatever was thrown and is under no obligation to be cloneable, and a value the algorithm refuses takes the send down with it, on the one path whose whole purpose is reporting a failure without crashing.

So `BridgeEngineEvent` is the engine's own event type with that one field removed. `message` carries what a person needs, and the thrown value stays in the main process, where a listener on `engine.on` can still reach it. Every other [engine event](/sdks/local-engine#what-the-app-can-read) crosses unchanged. `forRenderer` is exported for an application relaying events over a channel of its own.

## Packaging a desktop artifact

**The engine's SQLite binding ships its native code as nine platform packages, declared as optional dependencies of `libsql`, and an install resolves the build host's and skips the other eight.** That is right for a server, which runs where it was installed, and wrong for a desktop application, which is built on one machine and run on others: build on an Apple Silicon Mac and the Windows artifact carries a macOS binary, or nothing at all.

**None of that is an error at build time.** The build succeeds, the installer is signed, and the first report is a module-not-found at the first store open on somebody else's machine, on a code path with no visible relationship to a missing file.

So an application declares the platform packages it ships for as direct dependencies, which install whatever the host, and runs the check as part of the step that produces the artifact:

```ts
import { assertNativeTargets } from '@withmarfa/sdk/electron';
import type { LibsqlTarget } from '@withmarfa/sdk/electron';

const SHIPPED: readonly LibsqlTarget[] = [
  'darwin-arm64',
  'darwin-x64',
  'linux-arm64-gnu',
  'linux-x64-gnu',
  'win32-x64-msvc',
];

// Throws MissingNativeBinaryError, naming every target that would not load.
assertNativeTargets({ resolveFrom: import.meta.url, targets: SHIPPED });
```

`resolveFrom` is a module URL or a file path, usually `import.meta.url` of the script running the check, so the `node_modules` walk begins at the application that declared the packages. `verifyNativeTargets` takes the same options and returns a report with every finding, sound or not, for a build that wants to report rather than stop. `LIBSQL_NATIVE_TARGETS` maps each target to its package name, platform and architecture.

Run it from `build` rather than from a separate command, because the arrangement it replaces is exactly a thing somebody has to remember.

It checks only the targets it is given, so keep that list and the manifest in step in both directions. Drop a dependency and the check narrows to what is left and passes; add one without listing it and it ships unverified.

The cost of this route is install weight, roughly eight megabytes per target. The two alternatives are worse: building each platform on its own machine is a packaging decision rather than a dependency one, and fetching the right package per target while packaging puts a network request inside the step that produces the artifact and moves the failure somewhere with even less to say about it.

### What the check reads

**It reads object-file headers, not filenames**: the Mach-O `cputype`, including every slice of a universal binary, the ELF `e_machine`, and the PE COFF machine type. The shape being guarded against is a build that puts one platform's binary where another's belongs, and a Windows package holding a macOS binary looks like a healthy install from the filename down.

A universal binary is sound as long as the architecture it needs is among its slices, and unsound when it is not, which is the ordinary shape of a `lipo`-thinned artifact. Every unknown is a refusal rather than a pass: a file too short to hold the field being read, an architecture the check does not recognize, an `MZ` with no PE signature behind it, and a Java class file, which begins with the same four bytes a universal binary does.

It cannot tell glibc from musl, which no header records.

<Callout type="warn">
  **It reads the install tree on the build machine, not the artifact.** It says
  the bindings a packager could copy are present and are for the platforms they
  claim. Whether the packager then copies them into what it produces is that
  packager's configuration, and nothing here opens an artifact to find out.
</Callout>

### The nine targets

| Target | Platform | Architecture |
| --- | --- | --- |
| `darwin-arm64` | macOS | arm64 |
| `darwin-x64` | macOS | x64 |
| `linux-arm-gnueabihf` | Linux, glibc | arm |
| `linux-arm-musleabihf` | Linux, musl | arm |
| `linux-arm64-gnu` | Linux, glibc | arm64 |
| `linux-arm64-musl` | Linux, musl | arm64 |
| `linux-x64-gnu` | Linux, glibc | x64 |
| `linux-x64-musl` | Linux, musl | x64 |
| `win32-x64-msvc` | Windows | x64 |

An Electron application ships for five of them. Electron's own desktop builds are macOS on both architectures, Windows on x64, and Linux on x64 and arm64 against glibc, so the two musl variants and the two 32-bit ARM ones have no Electron to run under. Windows on arm64 is the gap in the other direction: Electron builds for it and libsql publishes no binding, which is a platform an application cannot ship rather than one it forgot.

### Installing them with a package manager other than pnpm

These packages declare `os` and `cpu` for platforms the build host is mostly not, and package managers differ on what they do about that.

- **pnpm installs them without complaint.** No warning on a default install, and `engine-strict=true` does not change it, because that setting governs the `engines` field rather than `os` and `cpu`.
- **npm refuses**, with `EBADPLATFORM` naming the first mismatched package, and installs nothing. An application that has to support `npm install` needs a different route to the same place.

`pnpm.supportedArchitectures` is the sanctioned mechanism for pulling other platforms' packages, and it does not help here: it applies to optional dependencies, so setting it in a workspace pulls every platform variant of every optional dependency in the tree to solve a problem direct dependencies already solve.

Pin the platform packages to the exact version of `libsql` that `@libsql/client` resolves, and bump them in step with it.

## Two traps in the build

- **The main-process subpath is ESM-only.** There is no `require` condition on it, and an Electron main process is overwhelmingly CommonJS, so a CJS main cannot require it. Bundle the subpath, or move the main process to ESM.
- **A module script never loads from a `file://` page.** `loadFile` gives the window a file URL, module scripts are fetched under CORS, and a file URL has an opaque origin, so the request fails, with or without a Content-Security-Policy and whether the script sits in the same directory or another. Build the renderer as a classic script and load it with a plain `<script src>`. **With `<script type="module">` the page renders and the script never runs**, which reads as a blank window rather than as a load failure.

## Surface

| Export | Entry point | What it is |
| --- | --- | --- |
| `openElectronLocalStore` | Main | Open the store for an identity, build the engine over it, and return the host. |
| `sandboxedWebPreferences` | Main | The three `webPreferences` flags a renderer reaching the engine must have. |
| `localStorePath`, `localStoreDirectory` | Main | Where a store for an identity lives under `userData`. |
| `forRenderer` | Main | Strip an engine event down to what can cross a process boundary. |
