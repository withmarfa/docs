The Marfa MCP server is the canonical agent surface for a Marfa space. It speaks the [Model Context Protocol](https://modelcontextprotocol.io/) over stdio, registers one tool per SDK method, and translates each tool call into a single [@withmarfa/sdk](https://www.npmjs.com/package/@withmarfa/sdk) invocation. Stateless between calls, Zod-validated inputs, JSON outputs. Serving covers the current 2026-07-28 protocol revision (per-request metadata, `server/discover`) and the earlier handshake revisions, negotiated per connection.

Published to npm as [@withmarfa/mcp](https://www.npmjs.com/package/@withmarfa/mcp). Wraps the TypeScript SDK; every operation the SDK exposes is reachable as an MCP tool.

## Install

```bash
# One-shot via npx (no install)
npx -y @withmarfa/mcp

# Or install globally to get a marfa-mcp binary on PATH
npm install -g @withmarfa/mcp
```

The same SDK releases the CLI consumes drive the MCP — both pin caret-ranged on the published SDK.

## Configure

Three environment variables drive runtime configuration. `MARFA_API_URL` is required; the server exits at startup if unset.

| Variable | Description |
| --- | --- |
| `MARFA_API_URL` | Marfa server URL (required; no default) |
| `MARFA_API_KEY` | API key; an explicit override that always wins when set |
| `MARFA_INSTANCE` | Which `~/.marfa/<instance>.json` to read (default: `default`) |
| `MARFA_MCP_TOOLSETS` | Comma-list of toolsets to enable: `standard`, `admin`, `all`. Default: `standard` |

The toolsets value can also be passed as a CLI argument: `--toolsets standard,admin`. The CLI argument takes precedence over the environment variable.

Credentials resolve in order: `MARFA_API_KEY` when set; otherwise the CLI's stored OAuth session from `~/.marfa/<instance>.json` when its issuer matches `MARFA_API_URL`; otherwise the file's `key` slot; otherwise a startup error naming both options. After `marfa auth login`, only `MARFA_API_URL` is needed — the server shares the CLI's signed-in session, including refresh, so the credential stays narrow and expiring instead of a long-lived key. A stored session for a different server is never sent.

One Marfa space per server process. A user with multiple spaces configures multiple MCP-server entries in their client.

## Connect

### Claude Code

Add to `~/.claude.json` under `mcpServers`. Uses `npx` for zero-install:

```json
{
  "mcpServers": {
    "marfa": {
      "command": "npx",
      "args": ["-y", "@withmarfa/mcp"],
      "env": {
        "MARFA_API_URL": "https://your-server.example.com",
        "MARFA_API_KEY": "marfa_k1_...",
        "MARFA_MCP_TOOLSETS": "all"
      }
    }
  }
}
```

If you've installed globally with `npm i -g @withmarfa/mcp`, `"command": "marfa-mcp"` (no args) works too.

After `marfa auth login`, the `MARFA_API_KEY` line can be dropped entirely — the server picks up the CLI's stored session for the same URL.

### Claude Desktop

Same `mcpServers.marfa` block in `~/Library/Application Support/Claude/claude_desktop_config.json`. Cmd-Q and relaunch to pick up changes — `/reload-plugins` doesn't restart MCP subprocesses.

### Other MCP clients

Any MCP-compatible client (Cline, Continue, custom hosts) works the same way — point its server-spawn config at `npx -y @withmarfa/mcp` or the globally-installed `marfa-mcp` bin, and pass the env vars through.

## Toolsets

The tool surface is partitioned into two named toolsets. `standard` is on by default; `admin` is opt-in. Pass `all` to enable both. The split keeps context-window cost low for clients that load every tool definition on connect.

### Standard toolset (default, 27 tools)

The `standard` toolset covers daily-driver reads, writes, tagging, search, edges, type discovery, profile, and the attachments composite.

- **Items** — `create_item`, `upsert_item`, `get_item`, `update_item`, `delete_item`, `restore_item`, `list_items`, `search_items`, `transition_item`, `list_versions`, `create_item_with_attachments`
- **Metadata** — `get_metadata`, `tag_item`, `untag_item`, `set_metadata`, `merge_metadata`, `list_tags`
- **Edges** — `create_edge`, `update_edge`, `delete_edge`, `list_edges`, `list_edges_from`, `list_backrefs`, `list_edge_types`
- **Types (read)** — `list_types`, `describe_type`
- **Profile** — `profile_get`

### Admin toolset (opt-in, 15 tools)

The `admin` toolset is the operator-flavored surface: bulk operations, type and edge-type registration, raw extension and blob I/O.

- **Bulk** — `bulk_items`, `bulk_action_items`, `bulk_edges`
- **Types (write)** — `register_type`, `update_type`, `delete_type`
- **Edge types (write)** — `create_edge_type`, `delete_edge_type`
- **Extensions** — `get_extensions`, `set_extension`, `delete_extension`
- **Blobs** — `upload_blob`, `download_blob`, `blob_exists`, `get_blob_url`

## Tool design

A few conventions worth knowing before reaching for the surface:

- **Every tool is a single SDK call.** No composition, no retries beyond what the SDK does, no caching. The server is stateless between calls — perfect for the agent's "make one decision, call one tool" loop.
- **Outputs are JSON text.** Successes return a single text content block with the JSON-serialized result. An error *from a tool* returns an error block carrying `{ "error": { "code", "message", "status", ... } }` — `error.code` is the stable string to branch on, `error.message` is human-friendly prose, and whatever else the failure carries travels alongside them. That last part matters where the recovery state is hard to reach any other way: `update_edge` refused on a stale `version` returns the edge as the server now holds it, and since no route reads a single edge back by id, the alternative is re-listing to find it again. A transport failure arrives in this same envelope as an API refusal.
- **Schema refusals are the exception, and the common one.** Argument validation happens in the MCP server kit, before any handler runs, so a refusal for an unrecognized key never passes through the envelope above. It arrives as `isError: true` carrying plain text — `Input validation error: Invalid arguments for tool list_items: Unrecognized key: "typ"`. Branch on `isError` first and parse the text only when you need the structured fields; a client that parses every error body will throw on the failure closed inputs make most likely.
- **Inputs are closed.** An unrecognized parameter is refused and the refusal names it, rather than being dropped on the way to the handler. For a model caller a stripped key is worse than a rejected one: a misspelled filter would otherwise come back as a successful call carrying everything the filter was meant to exclude, with nothing in the response to distinguish that from a filter that genuinely matched everything. Every tool advertises `additionalProperties: false`, nested shapes included, so the schema a client reads is the truth about what the tool takes.
- **Writes can carry a version precondition.** `update_item` and `update_edge` both accept an optional `version`, taken from the read the edit was computed against. Pass it and a write over a row that has moved on is refused rather than landing on top of it, with the current state on the error. Omit it and there is no conflict detection at all: the write is a **blind overwrite**. No ancestor is looked up, the type's `merge_policy` never runs, no `conflicted-copy` sibling is created, and a `200` comes back whichever way a concurrent change went — so a value another writer set in the meantime is gone with nothing recording that it existed. The right default for a single writer, the wrong one for an agent that read, reasoned for a while, and is now writing back. Pass the version and the policy applies; see [Conflicts](/guides/schema/conflicts).
- **Atomic item + edges on create.** `create_item` and `upsert_item` accept an `edges` payload (`{ "in-thread": [threadId] }`, `{ "about": [topicId] }`, etc.) so relationship setup lands in one call rather than two.
- **`upsert_item` returns `{ item, created }`.** Branch on the boolean to know whether you minted a new row or matched and updated an existing one. Pair with `source` + `source_id` for natural-key upsert.
- **Filter-DSL passes through.** `list_items` accepts the full filter grammar (`edge[type]=id`, `backref[type]=id`, tag filters, `tier`) so the model can query relationships without round-tripping through edge-listing tools.
- **List pages default small and scale on request.** Every `list_*` tool returns 20 rows per call unless the model passes `limit`, which is honored up to the serving route's own ceiling (200 for items, 500 for edge listings) and clamped there. The cursor always matches the rows actually delivered.

## Remote

Every Marfa server also serves the same tools over streamable HTTP at `/mcp` on its own origin — the agent and the instance no longer need to share a machine. The remote surface is protected by the same bearers as the rest of the API: an unauthenticated request gets a 401 whose `WWW-Authenticate` header names the [Protected Resource Metadata](/api-reference/authentication) document, and from there an MCP client discovers the authorization server, registers, and signs the user in through the standard consent screen. The issued token is bound to the user's space at consent, so the remote surface never chooses a space — the credential does — and every tool call is enforced by the same scope and space rules as a direct API call.

Claude Code, for a hosted or self-hosted server:

```bash
claude mcp add --transport http marfa https://your-server.example.com/mcp
```

Clients that cannot run an OAuth flow can send an API key as the bearer instead. Operators can disable the surface with `MARFA_MCP_ENABLED=false` or widen the offered toolsets with `MARFA_MCP_TOOLSETS` on the server; credentials still gate every call, so widening the toolsets widens offering, not access.

## What MCP is not

The Marfa MCP server exposes tools only — no MCP resources, no prompts, no sampling. Each tool call is independent: no in-process cache, no cross-call state. The lever for context-window cost is **toolsets**, not a dispatcher tool or lazy schema loader.

It's also not a CLI. The [CLI](/sdks/cli) is a terminal surface designed for human typing; MCP is an agent surface designed for an LLM reasoning about what to do next. Same SDK underneath, completely different ergonomics.
