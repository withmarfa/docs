The Marfa CLI is a Commander-based terminal client published on npm as [@withmarfa/cli](https://www.npmjs.com/package/@withmarfa/cli). Wraps the TypeScript SDK; every operation the SDK exposes is reachable as a `marfa <resource> <verb>` subcommand. Human-readable output by default; auto-switches to JSON when stdout is a pipe or redirected file.

## Install

```bash
npm install -g @withmarfa/cli
# or: pnpm add -g @withmarfa/cli
# or: yarn global add @withmarfa/cli
```

Installs the `marfa` binary on your `PATH`. Confirm with `marfa --help`.

## Authenticate

Two paths, both work; OAuth wins when present.

**Interactive (recommended for humans)** — `marfa auth login` runs the OAuth Device Authorization Grant. The CLI prints a URL and code; approve in a browser; tokens persist at `~/.marfa/<instance>.json` and refresh transparently.

```bash
marfa --url https://marfa.example.com auth login
marfa auth whoami
marfa items list        # uses the stored OAuth tokens
marfa auth logout
```

**API key (recommended for scripts and CI)** — set `MARFA_API_URL` and `MARFA_API_KEY`, or pass `--url` / `--key` per call.

```bash
export MARFA_API_URL=https://marfa.example.com
export MARFA_API_KEY=marfa_k1_...
marfa items list
```

OAuth tokens take precedence when a stored session matches the resolved URL — an explicit `marfa auth login` should beat a stale env var. To force the API-key path: `marfa auth logout`, unset `MARFA_API_KEY`, or pass `--key` explicitly.

## Command surface

```
marfa [--url <url>] [--key <key>] [--instance <name>] [--json] [--verbose]
  auth         login, logout, whoami, delete-account
  profile      show, update, avatar {set, clear}
  items        create, get, list, update, delete, restore, transition,
               search, versions, edges, backrefs, stats, purge, bulk, action
  metadata     get, tag, untag, set, merge, list-tags,
               extensions {get, set, delete}
  edges        create, list, update, delete, types {list, create, delete}, bulk
  blobs        upload, exists, url, download
  types        scaffold, list, describe, register, update, delete
  keys         create, update, list, revoke
  apps         register
  webhooks     create, list, get, update, delete, deliveries
  tenant       config {get, set}
  connections  list, get, configure, pause, resume, install, uninstall,
               logs, activity, preview-event, verify, replay-dlq
  credentials  create-oauth-provider, create-api-token, list, revoke
  platform     tenants {list, show, suspend, unsuspend, quotas, metrics},
               keys {list},
               account-deletion {purge-now}
  docs         search, get, list
  export       [--output <file.ndjson>]
  health
  bootstrap    <url>
```

`marfa --help` and `marfa <subcommand> --help` are the canonical reference for flags. The sections below walk the more substantial surfaces.

## Examples

### Items and edges

```bash
# Plain create
marfa items create --type core.note --prop title="Hello" --prop body="World"

# Atomic item + outbound edges in one transaction
marfa items create --type core.highlight --prop text="..." \
  --edge references:<doc-id> --edge about:<topic-id>

# Natural-key upsert — re-running with the same --source + --source-id
# updates the existing row in place. Human mode prints "Created." or
# "Updated (natural-key match)." based on the server's 200/201.
marfa items create --type core.note --prop title="Hello" \
  --source my-script --source-id intro-001

# Filter by edge / backref / state / tier
marfa items list --type core.note --tier library --edge in-thread=<root-id>
marfa items list --backref about=<topic-id>
```

### Types

`marfa types scaffold` writes a starting schema. It is the one command in the tree that talks to nothing — no URL, no credential — because the validator it runs is bundled in the CLI, the same one the server applies at registration. A schema it emits is one `register` accepts.

```bash
marfa types scaffold carla.meal_plan --output carla.meal_plan.json
# edit the fields
marfa types register --file carla.meal_plan.json
marfa types describe carla.meal_plan
```

The default scaffold carries one field per supported attribute, each field's description explaining what its attribute does. `--minimal` emits a couple of starter fields instead; `--parent <type>` inherits and leaves out fields the parent already declares; `--force` overwrites an existing `--output`. With no `--output` the schema goes to stdout, so `marfa types scaffold carla.meal_plan | marfa types register` works as one line.

The full loop, and what to change between scaffold and register, is on [Authoring workflow](/guides/schema/authoring-workflow).

### Scoped API keys

`marfa keys create` exposes the full permission-map surface. Permission flags use `=` between key and level (the `:` separator collides with the edge-create grammar).

```bash
marfa keys create --label app-cred --source acme-app --role member \
  --type-perm core.note=write \
  --type-perm core.task=read \
  --extension-perm app.acme=write \
  --edge-perm about=write

marfa keys update <key-id> --type-perm core.note=read
```

`--is-platform` is silently coerced to false unless the calling credential is itself platform-flagged — the server enforces this.

### Metadata extensions

The metadata layer's `extensions` map is a JSON sidecar keyed by namespace. Reserved namespaces (e.g. `connection.runtime`) have constrained write semantics; the CLI is the surface, not the gate.

```bash
# Set an app-scoped namespace from inline JSON
marfa metadata extensions set <item-id> app.acme --data '{"cursor":"abc"}'

# Or from a file / stdin
marfa metadata extensions set <item-id> connection.runtime --file runtime.json
echo '{"k":1}' | marfa metadata extensions set <item-id> app.foo

# Read back
marfa metadata extensions get <item-id>
marfa metadata extensions get <item-id> --namespace app.acme

# Distinct tag enumeration with usage counts
marfa metadata list-tags
```

### Connections

`marfa connections` is the operator-facing surface for `system.connection` items of kind `integration`.

```bash
marfa connections list                              # all connections in the tenant
marfa connections list --integration acme.gdrive    # filter by integration
marfa connections get <connection-id>               # hydrates connection.runtime when present
marfa connections configure <connection-id> --extension connection.runtime --data '{"cursor":"..."}'
marfa connections pause <connection-id>             # archived
marfa connections resume <connection-id>            # active
marfa connections logs <connection-id> --severity error
marfa connections preview-event --item <id> --event-type item.created [--connection <id>]
marfa connections uninstall <connection-id>         # orchestrated teardown
```

`install` calls the platform's `POST /connections/install` orchestration — the admin-only JSON sibling of the browser consent flow. Returns the connection id, seed credential id, and an activity id.

`uninstall` calls the platform's `POST /connections/:id/uninstall` orchestration: revokes runtime credentials, deletes upstream OAuth tokens, revokes leased tokens, disables inbound webhook subscriptions, transitions state to `revoked`, emits `system.activity`, audits.

`preview-event` is a debug verb. Given an item id and an event type, it renders the queue envelopes the bridge would emit to each subscribed connector — without invoking any handler. Each envelope carries a `dispatch_reason` (`ok`, `self_event`, `cross_tenant`, `hop_budget_exceeded`, `subscription_inactive`) so operators can see why a subscriber would or wouldn't receive a given event. Pure server-side; safe to run repeatedly while debugging fanout.

`verify <id> --event <json>` synchronously dispatches a sample event through `runtime-control` into the connector via service binding. Operator-debug; requires a platform credential. Reads the runtime-control endpoint from `MARFA_RUNTIME_CONTROL_URL` or `--runtime-control-url`.

`replay-dlq <id> [--message-ids id1,id2] [--yes]` re-enqueues DLQ messages back onto their main queues for a connection. Destructive (handlers re-run upstream); interactive confirmation unless `--yes` is passed (and `--yes` is required in non-TTY contexts). `marfa connections logs <id> --dlq` reads the same DLQ surface.

### Credentials

`marfa credentials` manages the shared upstream credentials an Integration authenticates with — the `system.credential` items a Connection points at through `credential_ref`. Tenant-admin gated. Two creation verbs, one per authentication model: `create-oauth-provider` for an upstream that speaks OAuth, `create-api-token` for one authenticated by a long-lived bearer. Both return a `credential_id`, which the install pipeline takes as `credential_ref` on `POST /connections/install`. See [Integrations](/guides/connections/integrations) for how it consumes them.

```bash
# OAuth-backed upstream — the secret reads from stdin, so it never lands in shell history
marfa credentials create-oauth-provider --label "Acme Drive" \
  --authorize-url https://acme.example.com/oauth/authorize \
  --token-url https://acme.example.com/oauth/token \
  --client-id acme-client-id \
  --client-secret - \
  --upstream-base-url https://api.acme.example.com \
  --default-scope files.read

# Token-authenticated upstream — --auth-scheme defaults to Bearer
marfa credentials create-api-token --label "Acme Reader" \
  --upstream-base-url https://api.acme.example.com \
  --token - --auth-scheme Token

marfa credentials list                      # id, kind, state, label, last-used
marfa credentials list --limit 200 --cursor <cursor>
marfa credentials revoke <credential-id>    # prompts unless --yes
```

Passing `-` to `--client-secret` or `--token` reads the value from stdin, which keeps it out of the process table and shell history. `revoke` deletes the underlying `system.credential` item and is idempotent: revoking an id that no longer exists succeeds. It prompts for confirmation unless `--yes` is passed, and `--yes` is required outside a TTY.

### First run

`marfa bootstrap <url>` mints the first admin key against a fresh self-hosted server and writes it to `~/.marfa/<instance>.json`, so subsequent commands authenticate without further setup. It is unauthenticated by design: a new server accepts `POST /keys` until the first key exists, and that window does not reopen if the keys are later revoked. Against a server that already has keys the command fails with a pointer to `marfa keys create`. Full walkthrough in the [self-hosted quickstart](/introduction/quickstart-self-hosted).

```bash
marfa bootstrap http://localhost:8600
marfa bootstrap http://localhost:8600 --label ci --source ci-runner
```

The key value is printed once and cannot be retrieved later.

### Tenant config

```bash
marfa tenant config get
marfa tenant config set --file ./tenant-config.json
```

The `set` body is a full `TenantConfig` JSON object. Plumbing for the schema-enforcement levers (`strict_mode`, `source_allowlist`, `source_filter`) and feed-tier retention. Editing tenant config is rare enough that per-field flags would invent a parallel grammar that drifts from the wire shape; raw JSON is the call.

### Webhook deliveries

```bash
marfa webhooks list
marfa webhooks deliveries <webhook-id>           # recent attempts
marfa webhooks deliveries <webhook-id> --limit 200
```

### Account deletion

`marfa auth delete-account` initiates the hosted-mode account-deletion flow. The CLI verb is initiation-only — the server emails a confirmation link; clicking it transitions the account to `pending_deletion`. See [Account lifecycle](/self-hosting/operate/account-lifecycle) for the full state machine.

```bash
marfa auth delete-account            # interactive: prints flow summary, prompts y/N
marfa auth delete-account --yes      # non-interactive (required outside a TTY)
```

### Profile

`marfa profile` reads and updates the calling user's own profile — name, handle, avatar. The avatar surface is two sub-verbs (`set` uploads an image, `clear` reverts to the deterministic placeholder).

```bash
marfa profile show
marfa profile update --name "Alex"
marfa profile avatar set ./avatar.png
marfa profile avatar clear
```

### Platform (operator)

`marfa platform` is the cross-tenant operator surface, gated on platform credentials. The two trees:

- `platform tenants` — list, inspect, suspend / unsuspend, set quotas, per-tenant metrics.
- `platform account-deletion` — force the next pending-delete purger sweep without waiting for the 1-hour cadence.

```bash
marfa platform tenants list
marfa platform tenants show <tenant-id>
marfa platform tenants metrics <tenant-id>
marfa platform tenants suspend <tenant-id> [--yes]
marfa platform tenants unsuspend <tenant-id> [--yes]
marfa platform tenants quotas <tenant-id> --items 10000 --webhooks 50 \
  --blobs 5000 --storage-gb 25 --rate-per-minute 600 [--yes]

marfa platform keys list <tenant-id>

marfa platform account-deletion purge-now [--yes]
```

Suspend / unsuspend / quota writes prompt for confirmation unless `--yes` is passed; the prompt is required in non-TTY contexts. `purge-now` is the operator escape hatch when an account just crossed its grace window and you want the cascade now rather than at the next 1-hour tick.

### Docs

`marfa docs` queries the docs MCP at `docs.marfa.so/mcp` (override with `--docs-url`). Three subcommands mirror the MCP tool surface:

```bash
marfa docs search "items natural-key upsert"       # docs_search
marfa docs get /guides/core-model/items       # docs_fetch
marfa docs list                                    # docs_list_topics
```

Self-hosters point `--docs-url` at their own docs deployment. Output is markdown chunks (search) or full markdown body (get) by default; pass `--json` to print raw MCP envelopes.

## Output modes

Human-readable tables in an interactive terminal; JSON when stdout is a pipe, a redirected file, or `--json` is set explicitly. There's no `--human` flag — scripts that consume output get JSON, full stop.

```bash
marfa items list                  # table in a TTY
marfa items list | jq '.[0]'      # JSON automatically
marfa items list --json           # force JSON in a TTY
marfa items list > items.json     # JSON automatically (non-TTY)
```

## Multi-instance config

`--instance <name>` (or `MARFA_INSTANCE`) selects the config-file slot under `~/.marfa/<instance>.json`. Use it to keep separate sessions per server (e.g. `production` + `staging`):

```bash
marfa --instance production --url https://marfa.example.com auth login
marfa --instance staging    --url https://staging.example.com auth login

marfa --instance production items list
marfa --instance staging    items list
```

The default instance name is `default`.
