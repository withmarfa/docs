title: Local replica
description: A volatile in-process copy of one type, so no read in the interactive path crosses the network.
---

## What it is

`@withmarfa/sdk/replica` keeps an in-memory copy of a single type and follows the server's change stream. Reads come from memory. Writes apply locally first and are persisted through the ordinary API, so a list renders on the first frame and a keystroke shows before a round trip completes.

**The copy is volatile.** It lives in the process, it is rebuilt from the server on every start, and nothing survives a reload. That is what separates it from a [local-mode](/guides/identity/deployment-modes) client, which holds a durable store, queues writes made with no network, and keeps them across a restart. Reach for the replica to take a read out of the interactive path; reach for a local-mode client when a write has to survive the app being closed.

```ts
import { createReplicaCollection } from '@withmarfa/sdk/replica';

const notes = createReplicaCollection(client, { type: 'core.note' });

// Reads are synchronous — no await, no loading state for data already held.
for (const note of notes.values()) render(note);
```

`@tanstack/db` is an optional peer dependency. Install it alongside the SDK when you use this subpath; consumers that only use the client never pull it in.

## Writes go through the API

The replica is fed by the API and the change stream, never by a direct database connection. That is deliberate: permissions, validation and conflict resolution live on the server, and a client that reaches past the API reaches past all three.

So a write is optimistic locally and authoritative remotely:

```ts
const tx = notes.insert({ type: 'core.note', properties: { title: 'Draft' } });
// Already visible in `notes.values()` here.
await tx.isPersisted.promise; // Server has accepted it.
```

If the server refuses the write, the optimistic change is rolled back.

## Conflicts resolve the way they always do

An update through the replica uses the same conflict strategy as `client.items.update`, defaulting to `auto`. Pass `conflict` to change it:

```ts
createReplicaCollection(client, { type: 'core.note', conflict: 'manual' });
```

This is the same answer the direct client gives and the same answer the Apple kit gives. Two clients of one platform resolving a conflict differently is a difference a user can see.

## Two orderings that matter

**The subscription opens before the initial read**, and events arriving during it are buffered rather than dropped. The other order loses every change that lands between the read finishing and the stream starting, and loses it invisibly: the replica looks populated and is quietly stale.

**A cursor that ages out means reload, not reconnect.** When the server reports the resume cursor predates its retention window, the gap cannot be replayed. The replica discards its copy and reads again, and tells you it did:

```ts
createReplicaCollection(client, {
  type: 'core.note',
  onResync: () => showBriefly('Catching up'),
});
```

Reconnecting with the same cursor would loop; reconnecting without one looks healthy and silently skips everything in the gap.

## A replica has a size

The whole type is held in memory, so a replica of something large is a page that stops responding. `maxItems` bounds it, defaulting to 50,000 — far above any single-player type and far below what wedges a tab. A type that outgrows it reports through `onError` rather than filling the page, so you find out at the point it stopped fitting instead of from a bug report about the tab freezing.

```ts
createReplicaCollection(client, {
  type: 'core.note',
  maxItems: 5_000,
  onError: (err) => report(err),
});
```

## Build locally before you connect

Nothing about the replica requires a hosted instance. Point the client at a local server and the same code path runs — the replica's contract is the API and the change stream, both of which a self-hosted instance serves identically. Build against a local instance, then change the URL.

## Lifecycle

| Call | Effect |
| --- | --- |
| `collection.preload()` | Resolves once the initial read has completed. Optional; reads work before it. |
| `collection.utils.resync()` | Discard the local copy and read it again. |
| `collection.utils.stop()` | Stop syncing. The collection keeps what it last held. |
