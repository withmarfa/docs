The Swift SDK is a Swift Package Manager library for Apple platforms. It offers both [client modes](/guides/identity/deployment-modes) over one API surface: a remote HTTP client, and a local SwiftData store that reconciles with a server when one is configured. Swift 6 concurrency throughout.

Repository: [withmarfa/swift-sdk](https://github.com/withmarfa/swift-sdk). Pin to the major version that tracks your server.

Platforms: iOS 26+, iPadOS 26+, macOS 26+, watchOS 26+, tvOS 26+, visionOS 26+. On-device storage uses SwiftData — no third-party runtime dependencies.

## Install

In `Package.swift`:

```swift
dependencies: [
  .package(url: "https://github.com/withmarfa/swift-sdk.git", from: "x.y.z"),
]
```

Or in Xcode: **File → Add Package Dependencies → `https://github.com/withmarfa/swift-sdk.git`**.

## Two client modes, three factories

Remote is one factory. Local is two, because a local store either has a server to reconcile with or it does not:

<Tabs items={['Remote', 'Local, no server', 'Local, with a server']}>
  <Tab value="Remote">
    A thin typed HTTP client. Every call hits the server.

    ```swift
    import MarfaSDK

    let client = MarfaClient(
      url: URL(string: "https://marfa.example.com")!,
      apiKey: "marfa_k1_..."
    )

    let note = try await client.items.create(
      CreateItemInput(type: "core.note", properties: ["body": .string("Hello")])
    )
    ```

    Best for: server-first apps, scripts, CI, server-to-server integrations.
  </Tab>
  <Tab value="Local, no server">
    SwiftData-backed on-device store. No server, no API key. Same namespace surface — every call resolves against the local store.

    ```swift
    let client = try await MarfaClient.local(path: "/path/to/store.sqlite")

    let note = try await client.items.create(
      CreateItemInput(type: "core.note", properties: ["body": .string("Offline")])
    )
    ```

    Best for: offline-first apps, privacy-first apps, prototyping before adding a server.

    <Callout type="info">
      `types`, `keys` and `webhooks` throw `LocalModeUnsupportedError` on a local client with no server. **`blobs` is not server-only**: `upload` writes into that client's own store and `download` answers from it, while `exists` and `presignedURL` still throw, and so does `download` for a hash the store does not hold. `client.blobs.url(hash:)` never touches the network at all.
    </Callout>

    <Callout type="info">
      For iCloud sync, build the container yourself with `MarfaModelContainer.make(path:cloudKitDatabase: .automatic(containerIdentifier: "iCloud.example.app"))` and pass it to `MarfaClient.local(container:)`. The schema is CloudKit-compatible from day one. That is Apple's sync rather than Marfa's: it replicates the store's file, so conflicts resolve by CloudKit's rules and a space maps to an iCloud account.
    </Callout>
  </Tab>
  <Tab value="Local, with a server">
    Writes hit the local store first (optimistic) and replay against the server in the background. SSE keeps the local store fresh from the server. This is the shape the [sync contract](/sdks/sync-contract) governs.

    ```swift
    let client = try await MarfaClient.synced(
      url: URL(string: "https://marfa.example.com")!,
      apiKey: "marfa_k1_...",
      storePath: "/path/to/store.sqlite"
    )

    await client.syncEngine?.start()

    // Writes are instant and durable even offline
    let note = try await client.items.create(
      CreateItemInput(type: "core.note", properties: ["body": .string("Hello")])
    )
    ```

    `start()` is the whole of the setup. Coming online catches the store up before the client subscribes to live events: writes queued while the engine was stopped replay, and a store that has never synced imports what the server already holds. See [Sync engine](#sync-engine) for what an app watches while that first import runs.

    Best for: user-facing apps that need instant UI, offline tolerance, and multi-device consistency.
  </Tab>
</Tabs>

Two more factories cover common auth patterns:

- `MarfaClient.fromEnvironment()` — reads `MARFA_API_URL` and `MARFA_API_KEY`. Returns `nil` if unset. (Parity with the TypeScript SDK's `MarfaClient.fromEnvironment()`.)
- `MarfaClient.fromKeychain(service:account:url:accessGroup:)` — loads the API key from the system Keychain. Pair with `client.saveToKeychain(service:account:accessGroup:)` to persist one.

## Configuration

`ClientConfiguration` controls retry, timeout, conflict strategy, and CDN routing:

```swift
var config = ClientConfiguration(url: url, apiKey: key)
config.conflictStrategy = .auto         // or .manual, .callback
config.timeoutInterval = 30
config.resourceTimeout = 120
config.streamTimeout = 60               // event-stream inactivity bound
config.cdnBaseURL = URL(string: "https://cdn.marfa.example.com")  // optional
config.debugLogging = true              // full-body logging at .private

let client = MarfaClient(configuration: config)
```

`retryPolicy` on the configuration controls retry behavior for transient errors — bounded exponential backoff with jitter.

## Authentication

API keys are the simplest path — embed or seed via `fromKeychain(...)` and move on. Third-party apps that want per-user consent use [OAuth 2.1 with PKCE](/api-reference/authentication#oauth-21) instead. The SDK drives that flow end to end: `MarfaAuth` runs the authorize redirect and the token exchange, and returns a `TokenProvider` that refreshes and persists on its own.

### Sign in with OAuth

`MarfaAuth` wraps `ASWebAuthenticationSession` and PKCE. Construct it once, then hand the provider it returns to the client.

```swift
import AuthenticationServices
import MarfaSDK

let auth = MarfaAuth(
  issuer: serverURL,
  clientId: clientId,
  redirectURI: URL(string: "\(scheme)://callback")!,
  scopes: ["core.note:read", "core.note:write"],
  storage: KeychainStorage()
)

let provider = try await auth.signIn(presentationContextProvider: contextProvider)

let client = try await MarfaClient.synced(
  url: serverURL,
  tokenProvider: provider,
  storePath: storePath
)
```

On later launches, rehydrate from the Keychain without showing the sheet. `restore()` returns `nil` when nothing is stored, which is the cue to run `signIn(...)`:

```swift
if let provider = try await auth.restore() {
  let client = try await MarfaClient.synced(
    url: serverURL,
    tokenProvider: provider,
    storePath: storePath
  )
}
```

`auth.signOut(provider)` revokes the tokens server-side and clears them from storage.

### Refresh and rotation

The provider refreshes shortly before the access token expires. Concurrent callers share a single exchange, so a burst of requests cannot fan out into competing refreshes.

That single-flight behavior is load-bearing, because refresh tokens rotate: every exchange invalidates the previous token, and replaying a rotated one returns `400 token_reuse_detected` and revokes the whole pair. A rejected grant is therefore never retried. The provider discards the tokens, emits a sign-out event, and fails subsequent calls immediately until a fresh sign-in. Transient failures (`429`, `503`) are retried with bounded backoff honoring `Retry-After` and leave the session intact.

Subscribe to `authEvents` to present sign-in when a session ends. Background work such as sync has no call site to catch a thrown error, so this is the signal to build on:

```swift
for await event in provider.authEvents {
  switch event {
  case .signedOut(let reason):
    // .refreshTokenRejected, .reuseDetected, or .noRefreshToken
    await presentSignIn()
  }
}
```

<Callout type="warn">
  `ASWebAuthenticationSession` requires a UI host — a `UIWindow` on iOS, `NSWindow` on macOS. Server-side Swift, background extensions, and command-line tools cannot run this flow; they must use an API key.
</Callout>

See [Authentication — OAuth 2.1](/api-reference/authentication#oauth-21) for the full endpoint reference, scope grammar, consent-screen behavior, and refresh-token rotation rules.

## Data access

### Namespaces

The client exposes one property per resource, plus top-level `search` and `health`:

- `client.items` — item CRUD, transitions, versions, stats
- `client.metadata` — tags, metadata merge operations
- `client.extensions` — namespaced sidecar data
- `client.edges` — edges and custom edge types
- `client.blobs` — upload, download, URLs
- `client.types` — type schema listing and registration
- `client.keys` — API key management (admin)
- `client.webhooks` — webhook registration and deliveries
- `client.search(query:filters:)` — full-text search
- `client.health()` — server reachability check

### Items

```swift
let note = try await client.items.create(
  CreateItemInput(
    type: "core.note",
    properties: ["body": .string("Hello"), "title": .string("First note")],
    tier: .library,
    tags: ["intro"]
  )
)

let fetched = try await client.items.get(id: note.id)

let page = try await client.items.list(
  filters: ListFilters(type: "core.note", state: .active, limit: 50)
)
// page.data: [Item], page.cursor: String?, page.hasMore: Bool

try await client.items.update(
  id: note.id,
  properties: ["body": .string("Updated")],
  options: UpdateOptions(version: note.version)
)

try await client.items.transition(id: note.id, to: "archived")
try await client.items.delete(id: note.id)     // → trashed
try await client.items.restore(id: note.id)    // trashed → active
```

`items.list` returns `PaginatedResult<Item>` with `data`, `cursor`, `hasMore`. Two `AsyncSequence` helpers walk every page automatically — `client.items.all(filters:)` yields `Item`, and `client.items.allWithMetadata(filters:)` yields `ItemWithMetadata` pairs for views that render tags or favorite flags alongside the item.

```swift
for try await item in client.items.all(filters: ListFilters(type: "core.note")) {
  // processed page-by-page; no manual cursor handling
}
```

**An unfiltered list leaves out trashed rows, on a local store as well as against the server.** Until 17.0.0 the offline path returned every state while the online one did not, so the same call gave two different answers depending on whether a store was there — and a bin view built on the offline behavior emptied itself the moment the client synced. `state: .trashed` is the bin. `includeTrashed: true` is every state at once, which is what a resuming client needs in order to see a row reach the bin rather than simply vanish — the local equivalent of the server's `state=any`, which a single `ItemState` cannot express. A named `state` wins over it, because that is the narrower request.

**`system.*` items are left out of a listing unless you name a system type.** These are operational records — devices, connections, activity — rather than anything a person filed, and they would otherwise dominate an untyped list: a synced device holds far more activity rows than everything else combined. Naming the type outright returns them, which is what `client.connections.list()` does. Search behaves the same way, as does the server. Counts from `client.items.stats()` deliberately do not: they include every row, matching the server.

### Edges

```swift
let edge = try await client.edges.create(
  source: note.id,
  target: person.id,
  edgeType: "about"
)

let outbound = try await client.edges.listFromSource(sourceId: note.id)
let inbound  = try await client.edges.listToTarget(targetId: person.id, edgeType: "about")

// Global space-scoped listing across all items, by edge type.
let allReplies = try await client.edges.list(edgeType: "in-thread")

try await client.edges.delete(id: edge.id)
```

In local mode `edges.create` writes the edge to the local store and returns before anything reaches the network, under an id the store mints. The replay sends that id, so the server stores the edge under it as well and the `edge.created` event that follows updates the row the device already has instead of adding a second one beside it. `edges.bulk` does the same for every edge in the call, and honors a per-edge `BulkEdgeInputItem.id` you supply: the local row is written under your id and that id travels on replay.

Repeating a create under an id the server already holds for the same source, target and type is answered as a repeat rather than a duplicate, so a lost response costs a retry. The server publishes no event for a repeat, so no `SyncEvent.edgeCreated` follows one — the same as a repeated item create. See [Local IDs](#local-ids-uuidv7).

#### Batched backrefs

`edges.listToTargets(targetIds:edgeType:limit:)` resolves inbound edges for many targets in one call:

```swift
let backrefs = try await client.edges.listToTargets(
  targetIds: items.map(\.id),
  edgeType: "in-thread"
)
// backrefs: [String: [Edge]] — keyed by target id
backrefs["msg-1"]?.count   // reply count for msg-1
```

In local mode this is one SQL query against the local store. In remote mode it fans out via a bounded `TaskGroup`; cap concurrency via `ClientConfiguration.maxBackrefBatchConcurrency` (default 8). Empty `targetIds` short-circuits to `[:]`, duplicate ids are deduplicated, and unknown ids map to an empty array.

#### Atomic item + edges

```swift
let highlight = try await client.items.create(
  CreateItemInput(
    type: "core.highlight",
    properties: [
      "text": .string("important passage"),
      "locator_type": .string("offset"),
      "start_location": .int(123),
      "end_location": .int(189)
    ],
    edges: [
      CreateItemEdge(edgeType: "references", direction: .outbound, otherId: documentId)
    ]
  )
)
```

Item and edges land in one transaction.

#### Custom edge types

Mirrors the TypeScript SDK's `client.edges.types.*`. Admin-gated server-side.

```swift
try await client.edges.edgeTypes.create(
  CreateEdgeTypeInput(
    id: "team.commented-on",
    cardinality: .manyToMany,
    sourceTypeConstraints: ["core.note"],
    targetTypeConstraints: ["core.note"]
  )
)

let types = try await client.edges.edgeTypes.list()
try await client.edges.edgeTypes.delete(id: "team.commented-on")
```

#### Bulk writes and chunked iteration

Admin-only bulk surfaces match the [bulk operations](/guides/querying/bulk-operations) shape. A local client with no server iterates through the store and returns per-record outcomes; one with a server enqueues a single replay record; a remote client round-trips straight through.

On a local client with a server each entry is written locally before the replay runs, under an id the store mints where you did not supply one, and the queued page carries those ids so the server stores the same rows rather than a second set beside them — the same guarantee `items.create` and `edges.create` give, applied per entry. Supplying `BulkItemInput.id` or `BulkEdgeInputItem.id` yourself names the local row and travels the same way. See [Local IDs](#local-ids-uuidv7).

When the replay runs, the sync engine reads the per-entry answer rather than only the status. An entry the server refuses goes to the dropped-mutation log with the code the server gave it and emits `.mutationDropped`, so a page where some or all entries fail surfaces through `store.queryDroppedMutations()` instead of disappearing as a success. An entry the server resolved to a different row — an upsert matching on `(source, source_id)` rather than the id the page carried — is logged and left alone: the answer carries ids, not rows, so there is nothing to adopt, and the catch-up import is what reconciles the device.

`atomic` defaults to `true` server-side, so one refused entry rolls the whole page back. That rollback is always final — the route rolls back only on a validation-class refusal of one entry's content — and the page is dead-lettered carrying the code from `details.code` rather than the `bulk_atomic_rollback` wrapper, which says only that something was refused. Nothing was written, so nothing is lost by not retrying. Send `atomic: false` when you would rather have each entry reported on its own and the rest of the page applied.

`items.bulkAction` behaves the same way. It takes a filter rather than a list, but it still fails per item, and each id in `BulkActionResult.errors` becomes its own dropped row keyed by that id.

One thing to know if you read the log directly: for a bulk kind, `payloadJson` holds the whole enqueued call when the record was dropped as a unit, and the single refused entry when the row stands for one entry. The row id tells them apart — a `#` suffix means the second.

```swift
// Items
let items = try await client.items.bulk(BulkInput(items: payload))

// Edges — sibling endpoint for graph-half migrations
let edges = try await client.edges.bulk(BulkEdgeInput(edges: edgePayload))
```

For inputs larger than the server's 5000 per-call cap, the Swift SDK provides client-side chunking helpers — `items.bulkAll` and `edges.bulkAll`. Both clamp `batchSize` to `[1, 5000]`, aggregate per-record outcomes with absolute indices preserved, and accept an optional `progressHandler` for UI wiring.

```swift
let result = try await client.edges.bulkAll(
  largeEdgeSet,
  batchSize: 500,
  progressHandler: { completed, total in
    await progressModel.update(completed: completed, total: total)
  }
)
```

Cross-batch atomicity does not hold — each batch's `atomic: true` guarantee stops at its own server transaction. Callers needing strict all-or-nothing semantics across a run larger than one batch reconcile failures out-of-band.

`items.bulkAction(_:)` is the filter-driven sibling of `items.bulk` — instead of taking a list of records, it applies one action across every item matching a `BulkActionFilter`. Use it to archive, trash, restore, purge, retag, flip tier, patch properties, or bump `updated_at` across a server-side slice without fetching ids first.

```swift
let result = try await client.items.bulkAction(
  .transition(
    filter: BulkActionFilter(type: "core.note", state: .active, tags: ["stale"]),
    state: .archived,
    options: BulkActionOptions(dryRun: true, maxItems: 1000)
  )
)
// result.matched / .succeeded / .errored / .dryRun
```

`BulkActionInput` is a discriminated enum — `.transition`, `.purge`, `.updateTags`, `.updateLibrary`, `.updateProperties`, `.updateTimestamp`. Purge requires `options.confirm == "PURGE"`. A local client with a server queues the action for replay; one without applies it in a single local-store transaction.

In remote mode, `bulkAction(_:options:)` polls the server-side job until it reaches a terminal status — `completed`, `failed`, or `cancelled`. Surface progress to the UI by passing `BulkActionPollOptions(onProgress:)`:

```swift
let result = try await client.items.bulkAction(
  .purge(filter: BulkActionFilter(type: "core.scratch"), options: .init(confirm: "PURGE")),
  options: BulkActionPollOptions(onProgress: { job in
    Task { await viewModel.update(processed: job.processed, of: job.matched) }
  })
)
```

For explicit-control flows (returning a job id to an LLM, driving polling from a long-lived UI), `bulkActionAsync(_:)` POSTs and returns the `BulkActionJob` envelope without polling; `bulkActionStatus(jobId:)` and `bulkActionCancel(jobId:)` wrap the GET / DELETE endpoints. Cancellation throws `BulkJobCancelledError`; a failed job throws `BulkJobFailedError` carrying the worker's reason.

### Metadata

```swift
let metadata = try await client.metadata.get(itemId: note.id)
try await client.metadata.addTags(itemId: note.id, tags: ["urgent"])
try await client.metadata.removeTag(itemId: note.id, tag: "urgent")
try await client.metadata.set(itemId: note.id, input: MetadataInput(tags: ["work"]))
try await client.metadata.merge(itemId: note.id, input: MetadataInput(tags: ["q2"]))

// Distinct tags across the space, with usage counts.
let tags = try await client.metadata.listTags()
```

`metadata.listTags()` is mode-aware. In local mode the call fetches metadata rows whose parent item is not trashed and buckets the tags in Swift; in remote mode it hits `GET /metadata/tags`. Either way the return shape is `[TagWithCount]` ordered `count DESC, tag ASC`. A local-mode read short-circuits the network round trip.

When a local client has a server, the server's metadata row is authoritative. A `metadata.changed` event carries the whole row — tags and extensions together — and the engine replaces the local row with it, so a tag added on another device arrives without a re-import and a namespace the server no longer holds goes away here too. The same row lands on the initial import. Metadata converges to the server rather than being merged locally, which is what makes two devices agree.

`metadata.set` is the exception, and it mirrors the route it replays against: `PUT /items/{id}/metadata` writes the tag set and touches nothing else, so setting tags locally leaves the item's [extensions](#extensions) alone.

The `tier` field sits on the item itself, not in metadata. Set it on create via `CreateItemInput.tier`, or flip it post-creation via `items.update(id:properties:options:)` with `UpdateOptions(tier: .library)`. Tier-only updates don't conflict — tier is metadata-axis, last-writer-wins. `system.*` items have no tier; the field is optional in the SDK shape (`Tier?`).

#### Consuming per-item metadata in UIs

Two paths, depending on client mode:

- **Local mode.** Apps render lists of items with their tags or favorite flag — a timeline, a grid, a detail view. Use the SDK's reactive layer rather than polling. In Swift, `store.queryItemsWithMetadata(filters:)` returns an `@Observable ItemsWithMetadataQuery` that re-emits `[ItemWithMetadata]` pairs whenever any matching item or metadata row changes. The query reads from the local SQLite store, so no network round-trip per view frame. See [SwiftUI reactive queries](#swiftui-reactive-queries) for the full list.

- **Remote-only mode.** Fetch pairs in bulk via `client.items.listWithMetadata(filters:)` (wire: `GET /items?include=metadata`). For ad-hoc single-item lookups use `client.metadata.get(itemId:)`.

### Extensions

Namespaced sidecar data. Writes route through the mutation queue on a local client with a server.

```swift
try await client.extensions.set(
  itemId: note.id,
  namespace: "my-app.reading_progress",
  data: ["offset": .int(1234), "percent": .double(45)]
)

let all  = try await client.extensions.getAll(itemId: note.id)
let one  = try await client.extensions.get(itemId: note.id, namespace: "my-app.reading_progress")
try await client.extensions.delete(itemId: note.id, namespace: "my-app.reading_progress")
```

A namespace is merged into the item's existing extensions, so writing one leaves the others alone. On a local client with a server the whole metadata row still converges to it: an inbound `metadata.changed` event and the initial import both replace the local extensions with the server's, and a namespace missing from what the server sent is removed locally.

That is safe for a write made offline because the write is replayed, not discarded. The queued write reaches the server on reconnect, the server emits `metadata.changed` for it, and the row that comes back carries the namespace — so the extension ends up on every device without the client needing a local-wins rule. Namespaces under the reserved `connection.` root are silent and emit no event; see [extensions](/guides/core-model/extensions) for what that covers.

### Blobs

```swift
let response = try await client.blobs.upload(data: imageBytes, mimeType: "image/png")
// response.hash, response.mimeType, response.size

let (bytes, contentType) = try await client.blobs.download(hash: response.hash)
let exists = try await client.blobs.exists(hash: response.hash)
let url = client.blobs.url(hash: response.hash)
let signed = try await client.blobs.presignedURL(hash: response.hash, ttl: 300)
```

`upload` accepts an optional `onProgress: (@Sendable (Int64, Int64) -> Void)?` for remote clients that want inline byte-progress updates. The callback fires on the `URLSession` delegate queue with `(bytesSent, totalBytes)` — hop to the main actor yourself if you're driving SwiftUI state from it. A local client ignores the callback; progress for queued uploads arrives via [`BlobUploadProgressQuery`](#blob-upload-progress) on the reactive layer instead.

```swift
let response = try await client.blobs.upload(
  data: imageBytes,
  mimeType: "image/png",
  onProgress: { sent, total in
    print("\(sent) / \(total)")
  }
)
```

**A client with no server holds blobs of its own.** `upload` writes the bytes into that client's store and returns their content hash — the same hash the server would compute, so a store that later gains one addresses the same blob. `download` answers from the store. What it cannot do is answer a question only a server has: `exists` and `presignedURL` throw `LocalModeUnsupportedError`, and so does `download` for a hash the store does not hold.

Bytes written that way are **owned** rather than cached, and the difference is what keeps them: the read-through cache evicts least-recently-used and silently declines anything larger than its whole bound, and both of those are right for a copy of something the server holds and wrong for the only copy there is. Owned bytes are skipped by the eviction and accepted past the bound. They still count toward the total, so a store holding more of them than the bound stops caching rather than pretending it has room.

<Callout type="warn">
  Nothing uploads owned bytes to a server later. A local store has no outbox, so those blobs live on the device and nowhere else until something puts them there. `createWithAttachments` is refused on **any** client with a local store, synced ones included, not just a local-only one — it needs a bulk create as well as the bytes, and that is separate work.
</Callout>

<Callout type="warn">
  `client.types`, `client.keys` and `client.webhooks` are still server-only on a local client, and throw `LocalModeUnsupportedError`.
</Callout>

### Search

```swift
let results = try await client.search(
  query: "orwell",
  filters: SearchFilters(type: "core.bookmark", tier: .library)
)

// Tag filtering — AND semantics, matching ListFilters.tags.
let tagged = try await client.search(
  query: "orwell",
  filters: SearchFilters(tags: ["fiction", "classic"])
)
```

`SearchFilters.tier` is a `TierFilter?` — pass `.library` or `.feed` to narrow, or omit (`nil`) to return both. There's no `.all` synonym; `nil` already expresses that. `SearchFilters.tags` requires items to have every listed tag. `system.*` items are excluded from list and search results by default. **`ListFilters` and `SearchFilters` cannot opt back in**: the wire takes an `include=system` token and neither type can express it, so from this kit the only way to reach system items is to name one of their types — `type: "system.device"` — which narrows the read to that type rather than adding the rows to a full listing. The sync engine reaches them internally when it hydrates; the public filters do not. So a client that lists everything it can see and prunes what the listing did not carry must enumerate the `system.*` types it holds rather than relying on one unfiltered read, or it will prune every system row it has.

## Typed models

Every core type has a generated typed wrapper: `CoreNote`, `CoreBookmark`, `CoreTask`, `CoreHighlight`, `CoreEvent`, `CoreMessage`, `CoreMedia` / `CoreMediaBook` / `CoreMediaArticle` / `CoreMediaFilm` / `CoreMediaSong` / `CoreMediaAlbum` / `CoreMediaSeries` / `CoreMediaEpisode`, `CoreEntity` / `CoreEntityPerson` / `CoreEntityPlace`, `CoreFile` / `CoreFileImage` / `CoreFileAudio` / `CoreFileVideo`.

Each wrapper conforms to the `MarfaItem` protocol — `typeIdentifier`, a failable `init?(from: Item)` that validates the type string and required fields, typed property accessors, and `toProperties()` for creating new items.

```swift
let item = try await client.items.get(id: noteId)

guard let note = CoreNote(from: item) else {
  throw UnexpectedType()
}

print(note.body)           // typed String — required
print(note.title ?? "")    // typed String? — optional
print(note.version)        // from MarfaItem default accessors

// To create a new item from a domain type:
let newItem = try await client.items.create(
  CreateItemInput(type: CoreNote.typeIdentifier, properties: note.toProperties())
)
```

Subtype-aware: `CoreMediaArticle(from: item)` returns `nil` unless `item.type == "core.media.article"`. Required fields are non-optional (`CoreMediaArticle.title`, `.body`); optional fields surface as `T?`.

### Custom-type codegen

Apps that register their own types (`myapp.booking`, `myapp.user`, …) can generate Swift wrappers in the same shape as `CoreNote` and friends. The generated structs conform to `MarfaItem`, expose typed property accessors, a failable `init?(from: Item)`, and `toProperties()` for round-trip with `client.items.create` / `update`. Parent fields are flat-inlined, so a `myapp.booking` extending `core.note` exposes `body`, `title`, and the booking-specific fields on the same struct.

**1. Configure.** Drop a `marfa-codegen.json` at your repo root:

```jsonc
{
  "schema": 1,
  "source": { "mode": "local", "directory": "MarfaTypes" },
  "output": { "directory": "Sources/MyApp/MarfaTypes/Generated", "accessLevel": "public" },
  "types": { "include": ["myapp.*"] }
}
```

Drop one `<type.id>.json` file per type under `MarfaTypes/`:

```json
{
  "id": "myapp.booking",
  "parent": "core.note",
  "version": 1,
  "fields": {
    "start_at": { "type": "string", "format": "datetime" },
    "party_size": { "type": "integer" }
  },
  "required": ["start_at"]
}
```

For `"mode": "live"`, replace `directory` with `cacheDirectory` and let the sync executable populate the cache from `GET /types`.

**2. Generate.** Three entry points:

```bash
# SwiftPM command plugin — sandboxed, one shot.
swift package --allow-writing-to-package-directory generate-marfa-custom-types

# Same plugin, but pull schemas from a live server first.
swift package --allow-writing-to-package-directory --allow-network-connections all \
  generate-marfa-custom-types --sync

# Executables — CI-friendly, no sandbox prompts.
swift run codegen-custom-types
MARFA_API_URL=… MARFA_API_KEY=… swift run sync-custom-types
```

The `--sync` flow and `sync-custom-types` executable both call `GET /types`, so `MARFA_API_KEY` must carry the `list_types` permission. Generating from a vendored payload needs no credentials. `core.*` ids are always excluded from generation regardless of include/exclude globs — core wrappers ship with the SDK, so a misconfigured glob can't clobber them.

**3. Use the generated types.**

```swift
import SwiftUI
import MarfaSDK

struct BookingDetail: View {
  let item: Item

  var body: some View {
    if let booking = MyappBooking(from: item) {
      VStack(alignment: .leading) {
        Text(booking.title ?? "Untitled")
        Text(booking.startAt)
        Text("Party of \(booking.partySize ?? 0)")
      }
    } else {
      Text("Not a booking")
    }
  }
}

let created = try await client.items.create(
  CreateItemInput(
    type: MyappBooking.typeIdentifier,
    properties: [
      "start_at": .string("2026-05-01T18:00:00Z"),
      "party_size": .int(4),
      "body": .string("Dinner with J and S"),
    ]
  )
)
```

**4. Keep generated files fresh.** Commit the generated files. Add a freshness check to CI so a schema drift fails the build instead of going unnoticed:

```yaml
- run: |
    swift run codegen-custom-types
    git diff --exit-code -- Sources/MyApp/MarfaTypes/Generated
```

## SwiftUI reactive queries

On a local client, `client.makeStore()` returns a `MarfaStore` — a `@MainActor @Observable` factory for live queries driven by `ModelContext.didSave` with a short debounce window and a `FetchDescriptor` refetch per save.

```swift
import SwiftUI
import MarfaSDK

struct NotesView: View {
  @State private var store: MarfaStore?
  @State private var query: ItemQuery?

  var body: some View {
    List(query?.items ?? [], id: \.id) { item in
      Text(item.properties["body"]?.stringValue ?? "")
    }
    .task {
      let client = try? await MarfaClient.local(path: dbPath)
      self.store = client?.makeStore()
      self.query = store?.query(filters: ListFilters(type: "core.note"))
    }
  }
}
```

The query classes:

| Query | Returns | Notes |
|---|---|---|
| `ItemQuery` | `[Item]` | Matches a `ListFilters`. |
| `TypedItemQuery<T: MarfaItem>` | `[T]` | For example `TypedItemQuery<CoreNote>`. |
| `SingleItemQuery` | one item by id | `nil` when purged. |
| `ItemsWithMetadataQuery` | `[ItemWithMetadata]` | Each pair is an item plus its metadata row. Re-runs when either the items or item-metadata tables change. Use when a view needs per-item tags or favorite flags alongside the item, in place of hand-rolling a cache subscribed to `SyncEngine.events`. |
| `EdgesQuery` | `[Edge]` | Outbound edges for a `sourceId`, optionally filtered by `edgeType`. A second initializer takes only an `edgeType` to track every edge of a type across the local store, such as `store.queryEdges(ofType: "in-thread")` for taxonomy-style reply surfaces. |
| `TagsQuery` | `[TagWithCount]` | For the whole space. Re-runs the tag aggregation when items or metadata change. |
| `BackrefsQuery` | `[String: [Edge]]` | Keyed by target id. Re-runs when edges change. |
| `SearchQuery` | `[SearchResult]` | Offline search over the local store. The one query that does its work off the main actor. See [Local search](#local-search). |
| `PendingMutationsQuery` | `[PendingMutationSummary]` | For the mutation queue. See [Pending mutations](#pending-mutations). |
| `BlobUploadProgressQuery` | `[String: BlobUploadProgress]` | Keyed by content hash. See [Blob upload progress](#blob-upload-progress). |

All are `@Observable @MainActor`. Views observe them directly — no `ObservableObject`, no manual Combine plumbing. Each query exposes its data property (`items`, `item`, `edges`, `tags`, or `edgesByTarget`), `isLoading`, and `error`. Call `stop()` to tear down the underlying observation.

<Callout type="info">
  `TagsQuery` and `ItemsWithMetadataQuery` both re-run their aggregations on every relevant write. They're tuned for UI-scale surfaces, not unbounded analytics.
</Callout>

A remote client returns `nil` from `makeStore()` — the reactive layer only materializes when a local store is configured.

### Local search

`store.querySearch(text:filters:)` vends a `SearchQuery` — full-text-ish search served entirely from the local store, so it works offline and without a round trip.

```swift
let hits = store.querySearch(
  text: term,
  filters: SearchFilters(type: "core.note")
)

ForEach(hits.results, id: \.item.id) { hit in
  NoteRow(hit.item)
}
```

The search term is fixed for the life of the query. For search-as-you-type, build a new query per term and `stop()` the previous one; an abandoned scan is cancelled rather than run to completion.

This is the one reactive query that does **not** do its work on the main actor. A scan decodes the `properties` JSON of every candidate row, which is too much for a view update, so the whole thing is handed to the local store actor and the main actor is touched only to publish results.

<Callout type="warn">
  Local search is a scan, not an index. SwiftData exposes no FTS index and a predicate cannot reach inside a JSON column, so the query narrows on `type` / `state` / `tier` and then reads every surviving row. Cost runs to tens of milliseconds per thousand rows scanned, and `limit` caps the results rather than the work — a query matching 60,000 items takes seconds whether you ask for 20 results or all of them. Narrowing with `type` or `tier` is the cheapest lever you have. A corpus this outgrows wants the server index, not a faster device.
</Callout>

#### How local search differs from the server

`SearchFilters` is the same type on both sides and the shared defaults match — `system.*` and trashed records are excluded unless you ask for them, and `limit` defaults to 20. The differences below are real, so plan for them before swapping a screen between local and remote:

| | Server `GET /search` | Local `querySearch` |
|---|---|---|
| Fields matched | Every textual property | Only `title` and `body` |
| Tags | Indexed as searchable text | Filterable, not searchable |
| `type` | Resolves subtypes by inheritance | Compared literally |
| `limit` | `1...100`, rejected outside | Non-positive returns empty; larger honored |
| Ranking | BM25, with recency boost | Ordinal — title over body, whole over prefix over substring |
| Snippets | `snippetHtml` populated | Always `nil` |
| `filter` expression | Evaluated | Ignored |

The field gap is the one that surprises. Because only the literal keys `title` and `body` are read, a type that keys its text elsewhere never appears in local results at all: `core.entity` and its subtypes store `name`, `core.highlight` and `readwise.highlight` store `text` and `note`, and a `marfa.captured_email` matches on its `body` but never on its `subject`. That is a whole-type blind spot rather than a partial one.

`type` not resolving subtypes is a deliberate limitation rather than an oversight: inheritance needs the type graph, which the local store does not persist, and inferring it from the dotted name would be wrong for exactly the custom types an app defines, since a custom type may declare any parent regardless of its name.

### Pending mutations

`store.queryPendingMutations()` vends a `PendingMutationsQuery` over the local mutation queue — every write that's been enqueued but not yet replayed to the server. Use it to render per-item "syncing" badges, queue-depth banners, or retry toasts without subscribing to `SyncEngine.events` and reimplementing the projection.

Each entry is a `PendingMutationSummary` with `id`, `kind` (e.g. `.createItem`, `.uploadBlob`, `.setMetadata`), `itemId`, `createdAt`, and a projected `status`:

- `.pending` — queued, not yet attempted.
- `.inFlight` — the sync engine is issuing the transport call right now.
- `.retrying(attemptCount: Int, lastError: String)` — a transient failure, will retry on the next drain cycle.
- `.blocked(reason: PendingMutationBlockReason, attemptCount: Int, lastError: String)` — the engine has stopped retrying. The write is still queued, but nothing will move it until something changes app-side.

`.retrying` says wait; `.blocked` says the waiting will not end on its own, so it is the one to render differently. Five reasons:

| Reason | What happened | How it clears |
| --- | --- | --- |
| `.resolverMissing` | A `.callback` update reached replay with no resolver registered on the client. Blocks on the first attempt, because a second cannot differ. | Call `registerConflictResolver(_:)`. No retry call — the next drain finds the resolver and replays the write. |
| `.conflictUnresolved` | A `409` on an update outlived the conflict loop. **Most often an `.auto` write the server declined** — that is the ordinary outcome for one it could not resolve, not an edge case. Also `.manual`, a `.callback` resolver that kept declining, a `sourceId` the server already holds against another row, or a thinned ancestor, which reaches this state under every strategy — on the first refusal for `.manual` and `.callback`, and once the rebase budget is spent for `.auto`. | Resolve the conflict, then `syncEngine.retry(id:)`. **A thinned ancestor is not cleared by retrying under any strategy** — the row's idempotency key is spent, so the server answers the repeat from its record. Re-read the item and write against the version it holds. See below. |
| `.retriesExhausted` | A refusal that is neither permanent nor any of the others failed `maxReplayAttempts` times (default 5). | Fix the cause, then `syncEngine.retry(id:)`. |
| `.credentialRefused` | A `401` the transport's one refresh could not clear. **This one parks every queued write together**, because they all carry the credential that was refused. | A working credential, then `syncEngine.retryAll(reason: .credentialRefused)`. See [When the credential is refused](#when-the-credential-is-refused). |
| `.idempotencyKeyReused` | The key on this write has already answered a different body, so the server refuses it identically however often it is sent. Blocks on the first refusal rather than spending the ceiling. | **Nothing yet.** `retry(id:)` re-sends the same spent key; re-applying the edit queues behind the blocked row rather than around it. See below. |

`SyncEngine.retry(id:)` clears the block, resets the attempt count and asks for a drain.

**Environmental failures never block.** A connectivity failure, a `5xx`, a `429`, a cancellation and a suspended space are statements about the environment rather than about the write, and they clear on their own, so they retry indefinitely and their attempt count keeps climbing past the ceiling. Stranding a valid write behind an outage — and then needing someone to release it by hand — would be worse than the problem the ceiling solves.

**A `401` was in that list until 17.0.0 and is not any more.** It looked environmental and is not: everything else in the class clears without anybody doing anything, and a credential the server has refused clears only when a person replaces it. It blocks as `.credentialRefused`, and it takes the rest of the queue with it.

A blocked row holds back writes queued *after* it for the same item, so the queue's per-item ordering is kept; writes queued before it, and writes to other items, are unaffected.

<Callout type="warn">
  A queue whose only remaining rows are blocked also holds off the catch-up import, so a store that has never imported stays empty until the block clears. The import replaces every row it receives with no merge, and a blocked row is still an unsent write, so importing over one would discard it — the gate deliberately counts the whole queue rather than only what the drain will attempt. This was already true of a write that retried forever; blocking makes it visible and gives the app something to show.
</Callout>

The query refreshes on every `ModelContext.didSave`. Non-optional, unlike `queryBlobUploadProgress()` — the queue's table is in every store. `makeStore()` is the optional step, and a client with no store has nothing to vend it from.

### Blob upload progress

`store.queryBlobUploadProgress()` vends a `BlobUploadProgressQuery` that projects the four `.blobUpload*` sync events into a dict keyed by content hash. Use it for global upload HUDs or per-attachment progress bars without reading the raw event stream.

Entries are evicted on `.completed` — apps wanting a "recently completed" fade should snapshot the final value in their own view layer. `.failed` entries linger so a consumer can render a retry affordance; a subsequent transient retry overwrites the entry with a fresh `.uploading(0, total)`. Returns `nil` on a client with no sync engine: a remote client, or a local store with no server.

## Sync engine

On a local client with a server, `client.syncEngine` is non-nil. Start it when your app is ready to sync:

```swift
await client.syncEngine?.start()
```

The engine:

1. Watches `NWPathMonitor` via `ConnectionStateManager` and comes online when the network path does.
2. Catches up before it subscribes: drains the `MutationQueue` if anything is in it, then imports the library if this store has never completed an import. The event stream carries only what happens after it opens, so a store that has never synced is filled here or not at all, and a write queued while the engine was stopped replays here rather than waiting for a stream close that a live server never delivers.
3. Opens an SSE stream on `GET /events` and applies events into the local store: item creates, updates, deletes, restores, state changes and purges; edge creates, updates and deletes; and `metadata.changed`, which carries an item's whole metadata row and replaces the local one with it, storing the item it carries alongside it. What an item frame does to a row it already holds is [its own section](#what-an-inbound-item-event-does-to-a-row). An event type this build has no case for is logged rather than dropped in silence. Persists `Last-Event-ID` so reconnection resumes from the correct point. The engine reports `.online` for as long as that stream is open, rather than only once it has closed.
4. Drains the `MutationQueue` within a short debounce window of any new enqueue, and again when the stream closes, replaying local writes against the server. The mutation queue captures per-call `UpdateOptions.conflict` so the chosen strategy applies on replay. A closure is not serializable, so a `.callback` replay resolves through the resolver registered on the client rather than the one passed at the call site. See [Conflict handling](#conflict-handling).
5. On failure, records the attempt against the queue record and retries on the next reachability cycle — unless the failure is one no retry can clear. **A refused credential is the exception that stops everything at once**: see [When the credential is refused](#when-the-credential-is-refused). Those split two ways. A refusal the server will repeat forever is **dropped** to the dead-letter log. A write that could still succeed once the app changes something is **blocked**: kept in the queue, skipped by the drain, and surfaced through [pending mutations](#pending-mutations) so the app can say what has to happen. A `409` is the case worth knowing: on a create it is final, because a repeat of the caller's own id is acknowledged rather than refused, while on an update it resolves through the [conflict strategy](#conflict-handling) — and blocks if that strategy cannot settle it. See [Local IDs](#local-ids-uuidv7).

`stop()` tears the engine down gracefully.

### What an inbound item event does to a row

An item frame is not copied over the local row. The engine recomputes what the app should show from the server's row plus the writes still queued against that row, so an edit that has not reached the server stays visible **and** another device's change to a different field lands in the same frame. Trashing, restoring and transitioning rebase the same way, and `metadata.changed` — which carries an item alongside its sidecar — takes the same path rather than a second one.

A frame naming a version older than the row it describes does not apply. The comparison is "not older" rather than "newer": a reconnect resumes from its cursor and re-delivers the frame it stopped on, so a frame at the version the row already holds is applied rather than refused.

One limit is worth knowing. That version check is skipped while the device holds queued writes for the row, because a local edit bumps the stored version and the column is then this device's guess at what the server will assign rather than a server fact. The queued edit survives regardless; a stale frame can still land in a field that edit does not mention.

**When both devices changed the same field, the local edit wins** until the queue drains and the server settles it. Queued writes are applied last, so your own unsent value is what stays on screen and the other device's value for that field is not shown at all. That is the right answer for the person typing — the alternative replaces a sentence as they write it — but it does mean someone can be looking at a field another device has already changed, with nothing on screen saying so.

An item frame never writes the metadata layer. The server owns tags and extensions and announces them as `metadata.changed`.

A frame the engine refuses announces nothing. Sync events describe what the local store actually did, so a stale `item.deleted` that the version check turns away leaves the row active and publishes no `.itemDeleted` for it.

### What the engine reports about itself

An app showing a sync state had to keep hold of the connection-state object it passed into the factory to learn whether it was online, and fetch three arrays and measure them to learn how much was outstanding. It asks the client instead.

```swift
switch client.connectionState {
case .online, .syncing: statusLine = "Up to date"
case .connecting:       statusLine = "Connecting"
case .offline:          statusLine = "Offline"
}

for await state in client.connectionStateUpdates {
  // Yields the current state immediately, then each change.
}

guard let status = try await client.syncStatus else {
  // No engine on this client. Not "nothing to sync" — nothing measured.
  return
}
status.connection            // ConnectionState
status.queue.pending         // waiting for the next drain
status.queue.inFlight        // sent, no answer yet
status.queue.blocked         // [PendingMutationBlockReason: Int]
status.queue.deadLettered    // refused for good, kept to show
status.queue.outstanding     // pending + inFlight + blockedTotal
status.queue.isSettled       // nothing waiting and nothing stuck
status.lastCleanDrainAt      // when the queue last emptied cleanly
status.hydration?.fraction   // 0…1 while a first fill runs
```

Three shapes are worth knowing, because each is a claim the SDK deliberately does not make.

- **A client with no engine reports `nil`, not a zeroed status.** "0 pending, 0 blocked" claims a state of health nobody measured, and an app showing a green tick because it forgot to build a synced client is the failure this prevents. `syncStatus` throws rather than defaulting when the queue cannot be read, for the same reason: a store that will not answer is not a store with nothing in it.
- **A dead letter is not outstanding.** A refusal is finished business, and "1 unsent change" for a write nobody will ever send again tells a person to wait for something that will not happen.
- **`blocked` is counted by reason rather than totaled**, because what clears each one differs. A credential a person must replace and a conflict an app must settle are both stopped, and one number can only say that something is. `blockedTotal` is there when the sum is what you want.

Hydration progress is present only while a first fill is running or after one has finished in this process, and the denominator is bought once — after the first page says there is more, so an import that fits in one page pays no extra request. `SyncEvent.hydrationProgress(imported:total:)` reports it as it goes and **`SyncEvent.hydrationEnded(imported:completed:)` says it stopped**, whether or not it finished. Handle that one: without it a bar built on the progress events sits at whatever fraction the import died on. A `stop()` mid-import arrives as `completed: false` and is deliberately not distinguished from a failure — for a progress bar the two mean the same thing, so treat it as a reason to stop drawing rather than a reason to raise an error.

### When the credential is refused

A `401` the transport's one refresh could not clear is not a statement about the network. It clears when a person signs in again and not before, so it **parks the whole queue** rather than retrying:

```swift
for await event in client.syncEngine?.events ?? .init({ $0.finish() }) {
  if case .queueParked(let reason, let count) = event {
    // reason == .credentialRefused, count == how many stopped
    showSignInAgain(unsent: count)
  }
}

// Once a working credential is in place:
try await client.syncEngine?.retryAll(reason: .credentialRefused)
```

Every queued write carries the credential that was refused, so sending the rest one at a time would spend a request per write to learn what the first already said. Nothing is dropped.

- **Rows already blocked keep the reason they have.** A conflict awaiting review is not settled by a new credential, which is why `retryAll` takes a reason: releasing everything would tell an app those writes were moving again when nothing has changed for them.
- **`queueParked` is not latched, and on a fresh process it does not arrive at all.** This is the one to build against rather than around. A write made while the credential is still dead is attempted, refused, and parks the queue again, so it fires once per drain cycle that attempted anything — not once per queued write, and not once per parked row.

  **On a relaunch over an already-parked queue it fires never.** Every row is blocked, so the drain finds nothing replayable and returns early; the clean-drain stamp is withheld because a parked row is not a settled one; and the cycle emits nothing. An app that renders this state from the event alone shows a healthy surface, indefinitely, over a queue that cannot move — and the person is told to sign in again only if they happen to make a write that gets refused.

  So read the state, not the event: `fullSyncState`, `queryFullSyncState()`, or `status.queue.blocked[.credentialRefused]`. All three ask whether it is still true rather than whether it just changed, and all three answer on a cold start. Use the event to know when to re-read, if at all.
- **A parked queue is not a synced one.** `FullSyncState` gains `parked(reason:count:)`, and both `fullSyncState` and `queryFullSyncState()` report it while any write is parked on a refused credential. It outranks `synced(at:)` and `failed(at:error:)`, which matters more than it sounds:

  - A store that synced cleanly an hour ago still holds that timestamp, and a refused credential does not erase it. Without the new state an app renders "last synced an hour ago" over a queue that has stopped — true, and not the answer to the question being asked.
  - A transient failure recorded *before* the parking would otherwise stand forever. A clean drain is the only thing that clears one, and a parked queue cannot produce a clean drain, so the app would show "the Internet connection appears to be offline" indefinitely while the remedy was to sign in again.

  `fullSyncState` stops reporting `.parked` the moment `retryAll` releases the rows, because it reads the live counts. Getting back to `synced(at:)` rather than `failed(at:error:)` needs a drain to succeed after that.

**A spent idempotency key blocks that one write, not the queue.** It shares the *timing* — it blocks on the first refusal rather than spending the ceiling — and nothing else: it produces a `mutationBlocked`, never a `queueParked`, and `fullSyncState` does not go to `.parked` for it. A refused credential is the only reason that stops everything, because it is the only one that is about the client rather than about a write.

**A `.conflictUnresolved` row can be a thinned ancestor, and what clears it depends on the strategy the write carried.** The write names a version history no longer retains.

**`retry(id:)` cannot clear it under any strategy, and the reason is the key rather than the version.** A retry does start a fresh conflict loop — the block is cleared, the attempt counter resets, and under `.auto` the rebase runs again. But the row's idempotency key is minted once and never rewritten, and the payload it re-sends is byte-identical, so attempt zero carries the same key as before. The server retains a `409` against a key rather than releasing it, and answers a repeat from the record. The rebased attempt derives its key from that same row key and the version the record reports, so it too is answered from the record, and the loop walks the same refusals to the same throw.

The strategies differ only in **when** the row parks: `.manual` and `.callback` on the first refusal, because rebasing would apply an edit onto a base the caller never saw, and `.auto` once its rebase budget is spent.

**Settling it means re-reading the item and writing against the version the server holds**, which makes a fresh row with a fresh key.

**The typed error does not reach the row.** `AncestorUnavailableError` carries `current` and `requestedVersion`, but a blocked mutation surfaces as `PendingMutationStatus.blocked(reason:attemptCount:lastError:)` and `lastError` is a formatted string — `code=ancestor_unavailable status=409 message=…`. Recognize the row by that code, and re-read the item to learn the version, because the object with it on is gone by the time the queue is what you are looking at.

`idempotency_key_reused` means the key has already answered a different body, so repeating it is refused identically however often anyone tries. **`retry(id:)` does not clear it** — the key is spent, not the write.

**And neither does re-applying the edit, which is what this page used to recommend.** The key is minted once at enqueue and never rewritten, so a replay carries the spent one. A fresh edit is a new row under the same local id, queued *after* the blocked one — and the engine defers every later write to an item behind that item's blocked row, deliberately, because releasing them out of order is how an edit gets lost. So the new write waits behind the thing it was meant to route around.

There is no public door to discard a blocked row: `SyncEngine`'s release surface is `retry(id:)` and `retryAll(reason:)`, and `retryAll(reason: .idempotencyKeyReused)` releases the row into the same refusal. **Nothing in the SDK clears it**, so a row blocked this way strands that item and every later write to it. An app should say so rather than offer a control, and should not present re-applying the edit as a remedy.

Everything that genuinely clears on its own is unchanged. A `5xx`, a rate limit, a dropped connection, a cancellation and a suspended space all ride it out without blocking, which is what keeps a valid write from being stranded behind an outage.

### Stream lifetime

One stream is held for as long as the engine runs. The server sends a heartbeat comment every thirty seconds, which keeps the connection alive and, on the client, keeps resetting the clock that would otherwise end it. See [Realtime](/guides/realtime/realtime) for the frame format.

Three things close a stream:

- **Silence.** `ClientConfiguration.streamTimeout` bounds how long the stream may deliver nothing at all, heartbeats included. It defaults to 60 seconds, twice the server's heartbeat interval, so one late or dropped ping does not end a stream that is otherwise healthy. Raise it for a deployment whose proxy batches SSE frames. A value below the heartbeat interval tears down healthy streams.
- **A network change.** `ConnectionStateManager` watches the path, and the engine opens a new stream on the way back.
- **The server.** A restart, a shutdown, or the `catchup_too_old` case where the events the cursor points at have been discarded.

Elapsed time is not among them. `ClientConfiguration.resourceTimeout` bounds an ordinary request's whole life and is not applied to the stream's session, which keeps URLSession's own seven-day default — a ceiling no stream is expected to reach, rather than no ceiling at all.

Opening the stream is bounded by `streamTimeout` too, not by the shorter `timeoutInterval`, so a subscribe against a server that accepts the connection and then never answers waits twice as long as an ordinary request would before giving up. That is the right trade here: the reconnect path retries anyway, and a slow open is far more often a server assembling a replay than a dead one, so failing fast would abandon exactly the subscribes worth waiting for.

Whatever closes it, the close is handled the same way: replay the mutation queue, then reconnect after a back-off, resuming from `Last-Event-ID`. A stream that failed without delivering anything backs off exponentially; one that closed healthily reconnects on the base delay.

### Proactive drain

The engine listens on `MutationQueue.drainRequests` and schedules a replay within `drainDebounceInterval` of each enqueue while the connection is online, so a device that's online but idle flushes pending writes promptly rather than waiting for the next SSE reconnect. Because the engine reports `.online` for as long as its stream is open, that covers the ordinary case of an app that is simply running. Offline and syncing states short out: the queue sits silently, or an in-flight drain coalesces the burst. The window before the stream opens is the one to know about — it spans the first import, so it is wide enough for someone opening the app to write inside it — and a request made there is dropped by the state gate rather than deferred, so the engine asks the queue again itself once the stream is up. Tune via `SyncEngine.init(drainDebounceInterval:)` (default `.milliseconds(150)`).

### Watching the first sync

`SyncEngine.fullSyncState` is a point-in-time read; `store.queryFullSyncState()` returns an `@Observable` `FullSyncStateQuery` bound to the same signals, which is what a SwiftUI app renders against.

```swift
if let sync = store.queryFullSyncState() {
  switch sync.state {
  case .notYetSynced:         ProgressView("First sync…")
  case .syncing:              ProgressView("Syncing…")
  case .synced(let at):       Text("Last synced \(at, format: .relative(presentation: .named))")
  case .failed(_, let error): Text("Couldn't sync: \(error.localizedDescription)")
  case .parked(_, let count): Text("Sign in again — \(count) unsent")
  }
}
```

A store that has never imported reads `.notYetSynced` until that first import lands, and `.synced(at:)` once it does — it cannot report itself synced before then, whatever its write queue is doing, because an empty queue on an empty store is a device that has not started rather than one in sync. It reads `.syncing` in between only while queued writes are replaying. An import that fails reads `.failed(at:error:)` — the stream still opens, so the device keeps receiving live events, and the next time it comes online it imports again.

**Unless writes were already queued when the credential was refused.** The engine drains before it imports, so a `401` meets the queue first — and if there is anything live in it, those writes park and the state reads `.parked(reason:count:)` rather than `.failed`. `.parked` outranks both `.synced` and `.failed`, so a later network failure cannot bury it. On a fresh store with an empty queue there is nothing to park, and a refused import reads `.failed(at:error:)` as above.

### Re-importing on demand

`performInitialSync(pageSize:)` runs that same import explicitly. A fresh store does not need it: the engine imports on its own when it comes online. Reach for it when you want to re-pull the library deliberately. The engine also uses it for the retention-gap case, where the server has discarded the events your cursor points at.

It refuses over a queue that has not drained, throwing `InitialSyncError.pendingMutations(count:)`. The import replaces every row it receives with no version check and no merge — unlike a stream frame, which [rebases](#what-an-inbound-item-event-does-to-a-row); the two paths differ deliberately, because the import is a bulk replacement of the whole library rather than news about one row. So importing over a write that has not reached the server would discard it silently. Let the engine drain first — `hasPendingMutations` reports when it is done — and ask again. A call made while the engine is already catching up joins that run rather than starting a second one.

**The import also removes the rows the server did not send.** A row purged while the device was away is absent from the answer rather than changed in it, so no event describes it and nothing else ever corrects it — this pass is the only thing that can notice. Each row it removes is announced as `.itemPurged(id:)`.

Three things keep that from destroying work, and all of them matter if you drive the import yourself, because each one is a different set of rows that would otherwise go.

- **It reads every lifecycle state** rather than the default slice, which excludes trashed rows. Without that widening a full bin reads as a server that purged all of it, and the device's bin would empty itself on every re-import.
- **It reads `system.*` rows**, which the same route also excludes by default while the event stream that fills the store does not. Without that, a re-import would remove every device, connection and activity row the store holds — `client.connections.list()` would come back empty against a server that still has all of them, and no later event would correct it, because no event describes a row that did not change. Holding them is separate from surfacing them: they stay out of search results unless you name a `system.*` type, exactly as before.
- **A row the mutation queue still holds a create for is never removed.** The refusal above asks once, before the first page, so a write made during the paging that follows is queued *and* absent from the answer, which is exactly the shape a prune would otherwise mistake for a purge.

The common thread is worth holding onto if you are reading the import as a plain read: it is not one. Every id it sees is a keep-set, so anything that narrows the answer widens what gets deleted.

**A partial answer is refused rather than pruned against.** If a page reports more results and carries no cursor to reach them with, the import throws `InitialSyncError.unresumablePage`, because finishing on a partial answer would delete every row the pages it never read would have named. Marfa's own server does not send that pair; the check is here because this SDK also talks to self-hosted servers. A read that fails partway through behaves the same way — the error propagates and nothing is pruned.

That refusal is not a rollback. Each page is written as it arrives, so rows that landed before the throw are still in the store, and on the edges pass the item pass has already finished — its prune has run and its `.itemPurged` events have already fired. The guarantee is the narrower one: **no row is removed on the strength of an answer nothing finished reading.** Re-running the import is the way to reconcile, and it is safe to do.

Edges are not pruned.

### Sync events

Subscribe to `client.syncEngine?.events` for typed sync activity:

```swift
for await event in client.syncEngine?.events ?? .init({ $0.finish() }) {
  switch event {
  case .synced(let at):                          // every successful drain
  case .failed(let error):                       // last error during a drain
  case .conflictAutoMerged(let payload):         // replay auto-merged a 409
  case .itemCreated(let id):
  case .itemUpdated(let id):
  case .itemDeleted(let id):                     // trashed; the row can come back
  case .itemPurged(let id):                      // gone for good; the local row is removed
  case .edgeCreated(let id):
  case .edgeUpdated(let id):                     // an edge edited on another device
  case .edgeDeleted(let id):
  case .mutationDropped(let kind, let itemId,
                        let attempt, let error): // permanent failure; queue record removed
  case .mutationBlocked(let kind, let itemId,
                        let reason):             // stopped retrying; queue record kept
  case .queueParked(let reason, let count):      // every queued write stopped at once
  case .syncing:                                 // a drain started, or a parked queue was released
  case .storeRecovered(let recovery):            // the store was rebuilt; the queue was rescued first
  case .hydrationProgress(let imported,
                          let total):            // a first fill, once per page
  case .hydrationEnded(let imported,
                       let completed):           // it stopped, finished or not
  case .blobUploadStarted(let hash, let total):
  case .blobUploadProgress(let hash, let sent, let total):
  case .blobUploadCompleted(let hash):
  case .blobUploadFailed(let hash, let error):
  }
}
```

`.itemPurged` is not the news `.itemDeleted` carries. A delete says the row was trashed and can come back; a purge says it is gone for good, and nothing later will correct a copy of it, so a view still holding one is showing something that no longer exists anywhere. It fires for both routes a removal reaches a device by — the server's `item.purged` announcement, and a re-import that finds the row absent. The reactive queries update on their own; subscribe only if you hold item ids outside the store.

The four `.blobUpload*` cases are the raw signal that `BlobUploadProgressQuery` projects into its observable dict — most apps subscribe to the query, not the events directly.

**`.hydrationEnded` is the one most easily left out and most worth handling.** `.hydrationProgress` fires once per page while a first fill runs, and nothing else says it stopped — so a progress bar built on the pair without this sits at whatever fraction the import died on. It fires whichever way the fill ended, and `completed: false` covers a `stop()` mid-import as well as a failure: for a bar those mean the same thing, so treat it as a reason to stop drawing rather than a reason to show an error.

`.mutationDropped` fires when a queued mutation meets a failure no retry can clear — a `400`, `403` or `404`, or a `409` on a create — and is removed from the queue and written to the dead-letter log. A mutation is dropped because the server's answer is final, not because it has been attempted enough times.

`.mutationBlocked` fires once, when a mutation stops for a reason the app can still do something about. The write stays in the queue and can be replayed; see [pending mutations](#pending-mutations) for the reasons and how each clears. It is the one case with a ceiling — `.retriesExhausted` — and that ceiling counts only refusals outside the network class.

**It does not fire once per blocked row when the queue parks.** A refused credential emits `.mutationBlocked` for the single row that met the `401`, and the rest are parked together with no per-row event. So a list of blocked writes folded from this event shows one entry while ten are stuck. Build that list from `store.queryPendingMutations()` or `status.queue.blocked` instead, which read the queue rather than recalling it.

`.failed` means the cycle could not drain. A blocked row does not produce it: the engine has stopped asking about that row, so a cycle whose only outstanding writes are blocked reports `.synced`.

**With one exception, and it is the one worth knowing.** The cycle that parks the queue reports `.queueParked` and neither `.synced` nor `.failed`: the clean-drain stamp is withheld because a parked row is not a settled one, and a green tick over a queue that cannot move until somebody signs in is louder than the failure it would be replacing.

**A cycle with nothing replayable reports nothing at all.** With every row blocked the drain returns before it reaches either emit, which is the silence a relaunch meets — and it is why the state, not the event, is what a surface should read.

A later write to an item that has no parked row is still replayable, so that cycle runs, meets the same refused credential, and re-emits `queueParked` from the tail. The emit is gated on the standing count rather than on whether this cycle did the parking, so it repeats for as long as anything is attempted.

Multi-subscriber — each access to `events` returns a fresh stream; past events are not replayed to late subscribers.

### End-to-end subscription

Own the lifecycle from a single place — typically an `@Observable` service or a SwiftUI `.task { }` — so the subscriber task cancels when the view goes away and the sync engine stops when the app backgrounds.

```swift
import MarfaSDK
import Observation

@MainActor
@Observable
final class SyncActivity {
  private(set) var lastSyncedAt: Date?
  private(set) var lastError: Error?
  private(set) var pendingConflictedCopies: [String] = []
  /// Blocked writes, read from the queue rather than folded from events.
  ///
  /// **Do not build this list from `.mutationBlocked`.** A parked queue emits
  /// it for the one row that met the `401` and for none of the rest, so a
  /// folded list shows one entry while ten are stuck. The query is `@Observable`
  /// and updates itself, so there is nothing to keep in step.
  private var pending: PendingMutationsQuery?
  var blockedWrites: [PendingMutationSummary] {
    pending?.mutations.filter {
      if case .blocked = $0.status { return true }
      return false
    } ?? []
  }

  private var client: MarfaClient?
  private var task: Task<Void, Never>?

  // 1. Create — on app launch / sign-in.
  func start(client: MarfaClient) async {
    self.client = client
    // The queue's table is in every store, so this is optional only because
    // `makeStore()` is — a client with no store has nothing to vend it from.
    pending = client.makeStore()?.queryPendingMutations()
    await client.syncEngine?.start()

    // 2. Subscribe — each access to `events` is a fresh stream.
    task = Task { [weak self] in
      guard let events = client.syncEngine?.events else { return }
      for await event in events {
        guard !Task.isCancelled else { break }
        await self?.handle(event)
      }
    }
  }

  /// The first fill's fraction, or `nil` when no import is running.
  ///
  /// Absent for a single-page import and whenever the count request fails, so
  /// a bar built on this has to tolerate never appearing.
  private(set) var firstFill: Double?

  // 3. Handle — side-effect into observable state.
  private func handle(_ event: SyncEvent) {
    switch event {
    case .synced(let at):
      lastSyncedAt = at
      lastError = nil
    case .failed(let error):
      lastError = error
    case .conflictAutoMerged(let payload):
      if let sibling = payload.conflictedCopyId {
        pendingConflictedCopies.append(sibling)
      }
    case .mutationBlocked:
      // Nothing to do. `blockedWrites` above reads the queue, which is right
      // for a park as well as for a single blocked row; acting on this event
      // would be a second answer to the same question, and the narrower one.
      break
    case .queueParked(_, let count):
      // The credential is spent. Every queued write has stopped and only a
      // person can start them again — `syncEngine.retryAll(reason:)` once a
      // working credential is in place.
      signInAgain(unsent: count)
    case .hydrationProgress(let imported, let total):
      firstFill = Double(imported) / Double(max(total, 1))
    case .hydrationEnded:
      // Whether or not it finished. Without this a bar built on the progress
      // events above sits at the fraction the import died on.
      firstFill = nil
    case .syncing, .itemCreated, .itemUpdated, .itemDeleted, .itemPurged,
         .edgeCreated, .edgeUpdated, .edgeDeleted, .mutationDropped,
         .storeRecovered,
         .blobUploadStarted, .blobUploadProgress,
         .blobUploadCompleted, .blobUploadFailed:
      break   // SwiftData-backed MarfaStore queries pick these up automatically
    }
  }

  // 4. Tear down — on sign-out / app termination.
  func stop() async {
    task?.cancel()
    task = nil
    await client?.syncEngine?.stop()
    client = nil
  }
}
```

The SDK's reactive queries already update when SSE writes land in the local store, so most views don't need to observe `events` directly. Subscribe when you need *sync-lifecycle* side effects — a "last synced" footer, a conflict toast, a sign-out-on-auth-failure hook.

See [Realtime](/guides/realtime/realtime) for the underlying SSE contract, event catalog, and `Last-Event-ID` semantics.

### Local IDs (UUIDv7)

`LocalStore.createItem` and `LocalStore.createEdge` both mint a UUIDv7 — RFC 9562, timestamp-prefixed, globally unique. Pass `CreateItemInput.id` explicitly to override for an item (still encouraged for callers that need to reference the new id before `createItem` returns; both paths produce server-compatible IDs). For `edges.create` an edge's id is always the one the store mints; `edges.bulk` accepts a per-edge override, and honors it on both sides.

In local mode that id travels. The replayed `POST /items` and `POST /edges` each name the id the store minted, the server stores the row under it, and the event that comes back afterwards matches the row already there. An id read from a `create` call is therefore the id the row keeps once the write reaches the server, not a placeholder swapped for a server id later on.

Both bulk doors do the same, per entry: a replayed `POST /items/bulk` and `POST /edges/bulk` name the id each local row was written under, whether you supplied it as `BulkItemInput.id` / `BulkEdgeInputItem.id` or left the store to mint one. See [Bulk writes](#bulk-writes-and-chunked-iteration).

Naming the row is also what makes a create safe to send twice. If the response to a create is lost, the sync engine replays it under the same id; the server recognizes an id the caller already holds, writes nothing, publishes nothing, and answers with the stored row. The replay adopts that row — item and metadata — so a device that retried a create ends up showing what the server actually holds rather than the copy it minted before the round trip.

A create that comes back `409` instead is refused for good. The id names a row in a space this caller cannot see, or the row's type is not the one declared, and neither changes however often the request is repeated. The engine drops the mutation to the dead-letter log with the server's own code — `conflict` or `type_mismatch` — emits `.mutationDropped`, and surfaces it through `store.queryDroppedMutations()`.

Whatever the refusal was — a `400`, `403` or `404` as much as a `409` — a dropped create takes its local row with it, so nothing is left showing something that can never sync. A dropped `createItem` also cascades to the mutations queued behind it, and the edge rows among those are removed too.

## Conflict handling

See [Errors — version_conflict](/api-reference/errors#version-conflict) for the enriched 409 payload and [Conflicts](/guides/schema/conflicts) for the resolution model. The Swift SDK exposes the three modes as `ClientConfiguration.conflictStrategy` and `UpdateOptions.conflict`.

```swift
try await client.items.update(
  id: note.id,
  properties: ["body": .string("...")],
  options: UpdateOptions(
    version: note.version,
    conflict: .callback,
    resolve: { conflict in
      return mergeManually(conflict)
    }
  )
)
```

`.auto` (default), `.manual` (throws `ConflictError` with `current`, `ancestor`, `conflictingFields` and `clientPatch`), and `.callback` are the three modes. The type's merge policy is not on that error — it reaches a resolver on `ConflictData.mergePolicy`, because it is what a resolver decides with and what a thrown error has already stopped needing.

**`.auto` resolves on the server, as of 17.0.0.** The kit sends `conflict=auto` and the server merges inside the write's own transaction by the type's policy, answering `200` with a `conflict_resolution` report. `.manual` and `.callback` send nothing, because the server's default for an omitted parameter is `manual` and silence says exactly what they mean.

<Callout type="warn">
  **This release requires a server that implements the `conflict` parameter, and degrades silently against one that does not.** A server ignores a query parameter it does not know, so an older deployment drops `conflict=auto` and returns the `409` envelope, so on a synced client every conflicted `.auto` write becomes a blocked mutation instead of a merged one, and on a remote-only client it throws `ConflictError` to the caller. There is no client-side fallback — the on-device merge was removed in the same release. Check the server before upgrading a self-hosted deployment.
</Callout>

The on-device three-way merge is gone, and it is worth knowing what it did, because a `409` under `.auto` now means something different from what it used to. Two implementations of one rule did not agree: the kit's `last_writer_wins` kept the *earlier* write where the server keeps the later one, so two devices editing one field reached different answers depending only on which kit resolved it. The kit also spawned its own `keep_both_copies` sibling through an unkeyed create, so a lost response made two siblings.

So under `.auto` a `409` is now a conflict the **server could not** resolve. It surfaces as `ConflictError` and is not retried — there is nothing left on the device to resolve it with.

`conflicted-copy` still exists as a tag, and an app filtering for siblings still wants it. What changed is who applies it: the server does, and the device no longer creates one.

**A write whose base version has been thinned away** returns [`ancestor_unavailable`](/guides/schema/conflicts#when-the-ancestor-is-gone) rather than a `version_conflict` naming every field — the safer answer, because the old shape led the kit to spawn siblings holding text nobody typed. **17.0.0 models it.** `AncestorUnavailableError` carries `current` and `requestedVersion`. Under `.auto` the kit rebases onto the version the server says it holds and retries within the call; under `.manual` and `.callback` it is thrown, because rebasing would apply an edit onto a base the caller never saw, which is the decision those strategies exist to keep.

The `SyncEngine.events` stream emits `.conflictAutoMerged(payload:)` whenever a replay **auto-merge** fires. Only `.auto` produces one: the payload is built from the server's `conflict_resolution` report, and a `.callback` resolution carries none because the caller resolved and the server merely accepted an ordinary write.

```swift
public struct ConflictAutoMergedPayload: Sendable {
  public let itemId: String                          // the original item
  public let mergedItemId: String                    // the original item id (post-retry)
  public let conflictedCopyId: String?               // the sibling, when keep-both spawned one
  public let fields: [String]                        // the conflicting fields
  public let strategy: [String: MergePolicyStrategy] // per field: .lastWriterWins or .keepBothCopies
}
```

`strategy` is per field rather than one verdict for the write, because a type's policy is declared per field and one update can cross both. Apps typically toast when `conflictedCopyId != nil` — the user's in-flight edit was preserved as a sibling rather than discarded.

### Resolvers on the replay path

In local mode the chosen `conflict` strategy is captured with the queued mutation, so it applies on replay against any 409 the server returns. The resolver closure cannot be queued alongside it, so a `.callback` replay looks one up on the client instead:

```swift
await client.registerConflictResolver { conflict in
  // conflict.itemId names the item, so one resolver serves every call site
  showConflictToast(itemId: conflict.itemId, fields: conflict.conflictingFields)
  return serverWinsMerge(conflict)
}
```

Register before the first write and before starting the sync engine. This is the write that most needs app logic: in local mode the edit that races is rarely the online one, it is the replay against a server the device could not reach at the time.

Nothing substitutes one strategy for another. A `.callback` update with no resolver anywhere — none passed to the call and none registered — is refused at the call site rather than queued. A replay that finds none blocks the mutation rather than retrying it: a second attempt could not differ while no resolver is registered, and retrying regardless is what used to make every later sync cycle report failure. It surfaces as `.blocked(reason: .resolverMissing, ...)`. Registering a resolver is the whole remedy — the next drain finds it and carries the write, with no call to `retry(id:)`.

`ConflictData` names the item in `itemId`. A per-call closure already knows it, but a registered one has no call site to learn it from, and it is the registered resolver a replay reaches.

## Errors

Errors are subclasses of a base `MarfaError`. Pattern-match on the subclass:

```swift
do {
  _ = try await client.items.get(id: "bogus")
} catch let error as NotFoundError {
  // missing item
} catch let error as ConflictError {
  // error.current, error.ancestor, error.conflictingFields
} catch let error as AncestorUnavailableError {
  // new in 17.0.0. The base version was thinned away; error.current and
  // error.requestedVersion are enough to rebase on. Under `.auto` you only
  // ever see this once the kit's own rebase budget is spent.
} catch let error as StoreIdentityMismatchError {
  // new in 17.0.0. This store was claimed by a different origin.
} catch let error as LocalModeUnsupportedError {
  // a call only a server can answer, on a local client — types, keys, auth,
  // admin, spaces, connections, blobs.exists among others, plus
  // items.createWithAttachments on any client with a store. error.operation
  // names which; the list is long enough that branching on it beats listing it
} catch let error as MarfaError {
  // everything else — error.code (String), error.message, error.status, error.details
}
```

<Callout type="info">
  `MarfaError.code` is a `String`, not an enum. Branch on the subclass where one exists; fall through to `MarfaError` and inspect `code` for anything else. Error codes are stable strings (`"version_conflict"`, `"rate_limited"`) — branch on them, not on the message.
</Callout>

Subclasses: `NotFoundError`, `ValidationError`, `UnauthorizedError`, `ForbiddenError`, `ConflictError`, `NetworkError`, `ResponseDecodingError`, `LocalModeUnsupportedError`, `ConflictResolverMissingError`, `LocalFilterUnsupportedError`, `BulkCapExceededError`, `BulkConfirmationRequiredError`, `SchemaVersionMismatchError`, and new in 17.0.0, `AncestorUnavailableError` and `StoreIdentityMismatchError`. `OAuthError`, `DeviceFlowError` and `PasskeyError` descend from it too, and surface from the auth flows rather than from an API call.

A `409` reaches you as `ConflictError` when the response carries version-conflict data, and as a plain `MarfaError` with the server's `code` — `conflict`, `type_mismatch`, `source_id_conflict` — when it does not. In local mode the two go different ways on replay: a conflict on an update resolves through the conflict strategy, while a conflict on a create is dropped to the dead-letter log, since the server has already acknowledged any repeat of an id this caller minted. See [Local IDs](#local-ids-uuidv7).

## Testing

`MarfaSDKTestSupport` ships as a separate product alongside `MarfaSDK` and provides scaffolding for unit tests:

- `MockTransport` — stub for the `Transport` protocol. Queue responses, assert on captured requests.
- `InMemoryKeychain` — in-memory `SecureStorage` substitute. SPM test binaries run unsigned and can't reach the real Keychain.
- `MarfaSDKTest.makeInMemoryClient()` — a local `MarfaClient` with no server, backed by an in-memory `ModelContainer`. Drop-in replacement for `MarfaClient.local(path:)` in test setups; sidesteps the cross-test container issues that show up when sharing a file-backed store across cases in the same process.

Add `MarfaSDKTestSupport` as a dependency on your test target only. The product is non-semver-stable across SDK minor versions and is not intended for production code.

The `Transport` protocol is public. `MockTransport` exists primarily for mocking the network in unit tests; the production `MarfaClient` init always instantiates `URLSessionTransport`. The protocol includes `rawUpload(method:path:body:contentType:query:onBytesSent:)`, the progress-aware upload hook that forwards `URLSessionTaskDelegate.didSendBodyData`, so stubs exercising byte-progress code paths (such as those against `BlobUploadProgressQuery`) can drive those callbacks deterministically from a mock.

<Callout type="warn">
  **A conformer that encodes its own request bodies must sort the keys.** The server fingerprints an idempotency key against the method, the path, the credential and the **body**, and refuses a key replayed with different bytes. Swift's synthesized `Codable` fills a keyed container backed by a dictionary, so the same value can encode two ways between attempts — and a replay of an unchanged write then comes back `idempotency_key_reused`, which no amount of retrying can clear. `URLSessionTransport` sets `.sortedKeys` for exactly this. A custom transport that does not is worse off than one sending no key at all, because an unkeyed replay merely conflicts.

  `requestWithConflict` also gained an `idempotencyKey` parameter in 17.0.0; a conformer has to forward it.
</Callout>

## Concurrency model

- `MarfaClient` is `Sendable` — safe to pass across actors.
- Namespace methods are `async throws` and don't require caller isolation.
- `LocalStore`, `MutationQueue`, `SyncEngine`, `ConnectionStateManager` are Swift actors. Shared state is actor-isolated; callers never synchronize manually.
- `MarfaStore` and query classes are `@MainActor @Observable` — observe them directly from SwiftUI views.
- The whole package builds under Swift 6 strict concurrency with zero `@unchecked Sendable` leaks in the public surface.
