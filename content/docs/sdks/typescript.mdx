The TypeScript SDK is an ES module, published on npm as [@withmarfa/sdk](https://www.npmjs.com/package/@withmarfa/sdk). Works in Node.js, Bun, Deno, and modern browsers (with a compatible `fetch`). Depends on [@withmarfa/shared](https://www.npmjs.com/package/@withmarfa/shared) for wire types and validation primitives.

Electron consumers should pre-externalize the SDK using `externalizeDepsPlugin` from `electron-vite` — same one-line config the broader ESM ecosystem uses.

The client runs in [remote mode](/guides/identity/deployment-modes): every call crosses the network, and a read without one fails rather than being answered from a store. The [local replica](/sdks/local-replica) subpath adds a volatile in-process copy of a single type, which serves reads for as long as the process lives and holds nothing across a restart.

## Install

```bash
pnpm add @withmarfa/sdk
# or
npm install @withmarfa/sdk
# or
bun add @withmarfa/sdk
```

## Connect

```typescript
import { MarfaClient } from "@withmarfa/sdk";

const client = new MarfaClient({
  url: "https://marfa.example.com",
  apiKey: process.env.MARFA_API_KEY!,
});
```

### Configuration

```typescript
interface ClientConfig {
  url: string;
  apiKey: string;
  fetch?: typeof fetch;        // override for custom transport (e.g. retry middleware)
  timeoutMs?: number;          // default 30000
  conflictStrategy?: "auto" | "manual" | "callback";   // default "auto"
  cdnBaseUrl?: string;         // optional CDN prefix for blob URLs
}
```

The `callback` strategy pairs with a per-call resolver — see [Conflict handling](#conflict-handling).

## Namespaces

The client exposes one namespace per resource:

- `client.items` — create, read, list, update, delete, transition
- `client.occurrences` — list the events falling in a time window, recurring series expanded
- `client.edges` — create, update properties, delete, list, edge types
- `client.metadata` — tags, tier, state mutations
- `client.blobs` — upload, download, presigned URL, exists
- `client.types` — list, register, describe, delete (custom types)
- `client.keys` — create, list, get, update, revoke (admin scope)
- `client.webhooks` — create, list, get, update, delete, deliveries
- `client.spaces` — current, config
- `client.connections` — install, list, get, configure, pause, resume, uninstall
- `client.admin` — operator surface (system-space admin)
- `client.auth` — sign-in flows plus `account.{requestDelete, confirmDelete, cancel}` post-sign-in lifecycle
- `client.events` — subscribe to the change stream
- `client.profile` — current user profile

### Items

```typescript
const note = await client.items.create({
  type: "core.note",
  properties: { body: "Hello, Marfa", title: "First note" },
  tags: ["intro"],
  tier: "library",
  source_id: "intro-001",        // optional; enables natural-key upsert on re-create
});

const one = await client.items.get(note.id);
const { data, cursor, has_more } = await client.items.list({
  type: "core.note",
  state: "active",
  limit: 50,
});

await client.items.update(
  note.id,
  { body: "Updated content" },          // properties to merge
  { expectedVersion: note.version },    // optimistic concurrency, no upfront GET
);

await client.items.transition(note.id, "archived");
await client.items.delete(note.id);         // → trashed
await client.items.restore(note.id);        // ← restore from trashed
```

#### Natural-key upsert

When `create()` is called with both `source_id` and a credential-stamped `source` that already resolve an existing non-trashed row in the space, the server short-circuits to update — properties shallow-merge, tags replace if provided, edges replace per-type if provided. The HTTP status flips from `201` to `200`; the SDK returns the updated item either way. See [Items — relationships, lists, and writes](/guides/core-model/items#relationships-lists-and-writes) for the wider semantics.

#### Update signature

`items.update(id, properties, options?)`. The second argument is the property bag itself — `{ body: "..." }` — not a wrapping object with a `properties` key. The optional third argument carries flow control: `expectedVersion` for optimistic concurrency, `conflict` to override the strategy per call, `resolve` for the callback resolver.

The patch carries only the fields you changed, and `expectedVersion` carries the version you read:

```typescript
const note = await client.items.get(id);
// ...the user edits the body...
await client.items.update(note.id, { body: edited }, { expectedVersion: note.version });
```

The server measures the patch against the ancestor snapshot rather than counting the keys it carries, so a field echoed at its unchanged value is dropped from the comparison and from the merge, and collides with nothing. Send only what changed regardless: a write that lands at the row's current version has every key it carries applied, and once the ancestor snapshot has been thinned the server falls back to naming every submitted field in conflict — under keep-both policy that is what surfaces as a duplicate item holding text the user never typed. Omitting `expectedVersion` makes the SDK fetch the current version at write time, which cannot detect anything that changed since your actual read. Properties merge shallowly, so a partial patch never loses omitted fields; pass `properties_mode: "replace"` when you mean the set you are sending to be the item's whole property set instead. See [the client write contract](/guides/schema/conflicts#the-client-write-contract).

Conflict-resolution behavior is unchanged. A 409 from the server still resolves through the configured `conflictStrategy`; the lazy type fetch on `keep_both_copies` paths still happens automatically. Pass `type` in options only if you also want to skip that specific lazy fetch.

### Edges

```typescript
await client.edges.create({
  source_id: note.id,
  target_id: person.id,
  edge_type: "about",
});

const outbound = await client.items.edges(note.id);            // edges from note
const inbound  = await client.items.backrefs(person.id);       // edges to person

// Global space-scoped listing across all items, by edge type.
const allReplies = await client.edges.list({ edge_type: "in-thread" });

await client.edges.delete(edgeId);
await client.edges.update(edgeId, { properties: { position: 3 } });

const edgeTypes = await client.edges.types.list();
```

### Atomic item + edges

```typescript
const highlight = await client.items.create({
  type: "core.highlight",
  properties: { text: "important passage", locator_type: "offset", start_location: 123, end_location: 189 },
  edges: { references: [documentId] },
});
```

Item and edges land in a single transaction.

### Bulk writes

`client.items.bulk` and `client.edges.bulk` are **admin-only**. The server stamps `source` from the credential, so only platform admins can bulk-write across sources — they're the ingest / migration primitive, not the every-day integration path. Third-party integrations writing many items should call `client.items.create` with `source_id` per item; `(source, source_id)` is the natural upsert key, so re-posts merge in place. See [Natural-key upsert](#natural-key-upsert) above.

`client.items.bulkAction` is a filter-driven mass-mutation primitive — `purge` is admin-only; the other five verbs require write access on every matched type.

```typescript
// Admin-only. For third-party flows, prefer natural-key upsert (see above).
await client.items.bulk({ items: payload });
await client.edges.bulk({ edges: edgePayload });
await client.items.bulkAction({ action: "transition", state: "archived", filter: { tags: ["wip"] } });
```

Behind the scenes, `bulkAction` POSTs, gets a 202 + job envelope from the server, and polls until the worker reaches a terminal status, then resolves with a `BulkActionResult`. Pass options to surface progress to a UI:

```typescript
const result = await client.items.bulkAction(
  { action: "purge", confirm: "PURGE", filter: { type: "core.scratch" } },
  { onProgress: (job) => console.log(`[${job.processed}/${job.matched}]`) },
);
```

Need explicit control? `client.items.bulkActionAsync(input)` returns the queued envelope without polling; `bulkActionStatus(jobId)` and `bulkActionCancel(jobId)` are thin wrappers over the GET / DELETE endpoints.

Semantics and outcome shape are documented on [Bulk operations](/guides/querying/bulk-operations); the SDK methods are thin wrappers.

### Metadata

```typescript
const metadata = await client.metadata.get(note.id);
await client.metadata.addTags(note.id, ["urgent"]);
await client.metadata.removeTag(note.id, "urgent");
await client.metadata.set(note.id, { tags: ["work"] });
await client.metadata.merge(note.id, { tags: ["q2-planning"] });

// Distinct tags across the space, with usage counts.
const tags = await client.metadata.listTags();
```

The `tier` field sits on the item itself, not in metadata — set it on create with `tier: "library"` or `tier: "feed"`, or flip it post-creation via `items.update(id, {}, { tier: "library" })`. Tier-only updates don't conflict — tier is metadata-axis, last-writer-wins. `system.*` items have no tier; the field is optional in the wire shape.

## Pagination

Every list method returns one page: `{ data, cursor, has_more }`. Pass `cursor` back to fetch the next one, and stop when `has_more` is false.

For walking a whole result set, the SDK does it for you. Each paginated method has an `All` sibling returning an async iterable, so one page is in flight at a time and a consumer that stops early stops the walk:

```typescript
for await (const note of client.items.listAll({ type: "core.note", limit: 100 })) {
  // one item at a time; only the current page is held in memory
}
```

The six are `items.listAll`, `items.listAllWithMetadata`, `items.listAllWithExtensions`, `edges.listAll`, `edges.listAllFromSource` and `edges.listAllToTarget`. They take the same filters as their single-page counterparts, minus `cursor` — the walk owns that.

### Collecting into an array

`collect` drains a walk, and asks how many rows you are prepared to hold:

```typescript
import { collect } from "@withmarfa/sdk";

const notes = await collect(client.items.listAll({ type: "core.note" }), {
  maxItems: 5_000,
});
```

There is no default ceiling. A walk that quietly returns the first N rows of a larger set looks exactly like a complete one at the call site, so `collect` throws `PageLimitExceededError` instead of truncating. If you hit it, either raise the ceiling because the result set really is that large, or switch to the iterator and handle rows as they arrive.

### Paginating anything else

The `All` methods are built on `paginate`, which takes any function returning a `{ data, cursor, has_more }` page. Reach for it directly when you are calling an endpoint the SDK does not wrap:

```typescript
import { paginate, collect } from "@withmarfa/sdk";

const walk = paginate(async (cursor) => {
  const url = new URL("/audit", "https://api.marfa.so");
  url.searchParams.set("limit", "200");
  if (cursor) url.searchParams.set("cursor", cursor);
  const res = await fetch(url, { headers: { Authorization: `Bearer ${key}` } });
  return res.json();
});

const entries = await collect(walk, { maxItems: 20_000 });
```

## Occurrences

A recurring event is stored as one item carrying its rule, so `client.items.list` returns the series once, dated to its first occurrence. `client.occurrences.list` asks what is actually on the calendar: over the window you name, it returns the events that fall there, with recurring series expanded from their rules and stored exceptions standing in for the occurrences they replace.

```typescript
const { data, series_errors } = await client.occurrences.list({
  from: "2026-05-01T00:00:00Z",   // inclusive; a Date is accepted
  to: "2026-05-27T00:00:00Z",     // exclusive
  type: "core.event",             // optional; defaults to every event type you can read
});
```

[Recurring events](/guides/querying/recurring-events) carries the semantics: what an entry holds, how a rule expands, how a moved occurrence is stored, and how a series' own zone anchors its schedule. What follows is what the SDK adds on top.

### The window is refused, never trimmed

The window is required, and two ceilings bound it. A span of more than 400 days is refused, and so is a result holding more than 5,000 occurrences across every series in it. Both raise `ValidationError`, and neither is quietly narrowed into something that would have worked: a calendar missing its last week looks exactly like a calendar, so the caller is told and decides what to narrow.

Read the limit off `err.details`, as `max_days` or `max_occurrences`, rather than hard-coding it. The second ceiling depends on what the window holds rather than on the dates, so the same span can pass against one space and be refused against another.

A third refusal wears the same shape and does not answer to the same fix. When a space holds more events than one read can scan, the call fails with `max_events_scanned` and neither of the other keys, and asking for a narrower window does not clear it: the passes that gather series and their exceptions cannot be windowed, so they read the space whole however little you ask about. Branch on which key is present rather than retrying smaller.

Neither span nor count is pre-checked locally. An over-long window makes the round trip and is refused by the server, which keeps one authority over the limit rather than a copy in every client that ages out of step with it. The one refusal raised without a request is a `Date` the SDK cannot convert. It throws `ValidationError` too, so there is a single catch shape, and carries `code: "invalid_window_bound"` with `status: 0` because no server saw it.

### Series errors are part of the answer

The call returns the whole envelope rather than a bare array. Beside `data` it carries `window`, the window the server read, and `series_errors`, one entry per series that could not be expanded.

A series that fails does not fail the read, so those entries are the only record that something is missing. A caller that ignores them renders a calendar with a repeating meeting silently absent from it.

This is also the one list that is not paginated. The window is the bound, so there is no cursor and no `listAll` sibling; a window too large to answer is refused rather than paged.

### Instants stay instants

`starts_at` and `ends_at` are the ISO 8601 UTC strings the server sent, and the SDK does not parse them. Turning an instant into a `Date` and rendering it collapses every event onto whatever zone the runtime sits in.

Each event's own zone travels on the item instead: `properties.timezone` anchors the start, `properties.end_timezone` covers an event that ends somewhere else, and `properties.all_day` marks one that occupies calendar dates rather than a span of time. A weekly 09:00 meeting in `Europe/Berlin` is 08:00Z before the spring transition and 07:00Z after it, and that pair reads as one recurring hour only with the zone alongside.

## Conflict handling

The TypeScript SDK exposes the three modes as `conflictStrategy` on the client config and `UpdateOptions.conflict` per call. See [Conflicts](/guides/schema/conflicts) for the resolution model, keep-both semantics, and per-core-type defaults; [Errors — version_conflict](/api-reference/errors#version-conflict) for the 409 payload.

Every mode assumes an honest patch. `conflicting_fields` is the overlap between what the server changed since the ancestor and what you changed against that same ancestor, so send only the fields you changed, with the version you read as `expectedVersion`; the contract and its failure modes are on [Conflicts](/guides/schema/conflicts#the-client-write-contract).

```typescript
await client.items.update(
  id,
  { body: "..." },
  {
    expectedVersion: 3,
    conflict: "callback",
    resolve: async ({ current, ancestor, clientPatch, conflictingFields, mergePolicy }) => {
      return { ...current.properties, ...clientPatch };
    },
  },
);
```

The `callback` strategy invokes a resolver with the three-way context plus the type's resolved `mergePolicy`; `auto` (default) and `manual` need no resolver. A client-level `conflictStrategy` sets the default; `UpdateOptions` overrides it per call.

When `auto` runs the SDK emits a `conflictAutoMerged` event:

```typescript
{
  itemId: string;            // the original item
  mergedItemId: string;      // the original item id (post-retry)
  conflictedCopyId?: string; // the new sibling, when keep-both spawned one
  fields: string[];          // the conflicting fields
  strategy: Record<string, "last_writer_wins" | "keep_both_copies">;
                             // per-field: which merge policy resolved each conflict
}
```

Apps typically toast on `conflictedCopyId` being present — the user's in-flight edit was preserved as a sibling rather than discarded.

## Errors

Typed error classes you can instanceof-check:

```typescript
import {
  MarfaError,
  NotFoundError,
  ValidationError,
  ConflictError,
  UnauthorizedError,
  ForbiddenError,
} from "@withmarfa/sdk";

try {
  await client.items.get("bogus");
} catch (err) {
  if (err instanceof NotFoundError) {
    // err.code === "item_not_found"
  }
  throw err;
}
```

All error classes extend `MarfaError`, which carries `code`, `message`, `status`, and optionally `details`. Branch on `err.code` (stable string) rather than message wording.

## Local type validation

Platform types ship with the SDK, so `validateProperties` already answers for them without a network call. A space's own custom types live only on the server. `hydrateTypeRegistry` registers them from a `GET /types` payload, so a client validates a write by the same rules the server applies:

```ts
import { hydrateTypeRegistry, validateProperties } from "@withmarfa/sdk";

const { data } = await client.types.list();
const report = hydrateTypeRegistry(data.types, { spaceId });

validateProperties("acme.invoice", { total: 12 });
```

The payload does not need sorting. The helper works out parent order itself, and a child listed before its parent is registered correctly either way.

<Callout type="warn">
  **Read `report.unresolvedParents`.** It names types whose declared parent resolves nowhere — not in the payload, not in the shipped registry, not already registered for this space. Field resolution stops at the break, so such a type validates against a narrower set of fields than the server holds, and a required field declared by the missing ancestor is not enforced at all. Local validation then **accepts** a write the server refuses. Refetch with a credential that can read the ancestor; ignoring it queues writes that come back refused.
</Callout>

`report.skippedPlatform` names payload entries the SDK already ships, which are deliberately left alone: the shipped vocabulary resolves globally, and copying it into a space's overlay would shadow it. `report.cycles` names types whose parent chain closes on itself; they are registered rather than skipped, because the server holds the same rows and raises `type_chain_unresolvable` for them too, so skipping would invent a disagreement.

The payload is never re-validated. These schemas are what the server accepted, and a client on an older `@withmarfa/shared` than the server would otherwise refuse types the server holds, then refuse every write against them — worse than not caching at all.

## OAuth helpers

The `@withmarfa/sdk/auth` subpath is a separately-exported entry point for apps that authenticate users through Marfa rather than holding an API key. Mirrors the OAuth 2.1 + Device Authorization Grant flows documented under [Authentication](/api-reference/authentication).

```typescript
import {
  MarfaAuth,
  startDeviceFlow,
  OAuthError,
  generateCodeVerifier,
  computeCodeChallenge,
  generateState,
  type TokenProvider,
  InMemoryTokenStorage,
  LocalStorageTokenStorage,
} from "@withmarfa/sdk/auth";
```

### MarfaAuth

The high-level helper for the Authorization Code + PKCE flow. Generates the PKCE verifier, builds the authorize URL, exchanges the redirected code for a token provider, and refreshes on demand. Pair it with a `TokenStorage` to persist the resulting tokens.

```typescript
const auth = new MarfaAuth({
  issuer: "https://marfa.example.com",
  clientId: "my-app",
  redirectUri: "https://myapp.example.com/oauth/callback",
  scopes: ["core.note:read", "core.note:write"],
  storage: new LocalStorageTokenStorage(),
});

// 1. Send the user to authorize
window.location.href = await auth.buildAuthorizeUrl();

// 2. On redirect back, exchange the `code` query param for a token provider
const tokenProvider = await auth.handleCallback(window.location.href);

// 3. Pass the provider to the client; it refreshes on 401 transparently.
const client = new MarfaClient({
  url: "https://marfa.example.com",
  tokenProvider,                     // alternative to a static apiKey
});
```

On a later page load, `auth.restore()` returns a `TokenProvider` (or `null` if no session is persisted) without re-running the flow.

### startDeviceFlow

For headless and CLI contexts. Implements RFC 8628 — initiate, display the `verification_uri` and `user_code`, poll until the user approves.

```typescript
import { startDeviceFlow } from "@withmarfa/sdk/auth";

const handle = await startDeviceFlow({
  issuer: "https://marfa.example.com",
  clientId: "my-cli",
  scopes: ["core.bookmark:read"],
});

console.log(`Open ${handle.verification_uri} and enter ${handle.user_code}`);
const tokenProvider = await handle.pollForToken();   // resolves once the user approves
```

### Token storages

The SDK bundles `InMemoryTokenStorage` (per-process; the default in Node) and `LocalStorageTokenStorage` (browser). Custom backends implement the `TokenStorage` interface.

The Node-only `@withmarfa/sdk/auth/node` subpath adds `FileTokenStorage`, which persists tokens into the per-instance config file at `~/.marfa/<instance>.json` — the same store the CLI writes on `marfa auth login`, so headless tools share one signed-in session and one refresh path instead of each holding its own credential. The subpath also exports the store's file helpers (`resolveInstanceName`, `resolveConfigPath`, `readConfigFile`, `parsePersistedTokens`) for tools that need to inspect the stored session without standing up a provider. It is a separate subpath so browser bundlers never see `node:fs`.

```typescript
import { StoredTokenProvider } from "@withmarfa/sdk/auth";
import {
  FileTokenStorage,
  resolveConfigPath,
  resolveInstanceName,
} from "@withmarfa/sdk/auth/node";

const path = resolveConfigPath(resolveInstanceName()); // ~/.marfa/default.json
const provider = new StoredTokenProvider({
  issuer: "https://your-server.example.com",
  clientId,
  storage: new FileTokenStorage({ path, clientId, issuer }),
  storageKey: "tokens",
});
if (await provider.hydrateFromStorage()) {
  const client = new MarfaClient({ url: issuer, tokenProvider: provider });
}
```

### OAuthError

Thrown by every helper. Carries the OAuth `error` code (`invalid_grant`, `slow_down`, `expired_token`, `access_denied`, etc.) and the optional `error_description`. Apps branch on `err.code` to decide between user-facing messaging and re-flow logic.

### PKCE primitives

`generateCodeVerifier()`, `computeCodeChallenge(verifier)`, and `generateState()` are exported for callers that need to drive the flow themselves rather than through `MarfaAuth`.

## Webhook signature verification

The top-level `verifyWebhookSignature` helper validates an incoming inbound-webhook receipt against the subscription's secret. Wraps the same canonical `X-Marfa-Signature` header check the server runs — handy for any consumer that wants to verify a forwarded payload (gateway, CI runner) without pulling in the full server.

```typescript
import { verifyWebhookSignature } from "@withmarfa/sdk";

const result = await verifyWebhookSignature({
  header: signatureHeader,      // the X-Marfa-Signature value
  rawBody: rawRequestBody,      // ArrayBuffer or string
  secret: subscriptionSecret,
});
```

Returns `{ valid: true }` on success and `{ valid: false; reason: string }` on failure.

## Realtime

`client.events.subscribe` is the change stream. It streams [`GET /events`](/guides/realtime/realtime) through `fetch`, which keeps the credential in a header — `EventSource` cannot set one — and handles frame reassembly, resume, reconnection with backoff, and the stale-cursor case.

```typescript
const sub = client.events.subscribe({
  type: "core.note,core.media",      // up to ten, each covering its subtypes
  edges: "none",                     // edges arrive by default, filter or not
  lastEventId: savedCursor,          // omit to receive only what happens next
  onCursor: (cursor) => persist(cursor),
  onEvent: async (event, eventId) => {
    await apply(event);              // awaited before the cursor moves
  },
  onCatchupTooOld: () => reseed(),   // the cursor predates retention
  onError: (err) => report(err),
});

// later
sub.close();
persist(sub.lastEventId);
```

### The first frame says where the stream is

`onCursor` fires at most once per connection, before any event, with the log position the stream opened at. It is what gives "subscribe, then read a snapshot" a resume point on a quiet space: without it a store that finished a full read and was then interrupted holds no cursor at all, and has no way to know it is missing one.

It can also not fire. The server bounds the read behind the announcement, so a stream opened while its database is not answering carries no cursor rather than holding its events back. The subscription is live either way, so hydrate on the events and treat the cursor as an optimization, never as a gate to await.

The subscription adopts the announced value as its own cursor **only when it has none yet**. On a resuming connection the announcement names the head of the log, which sits past the backlog that connection is about to replay, so adopting it there and then dropping mid-replay would leave the cursor over events you never saw and never ask for again.

The value is a starting position rather than a guarantee that nothing precedes it. [Realtime](/guides/realtime/realtime) states the bound; a store that cannot tolerate it pairs the cursor with a sweep on `updated_after`.

### The cursor advances on acknowledgement

`onEvent` is awaited, and the cursor moves only once it resolves. A handler that rejects leaves the cursor behind its event, so the next connection replays it.

That makes delivery **at-least-once**: write handlers to be idempotent, which item events already are, since each carries the whole item. If you would rather drop a failed event than see it again, catch inside your handler — one line, at the point you can see it. The reverse is not expressible: a caller cannot recover an event from an at-most-once subscriber, because the cursor has already moved by the time the failure surfaces.

A frame whose payload will not parse is the exception. It is reported through `onError` and stepped over on the same connection, because replaying it could only fail in the same place.

### Backoff

Reconnection backs off exponentially from `initialRetryMs` (500ms) to `maxRetryMs` (30s), and resets once a connection delivers something. Opening is not enough: a connection that opens, delivers nothing and dies is not evidence the endpoint is healthy, and treating it as evidence turns a handler that always fails into a hot reconnect loop.

## Versioning

The TypeScript SDK follows semver. Major-version bumps mean breaking wire or API changes. Minor bumps add capabilities. Patch bumps are bug fixes.

The SDK's major version tracks the server it was built against.

## Browser use

The SDK works in browsers that support `fetch`, `TextDecoder`, and `ReadableStream`. No polyfills needed for evergreen browsers. For older targets, bring your own polyfill.

When making requests from a browser, ensure the Marfa server's `CORS_ORIGINS` includes your origin (see [Configuration](/self-hosting/run/configuration)).

## Electron

The TypeScript SDK is ESM-only. Electron's main process bundle needs the SDK marked as an externalized dependency so it stays as a real `import` at runtime rather than being inlined.

Use the `externalizeDepsPlugin` from `electron-vite`. It reads `package.json` and externalizes every dependency automatically — `@withmarfa/sdk` and `@withmarfa/shared` are covered as long as they're listed as runtime dependencies, not `devDependencies`.

```typescript
// electron.vite.config.ts
import { defineConfig, externalizeDepsPlugin } from "electron-vite";

export default defineConfig({
  main: {
    plugins: [externalizeDepsPlugin()],
  },
  preload: {
    plugins: [externalizeDepsPlugin()],
  },
  renderer: {
    // Renderer is web-shaped; the SDK works without externalization here.
  },
});
```

Hold the credential in the main process — `safeStorage` on macOS (Keychain), DPAPI on Windows, libsecret on Linux. Treat the renderer as the UI layer and route SDK calls through IPC.
