## What it is

`@withmarfa/sdk/local` is the TypeScript kit's [local-mode](/guides/identity/deployment-modes) client. A write lands in a SQLite store on the device and reaches the server afterwards, so an app built on it keeps working with no network and opens with what it had last time. What it keeps is the [sync contract](/sdks/sync-contract), which is behavior rather than code: any engine that holds to those rules is correct, whatever language it is written in.

<Callout type="info">
  **Which one you want.** This page is the durable store: writes queue on
  disk and survive the process ending. The [local replica](/sdks/local-replica)
  is a volatile in-process copy of one type, rebuilt from the server on every
  start. Reach for the engine when a write has to survive the app being closed;
  reach for the replica when you only want a read taken out of the interactive
  path and are happy for it to disappear on reload.
</Callout>

The engine needs a filesystem. The store lock, the fail-safe and the migrations folder all read and write real files, so it runs in Node.js, Bun, Deno and an [Electron main process](/sdks/electron). **There is no browser store.** Nothing here changes the ordinary client entry point, which works where it always did.

## Install

```bash
pnpm add @withmarfa/sdk @libsql/client drizzle-orm
```

`@libsql/client` and `drizzle-orm` are optional peer dependencies, so a consumer that never opens a store does not pay for one. Add `@tanstack/db` as well if you use the [projection](#the-projection).

## Three layers

Everything below follows from the store holding three things rather than one.

- **Server state is what the server last said.** Items, edges and metadata sit in separate tables, so an item event cannot clobber a row's tags or extensions.
- **The outbox is what this client has written and not yet sent.** A queued mutation is the pending edit. Nothing writes a second, local copy of the row.
- **Visible state is the first with the second replayed over it**, recomputed on every read. That is what lets another device's change to one field arrive without hiding an edit this device has typed into a different one, and it settles what rolling a write back means: the outbox entry leaves and the row falls back to what the server holds, with nothing to undo.

## Opening a store

```ts
import { MarfaClient } from '@withmarfa/sdk';
import {
  openLocalStore,
  createLocalEngine,
  SINGLE_ACCOUNT,
  SINGLE_SPACE,
} from '@withmarfa/sdk/local';

const url = 'https://marfa.example.com';
const client = new MarfaClient({ url, apiKey: process.env.MARFA_API_KEY! });

const store = await openLocalStore({
  path: '/Users/me/Library/Application Support/my-app/marfa.db',
  identity: { origin: url, spaceId: SINGLE_SPACE, accountId: SINGLE_ACCOUNT },
  onRecovery: (recovery) => reportToTheUser(recovery),
});

const engine = createLocalEngine({ store, client });
await engine.start();
```

**A store is identified by origin, space and account together.** Any one of them alone lets two different corpora share a cursor. A server with no spaces has no space id to give, so `SINGLE_SPACE` stands in rather than the field being optional, and `SINGLE_ACCOUNT` does the same for a credential that names no account. Both are the empty string.

**Opening a store as somebody else is refused.** A store records its identity on first open and throws `StoreIdentityMismatchError` when a later open does not match it, because applying one account's events over another's rows and advancing a cursor that describes neither is not a state anything recovers from.

**Migrations run forward on open.** The store carries a schema version rather than being reconstructed from whatever the code expects. The package ships the migration folder alongside `dist`, so a build that drops it leaves the engine unable to open anything, and says so.

The database opens in WAL mode, so a read on the interactive path is not locked out for the length of a drain's transaction. `store.db` and `store.raw` are escape hatches for a query this surface does not have.

## A write is local and immediate

```ts
const note = await store.mutations.createItem({
  type: 'core.note',
  properties: { body: 'Written on a plane' },
});

await store.mutations.updateItem(note.id, { title: 'Draft' });
await store.mutations.deleteItem(note.id);
```

The edge equivalents are `createEdge`, `updateEdge` and `deleteEdge`. Each call returns the row as this client sees it, and returns it before anything has been sent.

- **The row and its queue entry land in one transaction.** A write is never visible without being queued and never queued without being visible, because there is only one row and it is the queue's.
- **The client names the row.** `createItem` mints an id when the caller does not pass one, so the row is on screen before the server has seen it and a create whose response was lost can be resent as a repeat rather than as a second row.
- **A create's row carries `version: 0` and an empty `source` until the server answers.** Both are the server's to stamp, and a client that guessed would produce a row that compares wrongly against the first event to arrive.
- **An update carries only the properties that changed**, plus the version the row was read at. An update sent while the row's own create is still queued has no server version to name, and the drain resolves one from the create's response.
- **An edge waits behind both its endpoints.** `createEdge` records the source and target as dependencies, so an edge is never sent against a row the server does not have yet.

Updating or deleting a row the store does not hold throws rather than queuing a write against nothing.

## The queue drains

```ts
await engine.drain();
```

One pass, and nothing here loops or waits. When a mutation is retried is the app's decision: a queue that retried on a timer of its own would be a second scheduler beside the app's.

- **Order is the order the writes were made in**, and a mutation is held behind any earlier unsent work naming the same row or, for an edge, either of its endpoints.
- **A mutation carries the idempotency key it was written with**, minted once and stored, so a retry names the attempt it is repeating rather than opening a new one. It goes out on `POST /items`, `DELETE /items/{id}`, `POST /edges` and `DELETE /edges/{id}`. The two update doors do not carry one in this version.
- **The server's answer and the queue removal are one transaction.** Settling in two steps would either lose the write or send it twice across a crash.
- **A successful delete removes the row from server state** rather than leaving it behind. It comes back as trashed through the stream's own event or a re-import.

### Failure classes

Every way a send can end has a class, and the classification is closed: an unclassified failure either retries forever or drops the write, and both are silent.

| Class | What it means | What the engine does | What clears it |
| --- | --- | --- | --- |
| **Offline** | The request never reached a server: a transport error or a timeout. | Ends the pass with no attempt recorded against anything. | Reaching the server. A laptop shut for a week arrives with its queue intact. |
| **Auth** | A `401`, after the transport has already made its one refresh. | Parks the whole queue and emits `queue.parked`. Nothing is dropped. | A working credential, then `outbox.retryAll('auth', …)`. |
| **Blocked** | A refusal whose stated cause is temporary: `space_suspended` or `quota_exceeded`. | Parks that mutation and holds whatever waits behind it. | The operator action the code names, then a retry. |
| **Conflict** | A `409` on an update the server could not merge — its ancestor snapshot has been thinned past merging. | Parks the mutation as `needs_review`, with the edit intact and still on screen. | The app re-applying the edit over what the server now holds, or dropping it. Waiting does not help. |
| **Permanent** | `400`, `403`, `404`, and a `409` on a create or a delete. | Dead-letters the write. A refused create takes its dependents with it, marked `cascaded`. | Nothing. It is kept for the app to show and dismiss. |
| **Transient** | `5xx`, a rate limit, `idempotency_key_in_flight`, and a local fault after the request went out. | Retries, counting toward the ceiling. | The next drain, or the ceiling, after which it parks as `retry_ceiling`. |

`DEFAULT_RETRY_CEILING` is 5 and `retryCeiling` overrides it. **Only attempts made while the server was reachable count**, which is why being offline is not a failed attempt.

### Conflicts are settled by the server

The engine sends every update with `conflict=auto`, and does not merge anything itself.

The server resolves inside the write's own transaction, by the type's policy: fields that do not collide merge, fields that do resolve by the policy, and a field the type marks `keep_both_copies` spawns a sibling there, with a deterministic id, in the same transaction. So two clients editing one such field leaves **one PATCH on the wire and two rows on the server** — the row, and a sibling carrying the edit that lost.

**This is deliberate and is not a convenience.** Settling a conflict inside one client is a resolution rule no other client shares: a second device on a different kit would settle the same edit differently, and a `keep_both_copies` field would spawn a different sibling on each. One outcome per write, for every client, is only possible where the write happens.

What still reaches the app as a conflict is the case the server could not merge at all: `ancestor_unavailable`, where the base version's snapshot has been thinned so far that there is nothing left to merge against. That parks as `needs_review` with the server's current state, and is never auto-merged.

One property worth knowing before relying on it. **A replayed update is not a no-op.** An update carries no idempotency key today, where a create repeats safely on the client-minted id and a delete on the key it carries. So an update whose response was lost re-sends the version it was computed against, meets the merge, and settles correctly — but the row is written twice, and the version moves twice for one edit. The outcome is right; the write is not yet idempotent.

`classifyFailure(error, kind)` is exported, and the mutation's kind is a parameter because one status means two things: a `409` on a create says the id is held by a row this client did not make, while a `409` on an update says the row moved on under an edit that is still wanted.

### Clearing what has parked

The reasons do not clear together, so the queue is unparked by reason rather than by state.

```ts
const at = new Date().toISOString();
await store.outbox.retryAll('auth', at); // Every write parked on a spent credential.
await store.outbox.retry(seq, at);       // One row, whatever it was parked for.
```

Sweeping every parked mutation on a credential recovery would spend a request re-parking each write awaiting review, and would tell the app those writes were moving again when nothing has changed for them.

Refused writes are read with `store.deadLetters.list()` and cleared with `store.deadLetters.dismiss(id)`. Each entry keeps the payload, the code, the message, the HTTP status and the time it failed, so an app can show a person what it could not send.

## What the app can read

`engine.status()` is a snapshot, read fresh every time, so nothing it returns can describe a state the store has already left.

| Field | What it says |
| --- | --- |
| `connection` | `idle`, `connecting`, `online`, `offline` or `stopped`. Derived from what the engine reports rather than tracked beside it. |
| `identity` | The origin, space and account this store belongs to. |
| `writer` | False when another engine holds the store and this handle can only read. An app showing a sync status has to say so: nothing this process writes will be sent. |
| `pending` | Mutations waiting to be sent. |
| `blocked` | Parked mutations counted by reason, split rather than totaled because what clears them differs. |
| `deadLetters` | Writes the server refused, kept for the app to show. |
| `lastDrainedAt` | When the queue last emptied cleanly, or null if it never has. |
| `cursor` | Where the stream has reached, or null before it has said. |
| `hydration` | `done`, the monotonic `items` and `edges` counts, and `totalItems` when the server would say. |

Some things cannot wait for the next `status` call, because each one is work that has stopped moving or a change a person will notice on screen. Those arrive as events.

```ts
const off = engine.on((event) => {
  if (event.type === 'mutation.blocked') showBanner(event.reason, event.message);
});
// `off()` stops listening.
```

| Event | When |
| --- | --- |
| `queue.parked` | The credential is spent. Carries how many mutations were parked. |
| `mutation.blocked` | One mutation parked, with its reason. |
| `mutation.dead_lettered` | A write was refused, or cascaded from a refused create. |
| `mutation.merged` | The server resolved a conflicting update. Carries the fields that collided, the policy applied to each, and the id of the sibling holding the losing values when a field keeps both. |
| `drain.finished` | A pass ended. Carries what was sent and what remains. |
| `hydration.progress` | A first read is walking. Counts rise and never fall, so a progress bar built on them cannot run backwards. |
| `hydration.finished` | A fresh store has read the server's state for the first time. |
| `catchup.finished` | A reconnection has read whatever changed while the client was away, with the bound it read from. |
| `reimport.finished` | The cursor had aged out, so everything was read again. Carries the pruned counts, which are rows that were on screen a moment ago. |

A catch-up that stops running looks, from every other signal, exactly like a quiet period. That is why it is reported rather than done quietly.

`mutation.merged` is worth handling for the same reason. A merged row arrives through the ordinary settle and looks like any other write, so without it a person's text leaves the row they typed it into and nothing says where it went. **The `conflictedCopyId` it carries is the only place that sibling is named** — no route reports what a write created — so an app that ignores this event cannot find the copy until the stream happens to deliver it.

## The projection

A store answers a question about any row in the space, and a list in an interface is bound to one type of it. `createProjection` is the second of those: a `@tanstack/db` collection over one type of **visible** state.

```ts
import { createProjection } from '@withmarfa/sdk/local';

const notes = createProjection({ store, type: 'core.note', onError: report });
engine.on(() => void notes.utils.refresh());
```

- **It shows the queue over what the server said**, which is why a write appears instantly and does not blink: the row a person just made is in the queue, and the queue is part of the projection.
- **It is read-only.** Writes go through `store.mutations`, which queues them in the same transaction as the local row. A collection that accepted writes of its own would be a second way to make one, and the two would order differently under a drain.
- **Refresh is the app's call.** The engine writes to the store, not to the collection, so something has to say when a re-read is worth doing, and the engine's events are that something. A projection that polled would be a second scheduler that was still wrong about when to look.
- **A projection has a size.** `DEFAULT_PROJECTION_MAX_ITEMS` is 50,000, matching the replica's ceiling because the two answer the same question about the same kind of object. A type that outgrows it reports through `onError` rather than filling the tab.

## Starting up

`engine.start()` subscribes first and reads second, and resolves once the store holds a full picture.

**The other order has a hole in it that no amount of care closes.** Anything changing between the read finishing and the subscription opening is missed by both, and nothing afterwards ever reports it. Subscribing first makes an overlap the failure mode instead, and an overlap is free: every write is version-compared, so an event delivered twice, or delivered and then re-read, settles to the same row.

The server announces the log position it opened at as the first frame, and `start` waits for it. Without that, a client that subscribed, read, and was interrupted on a quiet space would have no cursor to resume from and no way to know it had missed anything.

**A fresh store then reads everything**, in this order:

1. **What the server says it holds**, read once so the progress below has a denominator. Best-effort: a credential that cannot see that route leaves the total undefined rather than stopping the read.
2. **Items in every state, trashed included, with their metadata sidecars.** A client that read only active rows would never see a row reach the bin, and would keep showing one the person deleted somewhere else.
3. **Edges.**

Rows are counted as they land rather than per page, because a read that stalls part-way through a page is exactly when a person is watching. The store is stamped as hydrated **after** the read, so a process that dies part-way through comes back and reads again rather than trusting counts that never reached their total.

A store that has already hydrated skips all of this and resumes from its cursor.

### Applying events

Every inbound event goes through the same two rules.

- **A payload older than the row held is skipped, and that is a success, not a failure.** The stream is at-least-once and the catch-up read deliberately overlaps, so a stale payload is the ordinary shape of a replay. An equal version is the same row arriving twice and settles rather than being refused.
- **The event and the cursor advance in one transaction, in that order.** A process that dies between them comes back to the event rather than past it, and a store that refuses an event stops the stream at that event rather than skipping it.

An item event never touches the metadata layer, even when it carries a metadata field, because an item event carries no tags and no extensions: writing from there would erase them on every ordinary edit. `metadata.changed` is the only event that writes that layer, and it writes nothing else. A trashed item stays in the store as real state a restore can bring back; a purged one is removed along with its metadata, because nothing will ever correct a copy kept past that.

`applyEvent` is exported for a consumer driving its own subscription.

### Reconnecting

Every reconnection reads what changed while the client was away, before the new connection's frames are trusted to be the whole story. The event log is bounded and a disconnection is not.

The bound is the older of the newest `updated_at` held for an item and for an edge, taken from the store itself rather than from a stored high-water mark, so it cannot describe rows the store does not hold. Nothing is pruned on a catch-up: it reads a slice, and a slice would take the whole corpus for absent.

## When a cursor ages out

The server reports `catchup_too_old` when a resume point predates its retention window. Reconnecting with the same cursor loops on the same refusal, and dropping it silently skips every change in the gap, so the engine re-reads instead.

1. **Drain first**, so this client's own unsent writes are not read over and then contradicted.
2. **Clear the cursor before the read**, so a crash mid-read cannot leave one claiming a completed subscription.
3. **Read everything, and prune what the server no longer has** — items *and* edges. An edge removed while the client was away past the retention window has no event coming and no row in the read, so a client that pruned only items would hold a relationship between rows it had correctly removed.
4. **Resubscribe from nothing.** The new connection announces a cursor, and the re-imported state resumes from that.

`reimport.finished` reports the pruned counts, which is the only account an app has of why rows left the screen.

`importAll` is exported, and it protects unsent work in two ways:

- **It refuses to run over pending writes**, throwing `PendingWritesError` rather than recording a server state a write in flight is about to change.
- **It never prunes a row this client's queue still names.** A queued create's row exists nowhere but here, so the server was never going to return it and pruning would delete the write itself. A parked mutation is not counted as pending, because refusing to import while anything at all is queued would strand a client whose queue holds a write awaiting review — permanently, since the import is what lets it rebase.

## One writer per store

Two engines over one store file is not a corruption problem. It is a correctness one: each keeps its own idea of where the stream has reached, applies events the other already applied, and advances one shared cursor past what either of them took. The store looks healthy and is missing rows neither engine can name.

- **The lock is a lockfile beside the store**, taken with an exclusive create so the claim is one syscall rather than a check and a write another process can land between.
- **A second opener is told, not queued.** It gets a handle that reads and refuses every write, including the cursor, throwing `ReadOnlyStoreError`. `status().writer` is false, and an app showing a sync state has to say so.
- **A lock left behind by a process that is no longer running is taken over.** A crashed engine must not make its own store permanently read-only.
- **This is not an application's single-instance lock.** That answers a different question, whether a second window should open, and an app may want one while this refuses a second writer over the same file.

<Callout type="warn">
  `:memory:` has no file to contend over and is shared process-wide, so every
  in-memory store in one process is the same database. Anything needing
  isolation uses a file, which is also the shape the engine ships in.
</Callout>

## The fail-safe

Migrations only run one way. Code that has been rolled back, or a build older than the one that last wrote, meets a schema with columns it does not know, and the migrator has nothing to say about it because it only ever looks for work still to do.

A store this build cannot open, whether it was written by a newer engine or its migration failed, is set aside and rebuilt **in an order that only runs one way**:

1. Read the outbox and the dead-letter log straight out of the schema.
2. Write both to a sidecar JSON file beside the store, refusing rather than overwriting a sidecar already at that name.
3. Close the database, then move the store aside along with its write-ahead log.
4. Open a fresh store by the ordinary path and call `onRecovery` with what was rescued and where it went.

**Anything that fails before the move leaves the store exactly as it was and throws `StoreUnrecoverableError`.** The engine refuses rather than rebuilding when it cannot preserve the queue first, and it refuses from a read-only handle, because rebuilding under the engine that is writing would take the store out from under it. That direction is deliberate: an engine that always recovers and sometimes silently loses everything leaves a person with a working app and no way to know what went missing, and only one of those is something a consumer can act on.

`onRecovery` is worth wiring. Everything in a `StoreRecovery` is work a person did: writes that never left, refusals nobody has read. The sidecar is the only copy of it. An app that is told can offer it back; an app that is not gets a store that quietly starts empty.

## Types, blobs and search

Three things the store carries so that being offline is not a smaller product.

### A write is refused before it is queued

The type graph is local. Platform types ship with the kit; custom types are read from `GET /types` whenever the server is reachable and cached in the store, so a later open validates against them with no network at all.

`validateProperties` runs **before** the mutation is enqueued, by the same rules the server applies, so a write the type forbids never enters the queue. An update is validated as the merged row rather than as the patch, which is the shape the server's own door checks.

```ts
await store.mutations.createItem({ type: 'core.note', properties: {} });
// LocalSchemaRefusal: core.note requires body
```

**A schema refusal from the server buys exactly one refresh.** The local graph may simply be stale — a type changed on the server since it was cached — so a `400` on schema grounds triggers one registry refresh and one revalidation before the write is treated as permanent. The allowance is per mutation rather than per drain pass, so a write cannot spend it repeatedly and a stale graph cannot become a loop against `GET /types`.

### Blobs queue with their bytes

Bytes are hashed locally and written beside the store, so an attachment made with no network is an ordinary offline write. The upload is queued **before** the write that references it and completes first, because an item naming a blob the server does not hold is a reference to nothing.

On a replay a probe distinguishes "already there" from "lost", so a re-sent upload is not a second copy. **An upload that fails permanently dead-letters the write that referenced it and keeps the bytes** — the write can be dismissed, and the person's file is still on disk.

Downloaded blobs are cached read-through, bounded by total bytes and evicted least-recently-read first. Staged bytes are never evicted: they are owed to the server.

### Search is answered from the store

An FTS5 index over the fields the type's display hints name, with subtype resolution, maintained as the store changes rather than rebuilt.

```ts
const hits = await store.search.find('bassoon', { type: 'core.note' });
```

**It matches the same fields as server search and may rank differently.** The fields are the contract; the ranking is not, because relevance is relative to the documents in the index and this one holds one client's corpus rather than the space's.

## What this version does not do

The [sync contract](/sdks/sync-contract) names more than this engine keeps. Each boundary below is stated rather than left for a reader to discover, because an app built as though one of them were closed fails quietly.

- **An edge conflict parks without the server's current edge in the store.** The refusal carries it, and there is no route that reads one edge by its id, so an app resolving an edge conflict has only what it can reach through the error.
- **There is no browser store.** The engine needs a filesystem for its lock, its fail-safe and its migrations. A renderer in a desktop application does not get one either: it reaches an engine held by the [Electron main process](/sdks/electron) over IPC.
- **Nothing queues a metadata write.** Tags and extensions are held as server state, so an item event cannot clobber them, but the outbox carries item and edge writes only.
