---
title: Properties, metadata and edges
description: The three places data lives on an item, who defines each, and which ones change the item's version.
---

## Properties

Properties are the item's own content: named values such as a note's `title` and `body`.

The item's type defines them. It declares each property's name and shape, and which properties are required. Marfa checks every write against the type and refuses a missing or invalid property with `400 invalid_properties`. A property the type doesn't declare is kept, unless the instance's strict mode is on for that type.

You write properties with `POST /items`, `PATCH /items/{id}`, and `POST /items/bulk`. An update sends the `version` it read. By default, `PATCH /items/{id}` merges the properties you send over the ones you don't send. With `properties_mode` set to `replace`, the properties you send become the item's whole set.

Every update to the properties raises the item's `version` by one, and Marfa keeps a snapshot of the properties as they were. The version also counts changes to the item's `type`, `tier`, `occurred_at`, and `source_id`.

```http
PATCH /items/{id}
Content-Type: application/json

{ "version": 3, "properties": { "title": "Reading list" } }
```

The item comes back at `version: 4`.

## Metadata

Every item has a metadata record beside it, which holds its tags and its extensions. `GET /items/{id}/metadata` returns both. Neither is part of the item's properties, and neither changes the item's `version`.

### Tags

A tag is a free-form label on an item, such as `favorite`. Tags are flat: they have no hierarchy and no schema. You or an app decide which tags to use, and any key that can write the item's type can change them. An item holds at most 100 tags, each up to 128 characters. A search matches tags along with the item's text.

You write tags in these ways:

- `tags` on `POST /items` sets them when you create the item.
- `POST /items/{id}/tags` adds tags.
- `PATCH /items/{id}/metadata` merges tags into the ones the item has.
- `PUT /items/{id}/metadata` replaces all of the item's tags.
- `DELETE /items/{id}/tags/{tag}` removes one tag.

A tag write leaves the item's `version` as it is. It moves the item's `updated_at`, and Marfa announces it as `metadata.changed`.

```http
POST /items/{id}/tags
Content-Type: application/json

{ "tags": ["favorite"] }
```

### Extensions

An extension is a JSON object stored on an item under a namespace. It holds data that an app keeps about an item that something else wrote. For example, a reading app can keep your place in an article that a connector brought in.

The app that writes a namespace decides what goes in it. Marfa requires only a JSON object. Namespaces are independent: writing one leaves the others alone. Which namespaces a key can read and write is set on the key, and a key sees only the namespaces it can read. The namespaces `core`, `marfa`, and `system` are reserved.

You write an extension with `PUT /items/{id}/extensions/{namespace}`, which replaces that namespace's data whole, and remove it with `DELETE /items/{id}/extensions/{namespace}`.

An extension write leaves the item's `version` as it is. It moves the item's `updated_at`, and Marfa announces it as `metadata.changed`.

```http
PUT /items/{id}/extensions/com.example.reader
Content-Type: application/json

{ "position": 0.42 }
```

The item's metadata then carries `"com.example.reader": { "position": 0.42 }` under `extensions`.

## Edges

An edge is a typed, directed relationship from one item, its source, to another item, its target. For example, `parent-of` puts one item under another, and `about` says that one item is about another. An edge isn't part of either item. It has its own `id`, its own `properties`, and its own `version`.

The edge's type defines it: how many edges each end can hold, which item types can be at each end, and what deleting one end does to the other. Marfa ships edge types such as `about`, `parent-of`, `references`, and `in-folder`. You or an app can register more with `POST /edge-types`.

You write edges with `POST /edges`, `PATCH /edges/{id}`, `DELETE /edges/{id}`, and `POST /edges/bulk`. You can also send `edges` on `POST /items` and `PATCH /items/{id}`. `GET /items/{id}` returns the item's outbound edges, grouped by edge type.

A change to an item's edges leaves the item's `version` as it is. The edge has its own version instead: it starts at 1 and goes up by one on every update, and `PATCH /edges/{id}` sends the version it read.

```http
POST /edges
Content-Type: application/json

{ "source_id": "<note id>", "target_id": "<book id>", "edge_type": "about" }
```

The edge comes back at `version: 1`.

## How they compare

| | What it is | Defined by | Raises the item's version | Written with |
| --- | --- | --- | --- | --- |
| Properties | The item's own content | The item's type | Yes | `POST /items`, `PATCH /items/{id}`, `POST /items/bulk` |
| Tags | Free-form labels on the item | You or an app, freely | No. Moves `updated_at` | `POST /items/{id}/tags`, `PATCH /items/{id}/metadata`, `PUT /items/{id}/metadata`, `DELETE /items/{id}/tags/{tag}` |
| Extensions | JSON objects an app keeps on the item, one per namespace | The app that writes the namespace | No. Moves `updated_at` | `PUT /items/{id}/extensions/{namespace}`, `DELETE /items/{id}/extensions/{namespace}` |
| Edges | Typed, directed relationships between two items | The edge type | No. The edge has its own `version` | `POST /edges`, `PATCH /edges/{id}`, `DELETE /edges/{id}`, `POST /edges/bulk` |

Because tag, extension, and edge writes leave the item's version alone, they don't make another writer's pending property update stale. A title changed in one app and a tag added in another both land.
