description: Find the message a server shows when it won't start, and claim an instance when the setup code is lost.
job: An owner whose server won't start, or who lost the setup code, finds the message they see and fixes it.

The server checks its settings, folders and database before it opens a port, and **a refusal is a line in its log and an exit,** with nothing changed. A failed `marfa server install`, `start` or `upgrade` prints the end of the log. Later, `marfa server status` shows it, or `docker logs <name>`.

## The server cannot start; fix these settings

A start-only setting has a value the server doesn't take. The server names each one in the same message and exits with status `1`:

```text
MARFA_MAX_CONNECTIONS must be a whole number, from 1 to 1000000 (got "abc")
```

Correct each value it names, then start the server again. [Instance settings](/reference/instance-settings#start-only-settings) says what each takes.

## The port is already taken (EADDRINUSE)

Another process listens on the server's port, often an earlier Marfa server. Stop it with `marfa server stop`, or give this one a free port with `MARFA_PORT`.

## MARFA_CONTROL_SOCKET must be a normalized absolute path of at most 103 bytes

The data folder is so deep that its [private socket](/run/run-on-a-server#the-private-socket) path is longer than a system allows. Keep the data in a shorter path, or set `MARFA_CONTROL_SOCKET` to a shorter absolute one.

## Is a symbolic link, and the server keeps its data only where it can make it private

The data folder, the database or the blob folder is a link the server can't trust, such as one another account made. Name the folder the link points to, or give that folder to the server's account with `chown`. A link you or root made, in a path no other account can change, is followed.

## Is open in another Marfa server

Another server already holds that database or folder, and **one database has one server.** Stop the other server, or give this one a data folder of its own, and leave its `.server-lock` files in place.

## The server refuses its database (exit 78)

The log says why, the file is untouched, and `marfa server run` stays idle:

- **`… which a newer build wrote`:** [go back](/run/go-back-a-release) to that build, or to the copy from before the update.
- **`… is not this build's`:** the file is changed, or its schema is unread here. Export with the build that wrote it, and restore into a new install.
- **`… was not upgraded from schema version …`:** fix the cause named, such as no room on the volume.

## I lost the setup code

An unclaimed instance writes a new code to its log at each start, and **only the newest works:** an older one gets `That setup code isn't right, or Marfa has replaced it since.` For an install, run `marfa server install` again for a new link. On Railway or in a container, restart the server and read the new `Claim this Marfa at …` line. On the server's computer, claim through the private socket:

```bash
marfa --socket ~/marfa-server/data/control/marfa.sock setup claim --username sam
```

## 409 owner_exists

The instance already has an owner: it's claimed once, and a second tab shows **This Marfa already has an owner.** Its **Sign in** link signs you in. If you've lost the password, [recover it](/run/sign-in-as-the-owner#recover-the-owners-password) from the server's computer.
