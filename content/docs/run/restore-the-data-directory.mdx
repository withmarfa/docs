A copy of [the data directory](/run/run-on-a-server#the-data-directory) brings back the same instance, keys and sign-ins included. A [backup](/run/back-up-and-restore) brings back the data into a new instance, and needs only its place.

## Check the copy

**The copy must be an image of one moment:** a copy taken with the server stopped, or a snapshot, such as a host's disk snapshot or Time Machine, which copies from an APFS snapshot. A file-by-file copy of a running server can hold a database that isn't whole. Before you replace anything, check that the copy is whole and that you have what goes with it:

- **The server's secrets:** `marfa.env` from the install folder, or `marfa.secrets` where the server made them, or the two variables your platform holds. With a different `MARFA_KEY_SALT`, the server starts but refuses every key and app token, and every browser is signed out: sign in as the owner again and make new keys. A different `MARFA_AUTH_SECRET` also signs everyone out of the browser.
- **`marfa.settings.key`,** inside the data directory, which seals the secret settings. Without it, each must be set again.
- **The release that wrote the database.** A server refuses a database another build wrote: [Fix a server that won't start](/run/troubleshooting/start-and-claim#the-server-refuses-its-database-exit-78) says what to do.

## Put a copy back

Stop the server, move the current data directory aside, put the copy in its place, and start the server. **Never copy over a running server's folder, and keep the old directory** until the instance has run from the copy. The commands below are for a native install; a container keeps its data in a volume, and a root install needs `chown -R marfa:marfa` on the copy. On an install made with `marfa server install`, `marfa server stop` and `marfa server start` do the stopping and starting: [the install page](/run/install#look-after-the-service) lists them.

```bash
marfa server stop
mv ~/marfa-server/data ~/marfa-server/data.before-restore
cp -Rp /Volumes/Backup/marfa-data-copy ~/marfa-server/data
marfa server start
```

## Settle the work each device kept

**A device keeps the work the copy lost.** Each app or synced directory that wrote after the copy's moment finds that the server went back, and queues that work again, blocked `server_restored`, so nothing is sent back unasked: you may have restored the copy to undo it.

**A device finds out only when it next talks to the server.** Until then, `marfa folders status` shows every file in step and `marfa device queue` lists the writes as accepted. For a directory, run a push first; it sends nothing, and the files then show `waiting` in `marfa folders status`:

```bash
marfa folders push ~/Documents/Home
```

**Send the held work,** to put it back on the server:

```bash
marfa device release --reason server_restored --db ~/Documents/Home/.marfa/core.sqlite
marfa folders push ~/Documents/Home
```

**Or drop it.** `marfa device queue --db ~/Documents/Home/.marfa/core.sqlite` lists the held writes, and `marfa device withdraw <id> --db ~/Documents/Home/.marfa/core.sqlite` drops one. The next push writes the file back as the server holds it. An app with a working copy gives its own `--db` to the same three commands.

A restore from an archive or a backup only adds to what the server holds, and sets off none of this.

The rules behind this page are in the [backing up](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#backing-up) section of the instance chapter and the [device](https://github.com/withmarfa/marfa/blob/main/conformance/spec/device.md) chapter of the contract.
