---
title: What the CLI and apps send
description: See what the CLI and an app built on the Swift SDK report about themselves, when, and what they never send.
---

The CLI and apps built on the Swift SDK report on themselves apart from the instance. **Neither sends anything until it's given a destination**: the CLI by the environment of the person who runs it, and an app by the people who build it. What an instance sends is in [Send an instance's telemetry](/run/telemetry).

## What the CLI sends

**The CLI sends nothing unless its environment names a destination.** `OTEL_SDK_DISABLED=true` turns off both reports:

| Report | Sent when | What it holds |
| --- | --- | --- |
| One trace for each command | `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` is set | The command's name, its exit code, the core's operations beneath it with their counts and outcomes, and the error code of a refusal |
| One exception to PostHog | `MARFA_POSTHOG_HOST` and `MARFA_POSTHOG_PROJECT_TOKEN` are both set, and the command ends in a fault | The command's name, the error and exit codes, the version, the operating system and architecture, and a fixed sentence for the kind of error |

**Neither report holds an argument, address, credential, item content or message,** and neither names a person. As on the server, an exception needs no OTLP endpoint. A destination that is unreachable or slow changes neither the command's output nor its exit code, and the command waits for it no longer than its timeout, two seconds by default.

**A fault is something the CLI or the core got wrong,** such as a panic or an answer it can't read. A refusal, a usage error, Ctrl-C, being offline, a timeout, a rate limit and any `5xx`, which the server reports itself, send none.

A folder watch started at login carries the settings set in the shell that turned it on, as [Sync from login](/use/keep-folders-syncing#send-error-reports-from-the-watch) shows. [The CLI's telemetry reference](https://github.com/withmarfa/marfa/blob/main/core/marfa-cli/COMMANDS.md#telemetry) lists every setting it reads, and every kind of fault.

## What apps send

**An app built on the Swift SDK sends nothing unless the people who built it gave it a destination and reporting is on.** The SDK's [`MarfaTelemetry` product](/swift-sdk/errors-and-testing#report-errors-and-events) has no destination of its own. It stays inert until the app passes it an `https` PostHog host and a project token, and its switch, `Telemetry.shared.isEnabled`, starts off. A build from public source, with the token kept out of the source as the SDK asks, sends nothing.

An app that reports sends two kinds of report to the PostHog project it was built for:

- **Errors.** One exception for each failure the app reports: the error's kind, one fixed sentence, the operation that was running and the error's code, with no person and no location lookup. A failure that repeats is held back, and each exception counts how many were.
- **Events.** A fixed set of log records, each a name with counts, flags and words fixed in the app's source, sent in batches over OTLP.

Every report also names the app, its version, the operating system, its version and the chip. **No report names the instance** the app is connected to, unlike the server's own telemetry, which [tells instances apart](/run/telemetry#tell-instances-apart).

### What an app never sends

**The SDK's types keep a person's words out of a report:** a report takes only text fixed in the source, numbers and booleans. So a report never holds:

- item text, titles, tags, IDs or natural keys;
- keys or credentials;
- the instance's ID, name or address;
- file paths or search text;
- an error's `message`, which can repeat any of these.

The SDK sends no product analytics: nothing about which screens a person opens or what they do. Turning `isEnabled` off drops every report waiting to go and sends nothing more, and each app decides where its own switch is.
