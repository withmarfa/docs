An instance is one server process and one SQLite database, so there's no database server to set up. Run one server for each database: **keep a host at one replica**.

## Where it can run

| Where | How |
| --- | --- |
| A Mac or Linux machine with Docker that stays on | [Install with the CLI](/run/install), one command. |
| A container you run yourself, in your own layout | [Run it in a container](#run-it-in-a-container), with one volume. |
| A computer that can't run containers | [Run it without a container](#run-it-without-a-container), under a supervisor. |
| Railway, the quickest way onto the internet, billed by Railway | The [Marfa template](https://railway.com/new/template/5z9-Ja) sets up the server, a volume, a backup bucket and the settings ([steps](https://github.com/withmarfa/marfa/blob/main/deploy/railway.md)). |

The server runs [housekeeping jobs](/run/housekeeping) and backups in the background, so turn off any host feature that stops an idle service, such as Railway's Serverless mode.

## Run it in a container

[`marfa server install`](/run/install) does these steps for you.

Every release publishes the server image to `ghcr.io/withmarfa/marfa-server` for `linux/amd64` and `linux/arm64`, tagged with its release number and `latest`. The image sets `NODE_ENV=production`, the port and the paths under `/data`.

<Steps>
<Step>

### Generate the secrets

Generate each secret once:

```bash
openssl rand -hex 32
```

Back up both outside the data directory, which holds neither:

| Secret | What it does | If it changes |
| --- | --- | --- |
| `API_KEY_SALT` | Hashes keys and app tokens. The database holds only the hashes. | The server refuses every existing key and token with `401 unauthorized` until it starts again with the original. |
| `MARFA_AUTH_SECRET` | Signs sign-in cookies and the links the server makes. | Every browser is signed out. |

</Step>
<Step>

### Write the settings

Put the secrets and the instance's [address](#the-address) in `marfa.env`, with any [object store](#an-object-store)'s `S3_` settings. Keep the file out of any repository.

```bash title="marfa.env"
API_KEY_SALT=<a secret>
MARFA_AUTH_SECRET=<another secret>
MARFA_AUTH_BASE_URL=https://marfa.example.com
```

In production, the server refuses to start without these three, or with a weak secret. [Settings](/run/settings#every-environment-setting) defines every setting.

</Step>
<Step>

### Start the container

Pull a release by its tag, not `latest`, so a restart never changes the build and an [upgrade](/run/upgrade) can name both builds. Start it with one volume at `/data`:

<include cwd>src/generated/server-image.md</include>

`-p 127.0.0.1:8600:8600` publishes the port on the loopback address only, for a proxy or tunnel on the same machine. A bare `-p 8600:8600` opens it on every network interface, on Linux past the host's firewall.

Without `S3_BUCKET`, no copy leaves the machine, so [back up](/run/back-up-and-restore) the volume yourself. To run code that no release holds, [build the image yourself](https://github.com/withmarfa/marfa/blob/main/deploy/README.md#building-the-image-yourself).

</Step>
<Step>

### Claim the instance

Ask the CLI in the image for a setup link:

```bash
docker exec marfa marfa --socket /data/control/marfa.sock setup open --no-browser
```

The link works once, for five minutes. Open it in a browser and choose the owner's email and password.

</Step>
</Steps>

## Run it without a container

The container is the tested route. Without it, the server needs Node.js 22.14 or later. Build it in a clone of the repository:

```bash
pnpm install --frozen-lockfile
pnpm --filter "@withmarfa/server..." build
```

Give the server the three settings from the container steps, plus these four. Outside `production`, it uses defaults that suit only a trial.

```bash title="marfa.env"
NODE_ENV=production
PORT=8600
SQLITE_PATH=/srv/marfa/data/marfa.db
BLOB_PATH=/srv/marfa/data/blobs
```

Start it from `packages/server` under a supervisor, such as launchd or systemd, with these settings in its environment: the server doesn't read `marfa.env`. The `--import` loads [telemetry](/run/telemetry).

```bash
cd packages/server
node --import ./dist/instrumentation.js dist/index.js
```

Then claim the instance, as the server's account, with `marfa --socket /srv/marfa/data/control/marfa.sock setup open`.

## The address

`MARFA_AUTH_BASE_URL` is the URL your devices reach the instance at. The server uses it as the OAuth issuer and in its links. **The owner can claim the instance and sign in only over `https`**, or over `http` on `localhost`, `127.0.0.1` or `[::1]`.

Devices reach the instance on your local network, from anywhere over Tailscale, or through a Cloudflare Tunnel at an address on your own domain. Claude and ChatGPT connect from their own servers and [need a public address](/build/connect-claude-and-chatgpt#give-the-instance-a-public-address).

**Behind a proxy or tunnel, tell the server which caller address to believe.** Otherwise every request seems to come from the proxy, and anyone's wrong passwords count toward one address's limit of ten in fifteen minutes, locking the owner out. [`marfa server install`](/run/install#choose-how-its-reached) sets the right one. By hand, set one of these:

- **`TRUSTED_PROXY_CIDRS`** names the proxy's address ranges. The server believes `X-Forwarded-For` from any address in them, so list only your proxy. A proxy beside a container, such as Tailscale Serve, reaches it from Docker's network, which `docker network inspect bridge --format '{{json .IPAM.Config}}'` shows. Every container there is then trusted, so run nothing there you don't control.
- **`TRUSTED_PROXY_HEADER`** names a header the platform's edge overwrites with the caller's address, for a host whose edge addresses you can't list. Set it only when nothing reaches the server except through that edge, or any client can choose its address.

**Through Cloudflare, turn off Email Address Obfuscation**, or every email address on the instance's pages shows as `[email protected]`. Turn it off under **Security** > **Settings** in the Cloudflare dashboard, or for one hostname with a Configuration Rule that sets **Email Obfuscation** off.

## An object store

Set `S3_BUCKET` and the other `S3_` settings, and the server keeps a second copy of every blob in an S3-compatible bucket. The container also [streams the database there](/run/back-up-and-restore#with-a-bucket).

- **Give each instance that shares a bucket its own `S3_PREFIX`**, such as `trial/blobs`. Two instances with one prefix write one database replica, and a new volume of either starts on whichever was replicated last.
- **Share a bucket only between instances of one owner.** A prefix keeps replicas apart, not access: each instance holds credentials for the whole bucket.
- **Put the bucket on a different site from the instance.** A link the bucket signs serves a blob without the instance's download protections, so a bucket under the instance's domain could let an uploaded HTML file run as one of its pages.

## The data directory

The database and the blobs are the whole of your data, so put them on storage that survives a restart, such as a container volume. With the paths above, the directory holds:

<Files>
  <Folder name="data" defaultOpen>
    <File name="marfa.db" />
    <File name="marfa.db-wal" />
    <File name="marfa.db-shm" />
    <Folder name="blobs" />
    <Folder name="control" defaultOpen>
      <File name="marfa.sock" />
      <File name="marfa.sock.lock" />
    </Folder>
  </Folder>
</Files>

With an [object store](#an-object-store), the container's volume also holds Litestream's files. [Back up and restore](/run/back-up-and-restore) says which files a copy needs.

**A missing blob folder stops the start**, such as on a drive that didn't mount. When the database records files there, the server names the folder, creates nothing and exits with status `1`, unless a bucket can fill it ([the rule](https://github.com/withmarfa/marfa/blob/main/conformance/spec/stores.md#storesmissing-folder-refused)). Mount the drive or restore the folder, or point `BLOB_PATH` at another folder to start empty on purpose.

## The private socket

`control/marfa.sock`, or the path `MARFA_CONTROL_SOCKET` names, lets a command on the same machine, run as the server's account, act with the machine's own authority instead of a credential: to claim the instance or recover the owner's password, for example. [Use the private socket](/cli#use-the-private-socket) lists the commands that need it.

- **The socket's folder must belong to the server's account**, readable by no one else. On Linux, the server checks this with the `acl` package, so install it.
- **A start replaces a socket a crash left behind**, but refuses one another process listens on.

## Keep it running

Point your supervisor or monitor at [`GET /health`](/api-reference/health-and-maintenance/getHealth), which needs no credential. It answers `503` when the database, a write, the disk or blob storage is down, and `200` otherwise. The container checks it every 30 seconds.

`SIGTERM` or `SIGINT` stops the server within eight seconds, so give it ten before a runtime kills the process. Its exit status tells your supervisor whether to start it again:

| Status | Meaning | Your supervisor |
| --- | --- | --- |
| `0` | A clean stop. | Starts it again if you want it running. |
| `1` | A failed start or stop, such as a port in use, a setting outside its rules, a missing blob folder or, in the container, a database that may be older than the bucket's copy. | Starts it again. The last two repeat until you act: see [Back up and restore](/run/back-up-and-restore). |
| `78` | The server won't start on the database, such as one a newer build wrote or an update it couldn't finish, and changed nothing. The container stays up and unhealthy, with the reason in its log. | Doesn't start it again. See [Upgrade](/run/upgrade#when-a-build-refuses-the-database). |
