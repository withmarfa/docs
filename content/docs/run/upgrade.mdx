---
title: Upgrade an instance
description: Move an install to a newer release in place once that release says it opens your database, and move to a new install when it doesn't.
---

**Before Marfa 0.1, a release may not read another release's database,** so an install moves only when the release it moves to says it opens the database. `marfa server upgrade` is the one command that changes an install's release, and it asks that release first. When the answer is no, nothing changes, and you move your data to a new install instead. [The changelog](/changelog) says what each release changes.

## See whether a newer release is out

Every six hours the server asks GitHub's API for Marfa's newest published release, **only at public addresses**, whatever `allow_private_addresses` says. With a credential that holds `instance.read`:

<Terminal>

```bash
marfa update status
```

```text
release              0.0.86
latest.release       0.0.87
available            true
method               server
step                 -
```

</Terminal>

`available` is `true` only when the newest release is newer than the one running. `method` is `server` where the server can replace its own programs, else `manual`, with `step` saying what to do. A release whose files sit anywhere but withmarfa/marfa's GitHub releases is a failed check, named in `check_error`. `update_check_enabled` set to `false` stops the check.

## Upgrade in place

**Take a backup first,** with `marfa backups run`. Then move the install the way it was made:

- **The install script, as a service.** Run `marfa update start`, with `instance.maintain`. The server downloads the release from Marfa's release address, checks its checksums, and checks that the new server runs, accepts the settings and opens the database. If a check fails, it keeps the running programs, and `marfa update status` says why in `last`. [Go back to an earlier release](/run/go-back-a-release#after-the-server-updates-itself) says how the new release is tried and put back.
- **Homebrew.** `marfa update start` is refused `409 update_unavailable`, since Homebrew owns the programs. Run `brew upgrade marfa`, then `marfa server upgrade`.
- **Programs you install yourself.** Install the new release over the old, then run `marfa server upgrade` with the new `marfa`.
- **Docker, set up by the CLI.** Run `marfa server upgrade --release <version>`. It asks the image first, then names the release in `.env` and recreates the container on the same volume.
- **A container you run.** Create it again from the new release's image, on the same volume. [Check the image](/run/run-on-a-server#check-the-image) first.
- **Railway.** Set the image tag to the new release and deploy, on the same volume, which Railway's guide advises against: back up the volume first.

`marfa server upgrade` says what it moved from and to, and whether it updated the database. **A release that changes the database schema first copies the database** to `marfa.db.before-upgrade` beside it, replacing any earlier copy, when the database holds data. It refuses to start, and changes nothing, if the copy can't be written or would take the volume below `disk_reserve_bytes`. [Go back to an earlier release](/run/go-back-a-release) says how to use the copy.

**`marfa server install`, `start` and `restart` keep an install on its release.** Run with another release's `marfa`, or after Homebrew or the install script replaced the programs, they change nothing and name the `marfa server upgrade --dir` command that moves it.

## When the new release refuses your database

The command says so, and **the service, `.env` and the database stay as they were.** Homebrew and the install script have already replaced the programs, so the message also gives the commands that put the earlier release back. On Railway or in a container you run, a release that refuses the database doesn't start and says why in its log: set the earlier tag again.

Then move your data to a new install of the new release, as below.

## Move to a new install

Make a second install of the new release, restore your data into it, and retire the old install once the new one works. On Railway, restore into a new project.

<Steps>
<Step>

### Stop writing to the old instance

Close its apps and agents, and [pause its synced folders](/use/change-or-stop-a-folder#pause-a-folder). **A change made on the old instance after you take the copy never reaches the new one.**

</Step>
<Step>

### Take a fresh copy

With the old instance's CLI, run `marfa backups run`. With no backup place, export an archive instead: `marfa export --output marfa-move.tar`.

</Step>
<Step>

### Make the new install

Install the new release's programs into their own folder, then make an install with its own name, folder and port, reached from this machine alone for now:

```bash
curl -fsSL https://raw.githubusercontent.com/withmarfa/marfa/main/scripts/install.sh | MARFA_INSTALL_DIR=~/marfa-next/bin sh
~/marfa-next/bin/marfa server install --name marfa-next --dir ~/marfa-next/server --port 8610 --access local
```

Claim it. **Run the new install's commands with `~/marfa-next/bin/marfa` and its `--dir`,** and leave that folder off your `PATH`.

</Step>
<Step>

### Restore into it

The new install's [private socket](/run/run-on-a-server#the-private-socket) reaches that instance alone with no sign-in. For a backup, point it at the same place, then find the backup and restore it:

```bash
~/marfa-next/bin/marfa --socket ~/marfa-next/server/data/control/marfa.sock config set backup_path /Volumes/Backup/marfa
~/marfa-next/bin/marfa --socket ~/marfa-next/server/data/control/marfa.sock backups list
~/marfa-next/bin/marfa --socket ~/marfa-next/server/data/control/marfa.sock backups restore <instance id> <backup name>
```

For a bucket, set the same bucket, prefix and credentials, as [Use an object store](/run/back-up-and-restore#use-an-object-store) shows. For an archive, run `restore marfa-move.tar` through the socket instead. The answer counts what it restored, and `blobs_missing` names any file it lacks.

</Step>
<Step>

### Retire the old install

With the old install's own `marfa`, remove its service, since a stopped service starts again at the next login:

```bash
marfa server uninstall --dir ~/marfa-server
```

It keeps the data and `marfa.env`: **keep both until the new instance has proven itself.** Then give the new install the port and access the old install's `.env` names in `MARFA_PORT`, `MARFA_ACCESS` and `MARFA_ADDRESS`:

```bash
~/marfa-next/bin/marfa server install --dir ~/marfa-next/server --port 8600 --access cloudflare --address https://marfa.example.com
```

A tunnel or proxy aimed at the old port now reaches the new instance. Reconnect each device and app, as [On each device](/run/back-up-and-restore#on-each-device) says.

</Step>
</Steps>

## Try a release first

To look at a release before you upgrade, make a new install as above and restore an **archive** into it. Give it its own `backup_path` or `object_store_prefix`, never your instance's, so the two keep their backups and files apart. **A trial is a copy from the moment of its restore,** so it's never promoted: remove it with `marfa server uninstall --delete-data` and its own `--dir`.

## Types a new build leaves in conflict

A new release can give a built-in type a field that a type an app registered beneath it declares in another shape. The type and its items keep working, and [Change a type](/build/change-a-type) says how the app puts it right.

The rules behind this page are in the contract's [updates](https://github.com/withmarfa/marfa/blob/main/conformance/spec/updates.md) chapter and the [instance](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#a-database-this-build-did-not-write) chapter.
