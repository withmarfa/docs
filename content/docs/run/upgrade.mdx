title: Upgrade
description: Move an instance to a new build, which updates its database in place after copying it, and go back if you need to.
---

A new build **updates your database in place** the first time it starts on it. Before it changes anything, it copies the database to a file beside it, and **it keeps that copy until you remove it**. The copy is your way back to the build you upgraded from.

With an install the CLI set up, [`marfa server upgrade`](/run/install#change-upgrade-or-remove-it) moves the server to a release and prints where the copy is. In your own container or on your own machine, stop the server and start the new build on the same data directory, or the same volume.

## What a new build does with your database

When the server starts, it reads the database's schema version before it opens a port. A database at the build's own version opens as it is, with no copy. A database an earlier build wrote is updated:

1. **The server checks for room.** The disk that holds the database needs at least twice the database's size free, counting the `marfa.db-wal` log beside it: room for the copy and for the update. With less, it refuses to start and changes nothing.
2. **It copies the database** to a file beside it named `marfa.db.backup-schema-<from>-to-<to>-<time>`, such as `marfa.db.backup-schema-1-to-2-20261027T101500000Z`. The numbers are the two schema versions and the time is in UTC. It writes the copy under a name that ends in `.partial`, checks it, then renames it, so a file without that ending is always a whole copy.
3. **It updates the database in one transaction.** Before it commits, it checks that every table it kept holds as many rows as before, that no more rows refer to missing rows than before, and that the result has the build's own shape. If a check fails, it rolls the update back and refuses to start.
4. **It logs the update.** The line says the database was updated, from which schema version to which, and where the copy is:

```text
Updated the database in /data/marfa.db from schema version 1 to 2. The copy taken before the update is at /data/marfa.db.backup-schema-1-to-2-20261027T101500000Z, and stays until you remove it.
```

In the JSON log, the same line carries `schema_from`, `schema_to` and `backup_path`.

Because the update is one transaction, **a server stopped or killed partway leaves the database as it was**, and the next start updates it again, with a copy of its own. A `.partial` file left by a server stopped while it wrote the copy isn't a whole copy, and you can delete it. A later start of the same build finds the database already updated and makes no second copy.

## When a build refuses the database

A build refuses some databases. **It leaves the file as it found it**, opens no port, and exits with status `78`. The error in its log names the file and the reason:

- **A newer build wrote it.** The build doesn't know what the newer one changed. Run that build or a newer one.
- **Its shape matches no build's schema**, such as a database changed by hand, or one that holds tables or settings a build retired. The log says to export the data with the build that wrote it and restore the archive into this build, which [Export and restore](/run/export-and-restore) covers. A different build may refuse the archive, so keep the old build and its data until the restore has answered.
- **The update couldn't finish**: the disk lacked room, the copy couldn't be made, or the update failed a check. When the copy was made, the message names it.

The build you upgraded from still reads a database the new build refused, so starting it again brings the instance back. In the container, a refused database doesn't stop the container: it stays up and unhealthy with the reason in its log, so a restart policy can't loop on it. `marfa server upgrade` waits for the server, and when it refuses the database, says so and how to set the release back.

## Go back to the earlier build

To go back, start the earlier build on the copy, not on the updated database. A build that knows schema versions refuses a database a newer build updated, and an older build may open it without knowing what the update changed. **Writes made since the upgrade aren't in the copy.**

<Steps>
<Step>

### Stop the instance

Note the release you're going back to. Its image, `ghcr.io/withmarfa/marfa-server:<release>`, stays available under that tag.

</Step>
<Step>

### Put the copy in place

In the data directory, delete `marfa.db-wal` and `marfa.db-shm`, then rename the copy to `marfa.db`, replacing the updated database. SQLite applies a log it finds beside a database file even when the log belongs to another file, so **delete the log first**.

</Step>
<Step>

### Start the earlier build

With a bucket, the copy is older than the bucket's copy, so the container doesn't start it under the same `S3_PREFIX`. Give it a new prefix, as [Back up and restore](/run/back-up-and-restore#with-a-bucket) describes. Then read `GET /`, which answers the running build as `release`.

</Step>
</Steps>

With `marfa server upgrade`, the copy is in the install's data volume. `docker cp <name>:<copy> .` copies it out, and the CLI refuses to move the install to an older release, so start the older release on the copy yourself.

## Remove the copy

The copy is a whole database, as large as the one it copies, and **nothing removes it**. Once the new build holds what you expect and you won't go back, delete the file. In the container, `docker exec <container> rm /data/<copy>` removes it. Litestream replicates only `marfa.db`, so the copy isn't in the bucket. A machine backup holds the copy too, and you can leave it out once you won't go back.

On Railway, [update the server](https://github.com/withmarfa/marfa/blob/main/deploy/railway.md#update-the-server) says how to change the image's tag and go back with a volume backup.

The rules behind this page are in the [upgrading](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#upgrading) section of the instance chapter of the contract, and the steps for a container and a bucket are in the [deployment guide](https://github.com/withmarfa/marfa/blob/main/deploy/README.md#upgrading).
