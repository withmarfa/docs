---
title: Upgrade an instance
description: Move an install to a newer release in place, or into a new install when that release will not open the database, and go back to an earlier one.
job: An owner moves an install onto another release.
---

Before Marfa 0.1, a release may not read another release's database. `marfa server upgrade` moves the install, newer or older, and changes nothing if that release says no.

## See whether a newer release is out

With `instance.read`, `marfa update status` reports `available`, `method` (`server` or `manual`) and `check_error`. The server asks GitHub every six hours. `update_check_enabled` set to `false` stops it.

### What each release opens

| What | What a release opens |
| --- | --- |
| Your database | From 0.0.89 on, a database from 0.0.86 on, except one 0.0.88 wrote. 0.0.110 changes it, and 0.0.109 can't open it. |
| An archive | Its own version and earlier. 0.0.110 and later write version 5, 0.0.101 to 0.0.109 version 4, and 0.0.93 to 0.0.100 version 3. |
| An app or `marfa device` | From 0.0.110 on, only a server from 0.0.110 on, refusing an older one `server_too_old`. Upgrade the server first. |

## Upgrade in place

Take a backup with `marfa backups run`.

- **Install script, as a service.** `marfa update start`, or an agent calling `marfa_update_server`, with `instance.maintain`. [How the try ends](#after-the-server-updates-itself).
- **Homebrew.** `brew upgrade marfa`, then `marfa server upgrade`. `marfa update start` returns `409 update_unavailable`.
- **Programs you install.** Use the install script, which never overwrites running programs, then `marfa server upgrade` with the new `marfa`.
- **Docker from the CLI.** `marfa server upgrade --release <version>` on the same volume.
- **A container you run.** Same volume. [Check the image](/run/run-on-a-server#check-the-image).
- **Railway.** The new tag, on the same volume, after a volume backup.

When the database holds a row, a schema change writes `marfa.db.before-upgrade`, the database from before that change, replacing any earlier copy. Nothing changes if the copy can't be written or would leave less free than `disk_reserve_bytes`.

Installed Marfa plugins, their types, and their connector settings, secrets and mapping stay.

`marfa server install`, `start`, `restart` and another release's `marfa` change nothing. They name `marfa server upgrade --dir`.

On a refusal, the service, `.env` and the database stay. Follow the message to put replaced programs back, or set the previous tag, then [move to a new install](#move-to-a-new-install).

### Types a new build leaves in conflict

A built-in type can gain a field a type beneath it declares in another shape. The type and its items keep working. See [Change a type](/build/change-a-type).

## Move to a new install

Restore into a second install, on Railway a new project. Give a trial an archive and its own backup place, and remove it with `marfa server uninstall --delete-data` and its own `--dir`.

<Steps>
<Step>

### Stop writing to the old instance

Close its apps and agents. In each synced directory, run `marfa folders push <dir>` until it exits `0`: `3` means an edit may be unsent. Then [pause it](/use/change-or-stop-a-folder#pause-a-folder): a pause sends nothing, and a paused directory refuses a push. Later changes stay on the old instance.

</Step>
<Step>

### Take a fresh copy

Run `marfa backups run` with the old CLI. With no backup place, run `marfa export --output marfa-move.tar`.

</Step>
<Step>

### Make the new install

Claim the install, and run it with that `marfa` and its `--dir`, off `PATH`.

```bash
curl -fsSL https://raw.githubusercontent.com/withmarfa/marfa/main/scripts/install.sh | MARFA_INSTALL_DIR=~/marfa-next/bin sh
~/marfa-next/bin/marfa server install --name marfa-next --dir ~/marfa-next/server --port 8610 --access local
```

</Step>
<Step>

### Restore into it

Use the new install's [private socket](/run/run-on-a-server#the-private-socket):

```bash
~/marfa-next/bin/marfa --socket ~/marfa-next/server/data/control/marfa.sock config set backup_path /Volumes/Backup/marfa
~/marfa-next/bin/marfa --socket ~/marfa-next/server/data/control/marfa.sock backups list
~/marfa-next/bin/marfa --socket ~/marfa-next/server/data/control/marfa.sock backups restore <instance id> <backup name>
```

A bucket follows [Use an object store](/run/back-up-and-restore#use-an-object-store). For an archive, run `restore marfa-move.tar` through the socket. Check `blobs_missing`: it names any file the copy lacks.

</Step>
<Step>

### Retire the old install

`marfa server uninstall --dir ~/marfa-server` removes the service and keeps the data and `marfa.env` until the new instance has proven itself. Then set the old port and access:

```bash
~/marfa-next/bin/marfa server install --dir ~/marfa-next/server --port 8600 --access cloudflare --address https://marfa.example.com
```

Reconnect each device as [On each device](/run/back-up-and-restore#on-each-device) says.

</Step>
</Steps>

## Go back to an earlier release

Try `marfa server upgrade` first: it changes nothing if that release refuses. If it opens the database, everything stays, Marfa plugins and connector settings too. On a refusal, [swap in the copy](#once-the-database-has-changed): 0.0.109 needs it after 0.0.110.

### Go back by hand

- **Programs you install.** Set `MARFA_VERSION`. Homebrew ships only its newest release: run `~/.local/bin/marfa server upgrade`.
- **Docker from the CLI.** `marfa server upgrade --release <version>`. Before 0.0.76, [move to a new install](#move-to-a-new-install).
- **Railway.** Deploy the earlier tag.

```bash
curl -fsSL https://raw.githubusercontent.com/withmarfa/marfa/main/scripts/install.sh | MARFA_VERSION=0.0.109 sh
marfa server upgrade --dir ~/marfa-server
```

For 0.0.85 or earlier, or when a message says the last release can't be told, run that release's `marfa server restart`, which changes nothing on a database it can't read.

### After the server updates itself

`marfa update status` reports `last`. The old server is kept as `.marfa-server.previous`, and the new `marfa` is `.marfa.next`.

- **`succeeded`.** Both programs report the new release after the new server has stayed up for 20 seconds. The old `marfa` is `.marfa.previous`.
- **`rolled_back`.** Two early ends, or exit `78`, and the old release still opens the database. Stopping the service or the machine counts no start.
- **`failed`.** The old release can't open the database. The new release stays.

### Once the database has changed

<Callout type="warn" title="Everything written since the copy is lost">
The copy's Marfa plugins, types, settings, secrets and mapping come back. A Marfa plugin installed since, or a connector setting changed since, does not. 0.0.109 can't read an archive 0.0.110 writes. A readable archive adds only items the copy lacks.
</Callout>

<Steps>
<Step>

### Stop the server

Run `marfa server stop --dir ~/marfa-server`.

</Step>
<Step>

### Swap in the copy

Move `marfa.db`, `marfa.db-wal` and `marfa.db-shm` aside, then copy `marfa.db.before-upgrade` to `marfa.db`. A crash, or a stop while the database was open, can leave writes in `marfa.db-wal`.

```bash
mkdir ~/marfa-server/replaced
cd ~/marfa-server/data
mv marfa.db marfa.db-wal marfa.db-shm ~/marfa-server/replaced/
cp marfa.db.before-upgrade marfa.db
```

`mv` reports a missing file and moves the rest. Keep the moved files until the instance works.

On Docker's `<name>-data` volume, `docker cp` can't remove a file:

```bash
docker run --rm --user 65532:65532 -v marfa-data:/data busybox:1.37 sh -c 'cd /data && mkdir replaced && for f in marfa.db marfa.db-wal marfa.db-shm; do [ ! -e "$f" ] || mv "$f" replaced/; done && cp marfa.db.before-upgrade marfa.db'
```

`docker cp marfa:/data/replaced .`

</Step>
<Step>

### Move to the earlier release

Then [go back by hand](#go-back-by-hand).

</Step>
</Steps>

See [updates](https://github.com/withmarfa/marfa/blob/main/conformance/spec/updates.md) and [instance](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#a-database-this-build-did-not-write).
