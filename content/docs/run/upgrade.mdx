title: Upgrade an instance
description: Move to a newer release by restoring your data into a new install, try a release first if you like, and know what moving an install in place does.
---

**Before Marfa 0.1, a newer release is a new instance, not an upgrade of the one you run.** A release doesn't promise to read another release's database, archive or backup, and one that updates the database leaves it in a shape the earlier one refuses. So keep your instance on its release, and move by restoring into a new install. [The changelog](/changelog) says what each release changes.

## Keep an instance on its release

An install moves to another release only when something replaces its programs or its image:

| Install | What moves it | To keep it where it is |
| --- | --- | --- |
| [The install script](/run/install#install-the-programs) | Running the script again into the same folder | Install another release into another folder |
| Homebrew | `brew upgrade` | Run `brew pin marfa` |
| Either, as a service | `marfa server start`, `restart` or `install` run by another release's `marfa`, which points the service at the `marfa-server` beside it | Run each install's commands with its own `marfa` |
| Docker, set up by the CLI | Only `marfa server upgrade`, since `.env` names the release | Nothing to do |
| A container you run | A tag that moves, such as `latest` | Start it from a version tag |
| Railway | A changed tag, or image auto updates | Keep the tag pinned and auto updates off |

**To update only the CLI on the server's machine,** install it into a folder of its own, as [Update the CLI](/cli#update-the-cli) shows.

## Move to a newer release

Make a second install of the new release, restore your data into it, and retire the old install once the new one works. On Railway, deploy the template into a new project and restore there.

<Steps>
<Step>

### Stop writing to the old instance

Close its apps and agents, and [stop its folder watches](/use/pause-or-stop-a-folder). **A change made on the old instance after you take the copy never reaches the new one.**

</Step>
<Step>

### Take a fresh copy

With the old instance's CLI, take a backup:

```bash
marfa backups run
```

With no backup place, export an archive instead: `marfa export --output marfa-move.tar`.

</Step>
<Step>

### Make the new install

Install the new release's programs into their own folder, then make an install with its own name, folder and port, reached from this machine alone for now:

```bash
curl -fsSL https://raw.githubusercontent.com/withmarfa/marfa/main/scripts/install.sh | MARFA_INSTALL_DIR=~/marfa-next/bin sh
~/marfa-next/bin/marfa server install --name marfa-next --dir ~/marfa-next/server --port 8610 --access local
```

Claim it. **Run the new install's commands with `~/marfa-next/bin/marfa` and its `--dir`, and leave that folder off your `PATH`:** a `marfa server start` with no `--dir` would move the old install to the new release.

</Step>
<Step>

### Restore into it

Here, the new install's [private socket](/run/run-on-a-server#the-private-socket) reaches that instance alone with no sign-in. Elsewhere, [sign in](/run/back-up-and-restore#restore-a-backup) and drop `--socket`. For a backup, point it at the same place, then find the backup and restore it:

```bash
~/marfa-next/bin/marfa --socket ~/marfa-next/server/data/control/marfa.sock config set backup_path /Volumes/Backup/marfa
~/marfa-next/bin/marfa --socket ~/marfa-next/server/data/control/marfa.sock backups list
~/marfa-next/bin/marfa --socket ~/marfa-next/server/data/control/marfa.sock backups restore <instance id> <backup name>
```

For a bucket, set the same bucket, prefix and credentials, as [Use an object store](/run/back-up-and-restore#use-an-object-store) shows. For an archive, run `restore marfa-move.tar` through the socket instead.

</Step>
<Step>

### Check it

The answer counts what it restored, and `blobs_missing` names any file it lacks. `items summaries`, through the socket, lists the items.

</Step>
<Step>

### Retire the old install

With the old install's own `marfa`, remove its service, since a stopped service starts again at the next login:

```bash
marfa server uninstall --dir ~/marfa-server
```

It keeps the data and `marfa.env`: **keep both until the new instance has proven itself.** Then give the new install the port your devices use, and the way they reach it, as the old install's `.env` names them in `MARFA_PORT`, `MARFA_ACCESS` and `MARFA_ADDRESS`:

```bash
~/marfa-next/bin/marfa server install --dir ~/marfa-next/server --port 8600 --access cloudflare --address https://marfa.example.com
```

A tunnel or proxy aimed at the old port now reaches the new instance, and the command sets its sign-in address once the address answers as it. Then reconnect each device and app, as [On each device](/run/back-up-and-restore#on-each-device) says.

</Step>
</Steps>

## Try a release first

To look at a release before you move, make the new install as above and restore an **archive** into it. Give it its own `backup_path` or `object_store_prefix`, never your instance's, so the two keep their backups and files apart.

**A trial is a copy from the moment of its restore.** What you change on your instance afterward never reaches it, and restoring a later archive adds only what the trial lacks. So a trial is never promoted: when you're ready, remove it with `marfa server uninstall --delete-data` and its own `--dir`, then move as above.

## See whether a newer release is out

The server checks GitHub for a published release every six hours. With a credential that holds `instance.read`:

<Terminal>

```bash
marfa update status
```

```text
release              0.0.79
latest.release       0.0.80
available            true
method               server
step                 -
```

</Terminal>

`available` is `true` only when the newest release is newer than the one running. `method` is `server` where the server can replace its own programs, and `manual`, with `step` saying what to do, elsewhere. `update_check_enabled` set to `false` stops the check.

## Move an install in place

To move an install anyway, **take a backup first** with `marfa backups run`. Each way does this:

- **The install script, as a service.** `marfa update start`, with `instance.maintain`, makes the server download the release, check its checksums, and check that the new server runs, accepts the settings and opens the database. It keeps the running programs if a check fails, saying why in `last`, and otherwise swaps them, keeping the old ones.
- **Homebrew.** `marfa update start` is refused `409 update_unavailable`, since Homebrew owns the programs. Run `brew upgrade marfa`, then `marfa server upgrade`.
- **Programs you replaced yourself.** `marfa server upgrade`, run with the new `marfa`, restarts the service on the programs beside it, says whether it updated the database, and refuses an older release.
- **Docker, set up by the CLI.** `marfa server upgrade --release <version>` names the new release in `.env` and recreates the container on the same volume.
- **A container you run.** Create it again from the new release's image, on the same volume. [Check the image](/run/run-on-a-server#check-the-image) first.
- **Railway.** Changing the tag redeploys the service on the same volume, which Railway's guide advises against. Back up the volume in Railway first.

**A release that changes the database schema first copies the database** to `marfa.db.before-upgrade` beside it, replacing any copy from an earlier change, when the database holds data. It refuses to start, and changes nothing, if the copy can't be written or would take the volume below `disk_reserve_bytes`. `marfa server upgrade` says whether it made the copy and where. [Go back to an earlier release](/run/go-back-a-release) says how to use it.

## Types a new build leaves in conflict

A new release can give a built-in type a field that a type an app registered beneath it declares in another shape. The type and its items keep working, and [Change a type](/build/change-a-type) says how the app puts it right.

The rules behind this page are in the contract's [updates](https://github.com/withmarfa/marfa/blob/main/conformance/spec/updates.md) chapter and the [instance](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#a-database-this-build-did-not-write) chapter.
