---
title: Upgrade an instance
description: Find out whether a newer release is out, move an instance to it safely, and know what a release does when it can't read your database.
---

**Before Marfa 0.1, a release doesn't promise to read another release's database, or an archive or backup another release wrote.** The server checks before it changes anything, and refuses rather than guess, so trying a newer release never damages your data. [The changelog](/changelog) says what each release changes.

## See whether a newer release is out

The server checks GitHub for a published release every six hours. With `instance.read`:

<Terminal>

```bash
marfa update status
```

```text
release              0.0.80
check_enabled        true
checked_at           2026-11-19T00:03:47.797Z
check_error          -
latest.release       0.0.80
latest.published_at  2026-11-18T23:23:28.000Z
available            false
method               server
step                 -
progress.state       idle
progress.release     -
last                 -
```

</Terminal>

`available` is `true` only when the newest release is newer than the one running. `method` is `server` where the server can update itself, and `manual` elsewhere, with `step` saying what to do on the host. `update_check_enabled` set to `false` stops the check, and nothing leaves the machine for it. `marfa server status`, and `version` in what `GET /` answers, also show the running release.

## Update an installed server

On a machine you [installed with one command](/run/install), the server replaces its own programs. With `instance.maintain`:

```bash
marfa update start
```

Before it swaps anything, the server checks the download against the release's checksums, checks that each new program runs and reports the release, and **asks the new server whether it accepts this instance's settings and opens its database**. If any check fails, or the disk lacks room, it keeps the running programs and says why in `last`. It keeps the old programs beside the new ones, and if the new release doesn't stay up through its second start, it puts them back and reports the update as rolled back.

`marfa server upgrade` does the same from the machine itself: once you [install the CLI](/run/install#change-upgrade-or-remove-it) again, it moves the server to the release installed beside it, says whether it updated the database, and refuses an older release. If the new release refuses the database, it says how to go back.

## Update a container or Railway

A server in a container can't replace its own programs, so `marfa update status` answers `manual`, and `marfa update start` refuses `409 update_unavailable` with the step.

- **A Docker install** the CLI set up moves with `marfa server upgrade --release <version>`. To go back after a refusal, set `MARFA_RELEASE` in `marfa.env` to the earlier release and run `marfa server start`.
- **A container you run yourself** moves when you create it again from the new release's image, on the same volume. [Check the image](/run/run-on-a-server#check-the-image) first.
- **On Railway**, back up the volume in Railway first, then change the image's tag on the service, which redeploys it. If the new release refuses the database, set the earlier tag again.

Keep a container on a release you name, never `latest`, so that a restart never changes the release under your data.

## Try a release beside your instance

To try a newer release without moving the one you use, make a second install in another folder, with its own port:

```bash
marfa server install --dir ~/marfa-next --port 8610
```

Your instance and its data stay as they are. To move your data across, [restore a backup](/run/back-up-and-restore#restore-the-copy) or [an archive](/run/export-and-restore#restore-an-archive) into it.

## When a build refuses the database

A build checks the database before it opens a port. **When it refuses one, it leaves the file as it found it,** opens no port, logs the reason with the file's path, and exits with status `78`:

- **`… is at schema version …, which a newer build wrote`.** An earlier build doesn't know what a later one changed. Run that build or a later one.
- **`… is not this build's: …`.** The database isn't in the shape its version declares, such as one changed by hand. The message gives the way forward: export with the build that wrote the file, start a new instance, and restore the archive there.

`marfa server run`, which every install starts, stays up without the server after a `78`, so nothing starts it again into the same refusal. `marfa server status` shows the reason, and so does `docker logs <name>`. **To go back,** run `marfa server stop`, install the release that wrote the database again, and run `marfa server start`.

**A build that changes the database** first copies it to `marfa.db.before-upgrade` beside it, replacing the copy from any earlier change. It refuses to start, and changes nothing, if the copy can't be written or would take the volume below `disk_reserve_bytes`. An update that fails partway leaves the database as it was.

## Types a new build leaves in conflict

A new build can give a built-in type a field that a type registered beneath it already declares in another shape. A task type whose parent is `core.task` may declare `recurrence` as text where `core.task` comes to give a list. **The type keeps working,** and its items stay readable.

[List types](/api-reference/types/listTypes) gives such a type's entry a `conflicts` list:

```json
{
  "id": "app.tasks.task",
  "parent": "core.task",
  "conflicts": [
    {
      "field": "recurrence",
      "attribute": "type",
      "inherited_from": "core.task",
      "inherited": "type \"array\"",
      "declared": "type \"string\""
    }
  ]
}
```

**Registering the type again as it stands is refused** `400 inheritance_violation`, so the app or connector that registers it fails until its definition gives the field the inherited shape. Update it, or [change the type](/build/change-a-type) yourself. Once the shapes agree, `conflicts` is left out.

The rules behind this page are in the [updates](https://github.com/withmarfa/marfa/blob/main/conformance/spec/updates.md) chapter of the contract, and the section on [a database this build did not write](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#a-database-this-build-did-not-write) in the instance chapter.
