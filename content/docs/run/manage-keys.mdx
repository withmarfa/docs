---
title: Manage keys
description: Give a script or service a key that reaches only what it needs, then narrow, expire, rotate or revoke it.
---

A key is the credential for a script or service you run yourself. It reaches only what it was made with: a photo import gets images and nothing else. An app that people sign in to asks the owner to [approve it](/run/manage-apps) instead. [Access](/build/access) explains the maps and permissions a key holds.

Make and change keys from any machine, with the CLI signed in with `marfa login` or a key that holds `keys.mint`. A key makes keys only within its own access.

## Make a key

This key reads and writes images and nothing else:

<Terminal>

```bash
marfa keys create --label "Photo import" --source photo-import --type-permission core.file.image=write
```

```text
marfa_k1_…
key <id> (Photo import); the plaintext is shown once, keep it now
  core.file.image  Read and edit
```

</Terminal>

<Callout type="warn" title="Copy the key now">The plaintext, which begins `marfa_k1_`, appears once. If you lose it, make a new key.</Callout>

The source is stamped on every item the key creates. **A source belongs to one live key:** a second key naming it is refused `409 conflict`, with `Another key holds the source photo-import as its own.` With the photo key, a bookmark is refused `403 type_not_permitted`. Through the API, [Create an API key](/reference/api/api-keys/createKey) takes the same fields.

These flags work on `keys create` and `keys update` unless noted:

| Flag | What it sets |
| --- | --- |
| `--label`, `--source` | What the key is for, and the source it writes as. Both are needed to create, and the source never changes. |
| `--type-permission <pattern=level>` | A type map entry, such as `core.file.image=write`. Levels are `read` and `write`, and `none` denies a type a wildcard covers. Repeat it. |
| `--edge-permission`, `--extension-permission`, `--metadata-permission`, `--profile-permission` | Entries in the other four maps, as `name=level`. Only `username=write` lets a key change the owner's username. |
| `--permission <name>` | One [permission](/catalog/permissions), such as `audit.read`. Repeat it. |
| `--claim <source>` | Another source the key may write as. |
| `--default-tier <tier>` | Where its items land when a write names none: `library` or `feed`. |
| `--enforcement-override <json>` | [Levers](/run/settings#what-the-enforcement-levers-do) for this key alone, looser or stricter than the instance's. Setting them needs `config.manage`. |
| `--expires-in <duration>`, `--expires-at <time>` | When it stops, as a number and `s`, `m`, `h`, `d` or `w`, such as `7d`, or as a time such as `2027-01-31T12:00:00Z`. |
| `--all-access`, `--no-permissions`, `--no-claims` | Every permission and every map at its widest, nothing at all, or no source besides its own. |
| `--no-type-permissions` and four like it, `--no-expiry` | Update only. Empty one map, or clear the expiry. |

## What a key holds

- **Naming any permission, map or claim gives exactly what it names.** The photo key holds one map and no permission.
- **Naming nothing takes everything its maker holds.** Through the private socket that's refused, since the machine's authority has no limit to take: name what the key holds, or pass `--all-access`.
- **A key hands on only what it holds.** Asking for more is refused `403 forbidden`, naming the first missing entry in `details.required_scope`.

## A key for a connector

**A connector needs an owner's key,** one that no change to an app's access ends, and stops before it registers with a key an app made. Run `marfa keys create` from any computer with the CLI signed in with Full access, which makes an owner's key. Each connector's [Catalog page](/catalog/connectors) gives the command for its key, and [Connect a service](/use/connect-a-service#make-its-key) walks through one.

Through the API, an app, or a key an app made, sends `"owner_key": true` to [Create an API key](/reference/api/api-keys/createKey), with `keys.manage`.

## Let keys share a source

A key writes under its own source and any source it claims. Keys that stand for one thing, such as a laptop and a phone, can each use `--claim photo-sync` and update each other's items. An item without a `source` takes the key's own.

A key can grant only its own source and its claims, unless it holds `keys.manage`, with `keys.mint` to make or widen a key: then it grants any source. No source may begin with `oauth:` or `restored:`, which name an app and restored history.

## Make a key expire

Add `--expires-in 7d` to `keys create`. **Once the time passes, the key is gone:** a request with it is refused `401 unauthorized`, with the time in `details.expired_at`, it leaves `marfa keys list`, and its source is free for a new key.

A key's life is held to its maker's:

- **A key that expires makes only keys that expire no later.** A key it makes ends when it does, or sooner, and a later expiry, or none, is refused `403 forbidden`.
- **A key holding `keys.manage` can only shorten an expiry**, like every other change it makes.
- **A key holding `keys.mint` lengthens an expiry** no later than its own, and the private socket lengthens or clears one with `--no-expiry`. Nobody lengthens the expiry of a key an app made.

## Narrow a key

`marfa keys current` shows what the key you're using holds, so a program can check it holds no more than it should. `marfa keys list` shows each key's access, who made it, its last use and when it ends.

Change a key in place by its ID. A map or permission list you name replaces that part, and the rest stay as they were. This makes the photo key read-only for 30 days:

<Terminal>

```bash
marfa keys update <id> --type-permission core.file.image=read --expires-in 30d
```

```text
<id>  Photo import  tier library  expires 2026-12-19T00:32:23.000Z
  source photo-import
  claims nothing besides its own source
  made by the app <app id>
  created 2026-11-19T00:32:23.785Z  never used
  core.file.image  Read only
```

</Terminal>

Who can change which key:

- **`keys.manage`** reaches every key. Alone it only takes access away, and a widening is refused `403 forbidden`, saying the key doesn't hold what the change adds.
- **`keys.mint`** gives a key more, within the caller's own access and expiry. Without `keys.manage`, it reaches only the keys that hold nothing it doesn't, and any other ID answers `404 key_not_found`.
- **The private socket** reaches every key and can change anything.

A key an app made can only be narrowed. The CLI signed in with Full access holds both permissions.

`PATCH /keys/{id}` takes `"narrow_only": true`, which refuses `403 forbidden` any change that would give the key more, whoever sends it. Send it with a change based on an earlier read.

## Rotate a key

Replace a key when its holder changes.

<Callout type="warn" title="If a key may have leaked, revoke it first">Then make a new one. Keys it made keep working, so if it held `keys.mint`, find them in the [audit log](/use/audit-log) and revoke them too. The steps below are for a planned change and keep the old key working until the new one is in place.</Callout>

1. Make a key with the same access and a new `--source`, and give it to the script.
2. Check that the new key works. Later, `marfa keys list` should show the old key's last use before the switch.
3. Revoke the old key.

A new source starts new items. The old key's items keep its source, and an upsert by `source_id` looks only under the new one, adding a second copy. To keep the source, revoke the old key first, or the new key is refused `409 conflict`.

## Revoke a key

Revoking ends a key at once: its next request is refused `401 unauthorized`.

<Terminal>

```bash
marfa keys revoke <id>
```

```text
revoked key <id>
```

</Terminal>

[See and cut access](/use/see-and-cut-access) shows everything that can reach the instance, keys and apps together.

## Give a key to a folder watch

A folder watch that starts at login reads its key from the keychain. On a machine where nobody signs in to unlock the keychain, give it a key file instead: a file that holds two lines, which only you can read.

```bash title="marfa-watch.env"
MARFA_API_URL=https://marfa.example.com
MARFA_API_KEY=marfa_k1_…
```

```bash
chmod 600 ~/.config/marfa-watch.env
marfa folders autostart on --key-file ~/.config/marfa-watch.env
```

**Keep the file outside every folder you sync,** so the key is never synced as one of your files. Make the key reach only the types the folders carry. The watch uses the file for the folders of that server, and a folder of another server is reported as having no credential.

## Give a key to a script or agent

On your own machine, `marfa keys keep` checks a key with the server and keeps it in the keychain. In a script, a CI job or an agent, set `MARFA_NO_KEYCHAIN=1` and pass the key in `MARFA_API_KEY` from a secrets manager, with the server in `MARFA_API_URL`. [The CLI reference](/reference/cli) has every way to name a server and a key.
