---
title: Manage keys
description: Give a script or service a key that reaches only what it needs, then narrow, expire, rotate or revoke it.
---

A key is the credential for a script or service you run yourself. It reaches only what it was made with: a notes app gets notes and nothing else. An app that people sign in to asks the owner to [approve it](/run/manage-apps) instead, though it may also hold a key. [Access](/access) explains the maps and permissions a key holds.

The owner makes keys in a browser or through the [private socket](/run/deploy#the-private-socket), and a key holding `keys.mint` makes keys within its own access. The examples use the socket, on the instance's machine as the account that runs the server.

## Use the API keys page

Open **API keys** from [Home](/run/sign-in-as-the-owner#start-from-home) and choose **Create key**. **Details** holds the name and when the key ends. **Access starts with everything off**, so turn on only what the key needs. **Advanced** holds its sources and where its items land.

<Callout type="warn" title="Copy the key now">Marfa shows it once, under **Copy your key**. If you lose it, make a new one.</Callout>

A saved key can only get less access or an earlier end. **Creating a key, saving a change to it and revoking it need a sign-in from the last five minutes**: the page asks the owner to [confirm it's them](/run/sign-in-as-the-owner#confirm-its-you) when theirs is older. The socket, and a key with the permission for the operation, aren't held to it.

## Make a key

This key reads and writes notes and nothing else:

<Terminal>

```bash
marfa --socket /srv/marfa/data/control/marfa.sock keys create \
  --label "Notes app" --source notes-app --type-permission core.note=write
```

```text
marfa_k1_…
key 01a15f23-d3a8-7ccd-8fb6-0d50f3c6ce4a (Notes app); the plaintext is shown once, keep it now
  core.note  Read and edit
```

</Terminal>

The plaintext, which begins `marfa_k1_`, appears **once**. Through the API, [Create an API key](/api-reference/api-keys/createKey) takes the same fields.

The source is stamped on every item the key creates. A source belongs to one live key: a second key naming it is refused `409 conflict`. With the notes key, a bookmark is refused `403 type_not_permitted`.

These flags work on `keys create` and `keys update` unless noted.

| Flag | What it sets |
| --- | --- |
| `--label`, `--source` | What the key is for, and the source it writes as. Both are required to create, and the source never changes. |
| `--type-permission <pattern=level>` | A type map entry, such as `core.note=write`. Levels are `read` and `write`, and `none` denies a type a wildcard covers. Repeat it. |
| `--edge-permission`, `--extension-permission`, `--metadata-permission`, `--profile-permission` | Entries in the other four maps, as `name=level`. `email` is `read` only. |
| `--permission <name>` | One [permission](/catalog/permissions), such as `audit.read`. |
| `--claim <source>` | Another source the key may write as. |
| `--default-tier <tier>`, `--enforcement-override <json>` | Where its items land when a write names none (`library` or `feed`), and [levers](/run/settings#what-the-enforcement-levers-do) for this key alone, looser or stricter than the instance's. Levers need `config.manage`. |
| `--expires-in <duration>`, `--expires-at <time>` | When it stops, as a number and `s`, `m`, `h`, `d` or `w` such as `7d`, or as a time such as `2027-01-31T12:00:00Z`. Use one, not both. |
| `--no-permissions` | Hold nothing: no permission and no map. |
| `--no-claims` | Claim no source besides its own. |
| `--no-type-permissions` and four like it | Update only. Empty one map. |
| `--no-expiry` | Update only. Clear the expiry. |

## What a key holds

What a new key holds depends on what the request names:

- **Naming nothing takes everything its maker could give.** For the owner, that is every permission and `write` on all five maps.
- **Naming any permission, map or claim gives exactly what it names.** The notes key holds one map and no permission.
- **A key hands on only what it holds.** Asking for more is refused `403 forbidden`, with the first missing entry in `details.required_scope`.

## Let keys share a source

A key writes under its own source and any source it claims. Keys that stand for one thing, such as a laptop and a phone, can each use `--claim notes-sync` and update each other's items. An item without a `source` takes the key's own.

The owner can grant any claim except one beginning with `oauth:` or `restored:`. A key holding `keys.mint` can grant only its own source and its claims.

## Make a key expire

Add `--expires-in 7d` to `keys create`, or `"expires_at"` to `POST /keys`. **Once the time passes, the key is gone.** Requests with it are refused `401 unauthorized`, and it leaves the key list. Its source is free for a new key.

A key's life is held to its maker's:

- **A key that expires passes its expiry on.** A key it makes ends when it does, or sooner. A later expiry, or none, is refused `403 forbidden`.
- **A key holding `keys.manage` can only shorten an expiry**, like every other change it makes.
- **Only the owner, or a key with no expiry holding `keys.mint`, lengthens or clears one**, with `--no-expiry` or `"expires_at": null`. Nobody does that for a key an app made.

## Narrow a key

Any key can read itself with `marfa keys current`, or `GET /keys/current`, so a program can check it holds no more than it should. `marfa overview` shows the types, views and folders that access reaches. `marfa keys list` shows each key's access, its last use (recorded at most hourly) and when it ends.

Change a key in place by its ID. A map or permission list you name replaces what the key held in that part, and the parts you leave out stay as they were. This makes the notes key read-only for 30 days:

```bash
marfa --socket /srv/marfa/data/control/marfa.sock keys update 01a15f23-d3a8-7ccd-8fb6-0d50f3c6ce4a \
  --type-permission core.note=read --expires-in 30d
```

The same change is `PATCH /keys/{id}`. Who can change which key:

- **The owner** reaches every key and can change anything, but a key an app made can only narrow.
- **A key holding `keys.manage`** reaches every key and can only take access away.
- **A key holding `keys.mint`** reaches keys that hold nothing it doesn't. Any other ID answers `404 api_key_not_found`.

An update can say it must only narrow. Add `"narrow_only": true` to `PATCH /keys/{id}`, and Marfa refuses `403 forbidden` any change that gives the key more, whoever sends it. The **API keys** page sends it with every save.

## Rotate a key

Replace a key when its holder changes.

<Callout type="warn" title="If a key may have leaked, revoke it first">Then make a new one. Keys it made keep working, so if it held `keys.mint`, find them in the [audit log](/run/audit-log) and revoke them too. The steps below are for a planned change and keep the old key working until the new one is in place.</Callout>

1. Make a key with the same access and a new `--source`, and give it to the app.
2. Check that the new key works. An hour later, `marfa keys list` should show the old key's last use before the switch.
3. Revoke the old key.

A new source starts new items. The old key's items keep its source, and an upsert by `source_id` looks only under the new one, adding a second copy. To keep the source, revoke the old key first, or the new key is refused `409 conflict`.

## Revoke a key

Revoking ends a key at once: its next request is refused `401 unauthorized`.

```bash
marfa --socket /srv/marfa/data/control/marfa.sock keys revoke 01a15f23-d3a8-7ccd-8fb6-0d50f3c6ce4a
```

## Give a key to a script or agent

On your own machine, `marfa keys keep` checks a key with the server and keeps it in the keychain. In a script, a CI job or an agent, set `MARFA_NO_KEYCHAIN=1` and take the key from a secrets manager, through a profile's `key_command` or by running the CLI under the manager. [Name a server with a profile](/cli#name-a-server-with-a-profile) shows the first, and [Run without the keychain](/cli#run-without-the-keychain) the second.

The rules behind this page are in the [keys and sign-in](https://github.com/withmarfa/marfa/blob/main/conformance/spec/keys-and-oauth.md) chapter of the contract.
