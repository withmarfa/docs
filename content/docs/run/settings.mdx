title: Settings
description: Set an instance's startup environment and change its name, data rules and operating policies while it runs.
---

An instance has two places for settings. The **environment** is read once, when the server starts, and covers everything from where the database lives to how often each housekeeping job runs. The **configuration** at `/config` changes while the server runs: the instance name, three enforcement levers, retention windows, version policy, unused-app retirement, file extraction and reporting switches. Addresses and credentials stay in the environment.

## Set an environment setting

Set the setting as an environment variable of the server process, then start it. To change one, restart it:

```bash
export TRASH_RETENTION_DAYS=30
node dist/index.js
```

In the container, change its environment file and create the container again with `docker run`: **a restart keeps the environment the container was created with**. A blank value counts as unset.

If any setting is outside its allowed values, the server opens no port and creates no file. It logs one error line and exits with status `1`. The line's `error` field names every wrong setting at once, with the value it was given:

```text
The server cannot start; fix these settings:
  PORT must be a whole number, from 0 to 65535 (got "99999")
  MARFA_AUTH_SECRET must be at least 32 characters; generate one with `openssl rand -hex 32`
  TRASH_RETENTION_DAYS must be a whole number, from 0 to 36500 (got "forever")
```

A secret, or an address that can carry one such as `S3_ENDPOINT`, is named but never printed.

## The settings to check first

Most defaults suit any instance. Check these first:

| Setting | Check it when | Read more |
| --- | --- | --- |
| `NODE_ENV` | Always. `production` refuses a start without `API_KEY_SALT`, `MARFA_AUTH_SECRET` and `MARFA_AUTH_BASE_URL`. | [Deploy](/run/deploy#run-it-without-a-container) |
| `SQLITE_PATH`, `BLOB_PATH` | Always. They say where your data lives. | [Back up and restore](/run/back-up-and-restore) |
| `TRUSTED_PROXY_CIDRS`, `TRUSTED_PROXY_HEADER` | A proxy or tunnel sits in front of the server. | [Deploy](/run/deploy#the-address) |
| `S3_PREFIX` | Instances share a bucket. Each needs its own. | [Deploy](/run/deploy#an-object-store) |
| `MARFA_WEBHOOK_ALLOW_PRIVATE_ADDRESSES` | A webhook receiver is on a Tailscale or home network. | [Let webhooks reach a private network](#let-webhooks-reach-a-private-network) |
| `OTEL_RESOURCE_ATTRIBUTES`, `OTEL_SERVICE_NAME` | You run more than one instance and send telemetry. | [Send telemetry](/run/telemetry#tell-instances-apart) |
| `CORS_ORIGINS` | A web page on another origin calls the API. | [Connect a web page](/build/connect-a-web-page) |
| `PORT`, `MARFA_LISTEN_HOST` | The default port `8600` or address doesn't suit. `0` lets the operating system assign a port. | |

The container's entrypoint reads one more name, `MARFA_REPLACE_NEWER_REPLICA`, which the server doesn't read and the list below leaves out. Set it to `true` for one start to replicate a database that may be older than the bucket's copy. [With a bucket](/run/back-up-and-restore#with-a-bucket) says when to use it.

## Let webhooks reach a private network

Marfa posts webhooks only to public addresses. A `url` whose host is a loopback, private, link-local, unique-local or carrier-grade NAT address (`100.64.0.0/10`, which Tailscale uses) is refused `400 validation_error`, when the webhook is registered and when its `url` changes. A name counts too: Marfa looks it up and refuses it when any address it resolves to isn't public.

To reach a receiver on a Tailscale or home network, set `MARFA_WEBHOOK_ALLOW_PRIVATE_ADDRESSES=true` and restart the server. To try a receiver on your own machine, do that on a development instance and register `http://localhost:3000/marfa`. **Leave it off** on any other instance.

Marfa accepts a name that doesn't resolve or answer in time, and checks it again at each delivery. [Receive webhooks](/build/receive-webhooks#receive-deliveries-on-a-private-network) shows what a delivery to a non-public address records.

## Change settings while it runs

The configuration at `/config` **takes effect at once, with no restart**. Reading, replacing or updating it needs the `config.manage` permission; the owner, signed in or through the private socket, needs no key. [Read the configuration](/api-reference/instance/getConfig) lists every field and its type. A field you have not set is left out of the answer.

**A cleanup retention of `0` keeps those records with no age limit.** A zero version window is empty, and zero `grant_inactivity_days` disables retirement. A setting you leave unset takes its environment value. Version windows must not decrease from recent to daily to weekly; a type-specific version policy still takes precedence.

The owner can change the name, retention and version windows, unused-app retirement, file extraction and reporting switches on the **General** page, at `/auth/owner/general`. It sends only the settings you changed. Use the configuration API or CLI for the enforcement levers. A change applies to work that starts after it: switching something off doesn't cancel work already in flight. A reporting switch needs its receiver configured in the environment.

A new name takes effect on the next request. Marfa trims the name, and refuses an empty one, one over 200 Unicode code points, or one with a control or bidirectional formatting character.

An instance that has set nothing answers its `instance_id` alone. Over HTTP, send `GET /config`.

### Replace the configuration

**A replace sets the whole configuration: a field you leave out goes back to its default.** Read the configuration first, change what you need, and send all of it back. This names the instance Library, keeps the bin for 30 days and makes `core.note` refuse a property it doesn't declare:

```bash tab="CLI" tab-group="client"
marfa config replace --body '{"name": "Library", "enforcement": {"strict_mode": {"types": ["core.note"]}}, "trash_retention_days": 30}'
```

```http tab="HTTP"
PUT /config
Authorization: Bearer <key>
Content-Type: application/json

{
  "name": "Library",
  "enforcement": { "strict_mode": { "types": ["core.note"] } },
  "trash_retention_days": 30
}
```

The answer is the configuration as it now stands. `--file config.json` reads the body from a file, and `--file -` from standard input. **Sending `{}` clears every field.** A body with an unknown field, an invalid name or a retention out of range is refused, and the configuration stays as it was. [Replace the configuration](/api-reference/instance/replaceConfig) has every refusal.

### Update the configuration

**An update changes only the settings it names.** A setting in the body is replaced, a setting set to `null` is removed so that its default applies, and every other setting stays as it was. Two callers who each change one setting don't undo each other, as they can with a replace. This keeps the bin for 30 days and puts the name back to `Marfa`:

```bash tab="CLI" tab-group="client"
marfa config update --body '{"trash_retention_days": 30, "name": null}'
```

```http tab="HTTP"
PATCH /config
Authorization: Bearer <key>
Content-Type: application/json

{
  "trash_retention_days": 30,
  "name": null
}
```

`enforcement` is one setting: an update that names it replaces all three levers, and `null` removes them all. [Update the configuration](/api-reference/instance/updateConfig) has every refusal.

The server records each accepted replace or update in the [audit log](/run/audit-log) as `config.update`.

## What the enforcement levers do

A lever holds chosen types to a stricter rule. Each names `types`, and `source_allowlist` and `source_filter` also name `sources`.

| Lever | What it does | What the caller meets |
| --- | --- | --- |
| `strict_mode` | Refuses a write that names a property neither the item's type nor an ancestor declares. Without it, Marfa keeps an undeclared property and serves it back. | `400 invalid_properties`, with `details.code` set to `unknown_property`. |
| `source_allowlist` | Lets only the listed sources create items of a type. Use it when one app should own a type, such as a notes app that alone writes notes. | `403 forbidden`, with `details.type`, `details.source` and `details.allowed`. |
| `source_filter` | Leaves out of every read that returns a set, such as listings, searches, counts and exports, an item of a type whose source isn't listed. Event streams and webhook deliveries leave it out too. | Nothing: the item isn't there. |

`strict_mode` and `source_allowlist` hold for exactly the types they list, **not the types that inherit from them**, so list each type you mean. `source_filter` also covers the types under a listed type.

**Reading an item by its ID isn't filtered.** An item with no source counts as one whose source is `unknown`.

A key can carry levers of its own in `enforcement_override`. A lever it names replaces the instance's for that key, looser or stricter. Setting one needs `config.manage`, or the owner's own authority. A key made by another key doesn't take its maker's levers: unless it names its own, it follows the instance's. [Manage keys](/run/manage-keys) shows the `--enforcement-override` flag.
