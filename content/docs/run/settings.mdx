title: Change an instance's settings
description: Change an instance's name, limits and policies while it runs, and set what the server reads when it starts.

An instance has two kinds of settings. **Stored settings** live in the database and change while the server runs, from any machine with a key that holds `config.manage`: the name, the addresses, backups, retention, limits and reporting. **Start-only settings** are environment variables the server reads once, when it starts: where the data lives, the port, the proxy, the two secrets and telemetry.

## Change settings while it runs

A stored setting **takes effect at once, with no restart**. Change one by name, and return it to its default with `unset`:

<Terminal>

```bash
marfa config set trash_retention_days 30
```

```text
set trash_retention_days
```

</Terminal>

`config set` sends the value as the setting's own kind: a number, `true` or `false`, a comma-separated list or text. It refuses a value of the wrong kind before it sends anything, and **asks for a secret setting with no echo**, or reads it from standard input, never as an argument. `marfa config settings` lists every stored setting with its value and whether it's stored or the default, and names every start-only setting without its value.

To change several at once, send a body. **An update changes only the settings it names,** and `null` returns one to its default:

```bash tab="CLI" tab-group="client"
marfa config update --body '{"trash_retention_days": 30, "name": "Family archive"}'
```

```http tab="HTTP"
PATCH /config
Authorization: Bearer <key>
Content-Type: application/json

{
  "trash_retention_days": 30,
  "name": "Family archive"
}
```

`marfa config replace` (`PUT /config`) sets the whole configuration instead: **a setting you leave out returns to its default**, so read it with `marfa config get` first. A body with an unknown field or a value outside its rule is refused, and nothing changes. [Update the configuration](/api-reference/instance/updateConfig) has every refusal, and the server records each change in the [audit log](/use/audit-log) as `config.update`.

Two changes need [a sign-in from the last five minutes](/run/sign-in-as-the-owner#confirm-its-you), from the CLI signed in with `marfa login` rather than a key: moving `sign_in_address`, which [Give your instance an address](/run/address#move-the-address) covers, and changing `allow_private_addresses`.

A change applies to work that starts after it: switching something off doesn't stop work already under way. A reporting switch needs its receiver set too.

## What the enforcement levers do

`enforcement` holds the levers, which hold chosen types to a stricter rule. Each names `types`, and `source_allowlist` and `source_filter` also name `sources`:

```bash
marfa config update --body '{"enforcement": {"strict_mode": {"types": ["core.note"]}}}'
```

| Lever | What it does | What the caller meets |
| --- | --- | --- |
| `strict_mode` | Refuses a write that names a property neither the item's type nor an ancestor declares. Without it, Marfa keeps an undeclared property and serves it back. | `400 invalid_properties`, with `details.code` set to `unknown_property`. |
| `source_allowlist` | Lets only the listed sources create items of a type, such as one app that alone writes a type. | `403 forbidden`, with `details.type`, `details.source` and `details.allowed`. |
| `source_filter` | Leaves an item of a type whose source isn't listed out of listings, searches, exports, event streams and webhook deliveries. | Nothing: the item isn't there. |

`strict_mode` and `source_allowlist` hold for exactly the types they list, **not the types that inherit from them**, so list each type you mean. `source_filter` also covers the types under a listed type. **Reading an item by its ID isn't filtered.** An item with no source counts as one whose source is `unknown`.

`enforcement` is one setting: an update that names it replaces all three levers, and `null` removes them all. A key can carry levers of its own in `enforcement_override`, each replacing the instance's for that key, looser or stricter. [Manage keys](/run/manage-keys) shows the `--enforcement-override` flag.

## Let webhooks reach a private network

Marfa sends only to public addresses: webhooks, `heartbeat_url`, `error_webhook_url` and `object_store_endpoint`. A loopback, private, link-local, unique-local or carrier-grade NAT address (`100.64.0.0/10`, which Tailscale uses) is refused `400 validation_error`, and so is a name that resolves to one.

To reach a receiver or an object store on a Tailscale or home network, turn on `allow_private_addresses`. It needs a recent sign-in:

```bash
marfa login --fresh-sign-in
marfa config set allow_private_addresses true
```

**Leave it off** unless something you run needs it: it lets anyone who can register a webhook make the server send to your own network. [Receive webhooks](/build/receive-webhooks) shows what a delivery to a non-public address records.

## Set an environment setting

On a machine you [installed with one command](/run/install), add the setting to `marfa.env` in the install folder and run `marfa server restart`. The folder sets the port, the listening address and the paths itself, and the command refuses a `marfa.env` that sets them.

In a container you run yourself, change its environment file and **create the container again**: a restart keeps the environment the container was created with. On Railway, change the service's variables, which redeploys it. A blank value counts as unset.

If any setting is outside its rule, the server opens no port and makes no file. It logs one line naming every wrong setting at once, and exits with status `1`:

```text
The server cannot start; fix these settings:
  MARFA_PORT must be a whole number, from 0 to 65535 (got "99999")
  MARFA_AUTH_SECRET must be at least 32 characters; generate one with `openssl rand -hex 32`
```

A secret is named but never printed. A `MARFA_` name the server doesn't read only warns, and names the setting you may have meant, or says that it's a stored setting to set with `marfa config set`.

## Every environment setting

Most instances set none of these by hand: the install, the image and the Railway template set the ones they need. **Never set the `MARFA_TEST_` settings on an instance that holds real data:** they're for the conformance harness, and a server built without test hooks refuses to start with `MARFA_TEST_HOOKS` on.
