---
title: Install with the CLI
description: Take a Mac or Linux machine with Docker to an instance ready to claim, with one command.
---

`marfa server install` makes the secrets, sets the proxy setting for the way you reach the instance, starts **the release that matches your CLI** and prints **the link that claims the instance**. You need [the CLI](/cli#install) and Docker with Compose: Docker Desktop or OrbStack on a Mac, Docker Engine on Linux.

<Step>

### Run the install

The command asks how your devices reach the instance, whether to keep a copy of the data in a bucket and, on a Mac, whether to start the instance when you log in. Each question has a flag. With `--yes`, or when a script runs the command, it asks nothing and uses the flags or the defaults.

### Claim the instance

Open the link in a browser and choose the owner's email and password. **Keep a copy of `marfa.env` outside the folder.** It holds the two secrets, and a server started on the data without them refuses every key. Run the command again for a new link until the instance has an owner.

## Choose how it's reached

The way you reach the instance decides which caller address the server believes, so the command asks, and sets [the address](/run/deploy#the-address) and the proxy setting to match.

| `--access` | Reached | Address | Proxy setting |
| --- | --- | --- | --- |
| `local` | Only from this machine. | `http://localhost` and the port. | None. |
| `tailscale` | From your tailnet, through Tailscale Serve. | This machine's `ts.net` name, served with `tailscale serve` on port 443 unless you pass `--https-port`. The tailnet needs MagicDNS and HTTPS certificates. | `TRUSTED_PROXY_CIDRS` set to the range of the instance's Docker network. |
| `cloudflare` | Through a Cloudflare Tunnel on this machine. | The `https` address you give with `--address`. | `TRUSTED_PROXY_HEADER` set to `CF-Connecting-IP`. |
| `proxy` | Through another proxy on this machine, such as Caddy or nginx. | The `https` address you give with `--address`. | `TRUSTED_PROXY_CIDRS` set to the range of the instance's Docker network. |

The instance gets a Docker network of its own, named for the install (`marfa-net` unless you pass `--name`), and the command reads its range from Docker. The network is made once and kept when the container is replaced, so the range stays the one the setting names. The port is 8600, or the next free one, unless you pass `--port`. It is published on the loopback address only, so only a proxy or tunnel on the same machine reaches it.

**For `cloudflare` and `proxy`, point the tunnel or proxy at `http://localhost:` and the port, on the machine that holds the folder.** The command says so when it asks for the address, and its summary repeats it as **Point at**, with the machine's name beside the folder. A tunnel aimed at another port, or running on another machine, makes the address answer `502`.

## What the command writes

The command keeps everything in one folder, `marfa-server` in your home directory unless you pass `--dir`:

<Files>
  <Folder name="marfa-server" defaultOpen>
    <File name="compose.yaml" />
    <File name=".env" />
    <File name="marfa.env" />
  </Folder>
</Files>

- **`compose.yaml`** is the same for every install. It runs the release image with `restart: unless-stopped` and one volume.
- **`.env`** holds what Docker Compose reads and what the command remembers between runs: the install's name, the release, the port, how you reach the instance and whether it starts at login. It holds no secret.
- **`marfa.env`** holds the server's [settings](/run/settings), including the two secrets. Only you can read it. The command makes the secrets once and keeps them on every later run. If the data volume exists and `marfa.env` doesn't, it stops, because new secrets would make every key stop working.

The folder works without the CLI: `docker network create marfa-net` once, then `docker compose up -d` in the folder.

## Change, upgrade or remove it

Run `marfa server install` again with a flag to change a setting, such as `--access` or `--address`. It changes only what isn't already as asked. The other commands take the same `--dir`.

| Command | What it does |
| --- | --- |
| `marfa server status` | Shows whether the container runs and answers, the release, the address and whether the instance has an owner. |
| `marfa server upgrade` | Moves to the release of your CLI, or to `--release`. A release with a newer schema copies the database beside it and updates it in place, and the command prints where the copy is. It refuses an older release than the one installed, which doesn't know what a newer one changed in the database. See [Upgrade](/run/upgrade). |
| `marfa server start` | Starts Docker's engine on a Mac if it's down, then the container. |
| `marfa server uninstall` | Removes the container and keeps the data. `--delete-data` removes the volume, the network and the settings too, after you type the install's name (`--yes` skips the question). |

## Start at login or boot

The restart policy brings the container back whenever Docker's engine starts. **On Linux, `sudo systemctl enable docker` makes the engine start at boot.** On a Mac, the command writes a launchd agent, `so.marfa.server.marfa`, that runs `marfa server start` when you log in. It opens OrbStack or Docker Desktop first if the engine is down, and tries again after a failure. `--no-autostart` skips it.

## Keep the settings elsewhere

If a secrets manager writes `marfa.env`, pass `--external-settings`. The command then never makes or changes the file. It checks that the file holds both secrets, an address the server accepts and a proxy setting that fits the way you reach the instance, and names what's missing without printing a value. It reads a quoted value, such as the `'https://marfa.example.com'` a secrets renderer writes, the way Docker Compose reads it. Run the command again after the file changes: Docker Compose replaces the container when the file's content changes.

## Keep a copy in a bucket

Answer yes to the bucket question, or pass `--s3-bucket` and `--s3-access-key-id`. The secret key comes from `S3_SECRET_ACCESS_KEY` in the environment or a hidden prompt, never from an option. The command writes the [`S3_` settings](/run/deploy#an-object-store), with the install's name as `S3_PREFIX` unless you pass `--s3-prefix`.
