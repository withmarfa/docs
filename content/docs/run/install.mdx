---
title: Install on a Mac or Linux machine
description: Run Marfa as a service of your own Mac or Linux machine with one command, then claim it in the browser.
---

`marfa server install` sets up the server as a service of the machine it runs on: a launchd agent on a Mac, and a systemd service on Linux. It makes the server's two secrets, sets how devices reach it, starts it, and prints **a link that claims the instance**. You need a Mac with Apple silicon, or a Linux machine on x86_64 or arm64.

<Steps>
<Step>

### Install the programs

Marfa is two programs of the same release, side by side: `marfa`, the CLI, and `marfa-server`. Install both with Homebrew:

```bash
brew install withmarfa/tap/marfa
```

Or with the install script, which puts both in `~/.local/bin`:

```bash
curl -fsSL https://raw.githubusercontent.com/withmarfa/marfa/main/scripts/install.sh | sh
```

[The CLI's install](/reference/cli#install) gives the script's options and shows how to check a download. `marfa` uses only the `marfa-server` beside it, never one elsewhere on your `PATH`.

</Step>
<Step>

### Run the install

Run the command as the person who uses the server, not with `sudo`. It asks how your devices reach the server. Choose `local` to start on this machine alone; [Give your instance an address](/run/address) explains the other choices, and you can change it later.

<Terminal>

```bash
marfa server install
```

```text

  http://localhost:8600/setup#handoff=…
```

</Terminal>

The command shows each command that changes something as it runs, and never prints a secret. It ends by saying that **the server keeps no backups yet**: [Back up and restore](/run/back-up-and-restore#turn-on-backups) sets them up. If the server doesn't start, `marfa server status` shows the end of its log, and [Fix a server that won't start](/run/troubleshooting/start-and-claim) explains each message.

</Step>
<Step>

### Claim the instance

Open the link and choose the owner's username and password. The link works once, for five minutes; run `marfa server install` again for a new one until the instance has an owner. [Sign in as the owner](/run/sign-in-as-the-owner) covers passkeys and what to do after.

</Step>
<Step>

### Keep a copy of the secrets

Copy `marfa.env` from the install folder to a password manager or another safe place. The file is stored nowhere else, and you need it to bring the instance back from [a copy of its data directory](/run/restore-the-data-directory). **With another `MARFA_KEY_SALT`, the server starts but refuses every key and access token,** and you sign in as the owner again to make new ones. A restore from a backup needs neither secret.

</Step>
</Steps>

## What the command writes

The install lives in one folder: `marfa-server` in your home directory, or the folder you name with `--dir`. The folder's path, followed by `/data/control/marfa.sock`, must be 100 characters or fewer.

<Files>
  <Folder name="marfa-server" defaultOpen>
    <File name="marfa.env" />
    <File name=".env" />
    <Folder name="data" defaultOpen>
      <File name="marfa.db" />
      <Folder name="blobs" />
      <Folder name="control" />
      <File name="marfa.settings.key" />
    </Folder>
  </Folder>
</Files>

| Path | What it holds |
| --- | --- |
| `marfa.env` | The server's [start-only settings](/run/settings#set-an-environment-setting), including its two secrets, `MARFA_KEY_SALT` and `MARFA_AUTH_SECRET`. Only you can read it. |
| `.env` | What the `marfa server` commands record about the install: its name, release, port and how it's reached. The server doesn't read it. |
| `data/marfa.db` | The database. |
| `data/blobs/` | The bytes of your files. |
| `data/control/marfa.sock` | [The private socket](/run/run-on-a-server#the-private-socket), for claiming the instance and recovering the owner's password. |
| `data/marfa.settings.key` | The key that seals secret settings, such as an object store's secret key. Without it the server starts and asks you to set those settings again. |

The folder decides the port, the address the server listens on (`127.0.0.1`) and the paths of the data and the socket, so the command refuses a `marfa.env` that sets any of them.

## Where the service runs

- **On a Mac,** the service is a launchd agent named `so.marfa.server.<name>`, which starts when you log in and again after a failure. Its log is `~/Library/Logs/Marfa/<name>.log`.
- **On Linux,** it's a systemd user service named `marfa-<name>.service`, and the command turns on lingering for your account so the service starts at boot. Its log is in the journal: `journalctl --user -u marfa-marfa.service`.
- **As root on Linux,** the command installs a system service that runs under a `marfa` account it makes, with the install in `/var/lib/marfa-server`. The programs must be where every account can run them, such as `/usr/local/bin`.

`--name` names the install, which lets one machine run more than one, each in its own folder and on its own port. `--no-autostart` leaves the service off at login or boot, for `marfa server start` to start.

## Change, upgrade or remove it

Run `marfa server install` again with a flag to change what it set, such as `--access`, `--address` or `--port`. It changes only what isn't already as you asked, and **never a secret or the runtime**. Every command below takes the same `--dir`.

| Command | What it does |
| --- | --- |
| `marfa server status` | Whether the server runs and answers, its release and address, and whether it has an owner. When it isn't answering, the end of its log. |
| `marfa server stop` | Stops the server, and keeps the service, the data and the settings. |
| `marfa server start` | Starts it again, on the programs beside the `marfa` you run it with, so run it with the install's own `marfa`. |
| `marfa server restart` | Stops and starts it, so it reads `marfa.env` again after you change a setting there. |
| `marfa server upgrade` | Moves the install to the release of the programs installed beside `marfa`. Read [Upgrade an instance](/run/upgrade) first. |
| `marfa server uninstall` | Removes the service, and keeps the data and the settings, so `marfa server install` brings the same instance back. `--delete-data` also removes the data and `marfa.env`, after you type the install's name. |

## Run it in Docker

`marfa server install --docker` runs the release image `ghcr.io/withmarfa/marfa-server` with Docker Compose instead, for the same release as your `marfa` unless you name one with `--release`. You need Docker with Compose: Docker Desktop or OrbStack on a Mac, Docker Engine on Linux, reached without `sudo`.

The folder then holds a `compose.yaml`, and the data lives in the Docker volume `<name>-data`. The container publishes its port on `127.0.0.1` only. **An install keeps its runtime:** to move between Docker and a service, make a second install with its own `--name`, `--dir` and `--port`, and restore your data into it, as [Move to a newer release](/run/upgrade#move-to-a-newer-release) shows.

## Keep the settings elsewhere

If a secrets manager writes `marfa.env`, pass `--external-settings`. The command then never makes or changes the file. It checks that the file holds both secrets and a proxy setting that fits how the server is reached, and names what's missing without printing a value. Run the command again after the file changes.
