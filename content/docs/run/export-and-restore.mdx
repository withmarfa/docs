An archive is one file that carries your data to another instance: items with their history, the bin included, links, tables, your types and plugins, which app holds each app's types, the settings you chose, your connectors' settings and mappings, and your files' bytes. It carries **no key, app, sign-in, connector host, webhook, audit log or secret,** so it opens nothing on its own. Use an archive to keep a copy of your own or to move to an instance that shares no backup place; for everyday protection, [let the server back itself up](/run/back-up-and-restore).

## Export an archive

An archive holds what its credential can read. With the CLI signed in as the owner, that is everything:

<Terminal>

```bash
marfa export --output family-archive.tar
```

```text
9728 byte(s) of application/x-tar into family-archive.tar
```

</Terminal>

The CLI writes the path only once the export ended, so **an archive cut short never passes for a whole one.** `--type`, `--state`, `--source`, `--occurred-after` and `--occurred-before` narrow it.

The server writes temporary files on its data volume first: an export that would take it below `disk_reserve_bytes` is refused `507 insufficient_storage`.

## When an archive lacks a file

An archive leaves out the bytes of a file no store holds whole, or that the key may not read, such as one only an earlier version names without `blobs.manage`. With `--output`, the CLI keeps the archive as `<path>.incomplete`, writes nothing to the path and exits `1`:

```text
marfa: the archive lacks 1 blob(s), which its files.ndjson.gz marks not_carried or lost: sha256:4376bb202f0af45b74b0577fd04bec82e5296f2b6a69de80c09bcf74ac403115; it holds everything else it names, so it is kept at family-archive.tar.incomplete, and nothing was written to family-archive.tar, so nothing there lacks files
```

Export again with `blobs.manage`, or upload a lost file again with `marfa blobs upload <file>`.

## Restore an archive

A restore writes into whichever instance the CLI reaches, so **check that `marfa status` names the one you mean.** It needs `backups.manage` and [a sign-in from the last fifteen minutes](/run/sign-in-as-the-owner#confirm-its-you), or the private socket on the instance's own computer:

```bash
marfa login --url <address> --fresh-sign-in
marfa restore family-archive.tar
```

**A restore reads an archive from its own release or an earlier one, back to 0.0.72.** To move to a release that can't open your database, export while the old release runs and restore into a new install ([Upgrade an instance](/run/upgrade)). A restore is one write: one that is refused or fails, or that a stopping server cuts short, leaves nothing behind, so run it again. **Closing the CLI doesn't stop it:** the server goes on, and while it runs other writes are answered `503 write_contention`. Wait for it, and read the answer's counts before you run it again.

## What a restore changes

**A restore adds what the instance lacks and changes nothing it holds.** An item it already holds counts in `duplicates`, so restoring twice changes nothing more. It can still change how the instance behaves:

- **Something you deleted can come back:** a link, natural key or type the archive holds and the instance deleted is restored.
- **A setting the instance hasn't set is taken from the archive,** and one it has set stays. **A shorter `trash_retention_days` makes the next bin purge delete for good items the instance would have kept.** Before you restore, set it to the value you want to keep, the old instance's own to keep its policy, `0` (forever) included. Taking a setting also needs `config.manage`.
- **A type comes back with its guidance,** which takes `schema.write`.
- **A plugin's connector comes back on no host and with no key.** Its settings that aren't secret come with a plugin the instance lacked, and its mapping where the instance saved none. Restoring them needs `connectors.manage`.
- **Settings that describe a computer aren't carried:** `backup_path`, the `object_store_` settings, the addresses and `allow_private_addresses`. An archive that names one is refused `400 validation_error`.

The answer counts what it restored, then lists what it didn't: sign-ins, keys, apps, webhooks, inbound endpoints, connector keys, addresses, the name and the logs. Check these fields:

- **`blobs_missing`** lists files the archive lacks and the instance doesn't hold. Their items are restored, and uploading each file restores it. The CLI exits `1`.
- **`secrets_to_set`** and **`connector_secrets_to_set`** name each secret of the instance or of a connector to set again, since no archive holds a secret's value. [Give a connector its settings](/use/connector-settings#enter-a-secret) says how.
- **`previous_instance`** names the instance that wrote the archive, and the folders it kept in a backup place.

**Restoring into the same instance keeps its keys and devices.** Devices that move to another instance must connect again: [After a restore, on each device](/run/back-up-and-restore#on-each-device) says how.

## When a restore refuses the archive

A restore refuses the whole archive and writes nothing when the file isn't an archive, when its [`version`](/run/upgrade#what-each-release-opens) is later than this build reads, or when it registers a type the instance holds differently (`409 conflict`, each in `details.conflicting_ids`). [Restore from an archive](/reference/api/export-and-restore/restoreArchive) lists every refusal, and the [archive](https://github.com/withmarfa/marfa/blob/main/conformance/spec/archive.md) chapter of the contract has the rules.
