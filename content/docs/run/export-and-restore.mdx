An archive is one file that carries your data to another instance: items with their history, the bin included, links, tables, the types you registered, the settings you chose and the bytes of your files. It carries **no key, app, sign-in, webhook, audit log or secret,** so it opens nothing on its own. Use an archive to keep a copy of your own or to move to an instance that shares no backup place; for everyday protection, [let the server back itself up](/run/back-up-and-restore).

## Export an archive

An archive holds what its credential can read. With the CLI signed in as the owner, that is everything:

<Terminal>

```bash
marfa export --output family-archive.tar
```

```text
9728 byte(s) of application/x-tar into family-archive.tar
```

</Terminal>

The CLI writes the path only once the export ended whole, so **an archive cut short never passes for a whole one.** `--type`, `--state`, `--source`, `--occurred-after` and `--occurred-before` narrow what it carries. A key exports only what it reaches, and lacks the bytes of a file that only an earlier version names unless it holds `blobs.manage`.

The server reads everything from one moment, and writes temporary files on the volume of its data first: an export that would take the volume below `disk_reserve_bytes` is refused `507 insufficient_storage`. [Export an archive](/reference/api/export-and-restore/exportArchive) lists every answer.

## When an archive lacks a file

An archive leaves out the bytes of a file no store holds whole, as after a disk lost it, and of a file the key may not read. With `--output`, the CLI then keeps the archive as `<path>.incomplete`, writes nothing to the path and exits `1`:

```text
marfa: the archive lacks 1 blob(s), which its files.ndjson.gz marks not_carried or lost: sha256:4376bb202f0af45b74b0577fd04bec82e5296f2b6a69de80c09bcf74ac403115; it holds everything else it names, so it is kept at family-archive.tar.incomplete, and nothing was written to family-archive.tar, so nothing there lacks files
```

Export again with a credential that holds `blobs.manage`, or upload a lost file again with `marfa blobs upload <file>`.

## Restore an archive

A restore writes into whichever instance the CLI reaches, so **check that `marfa status` names the one you mean.** It needs `backups.manage` and [a sign-in from the last fifteen minutes](/run/sign-in-as-the-owner#confirm-its-you), or the private socket on the instance's own computer:

```bash
marfa login --fresh-sign-in
marfa restore family-archive.tar
```

**A restore reads an archive from its own release or an earlier one, back to 0.0.72.** Moving to a release that can't open your database is the main use: export while the old release runs, make a new install of the new release, and restore there ([Upgrade an instance](/run/upgrade) has the steps). A restore is one write: refused, failed or stopped, it leaves nothing behind, so run it again. While it runs, other writes are answered `503 write_contention`.

## What a restore changes

**A restore adds what the instance lacks and changes nothing it holds.** An item it already holds counts in `duplicates`, so restoring twice changes nothing more. It can still change how the instance behaves:

- **Something you deleted can come back:** a link, natural key or type the archive holds and the instance deleted is restored.
- **A setting the instance hasn't set is taken from the archive,** and one it has set stays. **A short `trash_retention_days` makes the next bin purge delete for good items the instance would have kept:** set it before you restore, or check it afterward with `marfa config get`. Taking a setting also needs `config.manage`.
- **Settings that describe a computer aren't carried:** `backup_path`, the `object_store_` settings, the addresses and `allow_private_addresses`. An archive that names one is refused `400 validation_error`.

The answer counts what it restored, then lists what it didn't: sign-ins, keys, apps, webhooks, inbound endpoints, connector keys, addresses, the name and the logs. Check three fields:

- **`blobs_missing`** lists files the archive lacks and the instance doesn't hold. Their items are restored, and uploading each file restores it. The CLI exits `1`.
- **`secrets_to_set`** names each secret setting to set again, since no archive holds a secret's value.
- **`previous_instance`** names the instance that wrote the archive, and the folders it kept in a backup place.

Every device must then connect again: [After a restore, on each device](/run/back-up-and-restore#on-each-device) says how.

## When a restore refuses the archive

A restore refuses the whole archive and writes nothing when the file isn't an archive, when its `version` is later than this build reads (restore it with a newer build), or when it registers a type the instance holds differently, refused `409 conflict` with each in `details.conflicting_ids`. [Restore from an archive](/reference/api/export-and-restore/restoreArchive) lists every refusal, and the rules are in the [archive](https://github.com/withmarfa/marfa/blob/main/conformance/spec/archive.md) chapter of the contract.
