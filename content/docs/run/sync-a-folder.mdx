---
title: Sync a folder
description: Keep a directory on your computer and a set of items in step, so each note is a Markdown file you can edit in any app.
---

- **You'll build** a folder on your computer that follows a set of items, so each note is a Markdown file you can edit in any app.
- **You need** the `marfa` CLI and an instance you own, as the [Quickstart](/quickstart) sets them up. You make the first key on the instance's own computer.
- **You'll have** a directory with a file for each note, where a change on either side reaches the other.

A folder is a [device](/devices) whose working copy is a directory. **Its settings live on the instance** as a `system.folder` item, so every computer that follows the folder shares them, and each keeps its own copy and queue of writes. If you stop following the folder, the files stay behind as plain files. [Folder safeguards](/run/folder-safeguards) says when a folder removes a file or an item.

The steps use the CLI. A Mac app does the same with the Swift SDK, as [Use a folder from a Mac app](/run/folder-from-a-mac-app) shows.

<Steps paged>
<Step>

### Make a key for the folder

The folder needs a key that reaches what it holds. Make one as the owner, on the instance's machine. This key suits a folder of notes and files:

```bash
marfa --socket /srv/marfa/data/control/marfa.sock keys create \
  --label "Notes folder" --source notes-folder \
  --type-permission system.folder=write \
  --type-permission core.note=write \
  --type-permission 'core.file.*=write' \
  --edge-permission in-folder=write
```

- **`system.folder`:** write creates the settings, and read lets `folders add` bind a directory to them.
- **The types the folder holds:** write on each type the query admits, here `core.note`. `core.file.*` covers `core.file` and every type under it.
- **`in-folder`:** write on this edge, which records where each file sits.

`folders add` is refused without read on `system.folder`, naming `system.folder:read`, and without write on `in-folder`, naming `edge.in-folder:write`. [Manage keys](/run/manage-keys) explains each flag.

</Step>
<Step>

### Create the folder's settings

The settings say which items the folder holds, through a query, and what a new file becomes. This folder holds every note:

<Terminal>

```bash
marfa folders create --title Notes --query '{"types":["core.note"]}'
```

```text
01a1232d-949d-758c-b244-70057174b96a  system.folder  2026-10-10T00:19:12.157Z  Notes
```

</Terminal>

**Keep the ID** in the first column: the next step binds a directory to it.

</Step>
<Step>

### Add the directory

Bind a directory to the folder. It can be empty or hold files already, and the CLI makes it if it isn't there:

<Terminal>

```bash
marfa folders add Notes --folder 01a1232d-949d-758c-b244-70057174b96a
```

```text
/Users/sam/Notes follows the folder 01a1232d-949d-758c-b244-70057174b96a
the first sync will write and send nothing until you confirm it: 2 file(s) to write into the directory, 1 to send to the server
`marfa folders confirm Notes` lets it go; `marfa folders remove Notes` drops the folder and leaves the files
```

</Terminal>

**Nothing is written into the directory or sent to the instance until you confirm the first sync.** Here the instance holds two notes and the directory held one file, `Ideas.md`. At a terminal the command asks first; in a script, pass `--yes` to confirm at once.

Where an item's file would land on a file the folder will send, one of the two gets a number added to its name, and **neither is written over**. If the existing file is held back, the plan counts the item as `left`, not as written beside it; that file stays for you to fix. A directory inside a folder you already added, or around one, is refused.

Keep the directory out of iCloud Drive, other cloud-synced folders and network storage: two programs syncing the same files can overwrite each other's changes. `marfa folders add` warns and goes on.

**For reference records kept beside code, use a folder inside the repository that git ignores.** Name it `marfa/`, add `marfa/` to `.gitignore`, and add that directory as the folder. Don't name it `.marfa`: every folder already holds a `.marfa` directory of its own, which has its store and `folder.yaml`, as `.git` does in a repository. Anywhere else, any directory works. If git tracks the directory, a checkout, reset or branch switch changes those files and Marfa syncs the changes, so git and Marfa both change the same files. `marfa folders add` warns and goes on, so you can back up a folder through git on purpose.

</Step>
<Step>

### Confirm the first sync

Check the plan first. **The query decides every item the folder takes in.** A query that names only a type holds every active and archived item of that type in the library tier, and the first sync writes all of them to disk. With no `types`, it holds every type the key reads except `system.*`.

Set `tier: all` to write matching items from both the library and feed tiers as files. To narrow the query, use `filter`, `tier`, `state` or `beneath`, as [list, filter and search](/build/list-filter-search) describes. **A folder's `filter` can't use a `backref` condition**, because a folder on disk can't follow one: the instance refuses the settings with `validation_error`, naming `query.filter`, and a computer refuses them before it sends them.

Then confirm, and sync once:

```bash
marfa folders confirm Notes
marfa folders push Notes
```

`marfa folders push` sends what changed in the directory, catches up with the instance, and writes out what changed there. To sync without running it by hand, [keep folders running](/run/keep-folders-running).

</Step>

## Change a folder's settings

Each computer writes the folder's settings out as `.marfa/folder.yaml`:

```yaml title="Notes/.marfa/folder.yaml"
# This folder's settings, the system.folder it follows. An edit here is
# sent through the folder operations by `folders push`, or while watching.
folder: 01a1232d-949d-758c-b244-70057174b96a
version: 1
title: Notes
query:
  types:
    - core.note
```

Edit the file and the next sync sends your change to the instance through [Update a folder](/api-reference/folders/updateFolder), so **it reaches every computer that follows the folder**. `folder` and `version` in this file are Marfa's to write. [Folder](/catalog/folder) lists every other setting.

**A `first_placement` directory can't hold a `..` name.** Write the directory the new files go in, such as `Notes/Tickets`, not `Notes/../Tickets`. Marfa refuses the settings with `validation_error`, naming `first_placement` and the type, because a computer treats a path with `..` as outside the folder and writes no file there.

**Each setting you send replaces its value whole.** Omitted settings the folder type declares stay, and every accepted change removes stored settings the type does not declare. A change names the version it starts from: changes to different settings can merge, but a collision is refused without changing the folder ([folder change rules](https://github.com/withmarfa/marfa/blob/main/conformance/spec/items.md#itemsfolder-change-declared)).

This edit leaves a `drafts` directory alone and tags every new note:

```yaml title="Notes/.marfa/folder.yaml"
ignore:
  - drafts/
defaults:
  tags:
    - from-folder
```

To change settings without opening the local folder, read the `system.folder` item with `marfa items get <id>` and note its `version`. Put the settings you want to change in a JSON file, then send it:

```json title="settings.json"
{"query":{"types":["core.note"]}}
```

```bash tab="CLI" tab-group="client"
marfa folders change <id> --version <n> --file settings.json
```

```http tab="HTTP"
PATCH /folders/<id>
Authorization: Bearer <key>
Content-Type: application/json

{"version":1,"query":{"types":["core.note"]}}
```

Use the version you read in place of `<n>` or `1`. The CLI also takes the JSON directly through `--body`. **To repair a folder that still stores `search`, use a server at v0.0.33 or later** and send the intended `query`, leaving out `search`. Copy every part of the old selection you want to keep, because the server never translates `search` into `query`. Editing `.marfa/folder.yaml` alone cannot remove it. Read the item again to check the accepted settings, then sync the folder.

**Moving a type's items changes the folder too.** When you [move items to another type](/build/move-items-to-another-type), Marfa changes `query.types`, `defaults.type`, `first_placement` and the `type eq` and `type neq` terms in `query.filter` in every folder that names the old type. Each item keeps its file, and the next sync writes the new type into the file's frontmatter.

## Replace a folder's key

A new key with the same `--source` is refused `409 conflict` while the old key is live. [Revoke the old key](/run/manage-keys#revoke-a-key), run the `keys create` command from the first step again, then run `marfa keys keep` so the folder reads the new key from the keychain.

Then run `marfa folders push Notes`. If the key's reach changed, the push rebuilds the working copy once and sends the waiting writes in the same run, keeping earlier verdicts. If the reach changes again during that run, it stops and keeps the remaining writes queued: try again once the access is settled.

## Move to a newer CLI

Each folder keeps its working copy, and its record of which file is which item, in a store that one build of the core made. When a newer CLI uses a different shape, the folder's next push, pull, scan or watch **replaces the store itself, as long as the old store holds no write still to be sent and no answer the folder has yet to record**. It says so on standard error, keeps the folder's record of its files and its first sync, and changes no file. If writes are waiting, push the folder with the earlier CLI first. [Folders](/run/troubleshooting/folders#wrong_schema-on-a-folders-store) covers a write the server refused or gave up on.

If folders sync from login, run `marfa folders autostart on` again with the same options after you upgrade, so the agent gets the newer build's settings. [Sync from login](/run/keep-folders-running#sync-from-login) says how to tell.

## Stop following a folder

To stop following a folder on one computer, run `marfa folders remove Notes`. It is refused while writes wait, apart from a first sync still waiting for confirmation. The folder's own state goes, and **the files stay where they are, as plain files**.

The rules behind a folder are in the [folders](https://github.com/withmarfa/marfa/blob/main/conformance/spec/folders.md) and [device](https://github.com/withmarfa/marfa/blob/main/conformance/spec/device.md) chapters of the contract.
