---
title: Back up and restore
description: Have the server back itself up to another disk or an object store, check that it does, and restore a backup after a lost disk or machine.
---

**The server backs itself up.** Give it one place outside its own disk, and it takes a backup every hour that anything changed, keeps a second copy of every file there, and restores from it when you ask. With no place set, it keeps no backup, and `marfa attention` says so.

| Where the instance runs | Back it up to |
| --- | --- |
| A Mac or Linux machine you [installed with one command](/run/install) | A folder on another disk, such as an external drive or a network share. |
| A container you run yourself | A second volume mounted outside `/data`, or an object store. |
| [Railway](/run/run-on-a-server#on-railway) | An object store. The template also keeps a daily Railway volume backup for six days. |

To carry your data into another instance by hand, [export an archive](/run/export-and-restore) instead.

## Turn on backups

Set **one** of two stored settings, from any machine with a credential that holds `config.manage`:

```bash
marfa config set backup_path /Volumes/Backup/marfa
```

- **`backup_path`** names a folder, best on another disk. The server makes only the folders inside it, and refuses a folder inside its data directory or blob folder, since a backup there is lost with the data. In a container, mount the folder as a volume and name its path inside the container.
- **`object_store_bucket`**, with the other `object_store_` settings, names a bucket. [An object store](/run/run-on-a-server#an-object-store) sets one up.

Setting both is refused `400 validation_error`, so a restore always knows where to look. `backup_interval_seconds` sets how often a backup runs, `3600` by default, and `0` turns the schedule off. A run that finds nothing changed takes no backup.

## What a backup holds

A backup holds what an [archive](/run/export-and-restore) holds: every item and its history, the bin included, every link, the types and the instance's settings. It holds **no file's bytes**: the backup folder or the bucket keeps its own copy of each file, once, while any backup names it.

It never holds a key, an app's token, the owner's password or passkeys, `marfa.secrets` or the object store's credentials, so a backup that leaks opens nothing. A restore brings none of them back.

**The server keeps every backup from the last 24 hours, and the newest of each of the 31 latest days that hold one.** It deletes the rest after each run.

## Take and list backups

With `backups.manage`:

<Terminal>

```bash
marfa backups run
marfa backups list
```

```text
took backup 20261119T003713.995Z.json; deleted 0 old backups
name                       instance_id  created_at                size_bytes
20261119T003713.995Z.json  <id>         2026-11-19T00:37:13.995Z  2010
20261119T001017.891Z.json  <id>         2026-11-19T00:10:17.891Z  2014
```

</Terminal>

`backups list` shows the backups of every instance that uses the place, newest first, so a new instance finds an old one's. `instance_id` says whose each is.

## Check that backups work

**A backup that stops working is a failure you learn of only when you need it.** `marfa attention` names a backup that failed, a backup folder whose disk isn't there and files still waiting for their copy, and stays quiet while all is well. The `backups` block of [Health](/api-reference/health-and-maintenance/getHealth) gives the detail:

```json
{
  "destination": "folder",
  "status": "ok",
  "last_backup_at": "2026-11-19T00:37:13.995Z",
  "failures": 0,
  "last_error": null,
  "copies_waiting": 0
}
```

A wrong or missing destination stops the backups, never the instance: it goes on serving, and tries the destination again on the next run.

## With a bucket

With an object store, **the bucket is the backup and the second copy of every file**. Everything the instance keeps there is under `object_store_prefix`, so give each instance on a shared bucket its own prefix. A new instance started on the same bucket and prefix finds the old instance's backups and its files.

## Restore the copy

To bring an instance back after a lost disk or machine:

1. [Install](/run/install) a new instance and claim it.
2. Point it at the same place: the same `backup_path`, or the same bucket, prefix and credentials.
3. Run `marfa backups list` to find the backup, and its `instance_id`.
4. Sign the CLI in again, since a restore needs [a sign-in from the last five minutes](/run/sign-in-as-the-owner#confirm-its-you), and restore within five minutes:

```bash
marfa login --fresh-sign-in
marfa backups restore <instance id> 20261119T003713.995Z.json
```

The server reads the backup and its files itself, so nothing is downloaded to your machine. On the server's own machine, `--socket` restores with no sign-in. **A restore adds to the instance:** an item it already holds counts in `duplicates`, a setting it already has stays, and nothing is deleted.

The answer counts what it restored, then says what it didn't restore and what to do about each:

```text
The owner's sign-in is not restored. Sign in again on this instance.
Keys are not restored. Make new keys on this instance.
Apps are not restored. Each app signs in again and is approved again.
Webhooks are not restored. Make them again.
A connector's state and agreements are restored but not its key. Give each connector a new key.
The instance's addresses are not restored. Set them on this instance.
The instance's name is not restored. Set it on this instance.
The audit log and the event log are not restored.
```

A connector's new key is made through the private socket today, as [Manage keys](/run/manage-keys#a-key-for-a-connector) shows. Set each secret setting the answer names in `secrets_to_set`, such as the object store's secret, since no backup holds one. **A file that neither the backup's place nor the instance holds** makes the restore refuse and name it. `--allow-missing-files` restores without it instead, listing it in `blobs_missing`, and uploading the file again restores it.

After a restore into a new instance, the answer names the old instance and the folders it kept in the backup folder: `backups/<id>`, `backup-parts/<id>` and `files/<id>`. Delete them only once the old instance no longer runs and nothing else restores from them.

## When the backup disk was replaced

The server writes only into a backup folder it has marked as its own, so a disk that didn't mount isn't filled by mistake. On a new disk, every backup fails, saying the folder isn't the one it knew. Once the new disk holds the folder, start afresh on it:

```bash
marfa backups folder adopt
```

The server forgets the backups and copies it kept on the old disk, and copies every file again with the next backup.

## Copy the data directory instead

A copy of [the data directory](/run/run-on-a-server#the-data-directory) brings back the same instance, keys and sign-ins included. Take it with the server stopped, or as a snapshot of the volume, such as a host's disk snapshot. A copy of the files taken while the server runs can leave a database that won't open. Copy `marfa.secrets` and `marfa.settings.key` with it, or keep the two secrets the platform holds: without them, a restored instance accepts no key.

The rules behind this page are in the [backing up](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#backing-up) section of the instance chapter of the contract.
