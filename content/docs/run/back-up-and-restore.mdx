**The server backs itself up.** Give it one place outside its own disk, and it takes a backup each hour that anything changed and keeps a second copy of every file there. With no place set, it keeps none, and `marfa attention` says so.

| Where the instance runs | Back it up to |
| --- | --- |
| A Mac or Linux computer you [installed with one command](/run/install) | A folder on another disk, such as an external drive or network share. |
| A [container you run](/run/run-on-a-server#in-a-container) | A second volume mounted outside `/data`, or an object store. |
| [Railway](/run/run-on-a-server#on-railway) | An object store. The template also keeps a daily Railway volume backup for six days. |

To carry your data to another instance by hand, [move it with an archive](/run/export-and-restore) instead.

## Turn on backups

Set **one** place. The folder must already exist: the server makes only the folders inside it, and refuses one inside its own data folder, where a backup would be lost with the data. **Changing where backups go needs [a recent sign-in](/run/sign-in-as-the-owner#confirm-its-you):** a key is refused `403 app_sign_in_required`.

```bash
marfa login --fresh-sign-in
marfa config set backup_path /Volumes/Backup/marfa
```

On the server's own computer, [the private socket](/run/run-on-a-server#the-private-socket) does the same with no sign-in. `backup_interval_seconds` sets how often a backup runs, `3600` by default, and `0` turns the schedule off.

## Use an object store

An S3-compatible bucket, such as Amazon S3, Cloudflare R2 or Backblaze B2, keeps the backups and a copy of every file. It needs the same recent sign-in. **Set the secret key last,** because changing the bucket or the endpoint removes the stored one:

```bash
marfa config set object_store_endpoint https://<account>.r2.cloudflarestorage.com
marfa config set object_store_region auto
marfa config set object_store_access_key_id <id>
marfa config set object_store_bucket marfa-backups
marfa config set object_store_secret_access_key
```

- **The endpoint is the store's own host,** without the bucket. For a store that puts the bucket before its host, set `object_store_path_style` to `false`.
- **The prefix, `marfa` by default, holds one instance's backups and files.** An instance that replaces another takes the old one's prefix and finds them there. Give an instance beside yours, such as a trial, a prefix of its own.
- **Share a bucket only between instances of one owner:** a prefix keeps instances apart, not access.
- **Serve the bucket from a different site from the instance,** so an uploaded HTML file can't run as one of the instance's pages.

[Instance settings](/reference/instance-settings) lists every `object_store_` setting.

## What a backup holds

A backup holds what an [archive](/run/export-and-restore) holds: every item and its history, the bin included, links, types and the settings you chose. Each file's bytes are kept once in the backup place while any backup names them. **It never holds a key, an app's token, the owner's password or passkeys, or a secret,** so a backup that leaks opens nothing. The server keeps every backup from the last 24 hours and the newest of each of the 31 days before.

## Check that backups work

`marfa attention` names a place that isn't set, a backup that failed, a folder whose disk isn't there, and files still waiting for their copy. To take one now and see what exists:

<Terminal>

```bash
marfa backups run
marfa backups list
```

```text
took backup 20261121T034911.289Z.json; deleted 0 old backups
name                       instance_id                           created_at                size_bytes
20261121T034911.289Z.json  01a1fc38-a2fc-74d9-aa20-7b4106ff9242  2026-11-21T03:49:11.289Z  2389
```

</Terminal>

Both need `backups.manage`. **A wrong or missing place stops the backups, never the instance,** and the next run tries again.

### When the backup disk was replaced

The server writes only into a folder it marked as its own, so on a new disk every backup fails. Once the new folder is there, `marfa backups folder adopt` starts afresh on it, and the next backup copies every file again.

## Restore a backup

**What you need is the backup place:** the folder, or the bucket with its prefix and credentials. Nothing else, not even the server's secrets.

<Steps>
<Step>

### Make a new instance

[Install](/run/install) one and claim it. Point it at the same place: the same `backup_path`, or the same bucket, prefix and credentials, set as above.

</Step>
<Step>

### Find the backup

`marfa backups list` shows the backups in the place, newest first, each with the `instance_id` of the instance that took it.

</Step>
<Step>

### Restore it

A restore writes into whichever instance the CLI reaches, so **check that `marfa status` names the new one.** It needs [a recent sign-in](/run/sign-in-as-the-owner#confirm-its-you), or the private socket on the new instance's computer:

```bash
marfa login --fresh-sign-in
marfa backups restore 01a1fc38-a2fc-74d9-aa20-7b4106ff9242 20261121T034911.289Z.json
```

</Step>
</Steps>

**A restore adds what the instance lacks and changes nothing it holds.** It carries no key, sign-in, app, webhook or address. A setting the new instance hasn't set is taken from the backup, so **a short `trash_retention_days` makes its next bin purge delete items for good:** check `marfa config get` afterward, and see [what a restore changes](/run/export-and-restore#what-a-restore-changes). A file the backup names that no store holds makes the restore refuse and name it: `--allow-missing-files` restores without it.

The answer names what the old instance left in the backup place, such as `backups/<id>` and `files/<id>`. Delete them once nothing restores from them, and **never delete a bucket's `blobs/`,** which every instance on the prefix shares.

## After a restore

### On each device

The old keys and sign-ins are refused, so connect each device to the new instance:

- **The address.** On the server's computer, give the new install the old one's `--access` and `--address`. Elsewhere, [set the sign-in address](/run/address#move-the-address).
- **The CLI.** Run `marfa login --url <address>`, or give a script [a new key](/use/manage-keys).
- **Synced folders.** The watch stops each folder, saying its server now answers as another Marfa instance: [Fix a folder](/use/fix-a-folder#now-answers-as-another-marfa-instance) says how to follow it again.
- **Agents, Claude and ChatGPT.** Remove Marfa and add it again, as [Connect your agent](/connect-your-agent) shows.
- **Connectors.** Give each [a new key](/use/manage-keys).

To bring back the same instance with its keys, from a copy of its data folder, see [Restore a copy of the data directory](/run/restore-the-data-directory).
