---
title: Back up and restore
description: Have the server back itself up to another disk or an object store, check that it does, and restore a backup after a lost disk or machine.
---

**The server backs itself up.** Give it one place outside its own disk, and it takes a backup every hour that anything changed, keeps a second copy of every file there, and restores from it when you ask. With no place set, it keeps no backup, and `marfa attention` says so.

| Where the instance runs | Back it up to |
| --- | --- |
| A Mac or Linux machine you [installed with one command](/run/install) | A folder on another disk, such as an external drive or a network share. |
| A container you run yourself | A second volume mounted outside `/data`, or an object store. |
| [Railway](/run/run-on-a-server#on-railway) | An object store. The template also keeps a daily Railway volume backup for six days. |

To carry your data into another instance by hand, [export an archive](/run/export-and-restore) instead.

## Turn on backups

Set **one** of two stored settings, from any machine, with a credential that holds `config.manage`:

```bash
marfa config set backup_path /Volumes/Backup/marfa
```

- **`backup_path`** names a folder, best on another disk. The server makes only the folders inside it, and refuses a folder inside its data directory or blob folder, since a backup there is lost with the data. In a container, name the path where the folder is mounted.
- **`object_store_bucket`**, with the other `object_store_` settings, names a bucket, as [Use an object store](#use-an-object-store) shows.

Setting both is refused `400 validation_error`, so a restore always knows where to look. `backup_interval_seconds` sets how often a backup runs, `3600` by default, and `0` turns the schedule off. A run that finds nothing changed takes no backup.

## Use an object store

An S3-compatible bucket, such as Amazon S3, Cloudflare R2 or Backblaze B2, keeps the backups and a second copy of every file. Set the bucket last, since the server uses the store from the moment it's set:

```bash
marfa config set object_store_endpoint https://<account>.r2.cloudflarestorage.com
marfa config set object_store_region auto
marfa config set object_store_access_key_id <id>
marfa config set object_store_secret_access_key
marfa config set object_store_bucket marfa-backups
```

`config set` asks for the secret key with no echo, or reads it from standard input.

- **A prefix holds one instance's backups and files,** and its default is `marfa`. An instance that replaces another, after a lost machine or [a move to a new release](/run/upgrade#move-to-a-newer-release), takes the old one's prefix and finds its backups and files there. Give an instance that runs beside yours, such as a trial, a prefix of its own.
- **Share a bucket only between instances of one owner.** A prefix keeps instances apart, not access: each holds credentials for the whole bucket.
- **Serve the bucket from a different site from the instance.** A link the bucket signs serves a file from the bucket's own origin, which keeps an uploaded HTML file from running as one of the instance's pages.

[Settings](/run/settings) lists every `object_store_` setting.

## What a backup holds

A backup holds what an [archive](/run/export-and-restore) holds: every item and its history, the bin included, every link, the types and the settings you chose. It holds **no file's bytes**: the backup folder or the bucket keeps its own copy of each file, once, while any backup names it.

It never holds a key, an app's token, the owner's password or passkeys, the server's secrets or the object store's settings, so a backup that leaks opens nothing.

**The server keeps every backup from the last 24 hours, and the newest of each of the 31 latest days that hold one.** It deletes the rest after each run.

## Take and list backups

Both need `backups.manage`:

<Terminal>

```bash
marfa backups run
marfa backups list
```

```text
took backup 20261119T003713.995Z.json; deleted 0 old backups
name                       instance_id  created_at                size_bytes
20261119T003713.995Z.json  <id>         2026-11-19T00:37:13.995Z  2010
20261119T001017.891Z.json  <id>         2026-11-19T00:10:17.891Z  2014
```

</Terminal>

`backups list` shows the backups of every instance that uses the place, newest first, so a new instance finds an old one's. `instance_id` says whose each is.

## Check that backups work

**A backup that stops working is a failure you learn of only when you need it.** `marfa attention` names a place that isn't set, a backup that failed, a backup folder whose disk isn't there and files still waiting for their copy. The `backups` block of [Health](/api-reference/health-and-maintenance/getHealth) gives the detail:

```json
{
  "destination": "folder",
  "status": "ok",
  "last_backup_at": "2026-11-19T00:37:13.995Z",
  "failures": 0,
  "last_error": null,
  "copies_waiting": 0
}
```

A wrong or missing destination stops the backups, never the instance, which tries it again on the next run.

## Restore a backup

**With a backup place, the place is all you need:** the folder, or the bucket with its prefix and credentials. A [copy of the data directory](#copy-the-data-directory-instead) also needs the server's secrets.

To bring an instance back after a lost disk or machine:

1. [Install](/run/install) a new instance and claim it.
2. Point it at the same place: the same `backup_path`, or the same bucket, prefix and credentials.
3. Run `marfa backups list` to find the backup and its `instance_id`.
4. Restore it. A restore writes into whichever instance the CLI reaches, so **check that `marfa status` names the new instance first.** It needs [a sign-in from the last five minutes](/run/sign-in-as-the-owner#confirm-its-you), so sign the CLI in again.

```bash
marfa login --fresh-sign-in
marfa backups restore <instance id> 20261119T003713.995Z.json
```

On the server's own machine, the [private socket](/run/run-on-a-server#the-private-socket) reaches that instance alone and restores with no sign-in: `marfa --socket <install folder>/data/control/marfa.sock backups restore …`.

**A file that neither the backup's place nor the instance holds** makes the restore refuse and name it. `--allow-missing-files` restores without it instead, listing it in `blobs_missing`, and uploading the file again restores it.

## After a restore into a new instance

A backup restores as an archive does: **it adds what the instance lacks and changes nothing it holds**. It carries no key, sign-in, app or webhook, and no setting that describes a machine, such as the address. The answer names what it didn't restore. [What a restore changes](/run/export-and-restore#what-a-restore-changes) lists what to check, starting with `trash_retention_days`.

The answer also names what the old instance kept in the backup place: in a folder, `backups/<id>`, `backup-parts/<id>` and `files/<id>`; in a bucket, `backups/<id>` and `backup-parts/<id>` under the prefix. Delete them only once nothing restores from them. **Never delete a bucket's `blobs/`:** every instance on the prefix shares the file copies there.

### On each device

The old sign-ins and keys are refused, so connect each device again, at the new instance's address:

- **The address.** On the server's machine, give the new install the old one's `--access` and `--address`, which the old install's `.env` names in `MARFA_ACCESS` and `MARFA_ADDRESS`, as [Upgrade an instance](/run/upgrade#retire-the-old-install) shows. Elsewhere, [set the sign-in address](/run/address#move-the-address).
- **The CLI.** Run `marfa login --url <address>`. Where a key is kept, run `marfa keys forget`, then keep a new one with `marfa keys keep`.
- **Synced folders.** Once the CLI reaches the new instance, the watch carries on: its first sync builds the folder's copy again from the new instance, then sends the edits made on disk meanwhile. `marfa folders push` does the same by hand. A watch that reads a key file needs [a new key](/run/manage-keys#give-a-key-to-a-folder-watch).
- **Agents, Claude and ChatGPT.** Remove Marfa and add it again, as [Connect your agent](/connect-your-agent) and [Use Marfa from Claude or ChatGPT](/use/claude-and-chatgpt) show.
- **Connectors and scripts.** Give each [a new key](/run/manage-keys).

## When the backup disk was replaced

The server writes only into a backup folder it has marked as its own, so a disk that didn't mount isn't filled by mistake. On a new disk, every backup fails, saying the folder isn't the one it knew. Once the new disk holds the folder, start afresh on it:

```bash
marfa backups folder adopt
```

The server forgets the backups and copies it kept on the old disk, and copies every file again with the next backup.

## Copy the data directory instead

A copy of [the data directory](/run/run-on-a-server#the-data-directory) brings back the same instance, keys and sign-ins included. **It must be an image of one moment:** a copy taken with the server stopped, or a snapshot, such as a host's disk snapshot or Time Machine, which copies from an APFS snapshot. The server opens such an image with every write it had answered. A copy of the files taken one by one while the server runs can hold a database that isn't whole.

Keep the server's secrets with the copy: `marfa.env` from the install folder, or `marfa.secrets` where the server made them, or the two variables your platform holds. **With a different `MARFA_KEY_SALT`, the server starts but refuses every key and app token,** and every browser is signed out: sign in as the owner again and make new keys. A different `MARFA_AUTH_SECRET` also signs everyone out of the browser. `marfa.settings.key`, inside the data directory, seals the secret settings: without it, each must be set again.

The rules behind this page are in the [backing up](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#backing-up) section of the instance chapter of the contract.
