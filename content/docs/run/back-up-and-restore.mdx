**The server backs itself up.** Give it one place outside its own disk, and it takes a backup each hour that anything changed and keeps a second copy of every file there. With no place set it keeps none, and `marfa attention` says so.

| Where the instance runs | Back it up to |
| --- | --- |
| A Mac or Linux computer you [installed with one command](/run/install) | A folder on another disk, such as an external drive or network share. |
| A [container you run](/run/run-on-a-server#in-a-container) | A second volume mounted outside `/data`, or an object store. |
| [Railway](/run/run-on-a-server#on-railway) | An object store. The template also keeps a daily Railway volume backup for six days. |

To carry your data by hand, [move it with an archive](/run/export-and-restore).

## Turn on backups

Set **one** place. The folder must already exist, and can't be inside the server's own data folder. **Changing where backups go needs [a recent sign-in](/run/sign-in-as-the-owner#confirm-its-you):** a key is refused `403 app_sign_in_required`.

```bash
marfa login --fresh-sign-in
marfa config set backup_path /Volumes/Backup/marfa
```

On the server's own computer, [the private socket](/run/run-on-a-server#the-private-socket) does the same with no sign-in. `backup_interval_seconds` sets how often (`3600`), and `0` turns it off.

## Use an object store

An S3-compatible bucket, such as Amazon S3, Cloudflare R2 or Backblaze B2, keeps the backups and a copy of every file, and needs the same sign-in. **Set the secret key last,** because changing the bucket or endpoint removes the stored one:

```bash
marfa config set object_store_endpoint https://<account>.r2.cloudflarestorage.com
marfa config set object_store_region auto
marfa config set object_store_access_key_id <id>
marfa config set object_store_bucket marfa-backups
marfa config set object_store_secret_access_key
```

- **The endpoint is the store's own host,** without the bucket.
- **The prefix, `marfa` by default, holds one instance's backups and files.** An instance that replaces another takes the old one's prefix and finds them there; give one beside yours a prefix of its own. A prefix keeps instances apart, not access, so share a bucket only between instances of one owner.
- **Serve the bucket from a different site from the instance,** so an uploaded HTML file can't run as one of its pages.

[Instance settings](/reference/instance-settings) lists every `object_store_` setting.

## What a backup holds

A backup holds what an [archive](/run/export-and-restore) holds, with each file's bytes kept once in the backup place. **It never holds a key, an app's token, the owner's password or passkeys, or a secret,** so a backup that leaks opens nothing. The server keeps every backup from the last 24 hours and the newest of each of the 31 days before.

## Check that backups work

`marfa attention` names a place that isn't set, a failed backup, a missing disk, files waiting for their copy and damaged copies. To take a backup now and see what exists:

<Terminal>

```bash
marfa backups run
marfa backups list
```

```text
took backup 20261121T034911.289Z.json; deleted 0 old backups
name                       instance_id                           created_at                size_bytes
20261121T034911.289Z.json  01a1fc38-a2fc-74d9-aa20-7b4106ff9242  2026-11-21T03:49:11.289Z  2389
```

</Terminal>

Both need `backups.manage`. **A wrong place stops the backups, never the instance.**

**A damaged copy doesn't stop the backups:** one an object store archived, or a disk changed or can't read, is stored again by the next backup that needs it. **A fault in the place itself, such as refused credentials, fails the backup.**

### When the backup disk was replaced

The server writes only into a folder it marked as its own, so every backup to a new disk fails. `marfa backups folder adopt` starts afresh on the new folder, and the next backup copies every file again.

## Restore a backup

**You need only the backup place:** the folder, or the bucket with its prefix and credentials, and not even the server's secrets.

**A restore brings back the last backup, so work written after it is lost:** up to an hour by default. If the old instance still runs, take a last backup first. Only what your devices hold survives.

<Steps>
<Step>

### Make a new instance and sign in to it

[Install](/run/install) one and claim it. Then run `marfa login --url <address> --fresh-sign-in` and allow it all: the restore needs a recent sign-in and, for [what it writes](/run/export-and-restore#what-a-restore-changes), more than `backups.manage`. Or, on its computer, put `--socket` and the path of its [private socket](/run/run-on-a-server#the-private-socket) before each command.

**Write down the ID on the `instance` line of `marfa status`.**

</Step>
<Step>

### Point it at the place and set what it keeps

Set the same place as above.

**Then set `trash_retention_days`, the days binned items are kept, before you restore.** A restore takes a setting only where the new instance has none, and a shorter value makes the next purge delete items for good. Use the old instance's value, even `0` (forever).

```bash
marfa config set trash_retention_days <days>
```

</Step>
<Step>

### Find the backup

`marfa backups list` lists the backups, newest first, each with the `instance_id` of the instance that took it. **Restore a row with the old instance's ID;** the new one soon lists its own backups too.

</Step>
<Step>

### Restore it

```bash
marfa backups restore 01a1fc38-a2fc-74d9-aa20-7b4106ff9242 20261121T034911.289Z.json
```

</Step>
</Steps>

**A restore adds what the instance lacks and changes nothing it holds.** It carries no key, sign-in, app, webhook or address ([what a restore changes](/run/export-and-restore#what-a-restore-changes)). **Read `blobs_missing` in the answer before you call it done.** A file the backup names that no store holds makes the restore refuse and name it, and `--allow-missing-files` restores without it. A file the backup lists as lost, which `marfa attention` reported when it was taken, restores without the flag and is named only there: upload it again with `marfa blobs upload <file>`.

The answer names what the old instance left in the backup place, such as `backups/<id>`. **Delete it only once the old instance is retired and a complete new backup of the new one is checked.** Never delete a bucket's `blobs/`, which every instance on the prefix shares.

## After a restore

### On each device

The old keys and sign-ins are refused, so connect each device again. **Settle the address first:** moving it afterward ends the app sign-ins you just made.

- **The address.** On the server's computer, give the new install the old one's `--access` and `--address`. Elsewhere, [set it](/run/address#move-the-address). `marfa config get` shows it.
- **Synced folders.** The watch stops each directory: its server now answers as another Marfa instance. [Fix a folder](/use/fix-a-folder#now-answers-as-another-marfa-instance) says what to do, and **one whose removal lists changes it couldn't send** follows [Keep a directory's unsent edits](/run/keep-folder-edits-after-a-restore).
- **Agents, Claude and ChatGPT.** Remove Marfa and add it again, as [Connect your agent](/connect-your-agent) shows.
- **Scripts and connectors.** Give each [a new key](/use/manage-keys).

To bring back the same instance with its keys, [restore a copy of the data directory](/run/restore-the-data-directory).
