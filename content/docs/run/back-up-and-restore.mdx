---
title: Back up and restore
description: Have the server back itself up to another disk or an object store, check that it does, and restore a backup after a lost disk or machine.
---

**The server backs itself up.** Give it one place outside its own disk, and it takes a backup every hour that anything changed, keeps a second copy of every file there, and restores from it when you ask. With no place set, it keeps no backup, and `marfa attention` says so.

| Where the instance runs | Back it up to |
| --- | --- |
| A Mac or Linux machine you [installed with one command](/run/install) | A folder on another disk, such as an external drive or a network share. |
| A container you run yourself | A second volume mounted outside `/data`, or an object store. |
| [Railway](/run/run-on-a-server#on-railway) | An object store. The template also keeps a daily Railway volume backup for six days. |

To carry your data into another instance by hand, [export an archive](/run/export-and-restore) instead.

## Turn on backups

Set **one** of two stored settings, from any machine, with a credential that holds `config.manage`:

```bash
marfa config set backup_path /Volumes/Backup/marfa
```

- **`backup_path`** names a folder, best on another disk. The server makes only the folders inside it, and refuses a folder inside its data directory or blob folder, since a backup there is lost with the data. In a container, mount the folder as a volume and name its path inside the container.
- **`object_store_bucket`**, with the other `object_store_` settings, names a bucket, as [Use an object store](#use-an-object-store) shows.

Setting both is refused `400 validation_error`, so a restore always knows where to look. `backup_interval_seconds` sets how often a backup runs, `3600` by default, and `0` turns the schedule off. A run that finds nothing changed takes no backup.

## Use an object store

An S3-compatible bucket, such as Amazon S3, Cloudflare R2 or Backblaze B2, keeps the backups and a second copy of every file. Set the bucket last, since the server uses the store from the moment it's set:

```bash
marfa config set object_store_endpoint https://<account>.r2.cloudflarestorage.com
marfa config set object_store_region auto
marfa config set object_store_access_key_id <id>
marfa config set object_store_secret_access_key
marfa config set object_store_bucket marfa-backups
```

`config set` asks for the secret access key with no echo, or reads it from standard input, and never takes it as an argument.

- **Give each instance its own `object_store_prefix`,** such as `home` and `trial`. A prefix holds one instance's files and backups, and its default is `marfa`. A new instance started on the same bucket and prefix finds the old one's backups and files.
- **Share a bucket only between instances of one owner.** A prefix keeps instances apart, not access: each holds credentials for the whole bucket.
- **Serve the bucket from a different site from the instance.** A link the bucket signs serves a file from the bucket's own origin, which keeps an uploaded HTML file from running as one of the instance's pages.

[Settings](/run/settings) lists every `object_store_` setting.

## What a backup holds

A backup holds what an [archive](/run/export-and-restore) holds: every item and its history, the bin included, every link, the types and the settings you chose. It holds **no file's bytes**: the backup folder or the bucket keeps its own copy of each file, once, while any backup names it.

It never holds a key, an app's token, the owner's password or passkeys, the server's secrets or the object store's settings, so a backup that leaks opens nothing.

**The server keeps every backup from the last 24 hours, and the newest of each of the 31 latest days that hold one.** It deletes the rest after each run.

## Take and list backups

Both need `backups.manage`:

<Terminal>

```bash
marfa backups run
marfa backups list
```

```text
took backup 20261119T003713.995Z.json; deleted 0 old backups
name                       instance_id  created_at                size_bytes
20261119T003713.995Z.json  <id>         2026-11-19T00:37:13.995Z  2010
20261119T001017.891Z.json  <id>         2026-11-19T00:10:17.891Z  2014
```

</Terminal>

`backups list` shows the backups of every instance that uses the place, newest first, so a new instance finds an old one's. `instance_id` says whose each is.

## Check that backups work

**A backup that stops working is a failure you learn of only when you need it.** `marfa attention` names a place that isn't set, a backup that failed, a backup folder whose disk isn't there and files still waiting for their copy, and stays quiet while all is well. The `backups` block of [Health](/api-reference/health-and-maintenance/getHealth) gives the detail:

```json
{
  "destination": "folder",
  "status": "ok",
  "last_backup_at": "2026-11-19T00:37:13.995Z",
  "failures": 0,
  "last_error": null,
  "copies_waiting": 0
}
```

A wrong or missing destination stops the backups, never the instance: it goes on serving, and tries the destination again on the next run.

## Restore a backup

**What you need depends on what you kept.** With a backup place, the place is all: the folder, or the bucket with its prefix and credentials. Nothing else is needed, since a restore brings back no key or sign-in. A [copy of the data directory](#copy-the-data-directory-instead) also needs the server's secrets.

To bring an instance back after a lost disk or machine:

1. [Install](/run/install) a new instance and claim it.
2. Point it at the same place: the same `backup_path`, or the same bucket, prefix and credentials.
3. Run `marfa backups list` to find the backup and its `instance_id`.
4. Restore it. A restore needs [a sign-in from the last five minutes](/run/sign-in-as-the-owner#confirm-its-you), so sign the CLI in again first.

```bash
marfa login --fresh-sign-in
marfa backups restore <instance id> 20261119T003713.995Z.json
```

On the server's own machine, the [private socket](/run/run-on-a-server#the-private-socket) restores with no sign-in: `marfa --socket <install folder>/data/control/marfa.sock backups restore …`. The server reads the backup and its files itself, so nothing is downloaded to your machine.

The answer counts what it restored, then says what it didn't restore and what to do about each:

```text
The owner's sign-in is not restored. Sign in again on this instance.
Keys are not restored. Make new keys on this instance.
Apps are not restored. Each app signs in again and is approved again.
Webhooks are not restored. Make them again.
Inbound endpoints are not restored, and the addresses other services hold for them no longer work. Make each endpoint again and give its sender the new address.
A connector's state and agreements are restored but not its key. Give each connector a new key.
The instance's addresses are not restored. Set them on this instance.
The instance's name is not restored. Set it on this instance.
The audit log and the event log are not restored.
```

A connector's new key is made through the private socket today, as [Manage keys](/run/manage-keys#a-key-for-a-connector) shows. **A file that neither the backup's place nor the instance holds** makes the restore refuse and name it. `--allow-missing-files` restores without it instead, listing it in `blobs_missing`, and uploading the file again restores it.

### After a restore

- **Check `trash_retention_days`** in what `marfa config get` prints. A restore takes each setting the instance hasn't set from the backup, and a short retention makes the next bin purge delete items for good.
- **Set what describes a machine,** which no backup carries: the addresses, `allow_private_addresses`, and each secret the answer names in `secrets_to_set`.
- **Expect deleted things back.** A restore [adds what the instance lacks](/run/export-and-restore#what-a-restore-changes), and a link or type the instance deleted comes back if the backup holds it.

The answer also names the old instance and the folders it kept in the backup folder: `backups/<id>`, `backup-parts/<id>` and `files/<id>`. Delete them only once the old instance no longer runs and nothing else restores from them.

## When the backup disk was replaced

The server writes only into a backup folder it has marked as its own, so a disk that didn't mount isn't filled by mistake. On a new disk, every backup fails, saying the folder isn't the one it knew. Once the new disk holds the folder, start afresh on it:

```bash
marfa backups folder adopt
```

The server forgets the backups and copies it kept on the old disk, and copies every file again with the next backup.

## Copy the data directory instead

A copy of [the data directory](/run/run-on-a-server#the-data-directory) brings back the same instance, keys and sign-ins included. **Take it with the server stopped,** or as a snapshot of the whole volume at one moment, such as a host's disk snapshot. Time Machine, or any copy of the files taken while the server runs, can catch the database mid-write and leave one that won't open, so it isn't a backup of Marfa.

Keep the server's secrets with the copy: `marfa.env` from the install folder, or `marfa.secrets` where the server made them, or the two variables your platform holds. **With a different `MARFA_KEY_SALT`, the server starts but refuses every key and app token,** and only the owner's password still signs in. A different `MARFA_AUTH_SECRET` signs everyone out of the browser. `marfa.settings.key`, inside the data directory, seals the secret settings: without it, each must be set again.

The rules behind this page are in the [backing up](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#backing-up) section of the instance chapter of the contract.
