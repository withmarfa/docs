---
title: Back up and restore
description: Have the server back itself up to another disk or an object store, check that it does, and restore a backup after a lost disk or machine.
---

**The server backs itself up.** Give it one place outside its own disk, and it takes a backup every hour that anything changed, keeps a second copy of every file there, and restores from it when you ask. With no place set, it keeps no backup, and `marfa attention` says so.

| Where the instance runs | Back it up to |
| --- | --- |
| A Mac or Linux machine you [installed with one command](/run/install) | A folder on another disk, such as an external drive or a network share. |
| A container you run yourself | A second volume mounted outside `/data`, or an object store. |
| [Railway](/run/run-on-a-server#on-railway) | An object store. The template also keeps a daily Railway volume backup for six days. |

To carry your data into another instance by hand, [export an archive](/run/export-and-restore) instead.

## Turn on backups

Set **one** of two stored settings, from any machine, with a credential that holds `config.manage`:

```bash
marfa config set backup_path /Volumes/Backup/marfa
```

- **`backup_path`** names a folder, best on another disk of the server's machine. The server makes only the folders inside it, and refuses one inside its data directory or blob folder, where a backup is lost with the data. In a container, name the mounted path. **It holds the folder for itself alone,** so a second server can't use it: on a network file system, whose locks may not keep out a server on another machine, `marfa attention` warns `The backup folder is on a network file system`.
- **`object_store_bucket`** and the other `object_store_` settings name a bucket, as [Use an object store](#use-an-object-store) shows.

Setting both is refused `400 validation_error`, so a restore always knows where to look. `backup_interval_seconds` sets how often a backup runs, `3600` by default, and `0` turns the schedule off.

## Use an object store

An S3-compatible bucket, such as Amazon S3, Cloudflare R2 or Backblaze B2, keeps the backups and a second copy of every file. Changing where they go needs [a recent sign-in](/run/sign-in-as-the-owner#confirm-its-you) or the [private socket](/run/run-on-a-server#the-private-socket). **Set the secret key last:** changing the bucket or the endpoint removes the stored secret unless the same write sets one.

```bash
marfa login --fresh-sign-in
marfa config set object_store_endpoint https://<account>.r2.cloudflarestorage.com
marfa config set object_store_region auto
marfa config set object_store_access_key_id <id>
marfa config set object_store_bucket marfa-backups
marfa config set object_store_secret_access_key
```

`config set` asks for the secret key with no echo, or reads standard input.

- **The endpoint is the store's own host, without the bucket.** For a store that puts the bucket before its host, set `object_store_path_style` to `false`, with a lowercase bucket name and an endpoint that's a host name, not an IP address, whose labels are 1 to 63 characters, with one dot at its end at most.
- **A prefix, `marfa` by default, holds one instance's backups and files.** An instance that replaces another, after a lost machine or [a move to a new release](/run/upgrade#move-to-a-newer-release), takes the old one's prefix and finds its backups and files there. Give an instance beside yours, such as a trial, a prefix of its own.
- **Share a bucket only between instances of one owner.** A prefix keeps instances apart, not access: each holds credentials for the whole bucket.
- **Serve the bucket from a different site from the instance.** A signed link serves a file from the bucket's origin, so an uploaded HTML file can't run as one of the instance's pages.

[Settings](/run/settings#every-stored-setting) lists every `object_store_` setting and the values each takes.

## What a backup holds

A backup holds what an [archive](/run/export-and-restore) holds: every item and its history, the bin included, every link, the types and the settings you chose. It holds **no file's bytes**: the backup folder or the bucket keeps one copy of each file while any backup names it.

It never holds a key, an app's token, the owner's password or passkeys, the server's secrets or the object store's settings, so a backup that leaks opens nothing.

**The server keeps every backup from the last 24 hours, and the newest of each of the 31 latest days that hold one.** It deletes the rest after each run.

## Take and list backups

Both need `backups.manage`:

<Terminal>

```bash
marfa backups run
marfa backups list
```

```text
took backup 20261119T003713.995Z.json; deleted 0 old backups
name                       instance_id  created_at                size_bytes
20261119T003713.995Z.json  <id>         2026-11-19T00:37:13.995Z  2010
20261119T001017.891Z.json  <id>         2026-11-19T00:10:17.891Z  2014
```

</Terminal>

`backups list` shows every instance's backups in the place, newest first, and `instance_id` says whose each is.

## Check that backups work

`marfa attention` names a place that isn't set, a backup that failed, a backup folder whose disk isn't there or that another program changed, and files still waiting for their copy. The `backups` block of [Health](/reference/api/health-and-maintenance/getHealth) gives the detail:

```json
{
  "destination": "folder",
  "status": "ok",
  "last_backup_at": "2026-11-19T00:37:13.995Z",
  "failures": 0,
  "last_error": null,
  "copies_waiting": 0
}
```

A wrong or missing destination stops the backups, never the instance, and the next run retries. **An object store setting that can't be read attaches no store:** files are served from the instance's own disk, and `marfa attention` names the setting. Correct it with `marfa config set`, and the store is used with no restart. **A store at an address that isn't public stays attached but unused** while `allow_private_addresses` is off: `backups.reason` is `destination_unusable`, `backups.store_error` and `marfa blobs stores` say why, and no file is purged until the store is used again.

## Restore a backup

**With a backup place, the place is all you need:** the folder, or the bucket with its prefix and credentials. A [copy of the data directory](/run/restore-the-data-directory) also needs the server's secrets.

To bring an instance back after a lost disk or machine:

1. [Install](/run/install) a new instance and claim it.
2. Point it at the same place: the same `backup_path`, or the same bucket, prefix and credentials.
3. Run `marfa backups list` to find the backup and its `instance_id`.
4. Restore it. A restore writes into whichever instance the CLI reaches, so **check that `marfa status` names the new instance first.** It needs [a recent sign-in](/run/sign-in-as-the-owner#confirm-its-you).

```bash
marfa login --fresh-sign-in
marfa backups restore <instance id> 20261119T003713.995Z.json
```

On the server's own machine, the [private socket](/run/run-on-a-server#the-private-socket) reaches that instance alone and restores with no sign-in: `marfa --socket <install folder>/data/control/marfa.sock backups restore …`.

**A file that neither the backup's place nor the instance holds** makes the restore refuse and name it. `--allow-missing-files` restores without it, listing it in `blobs_missing`; upload the file again to restore it.

## After a restore into a new instance

A backup restores as an archive does: **it adds what the instance lacks and changes nothing it holds**. It carries no key, sign-in, app or webhook, and no setting that describes a machine, such as the address. [What a restore changes](/run/export-and-restore#what-a-restore-changes) lists what to check, starting with `trash_retention_days`.

The answer names what the old instance kept in the backup place: in a folder, `backups/<id>`, `backup-parts/<id>` and `files/<id>`; in a bucket, `backups/<id>` and `backup-parts/<id>` under the prefix. Delete them once nothing restores from them. **Never delete a bucket's `blobs/`:** every instance on the prefix shares the file copies there.

### On each device

The old sign-ins and keys are refused, so connect each device again, at the new instance's address:

- **The address.** On the server's machine, give the new install the old one's `--access` and `--address`, as [Upgrade an instance](/run/upgrade#retire-the-old-install) shows. Elsewhere, [set the sign-in address](/run/address#move-the-address).
- **The CLI.** Run `marfa login --url <address>`. Where a key is kept, run `marfa keys forget`, then keep a new one with `marfa keys keep`.
- **Synced folders.** Once the CLI reaches the new instance, the watch builds the folder's copy again, then sends the edits made meanwhile. `marfa folders push` does it by hand. A watch that reads a key file needs [a new key](/run/manage-keys#give-a-key-to-a-folder-watch).
- **Agents, Claude and ChatGPT.** Remove Marfa and add it again, as [Connect your agent](/connect-your-agent) and [Use Marfa from Claude or ChatGPT](/use/claude-and-chatgpt) show.
- **Connectors and scripts.** Give each [a new key](/run/manage-keys).

## When the backup disk was replaced

The server writes only into a backup folder it has marked as its own, so a disk that didn't mount isn't filled by mistake. On a new disk, every backup fails, saying the folder isn't the one it knew. Once the new disk holds the folder, start afresh on it:

```bash
marfa backups folder adopt
```

The server claims the new folder first, then forgets what it kept on the old disk and copies every file again with the next backup. If it can't claim the folder, it forgets nothing, and the message says to check that the folder is writable and has room.

The rules behind this page are in the [backing up](https://github.com/withmarfa/marfa/blob/main/conformance/spec/instance.md#backing-up) section of the instance chapter of the contract.
