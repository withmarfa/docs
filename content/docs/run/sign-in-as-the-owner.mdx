The owner signs in at the instance's address, at `/auth/sign-in`, with the username and password chosen when claiming it, or with a passkey. **The browser is only for signing in and approving:** every owner task is a command, run from any computer with the CLI signed in or a key that holds its permission.

## Sign in the CLI

`marfa login` signs the CLI in through your browser, as an app you approve, and keeps its token in your keychain:

```bash
marfa login --url https://marfa.example.com
```

**Choose Full access on the approval screen** for the CLI you look after Marfa with: a narrowed CLI lacks the permissions owner tasks need. Give a script or agent [a key of its own](/use/manage-keys) instead.

## Confirm it's you

Some actions need **a sign-in from the last fifteen minutes:** restoring an archive or a backup, moving the [sign-in address](/run/address#move-the-address), changing `allow_private_addresses`, changing where files and backups go, and writing a type's [guidance](/catalog/type-definition#descriptions-and-guidance). Sign the CLI in again, then run the command:

```bash
marfa login --fresh-sign-in
```

An older sign-in is refused `401 insufficient_user_authentication`. A key is refused `403 app_sign_in_required`, because it has no sign-in to renew: use the CLI signed in with `marfa login`, or [the private socket](/run/run-on-a-server#the-private-socket). A key you made still writes guidance. Nothing changes when an action is refused.

**An agent meets the same rule** when it changes guidance with `marfa_save_type`, or `allow_private_addresses`, the backup place or an object store setting at `/mcp/admin`. Start a new browser authorization in your AI client and sign in again: a reconnect that only refreshes its stored token can be refused again. No agent over MCP moves `sign_in_address`: use [`marfa config set`](/run/address#move-the-address).

## Passkeys and the password

The **Password and passkeys** page, at `/auth/owner/passkeys`, changes the password and adds, renames and removes passkeys. **A passkey belongs to the address it was made at,** which is `https`, or `http` on `localhost`. Renaming or removing one, and adding one from an older session, opens a **Confirm it's you** dialog that takes your password or a passkey.

Each CLI command needs `sign_ins.manage`:

```bash
marfa owner passkeys list
marfa owner passkeys add --no-browser
marfa owner password
```

`passkeys add` opens the sign-in page to register one, and `--no-browser` prints its address instead. `rename` and `delete` take a passkey's ID. `password` asks for the current and new password with no echo and **signs out every browser**, while keys and apps keep working.

## See and end sign-ins

A sign-in is one of your browsers, apps or keys. [See and revoke access](/use/see-and-revoke-access) lists them and ends one or all.

## Change the profile

`marfa profile update` changes the owner's username, email, name or avatar. **The username is what you sign in with:** 1 to 64 lowercase letters, digits, `.`, `_` or `-`.

```bash
marfa profile update --username sam
marfa profile update --avatar ./me.png
```

**The avatar is a PNG, JPEG or WebP of 2 MiB or less.** Changing the profile leaves the password, passkeys, sign-ins, keys and apps as they were.

## Recover the owner's password

Recovery starts on the server's computer. As the server's account, use [the private socket](/run/run-on-a-server#the-private-socket):

```bash
marfa --socket ~/marfa-server/data/control/marfa.sock owner recover
```

The CLI asks for the new password with no echo. In a container, run it as `docker exec -it marfa marfa --socket /data/control/marfa.sock owner recover`. If the server can't start in full, `MARFA_CONTROL_ONLY=true` opens the socket alone.

**Without a shell on the computer,** such as on Railway, set `MARFA_OWNER_RECOVERY=true` and restart the server. Its log then shows `Recover this Marfa's owner at https://<address>/setup with recovery code: <code>`. Open the address, enter the code and choose a password. The code works once, for 60 minutes. Remove the setting afterwards.

Either way, **recovery signs out every browser** and keeps keys and apps working. If the password is wrong too many times, the sign-in page and the API answer `429` with a wait: a passkey still signs in.
