---
title: Sign in as the owner
description: Sign in with a password or a passkey, confirm it's you before a sensitive change, manage your sign-ins and profile, and recover a lost password.
---

The owner signs in at the instance's address, at `/auth/sign-in`, with the password chosen when claiming the instance or with a passkey. **The browser is only for signing in and approving:** Marfa has no owner console, so every task an owner has is a command, run from any machine with the CLI signed in or a key that holds the permission it names.

## Sign in the CLI

`marfa login` signs the CLI in through your browser, as an app the owner approves, and keeps its token in the keychain:

```bash
marfa login --url https://marfa.example.com
```

**On the approval screen, choose Full access** for the CLI you look after Marfa with. Restoring a backup, managing keys and apps, and changing settings each need a permission that a narrowed CLI lacks. Give a script or an agent [a key of its own](/run/manage-keys) instead. [Use Marfa from the command line](/use/command-line) covers profiles and keys.

## Confirm it's you

Four actions need **a sign-in from the last five minutes**: restoring an archive or a backup, moving the [sign-in address](/run/address#move-the-address), and changing `allow_private_addresses`. Sign the CLI in again first, then run the command within five minutes:

```bash
marfa login --fresh-sign-in
```

An older sign-in is refused `401 insufficient_user_authentication`, and an API key is refused `403 app_sign_in_required`, since a key has no sign-in to renew. Either way nothing changes.

In the browser, renaming or removing a passkey and adding one from an older session open a **Confirm it's you** dialog, which takes the owner's password or a passkey and then sends the change again. Confirming replaces your browser session with a new one, and a refused confirmation leaves it as it was.

## Passkeys

The **Password and passkeys** page, at `/auth/owner/passkeys`, changes the password and adds, renames and removes passkeys. **A passkey belongs to the sign-in address it was made at,** which must be `https`, or `http` on `localhost`. A passkey still signs you in while password attempts are locked.

From the CLI, each needs `sign_ins.manage`:

```bash
marfa owner passkeys list
marfa owner passkeys rename <id> --name "Laptop"
marfa owner passkeys delete <id>
marfa owner passkeys add --no-browser
```

`add` issues no credential: it opens the sign-in page, where you sign in yourself and register the passkey, and `--no-browser` prints the page's address instead.

## Change the password

`marfa owner password` replaces the password, as the same page does. It asks for the current password and the new one with no echo, or reads `{"current_password": …, "new_password": …}` with `--stdin`. **It signs out every browser**, and keys and apps keep working.

## See and end sign-ins

A sign-in is one of the owner's browsers, apps or keys. `marfa sign-ins list` lists them, and `marfa sign-ins end` and `end-all` end them at once, with `sign_ins.manage`. [See and cut access](/use/see-and-cut-access) shows each command and what a sign-in reaches.

## Change the owner's profile

`marfa profile update` changes the owner's email, name or avatar, with the profile write permission for each field. The email is the address for password sign-in: it's stored in lowercase and needs no confirmation, and a credential changes it only when its permission names `email`.

```bash
marfa profile update --name "Sam Rivera"
marfa profile update --avatar ./me.png
marfa profile update --clear-avatar
```

**The avatar is a file you upload, never a web address:** a PNG, JPEG or WebP of 2 MiB or less. Marfa decides the kind from the file's bytes and keeps it in its database. A change leaves the password, passkeys, sign-ins, keys and apps as they were. [Permissions](/catalog/permissions#the-five-maps) lists what an app may change.

## What the owner's browser reaches

A browser session reaches the sign-in pages and nothing else: signing in and out, claiming the instance, the approval screens for apps and devices, and the **Password and passkeys** page. **It never reads an item or changes a setting.** A browser left signed in, a copied cookie or a page that rides on it reaches no data.

## Recover the owner's password

Recovery starts on the server's machine. With a shell there, use [the private socket](/run/run-on-a-server#the-private-socket), as the server's account:

```bash
marfa --socket ~/marfa-server/data/control/marfa.sock owner recover
```

The CLI asks for the new password with no echo, and `--stdin` reads `{"password": …}` instead. In a container, run `docker exec -it marfa marfa --socket /data/control/marfa.sock owner recover`. If the server can't start in full, such as when its port is taken, start it with `MARFA_CONTROL_ONLY=true` to open the socket alone.

**Without a shell on the machine,** such as on Railway, set `MARFA_OWNER_RECOVERY=true` and restart the server. Its log then shows a line like `Recover this Marfa's owner at https://<address>/setup with recovery code: <code>`. Open the address, enter the code and choose a password. The code works once, for 60 minutes, and a restart prints a new one. Remove the setting afterwards.

Either way, **recovery signs out every browser**, keeps keys and apps working, and lifts the sign-in lock: ten wrong passwords from one address at one email in fifteen minutes, or thirty at any emails, answer `429` with `Retry-After`. Behind a proxy, every caller shares one address unless the server [trusts the forwarded one](/run/address#behind-a-proxy-you-set-up-yourself).
