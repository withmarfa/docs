An instance is one server program with one database and one folder of files. **One database takes one server:** keep a host at one replica, and turn off anything that stops an idle service. [Choose where to run Marfa](/run/choose-where-to-run) compares the routes.

## On Railway

Railway runs the release image on a volume and gives it an `https` address.

<Steps>
<Step>

### Deploy the template

Open the [Marfa template](https://railway.com/new/template/5z9-Ja), choose a workspace and deploy. The template starts on the newest release, `ghcr.io/withmarfa/marfa-server:latest`, and makes the two secrets. Once the deploy passes its `/health` check, `curl https://<address>/` names the release as `version`. **Pin it:** in the server's **Settings**, set the image to `ghcr.io/withmarfa/marfa-server:<version>` and deploy, so a later redeploy can't move your database to a newer release.

</Step>
<Step>

### Claim the instance

In the server's **Deployments** tab, open the deploy logs and find the line `Claim this Marfa at https://<address>/setup with setup code: <code>`. Open the address, enter the code and choose the owner's username and password. A restart before you claim prints a new code.

</Step>
<Step>

### Copy the secrets

From the **Variables** tab, copy `MARFA_KEY_SALT` and `MARFA_AUTH_SECRET` to a password manager. They aren't in the volume, and **a volume restored without its salt refuses every key.**

</Step>
</Steps>

**For your own domain,** add it in Railway and set `MARFA_CLAIM_ADDRESS` to it before you claim, because a passkey belongs to its address. Keep the template's other choices: **Serverless** off and image auto updates off, with the volume at `/data`. The [Railway guide](https://github.com/withmarfa/marfa/blob/main/deploy/railway.md) lists every setting, and says how to restore a Railway volume backup. [Back up and restore](/run/back-up-and-restore) covers a backup to an object store.

## In a container

Every release publishes `ghcr.io/withmarfa/marfa-server:<version>` for `linux/amd64` and `linux/arm64`, which runs as user 65532. Start it from a version tag, so a restart never changes the build under your database:

<include cwd>src/generated/server-image.md</include>

- **Publish the port on `127.0.0.1`,** for a proxy or tunnel on the same machine. A bare `-p 8600:8600` opens it to every network.
- **Mount one volume at `/data`.** A host folder must belong to user 65532 with mode `700`.
- **Keep the secrets.** Without `marfa.env`, the first start makes them in `/data/marfa.secrets`. Either way, keep a copy outside the volume.

Claim the instance through the CLI in the container, then open the link within five minutes:

```bash
docker exec marfa marfa --socket /data/control/marfa.sock setup open --address https://marfa.example.com --no-browser
```

### Check the image

Run `gh attestation verify oci://ghcr.io/withmarfa/marfa-server:<version> --repo withmarfa/marfa` with the [GitHub CLI](https://cli.github.com/) before you run it.

## With Docker from the CLI

`marfa server install --docker` runs the same image with Docker Compose, on the release of your `marfa`. The folder gets a `compose.yaml`, and the data lives in the volume `<name>-data`. **An install keeps its runtime:** to move between Docker and a service, make a second install and [move your data](/run/upgrade) into it.

## Under your own supervisor

Install [the two programs](/run/install) and run `marfa server run`, with the settings in its environment: the server reads its environment, not a file, so have the supervisor load `marfa.env`.

```bash title="marfa.env"
MARFA_DATABASE_PATH=/srv/marfa/data/marfa.db
MARFA_BLOB_PATH=/srv/marfa/data/blobs
MARFA_LISTEN_HOST=127.0.0.1
MARFA_PORT=8600
```

Point a monitor at [`GET /health`](/reference/api/health-and-maintenance/getHealth), which needs no credential. Allow ten seconds for a stop. `marfa server run` runs the server program and ends with its exit status:

| Status | Meaning | Your supervisor |
| --- | --- | --- |
| `0` | A clean stop. | Starts it again if you want it running. |
| `1` | A failed start, such as a port in use. The log names the cause. | Starts it again once fixed. |
| `128` and a signal number | The server was killed. | Starts it again. |

**A server that won't open its database exits `78` and changes nothing, but `marfa server run` doesn't pass that on.** It logs the refusal, stays up and idle so that nothing starts it again into the same refusal, and exits `0` when you stop it. [See why](/run/troubleshooting/start-and-claim#the-server-refuses-its-database-exit-78).

## The data directory

The database and the files are your data: keep them on local storage that survives a restart. `MARFA_DATABASE_PATH` and `MARFA_BLOB_PATH` set where, and [Instance settings](/reference/instance-settings#start-only-settings) lists the rest. Beside them the server keeps `marfa.secrets`, only where it made the secrets, and `marfa.settings.key`, which seals secret settings: **keep it with the data,** or set each again. To bring the instance back from a copy, see [Restore a copy of the data directory](/run/restore-the-data-directory).

The server refuses a folder another account can write to, and names the command that fixes it. A second server on the same folder is refused: leave the `.server-lock` files in place.

## The private socket

`control/marfa.sock` lets a command on the server's machine, run as the server's own account, act without a credential. **It can claim the instance and [recover the owner's password](/run/sign-in-as-the-owner#recover-the-owners-password),** which also have routes through a browser, as [the Railway guide](https://github.com/withmarfa/marfa/blob/main/deploy/railway.md#claim-your-instance) shows for a claim. It also stands in for [a recent sign-in](/run/sign-in-as-the-owner#confirm-its-you). Its folder must belong to the server's account, with mode `700`. `MARFA_CONTROL_SOCKET` moves it: an absolute path of 103 bytes or fewer.
