**Marfa sends nothing about itself until you set where.** An instance tells you of its own faults first, in places you already look. Sending anything further is your choice, to a destination you name, and each stored setting here applies from the next send, with no restart.

## See a fault yourself

When the server meets a fault of its own, such as a database failure, a panic or an internal error, `marfa attention` lists an entry of kind `fault`. Its reference names the kind and where, such as `internal:POST /items/{id}`, and never an item, and its title counts how often. The entry goes 24 hours after the fault last happened, or at a restart. **The server's log holds the detail,** which the entry points to: [where it is](/run/install#look-after-the-service) depends on how you installed it.

To be told at once, subscribe a [webhook](/build/receive-webhooks) to `attention.raised` with a key that holds `instance.read`. Even while the database fails, the server sends a new fault's event to such a webhook, from memory.

## Send traces, logs and metrics

The instance exports over OTLP, the OpenTelemetry protocol, to any receiver that takes it over HTTP. The endpoint and its headers are secrets, so `marfa config set` asks for each with no echo:

```bash
marfa config set otel_exporter_otlp_endpoint
marfa config set otel_exporter_otlp_headers
marfa config set otel_sample_ratio 0.1
```

The headers are `key=value` pairs with percent-encoded values, such as `authorization=Bearer%20<token>`. **A trace that holds an error is always exported,** whatever `otel_sample_ratio` says. The endpoint must be public unless [`allow_private_addresses`](/run/settings#let-webhooks-reach-a-private-network) is on. Separate settings send one signal, traces, logs or metrics, elsewhere.

**The server reads no `OTEL_*` variable.** It logs a warning that names each one it finds, so a variable a hosting platform sets can't move your telemetry. A log record carries its message and a fixed list of fields, and a span names the route, so neither holds what you wrote, a file's name or a credential.

**Everything an instance exports names it by `service.instance.id`** and its release by `service.version`. `otel_resource_attributes` adds attributes of your own: mark a test instance with `deployment.environment=test`.

## Send a heartbeat

An instance can't report its own death. Set `heartbeat_url`, and the `heartbeat` job requests it with a `GET`, no body and no identity, every minute: give it to an uptime monitor.

## Send errors to PostHog

PostHog is one optional route, never part of Marfa. If you already use it, a free PostHog Cloud project and two settings, `posthog_host` and `posthog_project_token`, send each unhandled error there: [Send an instance's errors to PostHog](/run/send-errors-to-posthog).

## Pause or turn it off

`telemetry_enabled` set to `false` pauses traces, logs, metrics and PostHog reports together and keeps every setting as it was. To stop for good, clear the endpoint, the heartbeat and the PostHog pair. A [restore](/run/export-and-restore#what-a-restore-changes) carries no telemetry secret: its answer names the settings to set again.

## What the CLI, connectors and apps send

**The CLI sends one trace for each command, and only when its environment names an OpenTelemetry collector,** in `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`. With neither set, it sends nothing, and `OTEL_SDK_DISABLED=true` turns the trace off. The trace names the command and carries its exit code and the error code of a refusal, and **holds no argument, address, credential or item content.** A folder watch that starts at login carries the `OTEL_*` settings of the shell that turned it on. [The CLI's telemetry reference](https://github.com/withmarfa/marfa/blob/main/core/marfa-cli/COMMANDS.md#telemetry) lists every setting.

**A connector sends nothing of its own** unless its environment sets `OTEL_EXPORTER_OTLP_ENDPOINT`; a failed run reaches you through `marfa attention` instead. **What an app sends is decided by the people who build it,** and its own settings say how to turn it off. The Swift SDK sends nothing itself.
