title: Send telemetry
description: Send an instance's traces and logs to an OpenTelemetry endpoint, its errors to PostHog, and a notice or a heartbeat to a URL you choose, and see what the CLI and apps send.
---

Marfa software can report on itself from three places: an instance, the CLI and an app built on the Swift SDK. An instance reports in four ways, and **each is off until you set its variable**: an instance that sets none of them sends nothing anywhere. Set the variables in the server's environment, as [Settings](/run/settings#set-an-environment-setting) shows, and restart the server. [What the CLI sends](#what-the-cli-sends) and [What apps send](#what-apps-send) say when the other two report.

| Variable | What it does | Default |
| --- | --- | --- |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | The OTLP receiver's base address. Setting it turns on traces and logs, posted to `v1/traces` and `v1/logs` under it. | None |
| `OTEL_EXPORTER_OTLP_HEADERS` | Headers sent with every export, as comma-separated `key=value` pairs with percent-encoded values. It is a secret. | None |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | An address for traces alone, used as written. It needs `OTEL_EXPORTER_OTLP_ENDPOINT` set too, or the server refuses to start. | None |
| `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` | The same for logs. | None |
| `OTEL_EXPORTER_OTLP_TRACES_HEADERS` | Headers for traces alone. They win over `OTEL_EXPORTER_OTLP_HEADERS`, and nothing reads them without the shared address. | None |
| `OTEL_EXPORTER_OTLP_LOGS_HEADERS` | The same for logs. | None |
| `MARFA_OTEL_SAMPLE_RATIO` | The share of traces exported, from 0 to 1. A trace that contains an error is always exported. | `0.05` |
| `OTEL_SERVICE_NAME` | The service name on what Marfa sends. It wins over a `service.name` in `OTEL_RESOURCE_ATTRIBUTES`. | `marfa-server` |
| `OTEL_RESOURCE_ATTRIBUTES` | Attributes added to everything exported, as comma-separated `key=value` pairs with percent-encoded values. | None |
| `MARFA_POSTHOG_HOST` | The PostHog host that exceptions go to. It needs `MARFA_POSTHOG_PROJECT_TOKEN` and `OTEL_EXPORTER_OTLP_ENDPOINT`. | None |
| `MARFA_POSTHOG_PROJECT_TOKEN` | The token of the PostHog project that exceptions go to. It needs `MARFA_POSTHOG_HOST` and `OTEL_EXPORTER_OTLP_ENDPOINT`. | None |
| `ERROR_WEBHOOK_URL` | Where the server posts a notice when a request fails with a `500`. | None |
| `MARFA_ERROR_WEBHOOK_TIMEOUT_MS` | How long one notice post may take. | `5000` |
| `MARFA_HEARTBEAT_URL` | An address the server requests on a schedule, so something else can notice when the requests stop. | None |
| `MARFA_HEARTBEAT_INTERVAL_MS` | How often the server requests `MARFA_HEARTBEAT_URL`. | `60000` |

[Every environment setting](/run/settings#every-environment-setting) has the limits.

## Send traces and logs

Marfa exports traces and logs over OTLP, the OpenTelemetry protocol, to any receiver that takes it over HTTP. This sends one tenth of the traces:

```bash
export OTEL_EXPORTER_OTLP_ENDPOINT=https://otel.example.com
export OTEL_EXPORTER_OTLP_HEADERS='authorization=Bearer%20<token>'
export MARFA_OTEL_SAMPLE_RATIO=0.1
```

Marfa drops what carries a credential, a request body, raw SQL or an email address, and strips the query string from a URL, before it exports anything.

### Tell instances apart

**Every log record and span names its instance by `service.instance.id`**, the `instance_id` that `GET /` answers, so several instances can share one project. Every PostHog exception does too, once the database has opened. The instance's name isn't sent, because it can change and can be personal.

`OTEL_RESOURCE_ATTRIBUTES` adds attributes of your own. **An attribute named there replaces the server's own of the same name**, `service.instance.id` and `service.version` included. Mark a test or demo instance with `deployment.environment`, which is `production` unless you set it:

```bash
export OTEL_RESOURCE_ATTRIBUTES=deployment.environment=staging
```

The `environment` of a [failure notice](#post-a-notice-when-a-request-fails) takes `deployment.environment.name` if the list names it, and otherwise `deployment.environment`. A malformed list stops the server from starting, and the message names the setting.

Telemetry loads **only when the server starts with its preload**, which the container does. When you run the server with Node yourself, start it this way, because plain `node dist/index.js` exports nothing:

```bash
cd packages/server
node --import ./dist/instrumentation.js dist/index.js
```

When it is on, the server prints `OpenTelemetry initialized` at start, with the service name, the sample ratio and whether it reports exceptions.

## Report errors to PostHog

PostHog's error tracking reads exception events, which OTLP doesn't carry, so Marfa sends exceptions on a path of its own. It needs **all three** of `OTEL_EXPORTER_OTLP_ENDPOINT`, `MARFA_POSTHOG_HOST` and `MARFA_POSTHOG_PROJECT_TOKEN`, or the server refuses to start and names the missing one:

```bash
export MARFA_POSTHOG_HOST=https://eu.i.posthog.com
export MARFA_POSTHOG_PROJECT_TOKEN=<project token>
```

Use the host of the region your PostHog project lives in: `https://eu.i.posthog.com` for EU Cloud, `https://us.i.posthog.com` for US Cloud. Marfa reports an error that no handler answered, which the request meets as a `500`, with its stack, the request's ID, the method and the path. It attaches no person to the event and turns off the location lookup.

## Post a notice when a request fails

Set `ERROR_WEBHOOK_URL` and the server posts a JSON notice to it when a request fails with a `500`. The notice holds the `timestamp`, `request_id`, `error`, `path`, `method`, `instance` and `environment`. A Telegram bot address gets a readable message in its place. The server sends the same error on the same path at most once a minute, and a post that fails is dropped without a word.

## Send a heartbeat

An instance can't report its own death. Set `MARFA_HEARTBEAT_URL` and the `heartbeat` [housekeeping job](/run/housekeeping) requests it with a `GET`, no body and no identity, every `MARFA_HEARTBEAT_INTERVAL_MS`. Give the address to an uptime monitor that raises an alarm when the requests stop. A failed request is logged as a warning.

## What the CLI sends

**The CLI sends nothing unless the environment asks for it.** `OTEL_SDK_DISABLED=true` turns off both reports:

| Report | Sent when | What it holds |
| --- | --- | --- |
| A trace for each command | `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` is set | The command's name and exit code |
| One exception to PostHog | `MARFA_POSTHOG_HOST` and `MARFA_POSTHOG_PROJECT_TOKEN` are both set, and the command ends in a fault | The command's name, the error and exit codes, the version, the operating system and a fixed sentence |

**On the CLI, an exception needs no OTLP endpoint**, unlike the server. Neither report holds an argument, address, credential, item content or message.

**A fault is something the CLI or the core got wrong**, such as a panic or an answer it can't read. A refusal, a usage error, Ctrl-C, being offline, a timeout, a rate limit or any `5xx` sends none. [The CLI reference](https://github.com/withmarfa/marfa/blob/main/core/marfa-cli/COMMANDS.md#telemetry) lists every variable it reads and every fault.

## What apps send

**An app sends nothing unless the people who built it gave it a destination, and reporting is on.** The Swift SDK's [`MarfaTelemetry` product](/swift-sdk/errors-and-testing#report-errors-and-events) has no destination of its own. It stays inert until the app passes it an `https` PostHog host and a project token, and the app turns it on.

Whoever builds the app chooses the destination:

- **A build from an app's public source** has no destination and sends nothing when the app keeps its project token out of the source, as the Swift SDK asks.
- **An app you build on the SDK** sends nothing unless you configure the product. If you do, you choose the project and own what it receives.

An app that reports sends two kinds of report, to the PostHog project it was built for:

- **Errors.** One exception for each failure the app reports, posted as the CLI posts its own. It holds the error's type, one fixed sentence, the operation that was running and the error's code. It has no stack frames, no person and no location lookup. A failure that repeats is reported at most once a minute for each type and operation, and at most 30 times an hour in all. Each exception says in `dropped_since_last` how many were held back since the previous one.
- **Events.** A fixed set of log records, each a name with counts, flags and words fixed in the app's source, such as how many writes a sync left waiting. They go out in batches over OTLP.

Every report also names the app, its version, the operating system, its version and the chip. **No report names the instance** the app is connected to: its `instance_id`, name and address are never sent, unlike the server's own telemetry, which [tells instances apart](#tell-instances-apart).

### What an app never sends

**No report holds a word a person wrote or a place they keep it.** The SDK's types make this hard to do by accident: a report takes only text fixed in the source, numbers and booleans. An app never sends:

- item text, titles or tags;
- item IDs or natural keys;
- keys or credentials;
- the instance's ID, name or address;
- file paths or search text;
- an error's `message`, which can repeat any of these.

An app sends no product analytics: nothing about which screens a person opens or what they do in Marfa.

### Turn it off

**Each app decides where its switch is.** In an app you build, the switch is `Telemetry.shared.isEnabled`, which is off until the app turns it on. **Turning it off drops every report waiting to go, stops a send under way and sends nothing more** until it is turned on again.
