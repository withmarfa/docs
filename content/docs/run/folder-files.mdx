title: Files in a folder
description: See what a file holds when a folder writes an item as a file, where attached files go, and how an edit on either side reaches the other.
---

A folder writes each item as a file and reads a changed file back as an edit. The examples follow the `Notes` folder made in [Sync a folder](/run/sync-a-folder).

## How items appear as files

A note is a Markdown file named after its title, or after its ID if it has none. Here's `Reading list.md`:

```markdown title="Notes/Reading list.md"
---
type: core.note
tier: library
title: Reading list
marfa_id: 01a1232d-947e-7399-86e1-97648a87c232
marfa_version: 1
---
Start with the essays, then the letters.
```

The lines between the `---` fences are the frontmatter. The text after them is the body.

- **`type`:** the item's type when the value is a Marfa type identifier. A value that is not a type identifier belongs to the item's `type` property instead and survives writing the file back.
- **`tier`, `tags`, `state` and `occurred_at`:** the item's own fields.
- **A line named after an edge type,** such as `references`: an edge.
- **Every other line:** a property.
- **`marfa_id` and `marfa_version`:** the item and the version the file was written from. Leave them to Marfa.

A new Markdown file needs no frontmatter. It takes its type and tier from the folder's `defaults` or its query, and its title from `defaults` or, without one, its file name. With `query.tier: all`, a new file without an explicit tier uses `defaults.tier` or, without one, `library`. Once the instance creates the item, Marfa writes the frontmatter and `marfa_id` into the file.

A `.txt` file is all body. Any other file the query admits, such as a photo, becomes a file item with its bytes uploaded as a blob, as [Handle files](/build/handle-files) describes. The file's extension gives its media type, and the media type gives the type: a photo becomes a `core.file.image`, and an `.html`, `.htm` or `.xhtml` file becomes a `core.file.webpage`, so a page an agent writes into the folder is kept as a page. Audio and video files become `core.file.audio` and `core.file.video`, and any other file becomes a `core.file`. The query must admit the type, and `core.file` in `types` admits every type under it. A file item stays a file item at a `.md`, `.markdown` or `.txt` name, such as after a pull places it there or you rename it: its bytes go to the item as they are, and Marfa doesn't read them as a note.

## Files attached to a note

**Every file attached to a note the folder holds is written with the note**, whether or not the query names its type. A file the note's body embeds, such as `![](photos/map.png)` or `![[map.png]]`, is written where the link says, and every other attached file beside the note.

An embed makes a `references` edge from the note to the file. **Embedding a file the query doesn't hold also attaches it**, since the folder holds it only as the note's. A file the query holds is attached only by the note's `has-attachment` line, which lists it even when the body embeds it. The line also lists every attached file the body doesn't embed:

```markdown title="Notes/Packing for the trip.md"
---
type: core.note
tier: library
title: Packing for the trip
has-attachment:
  - "[[map.png]]"
marfa_id: 01a1232d-94b0-7c1e-9d2a-3f6b8e0c5a71
marfa_version: 2
---
Pack light.
```

- **It follows the note.** Move the note to another directory and the next sync moves the file beside it. A file you move away from its note goes back beside the note; to keep it somewhere else, embed it by its path.
- **One file, one place.** A file attached to notes in two directories is written once, beside the first note in path order, and the sync reports the other note. Two attached files with the same name are told apart by a number.
- **Another folder keeps its own copy.** If another folder on the same Mac holds the file through its own query, each folder keeps a copy, and neither takes the other's. When a note leaves one folder's query for another's, its attached files move with it.
- **It goes to the bin with the note.** When every note it's attached to goes to the bin, Marfa moves the file there too, and restoring any of the notes brings it back. When the notes only leave the states the query holds, such as by being archived, the file leaves the folder with them, unless the query holds it itself. Either way it goes under the same [safeguards](/run/folder-safeguards) as any other file.
- **Remove the line or the embed, keep the file.** Take a file out of `has-attachment` and the next sync removes the `attached-to` edge. Take an embed out of the body and the sync removes only its `references` edge, so the file stays attached. Either way the file stays on disk.

The folder reads attached files with its key, so the key needs read on their types, such as `core.file.*` in [the key you made for the folder](/run/sync-a-folder#make-a-key-for-the-folder). A file whose bytes the folder can't fetch is reported, and the sync goes on.

## Links in a note's body

A link in a note's body, such as `[[Reading list]]`, makes a `references` [edge](/edges) from the note to the item it names, by ID, title or file name. `[[Reading list#Essays|my essays]]` names the same item: the text after `#` is a heading, and the text after `|` is what the note shows.

- **A link stays on one line.** It runs from the last `[[` before its `]]` on the same line, so a `[[` with no `]]` after it on its line opens nothing.
- **Code and comments are text.** A link in inline code, a code block or a comment makes no edge, and a `]]` inside a code span closes nothing.
- **A backslash stays as typed.** A link has no escapes.
- **A link to an item in the bin names nothing.** The sync reports it, as it reports a link that names no item or several, and keeps the note's edges until the link resolves.

An embed, such as `![[map.png]]`, has the same bounds. It makes a `references` edge to the file, and attaches the file as [the section above](#files-attached-to-a-note) shows. Its path reads Markdown escapes, as Obsidian's does: `![](my\_pic.png)` names `my_pic.png`, and in a table cell, `![[map.png\|200]]` names `map.png`.

### When a linked note is retitled

**Links follow a retitled note.** When a note gets a new title, in Marfa or because you renamed its file, each folder rewrites the links to it on its next pull: `[[Old#Steps|the plan]]` becomes `[[New#Steps|the plan]]`.

- **A title that can't sit in a link**, such as one that is empty, holds `|` or `#`, or names another item too, makes the link name the note by its ID: `[[<id>|Old]]`.
- **Only those links change.** Links by ID, Markdown links, embeds, code and frontmatter stay.
- **Your edits come first.** A file is rewritten only once the instance accepts the title, and never over an edit the folder hasn't read.

Until then, the link still names the same note. A pull counts the files it rewrote as `document(s) whose links were rewritten to follow a retitled item` ([retitled link rules](https://github.com/withmarfa/marfa/blob/main/conformance/spec/folders.md#foldersbody-link-retitled)).

### Links to a note written later

**A note can link to a note that doesn't exist yet.** The folder still creates the linking note's item and reports its file as left as written, naming the link. Once the working copy changes, such as when the folder creates the target or a pull brings it in from another device, the next sync looks the name up again, makes the edge and stops reporting the file. Two notes that link to each other resolve this way whichever you write first.

A name that matches several items is never guessed. It resolves once only one item has it, such as after you move the other to the bin. While neither the file nor the working copy changes, the folder doesn't ask the instance about the name again. A name in a frontmatter edge line, such as `references`, waits and resolves the same way ([held links](https://github.com/withmarfa/marfa/blob/main/conformance/spec/folders.md#foldersedge-held-retried)).

## Edit on either side

Edit a file and sync, and the edit reaches its item:

<Terminal>

```bash
marfa folders push Notes
```

```text
0 created, 1 updated, 0 renamed, 2 unchanged, 0 missing, 0 deleted, 0 skipped
the server answered 1 write(s)
1 file(s) written
```

</Terminal>

An edit is a write based on the `marfa_version` the file names. If another app changed the same note meanwhile, the instance settles the two as [Versions](/versions) explains: changes to different fields merge, and a collision the type can't merge leaves a conflicted copy, which appears as a second file.

A note's file name and its title stay in step. Rename the file and the new name, without its extension, becomes the title. Change the title anywhere else and the next sync renames the file, numbering the name if another file has it. The folder leaves a name alone when it can't tell whether you chose it.
