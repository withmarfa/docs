`AUTH_MODE` selects how the server authenticates callers. Two values:

- **`keys`** (default) — every space exists because someone created its admin key. Space provisioning is a manual server-side operation; there is no public sign-up flow. Suitable for self-hosted single-space setups, internal multi-space deployments where admins provision spaces out-of-band, and development.
- **`hosted`** — a managed-service shape. Better Auth's email + password sign-up endpoint is mounted, sign-up creates a user + space atomically, sessions are issued as HTTP-only cookies, and OAuth Authorization-Code + PKCE flows are available for third-party clients. Suitable for cloud deployments intended to serve end-users without operator involvement per sign-up.

API keys work the same way in both modes — a space owner mints scoped `marfa_k1_` keys, which authenticate the bearer-only data plane. The difference is whether a public endpoint provisions accounts.

## Enabling hosted mode

```bash
export AUTH_MODE=hosted
export MARFA_AUTH_BASE_URL=https://marfa.example.com   # your public origin
export MARFA_AUTH_SECRET="<long random secret>"        # required in production
export MARFA_AUTH_ALLOW_SIGNUP=true                    # opens public sign-up
```

At boot the server mounts Better Auth's HTTP surface under `/auth/*`:

- **`POST /auth/sign-up/email`** — creates a user record and a space. No auth required when `MARFA_AUTH_ALLOW_SIGNUP=true`. When email verification is on, the response carries no session until the address is confirmed.
- **`POST /auth/sign-in/email`** — issues a session cookie for an existing user.
- **`POST /auth/sign-out`** — clears the session cookie and invalidates the row.
- **`GET /auth/get-session`** — returns the current session details (the authenticated user and session).
- **OAuth surface** — `/auth/authorize`, `/auth/oauth2/token`, `/auth/oauth2/register` (Dynamic Client Registration), plus the Device Authorization endpoints for CLI / Raycast flows. See [Authentication](/api-reference/authentication).

Hosted mode requires a storage backend that supports the Better Auth tables (`auth_user`, `auth_session`, `auth_account`, `auth_passkey`) and the Marfa tables (`spaces`, `users`, `api_keys`). Both Postgres and SQLite work; multi-space production should use Postgres.

## Sign-up payload

```json
POST /auth/sign-up/email
{
  "email": "user@example.com",
  "password": "<at least 8 chars>",
  "name": "Optional display name"
}
```

The response returns the new user and a session object:

```json
{
  "user": { "id": "...", "email": "user@example.com", "name": "..." },
  "session": { "token": "...", "expiresAt": "..." }
}
```

When email verification is on — the case whenever a real email backend is configured — the account starts unverified: `session.token` is null and no session cookie is set. The user confirms the address before a session lands. Instances without an email backend skip verification and sign new accounts in directly, with `session.token` populated. This is deliberate: a self-host with no email backend (`MARFA_EMAIL_BACKEND=none`, the default) never locks its first admin out of sign-in.

The server creates a space transactionally with the user on every sign-up, so a new account always owns exactly one space. There is no separate space-provisioning step.

### Federated sign-up (OIDC)

Set `MARFA_OIDC_PROVIDERS` to a JSON array of provider configs and Better Auth surfaces "Sign in with `<providerId>`" on the sign-in page. Each entry:

```json
{
  "providerId": "google",
  "clientId": "...",
  "clientSecret": "...",
  "discoveryUrl": "https://accounts.google.com/.well-known/openid-configuration",
  "scopes": ["openid", "email", "profile"]
}
```

Successful federated sign-in creates the same user + space shape; OIDC `sub` claim is recorded in `auth_account` for subsequent matching.

## Space model

One space per user. A user signing up always owns exactly one space; users who want separate personal and work spaces sign up with different email addresses. Spaces are isolated — there is no cross-space sharing. See [Spaces](/guides/identity/spaces).

## API keys in hosted mode

Better Auth session cookies authenticate browser callers in the `/auth/*` zone. They do not authenticate the data plane: `/items`, `/keys`, and the rest are bearer-only and reject the session cookie with a 401. A new user reaches their first bearer credential through one of two self-serve paths:

- **Web console.** After sign-up and email verification, a signed-in user opens `/auth/keys` (cookie-authenticated) and creates a long-lived `marfa_k1_` key. The plaintext is shown once on that page.
- **Device flow.** `marfa auth login` runs the OAuth device flow and stores a `marfa_at_` token for CLI and SDK use. See [Authentication](/api-reference/authentication#device-authorization-grant).

Once a credential is in hand, the CLI (`marfa keys create`) and the SDK's `client.keys.*` surface mint further keys the same way they do in `keys` mode.

For third-party app integration, the user goes through OAuth Authorization-Code + PKCE rather than handing over a static key — see [Authentication](/api-reference/authentication#oauth-21).

## Operating a hosted deployment

Beyond `AUTH_MODE=hosted`, the additional operational requirements are:

- **TLS everywhere.** Sign-up posts credentials; HTTPS is non-optional. Set `ENABLE_HSTS=true` behind a TLS terminator.
- **Durable Postgres.** SQLite is viable for single-instance hosted but multi-user contention and multi-instance deployment quickly argue for Postgres. Configure `DB_DIALECT=pg` and `DATABASE_URL`.
- **Rate limit `/auth/sign-up/email`, `/auth/sign-in/email`, and `/auth/oauth2/token`.** The per-credential rate limiter doesn't help on unauthenticated routes. Tighten these at the reverse proxy or upstream gateway to guard against enumeration and credential-stuffing.
- **Email transport configured.** Sign-up verification, forgot-password, and account-deletion confirmation all require working email. See `MARFA_EMAIL_BACKEND` in [Configuration](/self-hosting/run/configuration). Unconfigured email returns a clean `503 email_transport_not_configured` from the affected routes.
- **Blob storage reachable from every instance.** Hosted deployments usually run behind a load balancer; use `BLOB_BACKEND=s3` rather than filesystem to avoid per-host divergence.

See [Configuration](/self-hosting/run/configuration) for the full variable set and [Account lifecycle](/self-hosting/operate/account-lifecycle) for the user-initiated deletion flow that hosted mode enables.
