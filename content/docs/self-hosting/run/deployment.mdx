This page covers getting a Marfa server onto a host and keeping it running: the deploy script, database migrations, running Marfa as a supervised service, and the operational concerns around it — reverse proxy, log rotation, and health monitoring.

For the full environment-variable reference, see [Configuration](/self-hosting/run/configuration).

<Callout type="warn">
  **Run one server process per database.** The event bus is in-process: a process
  only sees the change events it published itself. Start a second process against
  the same database and realtime subscribers stop seeing most writes, and installed
  integrations stop firing for most writes. Neither failure logs anything, and the
  health endpoint stays green. Scale vertically until the bus grows a cross-process
  transport. [Running more than one
  process](/guides/identity/deployment-modes#running-more-than-one-process) has the
  detail, including which subsystems are genuinely cluster-safe.
</Callout>

## Prerequisites

- A host you can reach over SSH.
- A clone of the repository on the host — the deploy script pulls into it.
- `pnpm` installed on the host.
- Postgres, if you run the `pg` dialect (recommended for multi-space or multi-app deployments). SQLite needs nothing extra.

## The deploy script

`deploy.sh` at the repository root deploys over SSH: it pulls the target branch into the source tree, builds, runs migrations, restarts the service(s), and health-checks each one. It is entirely environment-driven — nothing host-specific is baked in.

```bash
./deploy.sh                # deploy the latest main
./deploy.sh --rollback     # roll back to the previous SHA
./deploy.sh --host myhost  # override the SSH host
```

### Configuration

All inputs come from the environment:

| Variable | Purpose |
|---|---|
| `DEPLOY_HOST` | SSH host. Required — or pass `--host`. |
| `SERVICE_DIR` | Source tree on the host (default `$HOME/marfa`). |
| `REPO_BRANCH` | Branch to deploy (default `main`). |
| `DEPLOY_SERVICE_NAMES` | Comma-separated service names. |
| `DEPLOY_SERVICE_LABELS` | Comma-separated service-manager labels, one per service. |
| `DEPLOY_SERVICE_PORTS` | Comma-separated health-check ports, one per service. |
| `DEPLOY_SERVICE_DB_URLS` | Comma-separated Postgres URLs, one per service — the migration targets. |

The four `DEPLOY_SERVICE_*` lists are parallel: the Nth entry of each describes the same service. Most deployments run a single service. The list form lets one source tree drive several instances — for example a primary instance alongside a [conformance](/self-hosting/operate/conformance) instance — from a single deploy.

### What a deploy does

1. Pulls `REPO_BRANCH` into `SERVICE_DIR` on the host.
2. Runs `pnpm install --frozen-lockfile && pnpm build`.
3. Runs `pnpm --filter @withmarfa/server migrate` against each service's database.
4. Writes a `version.json` recording the current and previous commit SHA.
5. Restarts each service and polls its `/health` endpoint.

<Callout type="warn">
  **Migrations are forward-only.** `--rollback` reverts the source tree to the previous SHA but does not undo schema changes. If a rollback also has to undo a migration, that is a manual operator step.
</Callout>

### Migrations that rewrite whole tables

Most migrations are additive and effectively instant. Occasionally one changes how a column is stored — item content, for example, lives in the database's native structured JSON type (`jsonb` on Postgres, the binary JSON encoding on SQLite), and the migration that established that rewrote every row. What a rewrite means differs by dialect:

- **Postgres** holds an exclusive lock on the table for the duration of the rewrite. Writes queue behind it; at personal-scale data sizes the pause is well under a second, and it grows with row count.
- **SQLite** rebuilds the table in place (create, copy, swap). The database file briefly holds both copies, so allow free disk roughly equal to the table's size.

On a hosted deployment none of this needs operator action — migrations run before the new build serves traffic. Self-hosted, the same is true when `deploy.sh` or `pnpm --filter @withmarfa/server migrate` runs them: the pause happens then, not at first request. A pre-upgrade backup (or a filesystem snapshot of the SQLite file) is cheap insurance either way.

## Running Marfa as a service

Run the server under a process supervisor so it restarts on crash and on boot — `launchd` on macOS, `systemd` on Linux. The supervisor:

- Sets the environment (see [Configuration](/self-hosting/run/configuration)).
- Sets the working directory to the source tree.
- Restarts the process if it exits.
- Redirects stdout and stderr to log files.

`deploy.sh` restarts services by the labels passed in `DEPLOY_SERVICE_LABELS`, so those must match the supervisor's unit/label names.

## Run exactly one server process per database

<Callout type="warn">
  **Marfa does not currently support running more than one server process against the same database.** A second process does not fail, log, or error — it silently drops realtime events. Scale vertically (a bigger host) rather than horizontally until cross-process event distribution ships.
</Callout>

Realtime delivery is process-local. Server-Sent Events and outbound webhook dispatch are both distributed through an in-process event emitter, which means every subscriber has to live in the same process as the write that triggered it.

With two processes behind a load balancer, a write handled by process A publishes only inside process A. An SSE client connected to process B never receives it. A webhook whose delivery worker happens to be running in process B never fires.

What makes this worth a warning rather than a footnote is how it fails:

- The write **succeeds**. The API returns `200`.
- **Nothing** is logged as an error, on either process.
- **Nothing** retries — the delivery was never attempted, so there is no failure to back off from.
- The events that do arrive look completely normal, so the gap is invisible until someone notices a webhook that should have fired and didn't.

This affects any topology running multiple processes against one database: a load balancer over several hosts, Kubernetes replicas, `docker compose up --scale`, a Node cluster, or PM2 in cluster mode.

### Telling the server about your topology

The server warns at startup when it can tell it is one of several processes. It detects Node cluster workers and PM2 workers on its own, but a container orchestrator looks exactly like a single process from the inside — Kubernetes, Compose, and ECS expose nothing the process can read.

Set `MARFA_REPLICA_COUNT` so the check works in those environments:

```bash
MARFA_REPLICA_COUNT=3
```

It is purely declarative and changes no behavior. It exists so the warning can fire where detection is otherwise impossible. **A startup with no warning means nothing was detected, not that your deployment was verified safe.**

### If you need more capacity

Until cross-process distribution ships, the supported paths are a larger single instance, or a second instance backed by its own database serving a different set of spaces. Putting a read-only replica alongside the writer is also safe, provided nothing subscribes to events through it.

## Reverse proxy

Marfa serves plain HTTP. Put a reverse proxy in front of it for TLS termination and a stable hostname. [Caddy](https://caddyserver.com) is a good fit — it provisions and renews Let's Encrypt certificates automatically:

```
marfa.example.com {
    reverse_proxy localhost:8600
}
```

When Marfa runs behind a TLS-terminating proxy, set `ENABLE_HSTS=true` so it emits a `Strict-Transport-Security` header. If the proxy needs its `X-Forwarded-For` header trusted, set `TRUSTED_PROXY_CIDRS` to the proxy's address range — see [Configuration](/self-hosting/run/configuration).

## Log rotation

The server logs structured JSON to stdout and stderr, one object per line. The supervisor redirects those to files, which grow unbounded without rotation.

Any standard rotation tool works — `newsyslog` on macOS, `logrotate` on Linux. On macOS, `newsyslog` renames the log; a supervisor-held descriptor continues writing to the old inode until restart. Compression can then leave that inode unlinked but open. Restart the service after rotation so it opens the current log file. Rotated JSON stays parseable with `jq`.

## Health monitoring

Every Marfa server exposes `GET /health`, returning a JSON report of the server and its dependencies:

```json
{
  "status": "ok",
  "auth_mode": "hosted",
  "components": {
    "database": { "status": "ok", "latency_ms": 77 },
    "blob_storage": { "status": "ok", "latency_ms": 67 },
    "dead_letters": { "status": "ok", "count": 0, "oldest_failed_at": null }
  },
  "database_connections": {
    "total": 9,
    "ceiling": 22,
    "max_connections": 25,
    "reserved": 3,
    "clients": {
      "marfa-web:app": { "active": 1, "idle": 2 },
      "marfa-web:session": { "idle": 1 },
      "marfa-worker:app": { "idle": 2 },
      "other": { "idle": 3 }
    }
  },
  "placement": { "region": "lon1", "location": "London", "country": "GB" },
  "version": { "sha": "677ab4a" }
}
```

<Callout type="warn">
  The status code is always `200`, including when a component is down. Degradation
  is reported in the body's top-level `status` field, which flips to `degraded`.
  A monitor that checks the status code, or greps the body for the substring `ok`,
  passes on a server whose database is unreachable — the healthy components still
  carry the word. Assert on the parsed field.
</Callout>

Each component reports one of three statuses, and the difference between the
two unhealthy ones is what tells you where to look:

| Status | Meaning |
|---|---|
| `ok` | The probe answered, and `latency_ms` says how quickly. |
| `down` | The probe answered with a failure — the database refused the connection, object storage returned an error. `error` carries the message. |
| `degraded` | The probe did not answer within its budget. Nothing has necessarily failed; the server could not find out in time. |

Probes are bounded so that this endpoint always answers. Both the database
and blob-storage checks can block indefinitely by nature — the database probe
waits for a connection-pool slot, and the blob probe is a network round trip —
so an unbounded check turns the one endpoint whose job is to report the
server's state into the one that cannot. A `degraded` database component most
often means the connection pool is fully held, which is worth knowing as
itself rather than as a timeout at the monitor.

### Dispatches that gave up

`dead_letters` reports integration dispatches that exhausted their retries and
stopped. A non-zero `count` sets the component to `degraded` and the top-level
`status` with it, so a monitor watching one field sees it.

```json
"dead_letters": {
  "status": "degraded",
  "count": 2,
  "oldest_failed_at": "2026-08-20T13:39:39.925Z",
  "connection_ids": ["01a01ef6-fb73-7c70-8cce-4dc9d02ff14d"],
  "error": "2 dispatches gave up and reached nobody; replay or discard through the dead-letter route"
}
```

`connection_ids` names the affected connections, up to ten, so the response
that says something is wrong also says where to look. `count` is exact
regardless of that cap.

**It stays degraded until somebody acts on it.** A dead letter is an
unresolved failure and no amount of elapsed time makes it not one, so the
component clears when the jobs are replayed or discarded through
`POST /admin/runtime/dead-letters/{id}/replay` and not before.

This exists because the failure was previously honest in one place and
invisible everywhere else: the dispatch was recorded on an admin route, while
the connection that dropped the work went on reporting itself healthy and
every liveness check stayed green. A captured email sat dropped for two days
that way.

The component is **absent entirely** on a deployment with no local integration
substrate, which has no dispatch queue, and absent rather than zero when the
probe cannot answer. A zero would be a claim that nothing has failed, made by
a check that could not find out.

### Connection usage

`database_connections` reports how much of the database's connection ceiling
this deployment is holding, read from Postgres's own `pg_stat_activity` rather
than from the driver. It sees every connection to the database whatever opened
it, so one server's `/health` reports the whole deployment — a web process, a
worker process and your own `psql` session all appear in the same `total` that
is racing `ceiling`.

`ceiling` is the number `total` is actually racing: `max_connections` less the slots `superuser_reserved_connections` holds back, which an ordinary client can never reach. The two raw figures are reported alongside it, so the arithmetic is visible rather than something you have to trust. On a managed tier the difference matters — a cluster advertising 25 while reserving 3 gives you 22, and a monitor alerting at 90% of 25 fires after exhaustion rather than before it.

`clients` attributes those connections. Marfa's own pools are named
`marfa-<role>:<pool>`, where the pool is `app` (queries), `session` (streaming
reservations) or `lock` (the coordination lock). Everything else is folded into
`other`. The counts under each are Postgres backend states, so `idle` means a
pooled connection open but unused, not a leak.

Two things to know before you alert on it:

- **The reading is omitted, not zeroed, when it cannot be taken.** A pool held
  hard enough to starve the query has already turned the `database` component
  `degraded`, which is what an uptime check watches. This block is for seeing
  the number climb toward the ceiling beforehand.
- **Attribution needs the right privileges.** A role that is not a superuser and
  not a member of `pg_read_all_stats` can only read the application name and
  state of backends belonging to itself, so connections opened by other roles
  land in `other`. `total` is correct either way.

The block is absent on SQLite, which has neither a pool nor the view to read.

### Placement

`placement` says where this server runs. It is optional, absent when unset, and
built from three variables you set per environment:

| Variable | Example |
|---|---|
| `MARFA_PLACEMENT_REGION` | `lon1` |
| `MARFA_PLACEMENT_LOCATION` | `London` |
| `MARFA_PLACEMENT_COUNTRY` | `GB` |

Set them to whatever describes the location; nothing here is provider-specific.
It is worth the two minutes: a server running far from its database produces no
error, no failed deploy and no degraded status, only latency that the database
then gets blamed for. This is the field that says so.

Point an uptime monitor at it:

| Check | Value |
|---|---|
| Endpoint | `http://<host>:<port>/health` |
| Expect | HTTP 200 **and** the parsed `status` field equal to `ok` |
| Interval | 60 seconds is a reasonable default |

For 500-error alerting, set `ERROR_WEBHOOK_URL` to a webhook — a chat incoming-webhook, or an uptime tool's push URL. The server debounces to at most one notification per error type per minute; tune the delivery timeout with `MARFA_ERROR_WEBHOOK_TIMEOUT_MS`.
