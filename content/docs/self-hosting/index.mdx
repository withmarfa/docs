Self-hosting means running the Marfa server yourself instead of building against a hosted instance. The smallest working server runs against SQLite on disk with filesystem blobs, no external dependencies, brought up by a single required environment variable. From there you scale up to Postgres, S3-compatible blobs, and multi-tenant hosted mode as the deployment demands.

<Callout type="info">
  Want the fastest path to a running server? The [Quickstart (self-hosted)](/introduction/quickstart-self-hosted) takes you from a clone to your first item in a few minutes. This section is the operational reference around it.
</Callout>

## What it involves

Running your own instance breaks into three concerns:

- **Getting a server up.** Clone, build, set `API_KEY_SALT`, and run. Zero-config defaults give you a working single-tenant instance on SQLite. The [quickstart](/introduction/quickstart-self-hosted) walks the minimal path end to end.
- **Configuring it.** The server is configured entirely through environment variables — database dialect, blob backend, auth mode, rate limits, CORS, TLS headers. Local-dev is zero-config; production swaps in Postgres and object storage.
- **Operating it.** Deploying over SSH, running behind a reverse proxy, monitoring health, and the operator surfaces — account lifecycle, the platform-admin command tree, and conformance testing your instance against the spec.

<Callout type="warn">
  **One server process per database.** The event bus lives in the server process,
  so a second process against the same database silently stops delivering realtime
  events and stops firing installed integrations. Plan for vertical scaling. The
  constraint and its exact blast radius are in [Running more than one
  process](/guides/identity/deployment-modes#running-more-than-one-process).
</Callout>
