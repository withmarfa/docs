The Readwise Reader connector keeps the documents, highlights and annotations of a Reader library in the feed, with a copy of their content, and carries supported edits back to Reader. The [Readwise connector](/catalog/connectors/readwise) works without it, and the two share items.

**Its key's own source is `readwise-reader`, and it claims `readwise`**, so the items it writes carry `readwise`, and it and the Readwise connector keep separate progress.

## What it brings in

- **Documents** in your saved library. Feed documents are left out unless you set `READWISE_READER_INCLUDE_FEED`.
- **Highlights and annotations** on those documents. A note record is folded into the annotation. A highlight's `body` is the export passage as Markdown, or Reader's own passage where there is no export passage or Readwise cut it at 8,191 characters. Its `title` is the passage's first paragraph, and a passage with only a picture is titled after its document.
- **Content.** A copy of each document's HTML, its original file where there is one, Readwise-hosted images, text too long for a field, and a manifest of what was kept, pending or unavailable. Content comes only from Readwise's asset storage host, and no API credentials go to it.
- **Pictures from other websites,** only if you set `READWISE_READER_PICTURES` ([Saving pictures](#saving-pictures)).

Each run reads what changed since the last, with a five-minute overlap, and a full reconciliation runs daily.

## Types it writes

| Type | Parent type | Holds |
| --- | --- | --- |
| `readwise.source` | [Media](/catalog/media) | A Reader document |
| `readwise.highlight` | [Highlight](/catalog/highlight) | A highlight with its annotation and tags |
| `readwise.file` | [File](/catalog/file) | Kept content or a saved picture |

These are the Readwise connector's types, with the same [field kinds](/catalog/connectors/readwise#types-it-writes), so one item can hold what both connectors know. An item Reader manages carries a Reader link, `<account>:reader-document:<ID>` or `<account>:reader-highlight:<ID>`, in `canonical_key`.

## Edges it writes

| Edge type | From | To |
| --- | --- | --- |
| [`excerpt-of`](/catalog/edges/excerpt-of) | A highlight | Its document |
| [`attached-to`](/catalog/edges/attached-to) | A file | The document or highlight it belongs to |

Moving a document or highlight to the bin takes its files with it, and restoring it brings them back. **It writes no `references` edges**, and clears any it wrote before `excerpt-of` took their place, so its key keeps write on `references`.

## What goes back

Unless `READWISE_READER_INBOUND_ONLY` is set:

- **Document edits.** The title, author, summary (`description`), notes, tags, reading location (`reader_location`) and supported categories.
- **Highlight edits.** The annotation (`note`) and tags. An empty note or tag list clears them.
- **A new item.** Set `reader_create: true` and your `account` label on a `readwise.source` that has a stable HTTP URL, or on a `readwise.highlight` that has `reader_parent_id` and passage text. An item without that flag is never created in Reader.
- **Archive and restore.** Archiving a `readwise.source` item moves its document to Reader's archive, and restoring it moves the document to `later`.

Only changed supported fields are sent. The body, a passage, a highlight's `title` and `body`, reading progress and an original file stay read only. Moving an item to the bin changes nothing in Reader, and a purge deletes the Reader record only with `READWISE_READER_PROPAGATE_PURGE`.

## Archive in both places

Reader's archive and an item's `archived` [state](/build/items-and-types#an-items-life) mean the same thing: finished with, but kept. A document whose `reader_location` is `archive` is `archived` in Marfa, and one moved out of Reader's archive is `active` again. Highlights and pictures stay active when their document is archived. When both sides change in one run, the later change wins.

A document that disappeared from Reader is archived too, but its `reader_location` isn't `archive`.

## Saving pictures

`READWISE_READER_PICTURES` decides what happens to pictures a document's HTML shows from other websites. Pictures on Readwise's own storage are always kept.

| Value | What happens |
| --- | --- |
| `addresses` (the default) | Nothing is fetched. The manifest lists each picture as not kept, with the reason `third-party`. |
| `save` | The pictures of every document are saved. |
| `save-in-library` | Pictures are saved only for documents whose item is in the [library](/build/items-and-types#library-and-feed). |

A picture is the address in an `img` element's `src`, or its `data-src`, or the document's cover `image_url`; the HTML isn't changed. A saved picture is a `readwise.file` with `resource_kind` `picture` and its `source_url`, with an `attached-to` edge to its document.

Picture work runs after the content in each scheduled run, so it never holds a document up. A run fetches at most 100 pictures and 200 MiB, from at most 25 documents, and reaching a limit raises `readwise:reader-pictures-limit`; the next run carries on. One failed picture never fails its document or the run. The [README](https://github.com/withmarfa/marfa-connectors/blob/main/connectors/readwise-reader/README.md#pictures-from-other-websites) lists every reason a picture is not kept and the retry rules.

## Settings

| Setting | What it holds |
| --- | --- |
| `READWISE_ACCESS_TOKEN` | Your Readwise access token. A secret. |
| `READWISE_ACCOUNT` | The same stable account label as the Readwise connector. Required. |
| `READWISE_READER_INCLUDE_FEED` | `true` includes feed documents. The default is `false`. |
| `READWISE_READER_INBOUND_ONLY` | `true` turns off every edit going back. The default is `false`. |
| `READWISE_READER_PROPAGATE_PURGE` | `true` lets a purge in Marfa delete the Reader record. The default is `false`. |
| `READWISE_CONTENT_MAX_BYTES` | The largest resource to keep, in bytes, up to 1,073,741,824. The default is 268,435,456 (256 MiB). |
| `READWISE_READER_PICTURES` | `addresses`, `save` or `save-in-library`. Any other value stops the connector at start. |

## What to know

- **Use one account label in both connectors.** Never change it against saved progress.
- **Purges are capped.** With `READWISE_READER_PROPAGATE_PURGE` on, a run that would delete more than 20 Reader records fails before it reads or sends anything, until the count is 20 or fewer or you turn propagation off.
- **A disappearance needs proof.** A failed request or an incomplete listing never archives an item. More than 20 confirmed disappearances in one run archive none.
- **Over-limit content stays pending.** A resource larger than `READWISE_CONTENT_MAX_BYTES` keeps its last good copy and reports the limit.

## Make its key

Granting a key another source's claim needs `keys.manage` and `keys.mint`, which the CLI with Full access holds. Make the [Readwise key](/catalog/connectors/readwise#make-its-key) first if you run both.

```bash
marfa keys create --label readwise-reader \
  --source readwise-reader --claim readwise \
  --type-permission readwise.source=write \
  --type-permission readwise.highlight=write \
  --type-permission readwise.file=write \
  --edge-permission excerpt-of=write \
  --edge-permission references=write \
  --edge-permission attached-to=write \
  --metadata-permission types=write \
  --default-tier feed
```

Saving pictures needs no other permission. The contract sets out claims in [Claimed sources](https://github.com/withmarfa/marfa/blob/main/conformance/spec/keys-and-oauth.md#keys-and-oauthclaims-direct).

## Run it

[Bring in records from another service](/use/connect-a-service) builds and runs any connector, and [Connectors](/build/connectors) explains how they work.

```bash
node connectors/readwise-reader/dist/main.js --once
node connectors/readwise-reader/dist/main.js --every 15m
```
