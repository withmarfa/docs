title: Fix a folder that won't open or sync
sidebar_label: Fix a folder
description: Find the message a synced folder shows when it won't open, stops syncing or leaves a file behind, and fix it.
job: Someone whose folder refuses to open, stops syncing or leaves a file behind finds the message they see and fixes it.
---

Find the message you see. `marfa folders status ~/Home` lists every file that isn't in step, and why. [Sync a folder](/use/sync-a-folder) sets a folder up, and [How a folder treats files](/folder-rules) has every rule it follows.

## Edits stop arriving, or the watch stopped

The watch writes to `folder-watch.log`, beside `folders.json` in `~/Library/Application Support/Marfa` on a Mac, and `marfa folders autostart status` says where. **The last line says what stopped it,** such as a signal, with the time. An error from before the log opened goes to `folder-watch.launchd.log` beside it on a Mac, and on Linux to the user journal:

```bash
journalctl --user -u marfa-folder-watch.service
```

## is being worked by another process

Another process, usually a running watch, is working the folder, and one process works a folder at a time. Stop the other process, or let it finish, and run the command again.

## is held by another process, which did not let it go

A command asked the watch for the folder, and the watch didn't let it go within 10 seconds, because it's busy or stuck. **The command changed nothing:** run it again. If it keeps happening, restart the watch: `marfa folders autostart off`, then `on`.

## the server asked for a wait before the next drain

Your instance is [limiting requests](/use/limits), such as during the first sync of a large directory. **Nothing is lost:** the push stops sending and keeps the rest.

```text
the server asked for 60s before the next drain; push again after that to send the rest
```

Wait that long and run `marfa folders push` again. A running watch waits by itself and carries on.

## wrong_schema on a folder's store

A newer CLI can't open a store that another build made.

- **If no edits wait to be sent,** the next push, pull, scan or watch replaces the store and changes no file.
- **If edits wait,** push the folder with the build that made the store, then use the newer build.
- **If the CLI can't tell,** push with the earlier build, run `marfa folders remove`, which leaves the files, and add the folder again with the newer build.

## is left as written: matches more than one item

A link in the note names more than one item, so Marfa connects it to none and doesn't rewrite the file. The rest of the note still syncs.

```text
Route.md is left as written: [[Packing|the list]] in its body matches more than one item; name one by its id, [[<id>]]
```

Rename one of the items, move one to the bin, or write the link with the item's ID.

## links by name wait, since the server has no title lookup

Your instance is older than the CLI and can't look up items by title, so **the links and edge lines that name items wait.** The files are kept and their items made. [Upgrade the instance](/run/upgrade), and the next scan connects every link that waited.

## A file is in step, but an edge or an attachment is missing

- **`the folder's default <edge> edge to <id> was not applied`:** the folder's `defaults` asked for an edge the item can't take, such as to a collection in the bin. Restore the collection, write the edge's line in the note, or take it out of `defaults`.
- **`its attached file <id> cannot be read`:** your instance refused to show a file attached to the note. Each later pull asks again. Run `marfa items get <id>` to see why.
