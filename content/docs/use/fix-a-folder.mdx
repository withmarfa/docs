---
title: Fix a folder that won't open or sync
sidebar_label: Fix a folder
description: Find the message a synced folder shows when it stops syncing, holds a change for you or leaves a file out, and fix it.
job: Someone whose synced folder is out of step finds the message they see and fixes it.
---

Start with `marfa folders autostart status`, which says whether the watch runs and why a folder isn't watched. Then `marfa folders status ~/Documents/Home` lists each file that isn't in step, and why. Find the message you see below.

## Edits stop arriving

Read what `marfa folders autostart status` says:

- **`folders do not sync`:** autostart is off, so run `marfa folders autostart on`.
- **`the watch is not running`:** the end of the log named on the `it logs to` line says why. On Linux, see also `journalctl --user -u marfa-folder-watch.service`.
- **`not watched`,** after a directory: the words in brackets say why, such as a first sync that waits for `marfa folders confirm`, or a pause that `marfa folders resume` ends.

## a large addition waits

```text
a large addition waits: 55 new file(s) held, not sent; `folders confirm` sends them, and deleting the files you did not mean to add cancels it; new files that arrive meanwhile join it
```

A large addition is more than 50 new files that are also more than a quarter of the folder's files. The rest of the folder goes on syncing. Delete the files you didn't mean to add, then run `marfa folders confirm ~/Documents/Home`, and the next push sends the rest. Deleting every held file cancels the addition.

## a large removal waits

```text
a large removal waits: 50 delete(s) not sent; `folders confirm` sends them, `folders restore` writes the files back
```

A large removal is more than 100 files, or more than 10 that are over a quarter of the folder's files. **Nothing is deleted yet.** Run `marfa folders restore ~/Documents/Home` to get the files back, or `marfa folders confirm ~/Documents/Home` to bin their items at the next push. Renamed or moved files keep their items. A file `confirm` can't check, such as one in an unreadable folder, stays and shows `not let go yet`: confirm again once it's readable.

## not taken

```text
scan.pdf: not taken, it is empty, and a file item holds bytes
```

`marfa folders status` names each file the folder leaves out, and why: the file is empty, its name is one a secret goes by, or the folder's query holds no type the file would be, such as a PDF in a folder of notes. Add the file's contents, rename it, or [widen the query](/use/change-or-stop-a-folder#hold-only-some-items).

## another process is working this directory

One process works a directory at a time. A running watch lets a directory go when a command asks, so this usually means two watches: autostart's and one you started by hand. Stop the one you started, with Control+C.

If a command says a directory `is held by another process, which did not let it go`, it changed nothing: run it again.

## the server asked for a wait before more is sent

```text
the server asked for 60s before more is sent; push again after that to send the rest
```

Your instance is [limiting requests](/use/limits), such as during the first sync of a large directory. **Nothing is lost.** Wait that long and push again. A running watch waits by itself.

## now answers as another Marfa instance

A new instance took the folder's address, such as after a restore into a new install. The watch stops this folder alone. [Sign the CLI in to the new instance](/run/back-up-and-restore#on-each-device), then remove the directory and add it again with the folder's ID, which a restore keeps:

```bash
marfa folders remove ~/Documents/Home
marfa folders add ~/Documents/Home --folder 01a1f46f-bed0-7310-bb7c-840868eb64ac
```

**If `remove` is refused because edits wait to be sent,** the new instance will never take them: [Bring back a directory's unsent edits](/run/back-up-and-restore#bring-back-a-directorys-unsent-edits) keeps them.

If the folder's own instance answers there again, autostart's watch syncs it again within the hour.

## was made by another build of marfa

A CLI can't open a directory's saved state that another build of `marfa` made, and the message names the release that last saved it. If the state holds nothing still to send, the next push, pull, scan or watch replaces it and changes no file. Otherwise the CLI leaves the directory alone: install that release with the install script and `MARFA_VERSION=<release>`, push the directory with it, and this build then replaces the state.
